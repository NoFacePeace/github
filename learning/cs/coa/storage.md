# 存储

## 1. HDD 和 SSD

### 1.1 HDD 的含义

HDD（Hard Disk Drive，硬盘驱动器），通常称为机械硬盘，通过磁性盘片保存数据，使用磁头读写。

访问数据时，需要将磁头移动到对应磁道（寻道），再等待目标扇区旋转到磁头下方，最后传输数据。因此，HDD 的访问时间不仅取决于数据大小，还受寻道、旋转等待和请求排队影响。

- **顺序访问**：连续读写相邻位置的数据，减少磁头移动，较容易获得较高吞吐量。
- **随机访问**：读写分散位置的数据，频繁寻道和旋转等待，小块请求也可能耗费较长时间。

例如，7200 RPM 表示盘片每分钟旋转 7200 圈，一圈约需 8.33 ms，平均旋转等待约为半圈，即 4.17 ms。这只是旋转等待，不是完整 I/O 延迟，还没有计入寻道、传输和排队时间。

### 1.2 SSD 的含义

SSD（Solid State Drive，固态硬盘），通常使用 NAND 闪存保存数据，由控制器管理数据读写，没有旋转盘片和移动磁头。

SSD 不需要机械寻道和旋转等待，因此在随机访问和低延迟场景中通常比 HDD 更有优势。但 SSD 也有性能限制：闪存需要按页读写、按块擦除，控制器还需要进行垃圾回收和磨损均衡。这些机制，以及缓存、剩余空间和并发负载，都会影响写入性能。

SSD 的短时写入速度可能受缓存加速，持续写入时不一定能保持相同速度。

### 1.3 HDD 与 SSD 对比

| 对比项 | HDD（机械硬盘） | SSD（固态硬盘） |
|---|---|---|
| 存储介质 | 磁性盘片 | 通常为 NAND 闪存 |
| 机械运动 | 盘片旋转、磁头移动 | 无机械运动部件 |
| 随机访问 | 受寻道和旋转等待影响较大 | 无机械寻道，通常更快 |
| 顺序访问 | 连续访问可减少寻道，吞吐量明显优于随机小块访问 | 通常具有较高吞吐量，受接口、控制器和闪存能力限制 |
| 访问延迟 | 访问盘片通常为毫秒级，排队时可能显著增加 | 轻载下通常为微秒至亚毫秒级，繁忙或后台整理时也可能升至毫秒级以上 |
| IOPS | 随机小块 IOPS 相对较低 | 随机小块 IOPS 通常明显更高 |
| 单位容量成本 | 通常较低 | 通常较高 |
| 噪声和振动 | 存在机械噪声和振动 | 无机械噪声 |
| 抗冲击能力 | 工作中的机械部件对冲击较敏感 | 通常更耐冲击，但并非不会损坏 |
| 寿命影响因素 | 机械磨损、温度、振动及工作负载等 | 闪存写入磨损、写放大、温度及工作负载等 |
| 常见用途 | 大容量存储、备份、归档、顺序读写 | 系统盘、数据库、随机访问和延迟敏感应用 |

表中描述的是一般特征，不能代替具体型号的规格和实测。接口、请求大小、读写模式、并发深度、缓存和是否要求持久化，都会影响结果。

### 1.4 区分介质与接口

HDD、SSD 描述存储设备类别；SATA、SAS、PCIe 和 NVMe 涉及连接方式或协议，不是同一层次的分类。

- HDD 和 SSD 都可以使用 SATA 或 SAS。
- NVMe 是面向非易失性存储的协议，本地 NVMe SSD 通常通过 PCIe 连接。
- M.2 是外形与连接规格，不能仅凭 M.2 就认定设备使用 NVMe；也存在 SATA M.2 SSD。

### 1.5 结合性能指标理解

| 指标 | 含义 | 对比时需要注意 |
|---|---|---|
| IOPS | 每秒完成的 I/O 操作数 | 必须结合请求大小、随机或顺序、读写比例和并发深度 |
| 吞吐量 | 每秒传输的数据量 | 吞吐量约等于 IOPS × 平均请求大小，统计范围和单位需一致 |
| 延迟 | 一次请求从开始到完成的耗时 | 区分平均值和 P95、P99，以及应用层、块层和持久化操作的测量口径 |
| 未完成 I/O 数量 | 已提交但尚未完成的请求数 | 同时包含处理中的请求和排队请求，增加并发可能提高吞吐，也可能增加等待 |

HDD 在大量随机小块请求下，即使吞吐量不高，也可能已经出现明显排队；SSD 即使没有机械部件，也可能因为写入压力、垃圾回收或接口限制而出现延迟上升。

Linux 主机的采集指标和查询方式见 [Node exporter：常用指标和 PromQL](../infrastructure/prometheus/node-exporter.md)。

## 2. RAID

### 2.1 RAID 的含义

RAID（Redundant Array of Independent Disks，独立磁盘冗余阵列）是一种组织多块磁盘的技术，用于提高容量、并行读写性能或故障容忍能力。不同级别的目标不同，RAID 0 就不提供冗余。

RAID 不限于机械硬盘，HDD 和 SSD 都可以组成 RAID。它也不完全属于硬件，可以由专用控制器实现，也可以由操作系统实现。

| 基本机制 | 工作方式 | 作用 |
|---|---|---|
| 条带化（Striping） | 将数据分块分布到多块盘 | 利用多盘并行读写 |
| 镜像（Mirroring） | 将同一份数据写入多个副本 | 一份副本所在的盘故障后，仍可读取另一份 |
| 校验（Parity） | 保存根据数据计算的校验信息 | 在允许的故障范围内重建丢失数据 |

### 2.2 常见 RAID 级别

以下假设每块盘容量相同，N 为磁盘数量，S 为单盘容量；容量不计文件系统、阵列元数据等开销。

| 级别 | 常见最少盘数 | 可用容量 | 容错能力 | 性能特点 |
|---|---:|---|---|---|
| RAID 0 | 2 | N × S | 无冗余，任意一盘故障都可能导致阵列数据丢失 | 条带化提供并行能力，无镜像或校验开销 |
| RAID 1 | 2 | 两盘镜像时为 S | 两盘镜像可坏 1 块 | 写入需要更新两份副本，读取能否并行取决于实现 |
| RAID 5 | 3 | (N−1) × S | 可坏 1 块 | 分布式单校验，小块随机写可能需要读取旧数据和校验再更新 |
| RAID 6 | 4 | (N−2) × S | 可坏任意 2 块 | 分布式双校验，写入校验开销通常更大 |
| RAID 10 | 4 | N ÷ 2 × S | 每个镜像组最多坏 1 块 | 常见实现为两两镜像后条带化，兼顾并行与冗余 |

这里的 RAID 10 指常见的偶数盘、两副本结构；部分软件实现支持其他布局。RAID 10 能否承受多盘故障取决于故障位置：两块盘分属不同镜像组时可能继续运行，同一镜像组的两块盘都损坏则会丢失数据。

例如，4 块 4 TB 磁盘组成 RAID 0、RAID 5、RAID 6、RAID 10 时，可用容量分别约为 16 TB、12 TB、8 TB、8 TB。容量相同的阵列，容错规则和性能也可能不同。

### 2.3 硬件 RAID 与软件 RAID

| 实现方式 | 谁完成镜像、校验和请求分配 | 操作系统看到什么 |
|---|---|---|
| 硬件 RAID | 专用 RAID 控制器及其固件 | 通常主要看到控制器提供的逻辑盘，物理盘信息通过管理工具查看 |
| 软件 RAID | 操作系统的存储子系统 | 能管理底层磁盘，并向上层提供组合后的阵列设备 |

硬件 RAID 控制器通常是一张安装在服务器 PCIe 插槽上的 RAID 卡，也可能集成在主板上，或通过服务器专用插槽安装。卡上有处理器、固件，部分型号还带缓存及掉电保护。操作系统通过驱动向控制器发送请求。

Linux 软件 RAID 的例子是 `md` 子系统，`mdadm` 是配置和管理工具。它不需要专用 RAID 卡，但仍需要普通磁盘控制器或 HBA（主机总线适配器）来连接磁盘。

主机并非必须配备 RAID 控制器。外部存储阵列也可能将 RAID 控制器安装在存储设备中，计算主机通过存储网络访问逻辑卷。

### 2.4 RAID 控制器如何连接磁盘

以常见的 SAS/SATA RAID 卡为例，控制器通过物理数据线连接硬盘，或者连接硬盘背板后再接入多块盘。

```text
直接连接：
RAID 卡的数据接口 → SAS/SATA 线缆或分线缆 → 硬盘数据接口

通过背板连接：
主板 PCIe 插槽 → RAID 卡 → 数据线 → 硬盘背板
                                     ├── 插槽接口 → 硬盘 1
                                     ├── 插槽接口 → 硬盘 2
                                     └── 插槽接口 → 硬盘 3
```

背板是硬盘插槽后面的电路板。将硬盘装入托架并推入服务器时，硬盘尾部接口与背板上的接口接合。背板可能直接布线，也可能带 SAS 扩展器；具体连接数量和带宽取决于硬件设计。

硬盘通常由电源线或背板供电，普通 RAID 卡的数据线不负责给硬盘供电。接口、线缆、背板和控制器必须相互兼容；NVMe SSD 使用 PCIe 链路，不能假设普通 SAS/SATA RAID 卡都支持。

一次读写中，操作系统先向逻辑盘提交请求，RAID 控制器再根据阵列布局生成对具体物理盘的请求，通过线缆和背板发送。控制器何时报告写入完成，取决于回写、直写以及持久化命令等策略，不一定要等数据写入盘片。

### 2.5 操作系统能否直接使用磁盘

可以。未使用硬件 RAID 时，操作系统通过 SATA/SAS/NVMe 等驱动和硬件链路访问磁盘，自行分区、创建文件系统和挂载。

```text
普通磁盘访问：操作系统 → 驱动及磁盘控制器 → 单块磁盘
硬件 RAID：  操作系统 → RAID 驱动 → RAID 控制器的逻辑盘 → 多块物理盘
```

“直接使用”不意味着没有控制器，而是操作系统能够访问各块盘，不必先由硬件 RAID 将它们组合成逻辑盘。部分控制器提供直通或 JBOD 模式，让磁盘分别呈现给操作系统；具体行为取决于型号和配置。

### 2.6 单盘是否需要 RAID

单盘通常不需要 RAID，直接使用即可。某些硬件 RAID 控制器只向操作系统暴露配置好的逻辑盘，因此需要将单盘创建为一个 RAID 0 逻辑盘。

这种单盘 RAID 0 是设备呈现方式，没有多盘并行能力，也没有冗余保护。它可能使用控制器缓存或统一管理功能，但这些属于控制器能力，不是单盘 RAID 0 本身的收益。

| 控制器能力 | 可能的作用 | 条件或限制 |
|---|---|---|
| 写缓存 | 缓冲、合并或重排请求 | 回写缓存的安全使用需考虑掉电保护和持久化语义 |
| 统一管理 | 监控磁盘状态、告警和逻辑盘配置 | 可能需要厂商管理工具 |
| 扩容或级别迁移 | 增加磁盘、调整阵列结构 | 仅部分型号与配置支持，不能假定一定可用 |

通过 RAID 控制器使用单盘时，SMART、TRIM 等信息或命令能否透传也取决于实现。

### 2.7 SSD 组成 RAID

SSD 同样可以使用 RAID 0、1、5、6、10。容量与冗余规则不因介质改为 SSD 而改变，但性能不一定随磁盘数量成倍增长。

- RAID 控制器、PCIe 链路和接口带宽可能先成为瓶颈。
- 镜像和校验增加物理写入量，评估寿命时需考虑 SSD 耐写量与实际写放大。
- TRIM/Discard、健康状态和错误信息的支持取决于整个存储链路。
- 缓存策略、SSD 的掉电保护和应用持久化要求需要一起考虑。

### 2.8 容错、备份与性能监控

RAID 的冗余用于应对一定范围内的磁盘故障，不替代备份。误删除、软件损坏和勒索加密等问题，仍可能影响整个阵列。更换坏盘后的重建会产生额外读写，重建期间性能可能下降。

系统中一个块设备可能代表多块物理盘组成的逻辑盘。查看 IOPS、吞吐量和延迟时，应先确认监控对象是物理盘还是逻辑盘；逻辑盘性能不能直接与单块 HDD 的规格比较。

硬件 RAID 下，node_exporter 通常只能看到操作系统暴露的块设备。底层物理盘的健康、重建进度和控制器缓存状态，可能需要厂商工具或对应 exporter 额外采集。

## 3. 工具

### 3.1 fio

#### 3.1.1 简介

fio（Flexible I/O Tester）是可配置的 I/O 压测工具，可以对文件或块设备生成读写负载，测试 HDD、SSD、RAID 和云盘的性能。它支持顺序或随机访问、不同请求大小、读写比例和并发深度，并输出 IOPS、吞吐量及延迟统计。

fio 负责产生压力；`iostat`、node_exporter 和 Grafana 用于观察压测期间的存储状态。文件测试包含文件系统路径，裸块设备测试与其口径不同。

#### 3.1.2 常用参数

| 参数 | 示例 | 含义 |
|---|---|---|
| `name` | `seqwrite-1m` | 测试任务名称 |
| `filename` | `/data/fio-test/test.bin` | 测试文件或设备路径 |
| `size` | `10G` | 单个任务使用的测试范围；配合循环测试时，不限制累计写入量为 10 GiB |
| `rw` | `read`、`write` | 顺序读、顺序写 |
| `rw` | `randread`、`randwrite` | 随机读、随机写 |
| `rw`、`rwmixread` | `randrw`、`70` | 随机混合读写，其中读取占 70% |
| `bs` | `4k`、`1M` | 每次 I/O 的请求大小，分别为 4 KiB、1 MiB |
| `ioengine` | `libaio` | Linux 异步 I/O 引擎 |
| `direct` | `1` | 通常绕过操作系统页缓存，不等于每次请求都强制持久化 |
| `iodepth` | `1`、`8`、`32` | 每个任务目标保持的未完成 I/O 数量上限，实际深度受引擎和运行条件影响 |
| `numjobs` | `1` | 并行任务数量；总目标并发上限通常为 numjobs × iodepth |
| `time_based`、`runtime` | `--time_based --runtime=60` | 在指定范围内循环测试，运行约 60 秒 |
| `end_fsync` | `1` | 写阶段结束时同步文件，不等于每次写后同步 |
| `fsync` | `1` | 每完成指定数量的写 I/O 后发出 fsync；这里表示每次写后同步 |
| `group_reporting` | `--group_reporting` | 按组汇总任务结果 |

#### 3.1.3 顺序写与随机写

顺序写在逻辑地址上连续向后写；随机写在测试范围内选择位置写。每次写 4 KiB 时，可以理解为：

| 方式 | 写入偏移示意 | 特点 |
|---|---|---|
| 顺序写 | 0 → 4 KiB → 8 KiB → 12 KiB | 连续访问，HDD 通常可以减少寻道 |
| 随机写 | 80 KiB → 4 KiB → 200 KiB → 32 KiB | 访问分散位置，HDD 可能频繁寻道 |

`bs` 大小不决定是否顺序访问：`rw=randwrite --bs=1M` 仍是大块随机写。文件系统、文件碎片和 RAID 布局还可能改变最终物理访问模式。

| 测试目的 | rw | bs | iodepth 起点 |
|---|---|---|---:|
| 随机读基线 | `randread` | `4k` | 1 |
| 随机写基线 | `randwrite` | `4k` | 1 |
| 顺序读带宽 | `read` | `1M` | 1，再比较 8 |
| 顺序写带宽 | `write` | `1M` | 1，再比较 8 |
| 随机写并发压力 | `randwrite` | `4k` | 8，再比较 32 |

4 KiB 是观察小块随机访问的常见测试大小，不代表固定性能。换算关系为：

```text
吞吐量 = IOPS × 平均请求大小
4 KiB 请求：吞吐量（MiB/s）= IOPS ÷ 256
1 MiB 请求：吞吐量（MiB/s）与 IOPS 数值相同
```

例如，4 KiB、100 IOPS 对应约 0.39 MiB/s；1 MiB、100 IOPS 对应 100 MiB/s。测试必须区分请求大小，不能只比较 IOPS 或吞吐量。

#### 3.1.4 Linux 文件压测示例

下面会创建并覆盖专用测试文件，也会与业务竞争磁盘资源。使用有足够空间的目标挂载目录，不要指定已有业务文件；直接对 `/dev/sdX` 等设备做写测试会覆盖数据。

安装 fio，按发行版选择命令：

```bash
# Ubuntu / Debian
sudo apt install fio

# 已配置相应软件源的 RHEL / Rocky / Fedora
sudo dnf install fio

fio --version
```

假设 `/data` 是目标挂载目录，在同一个 shell 中执行。先完整写入 10 GiB 文件，避免后面的读取测试访问未写入区域：

```bash
df -h /data
test_dir=$(mktemp -d /data/fio-test.XXXXXX)

fio --name=prepare \
  --filename="$test_dir/test.bin" \
  --size=10G \
  --rw=write \
  --bs=1M \
  --ioengine=libaio \
  --direct=1 \
  --iodepth=1 \
  --end_fsync=1 \
  --group_reporting
```

确认准备成功后，测试 4 KiB 随机写：

```bash
fio --name=randwrite-4k \
  --filename="$test_dir/test.bin" \
  --size=10G \
  --rw=randwrite \
  --bs=4k \
  --ioengine=libaio \
  --direct=1 \
  --iodepth=1 \
  --numjobs=1 \
  --time_based \
  --runtime=60 \
  --group_reporting
```

测试大块顺序写时，将 `name` 改为 `seqwrite-1m`、`rw` 改为 `write`、`bs` 改为 `1M`，再分别比较 `iodepth=1` 和 `iodepth=8`。先保持其他参数不变，每次只调整一个条件。

10 GiB 和 60 秒用于入门，并非完整的全盘或稳态测试。较小测试范围会限制 HDD 的寻道范围，短测可能受控制器或设备缓存影响，不能直接视为长期性能。需要测试持久化写入时，应另外配置同步策略并关注同步操作的延迟；`direct=1` 本身不保证落盘。

#### 3.1.5 结果解读

| 输出项 | 含义 | 评估方法 |
|---|---|---|
| `IOPS` | 每秒完成的 I/O 数量 | 结合请求大小和读写模式比较 |
| `BW` | 数据吞吐量 | 注意 MiB/s 与 MB/s 的区别，与相同条件的基线比较 |
| `slat` | 提交延迟 | 观察请求提交阶段开销 |
| `clat` | 完成延迟 | 观察提交后到完成的耗时 |
| `lat` | 总 I/O 延迟 | 通常包含提交和完成延迟，不能直接等同于应用事务延迟 |
| `clat percentiles` | 完成延迟分位数 | P99 反映约 99% 请求不超过的延迟，关注尾部卡顿 |
| `IO depths` | 实际 I/O 深度分布 | 确认是否达到设置的并发水平 |
| 错误信息 | I/O 是否失败 | 正常完成应无 I/O 错误 |

稳定负载、相同统计边界下，可用以下关系辅助理解：

```text
平均延迟（秒）≈ 平均未完成请求数 ÷ IOPS
```

例如，1 MiB 顺序写在实际平均未完成请求数约为 1 时达到 150 IOPS，平均延迟约为 6.7 ms；并发约为 8 时达到 200 IOPS，平均延迟约为 40 ms。这是条件化计算，不是 HDD 标准阈值，设置的 iodepth 也不一定等于实际平均并发。

| 结果变化 | 分析方向 |
|---|---|
| 增加并发后吞吐量提高 | 并发可能有助于利用设备处理能力 |
| 吞吐量不再增长，延迟继续上升 | 增加的并发主要变成排队，可能已接近当前负载下的瓶颈 |
| 与同条件基线相比吞吐下降、延迟上升 | 排查业务干扰、设备状态、缓存策略和后台操作 |
| 开始很快，随后长期下降 | 检查缓存耗尽、后台整理等因素 |
| 平均延迟尚可，P99 明显偏高 | 存在尾延迟，不能只看平均值 |

Grafana 中的 `[5m]` 查询会平滑 60 秒的短测结果。观察短测时可以缩短窗口，但需要覆盖多个采样点；node_exporter 的块层平均延迟和 fio 的完成延迟也不一定具有完全相同的测量边界。

参数及输出语义参考 [fio 官方文档](https://fio.readthedocs.io/en/latest/fio_doc.html)。
