# 中断

中断是处理器暂停当前程序，转去处理某个事件，处理完成后再恢复执行的硬件机制。

从计算机组成原理的角度，中断的核心不是“插入一条中断指令”，而是：

> 中断控制器记录设备的请求，CPU 在合适的指令边界改变下一条指令的来源，转去执行中断处理程序。

具体的寄存器、信号线、现场保存方式和中断入口机制取决于处理器架构，但基本思想相同。

## 1. 中断系统的组成

一次硬件中断通常涉及以下部件：

- **中断源**：定时器、键盘、网卡、磁盘控制器等设备。
- **中断控制器**：接收多个设备的请求，记录待处理中断，完成屏蔽、优先级和中断号管理。
- **CPU**：判断是否接受中断，保存执行现场，并跳转到中断处理入口。
- **内存中的中断向量表**：根据中断号找到对应的处理程序入口地址。
- **操作系统**：初始化上述机制，并提供具体的中断处理程序。

可以先记住这条路径：

```text
设备产生事件
    ↓
中断控制器记录请求
    ↓
CPU 接受中断
    ↓
根据中断号找到处理入口
    ↓
执行中断处理程序
```

## 2. 中断请求如何产生

以网卡收到数据为例：

```text
网卡收到数据
    ↓
网卡把数据写入内存，或更新设备状态
    ↓
网卡发出中断请求
    ↓
中断控制器把请求标记为待处理
```

中断控制器可能通过硬件中断线接收请求，也可能通过 MSI/MSI-X 等消息方式接收请求。具体实现不同，但对 CPU 来说，最终都表现为一个待处理中断状态和一个中断向量。

### 2.1 硬件检测不是软件轮询

中断控制器通常会把请求保存为类似下面的状态：

```text
interrupt_pending = 1
```

CPU 内部的控制逻辑连接着这个状态。在指令执行的控制流程中，硬件会判断：

```text
interrupt_pending == 1
并且 CPU 当前允许响应中断
```

这不是操作系统执行下面这样的代码：

```c
while (1) {
    if (device_has_event()) {
        handle_event();
    }
}
```

上面的代码是**软件轮询**，会占用 CPU 执行指令。中断则是中断控制器保存请求，CPU 的硬件逻辑自动判断是否响应。

从非常宽泛的角度说，硬件电路当然也会在时钟驱动下采样和判断信号；但这不属于通常所说的软件轮询，因为没有查询循环，也不需要 CPU 主动逐个询问设备。

## 3. 指令边界与中断响应

### 3.1 什么是指令边界

指令边界是一条指令完成、下一条指令尚未开始的时刻。

```text
执行指令 A
    ↓
指令 A 完成
    ↓
指令边界
    ↓
准备执行指令 B
```

CPU 通常在这样的边界判断是否接受外部中断。这样可以保证当前指令完整执行，不会出现一条指令只执行了一半就被外部事件打断的情况。

现代 CPU 可能采用流水线、乱序执行和多级缓存，但从体系结构的角度，处理器仍然需要对外表现出明确、可恢复的指令执行状态。这种效果通常称为**精确中断**。

### 3.2 CPU 如何选择下一条指令

正常情况下，CPU 的程序计数器（PC）从下一条普通指令的地址继续执行：

```text
PC → 下一条普通指令
```

接受中断时，CPU 内部的下一地址选择逻辑改为选择中断处理入口：

```text
正常下一地址 ───────┐
                    ├─ 选择器 ─→ PC
中断处理入口地址 ───┘
```

可以把这个选择逻辑抽象成：

```text
if (take_interrupt == 0) {
    PC = normal_next_pc;
} else {
    PC = interrupt_vector_table[vector];
}
```

这段代码只是对硬件逻辑的抽象，并不是 CPU 真正执行的软件代码。硬件中实际由寄存器、组合逻辑和控制信号完成。

因此，中断不是把一条指令插入原程序，也不是修改原程序的指令。它只是暂时改变了 PC 的下一值：

```text
原执行流：A → B → C
发生中断：A → 中断处理程序 → B → C
```

## 4. 一次硬件中断的基本流程

以外部硬件中断为例，处理器通常按以下步骤工作：

1. **设备产生事件**，例如网卡收包或定时器到期。
2. **中断控制器接收请求**，记录待处理中断，并根据配置确定中断号和优先级。
3. **CPU 完成当前指令**，到达可以响应中断的指令边界。
4. **CPU 判断是否接受中断**，检查中断是否被屏蔽、优先级是否允许等条件。
5. **CPU 保存现场**，至少保存恢复执行所需的程序计数器和状态信息；具体保存内容由架构决定。
6. **CPU 获取中断向量**，通过中断向量表找到中断处理程序的入口地址。
7. **CPU 修改控制状态**，必要时切换特权级、切换栈或暂时屏蔽部分中断。
8. **CPU 跳转到中断处理程序**，开始执行操作系统或固件提供的处理逻辑。
9. **处理程序处理设备状态**，例如读取状态寄存器、确认中断、处理 DMA 结果或安排后续工作。
10. **执行中断返回操作**，恢复保存的现场，回到被中断的程序继续执行。

简化表示如下：

```text
原程序执行 A
    ↓
中断请求已挂起
    ↓
完成 A，到达指令边界
    ↓
保存 PC 和状态
    ↓
PC 改为中断入口地址
    ↓
执行中断处理程序
    ↓
恢复 PC 和状态
    ↓
继续执行 B
```

## 5. 中断向量与中断控制器

### 5.1 中断向量

中断向量可以理解为中断的编号。CPU 根据这个编号在中断向量表中找到处理入口：

```text
中断向量 = 5
    ↓
中断向量表[5]
    ↓
处理程序入口地址
```

中断向量表本质上是“中断编号到处理程序入口地址”的映射。不同处理器架构可能使用不同名称和格式，例如 x86 中常见的是 IDT。

### 5.2 屏蔽与优先级

中断控制器和 CPU 通常需要处理多个同时到来的请求：

- **屏蔽**：暂时不接受某些中断。
- **优先级**：优先处理更紧急的中断。
- **挂起**：暂时不能处理的请求先保留，之后再处理。
- **嵌套**：处理一个中断时，允许更高优先级的中断打断当前处理程序。

因此，“有中断请求”不一定意味着 CPU 会立即跳转。CPU 还要结合当前状态判断这个请求是否可以被接受。

## 6. 中断的分类

### 6.1 外部硬件中断

外部硬件中断由 CPU 外部的设备或定时器产生，例如：

- 键盘输入；
- 网卡收到数据；
- 磁盘 I/O 完成；
- 定时器到期。

它通常与 CPU 当前执行的具体指令没有直接关系。

### 6.2 异常

异常由 CPU 在执行指令时发现，例如：

- 除零；
- 非法指令；
- 缺页；
- 访问权限错误。

异常通常与当前指令有直接关系。根据异常类型，返回时可能重新执行当前指令，也可能跳过当前指令，或者终止当前程序。

### 6.3 软件中断与陷阱

软件中断或陷阱由程序主动执行特定指令触发，常用于：

- 请求操作系统服务；
- 实现系统调用；
- 调试程序；
- 从用户态进入内核态。

它与外部硬件中断的共同点是都会进入预先定义的处理入口；区别是触发源来自当前正在执行的软件指令。

| 类型 | 触发来源 | 与当前指令的关系 | 示例 |
|---|---|---|---|
| 外部硬件中断 | 外部设备或定时器 | 通常无直接关系 | 网卡收包、定时器到期 |
| 异常 | CPU 执行指令时发现 | 通常有直接关系 | 缺页、除零、非法指令 |
| 软件中断或陷阱 | 程序执行特定指令 | 由程序主动触发 | 系统调用、调试陷阱 |

## 7. 硬件与操作系统的分工

### 7.1 硬件负责什么

计算机组成原理主要关注以下硬件动作：

- 接收或检测中断请求；
- 保存待处理中断状态；
- 进行屏蔽和优先级判断；
- 保存必要的程序现场；
- 获取中断向量；
- 修改 PC，跳转到中断入口；
- 执行中断返回并恢复现场。

### 7.2 操作系统负责什么

操作系统利用硬件提供的中断机制完成设备管理和任务管理：

- 初始化中断控制器和中断向量表；
- 注册设备驱动的中断处理程序；
- 读取设备状态并处理 I/O 结果；
- 管理中断屏蔽和优先级；
- 在时钟中断中维护时间和进行进程调度；
- 将不适合在中断上下文中完成的工作延后处理。

Linux 的 `softirq` 属于操作系统内核中的延后处理机制，不是处理器执行的“软件中断指令”。它通常由硬件中断处理程序安排，之后由内核在合适的上下文中执行。

## 8. 中断与轮询的比较

### 8.1 轮询

CPU 主动、反复读取设备状态：

```text
读取设备状态
    ↓
有事件吗？
    ├─ 没有 → 再次读取
    └─ 有   → 处理事件
```

优点是流程简单、响应时间容易预测；缺点是设备没有事件时，CPU 仍然需要不断执行检查代码。

### 8.2 中断

设备发生事件后主动发出请求：

```text
设备产生事件
    ↓
中断控制器记录请求
    ↓
CPU 在指令边界接受中断
    ↓
执行中断处理程序
```

优点是设备空闲时不需要 CPU 持续查询；缺点是中断响应、现场保存和上下文切换也会产生开销。

实际系统常常组合使用两者。例如网卡可能先用中断通知 CPU 有数据到来，之后由操作系统批量处理数据，减少大量小中断带来的开销。

## 9. 与 DMA 的关系

中断经常用于通知 CPU 一次 DMA 传输已经完成：

```text
CPU 配置 DMA
    ↓
DMA 引擎在设备与内存之间传输数据
    ↓
DMA 完成
    ↓
设备产生中断
    ↓
CPU 检查并处理传输结果
```

DMA 负责搬运数据，中断负责通知 CPU 传输状态发生变化。两者解决的是不同问题：

- **DMA**：减少 CPU 搬运数据的工作。
- **中断**：让设备在需要 CPU 处理时主动通知 CPU。
