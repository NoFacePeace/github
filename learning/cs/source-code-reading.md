# 源码与开源仓库阅读方法

学习一个陌生的开源仓库，不应该从“读完所有代码”开始，而应该从“建立整体地图，并追踪一条真实流程”开始。

## 1. 推荐阅读顺序

```text
项目说明与规则
-> 启动程序
-> 查找主要入口
-> 跟踪一条核心调用链
-> 深入核心模块
-> 整理架构图
-> 通过小改动验证理解
```

## 2. 阅读项目说明

首先阅读以下内容：

- `README.md`：项目用途、安装方式、启动命令和基本示例。
- `AGENTS.md`、`CONTRIBUTING.md` 或类似文件：项目约定、分层规则和开发流程。
- `Makefile`、`package.json`、`pyproject.toml`、`go.mod` 等：项目使用的语言、框架和命令。
- `docs/`：设计文档、API 文档、术语表和开发指南。
- CI 配置：项目如何构建、测试和发布。

第一轮只需要回答：

1. 这个项目解决什么问题？
2. 它面向什么用户或调用方？
3. 如何安装和启动？
4. 输入和输出分别是什么？
5. 主要依赖哪些外部系统？

## 3. 启动程序

尽量先把项目运行起来，观察实际行为：

```bash
make help
make test
make run
npm run dev
go run .
```

具体命令以项目文档为准。启动时重点观察：

- 程序从哪个文件开始执行。
- 默认监听什么端口。
- 配置文件和环境变量从哪里加载。
- 日志输出在哪里。
- 数据库、缓存或临时目录在哪里。
- 启动后提供了哪些 HTTP API、CLI 命令或页面。

如果依赖安装失败，不要立即停止阅读。可以先通过启动脚本和入口代码理解启动关系，之后再处理环境问题。

## 4. 查找主要入口

根据项目类型定位入口：

| 项目类型 | 常见入口 |
| --- | --- |
| Go | `main.go`、`cmd/`、`internal/` |
| Java | `main` 方法、Spring Boot Application |
| Python | `__main__.py`、`main.py`、CLI 配置 |
| Node.js | `package.json` 的 `main`、`bin`、`scripts` |
| Rust | `src/main.rs`、`src/lib.rs` |
| 前端 | `main.ts`、`main.tsx`、`App.vue`、`App.tsx` |
| 服务端 | 路由注册、Controller、Handler |
| CLI | 命令注册、参数解析、子命令入口 |

可以使用搜索工具快速定位：

```bash
rg --files
rg "func main|createApp|createServer|router|register|command"
rg "POST /|GET /|Route|HandleFunc"
```

入口文件通常只负责初始化依赖和注册能力。真正的业务逻辑一般位于后续调用的模块中。

## 5. 跟踪一条核心调用链

不要同时研究所有功能。选择一个最容易观察的用户场景，例如：

- 创建一条任务。
- 登录一次。
- 发起一个 HTTP 请求。
- 执行一个 CLI 命令。
- 打开一个页面。
- 保存一条数据。

沿着下面的方向记录：

```text
用户操作
-> 页面 / CLI / API 入口
-> 路由或命令分发
-> 参数解析与校验
-> 核心业务逻辑
-> 数据库 / 文件 / 外部服务
-> 返回结果
-> UI 或调用方展示
```

每到一个函数，只问四个问题：

1. 它的输入是什么？
2. 它修改了什么状态？
3. 它调用了谁？
4. 它把结果返回给谁？

推荐边读边画简单的调用图：

```text
入口
  -> Handler
    -> Service / UseCase
      -> Repository / Client
        -> 数据库或外部服务
```

## 6. 再看核心模块

有了调用链之后，再按照职责理解模块：

- 入口层：接收请求、解析参数、返回响应。
- 业务层：实现核心规则和业务流程。
- 数据层：访问数据库、文件或缓存。
- 集成层：调用外部 API、消息队列或其他服务。
- 配置层：加载配置和环境变量。
- 安全层：认证、授权、审批、沙箱和风险控制。
- 可观测性：日志、指标、事件、追踪和审计。
- 测试层：验证每个模块的边界和完整流程。

阅读模块时优先关注：

- 对外暴露的接口。
- 关键结构体或类型。
- 依赖关系。
- 状态变化。
- 错误处理。
- 并发、缓存、重试和事务。
- 对应的测试文件。

不要一开始深入工具类、兼容代码、生成代码、迁移脚本和所有配置细节。

## 7. 通过测试理解行为

测试通常比实现代码更直接地说明模块的预期行为。可以按以下顺序阅读：

1. 一个最简单的成功测试。
2. 一个失败或边界测试。
3. 一个涉及多个模块的集成测试。
4. 测试使用的 mock、fake 或 fixture。

常用命令：

```bash
go test ./path/to/package
npm test
pytest path/to/test
cargo test
```

阅读测试时重点看：

- 测试准备了哪些输入。
- 哪个函数被调用。
- 断言了哪些状态或输出。
- 哪些依赖被替换成了 fake。
- 作者特别防止了哪些错误。

## 8. 整理架构图

架构图应该随着理解逐步修正，而不是第一次就追求完整。可以先画最小版本：

```text
用户或调用方
      |
      v
入口层
      |
      v
业务核心
   /      \
  v        v
数据层   外部服务
      |
      v
日志、事件、指标和审计
```

之后逐步补充：

- 模块边界。
- 依赖方向。
- 数据流。
- 控制流。
- 异步任务。
- 错误和重试路径。
- 权限和安全边界。
- 持久化位置。

架构图至少应该能回答：

1. 请求从哪里进入？
2. 谁负责业务决策？
3. 数据保存在哪里？
4. 外部系统在哪里被调用？
5. 失败时如何处理？
6. 状态如何传递给用户？

## 9. 做一个小改动验证理解

理解一个仓库的最好方式，是做一个范围很小的修改：

- 增加一个测试。
- 修改一条日志。
- 增加一个参数校验。
- 修复一处文档。
- 给现有接口增加一个无副作用字段。
- 为某个边界情况补充错误处理。

改动前先写出：

```text
我认为调用链是：
我准备修改的模块是：
预期影响是：
我会用什么测试验证：
```

改动后运行最相关的测试，并检查调用链是否与原来的理解一致。

```text
## 测试方式

## 架构图

## 尚未理解的问题
```

## 11. 最终检查清单

- [ ] 能用自己的话说明项目解决的问题。
- [ ] 能成功启动项目，或知道启动失败的具体原因。
- [ ] 能指出主要入口文件。
- [ ] 能完整描述一条真实调用链。
- [ ] 能解释核心模块的职责和依赖方向。
- [ ] 能说明数据存储和外部调用的位置。
- [ ] 能找到对应的测试。
- [ ] 能画出一张基本架构图。
- [ ] 能完成一个小改动并验证结果。
