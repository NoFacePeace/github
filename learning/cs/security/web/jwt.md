# JWT

## 1. 概述

JWT（JSON Web Token）是一种传递声明（Claims）的令牌格式。声明可以描述用户身份、签发方、接收方、有效期等信息。

JWT 常用于携带登录后的身份声明，通过签名检测篡改，并支持无需查询服务端会话的身份验证。签名不提供加密保护，也不能防止令牌泄露；被盗的有效令牌仍可能被冒用。需要立即撤销令牌或检查最新权限时，仍可能依赖服务端状态。

JWT 不是加密算法或完整的登录协议。[规范：RFC 7519](https://www.rfc-editor.org/rfc/rfc7519)

## 2. 常见结构

常见的签名 JWT 使用 JWS 紧凑格式，由三部分组成：

```text
Base64URL(Header).Base64URL(Payload).Base64URL(Signature)
```

### 2.1 Header：头部

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

- `alg`：签名或消息认证码算法。
- `typ`：令牌类型。
- `kid`：可选的密钥标识，常用于密钥轮换。

### 2.2 Payload：载荷

```json
{
  "iss": "https://auth.example.com",
  "sub": "user-123",
  "aud": "orders-api",
  "iat": 1800000000,
  "exp": 1800000900,
  "role": "reader"
}
```

以上仅用于说明字段，不是可直接使用的令牌。

| 字段 | 含义 |
| --- | --- |
| `iss` | 签发方 |
| `sub` | 主体，例如用户 ID |
| `aud` | 预期接收方，例如某个 API |
| `exp` | 过期时间 |
| `nbf` | 在此时间之前不可接受 |
| `iat` | 签发时间 |
| `jti` | 令牌唯一标识 |

时间字段使用 Unix 时间，单位为秒。JWT 基础规范并未要求所有场景必须包含上述字段，具体应用应明确必填字段及验证规则。`role` 是示例自定义声明，不是 JWT 内置的权限机制。

### 2.3 Signature：签名或消息认证码

#### 2.3.1 生成与验证

以 HS256 为例，服务端使用共享密钥 `secret` 生成消息认证码。`secret` 不是用户密码，也不会包含在 JWT 中或返回给客户端。

生成过程如下：

```text
message = Base64URL(Header) + "." + Base64URL(Payload)
signature = HMAC-SHA256(secret, message)
token = message + "." + Base64URL(signature)
```

验证方使用收到的 Header 和 Payload 的原始编码片段，以及同一个 `secret`，重新计算认证码，再通过安全的比较方式与令牌携带的认证码进行比较。

对于 HS256，相同内容使用相同 `secret`，计算结果一定相同。如果有人修改用户 ID 或角色，原来的认证码就无法通过验证。认证码验证通过后，仍需检查有效期、签发方、接收方等声明。

**Base64URL 是编码，不是加密。** 常见签名 JWT 的载荷可以被读取，不应放密码或不必要的敏感信息。JWT 也可以采用 JWE 加密格式，因此“三段式”并不适用于所有 JWT。[结构与声明定义：RFC 7519](https://www.rfc-editor.org/rfc/rfc7519)

#### 2.3.2 常见算法

JWT 使用共享密钥还是公私钥，取决于所选算法：

| 算法 | 类型 | 生成时使用 | 验证时使用 |
| --- | --- | --- | --- |
| HS256 | HMAC-SHA256 消息认证码 | 共享密钥 `secret` | 同一个 `secret` |
| RS256 | RSASSA-PKCS1-v1_5 与 SHA-256 数字签名 | 私钥 | 公钥 |
| ES256 | P-256 曲线与 SHA-256 的 ECDSA 数字签名 | 私钥 | 公钥 |

共享密钥方案中，能够验证的一方也能签发令牌。公私钥方案则可以分离这两种能力：认证服务保管私钥并签名，业务服务只持有公钥进行验签，不能签发令牌。

这些算法用于验证完整性和来源，不用于加密载荷。“私钥签名、公钥验签”也不是“私钥加密、公钥解密”。

验证端应固定允许的算法和对应密钥类型，拒绝不符合策略的令牌；普通登录认证场景不应接受 `alg: none`。不能仅根据输入令牌的 `alg` 自行决定信任规则。[算法与密钥验证建议：RFC 8725](https://www.rfc-editor.org/rfc/rfc8725)

#### 2.3.3 密钥管理

**密钥强度与保存**

在密钥足够强的情况下，无法根据已知内容和认证码，在实际可行的计算量内反推出 `secret`。但弱密钥可能被猜测或暴力枚举，因此应使用足够长、随机生成的共享密钥。

共享密钥和私钥需要保密，避免写入代码仓库或日志；公钥可以分发给验证服务，但必须确保来源可信。

**密钥标识 `kid`**

`kid`（Key ID）是 Header 中可选的密钥标识，不是密钥本身。存在多把密钥时，验证方根据它从受信任的密钥集合中选择密钥，然后验签。不能把 `kid` 当作任意文件路径或下载地址，也不能仅凭它信任令牌。

**密钥轮换**

轮换用于减少旧密钥长期有效的风险，也支持密钥泄露后的更换和安全升级。正常轮换时，通过一段新旧密钥重叠的时间，兼容已经签发的 JWT：

1. 先让验证服务支持新密钥，同时保留旧密钥的验证能力。
2. 使用新密钥签发 JWT，并通过 `kid` 区分新旧密钥。
3. 等旧密钥签发的 JWT 全部过期，并预留时钟偏差时间后，移除旧密钥的验证能力。

对于公私钥方案，停止使用旧私钥签发后，只需继续保留旧公钥供验证。如果旧密钥已经泄露，应停止信任受影响的令牌，而不是等待它们自然过期，用户可能需要重新认证。

## 3. 认证流程

### 3.1 认证流程

一个常见的登录流程：

1. 客户端提交登录凭据，服务端完成身份验证。
2. 服务端签发并发送 JWT：可以放在登录接口的 JSON 响应体中返回，也可以通过响应头 `Set-Cookie` 设置 Cookie。
3. 客户端接收并保存 JWT：响应体中的令牌由客户端代码读取，可以保存在内存、`sessionStorage` 或 `localStorage` 中；通过 `Set-Cookie` 返回的令牌由浏览器按 Cookie 规则保存。
4. 客户端请求 API 时携带令牌：代码读取保存的令牌并放入 `Authorization: Bearer <JWT>` 请求头，或由浏览器在符合条件的请求中自动携带 Cookie。
5. API 验证令牌，再根据当前业务规则判断是否允许访问资源。

保存方式的区别：

| 方式 | 保存特点 | 注意事项 |
| --- | --- | --- |
| 内存 | 保存在程序变量中，页面刷新后通常丢失 | 不持久化，但仍需防范 XSS |
| `sessionStorage` | 通常在当前标签页会话内保留，刷新后仍在，关闭标签页后清除 | JavaScript 可读取，存在 XSS 窃取风险 |
| `localStorage` | 跨页面刷新和浏览器重启保留，直到被清除 | JavaScript 可读取，存在 XSS 窃取风险 |
| Cookie | 浏览器管理，保存期限由 Cookie 属性决定 | 可设置 `HttpOnly` 限制 JavaScript 读取、`Secure` 限制通过 HTTPS 发送，并结合适当的 `SameSite` 设置与 CSRF 防护 |

客户端保存期限与 JWT 的有效期是两回事：即使令牌仍在存储中，服务端也必须检查它是否已经过期。

认证回答“你是谁”，授权回答“你能做什么”。即使 JWT 有效，也不意味着用户可以访问任意订单：API 仍应检查资源归属和权限。

### 3.2 验证规则

使用成熟库，并为具体用途配置明确规则：

1. 检查令牌格式和允许的算法，使用受信任密钥验证签名。
2. 要求并验证该场景需要的声明，例如 `iss`、`aud`、`exp`。
3. 检查是否过期、是否早于 `nbf`，必要时允许少量时钟偏差。
4. 区分令牌用途，避免将其他系统或其他类型的令牌当作本 API 的访问凭据。
5. 根据业务要求检查账号状态、撤销状态和资源访问权限。

**解码成功不等于验证成功，签名正确也不等于有权访问。** 在完成验证之前，不应信任载荷中的用户或权限信息。[验证最佳实践：RFC 8725](https://www.rfc-editor.org/rfc/rfc8725)

## 4. 与 Session、Cookie 的区别

| 概念 | 作用 |
| --- | --- |
| Cookie | 浏览器保存和随请求发送数据的机制 |
| Session | 服务端管理会话状态的方式，常通过 Session ID 找到会话 |
| JWT | 携带声明的令牌格式，可用于会话或访问令牌 |

| 对比 | 常见服务端 Session | 自包含的签名 JWT |
| --- | --- | --- |
| 客户端持有 | 通常是不透明的 Session ID | 包含声明的令牌 |
| 验证方式 | 查询会话存储 | 验证签名及声明，必要时查询业务状态 |
| 注销与撤销 | 删除或禁用会话 | 通常需要额外的撤销机制 |
| 权限变更 | 可以通过服务端状态及时反映 | 已签发声明可能持续有效至到期 |
| 多服务使用 | 共享会话存储或通过会话服务验证 | 可分发验证密钥，由各服务校验 |

JWT 不天然优于 Session。需要立即注销和集中管理会话的应用，Session 往往更直接；多个服务需要验证同一签发方的声明时，JWT 可能更合适。

“无状态”通常只表示验证令牌时不必查询会话库，并不意味着整个系统不需要数据库或撤销状态。

## 5. 过期、刷新与注销

常见设计是使用短期 Access Token 和更长期的 Refresh Token：

- Access Token 用于访问 API，可以采用 JWT。
- Refresh Token 用于获取新的 Access Token，不一定是 JWT，应限制其用途并安全存储。
- 刷新时可以轮换 Refresh Token，并记录使用状态，以发现旧令牌被重复使用。

具体有效期取决于业务风险和体验要求，不存在适用于所有应用的固定时长。

客户端删除 JWT 只会让当前客户端停止使用它，已经泄露的副本仍可能有效。若需要立即撤销，可以采用令牌拒绝列表、用户会话版本校验或在线状态检查；这些方案会引入服务端状态。

退出登录时撤销 Refresh Token 可以阻止后续刷新，但通常不会自动使已签发的 Access Token 立即失效。

## 6. 常见安全问题

| 问题 | 应对思路 |
| --- | --- |
| 令牌被窃取后重放 | 使用 HTTPS、缩短有效期，按需增加撤销或发送方绑定机制 |
| 把密码等敏感数据放入载荷 | 仅放必要声明，签名不提供保密性 |
| 只解码而不验证 | 使用库的验证接口，并配置声明验证规则 |
| 密钥过弱或泄露 | 使用足够强的密钥，隔离保存并轮换 |
| 权限声明过时 | 缩短有效期，关键操作查询当前权限 |
| JWT 出现在 URL 或日志中 | 避免放入查询参数，对认证头和令牌进行日志脱敏 |

浏览器保存方式也有取舍：

- `localStorage` 可被同源 JavaScript 读取，XSS 可能直接窃取令牌。
- `HttpOnly` Cookie 能限制 JavaScript 读取，但浏览器会自动携带 Cookie，需要结合 `Secure`、适当的 `SameSite` 设置及 CSRF 防护。
- 内存保存减少持久化，但页面刷新会丢失，也不能防止恶意脚本在页面内发起请求。

JWT 不会自动解决 XSS、CSRF 或重放攻击，应根据应用架构选择保存和防护方式。

## 7. 与 OAuth 2.0、OpenID Connect 的关系

- JWT 是令牌格式。
- OAuth 2.0 是授权框架，其 Access Token 不一定是 JWT。
- OpenID Connect 在 OAuth 2.0 之上提供身份认证，其 ID Token 使用 JWT。

ID Token 用于客户端理解认证结果，不应直接作为业务 API 的 Access Token 使用。
