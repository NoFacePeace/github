# Web 常见攻击

## 1. SQL 注入

### 1.1 概述

SQL 注入（SQL Injection）是指程序将不可信输入拼接进 SQL，使输入被解释成 SQL 语法，从而改变查询原本的含义。

关键问题是混淆了代码与数据。输入可能来自请求参数、表单、请求头，也可能来自之前保存的数据。

### 1.2 原理与示例

假设订单查询接口直接拼接用户输入的订单编号，下面是存在漏洞的伪代码：

```text
sql = "SELECT id, total FROM orders WHERE id = " + order_id
```

正常输入 `42` 时，生成：

```sql
SELECT id, total FROM orders WHERE id = 42
```

如果输入变成 `42 OR 1=1`，生成的语句就是：

```sql
SELECT id, total FROM orders WHERE id = 42 OR 1=1
```

`1=1` 恒为真，查询条件因此变成对所有行成立，原本按编号查询的逻辑被改变。如果应用直接返回结果，就可能泄露其他订单。

是否能进一步修改或删除数据，取决于查询位置、数据库能力和数据库账号权限，并非每个注入点都能执行任意操作。

### 1.3 防护方式

**使用参数化查询**，将 SQL 结构与参数值分开传递。例如下面使用 Python SQLite 的参数绑定写法：

```python
cursor.execute(
    "SELECT id, total FROM orders WHERE id = ?",
    (order_id,),
)
```

此时 `42 OR 1=1` 只会作为一个参数值处理，不会成为查询条件的一部分。占位符写法取决于数据库驱动，不能先拼接输入再交给执行接口。

其他防护措施：

- **动态标识符使用允许列表**：表名、列名和排序方向通常不能通过值占位符绑定，应映射到程序预定义的选项。
- **最小数据库权限**：应用账号只拥有业务需要的权限，避免使用管理员账号。
- **校验输入类型与范围**：例如订单编号必须符合预期格式，但输入校验不能代替参数化查询。
- **检查原生 SQL**：使用 ORM 或存储过程并不自动安全，内部拼接动态 SQL 仍可能产生漏洞。

参数化查询解决的是注入问题。即使查询安全，接口仍需检查订单是否属于当前用户，防止越权访问。[OWASP SQL 注入防护指南](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)

## 2. XSS（跨站脚本）

### 2.1 概述

XSS（Cross-Site Scripting）是指不可信内容被页面当作可执行代码处理，使攻击者的脚本在受害者浏览器中、以该网站的权限执行。

它可能读取页面数据、修改界面、冒用用户发起操作，或窃取 JavaScript 可访问的令牌。名称中的“跨站”不意味着攻击必须涉及两个网站。

### 2.2 原理与示例

假设页面通过下面的代码显示用户输入：

```javascript
const input = new URLSearchParams(location.search).get("message") ?? "";
document.querySelector("#message").innerHTML = input;
```

如果输入包含以下内容，在没有其他防护阻止执行时，浏览器会将它解析为图片元素，并在加载失败时执行事件处理代码：

```html
<img src="/missing-image" onerror="alert('XSS')">
```

这里的弹窗只是演示。漏洞根源在于 `innerHTML` 将输入当作 HTML 解析，输入因此可以从普通文字变成可执行内容。

如果只需要显示文字，应改为：

```javascript
document.querySelector("#message").textContent = input;
```

这会将输入作为文本展示，而不会把其中的标签解析成页面元素。

### 2.3 常见类型

| 类型 | 特点 | 示例场景 |
| --- | --- | --- |
| 存储型 XSS | 恶意内容被保存，其他用户访问时触发 | 评论被保存后，未经安全处理就渲染为 HTML |
| 反射型 XSS | 请求中的输入被服务端直接写入响应页面 | 搜索词未经编码就出现在搜索结果页 |
| DOM 型 XSS | 前端代码将不可信数据传入危险的 DOM 操作 | 将 URL 参数直接赋给 `innerHTML` |

这些分类并非完全互斥：存储型、反射型关注数据如何传递，DOM 型关注浏览器端的处理方式。上面的示例属于 DOM 型 XSS。

### 2.4 防护方式

- **纯文本使用安全接口**：例如 `textContent`，避免将用户输入直接交给 `innerHTML`。
- **根据输出位置编码**：HTML 文本、属性、URL 等位置需要对应的处理；不要将输入直接拼入脚本或事件处理属性。
- **富文本进行 HTML 净化**：确实需要保留标签时，使用维护中的净化库，并限制允许的标签、属性和 URL 协议。
- **谨慎绕过框架保护**：模板通常有自动转义，但直接输出 HTML 的接口仍需安全处理。
- **使用 CSP 作为额外防线**：限制脚本执行来源与方式，不能代替修复不安全的输出逻辑。

仅过滤 `<script>` 标签无法防住 XSS，事件属性等其他位置也可能执行脚本。[OWASP XSS 防护指南](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)

### 2.5 与 JWT 的关系

如果 JWT 存在 `localStorage` 或 `sessionStorage` 中，成功执行的同源恶意脚本可能读取它。使用 `HttpOnly` Cookie 可以阻止脚本直接读取该 Cookie，但不能阻止恶意脚本借助用户登录状态在页面内发起请求。

JWT 验签解决的是令牌篡改问题，不能阻止 XSS，也不能防止被窃取的有效令牌被冒用。

## 3. CSRF（跨站请求伪造）

### 3.1 概述

CSRF（Cross-Site Request Forgery）是指攻击者诱导用户浏览器向目标网站发送非用户本意的请求，利用浏览器自动携带的身份凭据执行操作。

典型场景是用户已经登录，目标接口使用 Cookie 认证，却没有充分验证请求来源或 CSRF Token。攻击者通常不需要知道 Cookie 内容。

### 3.2 原理与示例

假设 `app.example` 提供修改昵称的接口，仅凭登录 Cookie 确认用户。攻击者在另一个网站放置表单：

```html
<form action="https://app.example/profile/nickname" method="POST">
  <input type="hidden" name="nickname" value="changed-name">
  <button type="submit">领取奖励</button>
</form>
```

可能发生的过程：

1. 用户已登录 `app.example`，浏览器保存着登录 Cookie。
2. 用户访问攻击者页面，点击被伪装的按钮。
3. 浏览器向 `app.example` 提交表单；如果 Cookie 策略允许，会自动携带登录 Cookie。
4. 接口只检查登录状态，就可能将用户昵称改为攻击者指定的值。

这个示例依赖 Cookie 实际被发送，例如适用的 `SameSite=None; Secure` Cookie 且浏览器没有其他限制。显式设置 `SameSite=Lax` 或 `Strict` 通常会阻止这种跨站 POST 携带 Cookie，不能假设所有跨站请求都会携带凭据。

攻击者不必读取响应，只要操作发生就可能达到目的。同源策略主要限制跨源读取，并不会阻止所有跨源请求；普通表单提交也不依赖目标服务器开放 CORS。

### 3.3 防护方式

优先使用框架内置的 CSRF 防护，并确保服务端对修改状态的请求执行校验。

- **CSRF Token**：服务端提供与会话关联、不可预测的令牌，页面通过表单字段或请求头提交，服务端验证；仅自动携带认证 Cookie 不够。
- **SameSite Cookie**：按业务选择 `Lax` 或 `Strict` 限制跨站携带；它区分“站点”而非“源”，同站不同子域仍需考虑。
- **来源检查**：按允许列表校验 `Origin`，必要时检查 `Referer`；明确处理缺失情况。
- **Fetch Metadata**：根据 `Sec-Fetch-Site` 等请求头拒绝不符合策略的跨站修改请求。
- **正确使用方法**：GET 不应修改状态；仅改成 POST 也不等于防住 CSRF。

对于依赖自定义请求头的 API 防护，还需严格限制 CORS 来源和接受的请求格式，避免留有普通表单可调用的替代入口。[OWASP CSRF 防护指南](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

### 3.4 与 XSS、JWT 的关系

| 对比 | XSS | 典型 CSRF |
| --- | --- | --- |
| 核心方式 | 在目标页面上下文中执行恶意脚本 | 诱导浏览器向目标网站发送请求 |
| 是否需要目标站脚本注入漏洞 | 是 | 不需要 |
| 是否需要读取登录凭据 | 不一定 | 通常不需要 |

JWT 放在 Cookie 中并自动发送时，仍需考虑 CSRF；签名只能说明令牌可信，不能证明请求符合用户意图。`HttpOnly` 限制脚本读取 Cookie，不阻止浏览器发送它。

如果接口只接受客户端代码主动设置的 `Authorization: Bearer <JWT>`，且令牌未泄露、CORS 配置正确，普通跨站表单无法自动携带该认证头，典型 CSRF 的条件就不成立。这并不消除 XSS 风险：同源恶意脚本仍可能读取令牌或借助应用发起操作，也可能绕过 CSRF 防护。

## 4. DoS 与 DDoS（拒绝服务）

### 4.1 概述

DoS（Denial of Service，拒绝服务）是指通过耗尽资源或触发缺陷，使服务变慢、无法响应甚至崩溃，影响正常用户访问。其主要攻击目标是系统的可用性。

DDoS（Distributed Denial of Service，分布式拒绝服务）是 DoS 的一种，由多个分布式来源共同形成攻击流量。它并不限于 Web，也可能针对网络链路和基础设施。

| 对比 | DoS | DDoS |
| --- | --- | --- |
| 含义 | 拒绝服务攻击的统称，单一来源也可实施 | 来自多个分布式来源的拒绝服务攻击 |
| 资源消耗 | 不一定需要大流量，少量高成本请求也可能奏效 | 可聚合多个来源的流量或计算能力 |
| 防护难点 | 识别瓶颈、限制消耗、修复缺陷 | 还需处理来源分散、流量规模和上游带宽问题 |

流量突增或服务超时并不一定代表受到攻击，也可能是正常业务高峰或系统故障，需要结合请求行为和资源指标判断。

### 4.2 常见方式

| 类型 | 基本原理 | 主要影响 |
| --- | --- | --- |
| 流量型 | 大量流量占满网络带宽，例如反射放大流量 | 正常请求无法顺利到达服务 |
| 协议或连接资源型 | 消耗连接状态、连接表等资源，例如 SYN Flood | 服务器或中间设备难以接受新连接 |
| 应用层 | 大量访问接口，或反复触发高成本查询、报表生成 | CPU、内存、线程池或数据库连接池耗尽 |
| 慢速请求 | 缓慢发送请求，使连接和处理资源长时间被占用 | 并发处理能力下降 |

这些方式可能组合出现。判断攻击影响时，不能只看每秒请求数，还要看单次请求的资源成本和持续占用时间。

### 4.3 原理与示例

假设报表接口每次都要扫描大量数据，且没有并发限制：

1. 多个报表请求同时进入服务。
2. 每个请求占用数据库连接并进行耗时计算。
3. 连接池被占满，普通查询也只能排队。
4. 等待导致更多请求积压，最终出现超时或内存压力。

即使请求格式正确、用户已通过认证，也可能造成资源耗尽。攻击者无需修改数据，就能影响整个服务的可用性。

### 4.4 防护方式

防护需要覆盖网络入口和应用内部，避免资源在某一层被耗尽。

- **入口防护**：通过上游运营商或 DDoS 防护服务过滤大规模流量；带宽已被占满时，仅在应用内拦截通常来不及。
- **限流与配额**：按账号、接口、来源等维度限制调用，并设置全局上限；仅按 IP 限流可能误伤共享出口用户，也难以覆盖分布式来源。
- **资源边界**：限制请求体大小、处理时间、并发数和排队长度，及时释放超时资源。
- **成本控制**：高成本操作使用缓存、任务队列或专门配额；队列本身也要有容量限制。
- **隔离与降级**：隔离高成本任务，必要时暂停非核心功能，防止局部过载拖垮整个服务。
- **监控与预案**：观察带宽、连接数、延迟、错误率和资源使用，预先准备处置流程。

扩容能增加容量，但不能消除资源消耗漏洞，也可能放大费用；WAF 主要处理应用层流量，不能单独解决所有网络层攻击。[OWASP DoS 防护指南](https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html)

## 5. 点击劫持

### 5.1 概述

点击劫持（Clickjacking）是指攻击者通过界面覆盖或伪装，使用户以为自己在点击某个可见元素，实际却操作了另一个页面中的按钮或链接。

它利用的是用户看到的界面与实际点击目标不一致，通常不需要向目标网站注入脚本。

### 5.2 原理与示例

一个典型过程：

1. 攻击者通过 `iframe` 嵌入目标网站的操作页面。
2. 调整框架的位置和透明度，将目标按钮覆盖在“领取奖励”等诱导元素上。
3. 用户点击诱导元素，实际点击的是框架中的真实按钮。
4. 如果目标页面具有有效登录状态且操作无需其他确认，就可能执行非用户本意的操作。

攻击能否成功取决于目标页面是否允许被嵌入、浏览器是否允许其使用相关登录凭据，以及操作是否有额外验证。

### 5.3 防护方式

在目标页面的 HTTP 响应头中配置 CSP 的 `frame-ancestors`，限制哪些页面可以嵌入它：

```http
Content-Security-Policy: frame-ancestors 'none'
```

`'none'` 表示禁止任何页面嵌入。如果需要允许同源页面嵌入，可使用：

```http
Content-Security-Policy: frame-ancestors 'self'
```

需要兼容旧客户端时，还可以配置一致的 `X-Frame-Options` 策略：

```http
X-Frame-Options: DENY
```

其中 `DENY` 禁止嵌入，`SAMEORIGIN` 允许同源嵌入。这些限制应通过响应头发送；不能依赖 HTML 中的 `meta` 标签设置 `frame-ancestors` 或 `X-Frame-Options`。

敏感操作还可以要求重新认证或明确确认操作详情，但这些措施不能代替页面嵌入限制。[OWASP 点击劫持防护指南](https://cheatsheetseries.owasp.org/cheatsheets/Clickjacking_Defense_Cheat_Sheet.html)

### 5.4 与 XSS、CSRF 的区别

| 攻击 | 核心方式 |
| --- | --- |
| XSS | 在目标页面上下文中执行恶意脚本 |
| CSRF | 诱导浏览器发送非用户本意的请求 |
| 点击劫持 | 伪装点击目标，让用户实际操作被嵌入的真实页面 |

点击劫持可能通过目标页面自身的正常流程提交请求，因此即使页面具有 CSRF Token，也不能据此认定已经防住点击劫持。
