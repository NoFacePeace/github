# 密码学

整理 RSA、DH、ECDH、DHE、ECDHE 的用途、基本原理与区别，理解加密、数字签名、密钥协商和前向保密。

## 1. 基础概念

| 概念 | 解决的问题 |
| --- | --- |
| 加密与解密 | 如何让只有持有对应密钥的一方读取内容 |
| 数字签名 | 如何验证消息来自对应私钥的持有者，并检测修改 |
| 密钥协商 | 如何在不直接传输 Shared Secret 的情况下，让双方得到相同 Secret |
| 密钥派生 | 如何从 Secret 生成适合不同用途的密钥 |

公钥可以公开，私钥需要保密。Shared Secret 通常还要经过密钥派生，再用于对称加密；密钥协商本身不等于身份认证。

## 2. 非对称加密

### 2.1 RSA

RSA 名称来自 Rivest、Shamir、Adleman 三位发明者的姓氏。它是基于大整数模运算的公钥密码算法，其安全性与大整数分解等计算难题有关。

RSA 可以构造加密方案，也可以构造签名方案，两者用途不同：

| 方案 | 发送方操作 | 接收方操作 | 作用 |
| --- | --- | --- | --- |
| RSA 加密 | 使用接收方公钥加密 | 使用自己的私钥解密 | 保护内容机密性 |
| RSA 签名 | 使用自己的私钥签名 | 使用发送方公钥验签 | 验证来源与完整性 |

签名不是简单的“私钥加密”。实际方案有专门的编码与校验规则，例如 RSA-OAEP 用于加密，RSA-PSS 用于签名。参见 [RFC 8017](https://www.rfc-editor.org/rfc/rfc8017.html)。

## 3. 密钥协商

### 3.1 有限域 DH

DH（Diffie–Hellman）用于密钥协商。这里以有限域 DH 为例：双方共享公开参数，各自生成私钥并交换公钥，然后独立计算出相同的 Secret。

```text
公开参数：素数 p、适当子群的生成元 g

客户端：私钥 a，公钥 A = g^a mod p
服务端：私钥 b，公钥 B = g^b mod p

客户端计算：Z = B^a mod p
服务端计算：Z = A^b mod p

双方得到相同结果：Z = g^(ab) mod p
```

网络上传输的是公开参数与公钥 A、B，私钥 a、b 和 Shared Secret Z 不直接传输。对于合适的参数，仅凭公开信息计算 Shared Secret 在计算上是困难的。

#### 3.1.1 数字示例

下面的小数字只用于展示等式，不具备实际安全性：

```text
p = 23，g = 2
客户端私钥 a = 6，公钥 A = 2^6 mod 23 = 18
服务端私钥 b = 7，公钥 B = 2^7 mod 23 = 13

客户端：13^6 mod 23 = 6
服务端：18^7 mod 23 = 6
```

双方都得到 Shared Secret `6`，但没有直接把它发给对方。真实协议使用经过选择的大参数，并进行公钥检查和密钥派生。有限域 DH 的协议实例见 [RFC 2631](https://www.rfc-editor.org/rfc/rfc2631.html#section-2.1.1)。

### 3.2 ECDH

ECDH（Elliptic Curve Diffie–Hellman）把 DH 的协商思路应用到椭圆曲线群中。它使用曲线上的点与标量乘法，而非前述有限域模幂运算。

```text
公开参数：约定的椭圆曲线与基点 G

客户端：私钥 a，公钥 A = aG
服务端：私钥 b，公钥 B = bG

客户端计算：aB = abG
服务端计算：bA = abG
```

双方得到相同的共享点，再按具体方案从中提取 Shared Secret 并派生密钥。这里的 `aG` 是椭圆曲线标量乘法，不是普通整数乘法。参见 [RFC 6090：ECDH](https://www.rfc-editor.org/rfc/rfc6090.html#section-4)。

### 3.3 数学结构对比

| 对比 | 有限域 DH | ECDH |
| --- | --- | --- |
| 数学运算 | 模幂运算 | 椭圆曲线标量乘法 |
| 公钥形式 | 有限域中的元素 | 曲线点的编码，具体形式取决于方案 |
| 共同目标 | 协商 Shared Secret | 协商 Shared Secret |

ECDH 本身不限定密钥是否临时生成，也不提供签名。ECDSA 是另一种椭圆曲线算法，用于数字签名，不应与 ECDH 混淆。

### 3.4 身份认证与密钥派生

DH 与 ECDH 本身都不认证对端身份。攻击者若替换公钥，就可能分别与通信双方协商 Secret，因此需要数字签名、证书或预共享密钥等认证机制配合。

协商出的 Shared Secret 通常还需经过密钥派生，用于生成实际的对称加密密钥。签名认证、密钥协商和数据加密各自承担不同职责。

### 3.5 临时密钥与前向保密

#### 3.5.1 DHE 与 ECDHE

末尾的 E 表示 Ephemeral（临时），强调密钥的使用方式，而非另一套数学原理：

| 数学基础 | 算法名称 | 使用临时密钥时的名称 |
| --- | --- | --- |
| 有限域 | DH | DHE |
| 椭圆曲线 | ECDH | ECDHE |

DH、ECDH 名称本身不限定密钥生命周期，不能直接将它们理解为静态密钥方式。

#### 3.5.2 静态与临时密钥

| 对比 | 静态方式 | 临时方式（DHE、ECDHE） |
| --- | --- | --- |
| 密钥交换私钥 | 长期复用 | 为本次协商生成临时私钥 |
| 使用结束后 | 保留供后续使用 | 安全销毁临时私钥与不再需要的 Secret |
| 前向保密 | 不能仅凭静态协商保证 | 正确使用并销毁临时密钥时可提供 |

#### 3.5.3 前向保密的含义与条件

前向保密指：攻击者记录了过去的通信，即使日后取得长期身份认证私钥，也不能仅凭它恢复过去的会话密钥。DHE 和 ECDHE 都可以提供这一性质。

在使用数字签名认证的临时密钥协商中，两类私钥职责不同：

```text
长期签名私钥 → 签名认证身份
临时 DH / ECDH 私钥 → 协商本次通信的 Shared Secret
```

前向保密依赖新鲜临时密钥的生成、正确使用和使用后销毁，不意味着当前会话密钥泄露后数据仍然安全。参见 [RFC 8422：临时密钥与前向保密](https://www.rfc-editor.org/rfc/rfc8422.html#section-2)。

### 3.6 DH 与 ECDH 的优劣

比较时应以相近的安全强度为前提，不能直接按密钥位数判断谁更安全。

| 方面 | 有限域 DH | ECDH |
| --- | --- | --- |
| 参数与公钥大小 | 通常更大，传输开销较高 | 通常更紧凑，节省带宽 |
| 计算成本 | 大参数下的模幂运算通常较重 | 现代实现通常效率较高，但取决于曲线、硬件和库 |
| 兼容性 | 部分旧系统或既有实现支持更好 | 适合支持椭圆曲线的现代系统 |
| 实现要求 | 需要选择合适的群、检查对端公钥 | 需要选择合适的曲线，并按具体方案检查和处理公钥 |

例如，约 128 位经典安全强度可对应有限域方案的 3072 位模数、256 位子群阶，或约 256 位的椭圆曲线群阶。这里比较的是数学参数大小，不是最终公钥编码的字节数。参见 [NIST SP 800-57 Part 1 Rev. 5，表 2](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-57pt1r5.pdf)。

两者都需要可靠的随机数、正确的参数与实现，也都不能单独认证通信对端的身份。ECDH 的主要优势是同等安全强度下更紧凑；实际速度应在目标环境中测量，不能保证所有实现都更快。

### 3.7 选择思路

仅在有限域 DH 与 ECDH 之间选择时，若不受兼容性或特定实现要求限制，通常优先考虑 ECDH，以减少通信和计算开销。这是一般工程取舍，具体仍需结合目标环境的性能验证。

是否使用临时密钥是另一个选择：需要前向保密时，有限域 DH 采用 DHE，ECDH 采用 ECDHE。两者都可提供前向保密，前提是正确生成、使用并销毁临时私钥及不再需要的 Secret。

因此，选择有限域还是椭圆曲线，主要考虑参数大小、性能与兼容性；前向保密则取决于密钥的使用方式及协议设计，并非 ECDHE 独有的能力。DH、ECDH 名称本身都不保证前向保密。

## 4. 用途对比

| 算法 | 主要用途 | 核心特点 |
| --- | --- | --- |
| RSA | 加密或数字签名 | 加密与签名使用不同方案，分别保护机密性和验证来源 |
| DH | 密钥协商 | 基于有限域运算，双方独立计算相同的 Shared Secret |
| ECDH | 密钥协商 | 基于椭圆曲线运算，名称本身不限定密钥生命周期 |
| DHE | 使用临时密钥的密钥协商 | 沿用有限域 DH 原理，通过临时密钥的正确使用与销毁支持前向保密 |
| ECDHE | 使用临时密钥的密钥协商 | 沿用 ECDH 原理，通过临时密钥的正确使用与销毁支持前向保密 |

RSA 签名和 ECDHE 可以配合使用：前者认证身份，后者协商 Shared Secret。Shared Secret 还需经过密钥派生，生成实际用于对称加密的密钥。
