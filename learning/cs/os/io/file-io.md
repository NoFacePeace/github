# 文件 I/O

文件 I/O 关注应用程序如何读取、修改文件内容，以及数据如何在应用程序、内核缓存和存储设备之间流动。下面以 Linux 上普通磁盘文件的读写为例。

## 1. Page Cache（页缓存）

Page Cache 是内核使用物理内存保存的文件数据缓存，用于减少对存储设备的访问。它缓存的是文件某个偏移范围内的数据，而不是文件描述符本身；多个进程访问同一个文件的同一部分时，通常可以共享这些缓存数据。

Page Cache 位于文件 I/O 与内存管理的交界处：文件 I/O 使用它加速读写，内存管理负责缓存内存的分配和回收。这里从文件读写流程出发介绍它。

### 1.1 读取流程与预读

普通缓冲读取的基本流程如下：

1. 应用程序调用 `read(fd, buffer, size)`。
2. 内核检查目标文件范围的数据是否已在 Page Cache 中，并且可以使用。
3. 如果缓存命中，内核直接将数据复制到应用程序的 buffer。
4. 如果缓存未命中，内核从存储设备读取所需数据到 Page Cache，再复制到应用程序的 buffer。

```text
缓存命中：Page Cache → 应用程序 buffer
缓存未命中：存储设备 → Page Cache → 应用程序 buffer
```

因此，调用 `read()` 不一定产生磁盘读取。第二次读取同一个文件通常更快，但前提是数据仍在缓存中。缓存命中也不代表没有开销，普通 `read()` 仍涉及系统调用和向用户空间复制数据。

对于顺序访问，内核还可以进行预读（readahead）：提前将后续可能访问的数据加载到 Page Cache，减少后续读取的等待。预读不保证总能提升性能；没有被使用的预读数据会占用内存和 I/O 带宽。

### 1.2 写入流程与脏页

默认的缓冲写入通常先更新 Page Cache，再由内核写回存储设备：

```text
应用程序 buffer → write() → Page Cache（脏页）
                                      ↓ 写回
                                  存储设备
```

- **干净页（clean page）**：缓存中的数据与其后备存储一致，无需写回即可丢弃。
- **脏页（dirty page）**：缓存中的数据已修改，尚未完成向后备存储的写回。
- **写回（writeback）**：将修改后的数据提交到存储设备；成功完成且期间没有再次修改的数据可以恢复为干净状态。

后台写回、脏页积累达到一定条件，以及应用程序主动请求同步，都可能促使数据写回。延迟写回可以合并写入，但也意味着 `write()` 成功返回通常不等于数据已经持久化。

缓冲写入也不保证立即返回：内存不足、脏页过多等情况下，写入线程可能等待或受到限速。应用程序还需要处理部分写入和错误，不能假定一次 `write()` 就写完全部数据。

### 1.3 缓存回收

Page Cache 会占用内存，但这部分内存并非永久保留。内存紧张时，内核可以回收可释放的干净页；脏页通常需要先完成写回，再释放对应内存。回收后重新读取这些数据，可能再次访问存储设备。

因此，缓存占用较大本身不代表内存泄漏。缓存能提高重复读取的性能，但如果工作集超过可用内存，频繁淘汰和重新读取也会增加磁盘 I/O。

## 2. 用户态缓冲与 Page Cache

应用程序或语言运行库也可以维护自己的缓冲区，例如 C 标准库的 `FILE *` 缓冲。它与内核 Page Cache 是不同层次：

```text
应用程序 → 用户态缓冲 → write() → Page Cache → 存储设备
```

用户态缓冲主要用于合并小块操作、减少系统调用；Page Cache 用于缓存文件数据、减少存储设备访问。使用用户态缓冲时，仅将数据写入缓冲区，甚至还没有发生 `write()` 系统调用。

## 3. 写回与持久化

| 操作 | 主要作用 | 是否保证文件数据已持久化 |
| --- | --- | --- |
| 普通缓冲 `write()` | 将本次成功写入的数据交给内核，通常更新 Page Cache | 不保证 |
| `fflush()` | 将 C 标准库用户态输出缓冲交给底层写入接口 | 不保证 |
| `fsync()` | 同步文件数据及相关元数据，并等待设备报告完成 | 成功返回时提供对应的持久化保证 |
| `fdatasync()` | 同步文件数据及正确读取这些数据所必需的元数据 | 成功返回时提供对应的数据持久化保证 |

如果使用 `FILE *` 等用户态缓冲，需要先成功刷新该缓冲，再对底层文件描述符执行同步，并检查每一步的错误。同步文件本身也不保证新建或重命名后的目录项已经持久化；相关场景还需要同步对应目录。

参考：[fsync 与 fdatasync 接口文档](https://man7.org/linux/man-pages/man2/fsync.2.html)。

## 4. 与 mmap、Direct I/O 的关系

| 访问方式 | 与 Page Cache 的关系 |
| --- | --- |
| 普通缓冲 `read()` / `write()` | 通常经过 Page Cache，在用户缓冲区与缓存之间复制数据 |
| 普通文件的 `mmap()` | 通常通过文件映射访问 Page Cache 中的数据，无需每次调用 `read()` 将数据复制到独立 buffer |
| Direct I/O（`O_DIRECT`） | 在文件系统支持并满足相应要求时，绕过 Page Cache 传输文件数据 |

文件映射的 `MAP_SHARED` 修改可以作用于底层文件；`MAP_PRIVATE` 修改采用写时复制，不会写回原文件。`mmap()` 也不等于数据立即持久化，访问未驻留的数据时仍可能因缺页而触发读取。

`O_DIRECT` 通常对缓冲区地址、文件偏移和长度有对齐要求，具体限制取决于文件系统与设备。它不等于异步 I/O，也不自动提供 `O_SYNC` 或 `fsync()` 的持久化语义。

Page Cache 主要讨论文件数据缓存。网络 Socket 的收发缓冲区属于另一套机制，不能因为都使用 `read()` / `write()` 就将它们视为 Page Cache。

参考：[Linux Page Cache 文档](https://www.kernel.org/doc/html/latest/mm/page_cache.html)、[open 中的 O_DIRECT 说明](https://man7.org/linux/man-pages/man2/open.2.html)。
