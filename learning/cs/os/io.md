# I/O 学习笔记

I/O（Input/Output，输入/输出）指系统与外部设备之间的数据交换，例如读取文件、写入磁盘以及通过网络收发数据。

## 1. 学习内容

- 基本概念：文件描述符、用户态与内核态、系统调用。
- 数据传输：设备、中断、DMA 与内核缓冲区。
- I/O 模型：阻塞 I/O、非阻塞 I/O、I/O 多路复用与异步 I/O。
- 文件 I/O：页缓存、缓冲 I/O、直接 I/O 与数据持久化。
- 网络 I/O：Socket、收发缓冲区与事件通知。
- 性能分析：吞吐量、延迟、系统调用开销与数据拷贝。

## 2. I/O 模型

以 Socket 接收数据为例，可以将一次读取理解为两个阶段：等待数据就绪，以及将数据从内核缓冲区复制到应用程序缓冲区。不同 I/O 模型的主要区别在于：应用程序如何等待数据，以及由谁发起并完成数据读取。

### 2.1 基本概念

#### 2.1.1 同步与异步

以读取数据为例，同步与异步的区别在于如何提交读取，以及何时取得完成结果。两者都可以由系统将数据写入应用程序提供的缓冲区（buffer）。

- **同步 I/O**：应用程序调用 `read` / `recv`，从本次调用取得读取结果。成功返回时，本次读到的数据已经在 buffer 中；非阻塞读取在没有数据时会返回 `EAGAIN` 等错误，需要应用程序之后重试。
- **异步 I/O**：应用程序先提交读取请求并指定 buffer，再通过完成通知或完成队列取得结果。请求成功完成时，数据已经在 buffer 中，无需再次调用 `read` / `recv`。

例如，读取 `hello` 的过程可以表示为：

```text
同步读取：调用 read(buffer) → 返回读取字节数 5，buffer 中已有 hello
异步读取：提交读取请求(buffer) → 取得完成结果 → 检查读到 5 字节，使用 buffer 中的 hello
```

异步请求提交成功并不表示读取已经完成；使用 buffer 中的数据前，需要取得完成结果，并检查错误和实际读取字节数。异步请求也可能很快完成，关键是提交请求与取得完成结果在接口上分开。

在这里介绍的五种经典模型中，阻塞 I/O、非阻塞 I/O、I/O 多路复用和信号驱动 I/O 都属于同步 I/O，只有异步 I/O 属于异步模型。

#### 2.1.2 阻塞与非阻塞

阻塞与非阻塞描述的是：调用无法立即取得进展时，是否等待。

- **阻塞读取**：暂时没有数据时，调用线程等待，直到可以返回数据、遇到错误或其他结束条件。
- **非阻塞读取**：暂时没有数据时，立即返回 `EAGAIN` 或 `EWOULDBLOCK`，应用程序可以先执行其他工作，再尝试读取。

同步不等于阻塞，非阻塞也不等于异步。非阻塞读取返回 `EAGAIN` 后，不会留下一个等待系统继续完成的读取请求；异步请求成功提交后，系统负责执行该请求，应用程序之后取得完成结果。

#### 2.1.3 就绪通知与完成通知

- **就绪通知**：表示可以尝试读写。例如，`epoll` 返回 Socket 可读事件后，应用程序仍需调用 `read` / `recv` 将数据读入 buffer。
- **完成通知**：表示此前提交的 I/O 请求已经结束。异步读取成功完成后，应用程序根据实际读取字节数使用 buffer 中的数据，无需再次发起读取来获取这批数据。

就绪事件也可能对应文件结束或错误，完成通知也可能报告失败，因此都需要检查实际操作结果。

非阻塞 I/O 与多路复用通常配合使用：多路复用帮助应用程序等待多个连接的就绪事件，非阻塞模式保证后续读取在无数据时立即返回。

### 2.2 阻塞 I/O

应用程序调用读取接口后，如果没有数据可读，调用线程会阻塞。数据就绪并复制到应用程序缓冲区后，调用才返回。其流程简单，但等待期间该线程无法执行其他任务。

### 2.3 非阻塞 I/O

应用程序将 Socket 设置为非阻塞模式后，如果没有数据可读，读取调用会立即返回错误，例如 `EAGAIN` 或 `EWOULDBLOCK`。应用程序可以稍后重试；持续循环重试会消耗 CPU。数据就绪时，应用程序仍需调用读取接口获取数据。

### 2.4 I/O 多路复用

应用程序通过 `select`、`poll` 或 `epoll` 等接口等待多个文件描述符的就绪事件，再对就绪的描述符执行读写。等待接口本身可以阻塞，但一个线程能够同时等待多个连接，无需为每个连接分别阻塞一个线程。

就绪通知表示当前可以尝试 I/O，并不表示数据已经读入应用程序缓冲区。实际使用时通常配合非阻塞 Socket，避免就绪状态变化导致后续读写意外阻塞。

#### 2.4.1 select

`select` 使用 `fd_set` 表示关注的文件描述符集合，分别传入读、写和异常条件集合。可以将集合理解为位图：某一位对应一个描述符，置位表示关注它。参数 `nfds` 是被检查的最大描述符编号加一。

一次调用的流程如下：

1. 应用程序使用 `FD_ZERO`、`FD_SET` 构建集合，将集合和超时时间传给 `select`。
2. 内核读取集合，检查所关注文件的就绪状态；在需要等待时，将当前线程关联到相应等待队列。
3. 如果没有就绪事件且允许等待，线程睡眠；被事件唤醒后，内核重新检查就绪状态，也可能因超时或信号而返回。
4. 返回的集合只保留就绪描述符。应用程序使用 `FD_ISSET` 检查集合，再执行实际读写。

```text
输入读集合：{A, B, C}
        ↓ select
输出读集合：{B, C}
        ↓
应用程序检查集合，调用 read(B)、read(C)
```

由于集合会被修改，每轮等待前需要重新设置或从备份恢复。内核需要按描述符范围检查集合，应用程序也需要检查哪些描述符被置位；连接很多时，这些检查会增加开销。

Linux 常用的 glibc `fd_set` 固定为 1024 位，因此可放入的描述符编号必须小于 1024。这是描述符编号限制，并不意味着只要连接数少于 1024 就一定可用。

参考：[select 接口文档](https://man7.org/linux/man-pages/man2/select.2.html)、[Linux select/poll 实现](https://github.com/torvalds/linux/blob/master/fs/select.c)。

#### 2.4.2 poll

`poll` 使用 `pollfd` 数组描述关注的对象，每一项分别保存描述符、关注事件和返回事件：

```c
struct pollfd {
    int fd;         // 文件描述符
    short events;   // 应用程序关注的事件，例如 POLLIN
    short revents;  // 内核返回的事件
};
```

一次调用的流程如下：

1. 应用程序构建数组，填写各项的 `fd` 和 `events`，调用 `poll`。
2. 内核读取数组，逐项检查文件的就绪状态，并在需要时注册等待队列。
3. 没有事件时可进入睡眠；被唤醒后重新检查，或者因超时、信号而返回。
4. 内核通过各项的 `revents` 返回事件。应用程序遍历数组，对有事件的描述符执行读写。

```text
输入数组：[{A, POLLIN}, {B, POLLIN}, {C, POLLIN}]
        ↓ poll
返回事件：[A: 无事件, B: POLLIN, C: POLLIN]
        ↓
应用程序遍历 revents，调用 read(B)、read(C)
```

`events` 与 `revents` 分开，因而不需要像 `select` 那样恢复被覆盖的关注集合。数组也没有 `fd_set` 的固定 1024 位限制，但仍受进程文件描述符上限等资源限制。

`poll` 每轮仍需传入数组，内核和应用程序仍需遍历相关条目。它改善了 `select` 的接口和编号限制，没有消除大量连接下的扫描开销。另外，`poll` 等待时可以睡眠，并不是一直占用 CPU 忙轮询。

参考：[poll 接口文档](https://man7.org/linux/man-pages/man2/poll.2.html)、[Linux select/poll 实现](https://github.com/torvalds/linux/blob/master/fs/select.c)。

#### 2.4.3 epoll

`epoll` 将关注集合保留在内核中，把注册和等待拆成三个接口：

- `epoll_create1`：创建 epoll 实例。
- `epoll_ctl`：添加、修改或删除关注的描述符及事件。
- `epoll_wait`：等待并获取一批就绪事件。

Linux 实现中，关注项通过[红黑树](../data-structures/trees/red-black-tree.md)组织，另外维护就绪链表。注册描述符时，内核将回调挂到目标文件的等待队列；事件发生时，回调将对应关注项标记为就绪，并在需要时唤醒等待线程。注册时也会检查已有的就绪状态，因此数据先到达、后注册也能被处理。

```text
epoll_ctl 注册 A、B、C → 内核保存关注集合
                              ↓
B 有数据 → 等待队列回调 → B 进入就绪链表
                              ↓
epoll_wait → 检查就绪项，向应用程序返回事件
                              ↓
                          read(B)
```

`epoll_wait` 从就绪项中检查并返回事件，无需每次由应用程序重新提交完整关注集合。它仍然需要把事件结果复制到用户空间，也不会自动把 Socket 数据读入应用 buffer。

当连接很多、每次只有少量连接活跃时，这种方式能够减少反复扫描整个关注集合的开销。但不能将整个 epoll 简化为“所有操作都是 O(1)”：注册管理、就绪检查和返回多个事件都需要工作。

`epoll` 支持两种主要触发方式：

| 模式 | 通知行为 | 读取时的处理方式 |
| --- | --- | --- |
| 水平触发（LT，默认） | 只要仍满足就绪条件，后续等待仍可返回该事件 | 可以分批读取，未读完时仍可继续获得通知 |
| 边缘触发（ET，设置 `EPOLLET`） | 按新的就绪事件通知，不保证仅因仍有未读数据而再次通知 | 通常使用非阻塞读取，读到 `EAGAIN` 后再等待 |

例如，收到可读事件时有 100 字节，应用程序只读了 40 字节：LT 下剩余数据会使连接继续保持可读；ET 下如果直接回去等待，剩余的 60 字节可能无法触发下一次通知。

实际事件循环还应处理读取返回 `0`、错误和部分读写，并控制单个连接的处理量，避免一个连接长期占用线程。ET 下如果主动暂停读取，需要自行安排后续处理，不能只依赖新的边缘通知。

参考：[epoll 接口与触发模式](https://man7.org/linux/man-pages/man7/epoll.7.html)、[Linux epoll 实现](https://github.com/torvalds/linux/blob/master/fs/eventpoll.c)。

### 2.5 信号驱动 I/O

应用程序启用信号通知后，可以继续执行其他任务。当发生相关 I/O 事件时，内核通过信号通知应用程序，应用程序再发起读取。信号通知与实际数据读取是两个独立步骤。

### 2.6 异步 I/O

应用程序提交 I/O 请求后可以继续执行其他任务，由系统完成请求，并通过完成通知或完成队列告知结果。对于读取请求，完成结果说明本次读取已结束，可根据返回的字节数或错误信息处理缓冲区。

### 2.7 模型对比

| 模型 | 等待或通知方式 | 数据读取方式 |
| --- | --- | --- |
| 阻塞 I/O | 读取调用等待数据 | 本次读取调用完成数据复制后返回 |
| 非阻塞 I/O | 无数据时立即返回，稍后重试 | 应用程序再次调用读取接口 |
| I/O 多路复用 | 等待多个描述符的就绪事件 | 应用程序收到就绪事件后调用读取接口 |
| 信号驱动 I/O | 通过信号通知 I/O 事件 | 应用程序收到通知后调用读取接口 |
| 异步 I/O | 提交请求后获取完成结果 | 系统执行已提交的读取请求 |

阻塞与非阻塞描述调用在无法立即取得进展时是否等待；就绪通知与完成通知则区分通知发生在哪个阶段。非阻塞 I/O 和 I/O 多路复用都不等同于异步 I/O。

## 3. 文件 I/O

文件 I/O 关注应用程序如何读取、修改文件内容，以及数据如何在应用程序、内核缓存和存储设备之间流动。下面以 Linux 上普通磁盘文件的读写为例。

### 3.1 Page Cache（页缓存）

Page Cache 是内核使用物理内存保存的文件数据缓存，用于减少对存储设备的访问。它缓存的是文件某个偏移范围内的数据，而不是文件描述符本身；多个进程访问同一个文件的同一部分时，通常可以共享这些缓存数据。

Page Cache 位于文件 I/O 与内存管理的交界处：文件 I/O 使用它加速读写，内存管理负责缓存内存的分配和回收。这里从文件读写流程出发介绍它。

#### 3.1.1 读取流程与预读

普通缓冲读取的基本流程如下：

1. 应用程序调用 `read(fd, buffer, size)`。
2. 内核检查目标文件范围的数据是否已在 Page Cache 中，并且可以使用。
3. 如果缓存命中，内核直接将数据复制到应用程序的 buffer。
4. 如果缓存未命中，内核从存储设备读取所需数据到 Page Cache，再复制到应用程序的 buffer。

```text
缓存命中：Page Cache → 应用程序 buffer
缓存未命中：存储设备 → Page Cache → 应用程序 buffer
```

因此，调用 `read()` 不一定产生磁盘读取。第二次读取同一个文件通常更快，但前提是数据仍在缓存中。缓存命中也不代表没有开销，普通 `read()` 仍涉及系统调用和向用户空间复制数据。

对于顺序访问，内核还可以进行预读（readahead）：提前将后续可能访问的数据加载到 Page Cache，减少后续读取的等待。预读不保证总能提升性能；没有被使用的预读数据会占用内存和 I/O 带宽。

#### 3.1.2 写入流程与脏页

默认的缓冲写入通常先更新 Page Cache，再由内核写回存储设备：

```text
应用程序 buffer → write() → Page Cache（脏页）
                                      ↓ 写回
                                  存储设备
```

- **干净页（clean page）**：缓存中的数据与其后备存储一致，无需写回即可丢弃。
- **脏页（dirty page）**：缓存中的数据已修改，尚未完成向后备存储的写回。
- **写回（writeback）**：将修改后的数据提交到存储设备；成功完成且期间没有再次修改的数据可以恢复为干净状态。

后台写回、脏页积累达到一定条件，以及应用程序主动请求同步，都可能促使数据写回。延迟写回可以合并写入，但也意味着 `write()` 成功返回通常不等于数据已经持久化。

缓冲写入也不保证立即返回：内存不足、脏页过多等情况下，写入线程可能等待或受到限速。应用程序还需要处理部分写入和错误，不能假定一次 `write()` 就写完全部数据。

#### 3.1.3 缓存回收

Page Cache 会占用内存，但这部分内存并非永久保留。内存紧张时，内核可以回收可释放的干净页；脏页通常需要先完成写回，再释放对应内存。回收后重新读取这些数据，可能再次访问存储设备。

因此，缓存占用较大本身不代表内存泄漏。缓存能提高重复读取的性能，但如果工作集超过可用内存，频繁淘汰和重新读取也会增加磁盘 I/O。

### 3.2 用户态缓冲与 Page Cache

应用程序或语言运行库也可以维护自己的缓冲区，例如 C 标准库的 `FILE *` 缓冲。它与内核 Page Cache 是不同层次：

```text
应用程序 → 用户态缓冲 → write() → Page Cache → 存储设备
```

用户态缓冲主要用于合并小块操作、减少系统调用；Page Cache 用于缓存文件数据、减少存储设备访问。使用用户态缓冲时，仅将数据写入缓冲区，甚至还没有发生 `write()` 系统调用。

### 3.3 写回与持久化

| 操作 | 主要作用 | 是否保证文件数据已持久化 |
| --- | --- | --- |
| 普通缓冲 `write()` | 将本次成功写入的数据交给内核，通常更新 Page Cache | 不保证 |
| `fflush()` | 将 C 标准库用户态输出缓冲交给底层写入接口 | 不保证 |
| `fsync()` | 同步文件数据及相关元数据，并等待设备报告完成 | 成功返回时提供对应的持久化保证 |
| `fdatasync()` | 同步文件数据及正确读取这些数据所必需的元数据 | 成功返回时提供对应的数据持久化保证 |

如果使用 `FILE *` 等用户态缓冲，需要先成功刷新该缓冲，再对底层文件描述符执行同步，并检查每一步的错误。同步文件本身也不保证新建或重命名后的目录项已经持久化；相关场景还需要同步对应目录。

参考：[fsync 与 fdatasync 接口文档](https://man7.org/linux/man-pages/man2/fsync.2.html)。

### 3.4 与 mmap、Direct I/O 的关系

| 访问方式 | 与 Page Cache 的关系 |
| --- | --- |
| 普通缓冲 `read()` / `write()` | 通常经过 Page Cache，在用户缓冲区与缓存之间复制数据 |
| 普通文件的 `mmap()` | 通常通过文件映射访问 Page Cache 中的数据，无需每次调用 `read()` 将数据复制到独立 buffer |
| Direct I/O（`O_DIRECT`） | 在文件系统支持并满足相应要求时，绕过 Page Cache 传输文件数据 |

文件映射的 `MAP_SHARED` 修改可以作用于底层文件；`MAP_PRIVATE` 修改采用写时复制，不会写回原文件。`mmap()` 也不等于数据立即持久化，访问未驻留的数据时仍可能因缺页而触发读取。

`O_DIRECT` 通常对缓冲区地址、文件偏移和长度有对齐要求，具体限制取决于文件系统与设备。它不等于异步 I/O，也不自动提供 `O_SYNC` 或 `fsync()` 的持久化语义。

Page Cache 主要讨论文件数据缓存。网络 Socket 的收发缓冲区属于另一套机制，不能因为都使用 `read()` / `write()` 就将它们视为 Page Cache。

参考：[Linux Page Cache 文档](https://www.kernel.org/doc/html/latest/mm/page_cache.html)、[open 中的 O_DIRECT 说明](https://man7.org/linux/man-pages/man2/open.2.html)。
