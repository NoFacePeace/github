# 设备管理

设备是操作系统与外部世界交换数据的硬件对象，例如磁盘、网卡、键盘、显示器和定时器。操作系统通过设备驱动和 I/O 子系统，为应用程序提供统一的设备访问方式。设备管理关注操作系统如何与硬件设备协作，包括设备驱动、中断、DMA 和网络设备收包机制。

1. **设备基础**：学习设备按数据访问方式、设备功能和存在形式的分类。
2. **设备访问路径**：理解应用程序、系统调用、I/O 子系统、设备驱动、设备控制器和硬件设备之间的关系。
3. **设备组成**：理解设备控制器、固件、DMA 和具体硬件之间的关系。
4. **设备驱动**：掌握驱动的职责，包括设备初始化、寄存器配置、队列管理、状态处理和数据收发。
5. **网卡基础**：理解网卡的组成、收发队列，以及网卡从接收信号到将数据包交给网络协议栈的处理流程。
6. **中断处理**：理解硬中断、softirq、`ksoftirqd` 和 workqueue 的分工与执行关系。

## 1. 设备分类

设备可以从不同维度进行分类，这些分类维度可以交叉组合。

### 1.1 按数据访问方式

- **字符设备**：以字符或字节流为单位顺序传输数据，通常不支持随机访问，例如键盘、串口和终端。
- **块设备**：以固定大小的数据块为单位进行读写，通常支持随机访问和缓存，例如硬盘、SSD 和 U 盘。
- **网络设备**：以数据包为单位收发数据，通常通过网络协议栈和 Socket 接口访问，例如物理网卡和虚拟网卡。

### 1.2 按设备功能

- **输入设备**：接收外部输入，例如键盘、鼠标和摄像头。
- **输出设备**：向外部产生输出，例如显示器、打印机和音响。
- **存储设备**：保存和读取数据，例如硬盘、SSD 和 U 盘。
- **通信设备**：与其他设备或系统交换数据，例如网卡、无线网卡和串口。
- **控制与定时设备**：提供硬件控制或定时功能，例如 GPIO 控制器和定时器。

### 1.3 按是否真实存在

- **物理设备**：实际存在的硬件设备，例如物理网卡、硬盘和键盘。
- **虚拟设备或伪设备**：由操作系统或软件模拟出来的设备，例如虚拟网卡、`/dev/null` 和 `/dev/zero`。

同一个设备可以同时属于多个分类。例如，物理网卡是网络设备、通信设备和物理设备；虚拟网卡是网络设备、通信设备和虚拟设备。

## 2. 设备访问路径

应用程序通常不会直接操作硬件，而是通过系统调用和 I/O 子系统访问设备。

### 2.1 软件到硬件的访问路径

```text
应用程序
    ↓
系统调用与通用接口
    ↓
I/O 子系统
    ↓
设备驱动（软件）
    ↓
设备控制器（硬件）
    ↓
具体设备（硬件）
```

这里重点描述请求的调用关系：上层软件通过设备驱动访问设备控制器，再由设备控制器控制具体硬件。

### 2.2 一次 I/O 请求的流程

以读取数据为例：

1. 应用程序通过系统调用发起读取请求。
2. I/O 子系统创建请求，并检查参数、权限和缓存。
3. 驱动将请求转换为设备命令。
4. 驱动通过寄存器和队列配置设备命令、数据缓冲区与 DMA 参数。
5. 设备控制器驱动具体硬件执行操作。
6. 设备通过中断或状态信息返回操作结果。
7. 驱动和 I/O 子系统处理结果，最终将数据或错误返回给应用程序。

## 3. 设备组成

设备可以看作一个整体，内部通常包含设备控制器、具体硬件，以及可能运行在控制器内部的固件。

### 3.1 组成关系

```text
设备（整体）
├── 设备控制器（硬件控制单元）
│   ├── 控制逻辑
│   ├── 寄存器
│   ├── DMA 和中断逻辑
│   └── 固件（运行在控制器内部的程序）
└── 具体硬件（完成存储、收发数据等功能）
```

这里将设备控制器与具体硬件分开，是为了说明结构和职责；在实际硬件中，设备控制器可能集成在设备内部，也可能由独立芯片或 SoC 模块提供。

### 3.2 组成部分

- **设备控制器**：负责接收驱动发出的命令，管理寄存器、队列、DMA 和中断。
- **固件**：运行在设备或控制器内部的底层程序，负责部分硬件初始化和控制逻辑。
- **具体硬件**：完成存储、数据收发、输入或输出等实际功能。

## 4. 设备驱动

设备驱动是运行在操作系统中的软件模块，位于 I/O 子系统和设备控制器之间，负责把通用设备接口转换为具体硬件可以执行的操作。驱动可以由硬件厂商、内核社区或操作系统开发者提供，但本身属于软件，不是设备控制器或固件。

驱动通过寄存器、队列、中断和 DMA 等机制控制设备，并将设备状态和处理结果反馈给操作系统。完整访问路径见第 2.1 节“软件到硬件的访问路径”。

### 4.1 驱动生命周期

一个驱动通常经历以下阶段：

1. **发现与加载**：操作系统发现设备，并加载匹配的驱动模块。
2. **初始化与探测**：驱动读取设备信息，分配资源，配置寄存器和队列。
3. **注册接口**：驱动向内核注册字符设备、块设备或网络设备接口。
4. **运行与处理 I/O**：驱动处理应用程序或内核子系统发起的 I/O 请求。
5. **错误恢复与状态管理**：处理超时、设备故障、链路变化和数据收发错误。
6. **挂起、恢复与卸载**：系统休眠、设备移除或驱动卸载时释放资源。

### 4.2 网卡驱动示例

以网卡驱动为例，驱动通常负责：

- 初始化和配置设备寄存器
- 创建和管理 RX/TX 队列
- 分配并映射 DMA 缓冲区
- 注册中断处理函数和 NAPI poll 回调
- 处理设备状态、错误和数据收发
- 配合网络协议栈完成数据包的发送和接收

网卡驱动如何配合 RX Ring、DMA 和 NAPI 完成收包，见第 5.3 节“网卡收包流程”。

## 5. 网卡

网卡是计算机连接网络并收发数据包的设备。物理网卡通过以太网、无线网络等介质传输数据；虚拟网卡则由操作系统或虚拟化软件提供，例如回环设备、TUN/TAP 设备和虚拟机使用的虚拟网络接口。

### 5.1 硬件组成

物理网卡通常包含以下组成部分：

- **接口与介质**：例如以太网接口、光模块或无线射频模块，负责连接实际网络。
- **PHY**：在物理信号和比特流之间转换，并负责链路协商。
- **MAC 与网卡控制器**：识别以太网帧，执行数据收发、队列管理、DMA 和中断等操作。
- **收发队列**：保存 Packet Descriptor，供网卡和驱动交换数据的位置与状态信息。
- **DMA 模块**：在网卡和主内存之间传输数据包，减少 CPU 搬运数据的开销。
- **中断模块**：在数据到达、发送完成或设备状态变化时通知 CPU。

不同网卡的集成方式并不完全相同。例如，PHY 可能集成在网卡芯片内部，也可能作为独立芯片存在。

```text
网线、光纤或无线介质
        ↕
       PHY
        ↕
MAC 与网卡控制器
        ↕
DMA、收发队列和中断
        ↕
主内存与 CPU
```

PHY 将电信号、光信号或无线信号解调、解码为比特流。MAC 再识别帧起始位置，将比特流按协议格式还原为以太网帧，并检查 FCS 等信息。

### 5.2 收发数据结构

网卡通常分别维护接收队列和发送队列：

- **RX（Receive）队列**：用于接收来自网络的数据。
- **TX（Transmit）队列**：用于向网络发送数据。

#### 5.2.1 Ring Buffer

Ring Buffer 是首尾相接、循环使用的固定大小队列。网卡中的 RX Ring 和 TX Ring 通常是一组 Packet Descriptor 组成的环形队列，而不是直接存放完整数据包的连续区域。

```text
RX Ring
┌──────────────┐
│ Descriptor 0 │ ──→ DMA 数据缓冲区 0
│ Descriptor 1 │ ──→ DMA 数据缓冲区 1
│ Descriptor 2 │ ──→ DMA 数据缓冲区 2
└──────────────┘
        ↑
    循环使用
```

网卡和驱动分别推进队列中的生产者位置与消费者位置。索引到达队列末尾后会回到开头，使固定数量的描述符可以被重复使用。

#### 5.2.2 Packet Descriptor 与数据缓冲区

Packet Descriptor 是数据包描述符，通常记录：

- 数据缓冲区的内存地址
- 数据长度
- 处理完成状态
- 网卡或驱动的所有权
- 校验和、分段等附加信息

Descriptor 本身通常不保存完整数据包。真正的数据存放在 Descriptor 指向的 DMA 数据缓冲区中：

```text
Ring
  └── Descriptor
          ├── 地址
          ├── 长度和状态
          └──→ DMA 数据缓冲区
                     └── 网络包字节
```

DMA 数据缓冲区由内核中的网卡驱动分配和管理，但它只是内核缓冲区的一种，不能与 Socket 接收缓冲区等同。

#### 5.2.3 `sk_buff`

`sk_buff`，通常简称 skb，是 Linux 内核用于描述和管理网络数据包的数据结构。skb 记录数据地址、长度、协议头位置、接收设备、协议类型和校验和状态等信息。

```text
skb
├── 数据地址 ──→ 数据缓冲区
├── 数据长度
├── MAC、IP 和 TCP/UDP 头位置
├── 接收设备与协议类型
└── 校验和等控制信息
```

skb 不一定复制或直接保存完整数据包。现代驱动通常可以让 skb 引用 RX 数据缓冲区或相关内存页，并在协议栈各层之间传递 skb。

网络协议栈通过 skb 中的数据指针、长度和各层协议头位置，读取其指向的数据包字节。处理过程通常不需要在每一层复制或删除协议头，而是调整 skb 的当前数据范围和头部偏移：

```text
内核数据缓冲区
└── [以太网头][IP 头][TCP/UDP 头][应用数据]
        ↑
      skb 记录各层协议头位置和当前有效数据范围
```

以太网层、IP 层和 TCP/UDP 层依次解析对应协议头，并更新 skb 的元数据。校验和处理、分片重组、GRO、NAT 或防火墙等功能可能修改或重新组织数据，但应用程序不会直接看到 skb。

#### 5.2.4 多队列

现代网卡通常支持多组 RX/TX Ring。不同队列可以绑定到不同 CPU，使网络收发工作分散到多个处理器上，提高并行处理能力。

### 5.3 网卡收包流程

#### 5.3.1 从物理信号到主内存

以接收以太网数据为例：

```text
电信号或光信号
    ↓
PHY 恢复比特流
    ↓
MAC 还原并校验以太网帧
    ↓
网卡内部接收缓冲区
    ↓
DMA 写入主内存中的 RX 数据缓冲区
    ↓
网卡更新 RX Descriptor 的长度和完成状态
```

接收前，驱动会准备 RX Descriptor 和数据缓冲区，并将缓冲区地址交给网卡。接收时，DMA 从网卡内部接收缓冲区读取数据，写入 Descriptor 指向的主内存区域。

此时数据包已经位于驱动管理的内核内存中，但还没有进入网络协议栈或 Socket 接收队列。网卡完成 DMA 后，会更新 RX Descriptor 中的数据长度、完成状态和校验和等信息，并将该缓冲区的使用权交还给驱动。

#### 5.3.2 从网卡驱动到协议栈

NAPI（New API）是 Linux 网络子系统常用的收包机制，采用“中断加轮询”的混合模式：

```text
网卡将 RX Descriptor 标记为完成
    ↓
网卡触发硬件中断
    ↓
驱动的硬中断处理函数调用 napi_schedule()
    ↓
内核将 NAPI 加入待处理队列，并标记 NET_RX_SOFTIRQ
    ↓
NET_RX_SOFTIRQ 的 net_rx_action() 执行
    ↓
调用驱动注册的 NAPI poll()
    ↓
批量检查 RX Descriptor，并处理 DMA 数据缓冲区
    ↓
创建 skb，使其引用数据缓冲区或相关内存页
    ↓
补充新的 RX 数据缓冲区和 Descriptor
    ↓
以太网层
    ↓
IP 层
    ↓
TCP/UDP 层
    ↓
查找对应 Socket
    ↓
放入 Socket 接收队列
```

硬中断主要负责确认事件、抑制该队列继续产生接收中断，并调度 NAPI，然后尽快退出。硬中断不会逐字节读取网络包，数据包本身已经由 DMA 写入主内存。

网络协议栈是 Linux 内核的一部分，由 CPU 执行，不在网卡中运行。从 `net_rx_action()`、NAPI `poll()` 到以太网、IP、TCP/UDP 处理，再到数据进入 Socket 接收队列，通常都在当前 CPU 的 `NET_RX_SOFTIRQ` 上下文中完成。启用多队列、RPS 或其他分流机制时，后续处理也可能被安排到其他 CPU。

NAPI 的 `poll()` 是驱动提供的回调函数，负责从 RX Ring 批量取包。它通常执行以下工作：

1. 检查 RX Descriptor，读取数据长度、校验和状态等信息。
2. 完成必要的 DMA 同步，创建或组装 skb，并交给网络协议栈。
3. 为 RX Ring 补充新的空缓冲区，更新 Descriptor 和 Ring 位置。
4. 根据实际处理数量判断结束本轮处理还是继续轮询。

数据缓冲区、Descriptor 与 skb 的关系见第 5.2 节“收发数据结构”。“取包”通常不表示复制完整数据，但具体驱动可能因为小包优化或数据布局调整产生额外复制。

`poll()` 接收 `budget` 参数，表示本轮最多处理的数据包数量：

- 处理数量小于 `budget`，并且 RX Ring 已经清空：完成本轮 NAPI 处理，重新开启该队列的接收中断。
- 处理数量达到 `budget`：可能仍有数据，保持 NAPI 调度状态，等待下一轮继续处理。

低流量时，中断能够及时通知 CPU；高流量时，NAPI 暂时抑制中断并批量处理数据，避免每个数据包都产生一次硬中断。NAPI 与 softirq 的分工见第 6.2 节“softirq”。

#### 5.3.3 从 Socket 到应用程序

协议栈根据协议、地址和端口找到目标 Socket，将 skb 或其承载的数据加入 Socket 接收队列。应用程序调用 `recv()` 或 `read()` 后，内核通常将有效数据复制到应用程序提供的用户空间缓冲区。

```text
Socket 接收队列
    ↓
recv() 或 read()
    ↓
内核复制数据到用户空间
    ↓
应用程序处理数据
```

应用程序执行 `recv()` 或 `read()` 时处于进程上下文，已经离开 softirq 收包阶段。普通应用程序不会访问 skb，而是由内核根据 Socket 类型复制协议栈处理后的有效载荷。例如，TCP Socket 向应用程序提供连续字节流，应用程序通常看不到以太网、IP 和 TCP 头，也看不到原始数据包边界。

#### 5.3.4 数据拷贝次数

现代 Linux 使用普通 Socket 收包时，典型数据路径如下：

```text
网卡
  └── DMA → 内核 RX 数据缓冲区
                ↓
           skb 与协议栈
                ↓
         Socket 接收队列
                ↓
  CPU 复制 → 用户空间缓冲区
```

如果只计算 CPU 执行的内存复制，通常有一次，即从内核空间复制到用户空间。网卡通过 DMA 将数据写入主内存属于一次数据传输，但不占用 CPU 逐字节搬运数据。

协议栈通常通过 skb 和内存页引用传递数据，不会在每一层复制完整数据包。部分驱动、数据布局调整或特殊处理可能产生额外复制，因此实际次数取决于驱动和协议栈处理方式。

### 5.4 网卡发包流程

发送方向与接收方向大致相反：

```text
应用程序调用 send() 或 write()
    ↓
数据进入内核 Socket 缓冲区
    ↓
TCP/UDP、IP 和以太网层处理
    ↓
网卡驱动填写 TX Descriptor
    ↓
DMA 从主内存中的 TX 数据缓冲区读取数据
    ↓
MAC 将以太网帧转换为比特流
    ↓
PHY 将比特流转换为物理信号
    ↓
网络介质
```

TX Descriptor 告诉网卡待发送数据的内存地址和长度。网卡发送完成后会更新 Descriptor 状态，驱动随后回收 skb、数据缓冲区和描述符。

## 6. 中断管理

操作系统使用中断响应硬件事件，并将不适合立即完成的工作延后处理。硬中断、softirq 和 workqueue 最终都需要 CPU 执行，它们的区别在于执行时机、执行上下文、是否允许睡眠，以及对其他任务的影响。

### 6.1 硬中断

硬件设备通过中断通知处理器，例如网卡收到数据、磁盘 I/O 完成或定时器到期。处理器暂停当前执行流，进入驱动注册的硬中断处理函数。

典型流程如下：

```text
硬件设备产生中断
    ↓
处理器进入硬中断处理程序
    ↓
确认和记录硬件事件
    ↓
安排 softirq 或其他后续工作
    ↓
返回被中断的执行流
```

硬中断具有较高的响应优先级。处理时间过长会推迟其他中断和正常进程的执行，因此硬中断处理函数通常只完成紧急、少量的工作，然后尽快退出。硬中断上下文不能睡眠，也不适合执行大量计算或复杂 I/O。

### 6.2 softirq

`softirq` 是 Linux 内核中的延后处理机制，用于执行不必在硬中断中立即完成、但仍要求较高处理效率的内核工作。使用 softirq 不能减少工作的计算量，但可以缩短硬中断占用 CPU 的时间，并允许内核批量处理积压的事件。

softirq 与处理器指令触发的“软件中断”不是同一个概念：

- 软件中断通常指程序执行特定指令，进入预定义的处理入口。
- softirq 是 Linux 内核内部安排和执行延后工作的机制。

#### 6.2.1 谁触发 softirq

硬件不能直接触发 softirq。硬件只能产生硬中断，随后由硬中断处理函数或其他内核代码将某类 softirq 标记为待处理。

以网络收包为例：

```text
网卡产生硬中断
    ↓
驱动调用 napi_schedule()
    ↓
内核将 NAPI 加入待处理队列
    ↓
标记 NET_RX_SOFTIRQ 为待处理
```

此外，网络发送、定时器到期、块设备 I/O 完成和 RCU 回调等内核事件也可能触发对应类型的 softirq。

#### 6.2.2 谁执行 softirq

softirq 最终由 CPU 执行，而不是由设备执行。通常有两种执行方式：

1. 硬中断退出时，当前 CPU 检查并执行待处理的 softirq。
2. softirq 数量较多、处理时间超过限制或未能及时完成时，由当前 CPU 对应的 `ksoftirqd` 内核线程继续处理。

softirq 处理函数仍然不能睡眠。需要等待资源、执行阻塞操作或进行较长处理的工作，应交给 workqueue 等可以在进程上下文中执行的机制。

#### 6.2.3 与 NAPI 的关系

网络接收使用的 `NET_RX_SOFTIRQ` 对应处理函数是 `net_rx_action()`。它遍历已经调度的 NAPI 实例，并调用驱动注册的 NAPI `poll()` 回调。因此，`poll()` 不是直接注册的 softirq 处理函数，而是由 `net_rx_action()` 间接调用。完整的数据路径见第 5.3 节“网卡收包流程”。

### 6.3 `ksoftirqd`

`ksoftirqd` 是 Linux 为每个 CPU 创建的内核线程，用来处理没有在其他上下文中及时完成的 softirq。线程名称通常类似：

```text
ksoftirqd/0
ksoftirqd/1
```

数字表示关联的 CPU。

`ksoftirqd` 使积压的 softirq 可以作为可调度的内核线程继续运行，避免 CPU 长时间停留在硬中断退出后的 softirq 处理中。但被它调用的 softirq 处理函数仍然遵守 softirq 上下文的限制，不能因为执行者是内核线程就随意睡眠。

如果 `ksoftirqd/N` 长时间占用较高 CPU，通常表示 CPU `N` 上存在较多软中断工作，常见原因包括：

- 网络收发包速率较高
- 网络包处理或协议栈开销较大
- 定时器事件过多
- 块设备 I/O 或其他内核子系统产生大量 softirq

排查时应结合每个 CPU 的软中断统计、网卡收发包速率、I/O 负载和中断亲和性一起分析，不能只根据线程名判断具体原因。

### 6.4 workqueue

workqueue 用于将延后的内核工作交给 `kworker` 内核工作线程执行。workqueue 运行在进程上下文中，通常允许睡眠，适合执行可能阻塞、需要等待资源或耗时较长的工作。

workqueue 不属于网卡正常收包的主路径。网卡驱动通常使用它处理设备重置、故障恢复、链路状态变化和配置更新等辅助任务：

```text
驱动发现需要延后处理的任务
    ↓
调用 queue_work()
    ↓
任务进入 workqueue
    ↓
kworker 执行任务函数
```

### 6.5 机制对比

| 机制 | 执行主体 | 是否可以睡眠 | 适合处理 |
|---|---|---|---|
| 硬中断 | 硬中断处理程序 | 否 | 紧急、少量处理 |
| softirq | softirq 处理函数 | 否 | 高性能、可延后的内核工作 |
| `ksoftirqd` | 每 CPU 内核线程 | 处理函数本身仍受 softirq 约束 | 消化积压的 softirq |
| workqueue | 内核工作线程 | 通常可以 | 需要睡眠或较长时间的工作 |

在正常网络收包过程中，硬中断负责快速响应，softirq 通过 NAPI `poll()` 延后并批量处理数据，积压时由 `ksoftirqd` 继续执行。workqueue 不在这条主路径上，只用于适合进程上下文的辅助任务。

### 6.6 与计算机组成原理的边界

处理器如何响应中断、中断向量如何定位以及硬件中断控制器如何工作，属于计算机组成原理的中断机制。`softirq`、`ksoftirqd` 和 workqueue 则是 Linux 操作系统对中断后续工作的管理和实现。
