# 设备管理

设备是操作系统与外部世界交换数据的硬件对象，例如磁盘、网卡、键盘、显示器和定时器。操作系统通过设备驱动和 I/O 子系统，为应用程序提供统一的设备访问方式。设备管理关注操作系统如何与硬件设备协作，包括设备驱动、中断、DMA 和网络设备收包机制。

1. **设备基础**：学习设备按数据访问方式、设备功能和存在形式的分类，以及 Linux 设备文件的基本概念。
2. **设备访问路径**：理解应用程序、系统调用、I/O 子系统、设备驱动、设备控制器和硬件设备之间的关系。
3. **设备组成**：理解设备控制器、固件、DMA 和具体硬件之间的关系。
4. **设备驱动**：掌握驱动的职责，包括设备初始化、寄存器配置、队列管理、状态处理和数据收发。
5. **I/O 机制**：学习中断、DMA、轮询、缓冲、缓存和设备调度。
6. **中断处理**：理解硬中断、softirq、`ksoftirqd` 和 workqueue 的分工与执行关系。
7. **网络设备收包**：结合 RX Ring、Packet Descriptor、DMA 和 NAPI，理解网卡从收包到协议栈的处理流程。

## 1. 设备分类

设备可以从不同维度进行分类，这些分类维度可以交叉组合。

### 1.1 按数据访问方式

- **字符设备**：以字符或字节流为单位顺序传输数据，通常不支持随机访问，例如键盘、串口和终端。
- **块设备**：以固定大小的数据块为单位进行读写，通常支持随机访问和缓存，例如硬盘、SSD 和 U 盘。
- **网络设备**：以数据包为单位收发数据，通常通过网络协议栈和 Socket 接口访问，例如物理网卡和虚拟网卡。

### 1.2 按设备功能

- **输入设备**：接收外部输入，例如键盘、鼠标和摄像头。
- **输出设备**：向外部产生输出，例如显示器、打印机和音响。
- **存储设备**：保存和读取数据，例如硬盘、SSD 和 U 盘。
- **通信设备**：与其他设备或系统交换数据，例如网卡、无线网卡和串口。
- **控制与定时设备**：提供硬件控制或定时功能，例如 GPIO 控制器和定时器。

### 1.3 按是否真实存在

- **物理设备**：实际存在的硬件设备，例如物理网卡、硬盘和键盘。
- **虚拟设备或伪设备**：由操作系统或软件模拟出来的设备，例如虚拟网卡、`/dev/null` 和 `/dev/zero`。

同一个设备可以同时属于多个分类。例如，物理网卡是网络设备、通信设备和物理设备；虚拟网卡是网络设备、通信设备和虚拟设备。

## 2. 设备访问路径

应用程序通常不会直接操作硬件，而是通过系统调用和 I/O 子系统访问设备。

### 2.1 软件到硬件的访问路径

```text
应用程序
    ↓
系统调用与通用接口
    ↓
I/O 子系统
    ↓
设备驱动（软件）
    ↓
设备控制器（硬件）
    ↓
具体设备（硬件）
```

这里重点描述请求的调用关系：上层软件通过设备驱动访问设备控制器，再由设备控制器控制具体硬件。

### 2.2 一次 I/O 请求的流程

以读取数据为例：

1. 应用程序通过系统调用发起读取请求。
2. I/O 子系统创建请求，并检查参数、权限和缓存。
3. 驱动将请求转换为设备命令。
4. 驱动通过寄存器、队列或 DMA 配置设备控制器。
5. 设备控制器驱动具体硬件执行操作。
6. 设备通过中断或状态信息返回操作结果。
7. 驱动和 I/O 子系统处理结果，最终将数据或错误返回给应用程序。

## 3. 设备组成

设备可以看作一个整体，内部通常包含设备控制器、具体硬件，以及可能运行在控制器内部的固件。

### 3.1 组成关系

```text
设备（整体）
├── 设备控制器（硬件控制单元）
│   ├── 控制逻辑
│   ├── 寄存器
│   ├── DMA 和中断逻辑
│   └── 固件（运行在控制器内部的程序）
└── 具体硬件（完成存储、收发数据等功能）
```

这里将设备控制器与具体硬件分开，是为了说明结构和职责；在实际硬件中，设备控制器可能集成在设备内部，也可能由独立芯片或 SoC 模块提供。

### 3.2 组成部分

- **设备控制器**：负责接收驱动发出的命令，管理寄存器、队列、DMA 和中断。
- **固件**：运行在设备或控制器内部的底层程序，负责部分硬件初始化和控制逻辑。
- **具体硬件**：完成存储、数据收发、输入或输出等实际功能。

## 4. 设备驱动

设备驱动是运行在操作系统中的软件模块，负责把操作系统的通用设备接口转换为具体硬件可以执行的操作。驱动通常由硬件厂商提供，但本身属于软件，不是硬件设备或设备控制器。

### 4.1 驱动与硬件的关系

驱动通常位于 I/O 子系统和设备控制器之间：

```text
应用程序
    ↓
系统调用与 I/O 子系统
    ↓
设备驱动
    ↓
设备控制器与固件
    ↓
硬件设备
```

驱动通过寄存器、队列、中断和 DMA 等接口控制设备，并将设备状态和处理结果反馈给操作系统。

### 4.2 驱动生命周期

一个驱动通常经历以下阶段：

1. **发现与加载**：操作系统发现设备，并加载匹配的驱动模块。
2. **初始化与探测**：驱动读取设备信息，分配资源，配置寄存器和队列。
3. **注册接口**：驱动向内核注册字符设备、块设备或网络设备接口。
4. **运行与处理 I/O**：驱动处理应用程序或内核子系统发起的 I/O 请求。
5. **错误恢复与状态管理**：处理超时、设备故障、链路变化和数据收发错误。
6. **挂起、恢复与卸载**：系统休眠、设备移除或驱动卸载时释放资源。

### 4.3 网卡驱动示例

以网卡驱动为例，驱动通常负责：

- 初始化和配置设备寄存器
- 创建和管理 RX/TX 队列
- 分配并映射 DMA 缓冲区
- 注册中断处理函数和 NAPI poll 回调
- 处理设备状态、错误和数据收发
- 配合网络协议栈完成数据包的发送和接收

在网卡收包过程中，驱动负责准备 RX Ring 和数据缓冲区，响应硬件中断，并配合 NAPI 批量处理收到的数据包。

## 5. 关键机制

- **中断**：设备完成操作或需要处理时通知 CPU。
- **DMA**：设备与内存之间直接传输数据，减少 CPU 参与。
- **轮询**：CPU 主动检查设备状态，适用于部分低延迟或高频场景。
- **缓冲与缓存**：平衡设备和 CPU 的处理速度差异，减少等待和重复访问。
- **设备调度**：在多个 I/O 请求之间安排处理顺序，提高吞吐量和响应速度。

## 6. 设备文件

在 Linux 中，设备文件通常位于 `/dev` 目录下，是用户空间访问设备的一种文件抽象。应用程序可以使用打开、读取、写入和关闭等文件操作访问设备，内核再通过设备号找到对应的设备驱动。

设备文件主要包含：

- **主设备号**：标识设备所属的驱动。
- **次设备号**：标识驱动管理的具体设备或设备实例。
- **字符设备文件**：通常对应字符设备。
- **块设备文件**：通常对应块设备。

## 7. 中断管理

操作系统使用中断响应硬件事件，并将不适合在硬件中断上下文中完成的工作延后处理。Linux 中常见的处理层次包括硬中断、softirq、`ksoftirqd` 和 workqueue。

### 7.1 硬中断

硬件设备通过中断通知处理器，例如网卡收到数据、磁盘 I/O 完成或定时器到期。硬中断处理程序应尽快完成必要工作，避免长时间占用处理器。

典型流程如下：

```text
硬件设备产生中断
    ↓
处理器进入硬中断处理程序
    ↓
完成紧急处理，并安排后续工作
    ↓
返回被中断的执行流
```

硬中断上下文通常不能睡眠，也不适合执行大量计算或复杂 I/O。

### 7.2 softirq

`softirq` 是 Linux 内核中的软中断机制，用于延后处理不必立即完成的内核工作。网络收包、定时器和块设备 I/O 等子系统都可能使用 softirq。

softirq 与处理器指令触发的“软件中断”不是同一个概念：

- 软件中断通常指程序执行特定指令，进入预定义的处理入口。
- softirq 是 Linux 内核内部安排和执行延后工作的机制。

softirq 处理函数仍然不能睡眠，因此如果后续工作需要睡眠或执行较长时间，通常应继续交给 workqueue 等机制。

网络设备的 NAPI、RX Ring 和 Packet Descriptor 见第 8 节“网络设备收包”。

### 7.3 `ksoftirqd`

#### 7.3.1 作用

`ksoftirqd` 是 Linux 为每个 CPU 创建的内核线程，用来处理没有在当前上下文中及时完成的 softirq。线程名称通常类似：

```text
ksoftirqd/0
ksoftirqd/1
```

数字表示关联的 CPU。

softirq 通常会在硬中断返回前或其他合适的内核路径中尽快处理。如果待处理的 softirq 数量较多，或者处理时间超过限制，内核会唤醒对应 CPU 的 `ksoftirqd`，让它以可调度的内核线程身份继续处理。

```text
硬件中断
    ↓
产生 softirq
    ├── 立即处理
    └── 处理量过大或未及时完成 → ksoftirqd
```

#### 7.3.2 高 CPU 占用的含义

如果 `ksoftirqd/N` 长时间占用较高 CPU，通常表示 CPU `N` 上存在较多软中断工作，常见原因包括：

- 网络收发包速率较高
- 网络包处理或协议栈开销较大
- 定时器事件过多
- 块设备 I/O 或其他内核子系统产生大量 softirq

排查时应结合每个 CPU 的软中断统计、网卡收发包速率、I/O 负载和中断亲和性一起分析，不能只根据线程名判断具体原因。

### 7.4 workqueue

workqueue 用于将内核工作交给内核工作线程执行。与 softirq 相比，workqueue 更适合执行可能阻塞、需要睡眠或耗时较长的工作。

| 机制 | 执行主体 | 是否可以睡眠 | 适合处理 |
|---|---|---|---|
| 硬中断 | 硬中断处理程序 | 否 | 紧急、少量处理 |
| softirq | softirq 处理函数 | 否 | 高性能、可延后的内核工作 |
| `ksoftirqd` | 每 CPU 内核线程 | 处理函数本身仍受 softirq 约束 | 消化积压的 softirq |
| workqueue | 内核工作线程 | 通常可以 | 需要睡眠或较长时间的工作 |

### 7.5 与计算机组成原理的边界

处理器如何响应中断、中断向量如何定位以及硬件中断控制器如何工作，属于计算机组成原理的中断机制。`softirq`、`ksoftirqd` 和 workqueue 则是 Linux 操作系统对中断后续工作的管理和实现。

## 8. 网络设备收包

Linux 网卡收包通常涉及 DMA、RX Ring、Packet Descriptor、硬中断、NAPI 和 softirq。

### 8.1 RX Ring 与 Packet Descriptor

RX Ring 是网卡和驱动循环复用的接收队列。队列中的 Packet Descriptor 是数据包描述符，通常记录数据缓冲区地址、长度、状态和所有权等信息，不保存完整数据包。

```text
RX Ring
├── Descriptor 0 → 数据 buffer 0
├── Descriptor 1 → 数据 buffer 1
└── Descriptor 2 → 数据 buffer 2
```

驱动预先准备描述符和数据缓冲区，并把缓冲区地址交给网卡。网卡收到数据后，通过 DMA 将数据写入缓冲区，再更新描述符状态。

### 8.2 NAPI

NAPI（New API）是 Linux 网络子系统中的收包机制，采用“中断加轮询”的混合模式。

```text
网卡收到数据
    ↓
DMA 写入接收 buffer
    ↓
网卡更新 RX Ring，并触发一次硬件中断
    ↓
驱动关闭或减少接收中断，调用 napi_schedule()
    ↓
NET_RX_SOFTIRQ 执行 NAPI poll
    ↓
批量处理数据包
    ↓
队列为空后恢复接收中断
```

NAPI 的 `poll` 函数通常接收 `budget` 参数，表示本轮最多处理的数据包数量：

- RX Ring 为空：调用完成逻辑，重新开启接收中断。
- 达到 `budget` 但队列仍有数据：暂不恢复中断，继续下一轮 poll。

低流量时，中断可以快速通知数据到达；高流量时，NAPI 批量处理数据，避免每个数据包都触发一次中断。

### 8.3 与 softirq 的关系

NAPI poll 通常运行在网络接收 softirq 上下文中。softirq 负载较高时，相关工作可能由对应 CPU 的 `ksoftirqd` 内核线程继续处理。
