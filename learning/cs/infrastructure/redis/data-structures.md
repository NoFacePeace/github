# Redis 数据结构

学习基线：Redis [7.2.16](https://github.com/redis/redis/tree/7.2.16)。返回 [Redis 底层实现学习](README.md)。

本文从存储结构出发，学习内存布局、查找与更新过程，以及扩容和空间优化。同一种结构可以被多个数据类型复用。

## 1. 结构总览

| 数据结构 | 核心特点 | 主要关联 |
| --- | --- | --- |
| SDS | 带长度和容量信息的动态字符串 | String，以及键名、字段名等字符串数据 |
| 字典（dict） | 基于哈希表的键值映射 | 数据库键空间、Hash、Set、ZSet |
| 整数集合（intset） | 有序、紧凑存储整数 | Set |
| listpack | 在连续内存中紧凑存储多个元素 | List、Hash、Set、ZSet、Stream |
| quicklist | 将多个节点组织成双向链表，节点通常持有 listpack | List |
| 跳表（skiplist） | 通过多层索引支持有序查找 | ZSet |
| 基数树（rax） | 压缩公共前缀的树形索引 | Stream 的消息块索引及内部管理结构 |

## 2. SDS：动态字符串

- **作用**：保存二进制安全的字符串，显式记录长度，避免获取长度时扫描整个字符串。
- **学习重点**：不同长度的头部布局、已用长度与可用容量、扩容策略，以及与 C 字符串的关系。
- **关联类型**：String 的 `raw`、`embstr` 编码使用 SDS；两种编码的对象与字符串内存分配方式不同。
- **源码入口**：[sds.h](https://github.com/redis/redis/blob/7.2.16/src/sds.h)、[sds.c](https://github.com/redis/redis/blob/7.2.16/src/sds.c)。

## 3. 字典：哈希表

- **作用**：通过哈希函数定位桶，支持平均 O(1) 的查找、插入和删除。
- **学习重点**：桶与条目的组织、哈希冲突处理、负载因子、扩缩容，以及渐进式 rehash 如何分摊迁移成本。
- **关联类型**：Hash 存储字段和值，Set 存储成员，ZSet 借助字典按成员查分数；数据库本身也使用字典管理键。
- **源码入口**：[dict.h](https://github.com/redis/redis/blob/7.2.16/src/dict.h)、[dict.c](https://github.com/redis/redis/blob/7.2.16/src/dict.c)。

## 4. intset：整数集合

- **作用**：在连续内存中按顺序存储不重复的整数，减少通用哈希表的额外开销。
- **学习重点**：二分查找、插入与删除时的数据移动，以及 16、32、64 位整数存储宽度的升级。
- **关联类型**：Set 的一种底层编码。intset 内部的整数宽度升级与 Set 转为其他编码是两个不同过程。
- **源码入口**：[intset.h](https://github.com/redis/redis/blob/7.2.16/src/intset.h)、[intset.c](https://github.com/redis/redis/blob/7.2.16/src/intset.c)。

## 5. listpack：紧凑列表

- **作用**：把多个整数或字符串元素存入一段连续内存，减少逐个分配对象和保存指针的开销。
- **学习重点**：头部、元素编码、反向遍历所需的长度信息，以及插入、删除时的内存移动。
- **关联类型**：Hash、Set、ZSet 可直接使用 listpack；quicklist 和 Stream 则将它作为内部存储单元。
- **源码入口**：[listpack.h](https://github.com/redis/redis/blob/7.2.16/src/listpack.h)、[listpack.c](https://github.com/redis/redis/blob/7.2.16/src/listpack.c)。

## 6. quicklist：分块双向链表

- **作用**：将数据分散到多个双向链接的节点，在紧凑存储和局部修改成本之间取舍；普通节点持有 listpack，大元素也可独立存储。
- **学习重点**：节点布局、两端操作、节点分裂与合并、容量限制，以及中间节点的压缩策略。
- **关联类型**：List。quicklist 是组织节点的外层结构，listpack 是节点内的存储结构。
- **源码入口**：[quicklist.h](https://github.com/redis/redis/blob/7.2.16/src/quicklist.h)、[quicklist.c](https://github.com/redis/redis/blob/7.2.16/src/quicklist.c)。

## 7. skiplist：跳表

普通跳表的多层索引、查找、随机层高和前驱数组见 [跳表基础](../../data-structures/linked-lists/skip-list.md)。本节只说明 Redis 7.2.16 为 ZSet 增加的机制及实现选择。

下面先介绍节点、字段、排序规则和配置，再说明查询、插入、删除、更新及范围读取过程。

### 7.1 ZSet 的整体结构与字典协作

ZSet 使用 `skiplist` 编码时，`zset` 同时持有 `dict` 和 `zsl`：

| 结构 | 组织方式 | 负责的操作 |
| --- | --- | --- |
| 字典 `dict` | 按成员查找分数 | 判断成员是否存在、`ZSCORE` 等按成员查询 |
| 跳表 `zsl` | 按分数与成员共同排序 | 排名查询、按排名或分数范围读取、有序遍历 |

两种结构索引同一批成员。此版本中字典的键与跳表节点的 `ele` 共享同一个 SDS，字典的值指向跳表节点的 `score` 字段，避免重复保存成员字符串和分数。

字典保证 ZSet 的成员唯一；跳表底层的 `zslInsert` 假设调用者已检查重复成员。更新和删除时需要同步维护两种结构。

小型 ZSet 可以使用 `listpack` 编码，此时没有这套跳表与字典组合。相关源码：`zsetAdd`、`zsetConvertAndExpand`，见 [t_zset.c](https://github.com/redis/redis/blob/7.2.16/src/t_zset.c)。

### 7.2 跳表与节点结构

节点定义如下，省略了与本节无关的外围结构：

```c
typedef struct zskiplistNode {
    sds ele;
    double score;
    struct zskiplistNode *backward;
    struct zskiplistLevel {
        struct zskiplistNode *forward;
        unsigned long span;
    } level[];
} zskiplistNode;
```

节点的 `level[]` 保存各层的前向指针和跨度，`backward` 保存底层前驱。跳表整体通过 `header`、`tail`、`length` 和 `level` 记录头尾入口、元素数量和有效层数。

结构定义见 [server.h](https://github.com/redis/redis/blob/7.2.16/src/server.h) 中的 `zskiplistNode`、`zskiplist` 和 `zset`。

### 7.3 排序规则

节点保存 `double score` 和字符串成员 `ele`，比较顺序为：

1. 分数不同时，按分数从小到大排列。
2. 分数相同时，使用 `sdscmp` 按成员的字节序排列。

```text
(score=10, member="alice")
             ↓
(score=10, member="bob")
             ↓
(score=20, member="carol")
```

因此分数可以重复，但成员不能重复；修改已有成员的分数属于更新。字节序比较不按语言区域的排序规则处理。源码中的插入、删除定位都同时比较 `score` 和 `ele`，见 `zslInsert`、`zslDelete`。

### 7.4 span：跨度的含义与存储位置

当 `forward` 指向业务节点时，`span` 表示起点到终点的底层排名差：不包含起点，包含终点。

```text
底层：10 → 20 → 30 → 40
高层：10 ──────────→ 40
          span = 3
```

从 10 到 40 跨过的底层元素是 20、30、40，因此跨度为 3，而不是 2。头哨兵的内部排名视为 0，第一个业务节点的内部排名为 1。

`span` 保存在连接的起点节点中，与该层的 `forward` 配对。假设上图高层为第 1 层：

```text
节点10.level[1].forward = 节点40
节点10.level[1].span    = 3

节点10.level[0].forward = 节点20
节点10.level[0].span    = 1
```

`forward` 记录跳到哪里，`span` 记录这一步相当于在底层前进多少个位置。它记录的是元素数量，不是分数差，所以上图的跨度不是 `40 - 10 = 30`。

还有一个边界细节：某层 `forward == NULL` 时，`span` 可以非零，表示当前节点之后剩余的底层元素数量。例如某个高层在 20 处结束，但底层还有 30、40，该层从 20 指向 `NULL` 的跨度为 2。这一值用于更新维护，不代表可以向右移动到业务节点。

### 7.5 backward 与 tail：后退指针与尾节点

只有底层支持逐节点后退，高层没有对应的后退指针。逆序范围查询可先定位终点，再沿 `backward` 向前读取。

`tail` 是指向最后一个真实数据节点的指针，不是额外创建的尾哨兵。它与 `header` 的含义不同：`header` 指向不保存业务数据的头哨兵，空表时仍然存在；`tail` 在空表时为 `NULL`。

```text
header → 10 ⇄ 20 ⇄ 30 → NULL
                  ↑
                 tail
```

图中的数字表示按升序排列的分数。第一个业务节点 10 的 `backward` 为 `NULL`，最后一个业务节点 30 的底层 `forward` 为 `NULL`。每个业务节点只有一个 `backward`，它指向底层前驱，不能沿高层直接向后跳跃。

### 7.6 层高配置与空表状态

Redis 7.2.16 的实现选择如下：

| 配置 | 值或行为 |
| --- | --- |
| 晋升概率 `ZSKIPLIST_P` | 0.25，上层节点数期望约为下一层的四分之一 |
| 最大层数 `ZSKIPLIST_MAXLEVEL` | 32 |
| 头哨兵 | 初始化时分配全部 32 层，每层 `forward = NULL`、`span = 0` |
| 空跳表 | 有效层数为 1，元素数量为 0，`tail = NULL` |

`zslRandomLevel` 从层高 1 开始随机晋升，源码在随机循环结束后将结果截断到 32。忽略上限截断，每个业务节点的期望层数为 `1 / (1 - 0.25) = 4/3`，比晋升概率为 1/2 时的期望 2 层更少。

源码入口：`zslCreate`、`zslRandomLevel`，以及 [server.h](https://github.com/redis/redis/blob/7.2.16/src/server.h) 中的两个层高常量。

### 7.7 查询成员与排名

仅按成员读取分数时，通过字典查询即可；需要在跳表中定位节点时，同时使用分数与成员比较。排名查询和按排名定位则利用各层跨度。

#### 7.7.1 计算排名与按排名定位

查找某个成员时，沿途每向右移动一次，就累加该连接的跨度，到达目标时即可得到排名，无须从底层头部逐个计数。反过来，按排名查找时，只有“已累计跨度 + 下一条连接跨度”不超过目标排名才向右移动，否则下降一层。

例如从 `header` 到 10 的跨度为 1，从 10 到 40 的跨度为 3，累计 `1 + 3 = 4`，说明 40 是第 4 个元素。即使查找路径跳过了 20、30，也不会漏算它们。没有跨度信息，仅靠前向指针无法得知跨过多少个元素，通常需要沿底层逐个计数才能确定排名。

- `zslGetRank` 返回从 1 开始的内部排名，返回 0 表示未找到。
- `zslGetElementByRank` 按内部排名定位节点。
- 对外的 `ZRANK` 返回从 0 开始的排名，需要将内部排名减一。

#### 7.7.2 定位倒数第 k 个元素

跳表通过 `length` 保存元素总数 n。对于 `1 ≤ k ≤ n`，倒数第 k 个元素可以换算为从 1 开始的正序位置，再利用 `span` 定位：

```text
正序位置 = n - k + 1

例如共有 10 个元素：
倒数第 4 个 = 正序第 10 - 4 + 1 个 = 正序第 7 个
```

这里的位置从 1 开始，对应 `zslGetElementByRank` 的内部排名；示例中的元素对外正序排名为 6，逆序排名为 3。

另一种方式是从 `tail` 沿 `backward` 后退 k - 1 次。两种方式的作用不同：

| 方式 | 定位成本 | 特点 |
| --- | --- | --- |
| 换算正序位置，再利用 `span` | 期望 O(log n) | 适合定位任意倒数位置，无须逐个后退 |
| 从 `tail` 沿 `backward` 后退 | O(k) | k 很小时直接，适合从尾部连续读取 |

跨度不需要反向存储：先换算位置，再从头哨兵沿前向索引定位即可。定位后如需继续按逆序读取，再使用底层后退指针。

### 7.8 插入成员

调用方先通过字典检查成员是否已存在。对新成员，跳表插入依次完成定位、生成层高、更新连接与跨度、维护底层后退指针和字典。

#### 7.8.1 查找时记录 update 与 rank

除普通跳表的 `update[i]` 外，Redis 还记录 `rank[i]`：从头哨兵到第 i 层前驱 `update[i]` 已跨过的底层元素数量。它是该前驱的底层排名，不是该层的节点序号。

`update` 和 `rank` 都是本次插入使用的临时数组，不是节点字段：`update[i]` 记录第 i 层前驱是谁，`rank[i]` 记录这个前驱在底层排第几。它们让后续跨度更新无需再沿底层计数。

查找时，下降一层继承已经累计的位置，向右移动则加上经过连接的跨度：

```text
current = header
for i from 当前有效层数 - 1 down to 0:
    rank[i] = 0 if i 是最高有效层 else rank[i + 1]
    while 下一节点存在且按分数与成员比较排在待插入节点之前:
        rank[i] += current.level[i].span
        current = current.level[i].forward
    update[i] = current
```

例如插入 25，底层为 `10 → 20 → 30 → 40`，第 1 层为 `header → 10 → 40`：先在第 1 层走到 10，得到 `rank[1] = 1`；下降到底层继承 1，再走到 20，得到 `rank[0] = 2`。

```text
update[1] = 节点10，rank[1] = 1
update[0] = 节点20，rank[0] = 2
```

#### 7.8.2 生成层高并初始化新增层

使用 `zslRandomLevel` 生成新节点层高。如果超过当前有效层数，每个新增层先设置 `update[i] = header`、`rank[i] = 0`，将头哨兵的原跨度设为插入前的元素总数，并提高有效层数。这些层随后也使用相同的跨度拆分公式。

#### 7.8.3 拆分新节点参与层的连接与跨度

对新节点参与的第 i 层，设：

```text
d = rank[0] - rank[i]
oldSpan = update[i].level[i].span
```

每一层都使用 `rank[0] - rank[i]`，不是相邻两层相减，因为所有 `rank` 都按底层位置计数。`d` 表示该层前驱与底层插入前驱之间相隔多少个元素。原连接插入新节点后被分成两段：

```text
update[i] 到新节点的 span = d + 1
新节点到原后继的 span     = oldSpan - d
```

例如底层为 `10 → 20 → 30 → 40`，高层只有 `10 → 40`。在 20 后插入参与高层的 25，原跨度为 3，`d = 1`：

```text
高层：10 ──→ 25 ──→ 40
       span=2  span=2
```

前一段计入 20、25，后一段计入 30、40。

#### 7.8.4 新节点未参与的高层也要更新

如果上述 25 只参与底层，高层的前向指针不变，但跨度仍要从 3 增加为 4：

```text
底层：10 → 20 → 25 → 30 → 40
高层：10 ───────────────→ 40
            span = 4
```

所以，新节点层高低于当前有效层数时，高层的 `update` 仍然有用：

```c
for (i = level; i < zsl->level; i++) {
    update[i]->level[i].span++;
}
```

这里修改的是每个高层中跨越插入位置的那条连接，并非该层所有连接。

#### 7.8.5 更新后退指针、尾指针与字典

新节点的 `backward` 指向底层前驱；如果前驱是头哨兵，则设为 `NULL`。如果存在底层后继，将后继的 `backward` 指向新节点；否则将 `tail` 指向新节点。最后增加 `length`，由调用方把成员和新节点的分数地址加入字典。

插入完成后，临时数组 `update`、`rank` 不再需要；长期保留并供后续查询使用的是节点中的连接和 `span`。源码入口：`zslInsert`、`zsetAdd`，见 [t_zset.c](https://github.com/redis/redis/blob/7.2.16/src/t_zset.c)。

### 7.9 删除成员

先定位目标并记录各层前驱 `update[i]`。目标不存在时不修改结构；找到后，除普通跳表的断链操作外，还需要合并或缩短跨度。

`zslDeleteNode` 遍历所有有效层：

| 该层与目标的关系 | 跨度调整 |
| --- | --- |
| 前驱直接指向目标 | 两段连接合并：`前驱.span += 目标.span - 1`，再让前驱指向目标后继 |
| 目标不在该层，但位于前驱连接覆盖的底层范围内 | 前向指针不变，`前驱.span -= 1` |

减去 1 是因为底层少了目标这个元素。如果目标有底层后继，让后继的 `backward` 指向目标的前驱；否则让 `tail` 指向目标的前驱。减少 `length`，并在最高层变空时降低有效层数，至少保留底层。ZSet 删除还需要同步移除字典条目，并正确释放共享的成员字符串。

插入与删除公式见 [t_zset.c](https://github.com/redis/redis/blob/7.2.16/src/t_zset.c) 中的 `zslInsert`、`zslDeleteNode`。

### 7.10 更新成员分数

`zslUpdateScore` 会先找到原节点，再判断能否原地修改：

- 新分数严格大于前驱分数、严格小于后继分数时，直接修改 `score`；不存在的邻居不施加边界限制。
- 否则移除旧节点，再按新分数插入新节点，并重新随机生成层高。

此版本的原地更新判断只使用严格的分数比较。新分数与相邻节点相同时，即使按成员字节序仍可保持原位置，也会进入重新插入流程。

重新插入后，调用方还要将字典中的分数指针更新为新节点的 `score` 地址，避免继续引用旧节点。相关源码：`zslUpdateScore` 和 `zsetAdd`，见 [t_zset.c](https://github.com/redis/redis/blob/7.2.16/src/t_zset.c)。

### 7.11 范围读取与倒序遍历

按排名读取范围时，先利用 `span` 定位起点；按分数读取范围时，先按分数边界定位。随后沿底层 `forward` 连续读取，直到达到范围边界或返回数量。逆序读取则先定位范围内的最后一个节点，再沿 `backward` 读取。

从 `header` 沿底层 `forward` 遍历，得到的是低分到高分；从 `tail` 沿 `backward` 遍历，得到的是高分到低分。例如读取分数最高的两个成员，直接从 `tail` 读取 30，再后退一步读取 20 即可。从头部沿底层向前则需要遍历到末尾。

后退指针让每次后退只需 O(1)，从尾部取 k 个成员只需 O(k)。对于任意位置的逆序范围，先通过跳表索引定位，再沿底层后退，总时间期望为 O(log n + k)。高层负责定位，底层负责连续读取，因此不需要在每层都设置后退指针。

### 7.12 为什么选择跳表

时间复杂度相同，不代表实现成本、内存开销和实际运行速度相同。ZSet 既需要频繁插入、删除，也需要排序、排名和范围读取；跳表可以通过前向指针、跨度和底层后退指针直接组合出这些能力。

以下是结合上述实现的工程取舍分析，不作为 Redis 作者历史选型动机的直接引述。

#### 7.12.1 与平衡搜索树对比

| 需求 | Redis 跳表 | 平衡搜索树，如红黑树 |
| --- | --- | --- |
| 维护有序结构 | 修改各层连接，通过随机层高维持期望效率 | 通过旋转、重新着色等操作维护平衡 |
| 查询排名或按排名定位 | 维护每层连接的 `span` | 可额外维护每个节点的子树元素数量，并在更新和旋转时同步维护 |
| 正序范围读取 | 定位起点后沿底层前向指针遍历 | 可通过中序后继遍历，也能达到 O(log n + k) |
| 倒序范围读取 | 沿底层 `backward` 遍历 | 可通过中序前驱遍历 |
| 查找、插入、删除的时间保证 | 期望 O(log n)，最坏可能退化为 O(n) | 最坏 O(log n) |

跳表的操作主要围绕连接与跨度展开，不需要树的平衡修复，维护排名和双向范围遍历的逻辑也比较直观。平衡树完全可以提供同样的功能，但需要同时维护平衡约束和排名所需的附加信息。

例如读取排行榜第 100～120 名，可以先利用 `span` 定位第 100 名，再沿底层读取后续成员，总时间期望为 O(log n + k)，其中 k 为返回数量。带子树大小信息的平衡树同样能达到这个复杂度，因此范围查询不是跳表独有的能力，也不能单凭复杂度认定跳表更快。

#### 7.12.2 与数组、哈希表和 B+ 树对比

- **有序数组**：二分查找为 O(log n)，连续存储有利于缓存局部性，但插入和删除通常需要移动元素，成本为 O(n)。
- **哈希表**：按成员查找的期望效率高，但不能直接提供分数顺序、排名和有序范围查询。因此 Redis 将字典与跳表组合使用。
- **B+ 树**：同样支持有序查找和高效范围扫描，多键节点有利于减少层数、改善局部性；更新需要处理节点内元素移动及分裂、合并。它也可用于内存，实际表现取决于节点布局和工作负载。

#### 7.12.3 跳表的代价

多层指针与 `span` 带来内存开销，独立分配的节点可能影响缓存局部性，随机化也不提供平衡树的最坏对数时间保证。它不保证比红黑树或 B+ 树更快、更省内存；性能需要结合数据规模、成员大小、查询与更新比例以及具体实现衡量。

Redis 的实现体现了对有序操作能力和维护复杂度的取舍。同时，它为小型 ZSet 提供 `listpack` 编码，用紧凑存储降低小数据量时的开销。

## 8. rax：基数树

- **作用**：按键的字节序列建立索引，压缩公共前缀和单一路径，支持有序遍历。
- **学习重点**：压缩节点布局、路径匹配、插入时的节点分裂、删除与迭代器。
- **关联类型**：Stream 使用 rax 索引消息块，消息块内部通过 listpack 保存消息；消费者组的部分管理结构也使用 rax。
- **源码入口**：[rax.h](https://github.com/redis/redis/blob/7.2.16/src/rax.h)、[rax.c](https://github.com/redis/redis/blob/7.2.16/src/rax.c)。
