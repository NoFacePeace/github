# MySQL 学习

记录 MySQL 的 SQL 使用、架构设计、数据存储、索引、事务与运维实践，逐步深入底层实现与源码。

## 1. 学习主线

- **官方文档**：[MySQL Reference Manual](https://dev.mysql.com/doc/refman/8.4/en/)。
- **源码入口**：[mysql/mysql-server](https://github.com/mysql/mysql-server/tree/8.4)。

按“基本使用 → 执行流程 → 数据存储 → 索引 → 事务 → MVCC → 锁 → 日志与崩溃恢复 → 性能优化 → 复制与备份 → 源码阅读”的顺序学习。

已熟悉 SQL 的部分可以通过实验快速复习；事务、MVCC 和锁需要结合双会话实验反复验证。

## 2. 学习顺序

### 2.1 SQL 基础与表设计

- 数据库、表、行与列，常用数据类型、NULL、字符集与排序规则。
- 建表与增删改查，连接查询、聚合、子查询及窗口函数。
- 主键、唯一约束、外键，以及范式与适度冗余的取舍。
- **实践**：设计用户、商品、订单与订单明细表，完成订单查询、销售统计和分页查询。

### 2.2 架构与 SQL 执行流程

- 客户端连接、认证、会话与连接池的关系。
- Server 层与存储引擎的职责，解析、优化、执行与存储引擎接口。
- 分别梳理一条 SELECT 和一条 UPDATE 的执行路径，后续逐步补齐索引、锁和日志环节。
- **目标**：能够说明 SQL 从客户端发送到返回结果的主要步骤。

### 2.3 数据存储

- 表空间、段、区、页与记录之间的关系。
- 数据页与行格式，页内记录组织、页目录和溢出页。
- Buffer Pool、脏页与刷盘，理解内存中的修改如何进入磁盘。
- **目标**：能够从“读一行数据”解释到“访问索引页和数据页”。

### 2.4 B+ 树与索引

- B+ 树的查找、插入、页分裂，以及适合范围查询的原因。
- 聚簇索引、二级索引、回表与覆盖索引。
- 联合索引、最左前缀、索引下推，以及排序、范围条件对索引使用的影响。
- 索引选择性、主键设计，以及索引带来的写入和空间成本。
- **实践**：为订单查询设计联合索引，用 `EXPLAIN` 比较访问方式、使用的索引和预估扫描行数。

### 2.5 事务

- 学习事务边界、ACID、提交与回滚，以及隔离级别的并发语义。
- 详细内容与实验见[事务](#3-事务)章节。

### 2.6 MVCC

- 先理解 undo 保存历史版本的作用，为版本链学习做准备；完整日志机制见 2.8。
- 隐藏字段、undo 版本链、Read View 与可见性判断。
- RC 和 RR 下快照建立时机的差异，以及事务自身修改的可见性。
- 长事务对历史版本保留与清理的影响。
- **目标**：画出版本链和事务执行时序，解释[事务实践](#34-实践)中每次快照读取的结果。

### 2.7 锁与并发控制

- 共享锁、排他锁、意向锁，以及记录锁、间隙锁和 next-key lock。
- 普通 SELECT、锁定读、UPDATE 和 DELETE 的并发行为。
- 索引、查询条件与隔离级别如何影响加锁范围。
- 元数据锁（MDL）、锁等待、死锁检测，以及应用侧事务重试。
- **实践**：复现行锁等待、范围查询阻塞插入和死锁，结合实际执行计划分析加锁原因。

### 2.8 日志与崩溃恢复

- undo log、redo log 与 binlog 的职责和区别，串联事务回滚、历史版本、持久化和复制。
- WAL、检查点、脏页刷盘与崩溃恢复。
- InnoDB 与 binlog 之间的两阶段提交，以及事务提交过程中的日志写入与持久化。
- **目标**：沿一条 UPDATE 梳理数据、锁和日志的变化，解释“主动回滚”和“崩溃恢复”的区别。

### 2.9 查询优化与问题排查

- 阅读执行计划，理解访问方式、连接顺序、估算行数、排序与临时表。
- 统计信息与优化器成本估算，分析“存在索引但未使用”的原因。
- 慢查询日志、Performance Schema 与锁等待信息的使用。
- 深分页、批量写入、隐式类型转换与大事务等典型问题。
- **实践**：针对一条慢 SQL，保留优化前后的执行计划、耗时、扫描行数与数据规模，验证改进效果。

### 2.10 复制、备份与恢复

- 基于 binlog 的复制流程、中继日志、GTID 与复制延迟。
- 基于 binlog 的 [CDC（变更数据捕获）](cdc.md)，以及全量快照与增量同步的衔接。
- 异步复制、半同步复制，以及故障切换和读写分离中的一致性问题。
- 逻辑备份、物理备份，以及使用备份和 binlog 进行时间点恢复的思路。
- **实践**：在本地实验环境搭建复制，观察延迟，并完成一次备份恢复和数据校验。

### 2.11 源码阅读与专题深入

- 先固定与实验环境对应的源码 tag 或 commit，再沿具体 SQL 的调用链阅读；不直接以持续更新的分支作为可复现的源码基线。
- 建议顺序：SQL 执行入口 → 存储引擎接口 → B+ 树查找 → 行读取与 MVCC → 加锁 → 更新与日志 → 提交与恢复。
- 根据问题继续研究 Buffer Pool 管理、刷脏、purge、在线 DDL 和复制执行。
- **产出**：每个专题整理一张调用流程图、一组关键数据结构和一个可复现实验。

## 3. 事务

先理解事务的整体语义，再认识并发问题，接着学习隔离级别提供的保证，最后深入 MVCC 与锁的实现机制。隔离级别属于事务的隔离性；理解其实现需要结合 MVCC 和锁。

### 3.1 事务基础

- ACID、事务边界、自动提交、提交与回滚。
- 学习 `START TRANSACTION`、`COMMIT`、`ROLLBACK` 与 `SAVEPOINT`，明确事务开始、结束和部分回滚的位置。
- 以转账为例，理解多条 SQL 如何组成一个业务操作，以及约束和事务如何共同维护数据一致性。
- **实践**：执行转账事务，分别验证提交与回滚后的余额。

### 3.2 并发问题

- **脏读**：读到其他事务尚未提交的修改。
- **不可重复读**：同一事务重复读取同一行，因其他事务提交修改而得到不同的值。
- **幻读**：同一事务重复按相同条件查询，因其他事务提交插入或删除而得到不同的行集合。
- **丢失更新**：两个事务基于同一个旧值计算并写回，后一次写入覆盖了前一次修改。例如，两个事务都读到计数值 100，各自在应用中加 10，再执行 `UPDATE counters SET value = 110 WHERE id = 1`，最终值为 110，而预期为 120。

前三项属于读异常，丢失更新属于写入冲突。分析丢失更新时，需要结合“读取 → 计算 → 写回”的完整流程、SQL 写法及并发控制方式，不能仅凭隔离级别名称判断是否安全。

### 3.3 隔离级别

隔离级别规定并发事务之间的数据可见性。下面先按 SQL 标准对三类读异常的最低保证进行比较，“可能”表示该级别允许出现，并非一定发生。此表不涵盖丢失更新。

| 隔离级别 | 英文名称 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- | --- |
| 读未提交（RU） | READ UNCOMMITTED | 可能 | 可能 | 可能 |
| 读已提交（RC） | READ COMMITTED | 不允许 | 可能 | 可能 |
| 可重复读（RR） | REPEATABLE READ | 不允许 | 不允许 | 标准允许，具体行为见下文 |
| 串行化 | SERIALIZABLE | 不允许 | 不允许 | 不允许 |

**实现特点**：默认隔离级别为 RR。RC 的一致性读每次建立新快照；RR 的一致性读沿用同一事务内首次一致性读建立的快照，因此不会看到其他事务后来提交的新行。RR 的范围锁定读则通过间隙锁或 next-key lock 阻止向锁定范围插入。快照读与当前读的数据视图不同，混用时不能据此推断所有查询结果始终一致。详见[官方隔离级别文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)。

### 3.4 实践

**准备数据**：在本地学习数据库中执行一次，提交后再开始实验。两个会话均连接该数据库，并使用约定的默认存储引擎。

```sql
CREATE TABLE rr_demo (
    id INT PRIMARY KEY,
    value INT NOT NULL
);
INSERT INTO rr_demo VALUES (1, 100);
COMMIT;
```

**确认隔离级别**：两个会话均在事务外执行以下语句。默认值为 RR，但实验仍显式设置，避免已有配置影响结果。

```sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT @@session.transaction_isolation;
-- 预期：REPEATABLE-READ
```

#### 3.4.1 RR：快照读与当前读

按表格从上到下执行，“—”表示该会话此步不操作。

| 步骤 | 会话 A | 会话 B | 预期结果 |
| --- | --- | --- | --- |
| 1 | `START TRANSACTION;` | — | A 开启事务，此时尚未建立一致性读快照。 |
| 2 | `SELECT value FROM rr_demo WHERE id = 1;` | — | 返回 100，首次一致性读建立快照。 |
| 3 | — | `START TRANSACTION;` | B 开启事务。 |
| 4 | — | `UPDATE rr_demo SET value = 120 WHERE id = 1;` | B 修改该行，尚未提交。 |
| 5 | `SELECT value FROM rr_demo WHERE id = 1;` | — | 仍返回 100，不读取 B 未提交的修改。 |
| 6 | — | `COMMIT;` | B 提交修改。 |
| 7 | `SELECT value FROM rr_demo WHERE id = 1;` | — | 仍返回 100，沿用原快照。 |
| 8 | `SELECT value FROM rr_demo WHERE id = 1 FOR UPDATE;` | — | 返回 120，当前读并加锁。 |
| 9 | `SELECT value FROM rr_demo WHERE id = 1;` | — | 仍返回 100，锁定读不会刷新原快照。 |
| 10 | `COMMIT;` | — | A 结束事务并释放锁。 |
| 11 | `START TRANSACTION;` | — | A 开启新事务。 |
| 12 | `SELECT value FROM rr_demo WHERE id = 1;` | — | 返回 120，新事务建立新快照。 |
| 13 | `COMMIT;` | — | 结束实验。 |

**观察重点**：RR 的可重复读针对同一事务内的一致性读；当前读不受旧快照限制。上述实验中 A 没有修改数据，如果 A 自己执行了更新，后续一致性读也能看到自身修改。普通 `START TRANSACTION` 不会立即建立快照；`START TRANSACTION WITH CONSISTENT SNAPSHOT` 可在 RR 下主动建立快照。参见[一致性非锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)。

#### 3.4.2 RR：快照建立时机

确认两个会话均已结束事务并使用 RR，将 `rr_demo` 中 `id = 1` 的值重置为 100 并提交，然后按以下顺序执行：

| 步骤 | 会话 A | 会话 B | 结果说明 |
| --- | --- | --- | --- |
| 1 | `START TRANSACTION;` | — | A 已开启事务，但尚未查询表数据，也未建立一致性读快照。 |
| 2 | — | `START TRANSACTION;` | B 开启事务。 |
| 3 | — | `UPDATE rr_demo SET value = 130 WHERE id = 1;` | B 将值更新为 130。 |
| 4 | — | `COMMIT;` | B 提交修改。 |
| 5 | `SELECT value FROM rr_demo WHERE id = 1;` | — | A 此时才建立快照，读到 B 已提交的 130。 |
| 6 | `COMMIT;` | — | A 结束事务。 |

**实测结果**：第 5 步返回 **130**。决定可见性的关键是快照建立时机，而非仅看事务开始时间：先查询建立快照，再发生其他事务的提交，后续普通查询沿用旧快照；先开启事务但不查询，等其他事务提交后才首次查询，则能读到该提交。

#### 3.4.3 RC 与 RR 对比

确认两个会话均已结束事务，将数据重置为 100 并提交，把会话隔离级别改为 `READ COMMITTED` 后重做 3.4.1 的双会话实验。该实验第 7、9 步将返回 120，因为每次一致性读都会建立新快照。实验结束后可将会话隔离级别恢复为 `REPEATABLE READ`。

## 5. 笔记约定

- 默认以 MySQL 8.4 LTS 和 InnoDB 为学习基线；涉及其他版本或存储引擎时，明确注明差异。
- 每篇笔记围绕一个具体问题，按“问题 → 原理 → 实验 → 结论”组织。
- 实验开始时执行 `SELECT VERSION();`，记录完整补丁版本、表结构、索引、隔离级别与相关配置。
- 参考其他版本的资料时，以学习基线对应的文档和实验结果核对语法、配置、默认值与实现差异。
- 并发实验按会话列出 SQL 执行顺序，明确事务开始、提交和回滚的位置。
- 性能结论注明数据量、数据分布和执行计划，避免仅凭单次耗时判断。
- 引用源码时注明版本、文件与函数；区分实现事实、个人理解和实验结论。
