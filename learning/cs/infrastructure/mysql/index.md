# MySQL 索引

索引是帮助 MySQL 快速定位数据的数据结构。它通过维护一份有序或适合检索的数据表示，减少查询需要扫描的记录数量，但也会占用额外空间，并增加写入和维护成本。

学习索引时，先理解索引解决的问题和常见分类，再学习 B+ 树为何适合数据库，最后结合 InnoDB 的聚簇索引、二级索引和执行计划分析实际查询。

## 1. 索引的作用与代价

没有可用索引时，MySQL 可能需要扫描大量记录并逐行判断条件。索引可以加速：

- 等值查询，例如 `WHERE user_id = 10`。
- 范围查询，例如 `WHERE created_at >= '2026-01-01'`。
- 排序和分组，例如 `ORDER BY created_at`。
- 表连接，例如根据外键或关联字段查找另一张表的记录。

索引不是越多越好，它会带来以下成本：

- 占用磁盘和 Buffer Pool 空间。
- 插入、更新和删除数据时需要维护索引。
- 随机写入可能引发页分裂，增加写放大和空间碎片。
- 索引越多，优化器需要评估的访问路径也越多。

设计索引的目标不是让每个条件都有单列索引，而是围绕重要查询，用尽量少且合适的索引降低整体访问成本。

## 2. 索引分类

索引可以从约束与唯一性、索引键形式、特殊索引类型和索引属性等角度分类。这些分类描述的是不同维度，彼此可以重叠。例如，一个索引可以同时是唯一索引、联合索引、二级索引和 B+ 树索引。

### 2.1 按约束与唯一性分类

| 类型 | 作用 |
| --- | --- |
| 主键索引 | 唯一标识记录，索引列必须唯一且非空 |
| 唯一索引 | 保证索引列组合唯一 |
| 普通索引 | 加速查询，不要求索引列组合唯一 |

主键索引和唯一索引承担唯一性约束；普通索引也可以称为非唯一索引，只提供查询访问路径。

### 2.2 按索引键形式分类

| 类型 | 说明 |
| --- | --- |
| 单列索引 | 只包含一个列 |
| 联合索引 | 包含多个列，列顺序会影响可支持的查询 |
| 前缀索引 | 只索引字符串列开头的一部分 |
| 函数索引 | 索引表达式或函数计算结果 |

联合索引可以同时具有其他属性。例如，`UNIQUE (tenant_id, email)` 既是唯一索引，也是联合索引。

### 2.3 特殊索引类型

全文索引和空间索引不是普通 B+ 树索引的简单变体，而是面向特定数据和查询模型的专用索引：

| 类型 | 适用数据或查询 |
| --- | --- |
| 全文索引 | 文本关键词检索 |
| 空间索引 | 空间对象和空间关系查询 |

空间索引通常先使用空间对象的最小外包矩形筛选候选对象，再进行精确的几何关系判断。

### 2.4 索引属性

MySQL 还提供一些用于控制索引行为的属性：

- **降序索引**：按照指定的升序或降序保存索引键，帮助特定排序查询利用索引顺序。
- **不可见索引**：索引仍然被维护，但默认不参与优化器选取，可用于评估删除索引的影响。

降序和不可见描述的是索引属性，不是与主键索引、联合索引完全并列的独立分类。

## 3. 索引的底层实现

索引的底层结构由索引类型和存储引擎决定。先理解不同数据结构的特点，再学习 InnoDB 如何用这些结构组织索引。

### 3.1 为什么使用 B+ 树

索引需要同时支持等值查询、范围查询、排序、增删改以及磁盘分页存储。常见数据结构的特点如下：

| 数据结构 | 优点 | 局限 |
| --- | --- | --- |
| 有序数组 | 二分查找快，适合范围查询 | 插入和删除需要移动大量元素 |
| 哈希表 | 等值查询快 | 不擅长范围查询和有序遍历 |
| 二叉搜索树 | 支持有序查找 | 树高可能较大，磁盘访问次数多 |
| B+ 树 | 分支多、树高低，支持范围扫描 | 写入时需要维护页面和树结构 |

B+ 树适合数据库索引的主要原因：

- 一个节点可以保存多个键和子节点，分支因子大，树高通常较低。
- 非叶子节点主要用于导航，可以在一个页面中容纳更多键。
- 数据记录集中在叶子节点，查询路径稳定。
- 叶子页面按键顺序连接，便于范围扫描和有序遍历。
- 节点大小可以与数据库页面配合，减少磁盘随机访问。

### 3.2 哈希表

哈希索引通过哈希函数将键值映射到哈希桶，适合等值查询，但不适合范围查询、排序和有序遍历。

- `MEMORY` 存储引擎支持用户创建 `HASH` 索引。
- InnoDB 不支持用户手动创建普通哈希索引。
- InnoDB 的自适应哈希索引是存储引擎根据 B+ 树热点访问自动建立的内部内存结构，不是用户创建的独立索引。

### 3.3 倒排索引

倒排索引维护“词项 → 包含该词项的记录”的映射，适合全文关键词检索。InnoDB 的 `FULLTEXT` 索引属于这种实现。

### 3.4 R 树

R 树面向空间对象组织最小外包矩形，适合空间范围、相交和包含关系查询。InnoDB 的 `SPATIAL` 索引使用 R 树。

空间索引通常先根据最小外包矩形筛选候选对象，再进行精确的几何关系判断。

### 3.5 存储引擎差异

| 索引或特性 | 常见实现 | 典型存储引擎或场景 |
| --- | --- | --- |
| 主键索引 | 聚簇 B+ 树或引擎对应的主索引结构 | InnoDB |
| 普通索引 | 二级 B+ 树 | InnoDB |
| 唯一索引 | B+ 树加唯一性约束 | InnoDB |
| `MEMORY HASH` 索引 | 哈希表 | MEMORY |
| `FULLTEXT` 全文索引 | 倒排索引 | InnoDB |
| `SPATIAL` 空间索引 | R 树 | InnoDB |
| InnoDB 自适应哈希索引 | 内存哈希表 | InnoDB 内部自动维护 |

主键索引、唯一索引和普通索引描述的是约束或唯一性；B+ 树、哈希表、倒排索引和 R 树描述的是底层实现方式。

## 4. InnoDB 的索引组织

InnoDB 的表数据按照聚簇索引组织。索引树由页面组成，页面内记录按索引键排序；随着数据写入，页面可能发生分裂、合并或重新组织。

### 4.1 聚簇索引

聚簇索引的叶子节点保存完整行数据，因此一张 InnoDB 表只能有一个聚簇索引。

InnoDB 按以下顺序选择聚簇索引：

1. 使用显式定义的主键。
2. 没有主键时，选择第一个所有列均为 `NOT NULL` 的唯一索引。
3. 两者都不存在时，生成隐藏的行标识。

主键会影响整张表的数据组织。较短、稳定且趋势递增的主键通常可以减少二级索引空间占用和随机页分裂；业务上仍需结合唯一性、分布式写入和数据暴露风险选择主键。

### 4.2 二级索引

二级索引的叶子节点通常保存：

- 二级索引列。
- 对应记录的主键值。

通过二级索引查询完整记录时，InnoDB 先在二级索引中找到主键，再到聚簇索引中查找完整行，这个过程称为**回表**。

```text
二级索引树 -> 获得主键 -> 聚簇索引树 -> 获得完整行
```

因此主键越长，每个二级索引通常需要保存的主键数据也越多。

### 4.3 回表与覆盖索引

如果查询需要的列都能从一个索引中取得，就不必再访问聚簇索引，这称为**覆盖索引**。

假设存在联合索引 `(user_id, status, created_at)`：

```sql
SELECT status, created_at
FROM orders
WHERE user_id = 10;
```

查询条件和返回列都在索引中，有机会直接通过该索引完成查询。覆盖索引可以减少回表，但把过多列加入索引会增加空间和写入成本，需要根据查询频率和收益权衡。

### 4.4 主键、联合索引与聚簇索引

“联合索引”和“聚簇索引”属于不同维度：

- 联合索引表示索引键包含多个列。
- 聚簇索引表示叶子节点保存完整行数据。

因此，联合索引可以是聚簇索引，也可以是二级索引：

```sql
-- 联合主键：联合索引 + 聚簇索引
PRIMARY KEY (tenant_id, order_id)

-- 普通联合索引：联合索引 + 二级索引
INDEX idx_status_time (status, created_at)
```

## 5. 联合索引

联合索引按照定义的列顺序排序。索引 `(a, b, c)` 首先按 `a` 排序，`a` 相同时再按 `b` 排序，最后按 `c` 排序。

### 5.1 最左前缀

联合索引通常可以支持从最左列开始的查询组合：

- `(a)`
- `(a, b)`
- `(a, b, c)`

如果查询跳过最左列，只使用 `b` 或 `c`，通常无法直接利用该索引完成高效定位。优化器是否使用索引仍取决于数据分布、查询条件和成本估算，不能只根据 SQL 外观判断。

### 5.2 范围条件

遇到范围条件后，后续索引列通常不能继续用于缩小 B+ 树的扫描区间，但仍可能用于索引内过滤。应通过 `EXPLAIN` 的 `key`、`key_len`、`rows` 和 `Extra` 判断实际使用情况。

例如索引为 `(user_id, created_at, status)`：

```sql
WHERE user_id = 10
  AND created_at >= '2026-01-01'
  AND status = 'PAID'
```

MySQL 可以先定位 `user_id`，再扫描符合时间范围的索引记录；`status` 是否以及如何参与过滤，需要结合执行计划确认。

### 5.3 排序

当过滤条件和 `ORDER BY` 顺序与联合索引的排列方式匹配时，MySQL 可能直接按索引顺序返回结果，避免额外排序。

```sql
CREATE INDEX idx_orders_user_created
    ON orders (user_id, created_at);

SELECT id, created_at
FROM orders
WHERE user_id = 10
ORDER BY created_at DESC
LIMIT 20;
```

如果一次查询需要扫描多个不连续范围，或者排序列顺序与索引不匹配，仍可能出现额外排序。

## 6. 索引下推

索引条件下推（Index Condition Pushdown，ICP）允许存储引擎在读取完整行之前，先使用索引中的条件过滤记录，从而减少回表次数。

假设存在索引 `(user_id, status)`：

```sql
SELECT *
FROM orders
WHERE user_id BETWEEN 10 AND 20
  AND status = 'PAID';
```

即使 `status` 没有继续缩小索引扫描范围，也可能在索引层过滤不符合条件的记录。执行计划的 `Extra` 中出现 `Using index condition`，通常表示使用了索引条件下推。

## 7. 索引设计

### 7.1 根据查询设计

设计索引前应先明确：

- 查询使用哪些等值、范围和连接条件。
- 是否需要排序、分组或限制返回数量。
- 返回哪些列，回表成本是否显著。
- 查询频率、数据量和数据分布。
- 写入频率以及新增索引带来的维护成本。

联合索引通常优先考虑稳定、高频的查询模式，而不是简单地把选择性最高的列放在最前面。列顺序还要同时考虑等值条件、范围条件、排序和复用能力。

### 7.2 选择性

索引选择性可以粗略理解为不同值数量与总记录数的比例。选择性高的列通常更容易缩小扫描范围，但低选择性列与其他列组成联合索引后仍可能有价值。

可以查看索引基数：

```sql
SHOW INDEX FROM orders;
```

`Cardinality` 是估算值，不一定等于实际的不同值数量。优化器还会结合统计信息和成本模型决定访问方式。

### 7.3 避免冗余索引

已有联合索引 `(a, b)` 时，单列索引 `(a)` 可能是冗余的，因为联合索引通常也能支持只使用 `a` 的查询。但是否删除还要检查索引大小、查询计划、约束用途和实际负载。

`(a, b)` 与 `(b, a)` 的排序方式不同，不能简单视为重复索引。

## 8. 索引可能未被使用的情况

存在索引不代表优化器一定选择它。常见原因包括：

- 查询需要读取表中较大比例的数据，全表扫描成本更低。
- 对索引列进行计算或使用无法利用索引顺序的函数。
- 字符串与数字等类型不一致，发生隐式类型转换。
- `LIKE` 模式以通配符开头，例如 `LIKE '%keyword'`。
- 联合索引没有匹配可用于定位的左侧列。
- 统计信息不准确，导致优化器成本估算偏差。
- 返回列较多且回表次数过多。

这些情况不是绝对规则。应使用执行计划和实际数据验证，不要仅凭经验判断索引是否生效。

## 9. 执行计划

使用 `EXPLAIN` 查看优化器选择的访问方式：

```sql
EXPLAIN
SELECT id, created_at
FROM orders
WHERE user_id = 10
ORDER BY created_at DESC
LIMIT 20;
```

重点关注：

| 字段 | 含义 |
| --- | --- |
| `type` | 访问方式，例如 `const`、`ref`、`range`、`index`、`ALL` |
| `possible_keys` | 优化器认为可能使用的索引 |
| `key` | 实际选择的索引 |
| `key_len` | 实际使用的索引键长度 |
| `rows` | 预计需要读取的记录数 |
| `filtered` | 读取后预计能通过条件的比例 |
| `Extra` | 覆盖索引、索引下推、排序和临时表等补充信息 |

MySQL 8.4 还可以使用 `EXPLAIN ANALYZE` 执行查询并查看实际行数和耗时。分析性能时，应对比估算值与实际值，并记录数据规模和分布。

## 10. 慢查询排查

慢查询排查不能只看“是否使用索引”，而应结合执行计划、实际耗时、扫描行数和运行状态，确认慢在哪里以及为什么慢。

### 10.1 确认问题

先记录完整 SQL、参数、执行时间、返回行数和执行频率，并区分以下情况：

- 偶发变慢：可能与锁等待、I/O 抖动、缓存未命中或临时资源竞争有关。
- 持续变慢：可能与 SQL、索引、数据量增长或统计信息有关。
- 并发升高后变慢：可能与连接数、锁竞争、CPU、内存或磁盘 I/O 有关。

### 10.2 定位慢查询

根据查询是否已经执行完成，选择不同的数据来源：

#### 10.2.1 慢查询日志

慢查询日志记录超过 `long_query_time` 的 SQL，适合定位已经执行过的具体 SQL。先确认相关配置：

```sql
SHOW VARIABLES LIKE 'slow_query_log';
SHOW VARIABLES LIKE 'long_query_time';
```

日志中通常可以看到执行时间、锁等待时间、扫描行数、返回行数和具体 SQL。日志积累后，可以使用 `mysqldumpslow` 对相似查询进行初步汇总。

#### 10.2.2 Performance Schema

`events_statements_summary_by_digest` 按 SQL 模板聚合查询，可以找出一段时间内总耗时、平均耗时、最大耗时或扫描行数最高的 SQL 类型：

```sql
SELECT
    DIGEST_TEXT,
    COUNT_STAR,
    ROUND(SUM_TIMER_WAIT / 1000000000000, 2) AS total_seconds,
    ROUND(AVG_TIMER_WAIT / 1000000000000, 2) AS avg_seconds,
    ROUND(MAX_TIMER_WAIT / 1000000000000, 2) AS max_seconds,
    SUM_ROWS_EXAMINED,
    SUM_ROWS_SENT
FROM performance_schema.events_statements_summary_by_digest
WHERE DIGEST_TEXT IS NOT NULL
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 20;
```

慢查询日志更容易定位具体执行实例，Performance Schema 更适合发现需要长期优化的 SQL 模板。应同时关注总耗时、平均耗时、最大耗时、调用次数，以及扫描行数与返回行数的差距。

#### 10.2.3 当前正在执行的 SQL

正在执行或疑似卡住的 SQL 可以通过进程列表查看：

```sql
SHOW FULL PROCESSLIST;
```

重点查看 `Time`、`State` 和 `Info` 字段：

- `Time`：当前状态持续时间。
- `State`：是否正在等待锁、排序或其他资源。
- `Info`：完整 SQL 文本；使用 `FULL` 避免 SQL 被截断。

定位结果可以分为：

```text
慢查询日志：已经执行过的具体 SQL
Performance Schema：一段时间内最值得优化的 SQL 模板
Processlist：当前正在执行或等待资源的 SQL
```

### 10.3 根据证据判断现象

| 现象 | 主要依据 | 判断方式 |
| --- | --- | --- |
| 全表扫描 | `EXPLAIN` | `type = ALL`，`key` 为空，`rows` 接近全表行数 |
| 扫描行数过多 | `EXPLAIN ANALYZE` | 实际读取行数远大于最终返回行数 |
| 索引未生效 | `EXPLAIN` | `key` 为空，或使用了不符合预期的索引 |
| 回表很多 | 执行计划与返回列 | 使用二级索引但查询大量非索引列，实际读取行数很大 |
| 排序成本高 | `Extra` | 出现 `Using filesort`，再结合数据量和耗时判断 |
| 临时表成本高 | `Extra` | 出现 `Using temporary` |
| 锁等待 | 运行状态 | `SHOW PROCESSLIST` 显示等待锁，再结合锁表和事务信息定位阻塞者 |
| 统计信息不准 | 估算与实际对比 | `EXPLAIN` 的 `rows` 与 `EXPLAIN ANALYZE` 实际行数差距很大 |
| I/O 或内存压力 | 数据库与系统指标 | 磁盘 I/O 高、缓存命中率下降或资源使用持续升高 |

这些信号不能脱离数据规模单独下结论。例如，小表出现 `type = ALL` 可能比使用索引更快；`Using filesort` 也不一定意味着发生了磁盘排序。

### 10.4 排查步骤

1. 使用 `EXPLAIN` 查看访问方式、使用的索引、预计扫描行数和额外操作。
2. 对可安全执行的查询使用 `EXPLAIN ANALYZE`，对比预计行数与实际行数、耗时。
3. 检查 SQL 条件是否符合联合索引的最左前缀，是否存在函数、隐式类型转换或前导通配符。
4. 检查是否需要调整联合索引列顺序、减少回表或使用覆盖索引。
5. 使用 `SHOW FULL PROCESSLIST`、慢查询日志和 `performance_schema` 检查锁等待、阻塞事务和资源竞争。
6. 对比优化前后的执行计划、实际耗时、扫描行数、返回行数和资源消耗。

```sql
EXPLAIN
SELECT id, created_at
FROM orders
WHERE user_id = 10
ORDER BY created_at DESC
LIMIT 20;

EXPLAIN ANALYZE
SELECT id, created_at
FROM orders
WHERE user_id = 10
ORDER BY created_at DESC
LIMIT 20;

SHOW FULL PROCESSLIST;
```

### 10.5 优化原则

- 不要因为 `key` 为空就立即增加索引，先确认全表扫描是否真的成本更高。
- 不要只追求“走索引”，重点是减少无效扫描、回表、排序和锁等待。
- 索引调整后要检查写入成本、索引空间和其他查询是否受到影响。
- 生产环境先进行限流、分页、拆分大查询或终止异常 SQL 等止血操作，再做长期优化。

## 11. 实践

创建订单表和联合索引：

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    amount DECIMAL(12, 2) NOT NULL,
    created_at DATETIME NOT NULL,
    INDEX idx_orders_user_status_created (
        user_id,
        status,
        created_at
    )
);
```

准备具有不同用户、状态和时间分布的数据，然后依次实验：

1. 使用用户、状态和时间范围查询订单，观察联合索引的使用情况。
2. 分别省略 `user_id`、`status`，对比最左前缀和范围条件的影响。
3. 改变 `ORDER BY` 字段和方向，观察是否出现额外排序。
4. 分别只查询索引列和查询 `amount`，对比覆盖索引与回表。
5. 对索引列使用函数或隐式类型转换，检查访问方式和扫描行数。
6. 增加或调整索引后使用 `EXPLAIN ANALYZE` 对比实际读取行数和耗时。
7. 执行批量插入和更新，观察新增索引对写入性能和存储空间的影响。

完成实验后，应能够根据具体 SQL 解释索引的列顺序、扫描范围、回表过程和写入成本，而不是只判断查询是否“走索引”。
