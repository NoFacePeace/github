# MySQL CDC

CDC（Change Data Capture，变更数据捕获）用于识别数据库中的数据变化，并将新增、修改和删除事件持续同步到其他系统。MySQL CDC 通常通过读取 binlog 实现，常用于缓存更新、搜索索引同步、数据仓库入库和事件驱动架构。

## 1. 基本原理

应用向 MySQL 提交事务后，MySQL 会将数据变化写入 binlog。CDC 组件作为 binlog 消费者，解析其中的变更事件，再将事件发送到 Kafka、数据库、搜索引擎或数据仓库。

```text
应用
  |
  v
MySQL -> binlog -> CDC 组件 -> Kafka / Elasticsearch / 数据仓库 / 其他数据库
```

CDC 关注的是已经提交的数据变化。未提交事务不会作为完整的已提交变更交付给下游；事务回滚产生的修改也不应成为下游最终状态。

## 2. Binlog 基础

### 2.1 Binlog 格式

MySQL 支持三种 binlog 格式：

| 格式 | 记录内容 | CDC 适用性 |
| --- | --- | --- |
| `STATEMENT` | 执行的 SQL 语句 | 较差，部分语句难以准确还原行变化 |
| `ROW` | 每一行数据的变化 | 最适合 CDC |
| `MIXED` | 根据场景选择语句或行格式 | 解析逻辑更复杂 |

CDC 一般使用 `ROW`，因为它直接记录行级变更，不需要重新执行 SQL 来推导最终结果。

### 2.2 事件类型

在行格式 binlog 中，常见数据操作可以映射为以下事件：

| SQL 操作 | Binlog 行事件 | CDC 语义 |
| --- | --- | --- |
| `INSERT` | `Write_rows` | 创建记录 |
| `UPDATE` | `Update_rows` | 更新记录，通常包含修改前后的值 |
| `DELETE` | `Delete_rows` | 删除记录 |

除了行事件，CDC 还需要识别事务开始、提交、表结构和表映射等信息，才能正确恢复事件所属的数据库、表和事务边界。

### 2.3 消费位置

CDC 组件需要保存已经处理到的位置，以便重启后继续消费：

- **文件名与偏移量**：例如 binlog 文件和 position。
- **GTID**：使用全局事务标识记录消费进度，更适合主从切换和故障恢复。

只有在下游成功处理事件后再推进消费位置，才能降低事件丢失风险；如果处理成功但位置尚未保存就发生故障，则可能重复消费。

## 3. 同步流程

### 3.1 全量快照

首次接入时，下游通常没有历史数据，需要先读取当前表中的全部记录，建立一个数据快照。

快照必须与后续 binlog 增量事件正确衔接。如果记录 binlog 起点和读取快照的时机不一致，可能出现数据遗漏或重复。

### 3.2 增量同步

完成快照后，CDC 组件从对应的 binlog 位置继续读取变更，并持续发送到下游。

```text
确定 binlog 起点 -> 读取全量快照 -> 重放快照期间的变更 -> 持续增量同步
```

生产级 CDC 工具通常会处理快照与增量之间的衔接。自行实现时，需要重点保证快照一致性、事务边界和消费位置的持久化。

## 4. MySQL 配置

典型配置如下，实际参数应结合 MySQL 版本和部署方式调整：

```ini
[mysqld]
server_id=1
log_bin=mysql-bin
binlog_format=ROW
binlog_row_image=FULL
```

- `server_id`：标识 MySQL 实例，在复制拓扑中需要唯一。
- `log_bin`：启用 binlog。
- `binlog_format=ROW`：记录行级变化。
- `binlog_row_image=FULL`：记录完整的行镜像，便于下游获得更新前后的完整数据。

还需要为 CDC 客户端配置合适的账号权限，并确保 binlog 保留时间长于允许的最大消费中断时间。否则 CDC 长时间停止后，所需的历史 binlog 可能已经被清理，只能重新执行全量同步。

## 5. 一致性与可靠性

### 5.1 重复与丢失

CDC 常采用至少一次交付：允许事件重复，但尽量避免事件丢失。因此下游写入应具备幂等性，例如使用主键覆盖写入、事件唯一标识去重或事务性写入。

不能仅因为 CDC 工具读取 binlog，就认为整个链路实现了端到端的精确一次。是否精确一次还取决于消息系统、消费位置保存方式以及下游写入策略。

### 5.2 顺序

同一事务中的事件需要按原始顺序处理。事件进入 Kafka 等消息系统后，如果按照不同分区并行消费，全局顺序通常无法保证，应根据业务需要按照主键、表或其他稳定字段分区。

### 5.3 表结构变化

`ALTER TABLE` 等 DDL 可能改变字段名称、类型和顺序。CDC 系统需要同步维护表结构信息，下游也要考虑字段新增、删除和类型变更的兼容性。

### 5.4 大事务

大事务会一次产生大量 binlog 事件，可能增加内存占用、同步延迟和下游写入压力。业务侧应尽量避免超大事务，CDC 侧则需要设置合理的缓冲、批量和失败重试策略。

## 6. CDC 与 MySQL 复制

CDC 和主从复制都可以消费 binlog，但目标不同：

| 对比项 | MySQL 复制 | CDC |
| --- | --- | --- |
| 主要目标 | 维护 MySQL 副本 | 将数据变化交给异构系统 |
| 下游 | MySQL 实例 | Kafka、搜索引擎、数据仓库等 |
| 事件处理 | 在副本中重放 | 解析、转换、路由或聚合 |
| 典型用途 | 高可用、读扩展、灾备 | 数据集成、缓存更新、事件驱动 |

CDC 可以利用复制协议读取 binlog，但它不是 MySQL 主从复制本身。

## 7. 常见工具

- **Debezium**：常与 Kafka Connect 配合，将数据库变更写入 Kafka。
- **Canal**：模拟 MySQL 从库协议，解析 binlog 并提供变更数据。
- **Flink CDC**：将数据库快照和增量变更接入 Flink 数据处理任务。

选择工具时应重点比较快照能力、DDL 支持、断点恢复、事务语义、监控能力和目标系统连接器。

## 8. 实践建议

可以使用一张简单的用户表完成 CDC 实验：

1. 启用 MySQL binlog，并确认格式为 `ROW`。
2. 启动 CDC 工具，记录初始快照结果。
3. 分别执行 `INSERT`、`UPDATE` 和 `DELETE`。
4. 检查下游事件是否包含数据库、表、主键、操作类型和变更前后数据。
5. 连续提交包含多条 SQL 的事务，确认事务内事件顺序。
6. 停止 CDC 工具后继续写入 MySQL，再重启工具，验证断点续传。
7. 模拟下游写入成功但消费位置未及时保存的情况，验证幂等处理。

完成实验后，应能够解释 MySQL CDC 的数据来源、快照与增量的衔接方式，以及重复、顺序、DDL 和 binlog 过期带来的风险。
