# HTTP

建议按照下面的顺序学习 HTTP：

1. **基础概念**：理解 HTTP 的用途、客户端与服务器、资源、URI、请求—响应模型，以及 HTTP 在 TCP/IP 协议栈中的位置。
2. **一次请求的完整链路**：从 DNS 解析、建立 TCP 或 QUIC 连接，到发送请求、接收响应和关闭或复用连接。
3. **请求与响应报文**：掌握起始行、首部字段、空行、消息内容，以及请求和响应的基本结构。
4. **请求方法与状态码**：理解各方法的语义、安全性、幂等性和缓存特征，能够根据状态码判断处理结果。
5. **首部字段与消息内容**：学习内容协商、压缩、范围请求、重定向、认证、代理和跨域相关首部。
6. **资源表示与接口设计**：理解媒体类型、字符编码、JSON、表单、文件上传，以及 REST 风格接口中的 HTTP 语义。
7. **缓存**：掌握浏览器缓存、代理缓存、条件请求、验证器、缓存新鲜度和缓存失效。
8. **Cookie**：理解 Cookie 的生命周期、作用域、属性和安全策略。
9. **Session**：理解服务端如何维护登录状态，以及 Session ID、过期、注销和分布式存储。
10. **连接管理与性能**：学习 Keep-Alive、连接池、队头阻塞、超时、重试、代理和负载均衡。
11. **HTTP 版本演进**：按 HTTP/1.1、HTTP/2、HTTP/3 的顺序比较文本协议、多路复用、流控制和 QUIC。
12. **HTTPS 与安全**：在理解 HTTP 语义后学习 TLS、证书验证、TLS 终止、HSTS、mTLS 和常见误区。
13. **调试与实践**：使用 `curl`、浏览器开发者工具、`openssl s_client`、抓包工具和服务端日志观察真实请求。

学习时建议先掌握 HTTP/1.1 的请求—响应模型，再学习缓存、Cookie、代理和连接复用，最后比较 HTTP/2、HTTP/3 与 HTTPS。每学完一个主题，都可以用一个真实请求验证：请求发往哪里、携带了什么、服务器如何处理、响应能否被缓存，以及连接如何结束。

## 1. 基础概念

HTTP（Hypertext Transfer Protocol，超文本传输协议）是应用层协议，用于在客户端和服务器之间传输资源。资源可以是 HTML、CSS、JavaScript、图片、视频、JSON 数据或其他内容。

HTTP 的核心模型是请求—响应：

```text
客户端 ── HTTP 请求 ──> 服务器
客户端 <─ HTTP 响应 ─── 服务器
```

需要先区分几个概念：

- **客户端**：发起请求的一方，常见的是浏览器、移动应用、命令行工具和其他服务。
- **服务器**：接收请求并生成响应的一方，也可能由 CDN、反向代理、网关和应用服务共同完成。
- **资源**：可以通过 URI 标识并被访问的数据或服务对象。
- **表示（Representation）**：资源在某次响应中的具体表现，例如 HTML 文档或 JSON 文档。
- **安全方法**：不会由请求方主动产生状态变化的方法，例如 `GET` 和 `HEAD`。
- **幂等方法**：同一个请求执行一次或多次，预期的最终效果相同，例如 `GET`、`PUT` 和 `DELETE`。幂等不代表请求一定成功，也不代表服务器不会记录每次请求。

HTTP 本身主要定义消息语义和报文格式，不负责域名解析、可靠传输或加密。一次访问通常还会依赖 DNS、TCP 或 QUIC，以及 TLS。

## 2. 请求与响应

HTTP 报文由起始行、首部字段、空行和可选的消息内容组成：

```text
起始行
首部字段
首部字段

消息内容
```

请求起始行为：

```text
GET /articles/1 HTTP/1.1
```

响应的起始行为状态行：

```text
HTTP/1.1 200 OK
```

需要重点理解：

- 请求目标可以是路径、绝对 URI、权威组件或特殊的 `*`，具体形式取决于使用场景。
- `Host` 首部用于指示目标主机，HTTP/1.1 请求通常必须携带它。
- `Content-Length` 表示消息内容的长度；分块传输编码可以让 HTTP/1.1 在不知道总长度时逐块发送。
- `Transfer-Encoding` 和 `Content-Encoding` 解决的问题不同：前者描述消息如何传输，后者描述内容如何压缩或编码。
- 没有消息内容的响应不一定表示没有业务数据，数据也可能通过首部字段表达。

## 3. 请求方法与状态码

常用请求方法：

| 方法 | 主要用途 | 典型特征 |
| --- | --- | --- |
| `GET` | 获取资源 | 安全、幂等、通常可缓存 |
| `HEAD` | 只获取响应首部 | 安全、幂等，不返回消息内容 |
| `POST` | 提交数据或触发处理 | 通常不幂等，默认不作为普通缓存对象 |
| `PUT` | 创建或整体替换目标资源 | 幂等 |
| `PATCH` | 对资源进行部分修改 | 是否幂等取决于接口设计 |
| `DELETE` | 删除目标资源 | 幂等，但重复执行可能返回不同状态码 |
| `OPTIONS` | 查询通信选项 | 常用于 CORS 预检 |
| `CONNECT` | 建立隧道 | 常用于代理 |

状态码按第一位分为五类：

| 类别 | 含义 | 常见状态码 |
| --- | --- | --- |
| `1xx` | 信息响应 | `100 Continue` |
| `2xx` | 请求成功 | `200 OK`、`201 Created`、`204 No Content` |
| `3xx` | 重定向或缓存相关处理 | `301`、`302`、`304 Not Modified`、`307`、`308` |
| `4xx` | 客户端请求存在问题 | `400`、`401`、`403`、`404`、`409`、`429` |
| `5xx` | 服务端处理失败 | `500`、`502`、`503`、`504` |

重点区分：

- `401` 表示需要认证或认证失败，`403` 表示服务器理解请求但拒绝执行。
- `301`、`302` 可能改变后续请求方法；`307`、`308` 要求保留原请求方法。
- `304` 不是错误，而是条件请求命中缓存验证器后的结果，响应通常不包含消息内容。
- `502`、`503` 和 `504` 常见于网关或反向代理，但根因可能在上游应用、网络或依赖服务。

## 4. 首部字段

首部字段用于描述请求意图、目标资源、内容格式、缓存策略、认证信息和代理行为。建议按用途学习：

- **目标与路由**：`Host`、`Forwarded`、`X-Forwarded-For`。
- **内容描述**：`Content-Type`、`Content-Length`、`Content-Encoding`、`Content-Language`。
- **内容协商**：`Accept`、`Accept-Encoding`、`Accept-Language`、`Vary`。
- **缓存控制**：`Cache-Control`、`Expires`、`ETag`、`Last-Modified`、`If-None-Match`、`If-Modified-Since`。
- **认证与会话**：`Authorization`、`WWW-Authenticate`、`Cookie`、`Set-Cookie`。
- **重定向与来源**：`Location`、`Referer`、`Origin`。
- **连接与范围**：`Connection`、`Range`、`If-Range`。
- **安全策略**：`Strict-Transport-Security`、`Content-Security-Policy`、`X-Content-Type-Options`。

首部字段的值会影响服务器如何解析请求以及中间缓存如何处理响应。排查问题时，要同时看请求首部和响应首部，不能只看状态码。

## 5. 缓存

HTTP 缓存的目标是减少网络传输和服务器处理。缓存行为通常由响应中的 `Cache-Control`、`Expires`、`ETag`、`Last-Modified` 和 `Vary` 等字段控制。

建议按以下顺序理解：

1. **新鲜度**：缓存对象在有效期内可以直接复用。
2. **验证**：缓存过期后，客户端使用 `If-None-Match` 或 `If-Modified-Since` 向服务器确认资源是否变化。
3. **验证成功**：服务器返回 `304 Not Modified`，客户端继续使用本地内容。
4. **资源变化**：服务器返回新的表示和新的缓存元数据。
5. **缓存位置**：浏览器缓存、共享代理缓存、CDN 缓存和应用自身缓存可能同时存在。

需要区分浏览器刷新、强制刷新、禁用缓存、私有缓存和共享缓存的行为。缓存设计还要考虑用户身份、响应中的敏感数据、查询参数、`Vary` 维度以及发布新资源时的缓存失效策略。

## 6. Cookie

Cookie 是服务器通过 `Set-Cookie` 响应首部交给客户端保存的一小段状态数据，后续请求在匹配作用域时通过 `Cookie` 请求首部发送。

### 6.1 基本格式

服务器设置一个 Cookie 时，格式通常为：

```http
Set-Cookie: 名称=值; 属性=属性值; 属性标记
```

例如，`session_id` 是 Cookie 的名称，`abc123` 是值，后面的部分是属性：

```http
Set-Cookie: session_id=abc123; Domain=example.com; Path=/; Max-Age=3600; Secure; HttpOnly; SameSite=Lax
```

Cookie 的名称、值和属性之间使用分号分隔。

服务器可以通过多条 `Set-Cookie` 首部设置多个 Cookie，每个 Cookie 都有自己的名称、值和属性：

```http
Set-Cookie: session_id=abc123; Path=/; Secure; HttpOnly
Set-Cookie: theme=dark; Path=/; Max-Age=86400
```

客户端会分别保存这两个 Cookie。后续请求通常只携带名称和值，多个 Cookie 之间使用分号分隔：

```http
Cookie: session_id=abc123; theme=dark
```

`Domain`、`Path`、`Secure`、`HttpOnly` 等属性由客户端保存并用于判断是否发送 Cookie，通常不会作为请求首部再次发送给服务器。

### 6.2 常用属性

| 属性 | 格式 | 作用 |
| --- | --- | --- |
| `Domain` | `Domain=example.com` | 限制 Cookie 可以发送到的域名范围。 |
| `Path` | `Path=/admin` | 限制 Cookie 可以发送到的 URL 路径范围。 |
| `Max-Age` | `Max-Age=3600` | 指定 Cookie 还能保存多少秒；过期后客户端应删除它。 |
| `Expires` | `Expires=Wed, 09 Jun 2027 10:18:14 GMT` | 指定 Cookie 的过期时间。 |
| `Secure` | `Secure` | 只允许通过 HTTPS 发送 Cookie。 |
| `HttpOnly` | `HttpOnly` | 禁止浏览器脚本通过 `document.cookie` 读取 Cookie。 |
| `SameSite` | `SameSite=Lax` | 限制跨站请求是否携带 Cookie，常见值有 `Strict`、`Lax` 和 `None`。 |

`Max-Age` 和 `Expires` 都可以控制有效期，通常优先使用 `Max-Age`。设置 `SameSite=None` 时，通常还必须同时设置 `Secure`。第三方 Cookie、跨站请求和浏览器隐私策略会影响这些属性的实际行为。

### 6.3 常见用途

| 用途 | 示例 | 备注 |
| --- | --- | --- |
| 登录状态 | 保存 Session ID 或访问令牌 | 让服务器识别用户身份；保存 JWT 时应配置合适的安全属性。 |
| 会话数据 | 保存购物车、临时表单状态 | 适合保存短期、少量的状态信息。 |
| 用户偏好 | 保存语言、主题、地区 | 通常不涉及敏感数据，可以设置较长的有效期。 |
| 安全校验 | 配合 CSRF Token、设备标识 | 不能只依赖 Cookie 本身，还需要服务端校验。 |
| 统计分析 | 记录访问来源、页面访问情况 | 应考虑用户隐私、授权和数据合规要求。 |

Cookie 通常只保存短小的标识或配置，不适合保存密码、隐私信息或大量业务数据。

## 7. Session

Session 不是 HTTP 内置的协议机制，而是应用基于 HTTP 实现的一种会话管理方案。它用于在多个无状态的 HTTP 请求之间保存用户状态，例如登录状态、购物车和权限信息。

Session 本身不是认证过程，也不负责验证用户名和密码。认证负责确认用户身份；Session 负责在认证成功后保存认证结果，并在后续请求中维持用户状态。即使用户未登录，Session 也可以用于保存购物车、临时表单等状态。

常见做法是：服务端创建一个不可预测的 Session ID，通过 `Set-Cookie` 交给客户端；客户端后续请求通过 `Cookie` 发送 Session ID；服务端根据 Session ID 查询真正的会话数据。

### 7.1 基本流程

以用户登录为例：

```text
客户端                         服务端
  |                              |
  |-- POST /login -------------->|
  |                              | 验证用户名和密码
  |                              | 创建 Session 数据
  |<-- Set-Cookie: sid=abc123 ---|
  |                              |
  |-- Cookie: sid=abc123 ------->|
  |                              | 查询 Session，识别用户
  |<-- 返回受保护资源 ------------|
```

Session ID 只是查询会话数据的索引，不应该直接包含密码等敏感信息。真正的用户身份、登录时间、权限和过期时间通常保存在服务端。

### 7.2 生命周期

Session 通常经历以下阶段：

1. **创建**：用户登录成功后，服务端生成 Session ID 和会话记录。
2. **使用**：客户端在后续请求中携带 Session ID，服务端据此恢复用户状态。
3. **续期**：用户持续活动时更新过期时间，必要时轮换 Session ID。
4. **过期**：达到绝对过期时间或闲置超时时，服务端拒绝该 Session。
5. **注销**：删除或标记服务端会话记录，并让客户端删除对应 Cookie。

服务端通常同时设置两类时间限制：

- **闲置超时**：用户一段时间没有活动后失效；
- **绝对过期时间**：无论是否持续使用，到达上限后都必须重新登录。

注销时不能只依赖客户端删除 Cookie，因为客户端可能没有成功删除，或者攻击者已经复制了旧的 Session ID。服务端也应主动使会话失效。

### 7.3 会话存储

| 存储方式 | 特点 | 适用场景 |
| --- | --- | --- |
| 进程内存 | 访问快，实现简单 | 单实例服务或开发环境 |
| 数据库 | 持久性较好，便于查询和审计 | 会话数量较少或已有数据库 |
| Redis 等缓存 | 访问快，支持过期时间和共享 | 多实例服务的常见选择 |
| 加密文件 | 部署简单，但并发和扩展性有限 | 小型应用或特殊环境 |

如果服务部署为多个实例，不能只把 Session 保存在某一个实例的本地内存中，否则同一个用户的请求被转发到不同实例时可能无法找到会话。常见解决方案是使用共享存储，或者使用会话粘滞将用户固定到同一实例。

共享存储通常更可靠，但也需要考虑 Redis 或数据库不可用时的降级策略、会话数据大小、清理机制和访问权限。

### 7.4 安全问题

- **Session ID 可预测**：攻击者可以猜中其他用户的会话。应使用密码学安全的随机值，并保证足够长度。
- **会话固定**：攻击者先取得一个 Session ID，再诱导用户登录并继续使用该 ID。登录成功后应重新生成 Session ID。
- **Session ID 泄露**：日志、URL、浏览器历史记录或恶意脚本都可能泄露会话标识。不要把 Session ID 放在 URL 中。
- **窃取 Cookie**：应配置 `Secure`、`HttpOnly` 和合适的 `SameSite`，并全程使用 HTTPS。
- **CSRF**：浏览器可能自动携带 Cookie，服务端应使用 `SameSite`、CSRF Token 或来源校验等防护。
- **会话未及时失效**：密码修改、退出登录和权限变化后，应主动撤销相关会话。

Session ID 等同于临时凭证。拿到有效 Session ID 的攻击者通常可以冒充对应用户，因此不能将它写入日志，也不应在错误信息、分析参数或前端页面中暴露。

### 7.5 Session、Cookie 与 JWT

Session、Cookie 和 JWT 经常组合使用，但三者职责不同：

- **Session**：服务端保存用户状态的会话机制。
- **Cookie**：客户端保存并发送少量数据的 HTTP 机制。
- **JWT**：客户端携带的身份凭证，可以让服务端在不查询 Session 的情况下识别用户。

#### 7.5.1 Session 与 Cookie 的关系

Session 和 Cookie 不是同一种机制：

| 项目 | Session | Cookie |
| --- | --- | --- |
| 主要位置 | 服务端 | 客户端 |
| 主要作用 | 保存用户状态 | 保存并发送少量数据 |
| 是否负责认证 | 不负责认证，只保存认证结果 | 不负责认证，只传递标识或数据 |
| 常见内容 | `user_id`、权限、创建时间、过期时间 | `session_id=abc123` |

常见的 `Session + Cookie` 方案中，Cookie 保存 Session ID，服务端根据 Session ID 查询用户状态。Cookie 本身不等于登录状态；只有服务端找到有效 Session 时，用户才会被识别为已登录。

Session ID 也可以通过 `Authorization` 或自定义请求首部传递，不一定必须使用 Cookie。

#### 7.5.2 Session 与 JWT 的对比

| 对比项 | Session | JWT |
| --- | --- | --- |
| 状态保存位置 | 主要保存在服务端 | 主要编码在 Token 中，由客户端携带 |
| 请求携带内容 | Session ID | JWT |
| 服务端查询 | 通常需要查询 Session | 通常只需验证 Token |
| 注销和撤销 | 删除或撤销 Session 即可 | 通常需要短过期、刷新机制或黑名单 |
| 多服务使用 | 需要共享 Session 存储 | 便于在服务之间传递 |
| 主要风险 | Session ID 泄露、CSRF | Token 泄露、撤销和刷新较复杂 |

#### 7.5.3 Cookie 与 JWT 的组合方式

Session 和 JWT 都可以使用 Cookie，也可以使用请求首部传递：

| 方案 | 状态保存位置 | 常见传递方式 | 注意事项 |
| --- | --- | --- | --- |
| Session + Cookie | 服务端 | `Cookie: session_id=...` | 浏览器会自动携带，需要防范 CSRF |
| Session + 请求首部 | 服务端 | `Authorization` 或自定义首部 | 客户端需要主动管理 Session ID |
| JWT + Cookie | Token 中 | `Cookie: access_token=...` | 浏览器会自动携带，需要防范 CSRF |
| JWT + `Authorization` | Token 中 | `Authorization: Bearer ...` | 客户端主动携带，需要防范 Token 泄露和 XSS |

#### 7.5.4 选择建议

- **传统浏览器网站**：优先考虑服务端 Session 加 `HttpOnly`、`Secure`、`SameSite` Cookie。
- **需要立即注销和撤销会话**：Session 通常更直接。
- **需要跨服务传递身份或支持多种客户端**：可以比较 JWT 方案。
- **使用 JWT**：需要设计过期、刷新、撤销、密钥轮换和 Token 泄露后的处理方式。

无论采用哪种方案，都应使用 HTTPS，并保护 Session ID 或 Token。

## 8. 连接管理

HTTP 请求通常需要依赖底层连接。HTTP/1.0 常见“每个请求建立一次连接”的模式；HTTP/1.1 默认支持持久连接，可以在同一 TCP 连接上连续发送多个请求。

重点内容包括：

- TCP 三次握手、TLS 握手与 HTTP 请求之间的关系；
- Keep-Alive、连接池和空闲连接超时；
- 请求超时、连接超时、读取超时与整体截止时间；
- 代理、反向代理、网关和负载均衡器如何转发请求；
- 重试的适用条件，以及非幂等请求重复提交的风险；
- HTTP/1.1 管线化受限于队头阻塞，浏览器通常通过多个连接并发请求。

在排查慢请求时，应该区分 DNS、建立连接、TLS 握手、等待首字节和下载内容等阶段，而不是只记录一个总耗时。

## 9. 版本演进

### 9.1 HTTP/1.1

HTTP/1.1 使用可读的文本报文，支持持久连接、分块传输、范围请求、条件请求和缓存控制。它容易调试，但多个请求共享一个连接时可能受到队头阻塞影响。

### 9.2 HTTP/2

HTTP/2 将 HTTP 语义映射到二进制帧和流，支持同一连接上的多路复用、首部压缩、流优先级和流级别控制。HTTP/2 仍然通常运行在 TCP 上，因此丢包可能阻塞整个 TCP 连接上的多个流。

### 9.3 HTTP/3

HTTP/3 将 HTTP 映射到 QUIC。QUIC 基于 UDP 实现可靠传输、连接迁移和加密握手，使不同流能够减少相互阻塞。学习 HTTP/3 时要先理解 QUIC 的连接、流、包、拥塞控制和 TLS 1.3 集成。

比较不同版本时，重点关注“语义是否变化”和“传输方式如何变化”：请求方法、状态码和大多数首部语义保持连续，变化主要发生在报文编码、连接管理和传输层。

## 10. HTTPS

### 10.1 基本概念

HTTPS 是通过安全连接传输的 HTTP，使用 `https://` URI，默认端口为 `443`。HTTP 的请求方法、状态码、首部等语义仍然适用，TLS 负责保护传输过程。参见 [RFC 9110：HTTPS](https://www.rfc-editor.org/rfc/rfc9110.html#section-4.2.2)。

| 协议组合 | 通信结构 |
| --- | --- |
| HTTP/1.1 或 HTTP/2 的 HTTPS 连接 | HTTP → TLS → TCP → IP |
| HTTP/3 | HTTP → QUIC（集成 TLS 1.3 握手）→ UDP → IP |

HTTP/3 中，TLS 提供身份认证与密钥协商，QUIC 使用派生的密钥保护数据包，不使用传统的 TLS 记录层封装 HTTP 数据。参见 [RFC 9001](https://www.rfc-editor.org/rfc/rfc9001.html#section-4)。

TLS 的版本演进、加密机制、证书验证、握手、会话恢复与 mTLS，见 [TLS 学习笔记](../security/tls.md)。

### 10.2 解决的问题

| 能力 | 作用 |
| --- | --- |
| 机密性 | 防止链路上的旁观者直接读取请求与响应内容 |
| 完整性 | 检测传输中的数据篡改 |
| 身份认证 | 通过证书等机制验证通信对端的身份，通常由客户端验证服务端 |

HTTPS 保护通信链路，不代表网站内容可信，也不能自动防止应用漏洞或终端泄露数据。

### 10.3 TLS 终止与保护范围

实际部署中，TLS 可能终止于 CDN、负载均衡器或反向代理：

```text
客户端 ── HTTPS ── 反向代理 ── HTTP 或 HTTPS ── 应用服务
```

代理解密后能够读取 HTTP 内容。若代理到应用服务使用 HTTP，该段链路没有 TLS 保护；若使用 HTTPS，则是另一条独立的安全连接。浏览器显示 HTTPS，并不能说明后端所有链路都已加密。

### 10.4 常见误区

- **HTTPS 会隐藏所有访问痕迹**：HTTP 路径、查询参数、首部和正文在 TLS 链路内受到保护，但 IP 地址、流量大小与时序仍可能被观察；普通 DNS 查询或未加密的 SNI 也可能暴露域名。
- **证书有效就代表网站安全**：证书验证的是身份绑定，网站仍可能存在恶意内容或应用漏洞。
- **HTTPS 等于用户已登录**：常见 HTTPS 连接只认证服务端，用户身份仍由登录机制处理；双向 TLS（mTLS）可额外认证客户端证书。
- **忽略证书错误不影响安全**：跳过验证会失去对服务端身份的可靠确认，使中间人攻击成为可能。
