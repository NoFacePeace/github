# TCP

TCP（Transmission Control Protocol，传输控制协议）是面向连接、可靠、基于字节流的传输层协议。它通过序列号、确认、重传、流量控制和拥塞控制等机制，使数据能够按序、无重复地交付给接收方。

## 1. 基础概念

TCP 通信由源 IP、源端口、目标 IP 和目标端口共同标识。IP 地址用于定位主机，端口用于定位主机上的应用进程。

TCP 的主要特征包括：

- **面向连接**：传输数据前需要建立连接，通信结束后需要释放连接。
- **可靠传输**：通过确认、超时重传和快速重传处理丢包。
- **按序交付**：接收方根据序列号重排数据，向应用交付连续字节流。
- **全双工**：连接双方可以同时发送和接收数据。
- **字节流**：TCP 不保留应用消息边界，应用需要自行定义消息长度或分隔方式。
- **流量控制**：避免发送方速度超过接收方的处理能力。
- **拥塞控制**：根据网络状况调整发送速率，减少网络拥塞。

TCP 提供可靠交付，但不保证固定延迟，也不保证连接永远可用。网络中断、进程退出和设备故障仍可能导致连接失败。

## 2. TCP 首部

TCP 段由 TCP 首部和应用数据组成。首部由 20 字节的固定部分以及可选的选项与填充组成，总长度为 20～60 字节。下面按 RFC 9293 的基础格式介绍，AccECN 扩展的位分配差异见控制标志一节。

```text
0                   15 16                  31
+---------------------+---------------------+
|      源端口          |      目标端口        |
+---------------------+---------------------+
|                  序列号                    |
+-------------------------------------------+
|                  确认号                    |
+----+------+---------+---------------------+
|长度|保留位| 控制标志 |       窗口大小       |
+----+------+---------+---------------------+
|       校验和          |      紧急指针        |
+---------------------+---------------------+
|          选项（可选）与填充                 |
+-------------------------------------------+
|                  应用数据                  |
+-------------------------------------------+
```

### 2.1 字段总览

| 字段 | 长度 | 作用与说明 |
| --- | --- | --- |
| 源端口（Source Port） | 16 位，2 字节 | 标识发送方的应用端口，与源 IP 地址一起定位发送端点。 |
| 目标端口（Destination Port） | 16 位，2 字节 | 标识接收方的应用端口，与目标 IP 地址一起定位接收端点。 |
| 序列号（Sequence Number） | 32 位，4 字节 | 通常表示本段第一个数据字节的序号；`SYN=1` 时表示初始序列号 ISN，第一个数据字节从 ISN+1 开始。`SYN` 和 `FIN` 各占用一个序列号。 |
| 确认号（Acknowledgment Number） | 32 位，4 字节 | 仅在 `ACK=1` 时有效，表示本段发送方期望从对端收到的下一个序列号，即此前的字节已连续收到。 |
| 首部长度／数据偏移（Data Offset） | 4 位 | 表示数据从哪里开始，以 4 字节为单位；有效取值为 5～15，对应首部长度 20～60 字节，不包含应用数据。 |
| 保留位（Reserved） | 4 位（基础格式） | 留给扩展使用；未实现相应扩展时，发送端置零，接收端忽略。AccECN 使用其中 1 位作为 `AE`，剩余 3 位保留。 |
| 控制标志（Flags） | 基础格式共 8 位，每个标志 1 位 | 表示连接建立、关闭、复位、确认及拥塞反馈等状态；多个标志可以同时置位，例如 `SYN+ACK`。包含 `AE` 扩展时共 9 位。 |
| 窗口大小（Window） | 16 位，2 字节 | 通告从确认号开始愿意接收的字节数，用于流量控制；原始值范围为 0～65535。协商窗口扩大后，非 SYN 段的有效窗口按协商的移位量放大，字段本身仍为 16 位。 |
| 校验和（Checksum） | 16 位，2 字节 | 检查 TCP 首部、数据以及 IP 伪首部的完整性；必须计算和校验。伪首部参与计算，但不作为 TCP 首部字段传输。 |
| 紧急指针（Urgent Pointer） | 16 位，2 字节 | 仅在 `URG=1` 时有效，表示相对于本段序列号的偏移；两者相加得到紧急数据最后一个字节之后的序列号。它不是独立的数据通道，新应用不宜依赖该机制。 |
| 选项（Options） | 可变长，与末尾填充合计 0～40 字节 | 携带 MSS、窗口扩大、时间戳、选择确认等扩展信息，具体结构见下文。 |
| 填充（Padding） | 按需补齐，与选项合计不超过 40 字节 | 使首部总长度为 4 字节的整数倍；选项列表结束后的填充字节必须为零。 |

固定部分长度校验：`16 + 16 + 32 + 32 + 4 + 4 + 8 + 16 + 16 + 16 = 160 位 = 20 字节`。AccECN 将其中的“4 位保留位 + 8 位标志”调整为“3 位保留位 + 9 位标志”，不会增加首部长度。

### 2.2 控制标志

每个标志占 1 位。下表中 `ECE` 和 `CWR` 的独立含义适用于传统 ECN：

| 标志 | 作用 |
| --- | --- |
| `SYN` | 建立连接并同步初始序列号，自身占用一个序列号 |
| `ACK` | 表示确认号字段有效 |
| `FIN` | 表示发送方不再发送数据，自身占用一个序列号；不代表对端也停止发送 |
| `RST` | 立即重置异常或不存在的连接 |
| `PSH` | 提示接收方及时将已收到的数据交给应用，不构成应用消息边界 |
| `URG` | 表示紧急指针字段有效 |
| `ECE` | 在握手阶段参与 ECN 能力协商；传输阶段反馈收到 IP 层的拥塞标记 |
| `CWR` | 在握手阶段参与 ECN 能力协商；传输阶段表示发送方已对拥塞反馈作出减小拥塞窗口的响应 |
| `AE`（扩展） | 用于协商更准确的拥塞通知 AccECN，占用基础格式中的一个保留位 |

RFC 9768（2026 年 4 月）定义了 AccECN：协商成功后，在 `SYN=0` 的报文中，`AE`、`CWR`、`ECE` 合并解释为 3 位的 `ACE` 字段，用于更准确的拥塞反馈，不再分别按传统 ECN 标志解释。旧资料中的 `NS` 是历史 ECN-nonce 机制使用的名称，该位现被重新定义为 `AE`。

### 2.3 选项与填充

选项以 1 字节的 `Kind` 标识类型。除 `EOL` 和 `NOP` 外，一般还包含 1 字节的 `Length`，表示整个选项的字节数（含 `Kind` 和 `Length`），后面跟选项数据。

| 常见选项 | 长度 | 作用 |
| --- | --- | --- |
| 选项列表结束（EOL） | 1 字节 | 表示后面不再有选项，剩余首部空间以零填充。 |
| 无操作（NOP） | 1 字节 | 用于选项之间的对齐；它本身也是选项，与 EOL 后的零填充不同。 |
| 最大报文段长度（MSS） | 4 字节 | 在 SYN 段中通告自己能够接收的最大 TCP 数据长度，不包含 IP 和 TCP 首部。 |
| 窗口扩大（Window Scale） | 3 字节 | 在 SYN 段中协商窗口字段的移位量，以支持超过 65535 字节的接收窗口。 |
| 允许选择确认（SACK Permitted） | 2 字节 | 在 SYN 段中声明支持 SACK。 |
| 选择确认（SACK） | `2 + 8 × N` 字节 | 携带 N 个已收到的非连续数据块，每块用两个 32 位序列号表示左边界和右边界（不含右边界字节）；数量受选项空间限制。 |
| 时间戳（Timestamps） | 10 字节 | 携带发送时间戳及回显时间戳，用于 RTT 测量和防止旧的重复报文被误接收。 |

### 2.4 应用数据

应用数据位于 TCP 首部之后，不属于首部字段，长度可变，也可以为 0，例如不携带数据的纯 ACK 段。TCP 没有单独的“数据长度”字段，接收端根据 IP 层提供的长度扣除相关首部长度后得到 TCP 数据长度。

#### 2.4.1 TCP 如何确定段的边界

TCP 不依靠结束符判断一个段在哪里结束。IP 层交付的是具有明确长度的数据包，而不是无限延伸的字节流。以普通 IPv4 报文为例：

```text
IP 报文 = IP 首部 + TCP 首部 + TCP 数据
TCP 段长度 = IP 总长度 - IP 首部长度
TCP 数据长度 = TCP 段长度 - TCP 首部长度

示例：
[ IP 首部：20 字节 ][ TCP 首部：32 字节 ][ 数据：1000 字节 ]
IP 总长度：1052 字节
TCP 段长度：1052 - 20 = 1032 字节
TCP 数据长度：1032 - 32 = 1000 字节
```

TCP 首部长度字段的值在此例中为 8，表示 `8 × 4 = 32` 字节。接收端因此既知道数据从哪里开始，也知道还有多少字节，不需要额外的 TCP 数据长度字段。IPv4 发生分片时，先完成 IP 重组，再处理 TCP；IPv6 的长度字段含义不同，计算时还需扣除 TCP 之前的扩展首部。

#### 2.4.2 内核如何传递长度

以 Linux 6.12 的普通 IPv4 本机接收路径为例（省略 GRO 等聚合处理）：

1. `ip_rcv_core()` 校验 IPv4 长度，并通过 `pskb_trim_rcsum()` 裁掉 IP 总长度之外的多余字节。
2. `ip_local_deliver()` 在需要时完成分片重组。
3. `ip_local_deliver_finish()` 通过 `__skb_pull()` 跳过 IP 首部，然后按 IP 协议字段分发给 TCP 的 `tcp_v4_rcv()`。
4. TCP 通过 `struct sk_buff`（简称 `skb`）获得数据及长度。此时 `skb->len` 是 TCP 段长度；TCP 检查 `doff`（首部长度字段）和缓冲区长度，确定数据范围。

这里的长度是内核对象的元数据，并不是额外传输的 TCP 首部字段。跳过 IP 首部也不意味着丢弃所有 IP 信息，内核仍能访问源地址、目标地址等信息。

下面是简化伪代码，不是 Linux 源码。假设 IP 层已完成校验和重组，且数据连续存放；实际 `skb` 可以包含非线性数据，不能直接用一个连续指针范围概括：

```c
tcp_start = ip_start + ip_header_length;
tcp_length = ip_total_length - ip_header_length;

if (tcp_length < 20) {
    drop_packet();
    return;
}

tcp_header_length = read_data_offset(tcp_start) * 4;
if (tcp_header_length < 20 || tcp_header_length > tcp_length) {
    drop_packet();
    return;
}

payload_start = tcp_start + tcp_header_length;
payload_length = tcp_length - tcp_header_length;
```

实现参考：Linux v6.12 的 `net/ipv4/ip_input.c` 和 `net/ipv4/tcp_ipv4.c`。上述伪代码仅展示长度关系，省略了 TCP 校验和、连接查找、序列号检查等处理。

本节依据：RFC 9293（TCP 首部）、RFC 3168（ECN）、RFC 7323（窗口扩大与时间戳）、RFC 2018（SACK）、RFC 9768（AccECN）。

## 3. 建立连接

TCP 通常通过三次握手建立连接：

```text
客户端                                  服务端
  |                                      |
  | -------- SYN, seq = x -------------> |
  | <--- SYN + ACK, seq = y, ack = x+1 - |
  | -------- ACK, ack = y+1 ------------> |
  |                                      |
  |            连接建立                   |
```

三次握手的作用包括：

1. 确认双方的发送和接收能力基本正常。
2. 交换并确认双方的初始序列号。
3. 协商 MSS、窗口扩大和选择确认等 TCP 选项。

服务端执行 `listen` 后处于监听状态。收到 `SYN` 并回复 `SYN + ACK` 后，连接进入半连接状态；收到最终 `ACK` 后，连接建立完成，可以交给应用处理。

## 4. 可靠传输

### 4.1 序列号与确认

#### 4.1.1 按字节连续编号

TCP 编号的对象是字节，而不是数据包。TCP 首部中的序列号通常表示本段第一个数据字节的编号，其余字节的编号依次递增，不需要给每个字节额外附加编号。连接双方分别维护各自发送方向的序列号，两个方向独立编号。

初始序列号 ISN 在建立连接时通过 `SYN` 交换，不固定从 0 开始。由于 `SYN` 占用一个序列号，若 ISN 为 999，第一个数据字节就从 1000 开始。

连续发送新数据时，如果不涉及 `SYN`、`FIN` 和编号回绕，可以这样计算：

```text
下一段的序列号 = 当前段的序列号 + 当前段的数据字节数
```

例如，第一个数据字节从 1000 开始：

| 发送过程 | 数据长度 | 本段序列号 | 本段数据字节编号范围 | 下一个新数据字节的序列号 |
| --- | --- | --- | --- | --- |
| 第一段 | 500 字节 | 1000 | 1000～1499 | 1500 |
| 第二段 | 300 字节 | 1500 | 1500～1799 | 1800 |
| 第三段 | 200 字节 | 1800 | 1800～1999 | 2000 |

发送方维护 `SND.NXT`，表示下一个待发送的新字节的序列号。每发送一批新数据，就按消耗的序列号数量推进它；在接收窗口和拥塞窗口允许的情况下，不必等待上一段被确认才发送下一段。

#### 4.1.2 编号的特殊规则

- **重传沿用原编号**：第一段丢失后，重传同一批字节仍使用 1000～1499，不为这些字节分配新编号。重传时可以重新分段，但每个字节的编号不变。
- **首部不计入编号**：发送 500 字节数据，无论首部多长，数据本身只消耗 500 个序列号。
- **纯 ACK 不消耗序列号**：不携带数据且没有 `SYN`、`FIN` 的报文不会推进 `SND.NXT`。
- **`SYN`、`FIN` 各消耗一个序列号**：即使没有数据，也各推进 1。例如 500 字节数据附带 `FIN`，一共消耗 501 个序列号。
- **32 位编号会回绕**：序列号按模 `2^32` 递增，到 `2^32 - 1` 后，下一个编号为 0。因此，判断先后不能简单使用普通整数的大小比较。

#### 4.1.3 确认号与发送进度

接收方返回的确认号表示期望收到的下一个序列号，也就是该序号之前的数据已经连续收到。例如，接收方已经按序收齐第一段：

```text
发送方发送：seq = 1000, length = 500
接收方确认：ack = 1500
```

这里 `ack = 1500` 表示 1000～1499 的字节已经收齐，接下来期望从 1500 开始的数据。序列号帮助接收方对乱序数据排序、识别缺失范围，并避免把重传的重复字节再次交给应用。

**ACK 表示确认进度，不决定后续数据如何编号。** 如果发送方已经发完上表中的三段，即使当前只收到 `ack = 1500`，`SND.NXT` 也已经是 2000；1500～1999 的字节只是尚未被确认，不会因此重新编号。

TCP 通常使用累积确认。如果接收方收到了后面的数据，但中间仍有缺口，普通确认号仍指向缺失的第一个字节。启用 SACK（Selective Acknowledgment，选择确认）后，接收方还可以告知发送方已经收到的非连续数据范围。

### 4.2 重传

发送方在规定时间内没有收到确认时，会认为数据可能丢失并进行超时重传。连续收到多个相同确认时，发送方也可能在超时前执行快速重传。

重传超时时间会根据往返时间 RTT 动态计算。设置过短会造成不必要的重传，设置过长则会延迟丢包恢复。

### 4.3 校验和

TCP 校验和覆盖 TCP 首部、TCP 数据以及由 IP 地址等信息组成的伪首部。接收方发现校验和错误时通常会丢弃该 TCP 段，并依赖发送方后续重传。

## 5. 流量控制

流量控制用于保护接收方。接收方通过 TCP 首部中的接收窗口 `rwnd` 通告可用缓冲区大小，发送方未被确认的数据量不能超过该窗口。

```text
发送窗口上限 <= 接收方通告窗口 rwnd
```

接收缓冲区不足时，接收方可以通告零窗口。发送方会暂停发送普通数据，并定期发送窗口探测报文，等待接收窗口重新打开。

窗口字段原始长度为 16 位。双方可以在建立连接时协商窗口扩大选项，以支持更大的接收窗口和高带宽、高延迟网络。

## 6. 拥塞控制

拥塞控制用于保护网络。发送方维护拥塞窗口 `cwnd`，实际可发送但尚未确认的数据量同时受到接收窗口和拥塞窗口限制：

```text
发送窗口上限 = min(rwnd, cwnd)
```

常见机制包括：

- **慢启动**：连接开始或严重拥塞后，从较小窗口逐步提高发送量。
- **拥塞避免**：进入稳定阶段后，以更谨慎的速度增加拥塞窗口。
- **快速重传**：根据重复确认尽早判断丢包并重传。
- **快速恢复**：发生部分丢包后避免立即回到最初的发送状态。

不同操作系统可以使用不同的拥塞控制算法，例如 CUBIC 或 BBR。具体算法不同，但目标都是充分利用网络，同时避免发送过快导致持续拥塞。

## 7. 关闭连接

TCP 是全双工协议，两个方向需要分别关闭，因此正常关闭通常包含四次交互：

```text
主动关闭方                              被动关闭方
  | -------- FIN ----------------------> |
  | <------- ACK ----------------------- |
  | <------- FIN ----------------------- |
  | -------- ACK ----------------------> |
```

收到 `FIN` 只表示对方不再发送数据，对方仍可能继续接收数据。最后发送 `ACK` 的一方通常进入 `TIME_WAIT` 状态，等待一段时间后才彻底释放连接，主要用于：

- 确保最后一个 `ACK` 丢失时仍能重新发送。
- 避免旧连接中延迟到达的报文影响后续使用相同四元组的新连接。

`RST` 表示连接被立即重置，常见原因包括访问未监听端口、应用异常关闭套接字，或连接状态与收到的报文不匹配。

## 8. TCP 粘包与拆包

TCP 面向字节流，不保存应用调用 `send` 时的消息边界。一次写入的数据可能被拆成多个 TCP 段，多次写入的数据也可能在接收时一起读取。

应用层通常使用以下方式确定消息边界：

- 固定消息长度。
- 在消息前添加长度字段。
- 使用不会与内容混淆的分隔符。
- 使用能够描述消息边界的应用层协议格式。

所谓“粘包”和“拆包”不是 TCP 传输错误，而是应用把字节流误当成了带有天然边界的消息。

### 8.1 三种边界的区别

| 边界 | 由谁识别 | 识别方式 |
| --- | --- | --- |
| TCP 段的结束 | TCP 层 | 使用 IP 层交付的长度确定段的范围，见 2.4 节。 |
| 应用消息的结束 | 应用层 | 按固定长度、分隔符、长度前缀等应用协议规则解析。 |
| 一个方向的字节流结束 | TCP 层，并向应用报告 | `FIN` 表示对端不再发送数据；此前数据按序读完后，应用对流套接字的正常读取返回 0，表示 EOF。 |

TCP 只需要传输有序字节，不需要理解这些字节组成几条应用消息。例如：

```text
应用理解：[消息 A：HELLO][消息 B：WORLD]
TCP 理解：H E L L O W O R L D 这 10 个字节
```

这 10 个字节可以分成一个或多个 TCP 段传输。一次 `send()` 不对应一次 `recv()`，一次 `recv()` 也不一定返回一条完整消息。`PSH` 不提供消息边界保证；`FIN` 表示一个方向的流结束，不是每条消息的结束标记。同一条连接可以连续传输多条消息。

### 8.2 用长度前缀解析消息

例如，应用协议约定每条消息由“4 字节无符号正文长度 + 正文”组成，长度使用网络字节序，不包含长度字段自身：

```text
逻辑消息：[长度：5][HELLO][长度：3][BYE]

可能的接收结果（长度字段也可能被拆开）：
第一次：[长度：5][HE
第二次：LLO][长度：3][B
第三次：YE]
```

应用维护接收缓冲区，重复执行：

1. 将本次 `recv()` 收到的字节追加到缓冲区。
2. 不足 4 字节时，等待更多数据。
3. 凑齐 4 字节后，解析正文长度 N，并检查是否超过协议允许的最大值。
4. 不足 `4 + N` 字节时，保留当前内容，继续接收。
5. 凑齐后，取出并处理一条完整消息，移除这 `4 + N` 字节。
6. 对剩余缓冲区继续从第 2 步解析，直到不足以组成下一条消息。

实际实现还需防止长度计算溢出，并处理错误和超时。如果读到 EOF 时仍有未完成的消息，应按协议报告消息被截断，而不是当作完整消息。使用分隔符的协议则需要约定正文包含分隔符时如何转义。

## 9. TCP 与 UDP 对比

| 对比项 | TCP | UDP |
| --- | --- | --- |
| 通信方式 | 面向连接，传输前需要握手 | 无连接，可以直接发送 |
| 数据形式 | 连续字节流 | 独立数据报 |
| 消息边界 | 不保留，需要应用定义 | 保留，一次发送对应一个数据报 |
| 可靠传输 | 提供确认、重传和去重 | 不提供，需要应用按需实现 |
| 顺序保证 | 按序向应用交付 | 可能乱序到达 |
| 流量控制 | 通过接收窗口提供 | 不提供 |
| 拥塞控制 | 提供 | UDP 自身不提供 |
| 首部最小长度 | 20 字节 | 8 字节 |
| 连接状态 | 通信双方维护连接状态 | 协议层通常不维护连接状态 |
| 广播和组播 | 不支持 | 支持 |
| 丢包影响 | 等待重传可能增加后续数据延迟 | 不阻塞后续数据报，但应用可能缺少数据 |
| 典型场景 | Web、SSH、数据库连接、文件传输 | DNS、实时通信、游戏、QUIC |

### 9.1 如何选择

适合优先选择 TCP 的场景：

- 数据必须完整、按序到达。
- 应用希望直接使用成熟的可靠传输机制。
- 通信以连续字节流为主，例如文件、网页和数据库连接。
- 可以接受丢包重传带来的延迟。

适合考虑 UDP 的场景：

- 数据具有明确的消息边界。
- 更关注实时性，过期数据的价值较低。
- 需要广播或组播。
- 应用需要自行控制重传、顺序、拥塞或多路复用策略。

协议选择不能只依据“速度快慢”。如果应用基于 UDP 实现完整的可靠传输和拥塞控制，其实现复杂度和协议开销也会随之增加。

## 10. 常见排查命令

查看 TCP 监听端口和连接：

```bash
ss -lnt
ss -nt
```

测试目标 TCP 端口：

```bash
nc -vz example.com 443
```

抓取 TCP 握手、关闭和重置报文：

```bash
tcpdump -i any -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0'
```

排查时可以重点观察连接状态、序列号、确认号、窗口大小、重传、重复确认、RTT 和 `RST`。
