# TCP 与 UDP

TCP（Transmission Control Protocol，传输控制协议）和 UDP（User Datagram Protocol，用户数据报协议）是 TCP/IP 协议体系中最常见的两个传输层协议。它们都通过端口为应用进程提供端到端通信，但在连接方式、可靠性、数据边界和传输控制等方面存在明显差异。

## 1. TCP

TCP 是面向连接、可靠、基于字节流的传输层协议。它通过序列号、确认、重传、流量控制和拥塞控制等机制，使数据能够按序、无重复地交付给接收方。

### 1.1 基础概念

TCP 通信由源 IP、源端口、目标 IP 和目标端口共同标识。IP 地址用于定位主机，端口用于定位主机上的应用进程。

TCP 的主要特征包括：

- **面向连接**：传输数据前需要建立连接，通信结束后需要释放连接。
- **可靠传输**：通过确认、超时重传和快速重传处理丢包。
- **按序交付**：接收方根据序列号重排数据，向应用交付连续字节流。
- **全双工**：连接双方可以同时发送和接收数据。
- **字节流**：TCP 不保留应用消息边界，应用需要自行定义消息长度或分隔方式。
- **流量控制**：避免发送方速度超过接收方的处理能力。
- **拥塞控制**：根据网络状况调整发送速率，减少网络拥塞。

TCP 提供可靠交付，但不保证固定延迟，也不保证连接永远可用。网络中断、进程退出和设备故障仍可能导致连接失败。

### 1.2 TCP 首部

TCP 段由 TCP 首部和应用数据组成。未包含选项时，首部最小长度为 20 字节。

```text
0                   15 16                  31
+---------------------+---------------------+
|      源端口          |      目标端口        |
+---------------------+---------------------+
|                  序列号                    |
+-------------------------------------------+
|                  确认号                    |
+----+------+---------+---------------------+
|长度|保留位| 控制标志 |       窗口大小       |
+----+------+---------+---------------------+
|       校验和          |      紧急指针        |
+---------------------+---------------------+
|          选项（可选）与填充                 |
+-------------------------------------------+
|                  应用数据                  |
+-------------------------------------------+
```

主要字段如下：

- **源端口、目标端口**：标识通信双方的应用进程。
- **序列号（Sequence Number）**：表示当前 TCP 段中第一个数据字节的序号。
- **确认号（Acknowledgment Number）**：表示接收方期望收到的下一个字节序号。
- **首部长度**：表示 TCP 首部占用的长度。
- **窗口大小**：接收方通告自己当前还能接收多少数据。
- **校验和**：用于检查 TCP 首部和数据在传输过程中是否出错。
- **选项**：常见选项包括 MSS、窗口扩大、时间戳和选择确认。

常用控制标志包括：

| 标志 | 作用 |
| --- | --- |
| `SYN` | 建立连接并同步初始序列号 |
| `ACK` | 表示确认号字段有效 |
| `FIN` | 表示发送方不再发送数据 |
| `RST` | 立即重置异常或不存在的连接 |
| `PSH` | 提示接收方尽快将数据交给应用 |
| `URG` | 表示紧急指针字段有效 |

### 1.3 建立连接

TCP 通常通过三次握手建立连接：

```text
客户端                                  服务端
  |                                      |
  | -------- SYN, seq = x -------------> |
  | <--- SYN + ACK, seq = y, ack = x+1 - |
  | -------- ACK, ack = y+1 ------------> |
  |                                      |
  |            连接建立                   |
```

三次握手的作用包括：

1. 确认双方的发送和接收能力基本正常。
2. 交换并确认双方的初始序列号。
3. 协商 MSS、窗口扩大和选择确认等 TCP 选项。

服务端执行 `listen` 后处于监听状态。收到 `SYN` 并回复 `SYN + ACK` 后，连接进入半连接状态；收到最终 `ACK` 后，连接建立完成，可以交给应用处理。

### 1.4 可靠传输

#### 1.4.1 序列号与确认

TCP 对字节流中的每个字节进行编号。接收方返回的确认号表示该序号之前的字节已经连续收到。

```text
发送方发送：seq = 1000, length = 500
接收方确认：ack = 1500
```

TCP 通常使用累积确认。如果接收方收到了后面的数据，但中间仍有缺口，普通确认号仍指向缺失的第一个字节。启用 SACK（Selective Acknowledgment，选择确认）后，接收方还可以告知发送方已经收到的非连续数据范围。

#### 1.4.2 重传

发送方在规定时间内没有收到确认时，会认为数据可能丢失并进行超时重传。连续收到多个相同确认时，发送方也可能在超时前执行快速重传。

重传超时时间会根据往返时间 RTT 动态计算。设置过短会造成不必要的重传，设置过长则会延迟丢包恢复。

#### 1.4.3 校验和

TCP 校验和覆盖 TCP 首部、TCP 数据以及由 IP 地址等信息组成的伪首部。接收方发现校验和错误时通常会丢弃该 TCP 段，并依赖发送方后续重传。

### 1.5 流量控制

流量控制用于保护接收方。接收方通过 TCP 首部中的接收窗口 `rwnd` 通告可用缓冲区大小，发送方未被确认的数据量不能超过该窗口。

```text
发送窗口上限 <= 接收方通告窗口 rwnd
```

接收缓冲区不足时，接收方可以通告零窗口。发送方会暂停发送普通数据，并定期发送窗口探测报文，等待接收窗口重新打开。

窗口字段原始长度为 16 位。双方可以在建立连接时协商窗口扩大选项，以支持更大的接收窗口和高带宽、高延迟网络。

### 1.6 拥塞控制

拥塞控制用于保护网络。发送方维护拥塞窗口 `cwnd`，实际可发送但尚未确认的数据量同时受到接收窗口和拥塞窗口限制：

```text
发送窗口上限 = min(rwnd, cwnd)
```

常见机制包括：

- **慢启动**：连接开始或严重拥塞后，从较小窗口逐步提高发送量。
- **拥塞避免**：进入稳定阶段后，以更谨慎的速度增加拥塞窗口。
- **快速重传**：根据重复确认尽早判断丢包并重传。
- **快速恢复**：发生部分丢包后避免立即回到最初的发送状态。

不同操作系统可以使用不同的拥塞控制算法，例如 CUBIC 或 BBR。具体算法不同，但目标都是充分利用网络，同时避免发送过快导致持续拥塞。

### 1.7 关闭连接

TCP 是全双工协议，两个方向需要分别关闭，因此正常关闭通常包含四次交互：

```text
主动关闭方                              被动关闭方
  | -------- FIN ----------------------> |
  | <------- ACK ----------------------- |
  | <------- FIN ----------------------- |
  | -------- ACK ----------------------> |
```

收到 `FIN` 只表示对方不再发送数据，对方仍可能继续接收数据。最后发送 `ACK` 的一方通常进入 `TIME_WAIT` 状态，等待一段时间后才彻底释放连接，主要用于：

- 确保最后一个 `ACK` 丢失时仍能重新发送。
- 避免旧连接中延迟到达的报文影响后续使用相同四元组的新连接。

`RST` 表示连接被立即重置，常见原因包括访问未监听端口、应用异常关闭套接字，或连接状态与收到的报文不匹配。

### 1.8 TCP 粘包与拆包

TCP 面向字节流，不保存应用调用 `send` 时的消息边界。一次写入的数据可能被拆成多个 TCP 段，多次写入的数据也可能在接收时一起读取。

应用层通常使用以下方式确定消息边界：

- 固定消息长度。
- 在消息前添加长度字段。
- 使用不会与内容混淆的分隔符。
- 使用能够描述消息边界的应用层协议格式。

所谓“粘包”和“拆包”不是 TCP 传输错误，而是应用把字节流误当成了带有天然边界的消息。

## 2. UDP

UDP 是无连接、基于数据报的传输层协议。它提供端口复用、数据报边界和校验和等基础能力，但不负责建立连接、确认、重传、按序交付、流量控制或拥塞控制。

### 2.1 基础概念

UDP 通信使用 IP 地址定位主机，使用端口定位主机上的应用进程。一个 UDP 数据报从发送方应用交给 UDP 后，会作为一个完整消息进行传输；接收方读取时仍能识别该数据报的边界。

UDP 的主要特征包括：

- **无连接**：发送数据前不需要三次握手。
- **尽力而为**：数据报可能丢失、重复、乱序或损坏。
- **保留消息边界**：一次发送对应一个 UDP 数据报。
- **首部开销小**：UDP 首部固定为 8 字节。
- **支持单播、广播和组播**：具体能力取决于 IP 版本和网络配置。
- **低延迟**：协议本身没有连接建立和重传等待，但应用仍可能实现确认和重传。

UDP 不一定比 TCP 快。实际性能取决于网络质量、应用设计、数据大小，以及是否需要在应用层补充可靠传输和拥塞控制等机制。

### 2.2 UDP 首部

UDP 首部固定为 8 字节，由四个 16 位字段组成：

```text
0                   15 16                  31
+---------------------+---------------------+
|      源端口          |      目标端口        |
+---------------------+---------------------+
|       UDP 长度        |       校验和         |
+---------------------+---------------------+
|                  应用数据                  |
+-------------------------------------------+
```

各字段含义如下：

- **源端口**：标识发送方应用端口；在部分场景中可以为 `0`。
- **目标端口**：标识接收方应用端口。
- **UDP 长度**：UDP 首部和数据的总长度，最小值为 8 字节。
- **校验和**：检查 UDP 首部和数据在传输过程中是否出错。

UDP 长度字段为 16 位，因此普通 UDP 数据报的理论总长度上限为 65,535 字节。实际可用载荷还要减去 UDP 和 IP 首部，并受到路径 MTU、操作系统和应用限制。

### 2.3 数据报传输

发送方不需要先确认接收方是否在线，也不会等待协议层确认：

```text
发送方应用
  -> UDP 数据报
      -> IP 包
          -> 网络
              -> 接收方 UDP
                  -> 接收方应用
```

如果目标端口没有应用监听，接收主机可能返回 ICMP `Port Unreachable` 消息，也可能因为防火墙策略而直接丢弃数据包。发送方不一定能够立即知道数据是否成功交给目标应用。

同一个 UDP 套接字可以连续接收多个独立数据报。接收缓冲区不足时，新到达的数据报可能被丢弃，而不会阻塞网络中的发送方。

### 2.4 校验和

UDP 校验和覆盖 UDP 首部、UDP 数据以及由 IP 地址等信息组成的伪首部。伪首部不会实际放入 UDP 数据报，主要用于验证数据报是否被交付给正确的源地址、目标地址和上层协议。

在 IPv4 中，UDP 校验和可以不使用；在 IPv6 中，普通 UDP 通信通常必须使用校验和。即使校验和验证通过，也只能说明传输中没有检测到比特错误，不能证明数据一定来自可信发送方。

### 2.5 数据大小与分片

UDP 自身不负责分片和重组。UDP 数据报超过路径 MTU 时，可能发生以下情况：

- IPv4 由发送主机或中间路由器进行 IP 分片。
- IPv6 中间路由器不分片，由发送主机根据路径 MTU 决定是否分片。
- 设置禁止分片时，过大的数据包会被丢弃，并可能返回 ICMP 错误。

只要一个 IP 分片丢失，整个 UDP 数据报就无法完成重组。较大的 UDP 数据报会增加分片概率和丢包影响，因此应用通常会控制单个数据报大小，或在应用层实现分片、编号和重组。

### 2.6 可靠性与顺序

UDP 不保证数据报一定到达、只到达一次或按照发送顺序到达，也不保证接收方有能力及时处理。

需要更强保证时，应用可以根据业务需求实现：

- 消息编号和去重。
- 超时、确认和重传。
- 顺序恢复。
- 发送速率限制和拥塞控制。
- 前向纠错。

实时音视频有时宁愿丢弃过期数据，也不等待重传；文件传输和事务请求则通常更重视完整性。协议选择应由业务语义决定。

### 2.7 常见应用

| 场景 | 使用 UDP 的原因 |
| --- | --- |
| DNS 查询 | 请求和响应通常较小，希望减少连接建立开销 |
| DHCP | 客户端获取地址前可能没有可用 IP，且需要广播 |
| 实时音视频 | 更关注时效性，可以容忍少量丢包 |
| 在线游戏 | 需要快速传递位置和状态更新，旧数据价值较低 |
| NTP | 请求和响应简单，适合数据报通信 |
| QUIC | 在 UDP 之上实现可靠传输、拥塞控制和多路复用 |

这些协议使用 UDP，不代表它们都不可靠。例如，QUIC 会在用户空间补充确认、重传、加密和拥塞控制；DNS 客户端也会在超时后重试，或在需要时改用 TCP。

## 3. TCP 与 UDP 对比

| 对比项 | TCP | UDP |
| --- | --- | --- |
| 通信方式 | 面向连接，传输前需要握手 | 无连接，可以直接发送 |
| 数据形式 | 连续字节流 | 独立数据报 |
| 消息边界 | 不保留，需要应用定义 | 保留，一次发送对应一个数据报 |
| 可靠传输 | 提供确认、重传和去重 | 不提供，需要应用按需实现 |
| 顺序保证 | 按序向应用交付 | 可能乱序到达 |
| 流量控制 | 通过接收窗口提供 | 不提供 |
| 拥塞控制 | 提供 | UDP 自身不提供 |
| 首部最小长度 | 20 字节 | 8 字节 |
| 连接状态 | 通信双方维护连接状态 | 协议层通常不维护连接状态 |
| 广播和组播 | 不支持 | 支持 |
| 丢包影响 | 等待重传可能增加后续数据延迟 | 不阻塞后续数据报，但应用可能缺少数据 |
| 典型场景 | Web、SSH、数据库连接、文件传输 | DNS、实时通信、游戏、QUIC |

### 3.1 如何选择

适合优先选择 TCP 的场景：

- 数据必须完整、按序到达。
- 应用希望直接使用成熟的可靠传输机制。
- 通信以连续字节流为主，例如文件、网页和数据库连接。
- 可以接受丢包重传带来的延迟。

适合考虑 UDP 的场景：

- 数据具有明确的消息边界。
- 更关注实时性，过期数据的价值较低。
- 需要广播或组播。
- 应用需要自行控制重传、顺序、拥塞或多路复用策略。

协议选择不能只依据“速度快慢”。如果应用基于 UDP 实现完整的可靠传输和拥塞控制，其实现复杂度和协议开销也会随之增加。

## 4. 常见排查命令

查看 TCP 和 UDP 监听端口：

```bash
ss -lnt
ss -lnu
```

查看 TCP 连接：

```bash
ss -nt
```

测试目标 TCP 端口：

```bash
nc -vz example.com 443
```

向目标端口发送 UDP 数据：

```bash
printf 'hello\n' | nc -u example.com 9999
```

抓取 TCP 和 UDP 报文：

```bash
tcpdump -i any -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0'
tcpdump -i any -nn udp
```

排查 TCP 时可以重点观察连接状态、序列号、确认号、窗口大小、重传、重复确认、RTT 和 `RST`。排查 UDP 时可以重点观察源和目标地址、端口、数据报长度、IP 分片、ICMP 错误、接收缓冲区丢包和应用层重试。
