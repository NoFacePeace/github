# UDP

UDP（User Datagram Protocol，用户数据报协议）是无连接、基于数据报的传输层协议。它提供端口复用、数据报边界和校验和等基础能力，但不负责建立连接、确认、重传、按序交付、流量控制或拥塞控制。

## 1. 基础概念

UDP 通信使用 IP 地址定位主机，使用端口定位主机上的应用进程。一个 UDP 数据报从发送方应用交给 UDP 后，会作为一个完整消息进行传输；接收方读取时仍能识别该数据报的边界。

UDP 的主要特征包括：

- **无连接**：发送数据前不需要三次握手。
- **尽力而为**：数据报可能丢失、重复、乱序或损坏。
- **保留消息边界**：一次发送对应一个 UDP 数据报。
- **首部开销小**：UDP 首部固定为 8 字节。
- **支持单播、广播和组播**：具体能力取决于 IP 版本和网络配置。
- **低延迟**：协议本身没有连接建立和重传等待，但应用仍可能实现确认和重传。

UDP 不一定比 TCP 快。实际性能取决于网络质量、应用设计、数据大小，以及是否需要在应用层补充可靠传输和拥塞控制等机制。

## 2. UDP 首部

UDP 首部固定为 8 字节，由四个 16 位字段组成：

```text
0                   15 16                  31
+---------------------+---------------------+
|      源端口          |      目标端口        |
+---------------------+---------------------+
|       UDP 长度        |       校验和         |
+---------------------+---------------------+
|                  应用数据                  |
+-------------------------------------------+
```

各字段含义如下：

- **源端口**：标识发送方应用端口；在部分场景中可以为 `0`。
- **目标端口**：标识接收方应用端口。
- **UDP 长度**：UDP 首部和数据的总长度，最小值为 8 字节。
- **校验和**：检查 UDP 首部和数据在传输过程中是否出错。

UDP 长度字段为 16 位，因此普通 UDP 数据报的理论总长度上限为 65,535 字节。实际可用载荷还要减去 UDP 和 IP 首部，并受到路径 MTU、操作系统和应用限制。

## 3. 数据报传输

发送方不需要先确认接收方是否在线，也不会等待协议层确认：

```text
发送方应用
  -> UDP 数据报
      -> IP 包
          -> 网络
              -> 接收方 UDP
                  -> 接收方应用
```

如果目标端口没有应用监听，接收主机可能返回 ICMP `Port Unreachable` 消息，也可能因为防火墙策略而直接丢弃数据包。发送方不一定能够立即知道数据是否成功交给目标应用。

同一个 UDP 套接字可以连续接收多个独立数据报。接收缓冲区不足时，新到达的数据报可能被丢弃，而不会阻塞网络中的发送方。

## 4. 校验和

UDP 校验和覆盖 UDP 首部、UDP 数据以及由 IP 地址等信息组成的伪首部。伪首部不会实际放入 UDP 数据报，主要用于验证数据报是否被交付给正确的源地址、目标地址和上层协议。

在 IPv4 中，UDP 校验和可以不使用；在 IPv6 中，普通 UDP 通信通常必须使用校验和。即使校验和验证通过，也只能说明传输中没有检测到比特错误，不能证明数据一定来自可信发送方。

## 5. 数据大小与分片

UDP 自身不负责分片和重组。UDP 数据报超过路径 MTU 时，可能发生以下情况：

- IPv4 由发送主机或中间路由器进行 IP 分片。
- IPv6 中间路由器不分片，由发送主机根据路径 MTU 决定是否分片。
- 设置禁止分片时，过大的数据包会被丢弃，并可能返回 ICMP 错误。

只要一个 IP 分片丢失，整个 UDP 数据报就无法完成重组。较大的 UDP 数据报会增加分片概率和丢包影响，因此应用通常会控制单个数据报大小，或在应用层实现分片、编号和重组。

## 6. 可靠性与顺序

UDP 不保证数据报一定到达、只到达一次或按照发送顺序到达，也不保证接收方有能力及时处理。

需要更强保证时，应用可以根据业务需求实现：

- 消息编号和去重。
- 超时、确认和重传。
- 顺序恢复。
- 发送速率限制和拥塞控制。
- 前向纠错。

实时音视频有时宁愿丢弃过期数据，也不等待重传；文件传输和事务请求则通常更重视完整性。协议选择应由业务语义决定。

## 7. 常见应用

| 场景 | 使用 UDP 的原因 |
| --- | --- |
| DNS 查询 | 请求和响应通常较小，希望减少连接建立开销 |
| DHCP | 客户端获取地址前可能没有可用 IP，且需要广播 |
| 实时音视频 | 更关注时效性，可以容忍少量丢包 |
| 在线游戏 | 需要快速传递位置和状态更新，旧数据价值较低 |
| NTP | 请求和响应简单，适合数据报通信 |
| QUIC | 在 UDP 之上实现可靠传输、拥塞控制和多路复用 |

这些协议使用 UDP，不代表它们都不可靠。例如，QUIC 会在用户空间补充确认、重传、加密和拥塞控制；DNS 客户端也会在超时后重试，或在需要时改用 TCP。

## 9. 常见排查命令

查看 UDP 监听端口：

```bash
ss -lnu
```

向目标端口发送 UDP 数据：

```bash
printf 'hello\n' | nc -u example.com 9999
```

抓取 UDP 数据报：

```bash
tcpdump -i any -nn udp
```

排查时可以重点观察源和目标地址、端口、数据报长度、IP 分片、ICMP 错误、接收缓冲区丢包和应用层重试。
