# message

## 1. 消息调度机制

Agent 执行任务时，通常会反复调用模型、执行工具，并将工具结果加入对话上下文。用户在此期间发送的新消息，需要由 Agent 决定何时交给模型，以及是否中断当前操作。

Queue（排队）和 Steer（引导）描述了这一过程的不同侧面：Queue 侧重消息暂存与投递顺序，Steer 侧重新指令对当前任务方向的调整。两者不是统一的行业标准，也不一定是互斥的模式；具体行为取决于 Agent 和客户端的实现。

### 1.1 Queue

Queue 指在 Agent 忙碌时，将新消息暂存到队列，等待合适的时机处理。提交消息通常不会立即中断正在进行的生成或工具调用。

消息的处理时机可能包括：

- 当前工具调用结束后，在同一轮任务中交给模型。
- 当前轮响应结束后，作为下一轮输入处理。
- 当前任务完成后，再开始后续工作。

因此，界面显示“排队”只能说明消息正在等待处理，不能单凭这个状态判断它一定会等到整个任务结束。

例如，Agent 正在运行测试，用户发送“测试完成后，再检查登录接口”。系统可以先让测试返回，再将这条消息及测试结果一起交给模型。

Claude Code 的官方文档给出了具体规则：普通消息如果在工具调用期间入队，会在这些工具调用结束后、同一轮中交给 Claude；排队的命令和 shell 命令则等待当前轮结束后依次执行。这说明同一个队列也可以根据消息类型采用不同的调度规则。

Queue 适合追加后续工作、补充上下文，以及允许当前操作完成的场景。对于“立即停止发布”这类需要及时生效的要求，应使用系统提供的中断或立即发送入口，避免依赖队列的等待时机。

### 1.2 Steer

Steer 指在任务执行过程中，通过补充指令调整 Agent 的目标、约束、范围或执行顺序。

常见的补充指令包括：

- 调整范围：“只修改登录模块。”
- 增加约束：“保持现有 API 不变。”
- 改变顺序：“先运行测试，再继续修改。”
- 纠正理解：“我指的是服务端缓存。”

Steer 主要依赖 Agent 的消息调度能力，模型负责理解新要求并调整后续行为。常见实现是：先接收补充消息，在下一次调用模型前将其加入对话上下文，再让模型结合已有工作继续执行。

```text
用户发送补充指令
        ↓
Agent 接收并暂存消息
        ↓
到达可处理新消息的执行边界
        ↓
将新指令和已有结果加入上下文
        ↓
再次调用模型，调整后续行动
```

如果模型正在生成，系统可以等待当前生成结束，也可以取消生成后重新请求。如果工具正在运行，系统可能等待它返回、将它转到后台，或尝试取消；具体策略取决于工具是否支持这些操作。

因此，Steer 不一定需要把消息插入一次正在进行的模型生成，也不一定意味着立即中断。通过队列在工具调用结束后投递消息，同样可以实现对当前任务的引导。

新指令通常影响后续行动，已经完成的文件修改或外部操作不会自动撤销。需要撤销时，应明确提出撤销要求，并由 Agent 根据操作的可恢复性处理。

### 1.3 Queue 与 Steer 的关系

| 对比维度 | Queue | Steer |
| --- | --- | --- |
| 关注点 | 消息如何等待、按什么顺序投递 | 新指令如何调整当前任务 |
| 处理时机 | 由队列调度规则决定 | 在当前任务执行过程中生效 |
| 是否立即中断 | 通常不会 | 不一定，可等待执行边界或主动中断 |
| 对已有操作的影响 | 不自动撤销已完成的操作 | 不自动撤销已完成的操作 |
| 两者的联系 | 队列可以承载用于引导的消息 | 引导可以通过队列投递实现 |

判断一个 Agent 的实际行为时，需要分别确认：新消息何时进入模型上下文、当前生成是否会取消、工具调用如何处理，以及消息是否仍在当前任务中生效。

`Legacy` 通常表示旧版或兼容实现，不是 Queue 的同义词。某个产品的 Legacy 模式是否采用排队机制，需要查看该产品的具体定义。
