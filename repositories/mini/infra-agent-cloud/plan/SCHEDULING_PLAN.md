# 任务调度实施计划

## 1. 目标与范围

完成任务入队、调度领取、Runner 容量预占、消息投递、执行续约、事件处理和异常恢复闭环。

重点实现以下能力：

1. 使用 Redis Lua 原子预占执行租约与 Runner 容量，避免并发超卖。
2. 满载任务保留排队，结合唤醒和周期扫描继续调度。
3. 区分排队截止、调度领取过期和执行租约过期，分别处理超时。
4. 支持排队取消、执行停止，以及取消与投递之间的竞争处理。
5. 分别维护 Runner 心跳、调度领取续期和执行租约续期。
6. 固定执行消息，原子完成发布去重标记与消息写入。
7. Runner 对重复消息和失效执行进行检查，避免重复启动进程。
8. 校验事件归属、执行租约与事件序号，拒绝重复和过期事件。

本文件是实施计划，不代表这些能力已经实现。本次只新增文档，不修改业务代码。

### 1.1 组织与实现约定

- 保留 `server`、`runner`、`executor` 三个包，Runtime 放在 runner 包内。
- 数据存取继续通过 Server Store；Redis Lua、数据库事务及消息通道实现封装在存储和通信适配中。
- 调度信息和执行归属信息继续由现有 Job 表达，不增加独立的调度记录业务模型或表。
- 沿用当前 ClaimJob 的短数据库事务领取约定；Redis Lua 用于执行租约、容量及消息发布等对应热路径，不在本计划中直接替换现有调度领取方案。
- 调度锁或领取凭据、执行授权、节点身份分别处理，不能因为同在 Job 中就共用 token。
- 本计划不包含自动迁移工作区、故障执行自动重跑或第三方账号授权实现。
- 使用通用术语，不保存内部平台名称、部署地址、真实身份或凭证。

## 2. 当前基础与数据职责

### 2.1 当前代码基础

- Job 已有调度状态、排队时间、截止时间、调度领取 token 和执行 token。
- Server 已串联 ClaimJob、执行预留、发布消息、投递确认和失败重试，Store 仍缺具体实现。
- 调度领取续期已有调用骨架；错误分类、恢复收尾和真实原子语义仍需补齐。
- Runner 已定义心跳、消息消费、续约及事件回传接口，执行登记、续约和停止仍有占位方法。
- Runner 接收的 Job、控制命令和事件协议仍需补齐执行身份、实例、序号及有效期字段。
- 当前 ActiveSessions 是容量快照；实际是否允许预留必须通过原子操作复查。

### 2.2 数据职责

| 数据 | 作用 | 计划存储位置 |
| --- | --- | --- |
| Job | 调度状态、固定执行消息、Runner 绑定、执行归属及调度恢复信息 | 现有 Store 管理的持久化记录 |
| 调度领取信息 | ClaimToken、ClaimExpiresAt，限制单条 Job 的处理者 | 当前 Job 记录，按现有事务方案实现 |
| 待调度索引 | 按入队顺序发现候选任务 | 可由 Redis ZSet 加速；持久化 Job 为恢复依据 |
| Runner 心跳 | 实例、在线状态、引擎能力、容量及心跳截止时间 | Redis String，内容为 JSON，带 TTL |
| 执行租约 | Task、Session、Runner、实例、执行标识、期限及已接受序号 | Redis String，内容为 JSON，带 TTL |
| Runner 容量占用 | 当前预留及执行中的租约集合 | Redis ZSet，成员为执行标识，分数为过期时间 |
| Job 执行通道 | 将固定 Job 交给指定 Runner | Redis Stream |
| 发布标记 | Session 对应的固定 MessageID，防止重复写入执行通道 | Redis String，带保留期限 |
| 命令与事件通道 | 停止等命令和执行事件传输 | Redis Stream，具体分区及消费者组在协议阶段确定 |
| Session、Task | 业务状态、错误和执行结果 | DB |

如果使用 Redis 待调度索引，须补齐入索引失败和索引丢失的重建；索引不作为唯一任务来源。

### 2.3 固定消息与控制信息

- Job 表示一次确定的执行消息，首次预留成功后固定 MessageID、目标 Runner、执行 token 和执行输入。
- 业务 Job 可以保存控制字段，但实际发送给 Runner 的结构必须显式映射，排除调度 ClaimToken 等 Server 内部控制信息。
- 执行租约仅保存授权、归属、期限和序号，不保存完整 Job。
- 调度记录保存固定消息供重试恢复；Stream 中保存同一执行消息供 Runner 消费，职责分别为恢复与传输。
- Job 的排队截止时间不能因重试被延长；可重试失败保留记录及队列成员，后续唤醒或扫描时再次尝试。

## 3. 时限与状态约定

### 3.1 默认参数

以下作为初始参数，均需要配置化，并在真实联调后调整：

| 参数 | 初始值 | 用途 |
| --- | --- | --- |
| 排队调度截止 | 入队后 10 分钟 | 限制总排队调度时间 |
| 调度领取有效期 | 30 秒 | 限制当前调度处理权 |
| 调度领取续期间隔 | 10 秒 | 调度过程中保持处理权 |
| Runner 心跳有效期 | 30 秒 | 判断节点是否在线 |
| Runner 心跳间隔 | 10 秒 | 刷新节点在线状态 |
| 执行租约有效期 | 5 分钟 | 控制预留及执行资格 |
| 执行续约间隔 | 剩余有效期的 1/3 | 正常约 100 秒，首次立即确认 |
| 执行续约临时失败重试 | 10 秒与剩余有效期的 1/3 中较小值 | 在剩余有效期内恢复通信 |
| 恢复扫描间隔 | 30 秒 | 补偿遗漏唤醒、失效执行及未完成收尾 |
| 发布去重标记保留 | 至少 24 小时，且覆盖有效投递重试窗口 | 限制去重记录过早消失 |

调度扫描不固定等待完整周期：提交、容量释放等通知可以提前唤醒；定时扫描负责兜底。

### 3.2 状态约定

- Job 调度状态：queued、dispatching、dispatched、failed、cancelled。
- Session 创建即为 running，结束后进入 completed、failed 或 stopped，不另设 pending 状态。
- dispatched 只表示消息投递已确认，不表示引擎已经开始执行。
- Runner 开始准备执行与引擎进程就绪使用可区分的事件；这些阶段 Session 保持 running，不依赖 started 事件切换业务状态。
- 同一 Task 同时最多有一个活跃 Session；同一 Session 同时最多有一个有效执行归属。
- 终态不能被迟到日志、旧执行事件或重复处理改回活跃状态。
- 停止请求不等于进程已退出；容量释放以确认执行结束或原租约过期为依据。

## 4. 实施步骤

### 4.1 阶段一：入队、领取与重试

- [ ] 实现 EnqueueJob 按 SessionID 原子去重，重复提交不覆盖已保存输入。
- [ ] 实现 ClaimJob 的短事务领取、稳定排序和 SKIP LOCKED，领取后立即提交事务。
- [ ] 候选为无领取 token 或领取已过期的 Job，不设置单条任务的重试等待时间。
- [ ] 已过 Deadline 的任务允许领取后由 Service 收尾；不得抢占未过期的领取。
- [ ] 实现 RenewJobClaim、FailJob 和 CompleteJobDispatch，均校验当前领取 token 及期限；可重试失败保留记录与队列成员，不单独重新入队。
- [ ] 保留容量不足等可重试任务，继续处理其他候选，后续唤醒或周期扫描时再次尝试。
- [ ] 区分可重试错误、确定失败和发布结果不确定，避免所有错误无差别重试。
- [ ] 调度共享基础设施不可用时有界退出并等待下一轮，避免持续忙循环。

验收：重复入队只产生一条 Job；并发调度只允许一个有效处理者；单条失败不长期阻塞其他任务；重试不延长 Deadline。

### 4.2 阶段二：Lua 原子预占租约与容量

- [ ] 在同一 Lua 中检查 Runner 在线状态、实例、引擎能力、维护状态及容量限制。
- [ ] 原子删除容量 ZSet 中已过期占用，再计算是否有空闲名额。
- [ ] 检查 Session 无冲突租约；创建带 TTL 的执行租约，同时加入容量占用集合。
- [ ] 重复预留同一执行返回已确定的有效结果，不重复计数；执行归属冲突明确拒绝。
- [ ] 心跳不存在或过期、节点离线、实例变化、容量不足时不创建新租约。
- [ ] 将实际预留结果保存到 Job 和 Session 绑定；发布前确认持久化成功及调度领取仍有效。
- [ ] 处理 Redis 预留成功、DB 写入失败或响应丢失：按相同执行标识查询并恢复，确定未发布时才能释放预留。
- [ ] 核实 Redis Cluster 部署下 Lua 涉及 key 的同槽布局，不假设跨槽脚本可原子执行。

验收：多个调度器竞争最后一个名额时只有一个成功；预留即占容量；实例或租约失效后旧执行不能续期或释放新执行的名额。

### 4.3 阶段三：满载排队与调度唤醒

- [ ] 沿用常驻调度 goroutine 和容量为 1 的唤醒 channel，重复通知合并处理。
- [ ] 提交成功、执行终态、租约释放和节点恢复可接单时唤醒调度。
- [ ] 多 Server 部署接入跨实例容量通知，通知只提示扫描，不携带唯一任务事实。
- [ ] 保留周期扫描；重启后主动扫描，通知丢失不使任务永久停留在队列。
- [ ] 心跳可用于更新容量快照，最终能否预留仍由 Lua 决定。
- [ ] 使用待调度 ZSet 时，成员为 SessionID、分数为 QueuedAt，并补齐过期索引清理和缺失索引重建。

验收：满载时任务保持等待；容量释放后继续调度；通知合并、丢失或 Server 重启均可由扫描恢复，不产生多个重复调度循环。

### 4.4 阶段四：发布去重与 Runner 消费

- [ ] 通过 PublishJob 将固定消息写入目标 Runner 的 Job Stream。
- [ ] Lua 原子检查发布标记并执行 XADD；同一 MessageID 返回已发布，不同 MessageID 返回冲突。
- [ ] 首次发布前校验执行租约有效，不能发布已经过期的执行。
- [ ] 发布结果不确定时保留同一 Runner、MessageID、执行 token 和消息内容重试，不重新分配执行。
- [ ] 发布成功后确认 dispatched；DB 确认失败时允许幂等重试确认，不重新写入第二条消息。
- [ ] Runner 使用消费者组读取 Job，明确确认消费、待确认消息接管、重试次数和不可处理消息的处理方式。
- [ ] Runner 校验消息版本、目标节点、实例绑定、执行 token 和有效期。
- [ ] Runner 通过活跃执行登记和首次服务端续约确认拒绝同一执行重复启动；本地并发检查与登记原子完成。
- [ ] 同一活跃执行的重复消息不再次启动进程，也不能错误发布失败终态覆盖原执行。

验收：模拟消息已写入但响应丢失，重试仍只有一条消息；重复消费不启动第二个进程；晚到的过期 Job 不执行。

### 4.5 阶段五：心跳与执行续约

- [ ] 补齐 Runner 实例 ID，心跳更新和删除只允许当前实例，避免旧实例覆盖新实例。
- [ ] 心跳保存引擎能力、容量、运行状态和截止时间；停止接单与维护状态明确表达。
- [ ] Runner 在准备执行前首次确认执行租约，此后按剩余有效期安排续约。
- [ ] Server 校验 Session 状态、Runner 实例及执行绑定，不允许已撤销执行续期。
- [ ] Lua 原子延长执行租约 TTL、更新 expiresAt 和容量 ZSet 分数，不恢复已经过期的租约。
- [ ] Runner 使用本地单调时间维护保守的执行截止时间，区分明确拒绝与临时通信失败。
- [ ] 临时失败在剩余期限内重试；明确拒绝或到期时取消执行 Context，等待进程退出。
- [ ] 续约持续到受限的执行收尾完成；后台文件备份不无限延长执行租约。

验收：心跳存在但执行不续约时执行仍会过期；续约同时维护容量；网络短暂中断可恢复；失联到期后 Runner 停止执行。

### 4.6 阶段六：超时、取消与停止

- [ ] 排队到达 Deadline 后标记调度失败，收敛 Job、Session 和 Task，不继续安排重试。
- [ ] queued 状态支持原子取消并使旧领取者无法提交；保留足够信息进行补偿。
- [ ] 已预留或投递时先记录停止意图，再按实际执行归属发送有 ID、执行 token 和有效期的停止命令。
- [ ] Runner 幂等处理停止命令，匹配具体执行，避免迟到命令停止后续 Session。
- [ ] 取消与预留、持久化、发布之间设置状态校验；仍可能已发布时保留补偿，不把检查一次视为消除竞争。
- [ ] 停止请求后拒绝不再获准的续约，同时保留原租约追踪实际退出或自然过期，不立即重复释放容量。
- [ ] Runner 尚未消费 Job 时不发生续约；租约过期后由 Server 恢复扫描标记失败，存在停止意图则收敛为 stopped。
- [ ] Runner 晚到消费过期消息时直接拒绝启动；恢复过程不自动更换节点重跑原执行。

验收：排队取消不再投递；投递与停止并发时最终收敛；停止命令重复或迟到不影响新执行；未消费任务最终结束，不一直停留在 running。

### 4.7 阶段七：事件序号与业务幂等

- [ ] 定义事件 ID、执行标识、Task、Session、Runner、实例、Seq、类型和时间，明确序号按一次执行递增。
- [ ] Server 接收事件时校验执行归属及有效租约，拒绝旧实例、旧执行和错误 Session 的事件。
- [ ] 仅接受 Seq 大于已接受序号的事件；大于不代表必须严格加一，明确迟到事件的丢弃策略。
- [ ] 业务事务内再次校验当前执行及已处理序号，幂等写入日志、结果和终态，保护已结束 Session。
- [ ] 业务持久化成功后才推进 Redis lastSeq；终态持久化成功后再释放对应租约与容量。
- [ ] 推进序号或释放时使用 Lua 或条件更新，防止与续约、重试或旧处理者发生覆盖。
- [ ] DB 写入成功但 Redis 更新失败时允许重放；DB 写入失败时不得提前推进序号或释放容量。
- [ ] 明确 Stream 对同一执行的处理顺序；需要完整保留的日志不能仅靠最大 Seq 检查实现无损排序。
- [ ] 回传失败重试保留原事件 ID、Seq 和内容，不能每次生成新事件。

验收：重复事件只生效一次；较旧序号、旧租约和过期事件不改变业务状态；业务写入失败可重试；终态持久化后容量才释放。

### 4.8 阶段八：恢复扫描与清理

- [ ] 实现现有 recoverSessions 占位逻辑，分页检查长期未启动的 running 会话、执行租约失效和未完成停止补偿的会话。
- [ ] 恢复前读取最新调度阶段和租约，不能仅按 Session 创建时间判断失败。
- [ ] 无租约时先检查已可靠接收的终态事件，存在则补写结果，不直接覆盖为失败。
- [ ] 对仍在 queued 或 dispatching 的任务继续调度恢复，遵守 Deadline 和固定消息约束。
- [ ] 恢复更新使用当前状态和执行标识的条件写入，避免扫描期间新状态被覆盖。
- [ ] 清理已过期容量成员，只有当前执行可主动释放对应名额；过期占用不得继续减少可用容量。
- [ ] 按保留策略清理调度索引、发布标记、消息和恢复记录，保留业务历史及必要审计信息。
- [ ] 定义 Redis 数据丢失后的行为：通过持久化状态和重放记录恢复，不在执行结果不确定时自动重跑。

验收：漏通知、Server 重启、DB 与 Redis 部分成功均有明确恢复路径；不会把已完成任务误判失败，也不会因清理过早导致重复执行。

## 5. 验证与交付

### 5.1 核心验证场景

- [ ] 两个调度器争抢同一 Job、同一个剩余容量名额。
- [ ] 同一 Session 重复提交、重复预留和消息投递响应丢失。
- [ ] 单条 Job 持续失败与其他 Job 正常调度，避免队首反复重试。
- [ ] Runner 在线但一直未消费、心跳中断、执行续约中断及实例替换。
- [ ] 预留成功但持久化失败、发布成功但确认失败、业务终态成功但租约释放失败。
- [ ] 排队取消与调度、消息发布、Runner 启动并发。
- [ ] 事件重复、乱序、旧执行回传、终态之后迟到输出。
- [ ] 调度和续约 goroutine 退出、取消和 panic 后的资源收敛。
- [ ] 使用真实 Redis 验证 Lua、TTL 和 Stream 语义，使用数据库验证条件写入和事务边界。
- [ ] 并发实现完成后运行 `go test -race ./...`，记录实际验证结果。

### 5.2 交付内容

- Server Store 和 Runner Client 的具体适配与必要协议字段。
- 租约预占、续约、释放、发布去重等 Lua 脚本及 key 布局说明。
- 调度状态、执行授权、消息确认、停止补偿和事件幂等实现。
- 可配置时限、恢复扫描、脱敏日志及容量、排队、失败指标。
- 最小运行说明和上述故障场景的验证记录。

## 6. 实施顺序与依赖

先明确数据权威和协议，再实现入队领取、原子容量与租约、固定消息发布，随后接入 Runner 续约、停止、事件幂等和恢复扫描。每阶段补齐必要验证后再进入下一阶段。

### 6.1 开始实现前确认

- [ ] Job、Session 的 DB 权威状态与 Redis 热路径状态如何关联，跨存储失败如何补偿。
- [ ] Redis 单机或 Cluster 部署形态、Lua 同槽布局及服务连接方式。
- [ ] Runner 实例身份、执行 token 的传输范围及旧实例隔离方式。
- [ ] Stream 消费者组、消息保留、待确认消息接管和失败消息处理策略。
- [ ] 发布去重期限与消息重试、恢复保留期限的关系。
- [ ] 事件串行边界、日志保存方式及终态持久化与容量释放的先后关系。
- [ ] Session 从创建到终态的 running 语义、执行准备与进程就绪的事件边界，以及停止与失败的终态分类。

本计划不把 Redis Lua、DB 事务和消息通道视为一个跨系统原子事务；涉及多处写入的操作通过固定标识、幂等更新和恢复补偿完成。

## 7. Redis key 与端到端操作顺序

### 7.1 key 清单

以下名称仅用于说明数据职责，均为示意，不是现有部署中的真实名称。正式实现还需补齐环境隔离、资源范围及 Cluster 同槽布局。key 名称和 ZSet 成员使用非敏感标识，不放入认证用的完整执行 token。

| key 示意 | 类型 | 主要内容 | 写入及清理规则 |
| --- | --- | --- | --- |
| `dispatch:<sessionID>` | String | 调度状态、排队时间、截止时间、加密提交输入，以及准备好的固定 Job | 采用 Redis 调度队列时使用；调度结束后可保留 24 小时，期限配置化 |
| `dispatch:pending` | ZSet | SessionID，分数为入队时间 | 入队加入，调度成功、失败或取消收尾后移除 |
| `dispatch:claim:<sessionID>` | String | 当前调度领取 token | 采用 Redis 调度锁时使用；30 秒 TTL，处理期间续期，结束时比较 token 后删除 |
| `heartbeat:<runnerID>` | String | 实例、能力、在线状态、运行数量及心跳截止时间的 JSON | Runner 定期刷新，默认 30 秒 TTL；旧实例不能覆盖或删除新实例记录 |
| `heartbeat:index` | ZSet | RunnerID，分数为心跳过期时间 | 用于发现候选 Runner；读到候选后仍需检查实际心跳记录 |
| `maintenance:<runnerID>` | String | 节点维护或停止接单状态 | 按维护生命周期更新；不因短期心跳刷新而自动解除 |
| `lease:<sessionID>` | String | Task、Session、Runner、执行标识、期限及 lastSeq 的 JSON | 预留时创建，默认 5 分钟 TTL；续约延长，终态释放或自然过期 |
| `capacity:<runnerID>` | ZSet | 执行标识，分数为租约过期时间 | 与租约通过 Lua 同步预占、续约和释放；预占前清理过期成员 |
| `jobs:<runnerID>` | Stream | 给指定 Runner 的固定 Job 消息 | 幂等发布，Runner 消费确认；确认不等于删除，按消息保留策略裁剪 |
| `published:<runnerID>:<sessionID>` | String | 已发布的业务 MessageID | 与首次消息写入原子保存；默认至少保留 24 小时，并覆盖实际恢复窗口 |
| `commands:<runnerID>` | Stream | 带命令 ID、目标执行标识和期限的控制指令 | Runner 独立消费、幂等处理及确认，按保留策略清理 |
| `events:<partitionID>` | Stream | Runner 执行事件，含执行归属、事件 ID、Seq 和类型 | Server 消费；持久处理后确认，是否删除由事件通道保留策略决定 |
| `event-bytes:<partitionID>` | String | 事件通道待处理消息字节数 | 需要按字节背压时使用，随写入和清理同步增减 |

另外有一个示意频道 `capacity-available`，使用 Pub/Sub 在容量变化时通知其他 Server 实例重新扫描。每个实例运行自己的本地调度循环；提交入队后直接唤醒当前实例，不要求先发布 Redis 通知。该频道不是保存任务数据的持久化 key。

其中 `dispatch:<sessionID>` 和 `dispatch:claim:<sessionID>` 描述 Redis 调度队列方案；当前项目的调度记录和领取信息在 Job 的数据库记录中，不要求再创建这两个 key。待调度 ZSet 在当前方案中只是可选索引。

消费者组和待确认列表是 Stream 自身维护的元数据，不需要应用再为每条消息创建一个独立 key。Stream entry ID 由 Redis 产生，业务 MessageID 由发布者固定，两者用途不同。

### 7.2 从入队到完成的 Redis 队列流程

本节整理 Redis 调度队列的完整操作顺序。当前项目采用数据库领取时，按下一节替换对应步骤；执行租约、容量、消息和事件的职责保持一致。

| 顺序 | 执行方与阶段 | 涉及的 key 或频道 | 主要命令与结果 |
| --- | --- | --- | --- |
| 1 | Server 提交入队 | `dispatch:<sessionID>`、`dispatch:pending` | Lua 先 GET 去重，再 SET 调度记录、ZADD 排队成员；Task、Session 的创建在 DB |
| 2 | Server 本地唤醒调度 | 无 Redis key | 入队成功后直接调用本地调度唤醒方法；当前项目通过唤醒 channel 通知常驻调度 goroutine，此步骤不执行 PUBLISH |
| 3 | Server 发现候选并获取调度权 | `dispatch:pending`、`dispatch:claim:<sessionID>` | ZRANGE 按入队顺序读取候选；SET NX EX 获取单条调度锁，处理中按 token 续期 |
| 4 | Server 读取节点状态 | `heartbeat:index`、`heartbeat:<runnerID>`、`maintenance:<runnerID>` | 发现候选节点并检查状态；最终预留脚本内再次检查在线状态和可接单条件 |
| 5 | Server 原子预占 | `heartbeat:<runnerID>`、`maintenance:<runnerID>`、`lease:<sessionID>`、`capacity:<runnerID>` | Lua 检查心跳及已有租约，ZREMRANGEBYSCORE 清理过期占用，ZCARD 检查容量，SET PX 创建租约，ZADD 占用名额 |
| 6 | Server 保存固定执行消息 | `dispatch:claim:<sessionID>`、`dispatch:<sessionID>` | Lua 验证当前调度锁，SET 状态为 dispatching 并保存确定的 Job；执行归属审计等必要持久化在 DB |
| 7 | Server 幂等发布 | `jobs:<runnerID>`、`published:<runnerID>:<sessionID>` | Lua GET 发布标记；未发布则 XADD 消息并 SET 标记；相同 MessageID 直接返回已发布，不同 MessageID 拒绝 |
| 8 | Server 调度收尾 | `dispatch:<sessionID>`、`dispatch:pending`、`dispatch:claim:<sessionID>` | 保存 dispatched，完成业务投影后 ZREM 排队成员并 EXPIRE 调度记录；比较 token 后 DEL 调度锁 |
| 9 | Runner 接收执行消息 | `jobs:<runnerID>`、必要的维护状态 key | XREADGROUP 消费并校验消息及执行；按既定接单确认边界 XACK，Job 消息确认与执行终态分开 |
| 10 | Runner 请求 Server 续约 | `lease:<sessionID>`、`capacity:<runnerID>` | Server 校验后通过 Lua 条件更新租约及 TTL，并 ZADD 更新容量成员的过期分数；准备执行前先确认一次，此后周期续约 |
| 11 | Runner 发布接单、启动、输出等事件 | `events:<partitionID>`，按需包含 `event-bytes:<partitionID>` | XADD 事件；需要字节背压时由写入脚本同时维护字节计数 |
| 12 | Server 接收普通事件 | `events:<partitionID>`、`lease:<sessionID>` | XREADGROUP 批量读取，按同一次执行分组；GET 租约，验证执行归属、有效期和序号；业务处理成功后条件更新 lastSeq，再确认事件消费 |
| 13 | Server 处理终态事件 | `events:<partitionID>`、`lease:<sessionID>`、`capacity:<runnerID>`，按需包含字节计数 key | 先幂等保存 DB 终态及结果；Lua 比较当前租约后 DEL 租约、ZREM 对应容量成员；成功处理后确认终态事件 |
| 14 | Server 清理事件并唤醒后续调度 | `events:<partitionID>`、可选字节计数 key、`capacity-available` 频道 | 单一处理者组且不依赖 Stream 留存回放时，可在 XACK 后 XDEL 并同步减少字节计数；直接唤醒本地调度，另用 PUBLISH 通知其他实例容量可用 |

以上是逻辑先后关系，消息发布后的 Server 调度收尾与 Runner 消费可以并行，执行续约、心跳和事件消费也会并行运行。不能要求所有命令在全系统中形成一条严格串行链。

Job 接单后即可确认消息的模式需要可靠的执行登记、事件回传和租约恢复配套。本项目当前注释约定终态可靠回传后 AckJob；具体实现前需选定确认边界，不能仅照搬命令顺序就提前确认消息。

事件流采用处理后删除时，应明确历史日志和结果已保存到其他可靠存储。XACK 只清除待确认状态，本身不删除 Stream 消息。

### 7.3 当前项目的数据库领取映射

| Redis 队列流程中的操作 | 当前项目对应位置 |
| --- | --- |
| SET 调度记录 | EnqueueJob 保存 DB Job；可选 ZSet 只维护加速索引 |
| SET NX EX 获取调度锁 | ClaimJob 通过短事务、SKIP LOCKED 和 Job 中的领取 token、期限获取调度权 |
| 校验 Redis 调度锁后保存状态 | Store 条件更新时校验 DB 中的 ClaimToken、期限和当前状态 |
| Redis 调度锁周期续期 | RenewJobClaim 延长 DB 中的 ClaimExpiresAt |
| SET dispatched 并释放调度锁 | CompleteJobDispatch 在 DB 确认投递并清除领取信息；如有待调度 ZSet，再补偿移除索引 |
| 执行租约与容量预占、消息去重和事件处理 | 仍由对应 Redis 适配实现，遵守前述 Lua 与跨存储补偿约定 |

不同时把 DB 领取信息和 Redis 调度锁作为必须同时成功的两套调度权威；如将来更换调度后端，应单独评审迁移与恢复方式。

### 7.4 失败、取消与后台维护涉及的 key

| 场景 | 涉及的数据 | 操作要求 |
| --- | --- | --- |
| 调度容量不足 | 调度记录、排队集合、当前领取信息 | 保留 queued 及队列成员；释放当前处理权，后续唤醒或扫描时再次尝试，不新建执行租约 |
| 排队超时或取消 | 调度记录、排队集合、当前领取信息 | 条件写入失败或取消状态，阻止旧调度器提交；业务收尾成功后移出索引 |
| 已预留且确定尚未发布的准备失败 | `lease:<sessionID>`、`capacity:<runnerID>` | 比较执行标识后原子释放，不能误删后来执行的租约或名额 |
| 发布结果不确定 | 固定 Job、`published:<runnerID>:<sessionID>`、执行租约 | 保留原执行归属并幂等重试，不因请求报错就释放可能已被消费的执行 |
| 执行停止 | `commands:<runnerID>`、当前执行租约 | 发布有执行归属和有效期的停止命令；拒绝不再获准的续约，等待退出确认或原租约到期 |
| Runner 持续心跳 | `heartbeat:<runnerID>`、`heartbeat:index` | 更新 JSON、TTL 及索引分数；必要时发送接单能力恢复通知 |
| Runner 一直没有消费 | 执行租约、容量集合、Job 通道和业务状态 | 无续约则租约到期；扫描补写失败或停止状态；过期容量成员可回收，晚到消息不得启动 |
| 消费者失联 | 相应 Stream 的消费者组及待确认列表 | 按选定策略使用 XAUTOCLAIM 或 XPENDING、XCLAIM 接管，再按幂等语义处理 |
| 定期恢复与清理 | 调度记录或索引、执行租约、容量集合、发布标记及消息流 | 先复查最新状态与已保存终态，再补偿或清理；发布标记不得早于有效重试窗口消失 |

预留名额包含尚未启动和正在执行的任务，统一按容量 ZSet 中未过期成员计数，不再减一次 Runner 上报的运行数量。Redis key、索引和 DB 业务状态的实际一致性，需要通过实施阶段的故障验证确认。
