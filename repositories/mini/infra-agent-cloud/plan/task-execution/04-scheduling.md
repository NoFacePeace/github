# 容量调度闭环

## 1. 阶段目标

多个 Runner 同时接入，Server 按能力和容量选择节点；满载任务保留排队，容量释放后继续执行，多个 Server 不重复调度和超卖。

## 2. 可运行链路

```text
提交任务 → 持久调度记录和 pending 索引
  → 领取调度锁 → 检查业务状态和排队期限
  → 选择 Runner → 原子预占租约和容量
  → 固定执行消息 → 幂等发布 → 同步业务调度摘要
  → 确认移除 pending → 执行结束释放容量 → 唤醒下一批
```

## 3. 依赖与边界

- 依赖阶段三的远程执行、稳定执行身份、基础续约和事件终态处理。
- 已绑定任务优先保持工作区所在 Runner，不将节点故障自动解释为允许换节点重跑。
- 首版使用可解释的在线、能力与容量筛选，不提前建设复杂负载预测策略。

## 4. 模块实现事项

### 4.1 Runner 发现与准入

- [ ] 上报 RunnerID、实例标识、引擎能力、状态、容量与在线期限。
- [ ] 心跳记录使用有期限的 JSON，索引按期限排序；列举时清理失效索引并批量读取有效记录。
- [ ] 心跳更新和注销核对实例，旧实例不能覆盖或删除新实例心跳。
- [ ] 本地实际运行数用于节点观测和本地准入，服务端分配容量以有效预占租约集合为依据。
- [ ] 支持暂停接单与维护状态，停止接单不直接杀死已有执行。

### 4.2 调度队列与处理权

- [ ] 独立保存调度记录、待调度索引和短期调度锁，明确 TTL 与主动清理职责。
- [ ] pending 按入队顺序读取候选，获取带持有者标识的调度锁后再读取最新记录。
- [ ] 调度过程中续锁，写入和释放均核对持有者；失锁者不再提交调度修改。
- [ ] 保存 queued、dispatching、dispatched、failed、cancelled 阶段，定义每阶段可恢复的处理动作。
- [ ] 满载及临时故障保留排队，继续处理其他任务；到达排队截止时间后执行失败收尾。
- [ ] 使用发布订阅唤醒和定时扫描共同驱动，通知丢失后仍能推进；索引缺失有持久依据用于恢复。

### 4.3 租约与容量原子协调

- [ ] 为候选 Runner 在同一 Lua 中检查心跳、维护状态、租约冲突、有效容量并创建占用。
- [ ] 容量集合同时计算预留和运行中的执行，清理过期占用后判断，不等待 Runner 上报开始才扣容量。
- [ ] 执行续约原子更新租约到期时间与容量分数，保留并发推进的事件水位。
- [ ] 释放时核对当前执行，删除租约和对应容量成员，并维护集合的清理期限。
- [ ] 固定 Job 之前的孤立预留和固定消息之后的执行分开处理，禁止不加区分地释放后重新投递。
- [ ] 选节点后预占失败时，未绑定且尚未固定执行的任务可尝试下一个候选；绑定任务不静默改投其他节点。
- [ ] 确保多 key Lua 同槽；脚本在写入前完成可预检校验，不假定脚本运行错误会回滚已完成写入。

### 4.4 业务投影与调度收尾

- [ ] 业务同步入口读取最新 Session，避免迟到 queued 覆盖更晚调度摘要。
- [ ] queued 会话停止后取消调度；可能已发布时转入停止补偿，不仅修改记录就认定已停止。
- [ ] 发布成功后的记录保存失败复用固定消息恢复；确定失败与发布结果不确定分开处理。
- [ ] 调度终态同步或必要补偿完成后移除 pending，保留足够期限的调度记录和去重标记。
- [ ] 终态事件释放容量后发布唤醒通知，重复释放和重复通知均安全。

## 5. 验收场景

- [ ] 同时提交超过总容量的任务，最多允许有效预占数量执行，其余继续排队。
- [ ] 两个 Server 竞争同一任务和最后一个名额，均不产生重复执行或容量超卖。
- [ ] 模拟预占成功后保存失败、发布成功后响应丢失，可恢复到同一确定执行。
- [ ] 调度锁过期后旧调度器继续返回结果，条件写入阻止其覆盖新记录。
- [ ] Runner 离线、能力不匹配、维护或满载时不会错误创建执行预占。
- [ ] 容量通知丢失和部分候选失败时，后续扫描仍可继续调度其他任务。

## 6. 交付物

支持多 Server、多 Runner 的调度链路，包含节点发现、队列、调度锁、容量预占、业务投影及调度收尾的可重复并发验证。
