# Redis 分层与接入实施计划

## 1. 目标与范围

明确 Redis 基础连接、业务存储和执行消息通信的职责，在现有三个包内实现可维护的 Redis 接入。

本计划只描述分层和接入步骤，不新增顶层业务模块，不修改现有业务代码。调度规则与完整验收场景见[任务调度实施计划](./SCHEDULING_PLAN.md)。

### 1.1 组织约定

- 保留 `server`、`runner`、`executor` 三个包，不单独创建顶层 redis、transport 或 runtime 包。
- Server Service 继续调用 Store 的业务方法，不直接拼 Redis key 或执行 Lua。
- Store 是统一数据入口，可以组合数据库、Redis 和对象存储适配，不要求所有方法由同一种存储实现。
- Runner 继续通过 Client 获取任务、发送心跳、续约和回传事件，Runner 执行逻辑不直接操作 Redis key。
- Executor 不连接 Redis，不负责队列、租约、节点心跳或业务状态更新。
- 连接管理独立于业务规则，消息通信独立于普通 KV 操作；不把所有 Lua 和业务流程塞进一个通用 Redis 客户端。
- 仅保存通用设计，不包含内部平台名称、专属 SDK、部署地址、真实身份或凭证。

## 2. 分层职责

### 2.1 基础连接层

负责 Redis 客户端创建、配置、连接检查、超时、连接池、连接关闭和必要的通用原子辅助操作。

通用操作可以直接使用选定 Go 客户端提供的命令；不为每个 Redis 命令机械新增一层同名接口。只有调用侧确需统一约定的超时、结果转换或条件操作才封装辅助方法。

本层不识别 Task、Session、Job、Runner 等业务模型，不决定何时释放租约或更新任务状态。

### 2.2 业务存储层

负责将 Store 的业务方法映射为数据库事务、Redis 命令或 Lua：

| 业务职责 | 对应操作 |
| --- | --- |
| 调度候选及唤醒 | 待调度索引、通知发布订阅及恢复重建 |
| 节点状态 | 心跳读取、实例校验、在线期限及能力快照 |
| 执行协调 | 容量与租约原子预占、续约、释放 |
| 发布幂等 | 发布标记检查与执行消息写入 |
| 事件校验 | 执行归属、有效期、序号条件更新 |
| 状态补偿 | DB 与 Redis 部分成功后的查询、重放和清理 |

业务 key、TTL、Lua 和错误语义放在各自职责附近。基础客户端不负责 Job 重试、Session 终态或数据库事务编排。

### 2.3 消息通信层

负责 Job、控制命令和执行事件的传输，封装 Stream 发布、消费者组、确认消费、待确认消息接管、批量读取和失败处理。

对外使用 PublishJob、ClaimJob、AckJob、PublishEvent 等业务通信方法，不向上暴露 XADD、XREADGROUP 或 Stream entry 的底层字段。

Server Store 中的 ClaimJob 表示领取待调度任务，Runner Client 中的 ClaimJob 表示领取已分配的执行消息，两者保持语义区分。

### 2.4 调用关系

```text
Server Service
  → Store 的业务方法
      → 数据库适配：Job、Session、Task 等持久化
      → Redis 业务适配：心跳、租约、容量和索引
      → 消息适配：Job、命令和事件传输

Runner 执行逻辑
  → Client 接口
      → 具体通信适配
          → Server 接口或受限的执行消息通道

Executor
  → 接收执行输入并输出事件，不访问 Redis
```

Runner 是否直连执行消息 Redis 通道，在通信实现前明确。若通过 Server 接口领取，Redis 消费逻辑保留在 Server；若直连，Redis 命令只出现在 Runner 的 Client 适配中。执行授权校验和续约仍由 Server 管理，不能让 Runner 直接改业务租约。

## 3. 数据与 key 约定

### 3.1 Redis 数据类型

| 数据 | 类型 | 内容与用途 |
| --- | --- | --- |
| Runner 心跳 | String | JSON，保存实例、能力、状态及在线期限 |
| 执行租约 | String | JSON，保存执行归属、token 或标识、期限及 lastSeq |
| Runner 容量占用 | ZSet | 成员为执行标识，分数为租约过期时间 |
| 待调度索引 | ZSet | 成员为 SessionID，分数为排队时间；仅用于加速候选发现 |
| 发布去重标记 | String | 保存同一 Session 对应的固定 MessageID |
| Job 通道 | Stream | 传输固定的执行消息 |
| 命令通道 | Stream | 传输带执行归属及有效期的控制命令 |
| 事件通道 | Stream | 传输带事件 ID、执行归属和 Seq 的事件 |
| 调度唤醒 | Pub/Sub | 只通知重新扫描，不能作为唯一任务来源 |

Job 和调度领取信息继续按现有 Store 约定持久化。当前 ClaimJob 使用数据库短事务，不因为增加 Redis 基础封装就直接迁移调度权威状态。

### 3.2 命名与原子边界

- 使用统一 key 构造函数，规范资源标识、部署环境、数据类型和协议版本，避免各处拼接格式不一致。
- 不将凭证明文或可用于认证的完整 token 放进 key 名称。
- 明确每个 key 的读写者、TTL、主动删除条件、重建来源和清理策略。
- 使用 Redis Cluster 时，多 key Lua 必须满足同槽约束；预占租约与容量、发布消息与去重标记分别设计可原子访问的布局。
- 不把 Redis、数据库和外部 HTTP 调用当作同一个原子事务；跨系统操作依赖固定标识、幂等条件和恢复补偿。

### 3.3 连接使用

- 普通命令使用受控连接池；阻塞消费和订阅使用适合客户端模型的专用连接，避免阻塞普通业务请求。
- 显式设置连接、命令、阻塞读取和关闭超时，所有后台循环受 Context 控制。
- 网络重试按操作语义选择；发布等结果不确定的操作必须具备幂等协议，不能依赖客户端自动重试保证正确性。
- 生产连接凭证由配置或部署注入，日志不输出带密码的连接串、认证信息或原始敏感消息。
- 多个适配可以共享客户端连接池，连接创建和关闭由装配层统一管理，避免重复创建或提前关闭共享资源。

## 4. 建议文件位置

以下是后续实施位置建议，不要求一次创建全部文件，也不新增业务包。

| 文件 | 职责 |
| --- | --- |
| `server/store.go` | 保留 Store 业务接口，按阶段增加必要能力 |
| `server/redis_client.go` | Redis 配置、连接装配和生命周期辅助 |
| `server/redis_keys.go` | key 构造及统一命名约定 |
| `server/store_redis.go` | 心跳、执行租约、容量及候选索引适配 |
| `server/store_streams.go` | 消息发布、去重、事件消费等 Server 侧通信实现 |
| `runner/client.go` | 保留 Runner 通信接口，不放具体命令和连接信息 |
| `runner/client_http.go` | 需要通过 Server 访问的通信实现，按实际选型创建 |
| `runner/client_redis.go` | 仅在确定 Runner 直连消息通道时创建，限制可操作范围 |

Lua 脚本可以先作为对应适配文件中的常量；脚本增多或需要单独维护时，再放到所属包下英文命名的脚本目录。不得为了共享连接代码引入 Server 与 Runner 业务实现的相互依赖。

## 5. 分阶段实施

### 5.1 阶段一：接口与数据权威

- [ ] 逐项确认 Store、Runner Client 方法的职责，区分数据库操作、Redis 状态和消息传输。
- [ ] 明确各数据的权威来源及跨存储失败恢复方式，不同时维护两个互相覆盖的权威状态。
- [ ] 确认 Go Redis 客户端、部署形态、连接认证及 Cluster 同槽需求。
- [ ] 定义业务错误：容量不足、归属冲突、租约失效、重复发布、通信失败和无消息。
- [ ] 确认 Runner 消息通道采用 Server 转接还是受限直连，以及数据库、租约和消息通道的权限边界。

验收：每个业务操作有确定的实现位置、数据来源和错误语义；上层接口无需暴露 Redis 命令即可表达流程。

### 5.2 阶段二：基础连接与通用辅助

- [ ] 实现连接装配、配置校验、连接检查、连接池及优雅关闭。
- [ ] 为普通命令、订阅和阻塞消费配置适当的连接与超时。
- [ ] 仅封装必要的条件设置、比较删除或比较更新等通用辅助，不加入业务模型。
- [ ] 确认断连、重连、Context 取消和服务退出时的行为，避免泄漏 goroutine 和连接。
- [ ] 添加不含凭证的连接、超时和错误指标。

验收：连接可创建、使用并关闭；阻塞消费不耗尽普通命令连接；配置与异常日志不泄露连接凭证。

### 5.3 阶段三：业务存储适配

- [ ] 实现 Runner 心跳、执行租约、容量及待调度索引，集中管理 key 和 TTL。
- [ ] 通过 Lua 原子完成租约与容量预占、续约、释放，按当前执行身份进行条件更新。
- [ ] 保持当前调度领取和数据库事务边界，补齐 Redis 写入与数据库保存之间的失败补偿。
- [ ] 业务 Lua 返回明确结果，由适配转换为业务错误，上层不依赖脚本中的数字返回码。
- [ ] 实现必要的过期清理、容量重算、索引重建和通知发布订阅。

验收：预留不超卖、重复调用不重复占用，过期占用可回收；业务 Service 不直接依赖 key、JSON 存储格式或 Lua。

### 5.4 阶段四：执行消息适配

- [ ] 定义版本化 Job、命令和事件消息，只传执行所需字段。
- [ ] 实现固定消息发布和发布标记的 Lua 原子去重，处理结果不确定后的重试。
- [ ] 实现消费者组读取、确认、待确认接管和有界失败处理，区分 Stream entry ID 与业务 MessageID。
- [ ] 实现批量事件读取与按执行分组，保留原事件标识、Seq 和顺序语义。
- [ ] 将具体消息消费接入 Server 或 Runner Client 适配，保持执行逻辑只调用接口。
- [ ] 控制命令与执行任务使用独立的消费流程，长任务不得阻塞停止命令接收。

验收：投递重试不重复写入，消息重投不重复启动；任务、命令和事件通道可独立运行，退出时消费循环正确停止。

### 5.5 阶段五：集成、恢复与文档

- [ ] 在现有构造和启动流程中注入 Store 与 Client 的具体适配，统一管理资源生命周期。
- [ ] 接入心跳、调度唤醒、执行续约、事件校验及恢复扫描，逐项对照调度计划验收。
- [ ] 验证连接中断、Lua 返回失败、DB 部分成功、消息确认丢失和进程退出等故障路径。
- [ ] 使用真实 Redis 验证 String、ZSet、Stream、Pub/Sub、TTL 和 Lua 的实际行为。
- [ ] 对并发实现运行 `go test -race ./...`，仅为有行为约束的实现增加必要测试。
- [ ] 更新 key 布局、时限、连接配置、消费确认及跨存储补偿说明，不记录真实连接值。

验收：完整任务流程使用同一套业务接口完成；Redis 接入细节留在适配中，恢复扫描可处理部分成功，服务退出不遗留消费者或连接。

## 6. 交付标准

- 基础连接、业务存储、消息通信职责清晰，现有三个包保持不变。
- Store 统一入口不等于单个巨型实现，Runner Client 不暴露 Redis 原始命令。
- 数据库事务、Redis Lua 和消息确认的边界有明确说明及故障验证。
- key 命名、TTL、错误分类、重试与清理规则集中可查。
- 所有配置示例使用占位值，不包含内部系统或真实凭证。

本计划的下一步是阶段一：明确每个现有接口的数据权威、实现位置和 Runner 通信方式，再创建具体连接或适配代码。
