# 执行事件实施计划

## 1. 目标与范围

完成 Runner 输出回传、Server 校验与业务收尾、日志归档、历史恢复和 SSE 实时推送。

本文是待实施方案，不代表现有代码已经实现。只新增计划，不修改业务代码；使用通用名称和示例 key，不包含内部平台名称、部署地址、真实身份或凭证。

### 1.1 当前基础

- `runner/client.go` 已定义 `PublishEvent`，事件已有 started、output、completed、failed、stopped 类型，但缺少执行归属和 Seq 等协议字段。
- `runner/runner.go` 已串联启动、输出和终态回传，具体通信、执行登记及续约仍有占位实现。
- `executor.Event`、`executor.Result` 和 Runner Job 仍需补齐协议。
- `server/job.go` 的执行租约已有 `LastSeq`，但事件消费、序号更新和业务处理尚未接入。
- Session 已有 running、completed、failed、stopped；创建即 running，包含排队和执行阶段，started 不用于首次切换为 running。
- Server 已有停止编排、执行租约释放和恢复扫描，可作为事件终态收尾的接入点；DB 操作和部分 Store 方法仍未实现。

### 1.2 实现边界

- 保留 server、runner、executor 三个包，Store 的具体实现继续放在 `server/store.go`，不借此重构现有调度流程。
- 本计划补齐执行后的事件闭环，不新增自动换节点执行、完整工作区备份或第三方账号授权。
- 前端断开只结束该连接的订阅，不停止 Runner，也不撤销执行租约。
- 事件传输允许重复，通过固定执行身份、Seq 和幂等处理收敛，不声称端到端恰好处理一次。
- 日志可能包含用户输入、代码及工具结果；按任务访问权限读取，不将原始日志打印到运行诊断日志中。

## 2. 数据职责与调用链

### 2.1 职责划分

| 组件 | 职责 |
| --- | --- |
| Executor | 启动引擎、读取 stdout/stderr、产生结构化输出，在 Runner 指定的路径写 JSONL 日志 |
| Runner | 为同一次执行统一分配 Seq，可靠发布事件，管理停止和续约，直接上传本地日志到对象存储 |
| Server 事件消费者 | 批量接收事件、校验执行身份、按执行串行处理、更新 Session、完成租约和容量收尾 |
| Server Store | 封装 Stream、租约、事件缓存、日志缓存、DB 幂等更新等数据操作 |
| Server SSE 接口 | 校验用户访问权限、恢复历史、订阅当前执行后续事件、维护每个连接的游标 |
| 对象存储 | 保存 Runner 上传的日志归档，供 Redis 日志缓存失效后读取 |

### 2.2 正常链路

```text
Executor 输出 → 本地 JSONL 日志
            → Runner 分配 Seq → 发布事件 Stream
                                   ↓
                      Server 校验并处理同一次执行的事件
                         ├─ 写 Session 事件 ZSet
                         ├─ 提取输出写日志 String
                         ├─ 终态更新 DB
                         └─ 更新 LastSeq / 终态释放租约与容量
                                   ↓
                           确认 Stream 消费

Runner 本地日志 → 周期上传和结束备份 → 对象存储

页面建立 SSE → 历史恢复 → history_sync → event_delta / session_end
```

## 3. 事件协议与序号

### 3.1 事件字段

以下为拟补齐的字段，不直接要求新建共享包。

| 字段 | 用途 |
| --- | --- |
| Version | 协议版本，未知版本明确拒绝 |
| TaskID、SessionID | 业务归属 |
| RunnerID | 上报节点 |
| ExecutionID | 非授权用途的执行标识，用于区分不同执行；具体授权校验由通信和租约接口负责 |
| MessageID | 对应固定的执行消息，便于核对投递归属 |
| Seq | 同一次执行内从 1 开始递增，由 Runner 统一分配 |
| Type | started、output、completed、failed、stopped |
| OccurredAt | 诊断时间，不替代 Seq 排序 |
| Output | 输出通道、原始引擎记录或结构化输出；区分 stdout 和 stderr |
| Result、Error | 终态结果或错误，补充退出码、引擎会话 ID、用量等确需保存的字段 |

- 同一次执行内 `(SessionID, ExecutionID, Seq)` 唯一标识事件；重试必须复用同一 Seq 和内容。
- Stream entry ID 只用于传输确认，不是执行 Seq，也不作为 SSE 的业务游标。
- 多个输出来源进入同一个有序发布器，不能由 stdout、stderr 各自维护独立 Seq。
- 终态只发布一次逻辑事件，确认收到前可以重发；终态后不再产生普通输出事件。
- 新执行重新计数，旧执行的 Seq 不用于判断新执行；重连或重试复用原执行标识。
- ExecutionID 是本计划使用的通用协议名称，不代表现有代码已经具备该字段，也不能直接将授权凭据改名后用于公开标识。

### 3.2 两层序号校验

1. 执行租约层校验业务归属、执行标识、有效期及 `LastSeq`；新批次最大 Seq 必须大于 LastSeq。
2. Session 事件存储层剔除已写入的前缀，对尚未写入的事件要求顺序连续，再原子追加和推进存储水位。

只比较批次最大 Seq 并不代表中间事件完整。批次必须属于同一次执行、内部有序且无缺口；序号缺口暂缓确认并重试，持续无法补齐时进入明确的失败与诊断流程，不静默跳过输出。

`LastSeq` 表示已接受的事件进度，不是租约续期。普通事件不自动延长执行期限；执行续约更新有效期和容量分数时必须保留最新 LastSeq，使用条件更新避免互相覆盖。

## 4. Redis 数据与保留策略

### 4.1 key 与类型

下表仅使用通用 key 模板，省略项目、环境和部署前缀；不记录现网 key 或实际资源标识。字段和配置在实现时统一收敛。

| key | 类型 | 内容及用途 |
| --- | --- | --- |
| `events` | Stream | Runner 回传事件的入口，由 Server 消费者组读取 |
| `events:bytes` | String | 入口积压字节数，配合准入和消费确认维护 |
| `events:dlq` | Stream | 格式错误、超出重试限制等不可正常处理的消息及简短原因 |
| `events:<taskID>:<sessionID>` | ZSet | member 为事件 JSON，score 为 Seq；用于有序读取和短期重放 |
| `events:<taskID>:<sessionID>:log` | String | 从输出事件提取的日志文本，主要为一行一个 JSON 的 JSONL |
| `events:<taskID>:<sessionID>:state` | Hash | 当前执行绑定、已写入 Seq、字节数、terminal、finished、截断状态 |
| `lease:<sessionID>` | String | 现有执行租约 JSON，含归属、有效期和 LastSeq |
| `capacity:<runnerID>` | ZSet | 容量占用，member 为执行占用标识，score 为租约到期时间 |

- 一个 Task 有多个 Session，每轮日志 key 不同；DB 查询 Sessions 后拼 key，不用 SCAN 遍历 Redis。
- 容量通知可复用后续统一的跨 Server 唤醒机制，只提示重新扫描，不保存唯一业务事实。
- 多 key Lua 需满足同槽约束，具体分片和部署布局在实现时确定。
- key 和对外事件只使用业务标识，不承载授权凭据；读取前核对 state 中的执行绑定。

### 4.2 初始参数

| 参数 | 初始值或约定 |
| --- | --- |
| Server 每次入口读取数量 | 最多 100 条，返回少于 100 条也立即处理 |
| 运行中缓存 TTL | 24 小时，收到事件或有效执行续约时刷新 |
| 执行结束后的日志 String TTL | 默认 5 分钟，可配置为 1～15 分钟 |
| 执行结束后的事件 ZSet、state TTL | 24 小时，作为短期重连重放窗口 |
| Runner 周期日志备份 | 每 30 秒，结束后进行一次受超时限制的收尾备份 |
| SSE 事件轮询间隔 | 初始 500 毫秒，后续可用通知降低空读 |
| 对象存储日志保留 | 由部署明确配置生命周期，不在代码中假设永久保留 |

- 日志结束 TTL 与事件重放 TTL 分开，不能把事件 ZSet、日志 String 和租约视为同一份数据。
- 运行中续期只延长尚未 finished 的缓存，不把已完成缓存重新变成长期存活。
- 设置入口、单次执行事件缓存和日志缓存的字节上限，不仅设置条数上限。
- 不通过任意裁剪尚未确认的 Stream entry 解决积压；需要背压、告警和有界失败策略。
- 日志超限时保留截断标记，历史读取可退回更完整的归档；实时事件不能静默丢弃后继续声称输出完整。
- 本方案保留短期事件供多个 SSE 连接重放：单个连接推进游标不删除全局 ZSet。与消费回调后立即删除的方式相比，这是为刷新和多连接显式增加的保留策略，必须配合容量限制。

## 5. Runner 发布与 Server 消费

### 5.1 Runner 发布

- [ ] 补齐 Runner Job 与事件协议，为输出分配稳定 Seq，按序发布。
- [ ] 发布成功表示事件已进入约定的可靠传输边界；失败保留同一事件重试，不能跳过后继续推进。
- [ ] 明确进程退出前待发输出、终态和 Job Ack 的顺序，避免终态先于最后一段输出。
- [ ] Runner 只有在终态可靠进入事件通道后才 AckJob；回传失败 Nack 不能引发已执行任务再次启动。
- [ ] 将本地日志写入和上传归档纳入 Runtime 生命周期；Server 不重复承担远程 Runner 的周期文件上传。
- [ ] 网络错误、停止与租约失效时，保留受超时限制的终态回传和日志备份机会，不能无限延长执行授权。

### 5.2 批量读取与分组

- [ ] Server 启动独立事件消费循环，受服务 Context 控制，与调度扫描分开。
- [ ] 使用 XREADGROUP 读取入口 Stream；支持待确认消息接管和有限次数重试。
- [ ] 按 TaskID、SessionID、RunnerID、ExecutionID 分组，不把不同执行的 Seq 放在一起比较。
- [ ] 同一次执行串行处理；不同执行可有限并发。消费者组本身不保证同一次执行跨消费者的处理顺序，需按执行建立处理互斥或稳定路由，并以条件写入兜底。
- [ ] 每个执行批次只做一次租约准入检查，内部各事件仍分别校验类型和顺序；批次含终态时终态必须位于末尾。
- [ ] 批处理失败保留未确认消息；拆分处理时不能绕过顺序约束让后续事件提前成功。

### 5.3 校验、写入和确认顺序

正常处理顺序如下，Redis 与 DB 之间不视为同一个事务：

1. 查询并核对当前执行租约，拒绝错误归属、旧执行、过期执行；已处理事件走重复确认路径。
2. 原子追加尚未写入的事件、日志片段和缓存水位；重复事件不重复拼接日志。
3. 普通输出不逐条更新 Session DB；终态在 DB 事务中校验执行绑定，幂等保存结果与终态处理进度。
4. 普通批次条件推进租约 LastSeq；终态在业务持久化成功后，经归属校验条件释放租约和容量，保留可重试收尾信息。
5. 完成缓存 finish、容量唤醒等可恢复收尾后，XACK 并按保留策略 XDEL 入口消息，同时维护积压字节计数。

- [ ] 确认 Session 缓存写入水位与租约 LastSeq 是不同的进度：第 2 步成功而后续失败时，重试仍需完成剩余业务操作。
- [ ] 不在业务保存前推进唯一的已处理水位或删除租约，避免重试将未保存终态误判为重复。
- [ ] 租约条件更新因并发续约失败时重新核对，不覆盖较新的租约字段；旧执行不能释放新执行容量。
- [ ] DB 已提交、租约未释放时允许幂等重放完成清理；租约已删除但确认响应丢失时，使用已持久化的执行绑定和终态进度识别重放，不重新授权执行。
- [ ] DB 保存终态失败不确认入口消息。租约自然过期后的恢复扫描优先检查已接收终态，避免把尚未应用的完成事件直接覆盖为超时失败。
- [ ] 迟到旧执行事件只做丢弃或诊断，不修改新执行状态；无合法租约的普通输出不进入历史。
- [ ] 毒消息隔离到有界死信通道，记录原因和定位字段；正常业务消息不因一次暂时错误直接进入死信。
- [ ] 明确 Redis 持久化与故障恢复配置；XACK 不是 DB、Redis 和对象存储同时提交的证明。

### 5.4 Session 终态与容量收尾

- [ ] completed 保存结果、引擎会话 ID、必要用量；failed 保存错误和退出信息；stopped 保存停止结果。
- [ ] 沿用当前 Task 无运行状态的模型，不为同步事件额外给 Task 加状态字段。
- [ ] 已由用户标记 stopped 的 Session 不被迟到 completed 改为 completed，但仍需确认实际执行结束并释放对应容量。
- [ ] 同一终态重复处理不重复释放、不重复通知，不允许普通输出把 Session 改回 running。
- [ ] 终态事件缓存可先写入，但前端 session_end 只能在 DB 业务提交后发布；不能提前展示未提交成功的完成结果。
- [ ] 无终态但租约失效时交给现有恢复流程；事件消费者不自动换 Runner 重跑。

## 6. 日志归档与历史恢复

### 6.1 日志不是完整事件副本

- 事件包含执行身份、Seq、类型、业务结果和输出；日志主要保存 stdout/stderr 中可恢复展示的引擎记录，不复制授权字段。
- JSONL 每行一个 JSON；stderr 中非 JSON 文本需带通道记录或按确定的容错规则展示，不强行当作引擎消息解析。
- Redis 日志来自事件提取，本地归档来自 Executor 文件，两者需使用一致的输出格式；不要求包含所有 started、进度或控制事件。
- 调度失败、排队取消等可能没有引擎日志，页面直接按 Session DB 状态和提示词恢复。

### 6.2 归档与读取

- [ ] Runner 负责周期备份本地日志，归档路径使用 `tasks/<taskID>/sessions/<sessionID>.jsonl` 等统一通用布局。
- [ ] 同一 Session 的上传串行化，结束备份等待先前上传结束，避免旧快照覆盖新文件。
- [ ] Server 按任务权限读取日志：优先 Redis String，缺失或截断时尝试对象存储；归档尚未成功要返回可识别的暂缺状态。
- [ ] 整个 Task 历史先从 DB 查询 Sessions，按创建顺序读取各轮提示词、状态和日志，再解析为消息及工具调用。
- [ ] 实现分页、按需读取和批量缓存读取，避免 Task 历史变长后每次打开都无限量加载所有日志。
- [ ] 归档延迟或备份失败时不承诺无损历史；明确显示截断或缺失，不能把暂缺当作空回复。
- [ ] 归档路径、内容类型、最终完成标记及读取权限由服务端控制，Runner 不接受任意外部路径覆盖。

## 7. SSE 与页面刷新

### 7.1 必须接上当前执行

历史恢复和后续订阅是两个操作。本计划将当前执行重订阅作为独立待实现项，验收时同时检查历史展示和后续实时输出。

- [ ] SSE 以 TaskID 定位任务，先校验访问权限，再读取 Sessions；不只依赖浏览器记住的运行状态。
- [ ] 重建连接时查询当前活跃 Session 和执行绑定，直接订阅共享事件存储，不依赖旧请求中的内存回调。
- [ ] 新连接不创建 Session、不重新调用引擎、不重投 Job。
- [ ] 不同 Server 实例均能恢复历史并订阅同一个执行，浏览器连接不绑定最初投递所在的 Server。
- [ ] 每个连接独立维护 Seq 游标；Last-Event-ID 或显式游标仅用于恢复读取，不能作为授权依据。
- [ ] 对外 SSE ID 使用非授权用途的 Session/执行标识和 Seq，不返回执行凭据。新 Session 开始后切换执行标识和游标。

### 7.2 历史快照与增量衔接

直接“先读日志，再从最新 Seq 订阅”会漏掉两步之间的输出；“历史加载后从 0 重放”又会重复显示。按以下顺序实施：

1. 读取当前执行绑定，并预留历史恢复期间的事件读取窗口，固定缓存水位 S。
2. 获取与 S 对齐的历史快照，再发送 history_sync。
3. 从 Seq 大于 S 的事件继续发送 event_delta；已写入快照的事件不再重复追加。
4. 如已完成，以 DB 终态和最终水位发送 session_end；运行中持续读取，轮询通知丢失不丢事件。

- [ ] 实现可验证的快照与游标对齐方法，例如写输出事件时原子记录对应日志字节边界，并将日志快照和水位一致读取；不能把日志字节 offset 当成事件 Seq。
- [ ] 历史来自归档但水位无法对齐时，不拼接未经核对的热增量；重新建立一致快照或返回需要重同步的状态。
- [ ] 游标超出保留窗口、缓存被淘汰、执行绑定变化时发送 reset_required，重新恢复历史，不从缺口后悄悄继续。
- [ ] 用户停止使 Session 业务状态先终结时，仍按实际执行收尾进度处理剩余输出和连接结束，不把业务 stopped 当作进程已退出。
- [ ] SSE 断开只移除该连接，不删除全局事件，不停止任务；一个连接读取不影响其他页面。
- [ ] 慢连接使用有界缓冲，超限断开并要求重同步；设置心跳、写入超时并关闭代理缓冲。

## 8. 实施顺序与验收

### 8.1 阶段一：协议和基础接口

- [ ] 先补齐 Job、Event、Result、Seq 和稳定执行标识，明确终态及日志格式。
- [ ] 在 Store 定义事件批量领取、确认、幂等追加、读取、日志读取、终态提交和缓存收尾能力。
- [ ] 在 Service 定义事件消费循环和单批处理入口；接入生命周期后再逐项实现，不一次改写调度器。

验收：同一执行事件可排序、可定位；重复发布字段稳定；Executor 不访问 Redis 或 DB。

### 8.2 阶段二：消费、业务状态和资源释放

- [ ] 实现批量消费、执行校验、缓存幂等追加及 LastSeq 条件更新。
- [ ] 实现终态 DB 保存、租约与容量收尾、Stream 确认及恢复补偿。
- [ ] 验证重复、乱序、序号缺口、跨执行混批和旧执行事件不会污染当前 Session。
- [ ] 验证缓存写入后崩溃、DB 提交后崩溃、租约释放后确认丢失均能重试收敛。
- [ ] 验证事件与执行续约并发不会覆盖 LastSeq 或较新的到期时间。

验收：成功终态使 Session 和容量收敛；用户 stopped 不被覆盖；暂时故障不吞事件，不重复启动任务。

### 8.3 阶段三：日志和归档

- [ ] 实现 Executor 本地写入、Runner 周期上传和结束备份、Server Redis 日志提取及归档回退。
- [ ] 验证 TTL、缓存截断、归档缺失、上传竞争和超时停止。
- [ ] 验证只有提示词和 Session 终态、没有引擎日志的轮次也能展示。

验收：Redis 日志过期后可从成功归档恢复；备份失败可观察且不伪装为完整历史。

### 8.4 阶段四：SSE 和刷新恢复

- [ ] 实现历史快照、水位对齐、当前执行重订阅和每连接独立游标。
- [ ] 验证执行中刷新、刷新时恰好产生输出、终态同时到达、跨 Server 重连和多页面并行读取。
- [ ] 验证游标过期、慢连接、Task 出现新 Session 和历史分页。

验收：刷新不启动新执行，历史不重复，后续输出不断流；超出恢复能力时明确要求重同步。
