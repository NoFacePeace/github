# 授权与凭证管理实施计划

## 1. 目标与范围

实现用户账号授权、平台凭证配置、Runner 服务身份认证，以及远程执行中的凭证领取、使用、刷新回写和清理闭环。

本文件仅记录实施计划，不代表相关能力已经实现。保留现有三个包，不新增顶层业务模块；本次不修改业务代码，也不改写原有基础闭环计划。

### 1.1 授权能力清单

| 能力 | 目标实现方式 | 凭证维护方 |
| --- | --- | --- |
| Codex 个人订阅 | 设备码登录，后台轮询授权结果，交换并验证 Token | Server 管理保存和集中刷新，支持引擎刷新后回写 |
| Claude Code 个人订阅 | 用户通过 `claude setup-token` 获取 Token，再提交保存 | 用户更新 Token；初期不实现集中刷新 |
| 企业身份提供方 | OAuth 授权码加 PKCE，验证一次性 state，交换并保存用户 Token | Server 或可选身份代理维护，以实际协议为准 |
| GitLab 用户授权 | 使用提供方 OAuth；如已有授权代理，可通过适配器获取 Token | Server 或授权代理负责保存和刷新 |
| Google 用户授权 | 使用提供方 OAuth，按工具所需范围申请权限 | Server 或授权代理负责保存和刷新 |
| Figma 用户授权 | 使用提供方支持的授权协议，获取工具所需 Token | Server 或授权代理负责保存和刷新 |
| Jira、Confluence | 配置提供方授权入口及状态检查适配器 | 凭证获取、刷新和工具交付以具体部署协议为准 |
| MCP OAuth | 授权发现、客户端注册或配置、授权码交换、Token 保存和刷新 | Server 按用户和 MCP Server 管理 |
| 模型服务 API Key | 从平台配置读取对应服务凭证 | 平台配置维护，不要求用户个人订阅 |
| GitLab Bot、GitHub Token | 从平台配置读取，按仓库操作用途使用 | 平台配置维护 |
| 自定义工具凭证 | 用户提交变量、环境变量或认证 Header 的敏感值 | Server 加密保存，刷新取决于具体提供方 |
| 服务身份认证 | Runner 携带受控身份凭证，Server 验证调用者身份及权限 | 具体认证方式和凭证签发来源在实施时确定 |
| 可选临时服务认证 | 按部署需要评估短期凭证方案，绑定用途及有效期 | 独立配置、限时启用，不绕过任务授权 |

### 1.2 范围边界

- 用户登录系统的会话与授予 Agent 使用外部服务的权限分别处理，不能把登录成功视为已完成第三方授权。
- 本计划实现授权与凭证交付，不展开 Google、Figma、Jira、Confluence 的全部业务工具。
- Jira、Confluence 的授权状态查询不等于已实现 Access Token 获取或工具调用。
- 第三方 SDK、OAuth 客户端权限、服务身份配置和真实联调环境是实施依赖，需要分别核实。
- 外部服务地址、客户端标识、服务身份标识、KMS keyId 均配置化，不在文档或代码中保存真实密钥。

## 2. 当前基础与职责

### 2.1 当前代码基础

- `server/service.go` 已有执行预留、投递、调度收尾及恢复流程骨架。
- `server/job.go` 已有执行 token 和执行租约期限，尚无凭证引用字段。
- `runner/runner.go` 已串联活跃执行登记、执行续约、Runtime 调用和事件回传；部分方法仍为占位。
- `runner/client.go` 已定义任务、指令、续约和事件通信接口，尚无凭证领取及回写接口。
- `runner/runtime.go` 已定义环境准备、执行和清理流程，具体实现仍为占位。
- `runner/job.go`、Executor 请求及结果结构尚未补齐，不能视为已具有远程安全交付协议。

### 2.2 职责归属

| 位置 | 职责 |
| --- | --- |
| Server service | 编排用户授权、凭证解析、刷新、授权签发、领取校验和回写 |
| Server Store | 统一封装 DB、Redis 等存取，提供去重、条件更新和原子状态操作 |
| Server KMS 适配 | 封装加解密；与 Store 的数据持久化职责区分 |
| Runner Client | 封装身份获取、凭证领取、回写和既有执行通信 |
| Runner runExecution | 在 Runtime 启动前领取凭证，覆盖领取失败的执行收尾 |
| Runner Runtime | 使用凭证准备源码、Git 配置、私有认证文件和隔离环境，管理清理 |
| Executor | 接收本轮所需凭证，按引擎协议交付并执行，不直接访问业务数据库 |

各职责可在现有包内新增英文命名的文件，不继续拆分业务包。Store 不负责发起第三方 OAuth 登录或编排刷新流程。

## 3. 模型与存储

### 3.1 需要表达的数据

| 数据 | 主要内容 |
| --- | --- |
| 用户凭证 | 用户、提供方、认证方式、加密内容、状态、版本及更新时间；有效期按提供方实际信息记录 |
| OAuth 等待状态 | 所属用户、state、PKCE verifier 或设备授权标识、客户端和回调绑定、截止时间、进度 |
| MCP 凭证 | 用户、规范化 MCP Server 标识、Access/Refresh Token、到期时间、客户端及刷新地址、版本 |
| SecretGrant | 随机引用、加密凭证快照、执行绑定、领取截止时间、授权状态及清理信息 |
| ExecutionSecrets | Runner 领取后在内存中持有的凭证明文，按引擎、环境变量、工具配置区分 |
| 身份配置 | 允许的服务身份、凭证用途、可信签发来源，以及可选临时认证配置 |

SecretGrant 绑定 Task、Session、固定执行消息标识、Runner、Runner 实例及执行租约。当前执行 token 与调度 ClaimToken 分开使用；调度 ClaimToken 不传给 Runner。绑定使用执行 token 还是其摘要，在协议定义时明确。

### 3.2 存储位置

| 内容 | 计划存储位置 | 要求 |
| --- | --- | --- |
| Codex、Claude Code 用户凭证 | DB | KMS 加密，不保存凭证明文 |
| 用户连接的企业身份凭证、自定义敏感变量 | DB | 按用户和所属配置范围保存，KMS 加密 |
| SecretGrant | DB | 加密快照与执行绑定一起保存 |
| MCP OAuth 凭证 | Redis | 敏感 Token 必须加密；保留足够刷新所需的状态和期限 |
| OAuth state、设备码等待状态、刷新锁 | Redis | 有限 TTL、归属校验及一次性消费；敏感材料采取受控存储 |
| GitLab、Google、Figma 原始授权 | DB 或外部授权代理 | 直接接入时加密保存；使用代理时按需获取，避免重复维护 |
| Bot Token、平台 API Key、KMS 服务访问凭证 | 平台配置或部署提供的凭证来源 | 不写入仓库、Job 或日志 |
| Runner 请求使用的短期服务身份凭证 | 应用内存 | 不由业务代码落库，不交给 Executor；底层认证材料按选定方案管理 |
| 引擎私有认证文件 | 本轮执行私有目录 | 仅执行期间使用，收尾清理 |

来自授权代理或配置中心的凭证，一旦纳入本次执行，仍可能被 KMS 加密后暂存在 SecretGrant 中；这与长期维护原始凭证是两件事。

### 3.3 加密与有效期约束

- KMS 使用信封加密；存储密文及 SDK 所需元数据。Base64 只作存储编码，不作为加密措施。
- KMS 主密钥由平台管理，应用只配置 keyId 和受控访问方式；具体算法和密文格式以选定 Go SDK 为准。
- 生产凭证加密失败时返回错误，不回退明文存储。
- 服务身份凭证有效期、业务 Token 有效期、SecretGrant 领取窗口、执行租约期限分别处理。
- SecretGrant 初始领取窗口设为 5 分钟并配置化；窗口到期只禁止再次领取，不承诺撤销已交付的业务 Token。
- 领取窗口结束后，有效执行仍可能需要凭证回写；回写按有效执行授权校验，不受初始领取窗口直接限制。
- SecretGrant 清理不得仅因领取窗口过期就删除有效执行仍需要的快照及回写校验信息。

## 4. 目标调用流程

### 4.1 用户授权

```text
用户请求连接提供方
  → Server 创建有归属和期限的授权状态
  → 用户打开提供方授权页面，或提交自行生成的 Token
  → Server 交换并验证凭证
  → KMS 加密后保存
  → 返回连接状态，不向浏览器返回已保存的敏感 Token
```

Codex 的后台设备码轮询与前端查询登录进度是两层轮询。企业身份提供方、MCP 的授权码返回流程单独实现，不套用设备码机制。

### 4.2 任务凭证准备与领取

```text
Server dispatchJob
  → ReserveExecution：确定 Runner 和执行租约
  → 解析用户及平台凭证，必要时等待刷新
  → 创建或复用绑定本次执行的 SecretGrant
  → Job 携带 SecretRef，复用固定消息内容投递

Runner handleJob
  → 登记活跃执行
  → 首次校验并启动执行续约
  → runExecution
      → Client.ClaimSecrets
          → 获取服务身份 Token
          → 请求 Server
          → 校验响应与本次执行的绑定
      → Runtime.Run(ctx, job, secrets, emit)
          → 准备工作区、Git 和引擎配置
          → 准备隔离及资源限制
          → Executor.Run
          → 清理私有认证文件及临时资源
      → 回传终态
```

- SecretGrant 在执行归属确定后、发布执行消息前签发。消息投递重试复用同一引用与快照，不能每次重新生成不同消息。
- Job 不携带业务凭证明文；Runner 内部通过独立参数传递 secrets，不回填到可序列化的 Job。
- 凭证领取失败须进入现有失败事件及收尾流程，不得仍然启动引擎。
- 明确区分网络等可重试错误与授权撤销、租约失效、领取窗口过期等拒绝结果。
- 领取截止后不无限重新签发授权延长执行准备；按任务状态和期限收尾，用户重新执行时建立新的合法授权。

### 4.3 Server 领取校验

```text
解析请求并验证服务身份
  → 读取 SecretGrant，比较完整执行绑定
  → 检查 Session 可执行、Runner 实例和执行租约有效
  → 检查领取截止时间及授权状态
  → KMS 解密
  → 再检查关键授权状态、租约及领取窗口
  → 返回受限凭证集合，响应禁止缓存
```

服务身份与实例身份分别处理。RunnerID、实例 ID 和请求参数匹配本身不能证明调用者是该实例；部署时明确身份粒度和信任边界。需要实例隔离时，使用可验证的独立身份及通道权限隔离。

### 4.4 交付、回写与清理

- 独立 Executor 进程接入后，通过 stdin 匿名管道传递版本化敏感输入，校验执行标识、大小及读取超时；不通过命令参数传明文。
- 当前接口内调用阶段，可在内存中传递独立 secrets 参数；在完成独立进程前，不宣称已有管道或沙箱隔离。
- Runtime 管理私有路径和清理清单；Executor 按引擎需要写认证文件。目录权限采用 `0700`，敏感文件采用 `0600`，防止路径逃逸及符号链接替换。
- Git helper 与 gitconfig 不内嵌 Token；helper 在运行时读取环境变量，限定 HTTPS 和允许的目标主机。
- Codex 退出后、私有文件删除前，在有效授权和有界收尾期限内回写刷新结果，然后完成清理和执行租约收尾。
- 回写比较账号、刷新信息及原始凭证版本，使用条件更新，防止旧执行覆盖重新登录或其他执行写入的新凭证。
- 正常完成、失败、取消、启动部分失败及 Runner 重启恢复均覆盖私有文件清理；删除不等同于磁盘安全擦除。
- Session 结束或授权撤销后拒绝新领取和执行续约，通过现有取消及停止指令使 Runner 收敛；不能把撤销授权等同于外部 Token 立即失效。

## 5. 分阶段实施

### 5.1 阶段一：协议、存储与 KMS

- [ ] 定义用户凭证、授权等待状态、SecretGrant、ExecutionSecrets 及提供方错误的最小字段。
- [ ] 补齐 Runner 实例标识和执行协议；在 Server Job 与 Runner 接收协议中增加凭证引用。
- [ ] 在现有 Store 入口定义用户凭证、MCP Token、OAuth 等待状态、SecretGrant 的存取与条件更新操作。
- [ ] 明确用户、配置所属范围、提供方、MCP Server 的唯一键及查询权限。
- [ ] 在 server 包内定义 KMS 适配，确认可用 Go SDK、服务凭证来源、keyId、密文格式及密钥轮换兼容性。
- [ ] 实现基础存储与加解密；错误信息只携带必要诊断，不输出凭证、SQL 参数或原始请求体。

验收：敏感值可加密保存并解密使用；其他用户不能查询或修改；并发条件更新不覆盖新凭证；加密失败没有明文回退。

### 5.2 阶段二：用户凭证入口与 Codex

- [ ] 提供连接状态、断开连接和受权限控制的凭证提交接口。
- [ ] 实现 Codex 设备码申请、后台轮询、状态查询、取消及过期待办恢复策略。
- [ ] 轮询并发和请求超时有界；用户取消、状态过期或 Server 退出时停止对应轮询。
- [ ] 授权成功后交换 Token，使用固定可信 JWKS 地址验签，并按提供方协议检查有效期、issuer、audience 等约束。
- [ ] 保存 Access/Refresh/ID Token 和账号标识；领取前不足 1 小时时等待集中刷新，阈值配置化。
- [ ] 刷新使用按用户及提供方的并发保护，重新读取最新记录，按版本条件更新。
- [ ] 分类处理明确认证失效与临时通信失败，返回可供业务识别的重新授权原因。
- [ ] 实现 Claude Code Token 提交、格式检查、加密保存、查询状态及删除；明确保存成功不代表远端可用性已验证。

验收：完成一次真实 Codex 授权及刷新；重复申请、取消、过期和并发刷新状态正确；Claude Code 可保存和删除合法格式 Token；前端响应不泄露已保存 Token。

### 5.3 阶段三：企业身份与第三方授权

- [ ] 实现可配置企业身份提供方的 PKCE、state 归属与一次性消费、授权码交换和保存，隔离不同部署环境。
- [ ] 提供凭证状态和断开接口，回调校验客户端、用户、环境和预期重定向地址。
- [ ] 为 GitLab、Google、Figma 实现提供方适配器；直接 OAuth 与可选授权代理采用统一结果结构，避免重复刷新同一份凭证。
- [ ] 统一未授权、授权过期、用户会话失效、提供方或代理通信错误的业务状态及授权链接。
- [ ] 接入 Jira、Confluence 授权状态查询，明确与实际工具访问的边界。
- [ ] 明确哪些操作必须用户 Token；只有显式允许的场景才回退 Bot，不能因用户未授权静默扩大权限。
- [ ] 自定义变量按所属范围加密保存，敏感值查询仅返回状态或脱敏结果；向执行传递时按所需变量解析。

验收：各提供方状态可查询；用户授权后能获取允许的工具 Token；测试与正式凭证不混用；需要用户权限的操作不自动使用 Bot 绕过。

### 5.4 阶段四：MCP OAuth

- [ ] 实现 MCP 授权发现、客户端注册或已有客户端配置、授权链接生成和授权码交换。
- [ ] 授权 state、PKCE 及回调地址绑定当前用户和规范化后的 MCP Server。
- [ ] 实现 Redis 加密存储、状态查询、凭证删除及按需刷新。
- [ ] 刷新并发保护和条件写入防止旧 Token 覆盖新授权；刷新明确失败时要求重新连接。
- [ ] 校验发现及 Token 请求的目标地址，限制重定向，防止向非预期服务发送凭证。
- [ ] 准备任务时解析 MCP 认证 Header 和敏感配置，并纳入本次授权快照。

验收：至少一个真实 MCP Server 完成授权、调用和刷新；重复回调被拒绝；不同用户及不同服务的凭证不能互相复用。

### 5.5 阶段五：平台凭证与 Git

- [ ] 接入平台模型 API Key、GitLab Bot 和 GitHub Token 配置；限制凭证可发送的目标地址。
- [ ] 区分用户业务仓库权限和平台 Agent 配置仓库权限，不将 Bot 默认交给用户执行。
- [ ] 实现 Agent 配置源码按固定 commit 拉取，认证通过进程环境中的 Git 配置注入，不拼入远程 URL。
- [ ] 在 Runtime 启动 Executor 前生成执行私有 gitconfig、credential helper 和必要 wrapper。
- [ ] 用户 Git 操作使用 `GITLAB_ACCESS_TOKEN`；helper 仅对配置的 GitLab 主机及 HTTPS 返回凭证。
- [ ] 配置允许的 SSH 格式地址重写为 HTTPS；真实 SSH 私钥认证不属于本阶段实现。
- [ ] 防止宿主全局 Git 配置、其他 credential helper、日志或仓库 remote URL 意外泄露凭证。

验收：用户权限允许的仓库可完成 HTTPS clone、fetch 和 push；无权限仓库拒绝；helper、gitconfig、remote URL 不包含 Token；Bot 和用户凭证用途可区分。

### 5.6 阶段六：服务身份认证与限时领取

- [ ] 选择服务身份认证方式，确认凭证签发、获取、验证和轮换机制，以及可信材料来源。
- [ ] 按目标部署环境配置允许的调用者身份、凭证用途和可信签发来源。
- [ ] 实现 Runner 获取身份凭证、Server 验证身份；按选定协议验证真实性、有效期、身份和用途，不仅比较请求中的标识。
- [ ] 在执行预留后签发或复用 SecretGrant，保存 KMS 加密快照和领取期限，再发布固定执行消息。
- [ ] 实现 Server 领取接口；将身份验证、绑定匹配、有效租约和 Session 状态检查串联。
- [ ] 在 Client 定义 ClaimSecrets，并在 runExecution 调用 Runtime.Run 前接入。
- [ ] 领取后重新确认取消状态；失败不启动 Executor，执行续约持续保护后续准备阶段。
- [ ] 部署前明确服务身份粒度和实例隔离要求，验证身份与执行归属之间的对应关系。
- [ ] 如需临时服务认证，评估独立短期凭证，配置用途、到期时间和审计类型；不绕过 grant、租约及状态检查。

验收：合法执行可领取；只有 secretRef、错误服务身份、错误绑定、旧实例、失效租约、终态 Session 或过期领取请求均被拒绝；投递重试不改变消息及授权快照。

### 5.7 阶段七：引擎交付、回写及恢复

- [ ] Runtime.Run 使用单独 secrets 参数；Job 序列化、普通事件和日志不包含凭证明文。
- [ ] 补齐独立 Executor 进程的版本化管道协议，敏感输入与 stdout/stderr 输出区分。
- [ ] Codex 使用私有认证目录；Claude Code 按引擎要求注入订阅 Token；工具环境变量和 Header 只传给必要执行范围。
- [ ] 隔离 Executor 对 Runner 身份认证材料、KMS 服务凭证和其他执行私有目录的访问。
- [ ] 实现 Codex 刷新凭证读取和回写接口；检查当前有效执行、账号一致性及原凭证版本。
- [ ] 回写具有独立的有界收尾时间和可识别结果，不因失败而泄露凭证或无限保留执行。
- [ ] 正常、异常、取消及 Runner 重启时清理私有文件；恢复过程检查路径和执行归属。
- [ ] SecretGrant 定期清理结合执行状态、租约及保留策略；不影响仍获准的执行收尾。
- [ ] 对凭证访问和变更记录脱敏审计，覆盖授权、领取、拒绝、刷新、回写和删除。

验收：真实 Codex 与 Claude Code 可获得各自所需凭证执行；Git 和工具可访问授权资源；输出及持久化日志不含测试秘密；取消和重启无遗留认证文件；旧执行不能覆盖新登录凭证。

## 6. 验证与交付

### 6.1 必要验证

- [ ] 单元验证：凭证状态分类、期限判断、授权绑定、刷新条件写入、敏感协议解析。
- [ ] 并发验证：重复授权回调、同用户集中刷新、消息重投、取消与领取竞争、回写与重新登录竞争。
- [ ] 故障验证：KMS 不可用、提供方或代理超时、授权拒绝、租约过期、进程启动失败、Runner 重启恢复。
- [ ] 集成验证：DB 和 Redis 状态期限、真实 KMS 加解密、服务身份凭证获取和拒绝路径。
- [ ] 提供方验证：Codex 设备码及刷新、Claude Token 使用、企业身份及第三方授权、至少一个 MCP OAuth 服务。
- [ ] 变更涉及并发实现时运行 `go test -race ./...`；真实验证使用测试凭证，结果只记录脱敏信息。

### 6.2 交付内容

- 现有三个包内的授权、存储、KMS、领取协议和引擎适配实现。
- 用户授权与状态接口、Runner 领取与回写接口，以及必要传输结构。
- DB 迁移、Redis 键与 TTL 说明、配置模板及服务身份认证配置说明。
- 按授权类型记录首次连接、更新、断开、重新授权和错误处理方法。
- 记录实际完成的提供方联调，以及尚未验证的环境、SDK 和权限边界。

## 7. 实施顺序与待确认项

### 7.1 实施顺序

先完成阶段一的模型和存储基础，再逐项实现用户授权、第三方适配及平台凭证，随后完成服务身份、SecretGrant 和 Runner 交付，最后验证真实引擎、回写及恢复。各阶段按小步定义接口、实现和接入，避免一次扩大改动范围。

服务身份认证和 KMS 的实现依赖可提前核实；用户授权界面不是验证 Server 与 Runner 凭证闭环的前置条件，可以先用受控测试配置打通通道。

本计划涉及的持久化和授权能力是原基础闭环计划之外的专项扩展；原计划暂缓的内容不自动视为本专项已完成。

### 7.2 开始实现前需要确认

- [ ] 选用的 Go KMS SDK、访问认证方式、密文格式及可用测试环境。
- [ ] 服务身份认证的 Go 实现、目标部署环境的凭证签发方案及是否要求 Runner 独立身份。
- [ ] 各提供方的客户端配置、允许的回调地址、授权范围和服务可达性。
- [ ] Codex 设备码和 Token 接口是否允许当前客户端使用，以提供方文档和真实联调确认协议。
- [ ] 企业身份提供方的刷新能力，以及 Jira、Confluence 工具访问的实际凭证和认证方式。
- [ ] MCP 授权规范版本、客户端注册支持情况及凭证存储期限。
- [ ] SecretGrant 保留策略、回写收尾期限、首次领取窗口及执行租约的独立配置。

待确认项应在对应阶段开始前落实，不通过猜测平台能力或保存真实凭证到文档推进。
