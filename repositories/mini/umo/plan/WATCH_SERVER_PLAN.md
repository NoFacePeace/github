# Watch 服务端实现计划

## 1. 目标与范围

为 mini UMO 的 API Server 增加 Watch 接口。Controller 通过 HTTP GET 建立连接，先收到全量快照，随后在同一响应流中收到运维增量、集群 CR 增量和心跳。

按从入口到数据源的顺序实现。先用固定数据跑通流式接口，再接入多连接广播和数据库查询。协议沿用现有 Watch 客户端的 JSON 格式，Controller 通过 `WATCH_URL` 配置完整地址。本轮聚焦单个 API Server 实例，不涉及按客户端 offset 补发历史事件。

## 2. 核心流程

API Server 启动 → Controller 请求 Watch 路由并传入集群 ID → 服务端取得快照和对应 offset，注册连接 → Handler 先写出 `FullSync` → 持续写入增量和心跳 → 连接断开后释放资源。

广播器按 offset 轮询数据源。运维增量发给所有连接，集群 CR 增量只发给对应集群的连接。每条连接由自己的 Handler 按顺序写入 HTTP 响应。

## 3. 模块划分

| 模块 | 职责 |
| --- | --- |
| API Server 入口 | 启动 HTTP 服务、注册 Watch 路由并处理退出 |
| Watch Handler | 校验集群 ID、写入全量和增量 JSON、发送心跳、清理连接 |
| 广播器 | 注册和移除连接，按事件类型及集群分发，隔离队列已满的连接 |
| 数据源 | 返回全量快照及其 offset，按 offset 查询后续变更 |

## 4. 阶段一：接入 API Server 启动流程

### 4.1 启动和路由

- [ ] 在 `cmd/apiserver` 建立独立启动入口，启动 HTTP 服务并响应退出信号。
- [ ] 在 `apiserver/watch` 定义最小 Handler，注册 `GET /watch/:clusterID`，先用固定响应验证路由与集群 ID 传递。

### 4.2 阶段验收

- [ ] 启动 API Server，确认 GET 请求进入 Watch Handler，取消服务后能正常退出。

## 5. 阶段二：打通全量响应和心跳

### 5.1 写入事件流

- [ ] 定义服务端事件外层字段 `eventType`、`data` 和 `eventOffset`，其中 `data` 沿用 JSON 字符串形式。先用固定数据构造包含运维数据、集群 CR 和两类 offset 的 `FullSync`。
- [ ] 每条事件编码成 JSON，写入换行并调用 `Flush`，保持响应流打开。首条事件发送后，按固定间隔发送 `Heartbeat`。
- [ ] 监听请求取消和服务退出信号。写入失败时结束当前响应，退出时停止心跳定时器。

### 5.2 阶段验收

- [ ] 用 `curl -N` 验证同一次 GET 先收到 `FullSync`，随后持续收到心跳。断开客户端后确认 Handler 退出。
- [ ] 用现有 Controller Watch 客户端连接服务，验证全量中的运维数据能被解码并提交。

## 6. 阶段三：接入增量广播与慢连接隔离

### 6.1 注册连接和分发

- [ ] 为每条连接创建有界事件队列，Handler 在发送完 `FullSync` 后，从队列读取增量并写入响应。
- [ ] 先用构造的增量验证分发。运维事件广播给所有连接，集群 CR 事件按集群 ID 分发。
- [ ] 广播器非阻塞入队，队列满时通知对应 Handler 断开。限制单次响应写入时间，让卡在写入上的连接也能退出；退出后注销连接。

### 6.2 阶段验收

- [ ] 同时连接两个不同集群，确认两者都收到运维增量，只有目标集群收到对应的 CR 增量。
- [ ] 模拟一条连接消费缓慢，验证其队列满后能退出，其他连接仍可收到事件。

## 7. 阶段四：接入数据源和 offset

### 7.1 获取全量并持续轮询

- [ ] 先用内存数据源接通全量查询和增量轮询，再接入数据库。运维事件使用全局 offset，集群 CR 按集群记录 offset。
- [ ] 从同一份数据视图取得全量快照及其 offset，并让取快照与注册连接相对于广播有明确顺序。注册后的增量可先进入队列，由 Handler 在全量写出后再发送。
- [ ] 定时查询 ID 大于当前 offset 的记录，成功读取并分发批次后推进相应 offset。查询失败时保留原值，下一轮重新查询。
- [ ] 重连时重新读取全量快照和对应 offset，为当前连接建立新的增量起点。

### 7.2 阶段验收

- [ ] 在建立连接时写入一条变更，验证首条消息始终为 `FullSync`，变更能从快照或后续增量看到。
- [ ] 验证没有新增记录时只发心跳，新增记录时推动对应 offset；模拟查询失败后恢复，确认增量能继续发送。
- [ ] 模拟断流后重连，验证客户端重新收到全量快照并继续接收增量。集群 CR 路径先用流测试验证，待客户端配置接收方接通后联调。
