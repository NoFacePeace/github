# UMO 健康检查模块实现计划

## 1. 目标与范围

### 1.1 实现目标

在 `controller/healthcheck` 中实现可独立运行和验证的健康检查模块：发现受管 Pod 及其所在节点的异常，按配置选择处理策略，通过累计异常比例和执行去重控制处理范围，最终向 Pod 写入处理标签。

学习重点是 Checker 扩展、Kubernetes 状态读取、异常归一化、规则匹配、时间窗口统计，以及健康检查与资源调谐之间的职责划分。

项目根目录已初始化 Go module `umo`，Go 版本为 `1.26.3`；已定义 Manager 接口、私有实现结构及必要类型，入口通过协程调用 Run。当前已接入按配置间隔触发内部 runOnce，以及 context 取消时释放定时器并退出；runOnce 已并发调用注入的 Checker，并将汇总 Map 交给 processStatuses；runOnce 无返回值，processStatuses 已接入 Pod 列表读取、Action 分组、过期清理、命中时间刷新、累计比例过滤、动作去重及五种动作标签写入，写入成功后记录执行时间。SubmitEvent 已接入节点和 Pod 异常事件。具体内置与外部 Checker、Watch 网络接入及实际资源调谐仍待实现。

### 1.2 本次实现

- Go、Kubernetes API、controller-runtime；支持 kubeconfig 和集群内配置。
- 单 Kubernetes 集群、单活动实例运行，按中间件类型标签及可选集群过滤条件限定受管 Pod。
- 两种 Checker：读取 Kubernetes 状态的 `BuiltinHealthChecker`，以及读取外部 HTTP 健康接口的 `WebhookHealthChecker`。
- Kubernetes 检查覆盖节点健康 Conditions、相关污点和 Pod 上已有的磁盘检测注解；节点异常映射到受影响的受管 Pod。
- 支持异常状态匹配，以及按 NodeSet、集群和 Pod 标签附加条件匹配；按配置顺序选择第一条命中的策略。
- 支持时间窗口内累计命中比例检查、动作去重，以及 `Migrate`、`ReCreate`、`InPlaceUpdate`、`Manual`、`Automatic` 五种动作标签。
- 策略可配置 `Webhooks`，每轮标签处理结束后异步通知本轮匹配的 Pod 及各自的处理结果。
- 通过 Run 的运行模式配置支持单次检查与周期运行，提供只输出决策的 dry-run；通过 SubmitEvent 接收外部事件，用本地样例演示两条输入链路。

### 1.3 实现边界

- 本模块负责发出处理请求，独立验收终点是 Pod 标签写入成功；标签写入不等于重建完成。
- 实际实例迁移、Pod 重建、原地更新、PVC 处理、前后置检查和恢复结果确认由后续资源调谐模块负责，另列联调验收。
- 本次不实现磁盘检测程序，只读取检测组件已经写入的结果。
- Prometheus 查询由外部健康接口提供方负责；本次用 HTTP 样例服务模拟其结果，不建设 API Server 或第三种 Prometheus Checker。
- 本次实现 Manager 的事件提交入口与内部队列，使用本地调用模拟事件；运维事件长连接、心跳、重连、偏移量管理及事件持久化暂不实现。
- 本次不实现工单审批、指标存储、配置热更新。
- 累计命中与执行记录保存在内存中，进程重启后丢失；不承诺跨进程去重或严格只执行一次。

### 1.4 设计约定

- 先定义统一 Checker 接口和结果表达，用固定结果的测试桩打通 Manager 单次调用，再接入两种实际 Checker；测试桩不作为生产检查器注册。
- Manager 对外只提供 NewManager、Run 和 SubmitEvent；单轮检查、事件转换与状态处理分别保留为私有方法 runOnce、processEvent、processStatuses。
- Manager 负责调用、汇总和生命周期，Checker 负责具体异常检测；周期检查和外部事件由同一个 Run 循环串行处理。
- Run 阻塞运行，调用方通过 context 取消通知退出；需要并行运行其他组件时，由启动入口统一组织协程并等待退出。
- Checker 返回 map[string]Status，键使用 Pod 的 namespace/name；只返回异常 Pod，每个 Pod 对应一个状态。
- Manager 汇总为 map[string][]Status，同一 Pod 的不同状态全部保留，相同状态去重，列表顺序按 Checker 配置顺序确定；单个 Checker 仍返回一个状态，其内部多种异常按固定优先级选择。
- 标签写入成功后才记录成功下发时间，失败保留重试机会。
- 污点按 key 的含义判断，`NoExecute` 本身不作为节点不可达的充分条件。
- 读取状态失败时报告检查错误，不能解释为全部健康。
- 健康检查模块通过标签与资源调谐模块交互，检测与实际恢复分别验收。

## 2. 核心流程

启动与退出流程：入口加载配置并创建 Checker → NewManager 校验并初始化管理器 → 入口调用 Run → 管理器根据运行模式组织内部调度 → 取消 context → 停止接收事件并清理资源 → Run 返回。

```text
定时检查链路：
Run 的单轮或定时触发
    → 获取受管 Pod 快照
    → 执行已启用的 Checker
    → 将 Node 异常映射到 Pod，按 Checker 配置顺序汇总并去重多个状态
    → 进入统一处理流程

外部事件链路：
外部调用 SubmitEvent
    → 有界队列
    → Run 的同一事件循环取出事件
    → processEvent 匹配节点名和 Pod 名并转换结果
    → 使用同一份 Pod 列表进入统一处理流程（不调用 Checker）

统一处理流程：
检查结果或事件转换结果
    → 按顺序匹配处理策略
    → 清理过期记录并刷新本轮命中时间
    → 检查各动作的累计命中比例
    → 跳过冷却期内已成功下发的动作
    → 输出决策，或写入 Pod 处理标签
    → 写入成功后记录执行时间
```

输出包括本轮检查错误、Pod 异常、命中策略、比例检查结果，以及已下发、被比例拦截、被冷却跳过或执行失败的动作。

关键异常约定：受管 Pod 读取失败则终止本轮动作；单个 Checker 失败保留错误，其他 Checker 的成功结果仍可处理；未命中策略则不写标签；超过比例上限只暂停对应动作，不自动转为人工管理。

## 3. 模块划分与接口

### 3.1 模块职责

| 模块 | 职责 | 主要交互 |
| --- | --- | --- |
| 运行入口与配置 | 加载配置、初始化 Kubernetes 客户端、控制单次或周期运行 | 通过 NewManager 创建 Manager，并调用 Run |
| 受管资源读取 | 按统一过滤条件读取 Pod，提供节点映射和标签快照 | 为 Checker、策略和比例计算提供一致的受管集合 |
| Checker | 内置状态检查、外部 HTTP 检查 | 返回标准化异常及错误，不直接修改 Pod |
| 策略匹配 | 根据异常状态和 Pod 标签选择第一条命中策略 | 输出 Pod 与处理动作的对应关系 |
| 范围与去重控制 | 维护累计命中记录和成功下发记录 | 决定动作是否可以下发，不负责 Kubernetes 写入 |
| 动作标记 | 修改健康处理标签或人工管理标签 | 成功后反馈给 Manager，失败时保留可重试状态 |
| Manager | 串联检查、接收事件、汇总结果并管理运行生命周期 | 同一循环串行处理定时检查和事件，统一维护时间记录与动作决策 |

### 3.2 Manager 对外接口

接口与实现结构见 [manager.go](../controller/healthcheck/manager.go)，Checker 约定见 [checker.go](../controller/healthcheck/checker.go)。计划记录行为与验收要求，具体签名以代码为准。

| 接口 | 行为约定 |
| --- | --- |
| NewManager | 校验当前阶段所需配置和 Checker，初始化 Manager，不启动后台协程 |
| Run | 无返回值，阻塞运行；单次模式完成一轮后返回，周期模式处理定时检查及队列事件；context 取消后清理并退出，每个 Manager 由调用方启动一次 |
| SubmitEvent | 将事件提交到有界队列，成功只表示入队，不表示处理完成 |

SubmitEvent 使用有界队列，Run 启动前可以入队。队列满时等待空位或调用方 context 取消。Run 停止后队列仍可接收事件，调用方须随运行结束停止提交。已入队事件后续处理失败时通过报告和日志表达，不作为 SubmitEvent 的返回值。

Manager 为对外接口，私有结构 manager 实现该接口。NewManager 保存 Checker 列表和配置，并校验 CheckInterval：零值默认一分钟，负值返回错误。Run 串行处理定时检查与外部事件。SubmitEvent 将事件加入容量为 100 的队列；队列满时等待空位，提交方取消 context 时返回错误。

runOnce 并发调用 Checker 并汇总异常。processEvent 使用 Event.EKSNodes 中的 Node 名称和 Event.ClusterNodes 中的 Pod 名称匹配查询到的 Pod，同时命中时采用节点状态。两条链路共用策略匹配、累计比例检查、冷却去重、动作标签写入和 Webhook 通知。当前 Pod 列表按名称索引，受管范围过滤和入口的 Kubernetes 客户端注入仍待接入。

### 3.3 目录与实施顺序

复用项目根目录的 `go.mod`，启动入口为 `cmd/controller/main.go`，健康检查实现放在 `controller/healthcheck`，包名为 `healthcheck`。先在该包内完成必要职责，随实现需要拆分文件。

公共配置定义在 [controller/config](../controller/config/config.go)，包含中间件类型及集群白名单、黑名单；当前仅定义类型，匹配逻辑与加载注入后续补充。检查间隔等专用配置继续保留在 healthcheck.Config 中。

实施顺序：最小 Manager 调用链 → 内置 Checker → 外部 Checker → 周期调度与事件接入 → 策略匹配 → 比例保护与动作去重 → 动作标记 → 资源调谐联调。后续处理能力接在 Manager 的检查与事件转换之后，Checker 始终只返回检查结果。

## 4. 阶段一：管理器初始化、启动与单次调度可运行

本阶段流程：入口准备配置和测试 Checker → NewManager 校验并初始化 → 入口调用 Run → 管理器单次调用内部 runOnce → 汇总并输出检查结果 → Run 返回。本阶段不依赖 Kubernetes 或外部 HTTP 服务。

### 4.1 定义接口与结果

- [ ] 在 `controller/healthcheck` 定义统一 Checker 接口，提供检查器名称及接收 context 的检查方法；异常和检查错误分别表达。
- [ ] Checker 使用 map[string]Status 表达异常，Manager 汇总为 map[string][]Status，键均为 Pod 的 namespace/name；检查来源通过 Checker 名称记录，错误单独返回，区分无异常、检查失败和部分结果。
- [ ] 定义固定结果和失败结果的测试 Checker，用于验证接口及调用流程，不接入生产配置。

### 4.2 初始化管理器

- [ ] 在 NewManager 中注入 Checker 列表和运行配置，验证当前模式需要的参数；空列表、无效 Checker 或重复名称返回明确错误。
- [ ] 保存独立的 Checker 列表及配置，初始化未运行状态；构造过程不执行检查、不创建定时器，也不启动后台协程。
- [ ] 保留当前 Manager 接口与私有 manager 结构，单次调度、生命周期状态和结果汇总所需字段随本阶段补齐。

### 4.3 从入口启动管理器

- [ ] 在 `cmd/controller/main.go` 准备单次运行配置和测试 Checker，调用 NewManager，初始化失败时报告错误并退出。
- [ ] 启动逻辑直接放在 main 中，初始化失败以非零状态退出，退出前显式清理信号监听上下文。
- [ ] 在入口创建可取消的 context，通过独立协程调用 Run，使主流程可以继续启动其他组件；使用完成通道等待管理器退出，Run 不返回错误。
- [x] 每个 Manager 由启动入口调用 Run 一次。
- [ ] 单次模式完成一轮后返回；检查失败时保留可用报告并记录错误，正常取消时完成清理后退出。

### 4.4 管理器内部单次调度

- [x] runOnce 并发调用注入的 Checker，传递运行 context，等待全部检查结束后将汇总 Map 交给 processStatuses，自身不返回状态。
- [x] 各 Checker 先写入各自的结果位置，等待完成后按配置顺序汇总为 map[string][]Status，同一 Pod 保留不同状态并去重，不受完成先后影响。
- [ ] 在 processStatuses 中补齐报告或后续处理；当前仅接通调用入口，输出时按 Pod 键排序，不依赖 Map 遍历顺序。
- [x] 单个 Checker 失败时记录来源及错误日志，保留其部分结果和其他 Checker 的成功结果，不中止本轮汇总。
- [ ] 并发检查共享运行 context，取消后等待已启动的 Checker 响应取消并返回；本阶段不添加恢复动作。

### 4.5 阶段验收

- [ ] 单独调用 NewManager 不会触发 Checker；无效初始化参数明确报错，不产生后台任务。
- [ ] 不连接 Kubernetes 即可从入口完成初始化、Run 启动、单次调度、结果输出和退出。
- [x] 注入测试 Checker，验证并发启动、等待所有检查结束、context 传递，以及单个失败不阻止其他检查。
- [ ] 在状态处理逻辑接入后验证同一 Pod 的多状态保留与去重、部分结果保留及各轮 Map 独立性。
- [ ] 验证运行中取消，调用方能够通过完成通道确认退出。

## 5. 阶段二：接入内置 Checker

本阶段流程：初始化 Kubernetes 客户端 → Manager 调用 BuiltinHealthChecker → 读取受管 Pod、节点和磁盘检测结果 → 汇总输出。

### 5.1 接通 Kubernetes 状态读取

- [ ] 在根 Go module 中选择兼容的 Kubernetes 客户端与 controller-runtime 版本，复用已有 `go.mod`，不在 `controller` 中初始化嵌套 module。
- [ ] 支持从 kubeconfig 或集群内配置创建客户端，连接失败时返回可定位的错误。
- [ ] 增加中间件类型及可选集群过滤配置，确定受管范围；本阶段仅申请 Pod、Node 的读取权限。
- [ ] 实现 `BuiltinHealthChecker`，接入阶段一的统一接口及 Manager，返回结果不携带写入副作用。
- [ ] 按中间件标签和集群过滤条件读取受管 Pod，保存本轮快照；无受管 Pod 时返回空结果。
- [ ] 读取工作节点，识别 `Ready=False`、`Ready=Unknown`，以及 `NetworkUnavailable`、`DiskPressure`、`MemoryPressure`、`PIDPressure` 为 True 的状态。
- [ ] 根据污点 key 识别 `node.kubernetes.io/not-ready`、`node.kubernetes.io/unreachable`；自定义 `NoExecute` 污点不直接归为节点不可达。
- [ ] 通过 `pod.Spec.NodeName` 将异常 Node 映射到受管 Pod；未调度的 Pod 不凭空归为节点故障。
- [ ] 返回 Pod 到 Status 的 Map，需要的 Node 及来源信息通过日志补充；读取失败时报告错误，不将失败作为健康结果。

### 5.2 读取磁盘检测结果

- [ ] 定义磁盘异常注解 key 和取值，使用本地常量维护，并提供检测组件写入结果的样例。
- [ ] 将只读、无可用块、读写失败、延迟异常及检测程序错误等值转换为稳定的异常状态；区分磁盘故障和检测失败。
- [ ] 缺少注解不生成磁盘异常；未知取值记录提示，不推断未定义的处理动作。
- [ ] 支持按配置读取扩展 Node Conditions，例如 KernelDeadlock、HasIOError 和 FilesystemError，只有明确的异常值才生成结果。

### 5.3 阶段验收

- [ ] 使用客户端测试数据分别构造正常 Node、Ready=False、Ready=Unknown 和压力状态，验证只输出受影响的受管 Pod。
- [ ] 验证同名跨 namespace 的 Pod、未调度 Pod、不符合过滤条件的 Pod，以及自定义 NoExecute 污点的行为。
- [ ] 在本地测试集群中运行一次检查，能够列出检查范围并正常退出；读取权限不足时明确失败。
- [ ] 为样例 Pod 写入磁盘异常注解，Manager 输出对应状态；同时存在节点异常时优先返回磁盘状态，移除注解后返回仍存在的节点异常。

## 6. 阶段三：接入外部 Checker

本阶段流程：Manager 调用已启用的两种 Checker → 获取 Kubernetes 状态与外部 HTTP 结果 → 统一汇总输出。

### 6.1 实现并接入 WebhookHealthChecker

- [ ] 定义外部 HTTP 响应的最小契约，分别表达 Node 和 Pod 异常；Pod 目标包含 namespace/name，避免跨 namespace 歧义。
- [ ] 实现带请求上下文和超时的 HTTP GET，处理非成功状态码、空响应、非法 JSON 和结构校验失败。
- [ ] 仅保留当前受管范围内的 Pod 异常；Node 异常通过本轮快照展开为受影响 Pod。
- [ ] 用简单工厂按配置注册、启用或关闭两种 Checker，将实例注入已有 Manager；未知类型或未启用任何 Checker 时拒绝启动，实际入口不注册测试桩。
- [ ] 复用 Manager 的合并与错误汇总逻辑，将外部响应转换为统一结果；HTTP 请求失败时保留其他 Checker 的结果，并报告本轮检查不完整。

### 6.2 阶段验收

- [ ] 用测试 HTTP 服务返回节点异常、Pod 异常及二者重叠的数据，验证映射、范围过滤和去重结果。
- [ ] 同时启用两种 Checker，验证不同 Pod 的结果均被保留；同一 Pod 的不同状态均保留、相同状态去重，实际入口可以独立启用或关闭任一 Checker。
- [ ] 模拟 HTTP 超时、非成功状态码和非法响应，验证内置检查仍能输出，报告带有对应来源的错误信息。

## 7. 阶段四：管理器内部周期调度、事件接入与停止

本阶段流程：Run 的定时触发或 SubmitEvent 入队 → 同一循环调用 runOnce 或 processEvent → 交给共用策略流程 → 接收取消信号并退出。节点事件用于匹配 Pod，跳过 Node 健康标签写入。

### 7.1 初始化周期运行资源

- [ ] 在 NewManager 中补齐周期、Checker 超时和事件队列容量的配置校验，确定默认值；周期默认每分钟一次，有效周期、超时及容量均大于零。
- [x] 由 NewManager 创建有界队列，Run 创建定时器，退出时停止定时器。
- [ ] 入口按配置选择单次或周期模式，Run 保持阻塞，事件生产者由入口统一管理，不在构造函数中隐式启动。

### 7.2 管理器内部调度

- [x] 在 Run 的同一循环中处理定时触发、队列事件和 context 取消，分别调用私有 runOnce、processEvent 或进入退出流程。
- [ ] 明确周期模式首次检查在一个检查间隔后触发，单次模式立即执行一轮；外部事件就绪后可进入处理，无须等待下一次定时检查。
- [ ] 检查轮次与事件处理串行执行，每次处理完成后才取下一项，单轮内部的多个 Checker 并发执行；某轮耗时超过周期时不启动重叠轮次，不累计无限定时任务。
- [ ] 为每个 Checker 派生带超时的 context，Kubernetes 与 HTTP 调用均传递该 context；某个 Checker 失败不影响其他并发检查，Manager 已被取消时等待本轮退出。
- [ ] 定时检查和事件处理失败时记录错误并继续服务，不因单个输入失败退出整个周期循环。
- [ ] 每轮输出异常及检查错误，不沿用上一轮已经消失的异常；无异常与检查失败分别表达。

### 7.3 实现 SubmitEvent 与内部事件处理

- [x] Event 包含 EKSNodes 和 ClusterNodes，分别以 Node 名称和 Pod 名称为键记录异常；提交时拒绝空名称或空状态。
- [x] 实现 SubmitEvent，使用容量为 100 的内部队列；队列满时等待空位或调用方 context 取消。
- [x] 由调用方管理 Run 与事件生产者的生命周期，队列在 Manager 构造后即可接收事件。
- [x] SubmitEvent 成功后由 Run 取出并调用私有 processEvent；保留外部队列顺序，不额外导出事件执行方法。
- [ ] processEvent 获取当前受管范围，将 Node 事件映射到受管 Pod，过滤范围外对象并转换为统一结果；直接使用事件状态，不再次调用 Checker。
- [x] 事件转换后进入共用的策略和动作链路，SubmitEvent 返回成功表示已入队。
- [ ] 使用本地事件生产者模拟输入，不实现 Watch 网络连接、重连或持久化；周期运行取消时同步停止本地生产者。

### 7.4 取消与资源清理

- [ ] 退出时取消运行 context 和事件生产者的提交 context，停止检查、事件处理和入队等待。
- [ ] 释放定时器后 Run 返回；队列中尚未消费的事件仍为待处理。
- [ ] 在入口通过完成通道等待 Run 和其他受管协程退出；运行中的检查或事件错误由管理器记录。

### 7.5 阶段验收

- [ ] 验证 NewManager 只初始化、Run 才启动调度，周期模式首轮触发时机与单次模式符合约定。
- [ ] 连续运行多个周期，改变测试异常输入，验证报告随本轮结果变化；单个检查或事件处理失败不终止后续调度。
- [ ] 模拟单轮检查耗时超过周期，确认检查与事件处理不重叠，未累计无限定时任务；模拟单个 Checker 超时，确认其余 Checker 仍能运行。
- [ ] 通过 SubmitEvent 投递合法 Pod 和 Node 事件，确认进入同一循环处理、范围过滤正确且 Checker 未被事件链路调用。
- [ ] 验证启动前入队、队列满时取消提交和运行退出；SubmitEvent 不等待业务处理完成。
- [ ] 在 HTTP 请求阻塞及队列存在积压时取消 Run，确认请求与生产者退出，未处理事件不被标记为成功；对生命周期和并发提交执行竞态检测。

## 8. 阶段五：匹配策略并输出动作决策

本阶段流程：检查汇总或事件转换结果 → 共用策略匹配 → 输出处理动作及原因，仍不写入资源。

### 8.1 实现状态与条件匹配

- [ ] 定义策略配置：异常状态、可选条件和处理动作；本轮支持 Migrate、ReCreate、InPlaceUpdate、Manual、Automatic，未知动作拒绝启动。
- [ ] 实现简单状态匹配：Pod 的任一异常状态命中策略状态列表即可匹配，仍按第一条匹配策略选择一个动作。
- [ ] 实现条件状态匹配：先匹配异常状态，再要求该条目的所有附加条件成立；多个条件状态条目之间按 OR 组合。
- [ ] 简单状态列表与条件状态列表按 OR 组合；记录简单状态会绕过附加条件，示例中避免意外扩大匹配范围。
- [ ] 支持 nodeset、cluster_name、cluster_id、pod_name 条件，以及 exact、prefix、keyword、whitelist、blacklist 匹配方式；标签缺失时不匹配，未知字段或方式拒绝启动。
- [ ] 按配置顺序选择第一条命中策略；输出命中状态、策略及动作，没有命中时输出无动作原因。
- [ ] 在 processStatuses 中实现共用策略匹配，runOnce 和 processEvent 将状态交给该入口，相同状态和目标使用相同匹配规则。

### 8.2 阶段验收

- [ ] 用磁盘只读、节点不可达及需要人工处理的样例，验证动作选择符合配置。
- [ ] 验证同一 Pod 命中多条策略时只采用第一条；条件失败、标签缺失或未命中时不产生动作。
- [ ] 验证 AND、OR、白名单和黑名单边界；相同输入重复运行得到相同决策。
- [ ] 通过检查结果和 SubmitEvent 分别输入相同状态，确认两条链路采用一致策略，事件输入不触发额外检测。

## 9. 阶段六：累计比例保护与执行去重

本阶段流程：策略命中 → 清理窗口记录 → 累计比例检查 → 冷却判断 → 用测试动作执行器验证成功与失败。

### 9.1 明确窗口与统计约定

- [ ] 增加策略的 Threshold 和 ReconcileInterval 配置；比例为 0—1 的有限数值，窗口必须大于零，时间使用 Go duration 格式。
- [ ] 本轮每种动作只允许配置一份策略，通过状态和条件列表组合规则；拒绝同一动作配置多个不同阈值或窗口，避免共享记录含义不清。
- [ ] 定义两份内存记录：Pod namespace/name + action 的最近命中时间，以及相同键的最近成功下发时间；ReconcileInterval 同时作为统计窗口和动作冷却时间。
- [ ] 注入可控制的时钟，明确记录在“当前时间减记录时间大于窗口”时过期，恰好等于窗口时仍有效。
- [ ] 定义累计比例为窗口内命中过该动作、且仍在当前受管集合内的不同 Pod 数除以当前受管 Pod 总数；不按单个业务集群或 NodeSet 单独计算。

### 9.2 接通保护与去重

- [ ] 每轮先清理过期及已离开受管范围的记录，再刷新本轮命中时间；持续命中只刷新时间，不重复计数。
- [x] 在执行去重前刷新全部匹配对象的命中时间，即使动作被拦截或尚未下发，也属于命中过策略的对象；状态指向不存在的 Pod 时不计入。
- [x] 独立判断累计比例，严格大于 Threshold 时从待处理分组移除该动作，等于阈值允许保留；空 Pod 集合暂停动作，避免除零。
- [x] 在阈值判断后检查 podActionExecutedAt，跳过冷却期内相同 Pod 名称与动作的组合，再执行剩余动作。
- [ ] 使用测试执行器串起决策、执行结果和记录更新；仅执行成功才写入成功下发时间，失败保留下一轮重试机会。
- [ ] 比例拦截只暂停对应动作，不自动替换成人工管理；每轮即使没有新异常也清理过期记录。
- [ ] 检查与事件链路复用同一份累计命中和执行记录，统一在 Run 循环内更新，避免两个入口绕过保护。

### 9.3 阶段验收

- [ ] 使用 100 个受管 Pod、10 分钟窗口、10% 阈值：先命中 6 个，再新增 5 个，确认第二轮该动作全部被比例拦截；时间和比例为验收样例。
- [ ] 验证同一 Pod 重复异常只计一次，10/100 允许执行、11/100 被拦截，以及窗口到期、持续刷新、Pod 离开范围和空集合的行为。
- [ ] 验证相同 Pod 和动作在成功后被冷却跳过，失败后下一轮可以重试，不同动作不共享执行记录。
- [ ] 用可控时钟完成时间边界验证，不通过真实长时间等待验收；重建 Manager 后确认记录丢失并记录该限制。

## 10. 阶段七：写入动作标签

本阶段流程：Run 获取检查或事件转换结果 → 共用策略匹配与保护判断 → 写入 Pod 标签 → 成功后记录执行时间。复用阶段四的统一事件循环。

### 10.1 实现动作标记

- [x] Migrate、ReCreate、InPlaceUpdate 分别向 `health-status` 写入同名动作值；Manual 写入 `manual-management=true`；Automatic 写入 `manual-management=false`。
- [ ] 明确 Automatic 只恢复自动管理资格，不表示实例已恢复健康。
- [x] 已处于人工管理状态的 Pod 不再下发 Migrate、ReCreate、InPlaceUpdate，只有明确匹配 Automatic 才恢复自动管理；检查结果仍保留异常信息。
- [ ] 使用局部 Patch 修改目标标签，保留其他字段；基于最新对象确认 UID，避免将旧快照动作施加到同名替换对象；冲突重新读取后判断，NotFound 记录为目标已消失。
- [x] 标签更新成功或目标已处于相同请求状态时，记录请求已下发；更新失败不写成功记录，并输出 Kubernetes 错误原因。
- [ ] 提供 dry-run 模式，只输出异常、动作和拦截原因，不写标签，也不写成功下发记录。
- [ ] 将动作处理接到检查与事件共用的策略链路之后，保持 Checker 只读；输出区分异常命中、比例拦截、冷却跳过、已下发、dry-run 和失败。

### 10.2 阶段验收

- [ ] 在本地测试集群中创建带受管标签的样例 Pod，注入磁盘异常注解；运行后通过 kubectl 确认目标动作标签，其余字段保持不变。
- [ ] 验证 Manual、Automatic、重复检查、比例拦截和 dry-run；只有应下发的对象发生标签变化。
- [ ] 模拟 Patch 冲突、权限不足、对象删除及同名对象替换，验证不误写新对象，失败后仍可重试。
- [ ] 通过周期检查与 SubmitEvent 分别触发动作，验证共用保护和去重记录；入队、标签已写入及实际重建完成分别表达。
