# Agent 实现计划

## 1. 目标与范围

按业务流程逐步实现 Go Agent 服务，从“创建任务接口接收目标并保存 Task”开始，每一步需要什么，再补充相应类型、接口、存储、配置和测试。模块划分用于明确职责，不作为实施顺序，无需先建立完整配置系统或全部领域模型。事项默认未完成，实施时核对代码和验收证据后再勾选。

首个里程碑是完成“创建任务 → 启动 Run → 准备上下文 → 调用模型 → 保存并查询答案”。随后接入工具循环和取消，再逐步增加审批恢复、历史与压缩、故障恢复和委派。

## 2. 按流程推进

```text
创建 Task → 创建并启动 Run → 准备上下文 → 调用模型
                                           ├→ 无工具调用：保存答案并完成
                                           └→ 有工具调用：执行并保存结果 → 再次调用模型

执行期间：取消 → 通知停止 → 状态与资源收尾
需要确认：审批／输入 → 暂停 → 提交决定 → 恢复执行
后续增强：历史与压缩 → 故障恢复 → 委派 → 外部扩展
```

| 阶段 | 优先级 | 主题 | 前置依赖 | 主要验收结果 |
| --- | --- | --- | --- | --- |
| 01 | P0 | [创建任务](phase-01-create-task.md) | 无 | 接收目标、保存 Task，重启后可查询 |
| 02 | P0 | [创建并启动 Run](phase-02-start-run.md) | 01 | 发送消息后创建 Run，登记后台执行并防止重复启动 |
| 03 | P0 | [准备运行上下文](phase-03-prepare-context.md) | 02 | 解析工作区和模型，构造可直接使用的消息 |
| 04 | P0 | [调用模型并完成运行](phase-04-model-response.md) | 03 | 真实模型调用后保存答案，客户端查询到最终结果 |
| 05 | P0 | [执行工具并继续循环](phase-05-tools.md) | 04 | 工具结果反馈模型，完成实际文件或命令任务 |
| 06 | P0 | [取消执行与清理](phase-06-cancel.md) | 02、04、05 | 活跃和非活跃 Run 可取消，无残留进程和重复收尾 |
| 07 | P1 | [审批、输入与恢复](phase-07-approval.md) | 05、06 | 暂停后继续剩余调用，已完成工具不重复执行 |
| 08 | P1 | [历史、附件与上下文压缩](phase-08-context.md) | 04、07 | 支持多轮任务和长上下文，工具消息保持配对 |
| 09 | P1 | [故障恢复与执行协调](phase-09-recovery.md) | 06～08 | 崩溃可恢复，旧执行不能继续写入，不盲目重放副作用 |
| 10 | P2 | [多 Agent 委派](phase-10-delegation.md) | 07～09 | 子任务受预算、并发和父子生命周期管理 |
| 11 | P2 | [扩展与产品能力](phase-11-extensions.md) | 按功能依赖 | 按需接入 Skills、MCP、搜索、记忆、调度与界面 |

主线按上述顺序推进。Shell 工具与实际沙箱一起在阶段 05 交付。首版请求固定到同一执行器；若必须一开始支持多执行器接管，应将阶段 09 的租约和写入凭证随阶段 02 引入。

## 3. 模块与事项组织

模块边界、依赖关系及跨阶段职责见 [模块设计](modules.md)。各阶段按“入口 → 业务处理 → 存储或执行 → 返回结果 → 验收”拆事项，并标明涉及模块；使用 `P阶段号-事项号` 作为事项编号。

| 标记 | 含义 |
| --- | --- |
| `- [ ]` | 待实现或尚未完成验收 |
| `- [x]` | 已有实现，并有对应验收证据 |
| P0 | 跑通首版实际执行链路所必需 |
| P1 | 暂停恢复、长任务和可靠运行所必需 |
| P2 | 多 Agent 与产品扩展，按需求交付 |

实施时一次选取一个可独立验证的事项或一组紧密关联事项。类型、接口和配置在首次被实际调用时定义；提交说明记录事项编号和验证结果，不以“接口已定义”代替“能力可用”。

## 4. 里程碑

| 里程碑 | 覆盖阶段 | 演示场景 |
| --- | --- | --- |
| M1：任务可执行 | 01～04 | HTTP 创建任务、启动 Run，模型回答后可查询答案 |
| M2：工具闭环可控 | 05、06 | 读取、修改文件和运行命令，结果反馈模型，并可取消 |
| M3：可交互长任务 | 07、08 | 审批后继续，支持输入、附件、历史、裁剪与摘要 |
| M4：可靠执行 | 09 | 执行中重启、重复恢复、租约丢失和记录修复 |
| M5：委派与扩展 | 10、11 | 主 Agent 委派子任务，并按需使用外部工具和管理界面 |

## 5. 贯穿各阶段的约定

- 模型输出的工具调用先持久化，再启动工具；结果先可靠保存，再进入下一轮模型调用。
- 数据库负责业务状态、审批与授权、可查询事件；JSONL 负责消息与工具执行事实。明确关联标识和顺序，不假设两者能在同一事务内提交。
- 工具调用与结果按调用 ID 配对；等待审批不是执行结果，拒绝则需要形成可反馈模型的结果。
- 用户控制操作与执行器写入分别授权；租约启用后，执行器写入必须检查持有者、版本及有效期。
- 文件和联网的实际限制落实在访问层与沙箱中；Shell 工具随沙箱一起交付。
- 状态更新、取消、恢复及启动必须考虑并发；终态不能被旧执行恢复为运行中。
- 阶段 02 起保证后台执行的基本清理，阶段 06 再接入用户取消入口，不能在此之前泄露执行资源。
- 首版串行执行一批工具，后续仅对有明确安全条件的独立调用引入并发。
- 配置表区分已实现值和建议值；[配置文档](../configuration.md) 中的规划值不自动视为已经生效。
- 各阶段提供最小端到端验证，并对错误、取消和中断路径补充有意义的测试。
