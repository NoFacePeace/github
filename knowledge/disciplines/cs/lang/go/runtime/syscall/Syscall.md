# 系统调用

系统调用是用户态程序请求操作系统内核服务的入口，例如读取文件、创建 socket、注册 epoll 监听项。Go 的系统调用封装除了传递参数，还可能通知运行时处理 G、M、P 的状态变化，使阻塞在内核中的线程不会长期独占 Go 的执行资源。

本文以本地 Go 1.26.3 的 `src/runtime/proc.go` 为主要核对依据，并区分传统 `_Psyscall` 模型。运行时内部函数、状态和交接协议会随版本变化。

## 1. 系统调用与阻塞

系统调用不一定阻塞，也没有统一的“快调用”和“慢调用”分类。同样是文件读取，数据在页缓存中时可能很快返回，需要等待磁盘时则可能耗时较长。

| 场景 | 说明 |
| --- | --- |
| 普通磁盘文件读写 | 通常通过同步系统调用完成，可能阻塞执行它的 M |
| 非阻塞 socket 读写 | 未就绪时返回 `EAGAIN`，Go 可以挂起 G，等待网络轮询器通知 |
| `epoll_ctl` | Linux 系统调用，用于添加、修改或删除监听项，通常很快返回 |
| `epoll_wait` | Linux 系统调用，用于获取就绪事件；超时为零时立即检查，否则可能等待 |

是否进入内核与如何交接 P 是两个问题。底层系统调用指令本身不会替 Go 调度器管理 P。

## 2. 进入系统调用

### 2.1 普通调用路径

受运行时管理的普通系统调用通常遵循以下流程：

```text
G 调用系统调用封装
    ↓
entersyscall / reentersyscall
    → 保存调用现场，供 GC 和栈回溯使用
    → 将原 P 的引用记录到 M.oldp
    → 将 G 从 _Grunning 转为 _Gsyscall
    → 按条件唤醒休眠中的 sysmon
    ↓
执行系统调用指令，进入内核
    ↓
内核返回
    ↓
exitsyscall，确认或重新取得 P 后继续执行
```

进入内核之前，Go 已建立允许运行时收回 P 的状态。G 在系统调用期间仍与执行它的 M 关联；即使 P 被交给其他 M，原系统调用也可以继续在内核中执行。

### 2.2 P 的管理与版本差异

传统实现会在进入普通系统调用时解除 M 与 P 的绑定，并将 P 标记为 `_Psyscall`，供快速返回时尝试重新取得。这个 P 尚未直接进入空闲池，但可以被运行时收回。

本地 Go 1.26.3 的实现采用了不同的交接协议：进入 `_Gsyscall` 后，M 可能仍保有 P 的关联，但已经不能假设 P 始终归自己使用；其他运行时路径可以协调取走 P。退出系统调用时，代码先检查 `M.p` 是否仍存在，再处理失去 P 的情况。因此，不能把“进入时总会解绑并设置 `_Psyscall`”当作所有版本通用的代码流程。

两种实现的共同目标是：系统调用中的 M 不执行普通 Go 代码，必要时其 P 能被其他 M 使用。

### 2.3 oldp 的含义

`M.oldp` 记录进入系统调用时原 P 的引用，供退出路径识别和尝试重新获取。它不是独占凭证，不保证原 P 没有被其他 M 使用，也不保证返回后一定使用同一个 P。

### 2.4 主动交出 P 与底层调用

`entersyscallblock` 是主动交出 P 的系统调用进入路径，供明确需要相应阻塞处理的调用方使用；这不是运行时先计时、判断调用“很慢”后才选择的分支。

`RawSyscall` 等底层调用不会自动完成与普通封装相同的 `entersyscall` / `exitsyscall` 处理。运行时内部也有直接执行系统调用的封装，调用方需要遵守相应约束，不能据此认为所有系统调用都会以相同方式处理 P。

## 3. sysmon 如何参与

### 3.1 周期性收回 P

具体判断条件与交接流程参见[Sysmon P 回收](../sysmon/Retake.md)。

Sysmon 通过监控循环中的 `retake` 检查系统调用等状态，在满足条件时协调收回 P，让其他 M 可以执行 Go 代码。

这不是终止或打断系统调用，也不是强制让内核中的 G 立即恢复执行。被收回的是 Go 的调度资源 P，系统调用仍由原 M 继续执行。

收回条件涉及调度进度、系统调用进度和工作需求等状态，不能简化成“所有系统调用超过固定毫秒数就收回 P”。

### 3.2 进入时可能唤醒 sysmon

休眠条件、超时计算及通知唤醒过程参见[Sysmon 休眠](../sysmon/Sleep.md)。

不是每次进入系统调用都发送通知。Go 1.26.3 的 `reentersyscall` 会判断 sysmon 是否正在长休眠：

```go
if sched.sysmonwait.Load() {
    systemstack(entersyscallWakeSysmon)
}
```

`entersyscallWakeSysmon` 加锁后再次确认状态，再通过 `notewakeup(&sched.sysmonnote)` 唤醒它。

这里判断的是“sysmon 是否休眠”，而不是“当前系统调用会不会很慢”。唤醒的目的是恢复监控；是否收回 P，仍由后续监控逻辑判断。sysmon 正常运行时，通常依靠周期性检查即可。

## 4. 返回与快慢路径

系统调用返回后，M 必须具备可用 P，才能继续执行普通 Go 代码。

| 情况 | 后续行为 |
| --- | --- |
| 原 P 仍归当前 M 使用，或能按协议重新取得 | 恢复原 G，继续执行 |
| 原 P 不可用，但取得其他可用 P | 使用取得的 P 继续执行 |
| 无法取得 P | 将 G 转为可运行并交回调度，M 等待后续安排 |

“快路径”和“慢路径”是对代码分支的称呼，实际分支由 P 是否可用等条件决定，不是根据系统调用耗时与某个阈值比较后选择。耗时短的调用也可能失去原 P。

具体返回调度过程参见系统调用返回。其中内部辅助函数名称应以对应 Go 版本为准。

## 5. 与网络轮询的区别

网络轮询器 可以让业务 G 在 I/O 未就绪时登记等待并通过 `gopark` 挂起，M 随后调度其他 G。挂起 G 本身不要求 M 立即释放 P。

调度器中的阻塞网络轮询则发生在当前 M 查找后没有取得工作、满足轮询条件时：M 先主动释放 P，再执行 `netpoll(delay)`。Linux 下，其底层可能阻塞在 `epoll_wait`。

| 对比 | 普通受管理的系统调用 | 调度器阻塞网络轮询 |
| --- | --- | --- |
| P 的处理 | 原 P 可能暂时保有，运行时可协调收回；具体协议随版本变化 | 等待之前已主动释放 P |
| `oldp` | 记录原 P 的引用 | 不依靠系统调用进入协议中的 `oldp` 暂留 P |
| 是否等 sysmon 收回 P | 可能由 sysmon 等路径参与收回 | 不需要，P 已主动释放 |
| 返回后的执行条件 | 确认或重新取得可用 P | 重新取得可用 P 后才能执行普通 Go 代码 |

非阻塞 `netpoll(0)` 不属于上述阻塞等待路径，可以在持有 P 时立即检查事件；sysmon 自身不持有 P。

## 6. 源码入口

- `src/runtime/proc.go`：`entersyscall`、`reentersyscall`、`entersyscallblock`、`exitsyscall`、`retake` 及 sysmon 唤醒逻辑。
- `src/runtime/runtime2.go`：G、M、P 的结构及状态定义。
- `src/syscall`、`src/internal/runtime/syscall`：系统调用封装及平台相关实现，实际目录组织依版本而定。
- Go 1.26.3 的 proc.go：本文主要核对版本的调度与系统调用协议。
