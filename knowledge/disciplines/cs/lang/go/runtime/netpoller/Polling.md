# 网络轮询

网络轮询是 Go 运行时通过操作系统事件接口获取 I/O 就绪事件，再找出需要唤醒的 goroutine 的过程。Linux 下，核心调用为 `netpoll(delay)`，底层通过 `epoll_wait` 获取事件。本文按本地 Go 1.26.3 源码整理，具体条件与实现以所用版本为准。

## 1. 轮询在做什么

内核负责监测已注册 fd 的 I/O 状态，执行 `netpoll` 的 M 负责获取事件。这里的轮询不是 Go 持续遍历每个连接、逐个尝试读取。

```text
内核记录 fd 的就绪事件
    ↓
某个 M 调用 netpoll，通过 epoll_wait 获取事件
    ↓
从事件携带的信息定位 pollDesc
    ↓
根据可读、可写事件处理 rg、wg 等待状态
    ↓
收集需要唤醒的 G，返回调用方
    ↓
调用方将 G 交回调度，后续安排执行
```

如果事件先于 G 的等待到达，运行时也可以记录就绪状态，使后续等待路径不必真正挂起。网络轮询器不直接执行 G 的业务代码，也不代替 G 完成实际读写。

## 2. 非阻塞检查与阻塞等待

两种方式的条件与执行过程分别参见[非阻塞轮询](Nonblocking.md)和[阻塞轮询](Blocking.md)。

`netpoll` 的 `delay` 单位为纳秒，其含义如下：

| delay | 行为 |
| --- | --- |
| `0` | 立即检查已有事件，没有事件就返回 |
| 正数 | 最多按指定期限等待事件，平台会转换超时单位和精度 |
| `-1` | 不设置超时期限，等待事件或主动打断 |

因此，调用 `epoll_wait` 不等于一定阻塞。即使允许等待，已有事件也可能使它立即返回。

## 3. 调度器何时检查

### 3.1 工作窃取前的非阻塞检查

`findRunnable` 在前面的工作检查没有取得 G 后，可以在工作窃取前执行网络检查。Go 1.26.3 的条件为：

```go
if netpollinited() &&
    netpollAnyWaiters() &&
    sched.lastpoll.Load() != 0 &&
    sched.pollingNet.Swap(1) == 0 {
    // netpoll(0)，随后释放此路径的轮询资格
}
```

各条件分别表示：轮询器已初始化、存在网络等待者、没有阻塞轮询者，以及当前 M 取得这条路径的非阻塞轮询资格。

这一检查不要求距离上次轮询超过 10 毫秒，也不会为等待事件而释放当前 P。取得就绪 G 后，可以选择其中的 G 执行，并将其余工作交回运行队列。

### 3.2 没有工作时的等待

当前 M 查找后没有取得工作，准备休眠时，会协调释放 P、退出自旋并重新检查工作。在相应路径中，满足以下条件可以取得阻塞轮询资格：

- 网络轮询器已经初始化。
- 有网络等待者，或存在需要考虑的计时器期限。
- `sched.lastpoll.Swap(0)` 返回非零值，当前 M 成功取得资格。

随后根据下一次计时器期限计算 `delay`，调用 `netpoll(delay)`。此时 M 已主动释放 P，不需要等待 sysmon 再收回。

“没有工作”指当前 M 没有取得工作，不代表其他 M 没有在执行 G。准备等待时也可能计算出 `delay == 0`，因此进入这条路径不保证实际阻塞。

返回后，M 需要协调重新取得 P、处理就绪 G 或继续寻找工作；不能因为收到事件就直接无条件执行普通 Go 代码。

## 4. 其他轮询入口

| 入口 | 用途 |
| --- | --- |
| `sysmon` | 满足状态和时间条件时，以 `netpoll(0)` 兜底检查，避免工作 M 忙碌时长期没有获取网络事件 |
| `pollWork` | 后台工作检查是否出现值得让出执行资源的工作时，按条件检查网络事件 |
| `startTheWorldWithSema` | STW 结束时，非阻塞收集暂停期间已就绪的 G |

sysmon 的兜底路径通常要求距离记录的上次轮询超过约 10 毫秒，这不是所有 `netpoll` 调用共用的时间限制。

## 5. 多线程协调与主动打断

| 状态或函数 | 作用 |
| --- | --- |
| `sched.lastpoll` | 记录轮询时间，并通过零值协调阻塞轮询资格 |
| `sched.pollingNet` | 限制工作窃取前那条非阻塞检查路径的并发，不覆盖所有轮询入口 |
| `sched.pollUntil` | 记录当前阻塞轮询考虑的计时器期限 |
| `netpollBreak` | 主动打断轮询等待，例如需要更早处理计时器或重新检查工作时 |

负责阻塞轮询的 M 可以变化，不固定绑定某个专用线程。一个 M 可以等待多个 fd 的事件，其他运行时路径也可以在满足条件时执行非阻塞检查。

## 6. 与业务 G 等待的区别

业务 G 在读写返回 `EAGAIN` 后登记到 `pollDesc` 并挂起；M 则转入调度，可能继续执行其他 G。这个动作不要求原 M 立即调用阻塞的 `epoll_wait`。

后续由某个进入轮询路径的 M 获取事件，找到等待的 G。G 获得运行机会后，再次尝试实际读写。业务等待与 M 的轮询等待是两个不同层次的过程。

## 7. 源码入口

- `src/runtime/proc.go`：`findRunnable`、`pollWork`、`sysmon` 及轮询资格协调。
- `src/runtime/netpoll.go`：等待状态、`netpollready` 及 G 的收集。
- `src/runtime/netpoll_epoll.go`：Linux 下的事件注册、事件获取和主动打断。
