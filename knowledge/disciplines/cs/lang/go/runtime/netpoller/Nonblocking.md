# 非阻塞轮询

非阻塞轮询通过 `netpoll(0)` 检查已经就绪的网络事件，没有事件就返回，不为等待新事件而阻塞 M。Linux 下底层调用超时为零的 `epoll_wait`。本文按 Go 1.26.3 的主要路径说明，具体条件以所用版本为准。

## 1. 为什么检查

网络事件是可运行工作的来源之一。调度器在没有从队列取得工作时，可以先检查网络事件，再决定是否窃取工作或休眠；sysmon 等路径也可以提供额外的检查机会。

这不是遍历所有连接并逐个尝试读取，也不是反复忙等。内核负责记录事件，Go 运行时调用事件接口取回结果。

## 2. findRunnable 的调用条件

工作窃取前的网络检查需要前面的工作检查尚未取得 G，并满足：

```go
netpollinited() &&
    netpollAnyWaiters() &&
    sched.lastpoll.Load() != 0 &&
    sched.pollingNet.Swap(1) == 0
```

| 条件 | 含义 |
| --- | --- |
| `netpollinited()` | 网络轮询器已初始化 |
| `netpollAnyWaiters()` | 存在网络等待者 |
| `lastpoll != 0` | 没有 M 正承担阻塞轮询 |
| `pollingNet.Swap(1) == 0` | 取得这条非阻塞检查路径的资格 |

该路径在 `netpoll(0)` 返回后释放 `pollingNet` 资格。这个并发限制不覆盖所有网络轮询入口。

## 3. 检查后的处理

```text
满足检查条件
    ↓
netpoll(0)
    ├─ 没有就绪 G → 继续工作搜索
    └─ 有就绪 G
         → 协调等待者数量和 G 状态
         → 选择 G 返回，或将工作交回运行队列
```

运行时根据事件携带的信息找到 `pollDesc`，处理读写等待状态。事件先于等待到来时，也可能只记录就绪标记，而没有可立即唤醒的 G。

事件获取不直接执行读写；被唤醒的 G 获得调度机会后，才继续尝试实际操作。

## 4. P 的处理

`findRunnable` 中这条非阻塞检查路径保留当前 P，检查后可以继续搜索或安排执行，无需为了等待网络释放 P。

sysmon 本来就不持有 P，因此它执行 `netpoll(0)` 时没有 P 可以释放。是否持有 P 由调用上下文决定，不能只根据 `netpoll(0)` 推断。

## 5. 其他调用路径

| 调用方 | 检查场景 |
| --- | --- |
| `sysmon` | 轮询器已初始化、没有阻塞轮询者，且距记录的上次轮询超过约 10 毫秒时兜底检查 |
| `pollWork` | 后台工作检查是否需要让出执行资源时，按条件检查网络事件 |
| `startTheWorldWithSema` | STW 结束时收集暂停期间已就绪的 G |

这些路径有各自的条件和结果处理方式。“超过约 10 毫秒”是 sysmon 兜底检查的条件，不是所有非阻塞轮询共同的限制。

## 6. 与非阻塞 socket 的区别

非阻塞 socket 指读写系统调用暂时不能完成时返回 `EAGAIN`，不一直等数据或缓冲区空间；非阻塞轮询指立即检查已有事件，不等待新事件。

两者配合实现业务层的同步读写体验：G 先尝试操作，未就绪时登记等待，运行时获取事件后再安排它重试。socket 为非阻塞模式，不代表调用 `conn.Read` 或 `conn.Write` 的 G 永远不会等待。
