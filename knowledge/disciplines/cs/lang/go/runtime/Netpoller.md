# Netpoller

网络轮询器（netpoller）将操作系统的 I/O 事件机制接入 Go 调度器。对于受其管理的网络连接，goroutine 可以在 I/O 尚未就绪时挂起，并在事件到来后恢复调度，避免为每个等待中的连接长期占用一个操作系统线程。

## 1. 运行时中的定位

### 1.1 全局共享机制

netpoller 是同一个 Go 运行时内共享的 I/O 机制，由运行时函数、状态结构和操作系统事件设施共同组成。例如，Linux 下通常共享一个 epoll 实例，用于管理多个连接的事件；不同进程不共享这份运行时状态。

其状态分为两类：

- 全局状态：初始化状态、平台事件设施，以及轮询时间和轮询资格等协调信息。
- 每个连接的状态：通过 `pollDesc` 等结构记录读写等待、deadline 和等待中的 G。

### 1.2 与 G 和 M 的关系

netpoller 本身不是一个 G，也没有一个专门的业务 goroutine 持续执行它。调度器中的轮询通常由 M 在 `g0` 的系统栈上执行，`sysmon` 等运行时路径也可以调用轮询逻辑。

它不固定绑定某个 M。某个线程可以承担阻塞等待，但负责等待的线程可以变化；其他线程在适当路径上还可以执行非阻塞检查。

业务 G 在等待 I/O 时挂起，执行 netpoll 的 M 获取事件，调度器再安排就绪的 G 恢复执行。

## 2. 工作流程

以读取网络连接为例：

1. goroutine 尝试从连接读取数据。
2. 在非阻塞 I/O 模式下，如果暂时没有数据可读，运行时登记等待并挂起该 goroutine。
3. 操作系统事件机制报告连接可读，网络轮询器找出相关的等待 goroutine。
4. 调度器将其置为可运行，随后安排执行并再次尝试读取。

事件就绪不等于业务操作已经完成，被唤醒也不保证立即执行。运行时需要协调事件通知与挂起过程，避免事件发生在登记等待期间时丢失唤醒。

### 2.1 谁负责监测事件

操作系统内核负责监测 I/O 状态，执行 netpoll 的 M 负责获取事件。以 Linux 为例：

1. Go 将连接的文件描述符注册到 epoll。
2. 内核监测文件描述符，记录可读、可写等就绪事件。
3. 某个 M 调用 `epoll_wait` 获取事件，可以立即检查，也可以阻塞等待。
4. netpoll 根据事件对应的 `pollDesc` 找到等待的 G，并交回调度器。

因此，不需要为每个连接创建一个监听线程，也不是每个 M 都固定去调用 `epoll_wait`。

## 3. 与调度器的协作

网络轮询是调度器获取可运行 goroutine 的工作来源之一。调度器可以检查网络事件；缺少其他工作时，适当的线程还可以等待事件，并结合计时器等因素决定等待时间。

I/O 等待中的 goroutine 不在普通运行队列里持续轮转。事件到来后，相关 goroutine 才重新进入调度流程，具体入队方式取决于轮询路径及当前是否持有 P 等条件。

轮询器等待事件时仍可能占用一个操作系统线程，但该线程可以等待多个连接的事件，不需要为每个连接配置一个等待线程。

## 4. 轮询调用时机

以下按 Go 1.27.2 的 `src/runtime/proc.go` 整理。该版本是截至 2026 年 10 月 10 日的最新稳定版；后续版本可能调整具体条件。Linux 下，`netpoll()` 底层通过 `epoll_wait` 获取事件。

### 4.1 主要调用路径

| 时机 | 源码入口 | 条件与调用方式 |
| --- | --- | --- |
| 寻找可运行 G，准备工作窃取之前 | `findRunnable()` | 本地、全局队列未找到工作；轮询器已初始化、有网络等待者、没有阻塞轮询者，且取得该路径的非阻塞轮询资格时，调用 `netpoll(0)` |
| 找不到工作，准备休眠 | `findRunnable()` | 轮询器已初始化，有网络等待者或计时器期限，且取得阻塞轮询资格时，调用 `netpoll(delay)`；此时 M 已释放 P，并退出自旋状态 |
| 后台工作检查是否应让出资源 | `pollWork()` | 例如空闲 GC 工作循环检查；队列没有工作，但轮询器已初始化、有网络等待者且没有阻塞轮询者时，调用 `netpoll(0)` |
| 系统监控兜底检查 | `sysmon()` | 轮询器已初始化，没有阻塞轮询者，且 `lastpoll` 距今超过 10ms 时，调用 `netpoll(0)`；不是严格每 10ms 执行一次 |
| STW 结束，恢复程序执行 | `startTheWorldWithSema()` | 轮询器已初始化时，调用 `netpoll(0)`，收集暂停期间已就绪的 G |

这不是每个 M 固定或定期执行的任务。M 正在执行业务 G 时，不会持续检查网络事件；调用取决于进入的运行时路径和共享状态。

### 4.2 等待时间

| delay | 含义 |
| --- | --- |
| `0` | 立即检查已有事件，不阻塞等待 |
| 正数 | 最多等待指定的纳秒数，调度器通常根据下一次计时器期限计算 |
| `-1` | 不设置超时期限，等待事件或主动唤醒 |

因此，准备休眠的路径也不一定实际阻塞：计时器已经到期时，计算出的等待时间可以是 `0`。平台实现还可能对超时精度和最大等待时间作转换。

### 4.3 多线程协调

- `sched.lastpoll`：非零值记录轮询时间；阻塞轮询路径通过 `Swap(0)` 取得资格，返回后恢复时间戳。其他路径据此判断是否已有阻塞轮询者。
- `sched.pollingNet`：限制工作窃取前那条非阻塞轮询路径的并发，减少多个线程同时检查引起的内核竞争；它不覆盖所有 `netpoll()` 调用路径。
- `sched.pollUntil`：记录当前轮询的计时器期限。其他线程发现需要更早唤醒时，可以通过 `netpollBreak()` 打断等待。

负责阻塞轮询的 M 可以变化，轮询器不固定绑定某个专用线程，也不是独立的业务 G。操作系统监测 I/O 状态，执行轮询的 M 获取事件并将等待中的 G 交回调度器。

## 5. 平台实现

| 平台 | 主要机制 | 主要源码文件 |
| --- | --- | --- |
| Linux | epoll | `netpoll_epoll.go` |
| macOS、部分 BSD 系统 | kqueue | `netpoll_kqueue.go` |
| Windows | I/O completion ports（IOCP） | `netpoll_windows.go` |

Unix 平台通常基于非阻塞 I/O 和就绪通知；Windows 使用完成通知机制，不能将所有平台都理解为相同的 epoll 流程。支持范围及文件组织以对应 Go 版本为准。

## 6. 等待状态与超时

运行时使用 `pollDesc` 等结构记录文件描述符对应的轮询状态，并分别协调读、写等待。关闭连接和 deadline 到期也可以唤醒等待中的 goroutine，让它返回相应错误。

### 6.1 等待的 G 保存在哪里

等待的 G 主要记录在对应文件描述符的 `pollDesc` 中，而不是统一放入一个全局 G 等待队列。

| 字段 | 用途 |
| --- | --- |
| `rg` | 记录等待读事件的 G 或读等待状态 |
| `wg` | 记录等待写事件的 G 或写等待状态 |

这两个字段不是始终保存 G 指针，还可能保存无等待者、已就绪、正在准备等待等状态标记。运行时通过原子状态转换协调登记等待、挂起和事件通知，避免丢失唤醒。

I/O 事件到来时，netpoll 从 `pollDesc` 找出需要唤醒的 G。相关 G 随后恢复为可运行状态，进入调度流程；事件通知本身不直接执行该 G 的业务代码。

### 6.2 适用范围

网络轮询并不自动覆盖所有 I/O。普通磁盘文件、某些系统调用或外部库调用可能仍阻塞操作系统线程，不能仅根据 API 是否提供阻塞式调用就判断底层是否使用 netpoller。

## 7. 源码入口

- `src/runtime/netpoll.go`：`pollDesc`、等待与唤醒逻辑，包括 `netpollblock()`、`netpollready()` 等。
- `src/runtime/netpoll_*.go`：平台事件机制适配。
- `src/runtime/proc.go`：调度器检查网络事件及注入可运行 goroutine 的逻辑。
- `src/internal/poll`：文件描述符操作与运行时轮询接口之间的衔接。
- [runtime 源码](https://github.com/golang/go/tree/master/src/runtime)：阅读时切换到所用 Go 版本的 tag。
- [Go 1.27.2 的 proc.go](https://github.com/golang/go/blob/go1.27.2/src/runtime/proc.go)：上述轮询调用路径与协调逻辑的版本固定源码。
