# 显式调用触发

业务代码可以通过 `runtime.GC()` 请求垃圾回收，并等待相应回收完成。运行时使用周期进度及 `gcTriggerCycle` 等机制协调请求，具体实现以所用 Go 版本为准。

## 1. 调用方式

```go
runtime.GC()
```

这会阻塞调用方，但其他业务 G 仍可以在 GC 的并发阶段执行；不能将整个调用期间都理解为 STW。

## 2. 周期协调

调用时可能已有 GC 进行中。运行时先协调相关周期进度，再请求需要的周期，并等待对应标记和清扫等工作达到 API 所要求的完成条件。

```text
runtime.GC
    ↓ 协调已有周期进度
按周期条件调用 gcStart
    ↓ 等待相应周期推进
确认相应回收完成后返回
```

这不是绕过同步机制强行启动一轮。多个显式调用和自动触发仍需共同遵守启动及阶段协议，不能重叠开启互不协调的标记周期。

## 3. 与自动触发的区别

显式调用不要求先达到堆增长阈值或等待时间阈值。即使 `GOGC=off`，仍可调用 `runtime.GC()`。

它适合特定测量或诊断场景，频繁调用可能打乱运行时的节奏并增加开销。业务通常不需要为了释放每批临时对象而手动触发。

## 4. 完成不代表什么

GC 只能回收不可达对象，不能强制回收仍有有效引用的数据。对象空间可复用，也不代表物理内存立刻归还操作系统，因此调用返回后 RSS 不保证下降。

调用完成也不能替代文件、连接等资源的显式关闭，不能作为所有终结器均已执行完成的保证。

## 5. 源码入口

- `src/runtime/mgc.go`：`runtime.GC`、`gcTriggerCycle`、`gcStart` 及周期等待。
- `src/runtime/mgcsweep.go`：清扫推进与完成协调。
