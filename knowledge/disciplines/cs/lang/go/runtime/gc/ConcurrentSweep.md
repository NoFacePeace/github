# 并发清扫

并发清扫（concurrent sweep）在标记终止之后推进，根据本轮标记结果回收不可达对象占用的空间，让后续分配可以复用。清扫与业务执行交错进行，具体实现以所用 Go 版本为准。

## 1. 主要工作

标记阶段确定哪些对象存活，清扫阶段将结果落实到堆空间的分配状态：保留已标记对象，回收未标记且已分配对象的空间，并更新 span 的分配信息。

清扫通常以 span 为单位，不是为每个死亡对象单独创建一个清扫任务。某个 span 中如果仍有存活对象，其可用槽位可以供同类对象后续分配；整个 span 空闲时，则可以按堆管理规则回收其占用的页。

## 2. 谁执行清扫

### 2.1 后台清扫

后台 goroutine 的入口 [bgsweep](../functions/bgsweep.md) 通过 `sweepone` 等逻辑领取待清扫 span，逐步推进工作，并在适当时机让出执行权或等待后续周期。

它不是并发标记 worker。清扫不从 `gcBgMarkWorkerPool` 领取执行者，两者属于不同的工作机制。

### 2.2 分配路径中的清扫

内存分配也可能触发清扫，以取得已清扫且可以安全复用的空间，或按清扫节奏要求推进工作。分配相关路径会检查 span 的清扫状态，必要时完成清扫或等待其他执行者完成。

因此，并发清扫并不表示所有清扫成本都由后台承担，分配操作也可能受到影响。

## 3. 如何避免重复清扫

运行时通过清扫代次、span 状态及原子操作取得清扫权。一个执行者取得某个 span 的清扫权后，其他执行者不能同时重复清扫该 span。

业务分配与清扫也需要遵守同一套状态协议。不能把尚未完成清扫的旧对象槽位直接当成可用空间复用。

清扫关键过程受到相应不可抢占等约束保护，STW 必须等待相关执行到达安全位置，不能任意将 span 停在状态修改一半的位置。

## 4. 与业务并发执行

清扫期间业务 G 可以继续运行和分配内存。运行时协调清扫进度与分配需求，避免分配无限领先于必要的清扫工作。

“并发”不保证后台清扫与业务始终在不同 CPU 上同时运行。只有一个 P 时，也可以通过调度轮换推进。

## 5. 空间复用与内存归还

| 操作 | 目的 |
| --- | --- |
| 清扫对象槽位 | 让后续对象分配复用空间 |
| 回收空 span 的堆页 | 让堆管理器重新使用这些页 |
| scavenger 归还空闲物理内存 | 降低运行时保留的物理内存占用 |

清扫不等于立即把内存归还操作系统，因此对象被回收后，进程 RSS 不一定立刻下降。清扫也不是将所有存活堆对象搬到新地址的整理过程。

## 6. 与下一轮 GC 的交接

后台与分配路径可以在下一轮标记开始前持续推进剩余清扫。如果新一轮 GC 已触发但旧清扫尚未全部完成，运行时会在清扫终止阶段完成剩余工作，再开始新一轮标记。

触发新一轮不表示旧清扫与新标记可以不受协调地重叠。后台清扫者后续也会按当前代次和任务状态领取工作，不会无条件重复执行已完成的旧任务。

## 7. 源码入口

- `src/runtime/mgcsweep.go`：`bgsweep`、`sweepone`、span 清扫及清扫协调。
- `src/runtime/mgc.go`：标记终止、清扫准备与下一轮清扫终止。
- `src/runtime/mcentral.go`：对象分配相关的 span 获取与清扫检查。
- `src/runtime/mgcscavenge.go`：空闲物理内存归还。
