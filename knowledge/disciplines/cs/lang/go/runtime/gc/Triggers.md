# GC 触发

Go runtime 根据堆增长、距上次 GC 的时间以及显式调用等条件请求启动 GC。触发只是提出启动需求，仍需经过条件复查和启动协调，具体策略以所用 Go 版本为准。

## 1. 主要入口

| 场景 | 典型入口 | 含义 |
| --- | --- | --- |
| [堆增长](HeapTrigger.md) | 分配路径检查堆触发阈值 | 随堆分配增长，按控制器策略启动标记 |
| [时间条件](TimeTrigger.md) | sysmon 检查并唤醒后台强制 GC 的 G | 长时间没有 GC 时请求一轮回收 |
| [显式调用](ExplicitTrigger.md) | `runtime.GC()` | 请求推进 GC 周期并等待相应回收完成 |

源码中常见的触发类型为 `gcTriggerHeap`、`gcTriggerTime` 和 `gcTriggerCycle`。内存软限制主要通过控制器调整堆目标和节奏参与决策，不是同级的第四种触发类型。

## 2. 堆增长触发

内存分配相关路径会在适当位置检查是否达到启动阈值。不是每次分配都必然启动 GC，也不是发现单个对象不可达就立刻触发回收。

`GOGC` 影响目标堆大小，控制器还结合标记速度、分配速度及其他约束决定触发阈值。通常在达到目标堆大小前启动，以便并发标记期间继续分配。

```text
分配推进堆增长
    ↓ 检查触发阈值
gcStart
    ↓ 复查条件并协调启动
本轮 GC
```

目标堆大小不是固定的“超过就马上 STW 清空”的硬边界；仍然存活的对象也不能被 GC 回收。

## 3. 时间条件触发

sysmon 会检查距离上次 GC 是否已超过运行时设定的时间。常见实现的 `forcegcperiod` 为约两分钟，但它不是严格的周期定时器，检查间隔和运行时状态都可能影响实际启动时间。

满足条件时，sysmon 唤醒后台强制 GC 的 goroutine，由后者请求启动 GC。sysmon 不会因此亲自执行整轮标记与清扫。

时间触发还要满足 GC 已启用、当前阶段允许等条件。不能理解成任何配置下每两分钟一定发生一次 GC。

## 4. 显式触发

业务代码可以调用 `runtime.GC()` 主动请求 GC，并等待相应周期完成；已有 GC 周期进行时，运行时会先协调周期进度，不会直接重叠开启另一轮标记。

该调用会阻塞调用方直到相应回收完成，但整轮 GC 仍包含并发工作，不代表整个调用期间都处于 STW，也不保证回收后进程 RSS 立即下降。

## 5. GOGC 与内存软限制

- `GOGC` 控制堆增长目标，影响自动 GC 的频率和内存开销。
- `GOMEMLIMIT` 或 `debug.SetMemoryLimit` 为运行时管理的内存设置软限制，控制器据此约束堆目标，可能导致更频繁的 GC。
- `GOGC=off` 关闭由堆增长比例驱动的自动 GC，常见实现也会抑制时间触发；显式 `runtime.GC()` 仍可使用，内存软限制也仍可能驱动 GC。

软限制不等于操作系统的进程内存硬上限，也不包含所有外部内存。无法回收足够存活对象时，运行时可能超过该限制。

## 6. 触发与阶段的区别

触发回答“为什么现在请求 GC”，四个主要阶段回答“启动后依次做什么”。触发成功后，还要完成启动准备，再进入清扫终止、并发标记、标记终止及并发清扫。

多个 G 可以同时发现触发条件，运行时通过启动同步机制串行化推进，并在取得权限后重新检查条件。一次条件检查成立，不保证调用方最终实际启动新一轮。

## 7. 源码入口

- `src/runtime/mgc.go`：`gcTrigger`、`gcStart`、`runtime.GC` 及后台强制 GC 路径。
- `src/runtime/mgcpacer.go`：堆目标、触发阈值和 GC 节奏控制。
- `src/runtime/malloc.go`：分配相关的 GC 触发检查。
- `src/runtime/proc.go`：sysmon 的时间条件检查。
