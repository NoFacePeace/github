# GC 启动准备

GC 启动准备是 `gcStart` 在进入本轮主要阶段前执行的检查和资源准备。它与清扫终止中的标记准备需要区分：前者包括 STW 前的工作，后者在清扫终止的 STW 区间内完成。具体调用顺序以所用 Go 版本为准。

## 1. 与四个阶段的关系

清扫终止、并发标记、标记终止和并发清扫，是理解一轮 GC 主要工作的四个阶段，不是 `gcStart` 每一步操作的完整分类。

```text
启动准备：检查触发条件、协调启动、补齐 worker
    ↓
清扫终止（STW）：完成旧清扫，准备本轮标记并开启写屏障
    ↓
并发标记：调度 worker，扫描根和对象
    ↓
标记终止（STW）
    ↓
并发清扫
```

这里将“启动准备”单独说明，不表示新增了一个与四个主要阶段并列的源码 GC 状态。

## 2. 检查与协调启动

内存分配、后台强制 GC 和 `runtime.GC()` 等路径都可能请求启动 GC。运行时检查触发条件，并通过启动同步机制协调并发请求。

取得启动权限后还需重新检查条件，避免多个请求各自启动同一轮。发现仍有 GC 周期进行时，需要遵守相应协调协议，不能直接重叠开启另一轮标记。

## 3. 准备后台标记 worker

后台标记 goroutine 的生命周期参见 [GC 标记 worker](worker.md)，可用记录的组织与领取参见 [gcBgMarkWorkerPool](../variables/gcBgMarkWorkerPool.md)。

### 3.1 创建或补齐

`gcBgMarkStartWorkers` 等逻辑通常在清扫终止的 STW 之前补齐所需后台标记 worker。worker 是专门执行标记工作的 G，不是专门占用的一条操作系统线程。

已有 worker 可以跨 GC 周期复用。首次准备或 P 数量增加等情况下可能需要补充创建，并不是每轮 GC 都重新创建全部 worker。

### 3.2 挂起与等待调度

worker 创建后通过挂起协议进入等待状态，关联的可用记录进入 worker 池。池中有记录表示运行时可以找到可用 worker，不代表它已经在执行，也不代表本轮所有标记工作已经准备完毕。

进入并发标记后，调度器根据需要领取并选择 worker，将对应 G 变为可运行并安排执行。完成当前工作片段后，worker 可以再次挂起回池。

## 4. 每轮仍需做哪些准备

worker 是可以复用的执行资源，但每轮需要处理的存活对象、根任务及标记状态都可能不同。因此，后续 GC 仍需要完成本轮的阶段准备。

| 内容 | 是否可以跨轮复用 | 何时处理 |
| --- | --- | --- |
| worker G | 通常可以 | 启动准备时确保数量足够 |
| 本轮标记状态与根扫描任务 | 需要按本轮初始化或重置 | 清扫终止等标记准备路径 |
| 写屏障启用状态 | 按阶段切换 | 业务恢复并发标记前开启 |
| worker 的运行资格 | 按需安排 | 并发标记调度路径 |

“worker 已准备好”仅表示有可用的执行者，不表示后续每轮 GC 无需准备任务或状态。

## 5. 源码入口

- `src/runtime/mgc.go`：`gcStart`、`gcBgMarkStartWorkers` 和 worker 生命周期。
- `src/runtime/mgcpacer.go`：标记 worker 的选择与调度策略。
- `src/runtime/proc.go`：STW 及恢复执行相关协调。
