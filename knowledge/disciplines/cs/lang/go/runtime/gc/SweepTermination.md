# 清扫终止

清扫终止（sweep termination）是新一轮 GC 标记开始前的阶段，用于结束上一轮剩余清扫并完成本轮标记准备。它处于 STW 边界内，具体调用顺序和同步机制以所用 Go 版本为准。

## 1. 主要工作

1. 完成上一轮尚未结束的清扫，确保旧一轮清扫不会与新一轮标记混用状态。
2. 准备本轮标记所需的状态、根扫描任务及相关工作。
3. 切换到标记阶段并开启[写屏障](write-barrier.md)，使业务恢复后产生的指针变化受到正确处理。

“终止”指结束上一轮清扫，不是本轮 GC 已经结束。准备完成后恢复业务执行，进入[并发标记](ConcurrentMark.md)。

## 2. 谁负责执行

由发起本轮 GC 的 `gcStart` 路径协调执行。发起者可能来自内存分配触发、`runtime.GC()` 或后台强制 GC 等路径，不固定由 sysmon 或某一条专门的清扫线程执行。

剩余清扫等要求系统栈的工作通过 `systemstack` 在当前 M 的 `g0` 栈上执行。切到 `g0` 不会创建新线程。

```text
请求启动新一轮 GC
    ↓ 串行化启动并重新检查触发条件
请求 STW，等待各 P 安全停止
    ↓ 在系统栈上执行相关工作
finishsweep_m：完成上一轮剩余清扫
    ↓
准备本轮标记，开启写屏障
    ↓ 恢复业务执行
并发标记
```

## 3. 上一轮清扫尚未结束怎么办

达到新一轮触发条件，只表示需要启动 GC，不表示新一轮标记已经开始。运行时先完成阶段交接，再推进本轮标记。

STW 下通过 `finishsweep_m` 等逻辑完成剩余清扫，不是单纯等待后台清扫任务慢慢结束。如果遗留清扫工作较多，会增加这段暂停的耗时。

这里的“上一轮未结束”具体指上一轮标记已经结束、清扫尚未全部完成。若上一轮仍在标记，则需要协调已有 GC 周期，不能同时开启另一轮标记。

## 4. 与原清扫执行者的协调

### 4.1 STW 先等待安全停止

暂停范围、停止请求及恢复过程参见 [STW](STW.md)。

发起 STW 与完成 STW 是两件事。运行时请求各 P 停止，并等待不能安全中断的关键操作完成后到达安全位置。

清扫单个 span 的关键过程受到不可抢占等约束保护，不能任意停在修改一半的位置，再交给另一个执行者重复处理。等待的是这类关键部分安全结束，不是整个后台清扫 goroutine 退出。

### 4.2 清扫权与代次

并发清扫通过清扫代次、span 状态和原子操作协调清扫权，防止不同执行者重复清扫同一个 span。清扫终止也遵守这些状态规则。

后台清扫 goroutine 后续恢复时，按当前状态继续领取工作，不会无条件重新清扫已经完成的 span。它是长期运行的工作循环，不等于一份可以忽略状态、反复执行的旧清扫任务。

## 5. 多个 GC 启动请求的协调

多个 G 可能同时发现达到 GC 触发条件。运行时通过 `work.startSema` 等机制串行化启动，并在取得权限后重新检查触发条件，避免重复开启同一轮 GC。

STW 及阶段切换另有相应同步协议。触发者不能仅凭发现阈值已到，就各自在自己的系统栈上独立执行一轮清扫终止。

## 6. 与其他阶段的区别

- 清扫终止：结束旧清扫并准备新标记，处于 STW 边界内。
- 并发标记：业务执行与存活对象标记交错进行。
- 标记终止：确认本轮标记完成并准备清扫，是另一个 STW 边界。
- 并发清扫：回收未标记对象的空间，通常与业务执行并行推进。

清扫终止不负责把所有空闲物理内存归还操作系统，后者属于 scavenger 等机制的职责。

## 7. 源码入口

- `src/runtime/mgc.go`：`gcStart`、`finishsweep_m` 及 GC 阶段协调。
- `src/runtime/mgcsweep.go`：清扫任务领取、span 清扫与并发协调。
- `src/runtime/proc.go`：STW 和调度相关实现。
