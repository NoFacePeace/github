# Select

`select` 用于在多个 channel 发送、接收操作之间选择一个执行。一般多分支场景的核心运行时实现位于 `src/runtime/select.go`，主要入口是 `selectgo()`；编译器会对部分简单形式使用专门的转换或优化。

## 1. 选择规则

1. 进入 `select` 时，按源码顺序求值各通信分支的 channel 操作数及发送值表达式，每个只求值一次。
2. 如果有多个通信操作可以立即完成，从中按均匀伪随机方式选择一个。
3. 没有可立即完成的通信操作时，存在 `default` 就执行它，否则阻塞等待。
4. 选中的接收操作完成后，再求值接收赋值左侧的表达式并完成赋值，随后执行分支语句。

`default` 不会覆盖已经就绪的通信分支。多个分支同时就绪时，不保证按书写顺序选择，也不提供严格的轮流执行或实时公平性保证。

## 2. 运行时流程

### 2.1 检查就绪操作

一般多分支路径会准备通信描述，随机化检查顺序，并按 channel 锁的确定顺序获取锁，以协调多个 channel 上的并发操作。

如果找到可以完成的通信操作，就执行数据传递并释放相关锁。关闭 channel 对发送和接收的影响同样适用于 `select`：选中向已关闭 channel 发送的分支会 panic。

这一轮可以理解为“按随机化顺序检查各通信分支，找到能立即完成的操作就执行”。检查时不会因为某个分支尚未就绪，就单独等待该分支；但获取 channel 锁仍可能发生竞争，因此这里的非阻塞检查不表示无锁或无等待开销。

### 2.2 登记等待与挂起

没有分支就绪且没有 `default` 时，运行时为相关通信操作准备 `sudog`，加入各 channel 对应的发送或接收等待队列，然后挂起当前 G。

同一个 G 可以因此同时出现在多个 channel 的等待结构中，但仍是一个 goroutine。运行时通过选择完成状态等机制协调竞争，确保最终只选中一个通信操作。

### 2.3 唤醒与清理

某个通信操作成功配对或相关 channel 关闭时，等待的 G 可以被唤醒。恢复执行后，运行时确认被选中的分支，并清理其他分支遗留的等待记录。

被唤醒不代表所有分支都执行，也不保证该 G 立即获得线程执行。

### 2.4 随机检查与阻塞等待的区别

`selectgo()` 的整体行为是先随机顺序检查，再按需阻塞等待，而不是不断重复遍历分支进行忙等。

| 第一轮检查结果 | 后续行为 |
| --- | --- |
| 有通信分支就绪 | 完成一个通信操作，返回选中的分支编号 |
| 都未就绪，有 `default` | 立即返回默认分支结果，不等待 channel 就绪 |
| 都未就绪，没有 `default` | 登记多个等待记录，挂起当前 G，等待某个操作唤醒它 |

运行时返回后，由编译器生成的代码执行选中分支的业务语句。多个分支共享同一个 G，不会为每个分支创建新的 goroutine。

## 3. 特殊形式

| 形式 | 行为 |
| --- | --- |
| `select {}` | 永久阻塞当前 G |
| 单个通信分支，没有 `default` | 行为类似对应的普通阻塞发送或接收 |
| 单个通信分支加 `default` | 尝试非阻塞通信，无法立即完成时执行 `default` |
| 操作 nil channel 的分支 | 不会就绪，可用于动态禁用分支 |
| 所有通信分支都是 nil channel，且没有 `default` | 永久阻塞 |

在循环中使用 `default` 而不安排等待，可能形成忙循环并消耗 CPU。若是从已关闭 channel 接收，分支可以持续就绪，应根据 `ok` 或业务状态及时退出或禁用该分支。
