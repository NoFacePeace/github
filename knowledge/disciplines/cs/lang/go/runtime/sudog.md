# sudog

`sudog` 是 Go runtime 的等待节点，定义于 `src/runtime/runtime2.go`，用于关联 goroutine 与具体等待操作。channel 通信和 runtime 信号量等待机制都会使用它。

## 1. 与 goroutine 的关系

`sudog` 不是 goroutine 本身：`g` 表示 goroutine，`sudog` 表示一次等待关系。一个 G 在 `select` 中可能同时等待多个 channel，因此可以关联多个 `sudog`。

运行时通过 `acquireSudog` 获取节点，通过 `releaseSudog` 归还节点以供复用，不是每次等待都重新分配。

## 2. 常见字段

以下列出部分常见字段，并非完整结构定义，具体布局以所用 Go 版本为准。不同等待机制使用的字段不同。

| 字段 | 作用 |
| --- | --- |
| `g` | 关联的 goroutine |
| `next`、`prev` | 连接等待队列中的前后节点 |
| `elem` | channel 通信中待发送值或接收存储位置的地址，可为 `nil` |
| `c` | 关联的 channel |
| `isSelect` | 标记是否属于 `select` 等待 |
| `success` | channel 等待的完成结果，区分成功传值与关闭唤醒等情况 |
| `waitlink` | 用于连接其他等待记录，例如 G 的等待列表或信号量等待者 |

## 3. channel 中的等待与传值

普通发送或接收无法立即完成且允许阻塞时，运行时将相应 `sudog` 加入 channel 的发送或接收等待队列，再挂起 G。通信条件满足或 channel 关闭时，运行时处理等待节点并唤醒相关 G。

### 3.1 elem 的含义

`elem` 保存内存地址：发送等待节点中，它指向待发送值的存储位置；接收等待节点中，它指向用于接收值的存储位置。该位置可能是编译器准备的临时存储，不一定直接对应源码变量的地址。丢弃接收值等情况下，`elem` 可以为 `nil`。

### 3.2 直接传递与缓冲区

直接配对通信时，运行时从发送数据的地址复制值到接收数据的地址。正在执行的通信方可以直接提供地址，不要求双方都有 `sudog`：

- 接收方已阻塞时，发送方将值复制到接收方的 `sudog.elem` 所指位置；接收方丢弃值时无需复制。
- 发送方已阻塞时，接收方可从发送方的 `sudog.elem` 所指位置取得值。

有缓冲 channel 还可能通过缓冲区传值，例如缓冲区满且存在等待发送方时，接收操作先取出队首缓冲值，再将等待发送方的值补入缓冲区。

复制遵循元素类型的赋值语义。如果元素本身是指针，复制的是指针值，不会深拷贝其指向的对象；`elem` 本身则是用于定位这个元素的地址。

## 4. select 中的多个等待节点

阻塞的 `select` 会为相关通信分支登记等待节点。同一个 G 因此可以出现在多个 channel 的等待结构中，但最终只会选择一个通信分支。

运行时需要协调选择结果，跳过已失效的竞争节点，并在恢复后清理其他分支的等待记录。不能把节点的排队顺序等同于 G 最终执行或完成的顺序。

## 5. 信号量等待中的用途

runtime 信号量机制也通过 `sudog` 管理等待的 G。`sync.Mutex`、`sync.RWMutex`、`sync.WaitGroup` 等在需要挂起等待的慢路径中，会间接使用这一机制。

这些场景通常不通过 `elem` 传递业务数据，也不使用 channel 的 `waitq` 来组织等待者；它们使用信号量实现自己的等待结构。
