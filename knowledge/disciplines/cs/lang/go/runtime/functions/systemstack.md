# systemstack

`systemstack` 是 Go runtime 临时使用系统栈执行函数的内部入口。声明位于 `src/runtime/stubs.go`，具体实现通常位于对应架构的 `src/runtime/asm_*.s`。实现细节以所用 Go 版本和平台为准。

## 1. 职责与执行栈

从普通 G 调用时，`systemstack(fn)` 将执行切换到当前 M 的 [g0](../scheduler/g0.md) 栈，执行 `fn`，完成后切回原 G 的栈，继续调用点之后的代码。

```text
普通 G 栈：systemstack(fn)
                ↓ 切换到当前 M 的系统栈
g0 栈：         fn()
                ↓ fn 返回，切回原 G 栈
普通 G 栈：继续执行
```

整个栈切换不创建新线程，也不把 `fn` 作为一个新的 goroutine 加入运行队列。当前已经在 `g0` 上时，可以直接执行 `fn`；运行时还对信号栈等特殊调用上下文有专门处理与约束。

## 2. 为什么需要系统栈

有些运行时操作不能依赖普通 G 的可增长栈，或要求在系统栈上维护内部状态，例如部分调度、栈管理和 GC 操作。

系统栈仍是用户态的栈，不是操作系统内核栈。切到系统栈也不自动产生 STW，不代表获得所有共享状态的独占权限，调用方仍需遵守同步与执行约束。

## 3. 典型调用

`goready` 通过 `systemstack` 执行内部的 `ready`，将目标 G 置为可运行。系统栈上的操作完成后，调用方通常继续执行，不会仅因调用 `systemstack` 就挂起自己。

GC 启动等路径也使用 `systemstack` 执行要求系统栈的工作。

## 4. 与 mcall 的区别

| 对比 | systemstack | mcall |
| --- | --- | --- |
| 常见目的 | 临时在系统栈上执行一段代码 | 交出当前 G 的执行控制，进入调度相关路径 |
| 回调形式 | `func()` | `func(*g)`，参数是原 G |
| 回调返回 | 正常返回，切回原栈 | 不允许直接返回 |
| 原 G 继续执行 | 通常在函数完成后继续 | 由后续运行时控制流决定何时恢复 |
