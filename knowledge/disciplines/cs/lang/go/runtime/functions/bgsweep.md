# bgsweep

`bgsweep` 是 Go runtime 后台清扫 goroutine 的入口函数，定义于 `src/runtime/mgcsweep.go`。它推进并发清扫，回收未标记对象占用的空间。具体实现以所用 Go 版本为准。

## 1. 函数与执行者

严格来说，`bgsweep` 是函数名，执行它的是一个专门的后台 G。该 G 通常在运行时初始化路径中创建，长期复用，不是每轮 GC 重新创建。

专门的后台清扫 G 通常只有一个，但它不是唯一能执行清扫的 G：业务 G 也可能在分配路径中参与清扫。

## 2. 清扫过程

`bgsweep` 通过 `sweepone` 等逻辑领取待清扫 span，取得对应清扫权后执行清扫，更新空间的可用状态，并继续处理后续任务。

它会在适当时机让出执行权，避免长期独占执行资源。运行中需要 P，不独占一条操作系统线程；关键清扫操作可按内部约束在系统栈上执行。

多个执行者通过清扫代次、span 状态和原子操作协调，不能同时重复清扫同一个 span。

## 3. 挂起与唤醒

当前没有可领取的清扫工作时，后台清扫 G 通过挂起协议进入 `_Gwaiting`，保留栈和执行现场，让 M 继续执行其他 G。

运行时通过全局清扫状态 `sweep` 中的 `g`、`parked` 等字段记录后台 G 和挂起情况。后续 GC 准备清扫工作时，通过相应同步协议将其恢复为可运行，再由调度器安排执行。

```text
后台清扫 G 执行 bgsweep
    ↓ 领取并清扫 span
当前可领取工作耗尽
    ↓ 登记挂起状态并暂停
后续周期准备清扫工作
    ↓ 恢复运行资格
继续领取并清扫
```

登记挂起与唤醒需要协调，避免工作已经准备好、后台 G 却错过通知。工作是否全部结束还要结合其他清扫执行者的状态判断，不能仅凭后台 G 暂时没有取到任务下结论。

## 4. 是否有 worker 池

`bgsweep` 没有类似 `gcBgMarkWorkerPool` 的可用 worker 池。后台执行者通常是一个长期复用的 G，由清扫状态直接保存其引用。

待清扫 span 的工作集合与执行者的管理不同：前者记录“还有什么要清扫”，后者记录“哪个 G 负责后台推进”。业务 G 参与清扫时，也不需要从池中领取 `bgsweep`。

## 5. 与标记 worker 的区别

| 对比 | bgsweep | 后台标记 worker |
| --- | --- | --- |
| 工作 | 回收未标记对象的空间 | 扫描根与对象，确定存活对象 |
| 专门的后台 G 数量 | 通常一个 | 通常按 P 数量准备多个 |
| 可用执行者管理 | `sweep` 中保存后台 G 及状态 | `gcBgMarkWorkerPool` 管理可用记录 |
| 业务 G 是否参与 | 分配路径可能参与清扫 | 分配路径可能参与标记辅助 |

## 6. 源码入口

- `src/runtime/mgcsweep.go`：`bgsweep`、`sweepone` 及全局清扫状态。
- `src/runtime/mgc.go`：清扫阶段准备、后台清扫唤醒与 GC 阶段切换。
- `src/runtime/proc.go`：运行时初始化中后台清扫 G 的创建路径。
