# schedule

`schedule` 是 Go runtime 选择下一个 goroutine 并安排执行的核心调度函数，定义于 `src/runtime/proc.go`。它在当前 M 的 `g0` 系统栈上运行，具体工作选择顺序与策略以所用 Go 版本为准。

## 1. 职责

`schedule` 在当前执行上下文符合调度条件时寻找后续工作，将选中的 G 交给 `execute`，切换到该 G 的栈开始或恢复执行。它不是业务代码可调用的公开 API。

原 G 为什么暂停、是否还能运行，由进入调度前的路径决定。例如，`park_m` 提交等待状态，`gopreempt_m` 将原 G 重新排队，`preemptPark` 提交抢占停止状态。

## 2. 从哪里寻找工作

调度逻辑会结合快速检查和 `findRunnable` 等路径，从多个来源选择工作：

| 来源 | 说明 |
| --- | --- |
| P 的本地运行队列 | 当前 P 保存的可运行 G，包括相关优先执行机制 |
| 全局运行队列 | 多个 P 共享的可运行工作，并参与公平性协调 |
| GC 标记 worker | 根据标记需求和 CPU 策略选择可用 worker |
| 网络轮询与计时器 | 处理就绪事件和到期任务，使相应工作可以执行 |
| 其他 P | 本地工作不足时，通过工作窃取取得工作 |

这不是一个固定优先级列表。运行时会根据公平性、GC、线程状态及其他条件决定具体检查顺序，不能依赖它推断业务执行顺序。

## 3. 找到 G 之后

选中 G 后，运行时还会检查是否需要将工作交给锁定的 M 等约束，再通过 `execute` 建立运行关系、更新状态，并恢复 G 的执行现场。

```text
g0 栈：schedule
           ↓ 选择可运行 G
       execute
           ↓ 恢复执行现场并切换栈
目标 G：开始执行或从之前暂停的位置继续
```

`schedule` 不会像普通函数调用那样执行完一个业务 G 再直接返回；业务 G 后续等待、让出或结束时，会通过相应运行时路径再次进入调度。

## 4. 没有可运行工作时

找不到工作时，运行时会协调工作搜索、P 的释放和 M 的等待。并不是每次本地队列为空就立即休眠，也不会无条件持续忙等。

后续出现可运行工作时，运行时通过对应唤醒机制安排 M 继续执行。

## 5. 与挂起、唤醒的关系

- 挂起：先将原 G 置为等待等状态，再进入调度选择其他工作。
- 普通抢占：将原 G 重新置为可运行并排队，再进入调度。
- 唤醒：让目标 G 获得运行资格，不保证调用方当场进入 `schedule` 或立即切换到目标 G。

因此，“唤醒了某个 G”和“调度器已经选中它执行”是两个不同步骤。

## 6. 源码入口

- `src/runtime/proc.go`：`schedule`、`findRunnable`、`execute` 及运行队列操作。
- `src/runtime/asm_*.s`：恢复 G 执行现场的架构相关实现。
