# findRunnable

`findRunnable` 是 Go runtime 寻找可运行 goroutine 的内部函数，定义于 `src/runtime/proc.go`。它由 [schedule](schedule.md) 调用，在当前 M 的 `g0` 系统栈上执行；没有合适工作时，可以等待后再继续寻找。

## 1. 职责与工作来源

`findRunnable` 为当前 M 寻找下一次执行的 G，结合运行队列、运行时任务及外部事件获取工作。

| 来源 | 说明 |
| --- | --- |
| 本地与全局运行队列 | 获取已处于可运行状态的 G，并兼顾公平性 |
| GC 工作 | 根据 GC 状态和调度策略选择标记 worker 等工作 |
| 计时器 | 检查到期计时器，处理相关回调及唤醒 |
| 网络事件 | 获取 I/O 就绪事件，使等待网络的 G 可以恢复执行 |
| 其他 P | 通过工作窃取取得可运行工作 |

这些来源并非严格按表格顺序检查。运行时可能重新检查或重试，具体顺序与条件以所用 Go 版本的源码为准。

## 2. 在调度中的位置

以下是突出网络轮询路径的简化流程，省略 GC、计时器、公平性检查及部分重试逻辑：

```text
schedule
    ↓
findRunnable
    ├─ 检查本地、全局运行队列等工作来源
    ├─ 满足条件时执行 netpoll(0)，非阻塞检查网络事件
    ├─ 尝试从其他 P 窃取工作
    └─ 仍未找到工作，协调释放 P、退出自旋并再次检查
         ├─ 取得轮询资格时，可执行 netpoll(delay)
         └─ 无法取得工作和 P 时，可以停放 M，唤醒后重试
    ↓ 找到 G，并取得执行所需的 P
返回 schedule
    ↓
execute，切换到选中的 G 执行
```

“找不到可运行的 G”指当前 M 经过查找后没有取得工作，不表示整个进程的所有 G 都处于等待状态；其他 M 仍可能正在执行 G。

## 3. 网络轮询

网络轮询的事件获取、调用条件及多线程协调参见[网络轮询](../netpoller/Polling.md)。Linux 下，`netpoll` 底层通过 `epoll_wait` 获取事件。

### 3.1 非阻塞检查

在准备工作窃取等路径上，满足轮询器已初始化、有网络等待者及轮询资格等条件时，可以调用 `netpoll(0)`。

该调用只检查已经就绪的事件，没有事件就返回，不会为了等待网络数据而阻塞当前 M。有就绪的 G 时，调度器可以选择其中的 G，并将其余工作放回运行队列。

### 3.2 等待事件

找不到工作、准备休眠时，若轮询器已初始化，有网络等待者或计时器期限，并且取得阻塞轮询资格，M 可以调用 `netpoll(delay)`。进入这条路径时，M 已释放 P，并退出自旋状态。

| delay | 行为 |
| --- | --- |
| `0` | 立即检查，不等待 |
| 正数 | 最多等待指定的纳秒数，通常与下一次计时器期限有关 |
| `-1` | 不设置超时期限，等待事件或主动唤醒 |

因此，进入准备休眠的路径不保证实际阻塞。网络事件就绪、等待超时或主动打断都可能使轮询返回；返回后运行时还需要协调取得 P、处理就绪 G 或重新寻找工作。

## 4. 与业务 G 等待 I/O 的区别

业务 G 读取非阻塞 socket 返回 `EAGAIN` 时，会通过网络等待逻辑登记到 `pollDesc`，再调用 [gopark](gopark.md) 挂起。随后 M 可以调度其他 G，不要求立即阻塞在 `epoll_wait` 中。

只有后续调度搜索进入相应路径、满足条件时，某个 M 才会承担阻塞轮询。这个 M 不必是原先执行该业务 G 的 M；它可以同时等待多个 fd 的事件。

事件到来后，网络轮询器根据 `pollDesc` 找出需要唤醒的 G，再交给调度器。事件就绪与 G 实际获得执行机会是两个步骤。

## 5. 源码入口

- `src/runtime/proc.go`：`schedule`、`findRunnable`、工作窃取及 M 的等待与唤醒。
- `src/runtime/netpoll.go`：网络等待状态及 G 的挂起、唤醒协调。
- `src/runtime/netpoll_epoll.go`：Linux 上的 epoll 注册与事件获取。
- [Go runtime 源码](https://github.com/golang/go/tree/master/src/runtime)：阅读时切换到所用 Go 版本的 tag。
