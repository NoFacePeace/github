# table growthLeft

growthLeft 是 table 中的 uint16 字段，记录在负载约束下还能消耗多少新空槽的插入预算。它不是物理空槽数量，也不是 map 当前条目数。本文按 Go 1.27.2 官方源码说明。

## 1. 初始值

空 table 初始化时，growthLeft 设为 maxGrowthLeft。常规容量下按总槽位数的 7/8 计算；最小单组 table 则保留一个空槽，即 capacity 减一。

| table.capacity | 初始 growthLeft |
| --- | --- |
| 8 | 7 |
| 16 | 14 |
| 64 | 56 |
| 1024 | 896 |

表级预算不表示每组最多放 7 个条目。某些组可以填满，其他组仍有空槽，整体通过负载规则维持探测效率和终止条件。

小 map 的单组模式没有独立 table，因此不使用这个字段，可以保存 8 个条目；不能把单组 table 与小 map 模式混为一谈。

## 2. 操作如何影响预算

| 操作 | growthLeft 的变化 |
| --- | --- |
| 使用新空槽插入 | 减 1 |
| 更新已有键的值 | 不变 |
| 复用删除槽插入 | 净变化为 0 |
| 删除后直接标为空槽 | 加 1 |
| 删除后保留删除标记 | 不变 |
| 安全清除一个删除标记 | 加 1 |

删除槽虽然不包含有效条目，仍承担探测路径信息并占用相应预算。复用它不额外消耗新空槽预算；这些变化由锁外的 map 内部协议维护，不代表并发安全。

## 3. 为零时发生什么

插入新键时，如果可以复用已发现的删除槽，就不额外消耗预算。否则预算为零时，先尝试清理删除标记；恢复预算后继续插入，不能恢复则进入表扩容或拆分路径。

```text
确认键不存在
    ├─ 能复用删除槽 → 插入，预算净变化为 0
    └─ 使用新空槽
         ├─ 预算大于 0 → 插入，预算减 1
         └─ 预算为 0 → 尝试清理
                          ├─ 恢复预算 → 插入
                          └─ 未恢复 → 扩容或拆分
```

预算为零不代表所有槽位都已占用，仍可能存在为探测协议保留的空槽。

## 4. 清理的门槛

该版本 pruneTombstones 在删除槽数量不足容量的 10% 时直接返回；检查现有键的探测路径后，如果可安全移除的删除标记仍不足容量的 10%，也不会执行清理。

实际清理只把不再需要的删除标记转为空槽，不移动有效条目。清理不足时，rehash 走表扩容或拆分，没有独立的同容量重建步骤。

## 5. clear 与重新分配

清空 table 后，used 归零、控制信息重置为空，并将 growthLeft 恢复为该表的 maxGrowthLeft。clear 通常保留表存储，不等于缩容。

扩容或拆分创建的新表，先按各自容量建立预算，再随条目迁入扣减。因此，有效数据迁入后的预算通常不再等于空表的初始值。

## 6. 与其他计数的区别

- capacity 表示该表总槽位数。
- used 表示该表有效条目数。
- growthLeft 表示剩余增长预算。
- lengthMask 表示组数减一，用于组定位。

这些字段需要配套解释，不能用 capacity 减 used 简单替代 growthLeft。

## 7. 源码入口

- `src/internal/runtime/maps/table.go`：maxGrowthLeft、reset、插入、删除、pruneTombstones、Clear 和 rehash。
