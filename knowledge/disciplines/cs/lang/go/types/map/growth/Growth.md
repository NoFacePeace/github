# Map 扩容

map 插入新键时，如果现有表的增长预算不足，运行时可能清理删除标记、扩大表，或拆分表并按需扩大目录。本文按 Go 1.27.2 的 Swiss Table 实现说明，具体优化与触发条件以对应版本源码为准。

## 1. 结构调整的区别

| 操作 | 主要作用 | 是否一定增加容量 |
| --- | --- | --- |
| [清理](Cleanup.md) | 原地移除不再需要的删除标记，不移动有效条目 | 否 |
| [表扩容](TableGrowth.md) | 为一个 table 准备更大的组数组，重排条目 | 是，增加该表槽位数 |
| [表拆分](TableSplit.md) | 将一个表的条目按更多哈希前缀位分配到两个表 | 该版本的常规拆分增加总槽位数 |
| 目录扩容 | 增加 table 指针目录项，使其能区分更多哈希前缀 | 增加目录项，不直接存放更多键值 |

“必要时扩容”适合概述，但不能把所有重新组织数据的动作都理解为扩大同一个数组。

该版本没有独立的同容量重建步骤：pruneTombstones 清理控制信息，清理不足时 rehash 走扩容或拆分。

## 2. 插入时何时需要处理

写入先按探测规则判断键是否存在。已有键通常直接更新对应值，不因新增条目触发容量需求；新键则需要可用槽位及相应预算。

table.growthLeft 不是简单的 `capacity - used`，它还受负载限制与删除标记影响。存在物理空槽，不代表运行时一定继续插入而无需处理表结构。

删除标记积累时，清理可能恢复足够预算，避免不必要地扩大容量。复用删除槽与使用新空槽的预算变化也不相同。

## 3. 小 map 转入常规模式

小 map 的 dirLen 为零，dirPtr 可以直接指向单个 group，最多保存 8 个条目。已有键更新不增加条目数；需要放入更多条目时，运行时建立常规表和目录组织，并重新安排已有数据。

这不是简单把 dirLen 从零加一：指针的目标含义、组存储、哈希定位及相关状态都需要配套转换。

## 4. 单表扩容

该版本单个 table 的最大容量为 1024 个槽位。达到增长处理条件、且可以在上限内继续扩展时，通常为该表建立更大的替代存储，并重新插入已有条目。

```text
原 table 的组数组
    ↓ 准备更大的表存储
逐条按新组数重新定位
    ↓
目录中的相关项指向新表
```

组数变化后，lengthMask 随之变化，起始组与后续探测位置可能改变，因此不能仅增加容量字段而不重排条目。

## 5. 表拆分

需要继续增加空间而单表已达到上限时，可以拆成两个表，使用下一位哈希前缀区分条目，两个新表的 localDepth 相应增加。

```text
旧表 A
    ├─ 新前缀位为 0 的条目 → 新表 A0
    └─ 新前缀位为 1 的条目 → 新表 A1
```

拆分只重排相关旧表的条目，不要求每次都重新搬迁整个 map 的全部键值。常规表内仍采用组探测，不是把冲突条目变成链表。

## 6. 目录何时扩容

如果待拆分表的 localDepth 小于 Map.globalDepth，已有目录能区分新表，可以更新相关目录项，不必扩大目录。

如果 localDepth 等于 globalDepth，则需要增加目录使用的哈希位数，使 globalDepth 加一、dirLen 翻倍，并更新 globalShift、dirPtr 等状态。

多个目录项仍可以引用同一个尚未拆分的表。目录扩容可能复制指针数组，因此不能将整个增长操作都视为与 map 大小完全无关的固定成本。

## 7. 旧存储与迭代

旧表被替换不代表其存储立即消失。迭代器等路径可能仍需要旧引用，运行时需要维护遍历语义和对象生命周期。

业务代码无法取得可长期依赖的 map 元素地址，内部布局调整也是理解元素不可寻址的一个背景，但具体规则由语言规定。

## 8. 性能与使用

插入的平均或均摊成本通常视为常数，但某次清理、重排、拆分或目录复制会增加延迟。创建时提供合理的大小提示可以减少部分后续调整，但不保证固定布局、精确容量或零扩容。

删除条目不保证自动缩回小 map，也不保证立即将内存归还操作系统。扩容机制同样不提供并发安全，普通 map 的冲突访问仍需同步。

## 9. 源码入口

- `src/internal/runtime/maps/table.go`：增长预算、清理、rehash、grow 与 split。
- `src/internal/runtime/maps/map.go`：小 map 转换、目录替换与拆分更新。
- `src/internal/runtime/maps/group.go`：组数组分配及布局访问。
