# Map 表扩容

表扩容为一个 table 创建更大的替代表，重新计算旧条目的哈希并插入新布局，最后更新目录指针。本文按 Go 1.27.2 的 table.grow 实现说明。

## 1. 触发条件

新键插入无法继续消耗增长预算，且清理未恢复预算时，进入 rehash。该版本先计算 `newCapacity = 2 * capacity`；结果不超过单表上限 1024 时，调用 grow，否则走拆分路径。

已有键更新通常不需要因新增条目而扩容。也不是物理槽位全部填满才触发，负载预算可能更早耗尽。

## 2. 准备新表

grow 创建具有新容量的 table，保留旧表的 index 和 localDepth，并为新组数组初始化控制信息和增长预算。

组数增加后，lengthMask 也随之改变。旧表中某个键的起始组与后续探测位置可能变化，因此不能直接把原组数组复制后仅修改容量。

## 3. 遍历条目并重新计算哈希

运行时遍历旧表所有组和槽位，跳过空槽、删除槽，取出每个有效条目的键和值。间接存储的键值先按类型规则解引用。

```go
hash := typ.Hasher(key, m.seed)
newTable.uncheckedPutSlot(typ, hash, key, elem)
```

源码明确重新调用键的哈希函数。控制信息只保存 H2 指纹，无法从中还原完整哈希，因此需要从实际键计算。

扩容继续使用同一个 Map.seed，不主动换种子。普通自反键的哈希通常保持一致，但 NaN 等特殊键的哈希实现可能有额外随机性，不能承诺所有键每次重算都获得相同哈希。

## 4. 在新布局中插入

迁移路径已知条目来自旧表，不需要像业务插入那样重新检查是否覆盖已有键；它根据新表组数和哈希选择位置，写入条目、控制信息并维护新表计数与预算。

删除标记不迁移到新表。全 map 的有效条目总数不因单纯迁移而增加，等待插入的新键由外层写入流程继续处理。

## 5. 替换目录引用

完成迁移后，replaceTable 更新原来指向旧表的相关目录项，使其指向新表，并将旧表 index 标为 -1。

```text
旧 table → 分配更大 table
             ↓
         重算哈希，逐条迁入
             ↓
         更新相关目录项
             ↓
         外层写入按新布局重试
```

单表扩容不增加 localDepth，也不因此必然增加整个目录长度。多个目录项原本引用同一旧表时，需要共同更新。

## 6. 成本与旧存储

扩容需要遍历旧表、计算哈希并安排新存储，长键的哈希和条目访问也有成本。调整范围主要是当前表，不是重算整个 map 中所有表的键。

旧表可能仍被迭代器引用，不保证替换后立即回收。该过程也不授予普通 map 并发读写能力。

## 7. 源码入口

- `src/internal/runtime/maps/table.go`：rehash、grow 和 uncheckedPutSlot。
- `src/internal/runtime/maps/map.go`：replaceTable 与写入重试。
