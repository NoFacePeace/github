# Go 并发同步

多个 goroutine 访问共享状态时，需要同步来协调执行并保证数据可见性。Go 提供锁、channel、原子操作等工具；应根据共享数据和协作方式选择，而不是只看 goroutine 的数量。

## 1. 常见工具

| 工具 | 主要用途 |
| --- | --- |
| [Mutex](mutex/Mutex.md) | 互斥访问共享状态，同一时刻只有一个持有者 |
| [RWMutex](RWMutex.md) | 多读者并发读取，写入时独占 |
| `sync.WaitGroup` | 等待一组任务完成 |
| `sync.Once` | 保证初始化动作只执行一次 |
| `sync.Cond` | 围绕共享条件等待和通知，配合锁使用 |
| [sync/atomic](atomic/Atomic.md) | 对单个值执行原子读写或更新，支持构建特定同步协议 |
| channel | 通过通信传递数据、通知事件或协调执行 |

WaitGroup 用于等待，不会自动保护任务并发修改的共享数据。原子操作也不会自动使多个字段组成的业务操作成为原子事务。

## 2. 同步与数据可见性

锁不仅防止多个 G 同时进入临界区，也建立内存模型中的同步关系，使受同一锁协议保护的修改能被后续访问正确观察。

所有对共享数据的相关访问都需要遵守同一同步协议。只给写入加锁，而让读取无锁进行，仍可能产生数据竞争。

## 3. 与 G、M 的关系

锁没有竞争时，通常通过原子操作完成快速获取。发生竞争时，Mutex 等实现可能先在满足条件时短暂自旋，随后挂起等待的 G，让 M 调度其他工作。

因此，业务 G 等锁不等于持续占用一个 OS 线程，但锁竞争仍可能造成等待、调度和缓存开销。自旋条件、唤醒策略等属于具体版本的实现细节。

## 4. 选择与检查

- 需要保护一组字段或完整业务操作时，通常先考虑 Mutex。
- 读多写少且并发读取收益足够时，可以测量 RWMutex 是否更合适。
- 需要表达任务交接或事件通知时，可以考虑 channel。
- 简单计数或状态更新可以考虑原子操作，但必须明确整体同步协议。

锁的零值可以使用，Mutex、RWMutex 等同步对象首次使用后不能复制。应避免在持锁期间执行不必要的耗时操作，并通过 `go test -race` 等手段检查实际执行路径中的数据竞争。
