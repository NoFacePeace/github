# Mutex 唤醒

Mutex 普通模式在需要时选择一个等待者唤醒，使其恢复竞争锁。`mutexWoken` 标记用于协调已经被唤醒或承担自旋竞争的 G，减少重复唤醒。本文按 Go 1.26.3 的内部实现说明。

唤醒状态位的含义参见[mutexWoken](mutexWoken.md)。

## 1. 唤醒不等于取得锁

普通模式下，解锁方通过运行时信号量路径唤醒等待者。被唤醒的 G 需要恢复调度，再与新来的 G 竞争锁。

```text
G1 解锁，唤醒 G2
    ↓
新来的 G3 可能先取得锁
    ↓
G2 恢复执行，继续竞争
```

仍在队列中等待的其他 G 不参与这次竞争。解锁通常按需唤醒一个等待者，不会把所有等待 G 同时叫醒。

## 2. 解锁时设置唤醒标记

普通模式的 `unlockSlow` 确认有等待者，且没有其他已锁定、已唤醒或饥饿状态需要避让时，尝试取得唤醒资格：

```go
new = (old - 1<<mutexWaiterShift) | mutexWoken
if atomic.CompareAndSwapInt32(&m.state, old, new) {
    runtime_Semrelease(&m.sema, false, 2)
    return
}
```

CAS 同时减少锁协议的等待计数并设置 woken，随后释放信号量。标记表示已经安排一个竞争者，不保证目标 G 此时已经在 CPU 上执行。

如果新来的 G3 先取得锁并再次解锁，看到已有 woken 标记，就不必再额外唤醒 G4，避免积累无效竞争者。woken 本身不会阻止 G3 抢锁，也不要求它直接入队。

## 3. 自旋者也可以设置

在 `lockSlow` 的自旋路径中，如果存在等待者、当前没有 woken 标记，且该 G 尚未承担唤醒标记责任，就可以通过 CAS 设置 woken，并将局部 awoke 设为 true。

含义是已有 G 主动等待锁，解锁时暂时无需再叫醒另一个等待者。设置 woken 不代表持有锁，也不记录具体 G 的 ID。

## 4. 在加锁路径清除标记

普通模式等待者从信号量等待返回后，会将局部 awoke 设为 true。承担该责任的 G 在后续循环准备新状态时清除 woken：

```go
if awoke {
    // 省略一致性检查。
    new &^= mutexWoken
}
// 随后通过 CAS 提交新状态。
```

这次更新可能取得锁，也可能增加等待计数并准备再次等待。CAS 成功才真正清除标记；失败时重新读取并循环，不会直接覆盖其他 G 的修改。

## 5. 为什么重新等待不会遗留标记

G2 尚未恢复执行时，woken 表示它已被安排回来竞争，无需再次唤醒。如果 G2 恢复后抢不到锁，需要重新等待，则先通过状态更新清除自己负责的 woken，再进入信号量等待。

```text
G2 已安排唤醒，尚未继续执行
    → woken 保留，避免重复通知

G2 恢复执行，但仍未取得锁
    → 清除 woken，同时协调等待计数
    → 进入信号量路径，必要时再次挂起
```

如果 G3 解锁发生在 G2 清除标记、准备挂起的交错期间，原子状态更新和运行时信号量令牌、队列锁等机制共同避免丢失唤醒。不能把它简化为先无保护地清标记，再无条件睡眠。

## 6. 与饥饿模式的区别

| 对比 | 普通模式的唤醒标记 | 饥饿模式 |
| --- | --- | --- |
| 主要作用 | 避免额外唤醒竞争者 | 向等待者交接，缓解长期等待 |
| 新来的 G | 仍可按协议竞争 | 不自旋抢锁，进入等待流程 |
| 等待者恢复后 | 通常还需要竞争 | 按交接协议取得锁并修正状态 |

woken 与 starving 作用不同，不能根据 woken 推断锁已经交给某个 G。

## 7. 源码入口

- `src/internal/sync/mutex.go`：`unlockSlow` 的唤醒资格、`lockSlow` 的自旋标记及清除逻辑。
- `src/runtime/sema.go`：信号量释放、等待记录出队与 G 的唤醒。
