# Mutex 饥饿恢复

Mutex 从饥饿模式恢复为普通模式，由接收到锁交接的等待者在 `lockSlow` 中完成。它不是由解锁者定时恢复，也不需要 sysmon 参与。以下按 Go 1.26.3 内部实现说明。

被清除的饥饿状态位参见[mutexStarving](mutexStarving.md)。

## 1. 判断发生在哪里

等待者从运行时信号量等待返回后，先更新自己的局部 starving 标记，再读取锁状态。如果锁处于饥饿模式，则按交接协议修正状态，并判断是否退出该模式。

```text
信号量等待返回
    ↓
计算累计等待时长，更新局部 starving
    ↓
发现锁处于饥饿模式
    ↓
接收交接，准备设置 locked、减少等待计数
    ↓
按条件一并清除 mutexStarving
    ↓
提交状态更新，完成加锁并返回
```

## 2. 退出条件

满足以下任意一个条件即可恢复普通模式：

| 条件 | 含义 |
| --- | --- |
| `!starving` | 当前接收者没有处于长时间等待状态 |
| `old >> mutexWaiterShift == 1` | 当前接收者是最后一个等待者 |

局部 starving 在等待返回后根据累计等待时长更新，该版本阈值约为 1 毫秒；一旦在本次 Lock 调用中变为 true，就不会被后续计算自动改回 false。

这里的等待计数仍包含正在接收交接的自己。因此，计数为 1 表示自己接收后没有其他已计入的等待者，并不是说后面还排着一个 G。

## 3. 状态如何更新

核心代码如下，省略状态一致性检查等细节：

```go
delta := int32(mutexLocked - 1<<mutexWaiterShift)
if !starving || old>>mutexWaiterShift == 1 {
    delta -= mutexStarving
}
atomic.AddInt32(&m.state, delta)
```

这次原子更新包含：设置锁定位、减去当前接收者对应的等待计数，并在满足条件时清除饥饿位。

恢复普通模式不等于立即释放锁。当前 G 已取得锁，可以进入临界区；新来的 G 仍需等待它解锁，或按普通竞争规则处理。

## 4. 两种典型情况

### 4.1 最后一个等待者

G2 已等待很久，但它是最后一个等待者。G2 接收交接时，等待计数为 1，因此清除饥饿位；即使局部 starving 为 true，也可以恢复普通模式。

### 4.2 接收者没有等太久

G2 接收交接时，后面还有等待者，但 G2 自己没有进入长时间等待状态。此时也会清除饥饿位，让锁恢复普通竞争，以避免不必要地长期维持交接模式。

如果 G2 已等待很久且后面还有等待者，则保留饥饿模式。它后续解锁时继续按饥饿交接协议处理。

## 5. 并发与公平性

判断依据接收交接时观察到的状态，并按运行时协议原子提交。恢复后仍可能有新的等待者或竞争者到来，不能把“最后一个等待者”理解为之后不会再有 G 请求这把锁。

恢复策略用于兼顾吞吐量与等待延迟，不承诺严格 FIFO，也不承诺固定的最长等待时间。

## 6. 源码入口

- `src/internal/sync/mutex.go`：`lockSlow` 中饥饿模式的接收、状态修正和退出条件。
- `src/runtime/sema.go`：信号量等待与 handoff 交接支持。
