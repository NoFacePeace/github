# Mutex 自旋

自旋是在未取得锁时继续占用当前执行资源，短暂等待并重新检查状态，而不是立即挂起 G。它适合锁可能很快被其他执行者释放的情况，可以避免一次挂起与唤醒的开销。本文按本地 Go 1.26.3 的 Mutex 实现说明。

## 1. 何时自旋

Lock 快路径的 CAS 失败后进入 `lockSlow`，并不是无条件先自旋。锁层面的条件为：

```go
old&(mutexLocked|mutexStarving) == mutexLocked && runtime_canSpin(iter)
```

这要求锁已被持有、没有处于饥饿模式，并且运行时判断本轮可以自旋。

## 2. 运行时判断条件

`runtime_canSpin` 结合以下状态保守判断：

| 条件 | 目的 |
| --- | --- |
| 自旋轮数未达到 `active_spin` 限制 | 防止无限空转 |
| 启动时检测的 CPU 数量大于 1 | 单 CPU 下自旋难以让另一个执行者同时释放锁 |
| P 数量扣除空闲 P、自旋 M 和当前执行者后仍有余量 | 估计还有其他执行者可以推进工作 |
| 当前 P 的本地可运行结构为空 | 避免已有本地工作却一直空转 |

这是根据调度资源作出的启发式判断，不会直接查明持锁 G 正在哪个 CPU 上执行，也不保证它马上释放锁。

## 3. 自旋执行过程

```text
lockSlow 读取锁状态
    ↓
满足锁状态及 runtime_canSpin 条件
    ↓
按条件设置 mutexWoken，避免解锁方重复唤醒等待者
    ↓
runtime_doSpin → procyield
    ↓
增加自旋轮数，重新读取锁状态
    ├─ 仍允许自旋 → 再执行一轮
    └─ 不再自旋 → 尝试 CAS 获取或更新等待状态
```

`procyield` 通常执行架构相关的处理器自旋提示指令。它不是 `runtime.Gosched`，不会因此把当前 G 放回运行队列，也不是让 OS 线程进入休眠。

## 4. 自旋后仍未取得锁

如果无法取得锁，G 按锁协议登记等待，通过运行时信号量机制在必要时挂起。M 随后可以调度其他 G。

进入慢路径或执行自旋都不意味着必然挂起：状态变化后也可能直接通过 CAS 取得锁并返回。

## 5. 与饥饿模式的关系

饥饿模式要求新竞争者排队，锁按交接协议传给等待者，所以新来的 G 不通过自旋抢锁。普通模式中的自旋与唤醒竞争可以提高吞吐量，饥饿交接则用于缓解长时间等待。

## 6. 成本与边界

自旋期间，G 仍在当前 M 上执行并持有 P，会占用 CPU 和调度资源。它不是免费的等待，也不能保证比挂起更快，所以实现会限制次数并检查是否还有其他工作可做。

业务代码不应简单使用无限 TryLock 循环模仿这套机制；它绕过正常等待与公平性处理，可能增加 CPU 消耗。

## 7. 源码入口

- `src/internal/sync/mutex.go`：`lockSlow` 的自旋条件、轮数和 woken 协调。
- `src/runtime/proc.go`：`internal_sync_runtime_canSpin`、`internal_sync_runtime_doSpin` 及相关桥接入口。
- `src/runtime/asm_*.s`：`procyield` 的架构相关实现。
