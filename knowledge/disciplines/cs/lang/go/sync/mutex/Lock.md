# Mutex 加锁

`sync.Mutex.Lock()` 获取互斥锁，成功返回后调用方进入临界区。如果暂时不能取得锁，调用方可能短暂自旋，或挂起等待。本文按本地 Go 1.26.3 的 `src/internal/sync/mutex.go` 整理，内部策略以所用版本为准。

## 1. 入口与快路径

对外的 `sync.Mutex.Lock` 委托内部实现，先尝试用 CAS 将状态从零改为已锁定。以下省略竞态检测相关代码：

```go
func (m *Mutex) Lock() {
    if atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked) {
        return
    }
    m.lockSlow()
}
```

[CAS](../atomic/CAS.md) 是原子的比较并交换，多个 G 同时尝试时只有一个能成功。这里要求整个 state 为零，不只是锁定位为零；失败后进入 `lockSlow`，由它处理其他状态。

## 2. 锁状态

| 状态 | 作用 |
| --- | --- |
| `mutexLocked` | 锁已被持有 |
| `mutexWoken` | 已有被唤醒或承担竞争的 G，避免重复唤醒 |
| `mutexStarving` | 处于饥饿模式，使用交接策略 |
| 高位等待计数 | 记录参与等待的 G 数量 |

`sema` 配合运行时信号量机制完成等待和唤醒。等待者不是直接保存在 Mutex 内部的普通 Go 切片中。

## 3. 慢路径与自旋

自旋的判断条件、执行过程及资源开销参见[Mutex 自旋](Spin.md)。

`lockSlow` 循环读取并原子更新状态。在普通模式、锁已被持有且运行时允许自旋时，可以短暂执行 `runtime_doSpin`，期待其他执行者很快释放锁。

自旋期间 G 仍在执行，会占用执行资源；它不是休眠。自旋有条件和次数限制，饥饿模式下新竞争者不通过自旋抢锁。

如果锁在循环期间变为可获取状态，慢路径也可以通过 CAS 取得锁，所以进入慢路径不意味着必然挂起。

## 4. 登记等待与挂起

无法取得锁时，G 更新等待计数，并调用 `runtime_SemacquireMutex(&m.sema, ...)`。运行时协调信号量计数、等待队列和 G 的挂起，避免解锁通知与登记等待交错时丢失唤醒。

```text
Lock 快路径失败
    ↓
lockSlow 检查状态，按条件短暂自旋
    ├─ 取得锁 → 返回
    └─ 仍不能取得
         → 登记等待，进入运行时信号量路径
         → 必要时挂起 G，M 调度其他工作
         → 被唤醒后继续处理锁状态
```

首次等待通常按队尾入队，被唤醒后再次竞争失败的 G 可按相应策略进入队首。普通模式下，唤醒不等于已取得锁，仍需与其他 G 竞争。

## 5. 饥饿处理

该版本的等待时间阈值为约 1 毫秒。等待者恢复后发现等待过久，会记录饥饿状态，并在符合条件的后续状态更新中推动锁进入饥饿模式；不是后台计时器一到 1 毫秒就自动切换。

饥饿模式下，新来的 G 排队，锁通过解锁路径向等待者交接。接收者修正锁定位与等待计数，并在符合条件时退出饥饿模式，例如自己是最后一个等待者，或未处于长时间等待状态。

这些策略用于兼顾吞吐量和等待延迟，不提供业务层严格 FIFO 保证。

## 6. 返回与使用约束

Lock 返回代表已取得锁。Mutex 不可重入，同一个 G 持锁后再次调用 Lock 可能造成自我死锁。首次使用后不能复制锁，也不能复制包含已使用锁的值来制造另一份同步状态。

## 7. 源码入口

- `src/sync/mutex.go`：对外 Lock 方法。
- `src/internal/sync/mutex.go`：Lock 快路径、`lockSlow` 与状态位。
- `src/runtime/sema.go`：运行时信号量等待及相关调度处理。
