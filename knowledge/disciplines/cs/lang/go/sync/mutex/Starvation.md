# Mutex 饥饿

Mutex 饥饿指等待者反复未能取得锁、长时间无法进入临界区的情况。Go 的 Mutex 通过饥饿模式缓解这种等待：普通模式允许竞争，饥饿模式按协议向队列中的等待者交接。本文按 Go 1.26.3 的 `lockSlow` 和 `unlockSlow` 实现说明。

饥饿状态位的含义参见[mutexStarving](mutexStarving.md)。

## 1. 为什么入队后仍可能饥饿

普通模式下，解锁通常按需唤醒一个 G，但唤醒并不直接授予锁。它恢复执行后，仍需与新来的 G 竞争；新来的 G 已经在 CPU 上运行，可能先取得锁。

```text
G2 入队等待
    ↓
G1 解锁，唤醒 G2
    ↓
新来的 G3 先取得锁
    ↓
G2 需要再次等待
```

仍在队列中挂起的其他 G 不参与这次竞争。已经等待过的 G 再次入队时，按相应策略进入队首，但这仍不能保证它下一次被唤醒后一定取得锁。

## 2. 等待时间在哪里判断

判断位于加锁慢路径 `lockSlow` 的循环内。首次进入信号量等待前记录 waitStartTime；从等待返回后计算累计时长：

```go
runtime_SemacquireMutex(&m.sema, queueLifo, 2)
starving = starving ||
    runtime_nanotime()-waitStartTime > starvationThresholdNs
```

该版本阈值约为 1 毫秒。再次等待时不重新设置开始时间，因此记录的是从首次等待开始的累计时间，包含恢复调度等期间的耗时。

G 挂起时不会持续计算时间。判断在它恢复执行后进行，也没有专门的计时器到点切换模式。信号量等待也可能无需真正挂起，所以准确说法是“等待返回后判断”。

## 3. 局部 starving 与锁状态

| 状态 | 所属位置 | 含义 |
| --- | --- | --- |
| `starving` | 当前 Lock 调用的局部变量 | 当前等待者发现自己已经等太久 |
| `mutexStarving` | Mutex.state 中的状态位 | 整把锁已经进入饥饿交接模式 |

局部变量变成 true 不代表锁状态已经改变。锁的模式需要后续通过原子操作提交。

## 4. 什么时候设置饥饿位

等待返回后，如果发现锁已经处于饥饿模式，就处理交接；否则继续普通模式的循环。准备新状态时，使用以下判断：

```go
if starving && old&mutexLocked != 0 {
    new |= mutexStarving
}
// 随后通过 CAS 将 old 更新为 new。
```

这要求自己已等太久，而且读到的锁仍被持有。等待计数、相关状态位等在同一次 CAS 中更新；成功后才真正设置饥饿位。

不是先执行一次独立的抢锁 CAS，失败后再单独写入饥饿位。代码根据当前状态决定尝试获取还是登记等待；若锁已空闲且没有饥饿标记，可以直接竞争取得锁，无需开启饥饿模式。

读取后若其他 G 改了状态，CAS 会失败，随后重新读取并循环；此前的判断不会强行覆盖新状态。普通模式的自旋判断也可能先执行，因此局部 starving 为 true 并不保证下一条指令就设置模式。

## 5. 饥饿模式如何运行

进入饥饿模式后，新来的 G 不自旋抢锁，进入等待协调，首次等待通常排队尾。解锁方请求把机会交给队首等待者；接收者恢复后修正 locked 位和等待计数。

交接中 locked 位可能暂时为零，但 starving 位仍阻止新来的 G 抢锁。不是同时唤醒全部等待者，也不会强制让当前持锁者提前解锁。

## 6. 如何退出

恢复条件、判断时机及原子状态更新过程参见[Mutex 饥饿恢复](StarvationRecovery.md)。

接收交接的等待者发现自己是最后一个等待者，或自己未处于长时间等待状态时，可以清除饥饿位，恢复普通竞争模式。

普通模式通常有更好的吞吐量，饥饿模式缓解极端等待延迟。约 1 毫秒只是实现阈值，不保证所有 G 在该时间内取得锁，也不保证严格的业务 FIFO 顺序。

## 7. 源码入口

- `src/internal/sync/mutex.go`：`lockSlow` 中的时间判断、模式提交与退出；`unlockSlow` 中的交接请求。
- `src/runtime/sema.go`：信号量排队、唤醒和交接支持。
