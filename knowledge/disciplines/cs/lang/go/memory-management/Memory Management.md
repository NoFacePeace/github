# Memory Management

Go 内存管理主要由编译器和运行时共同完成：编译器通过逃逸分析决定部分数据的存储位置，运行时负责堆内存分配、垃圾回收以及 goroutine 栈的管理。

## 1. 栈与堆

| 区域 | 主要用途 | 管理方式 |
| --- | --- | --- |
| 栈 | 保存函数调用相关的数据，以及适合在栈上分配的局部变量 | 每个 goroutine 有自己的栈，由运行时按需调整 |
| 堆 | 保存无法安全留在当前栈帧中的对象等数据 | 运行时分配，由垃圾回收器回收不可达对象 |

局部变量不一定分配在栈上，使用 `new` 或取地址也不一定导致堆分配。实际位置取决于逃逸分析、内联等编译器优化，有些变量还可能保存在寄存器中或被消除。

## 2. 逃逸分析

逃逸分析用于判断对象的生命周期是否超出其所在栈帧，以及对象能否安全分配在栈上。

```go
package example

func NewValue() *int {
    value := 42
    return &value
}
```

该函数返回局部变量的地址。Go 保证返回的指针有效；在函数未被内联等优化改变分析结果时，`value` 通常会逃逸到堆上。

在包含 `go.mod` 的项目目录执行以下命令，可查看当前项目的编译器分析结果：

```sh
go build -gcflags='-m=2' ./...
```

常见输出包括 `escapes to heap` 和 `moved to heap`。分析结果可能随 Go 版本、调用方式和编译优化变化，应结合实际构建输出判断。

## 3. 内存分配

Go 运行时通常按对象大小组织堆内存分配。常见实现包含以下层次，具体细节可能随版本变化：

- `mcache`：每个 P 的分配缓存，用于降低小对象分配时的锁竞争。
- `mcentral`：按大小类别管理可供分配的 span，为 `mcache` 补充空间。
- `mheap`：管理堆页及 span；大对象通常直接从堆管理器获取空间。

频繁分配会增加分配开销和 GC 压力。优化前应先测量分配次数、分配字节数及对象保留情况。

## 4. 垃圾回收

Go 使用自动垃圾回收（GC）回收不可达的堆对象。其运行时采用并发标记清扫机制，并通过写屏障等机制在程序继续运行时维护标记的正确性；部分阶段仍需要短暂的 STW（Stop the World）暂停。

详细原理与调优方法参见 [GC](GC.md)。

根对象与可达性示例参见 [roots](roots.md)。

### 4.1 可达性与内存保留

GC 根据对象是否仍可从根对象到达决定是否回收，而不是仅根据变量是否离开词法作用域。全局变量、活跃 goroutine、缓存和切片底层数组等都可能让对象持续可达。

例如，长时间保存大切片的一小段，可能保留整个底层数组。确认存在这类问题后，可以复制需要保留的数据，以解除对原底层数组的引用。

### 4.2 常用配置

| 配置 | 作用 |
| --- | --- |
| `GOGC` | 控制 GC 的目标堆增长比例，默认值为 `100`；较低值通常增加 GC 频率，较高值通常允许使用更多堆内存 |
| `GOMEMLIMIT` | 设置运行时管理内存的软限制，Go 1.19 起支持；不等同于进程 RSS 或容器的硬限制 |
| `GODEBUG=gctrace=1` | 在程序运行时输出 GC 跟踪信息，便于观察回收频率、耗时和堆变化 |

应结合延迟、CPU、内存和容器限制调优。不可达对象被回收后，对应内存也不一定立即归还操作系统，因此 GC 堆大小和进程 RSS 可能不同。

## 5. 测量与排查

### 5.1 基准测试

```sh
go test -bench=. -benchmem ./...
```

该命令运行已有的基准测试。输出中的 `B/op` 表示每次操作分配的字节数，`allocs/op` 表示每次操作的分配次数。

### 5.2 内存分析

对包含基准测试的单个包采集内存 profile：

```sh
go test -bench=. -benchmem -memprofile=mem.out .
go tool pprof -alloc_space mem.out
go tool pprof -inuse_space mem.out
```

- `alloc_space`：累计分配量，用于定位分配热点。
- `inuse_space`：采样时仍在使用的内存，用于定位内存保留问题。

内存 profile 默认使用采样，统计结果不是每一次分配的精确记录。在线服务也可以通过 `net/http/pprof` 采集运行时 profile。
