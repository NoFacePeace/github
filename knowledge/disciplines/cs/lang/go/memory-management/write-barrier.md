# 写屏障

写屏障（Write Barrier）是在修改指针引用时执行的额外逻辑，用于维护并发 GC 标记的正确性。Go 编译器与运行时自动完成这些工作，开发者无需手动调用。

## 1. 为什么需要写屏障

并发标记期间，业务代码仍然运行，可能修改对象之间的引用。如果一个已扫描的黑色对象指向尚未发现的白色对象，而白色对象又失去了其他待扫描路径，GC 就可能漏标仍然可达的对象。

写屏障在引用变化时保护必要的对象，确保它们被纳入标记。颜色含义参见 [三色标记](../../../runtime/tri-color-marking.md)。

这里的写屏障不是互斥锁，也不等同于 CPU 内存屏障；它主要解决 GC 如何正确追踪引用变化的问题。

## 2. 编译器与运行时如何配合

编译器将指针赋值转换为机器指令时，在需要的位置生成写屏障检查和相关操作。运行时在并发标记阶段启用屏障，并处理记录的指针。

```go
a.child = newObj
```

可以用以下伪代码理解执行过程：

```text
如果写屏障已启用：
    记录需要保护的旧、新引用
完成指针赋值
```

这段代码在编译时生成，不是在 GC 开始后临时生成。实际实现会使用缓冲和批量处理等优化，记录引用也不意味着立即扫描整个对象。

不是每次赋值都需要屏障。是否生成相关代码取决于赋值位置、是否包含指针以及编译器分析；普通整数赋值不需要 GC 写屏障。

## 3. 混合写屏障

### 3.1 插入与删除

对于 `a.child = newObj`，赋值既覆盖旧引用，也建立新引用：

```text
赋值前：a.child → oldObj
赋值后：a.child → newObj
```

| 屏障 | 保护对象 | 目的 |
| --- | --- | --- |
| 删除写屏障 | 旧引用指向的对象 | 防止尚未扫描的引用被删除后丢失标记路径 |
| 插入写屏障 | 新引用指向的对象 | 防止对象被挂到已扫描对象上后被漏标 |

“删除”包括覆盖引用，不只是赋值为 `nil`。写入 `nil` 也可能需要保护旧引用。

### 3.2 理论规则与实现

Go 1.8 起采用混合写屏障，结合两类屏障的保护作用。设计中的规则可概括为：

```text
shade(旧引用)
如果当前 goroutine 的栈尚未扫描：
    shade(新引用)
完成赋值
```

`shade` 可以直观理解为：**将引用指向的白色对象置灰，加入待扫描队列**。GC 后续扫描它的引用，完成后将其视为黑色。已经是灰色或黑色的对象无需重复入队，`nil` 等非堆对象引用无需处理。

Go 实际实现通常不在每次写入时判断栈是否已经扫描，而是对旧、新指针都采取保护。因此，可以理解为：**覆盖指针时，将旧引用和新引用指向的白色对象置灰**。这里处理的是引用指向的对象，不是删除对象或创建对象。

颜色是概念模型。实际实现通常先将指针记录到写屏障缓冲区，再处理标记和入队，不一定在赋值现场立即完成置灰，也不会立即扫描完整对象。具体屏障代码与优化应以所用 Go 版本的源码为准。

### 3.3 强、弱三色不变式

**Go 混合写屏障的正确性以弱三色不变式为基础，不要求始终满足强三色不变式。**

| 不变式 | 约束 |
| --- | --- |
| 强三色不变式 | 黑色对象不能直接引用白色对象 |
| 弱三色不变式 | 黑色对象可以引用白色对象，但该白色对象必须受到灰色对象保护，即存在从灰色对象出发、经过白色对象到达它的路径 |

弱三色不变式关注的是“仍然有待扫描路径能够发现这个对象”，而不是完全禁止黑色到白色的引用。

例如，已扫描栈上的变量从尚未扫描的堆对象读取一个白色对象的引用。栈写入通常没有屏障，白色对象此时不会立即置灰，但仍可通过原来的待扫描堆路径找到它。如果之后删除这条堆引用，删除屏障就会保护旧引用，将白色对象纳入标记，避免它被隐藏在已扫描的栈中。第 4.1 节给出了对应代码。

Go 旧版使用的 Dijkstra 插入写屏障以强三色不变式为基础；由于普通栈写入没有屏障，还需要配合标记结束时的栈重扫。混合屏障则结合引用保护与栈扫描规则，允许采用较弱的约束而不漏标。

实际实现还包含写屏障缓冲区等待处理工作，分析正确性时必须将这些记录一并考虑。不能只观察某次赋值后的堆标记位，也不能因为实现通常保护旧、新引用，就断言始终满足强三色不变式。

## 4. 栈没有写屏障，如何避免漏标

普通的当前 goroutine 栈上的指针赋值通常不加写屏障，以降低开销。扫描栈时，运行时会暂停对应 goroutine，避免它同时修改栈；扫描完成后的引用变化则需要配合堆写屏障等规则保证正确性。

以下代码是引用关系示意，假设 `a` 是堆对象，`local` 是栈上的活跃引用。实际分配及指令可能受编译器优化影响。

### 4.1 从堆转移到已扫描的栈

假设栈已扫描，但 `a` 尚未扫描，其引用的对象也尚未标记：

```go
local := a.child // 栈写入，通常没有写屏障
a.child = nil   // 堆字段写入，屏障保护旧引用指向的对象
use(local)
```

GC 不会重新扫描 `local`，但删除堆引用时，屏障会保护旧引用指向的对象，避免它只剩下已扫描栈中的引用而被漏标。

如果没有执行 `a.child = nil`，对象仍可通过堆字段找到。GC 后续扫描 `a` 时会发现它，所以仍然安全：保留引用时由扫描发现，删除或覆盖引用时由屏障保护。

### 4.2 从未扫描的栈转移到已扫描的堆

假设栈尚未扫描，`a` 已扫描，而 `local` 指向的对象尚未标记：

```go
a.child = local // 堆字段写入，屏障保护新引用指向的对象
local = nil     // 栈写入，通常没有写屏障
```

如果只有普通赋值，GC 既不会重新扫描 `a`，也无法从之后的栈扫描中找到已清空的 `local`。插入屏障保护新引用，使对象不会漏标。

这些例子展示的是引用转移，对象本身并没有从堆移动到栈，也没有因为赋值移动存储位置。

## 5. 为什么混合屏障可以减少暂停

单一插入或删除屏障也能用于正确的收集器，但需要配合相应的根扫描、分配和引用处理规则。混合屏障是 Go 为其并发 GC 选择的方案。

### 5.1 旧版为什么需要重扫栈

Go 早期使用插入写屏障，它保护新写入的引用，但不保护被覆盖的旧引用。同时，普通栈上的指针赋值没有写屏障，因此已经扫描过的栈仍可能接收到尚未标记对象的引用。

假设当前 goroutine 的栈已经扫描，堆对象 `a` 尚未扫描，`a.child` 指向的对象仍为白色：

```go
local := a.child // 栈写入没有屏障，对象不会因此置灰
a.child = nil   // 旧版插入屏障只保护新引用；nil 无需标记
use(local)      // 对象仍在使用
```

这时，对象只剩下已扫描栈上的 `local` 引用。GC 后续扫描 `a` 时看到的是 `nil`，无法再通过这条堆引用找到对象。如果不重扫栈，就可能将仍然可达的白色对象误回收。

因此，旧版在标记终止阶段需要全局暂停，重新扫描需要重扫的 goroutine 栈，找出这些新出现的活跃引用，并完成由此产生的标记工作。这里通常概括为“整体栈重扫”；具体版本可以跳过未发生相关变化的栈，并不意味着所有栈都必然逐一重扫。

之所以需要暂停，是因为重扫期间若业务代码继续修改没有写屏障保护的栈引用，仍可能再次产生漏标窗口。

### 5.2 混合屏障如何避免重扫

对于同一个例子，混合屏障在 `a.child = nil` 时会保护旧引用，将它指向的白色对象置灰。即使对象只剩下已扫描栈上的引用，GC 仍会通过待扫描工作找到它。

混合屏障保护引用在栈与堆之间转移的两种方向，配合栈扫描及标记期间新分配对象按已标记对象处理等规则，取消了标记终止阶段的整体栈重扫。

### 5.3 仍然存在的暂停

这不意味着完全消除暂停：

- 标记开始和结束时仍需要短暂的全局暂停（STW）。
- 扫描某个 goroutine 的栈时，需要暂停该 goroutine，其他 goroutine 可以继续执行。

变化是减少全局暂停期间需要完成的工作，而不是将所有全局暂停替换为单个 goroutine 暂停。
