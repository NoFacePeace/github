# GC

GC（Garbage Collection，垃圾回收）负责自动回收不可达的堆对象。Go 运行时采用并发标记清扫机制，主要在程序继续运行时完成回收工作，部分阶段仍需要短暂暂停程序。具体实现细节可能随 Go 版本变化。

## 1. 可达性

GC 从根对象出发，沿指针引用查找仍然可达的对象。根包括全局变量以及 goroutine 栈中的活跃引用等。无法从根到达的堆对象可以被回收，即使多个对象之间形成引用环，也不妨碍回收。

根引用的来源和引用链示例参见 [roots](roots.md)。

变量离开词法作用域不代表对象立即被回收；对象是否仍然可达，以及 GC 何时运行，才决定其回收时机。文件、网络连接等资源仍应显式关闭，不能依赖 GC 及时释放。

## 2. 标记与清扫

### 2.1 三色标记模型

三色标记是追踪式垃圾回收的通用模型，不是 Go 特有的算法。颜色含义、标记过程和并发漏标问题参见 [三色标记](../../../runtime/tri-color-marking.md)。

Go 的并发标记可以用该模型理解；运行时通过标记位和工作队列等结构表达标记状态，并使用写屏障维护并发标记的正确性。

### 2.2 一轮 GC 的主要阶段

1. **清扫终止**：短暂 STW，完成必要准备，并开启标记阶段使用的写屏障。
2. **并发标记**：扫描根和可达对象，GC 标记工作与应用执行交错进行；goroutine 栈扫描需要对相应 goroutine 做同步。
3. **标记终止**：短暂 STW，完成标记终止工作并切换阶段。
4. **并发清扫**：回收未标记对象占用的空间，清扫也可能由后续分配操作触发。

清扫让空间能够被后续分配复用；将空闲物理内存归还操作系统由 scavenger 等运行时机制处理，两者不是同一个步骤。

### 2.3 写屏障与标记辅助

并发标记期间，应用可能修改对象之间的指针关系。Go 通过写屏障记录必要的引用变化，避免漏标仍然可达的对象。Go 1.8 起采用混合写屏障，其具体规则应结合对应版本的运行时实现理解。

当分配速度较快、标记进度不足时，进行分配的 goroutine 可能参与标记工作，称为标记辅助（mark assist）。因此，GC 对请求延迟的影响不仅来自 STW，也可能来自标记辅助和并发 CPU 消耗。

## 3. 触发与调优

### 3.1 GOGC

`GOGC` 控制目标堆增长比例，默认值为 `100`。在 Go 1.18 及之后的 GC 调优模型中，可用以下公式理解目标堆大小：

```text
目标堆大小 ≈ 存活堆大小 +（存活堆大小 + GC 根大小）× GOGC / 100
```

这是理解调优的模型，运行时还会考虑最小堆目标、内存限制和标记进度等因素。GC 通常在达到目标堆大小之前启动，以便在分配继续发生时完成标记。

- 降低 `GOGC`：通常减少堆内存占用，但增加 GC 频率及 CPU 开销。
- 提高 `GOGC`：通常降低 GC 频率，但允许堆使用更多内存。
- `GOGC=off`：关闭由该增长比例驱动的自动 GC；内存软限制仍可能触发 GC。

### 3.2 GOMEMLIMIT

Go 1.19 起支持 `GOMEMLIMIT`，也可以通过 `runtime/debug.SetMemoryLimit` 设置运行时管理内存的软限制。例如：

```sh
GOGC=100 GOMEMLIMIT=512MiB ./app
```

其中 `./app` 表示已构建的程序。该限制大致对应 `runtime.MemStats.Sys - runtime.MemStats.HeapReleased`，不等同于进程 RSS，也不包含所有由 C 库等外部组件分配的内存。

容器环境应为外部内存及使用波动预留余量。如果存活对象本身接近或超过限制，GC 无法回收它们；过低的限制可能导致频繁回收，而软限制仍可能被突破。

### 3.3 主动触发

`runtime.GC()` 会触发一轮垃圾回收并等待其完成。它可用于特定实验或诊断，但频繁调用可能带来额外开销，应先通过测量确认必要性。

## 4. 观察与排查

### 4.1 GC 跟踪

```sh
GODEBUG=gctrace=1 ./app
```

GC 跟踪信息输出到标准错误，可用于观察回收频率、各阶段耗时、堆变化和目标堆大小。字段格式可能随版本变化，具体解释参见对应版本的 `runtime` 文档。

### 4.2 内存与 CPU 分析

- 使用 `go test -bench=. -benchmem` 观察已有基准测试的 `B/op` 和 `allocs/op`。
- 使用内存 profile 的 `alloc_space` 查找累计分配热点，使用 `inuse_space` 查找仍被保留的对象。
- 使用 CPU profile 和执行追踪判断并发标记、标记辅助及暂停对实际请求的影响。

判断内存问题时，应分别观察存活堆、运行时管理内存和进程 RSS，避免仅凭一个指标判断是否存在内存泄漏。

## 5. 常见优化方向

- 减少热点路径中不必要的临时对象分配，并通过基准测试验证收益。
- 为已知容量的切片或 map 合理预分配，避免过度预留导致内存长期占用。
- 检查缓存、全局引用和未退出的 goroutine 是否长期持有对象。
- 保存大切片的一小部分时，评估是否需要复制以解除对整个底层数组的引用。
- 使用 `sync.Pool` 前先确认存在适合复用的临时对象；池中的对象可能被运行时移除，不适合作为持久缓存。

优化应同时比较 CPU、内存和延迟。减少分配次数并不总意味着整体性能改善。
