# 协调

协调（Coordination）用于管理多个进程或节点对共享资源、任务和角色的访问，明确谁有权操作、如何交接，以及旧持有者失效后如何处理。

## 1. 核心问题

| 问题 | 示例 |
| --- | --- |
| 互斥 | 多个调度器不能同时为同一任务创建冲突的分配。 |
| 所有权 | 明确任务、资源或主节点角色当前属于哪个实例。 |
| 交接 | 原持有者退出或失联后，其他实例如何接管。 |
| 失效隔离 | 已失去权限的旧实例恢复运行后，不能继续产生有效写入。 |

共享状态需要由各参与者共同认可的权威存储或协议维护，不能只依赖某个进程的内存判断。

## 2. 常见机制

- [分布式锁](distributed-lock/DistributedLock.md)：限制多个进程或节点对同一临界区或资源的并发访问。
- [租约](lease/Lease.md)：在有限时间内授予权利，通过续约维持，超时后允许回收。
- **选主**：从多个候选者中确定负责协调或处理特定工作的实例。
- **Fencing**：由资源端检查执行代次或有效凭证，拒绝旧持有者的操作。

这些机制可以组合使用。例如通过租约维护主节点角色，同时对它提交的写入进行代次校验。

## 3. 与故障检测的关系

故障检测关注参与者是否可能失联；协调关注它是否仍有权访问某项资源。节点在线不意味着持有任务执行权，心跳超时也不能证明旧进程已经停止。

接管流程需要明确撤销或等待旧权利失效，并保护资源免受延迟到达的旧操作影响。

## 4. 正确性与可用性

网络分区或协调存储不可用时，系统需要选择是否暂停获取、续约和写入。若无法确认所有权仍有效，继续执行可能与新持有者发生冲突。

设计时应明确原子操作、身份校验、过期语义、失败重试与结果去重的边界，不能仅凭“有一把锁”就推断整个业务流程安全。
