# 分布式锁

分布式锁（Distributed Lock）用于协调多个进程或节点对同一共享资源的访问，使遵循协议的参与者在有效持锁期间互斥执行受保护操作。

## 1. 数据与参与者

| 要素 | 作用 |
| --- | --- |
| 资源标识 | 确定哪些请求竞争同一把锁，例如订单 ID 或任务 ID。 |
| 持有者标识 | 区分每次成功获取锁的实例或请求。 |
| 协调存储 | 原子判断资源是否可用，并维护当前持有者。 |
| 有效期 | 采用租约时限制持有时间，避免故障后无限占用。 |

同一资源必须使用一致的锁标识。不同锁标识之间不会自动产生互斥关系。

## 2. 生命周期

```text
尝试获取锁
    ├─ 失败 → 返回或有界退避重试
    └─ 成功 → 执行受保护操作
                ├─ 时间较长 → 校验身份后续约
                └─ 完成 → 校验身份后释放
```

获取结果不确定时，例如请求超时，不能直接假设已持锁并进入临界区。正常异常退出路径都应尝试释放，但也需要为进程崩溃提供超时或会话失效机制。

## 3. 租约与续约

很多分布式锁采用租约限制持有时间。工作超出原有效期时，需要在期限内申请续约；确认失效后应停止依赖该锁的操作。

续约和释放都应验证本次授予的身份，不能仅凭资源名称操作。租约失效不会自动停止旧持有者的进程，定时续约也不能消除长暂停和网络分区风险。

## 4. 失效后的资源保护

```text
A 持锁 → A 暂停 → 锁到期 → B 获取锁
                                    ↓
                             A 恢复后仍可能写入
```

锁服务认为 B 持锁，并不意味着资源能识别 A 的旧请求。严格场景需要资源端配合，例如检查单调递增的 fencing token、校验当前执行代次或采用条件写入。

业务幂等与唯一约束可以限制重复效果，但不能不加分析地当作所有互斥问题的替代方案。锁的随机身份 token 也不等于有顺序语义的 fencing token。

## 5. 实现方案

- [Redis](Redis.md)：通过 `SET NX PX` 获取带有效期的锁，使用 Lua 校验释放和续约，并分析复制与故障切换边界。
- 数据库锁或条件更新：依赖数据库事务、约束及连接生命周期管理访问。
- 一致性协调服务：通过会话、租约或有序节点维护持有者，需要结合具体服务保证设计接管流程。

选型取决于是否只是减少重复工作，还是必须保护不可重复、不可并发的业务效果。不能仅比较获取锁的速度。

## 6. 设计检查

- 明确保护的资源、临界区和所有参与者，避免绕过协议访问。
- 确认获取、续约和释放的原子性及身份校验规则。
- 处理超时、崩溃、暂停、网络分区和协调服务故障切换。
- 使用有界等待、退避与随机抖动，减少集中竞争；不默认保证公平或可重入。
- 将锁释放与业务提交区分开，外部副作用仍需幂等或其他一致性保护。
