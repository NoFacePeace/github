# Plan-and-Execute

Plan-and-Execute（规划与执行）先为任务制定计划，再按计划实施，并在获得新信息后按需重新规划。通俗理解是“先列步骤，再动手”。

## 1. 基本过程

```text
明确任务 → 调查并制定计划 → 执行步骤 → 检查结果
                    ↑                     ↓
                    └── 情况变化：重新规划 ─┘
                                          ↓
                                    完成：交付结果
```

例如，修复登录报错的初始计划可以是：复现问题、检查认证逻辑、修改代码、运行测试。如果调查发现问题来自数据库连接，则应调整计划，而不是继续机械执行原步骤。

## 2. 与其他概念的区别

| 概念 | 区别 |
|---|---|
| Plan 工作模式 | 通常停留在研究和提出方案，暂不实施 |
| ReAct | 强调根据每次行动反馈逐步决定下一步，不要求先形成整体计划 |
| Workflow | 强调显式流程及其执行规则，计划强调当前任务的具体步骤 |

这些方式可以结合：整体采用规划与执行，各步骤内部使用 ReAct；固定工作流也可以包含生成计划、实施计划和检查结果的阶段。

## 3. 使用特点

适合目标较复杂、需要协调多个步骤的任务。计划应包含可验证的结果，并允许根据事实更新；列完全部步骤不等于任务已经完成。

## 4. 计划由谁提供

通常不需要用户提供完整计划。用户说明目标与必要约束后，Agent 可以调查任务背景并生成计划。例如，用户要求“修复登录报错，不改数据库结构”，Agent 再确定复现、定位、修复和验证的具体步骤。

用户也可以提供计划或指定步骤顺序。Agent 应在这些约束内推进，发现问题时提出调整；缺少影响方案的关键信息时，再向用户澄清。

## 5. 常见实现

### 5.1 生成并保存计划

基础实现可以使用同一个模型完成规划与执行，不要求单独训练规划模型。程序向模型提供目标、上下文和可用工具，模型调查后生成计划。

计划可以保存在对话上下文、Markdown 文件、内存对象或数据库中。需要跟踪进度时，可以使用结构化数据，例如：

```json
{
  "goal": "修复登录报错",
  "steps": [
    {"id": 1, "task": "复现问题", "status": "completed"},
    {"id": 2, "task": "定位原因", "status": "in_progress"},
    {"id": 3, "task": "实施修复", "status": "pending"},
    {"id": 4, "task": "运行测试", "status": "pending"}
  ]
}
```

复杂实现还可以记录步骤依赖、验收条件、执行结果和计划版本。具体字段由系统设计决定，不存在统一格式。需要跨进程重启恢复时，应将状态持久化保存，仅保存在内存中不足以恢复。

### 5.2 Agent 请求更新，程序负责保存

常见做法是提供计划更新工具，例如 `update_plan`。Agent 根据任务进展请求新增步骤、调整顺序或更新状态，程序校验请求后保存，再向 Agent 和界面提供最新计划。

```text
Agent 决定如何调整计划
          ↓
调用计划更新工具
          ↓
程序校验并保存修改
          ↓
界面刷新，后续执行读取最新计划
```

工具名称及更新方式只是实现选择。有的工具整体替换计划，有的支持局部更新；简单实现也可以允许 Agent 直接编辑计划文件。

### 5.3 执行与重新规划

程序或 Agent 读取目标和当前计划，选择下一步执行，并结合实际结果更新状态。发现前提不成立、新依赖或执行失败时，可以修改计划后继续。

```text
读取目标与计划 → 选择步骤 → 执行 → 验证结果
                     ↑                ↓
                     └── 更新状态或重新规划
                                      ↓
                               完成或满足停止条件
```

单个步骤内部可以使用 ReAct，通过多次工具调用完成工作。计划更新工具通常只维护状态，不会因为某一步被标记为进行中就自动执行该步骤；具体推进仍需 Agent 或调度程序完成。

### 5.4 状态展示与实际完成

界面上的步骤和进度通常来自计划数据，但展示了计划不等于系统会严格按计划执行。需要在执行循环中读取并使用计划，才能让它持续指导行动。

同样，将步骤标记为完成只是状态更新，不能代替结果验证。程序可以校验字段是否合法、状态是否符合规则；任务是否真正完成，还需要测试结果、产物或其他验收证据。

## 6. Plan 工作模式的实现边界

Plan 工作模式通常在生成和展示方案后等待用户确认，Plan-and-Execute 则包含后续执行循环。是否必须确认由产品行为和已有授权决定，规划本身不要求每一步都向用户确认。

如果产品承诺规划期间不实施项目改动，就需要在工具权限或执行校验层限制写入和其他实施性操作，不能仅依靠提示词要求模型“不要修改”。若允许保存计划文件，则应明确其写入范围。
