# 摘要压缩

摘要压缩（Summarization）是将对话历史和执行过程整理为简短摘要，再用摘要替换后续模型输入中的详细消息的一种上下文压缩方式。摘要通常由模型生成，运行时负责选择消息、调用模型和组装后续上下文。

## 1. 基本流程

1. 在上下文接近预设阈值或任务阶段切换时触发压缩。
2. 划分需要生成摘要的旧历史和继续保留原文的近期消息。
3. 调用模型，根据旧历史及已有摘要生成新的任务摘要。
4. 将有效指令、任务摘要、近期原文和当前输入组织为后续上下文。
5. 继续执行；需要细节时，按引用读取保留在外部的原始记录。

生成摘要通常需要一次额外模型请求。摘要可以保存为 checkpoint，用于后续加载和恢复；checkpoint 是保存形式，不是另一种压缩方式。

## 2. 摘要内容

- 用户目标、有效约束、纠正意见和授权范围。
- 已确认的事实、关键决策及其依据。
- 已完成的工作、验证结果和当前进度。
- 尚未解决的问题、待验证假设和下一步行动。
- 必须准确保留的路径、标识、命令、数值及外部记录引用。

摘要需要区分已确认事实与推测，记录重要的失败原因，避免后续 Agent 把假设当成结论或重复已经失败的尝试。

## 3. 近期消息的保留

常见方式是“旧历史摘要 + 近期原文”。近期范围可以按对话轮次、消息块或 Token 预算选择，不一定等于上一轮完整对话。

按 Token 预算保留时，较长的一轮可能只有后半段保留原文，用户输入和前面的过程进入摘要。这时需要由摘要补足近期消息的任务背景。

切分边界应维护模型接口要求的消息结构，避免将工具调用移入摘要，却把对应结果单独留在原文中。对于当前最新输入，可以单独保留，不纳入旧历史摘要；这是需要由运行时明确实现的保留策略，并非摘要压缩自动提供的保证。

## 4. 示例

压缩前：

```text
用户：排查 API 延迟，只读检查，不要修改生产配置。
助手：先检查服务指标。
工具：大量指标数据……
助手：P99 从 200ms 上升到 2s，继续检查数据库。
工具：大量慢查询记录……
助手：未发现明显慢查询，继续检查连接池。
工具：连接池使用率和等待时间……
助手：连接池使用率达到 100%，请求在等待连接。
用户：再确认是不是连接泄漏。
助手：调用工具读取连接获取与释放逻辑。
工具：相关代码……
```

压缩后，后续模型输入中的相关部分：

```text
[旧历史摘要]
目标：排查 API 延迟升高。
约束：仅允许只读检查，不得修改生产配置。
已确认：P99 从 200ms 上升到 2s；未发现明显慢查询；
连接池使用率达到 100%，存在连接等待。
待验证：是否存在连接泄漏，尚未确认根因。

[近期原文]
用户：再确认是不是连接泄漏。
助手：调用工具读取连接获取与释放逻辑。
工具：相关代码……
```

## 5. 局限与配合机制

摘要可能遗漏细节或改变原意，多次基于旧摘要生成新摘要也可能累积偏差。影响后续判断的精确数据和证据应保留原文或可访问的引用。

- 裁剪：移除旧消息时维护必要约束和工具配对。
- 外置：保存详细记录，使摘要未覆盖的内容仍可按需读取。

保存摘要不会自动减少已经进入模型上下文的内容；运行时还需要在后续请求中用摘要替换旧历史。原始记录可以继续保留，供审计和恢复使用。
