# Agent 故障恢复

故障恢复（Recovery）是 Agent 在进程退出、工具超时、网络断开或执行中断后，依据持久化记录与实际环境状态，判断已完成的工作并继续执行的机制。核心问题是避免丢失进度、重复产生副作用，以及让会话记录与实际状态保持一致。

## 1. 恢复对象

| 对象 | 需要恢复或确认的内容 |
|---|---|
| 会话与模型上下文 | 用户目标、历史消息、工具请求与结果，以及下一次模型调用需要的信息 |
| 运行状态 | 当前步骤、工具调用标识、执行状态和重试次数 |
| 外部状态 | 文件、数据库记录、远程任务等是否已经被修改 |
| 执行结果 | 已完成操作的输出是否已持久化，能否重新交付给模型 |

保存会话不等于具备完整的故障恢复能力。会话记录可能停留在工具请求，而文件修改或远程操作已经完成。

## 2. 工具调用的崩溃窗口

以修改文件为例，一次工具调用可以拆成以下阶段。实际系统的持久化边界可能不同：

```text
记录工具调用意图 → 修改文件 → 持久化工具结果 → 将结果交给模型
```

| 中断位置 | 恢复时的判断 |
|---|---|
| 已记录意图，尚未修改文件 | 确认没有副作用后，可以重新执行 |
| 文件已修改，结果尚未持久化 | 完成状态未知，需要核对文件，不能仅凭缺少结果判定失败 |
| 结果已持久化，尚未交给模型 | 可重用已保存结果，避免再次修改文件 |
| 文件写入过程中 | 是否存在部分写入取决于工具实现，需要校验文件完整性 |

工具调用缺少结果，只能说明缺少完成记录，不足以证明操作没有发生。反过来，将悬挂调用标记为失败，也不意味着外部修改已被撤销。

## 3. 恢复机制

### 3.1 持久化执行与检查点

持久化执行保存运行进度、工具调用和结果，使重启后的运行能够识别已经完成的步骤。要跨进程恢复，记录必须存入能跨重启保留的存储中。

检查点可以保存会话状态、运行状态或文件快照；具体恢复范围取决于实现。保存文件快照可以帮助回滚，但不自动保证文件修改与会话记录作为同一个事务提交。

### 3.2 状态核对

对有执行意图、没有完成结果的调用，应根据实际环境核对操作是否完成。文件编辑可以记录修改前的摘要和预期修改后的摘要，并在恢复时比较当前文件：

| 当前文件状态 | 可采用的处理方式 |
|---|---|
| 与修改前一致 | 在确认没有仍在执行的写入者后，按原前提重试 |
| 与预期修改后一致 | 将目标状态视为已达成，记录核对依据并补记完成状态 |
| 与两者都不一致 | 标记冲突，重新读取并判断，避免覆盖其他修改 |

以上是设计示例，不代表所有 Agent 都采用该实现。内容一致只能证明当前目标状态，未必能证明是哪次调用造成的；格式化、并发编辑和多文件修改也需要额外处理。若原始输出无法重建，应明确记录恢复后的核对结果，不伪造原始工具输出。

### 3.3 重试与幂等

幂等要求同一逻辑操作重复执行时，不会重复产生预期之外的副作用。例如，确保配置项具有指定值，比无条件向文件追加一行更容易安全重试。

- 为同一逻辑操作使用跨重试稳定的幂等键，将每次尝试的标识单独记录。
- 调用方传入幂等键后，工具或外部服务必须实际执行去重；仅记录一个键不构成幂等保证。
- 超时不代表原操作已经停止。重试前应确认原执行是否仍在运行，必要时通过锁、租约或 fencing token 阻止旧执行者继续写入。
- 非幂等且无法核对的操作，应保留“结果未知”状态，交由专门的恢复流程或人工处理。

### 3.4 回滚与补偿

回滚通过快照等方式恢复先前状态；补偿通过后续操作修正已发生的副作用，例如撤销远程创建的资源。两者都需要考虑并发修改，补偿本身也可能失败。

正常取消可以执行清理逻辑；进程被强杀时，`catch`、`finally` 或退出回调可能没有机会运行。因此，内存中的撤销信息和正常取消路径不能代替重启后的恢复机制。

## 4. 一致性与执行语义

文件修改、远程请求和工具结果记录通常分属不同存储边界。若没有共同事务或外部系统配合，就存在“副作用已发生、完成记录未保存”的窗口。

| 语义 | 含义与代价 |
|---|---|
| 至多一次（At-most-once） | 避免重复执行，但不确定的操作可能无法完成 |
| 至少一次（At-least-once） | 允许重试，副作用可能重复，需要幂等或去重 |
| 恰好一次效果（Exactly-once effect） | 通常需要事务、稳定的操作身份及目标端原子去重等条件，不能仅靠 Agent 检查点保证 |

恢复流程需要分别回答：会话能否继续、工具是否执行过、外部状态是否正确，以及操作能否安全重试。

## 5. 相关实现

以下区分已公开的行为与实现范围，不将正常中断处理等同于任意崩溃下的一致性保证。

- [Claude Code 检查点机制](../../../ecosystem/anthropic/claude-code/Checkpointing.md)：支持文件快照、代码与对话回退；官方使用文档未说明文件写入与工具结果记录之间的事务保证。
- [OpenCode 工具调用恢复源码](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/session/runner/llm.ts#L401-L424)：查询于 2026-11-02 的 `dev` 分支中，`settleStaleToolCalls()` 将遗留的 `streaming`、`running` 工具调用标记为中断失败；该函数没有核对或回滚文件。分支内容可能变化。
- [Cline v3.0.0 源码](https://github.com/cline/cline/blob/v3.0.0/src/core/Cline.ts)：恢复历史时补齐旧格式调用缺失的中断结果，并提示模型重新评估；正常中断流程会尝试撤销仍处于编辑中的文件。该版本先保存文件再构造工具结果，不能据此认为强杀后会自动撤销所有修改。
- [Conductor 故障语义](https://docs.conductor-oss.org/devguide/ai/failure-semantics.html#tool-call-fails-after-side-effects)：明确讨论副作用发生后、worker 报告完成前崩溃的情形；配置重试可能导致重复执行，需要幂等操作或补偿。

### 5.1 Codex App Server

依据 [Codex App Server 官方文档](https://learn.chatgpt.com/docs/app-server)，核对日期为 2026-11-02：

| 接口 | 已公开的行为 |
|---|---|
| `thread/resume` | 继续已有会话 |
| `turn/interrupt` | 请求取消进行中的轮次；成功后轮次以 `interrupted` 状态结束 |
| `thread/revert` | 从持久化分页会话的历史中移除指定轮次及后续轮次，不撤销本地文件修改 |

这些接口说明了会话继续、中断和历史撤回的行为，但该文档未说明“文件已修改、工具结果尚未持久化就崩溃”时，如何核对文件、补齐结果或避免重复执行。因此，不能据此推断 Codex 会自动回滚文件，或保证该窗口内的操作不会重复；具体策略仍需核对对应版本的源码。
