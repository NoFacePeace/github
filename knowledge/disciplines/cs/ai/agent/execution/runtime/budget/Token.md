# Agent Token 预算

Token 预算限制模型处理的信息量或任务累计消耗。需要分别管理上下文容量、单次输出和整轮累计用量，避免将三者混为同一个数值。

## 1. 三种口径

| 口径 | 限制对象 | 达到限制时的典型处理 |
|---|---|---|
| 上下文预算 | 某次调用携带的输入及需要预留的生成空间 | 裁剪、压缩、减少工具定义，或拒绝调用 |
| 单次输出预算 | 一次请求允许生成的 Token | 接口停止生成，检查是否被截断 |
| 任务累计预算 | 多次请求的输入与输出用量之和 | 收尾或停止发起新调用 |

不同模型可能采用输入输出共享窗口或分别限制的口径，应依据接口定义计算。系统指令、历史消息、工具定义和工具结果都可能占用输入预算；图片、音频等按接口规则计量。

## 2. 累计用量

```text
任务累计 Token = 各次调用输入 Token 之和 + 各次调用输出 Token 之和
```

每次重新发送历史上下文都计入该次输入。例如，两次请求分别使用 10,000 输入加 1,000 输出、12,000 输入加 2,000 输出，累计消耗为 25,000 Token。

应依据接口返回的实际用量统一口径：

- 输出用量已经包含推理 Token 时，不再额外相加。
- 输入用量已经包含缓存命中 Token 时，不重复计入；缓存的计费折扣单独处理。
- 摘要、重试和子 Agent 调用按任务归属结算，失败请求存在消耗时也需要记录。
- 用量未知时标记为待确认，不能直接当作零。

## 3. 预留与结算

调用前估算输入并预留本次输出额度，同时检查模型容量与任务剩余预算。输出上限应由模型能力、剩余上下文和任务可用额度共同约束。

并发请求需要原子预留；请求结束后，用实际用量结算并释放未使用的额度。Token 估算误差或服务端缺失用量可能导致差异，应保留余量并明确预算精度。

达到输出上限后，响应可能只生成了部分 JSON、代码或工具参数。运行时应检查结束原因和结构完整性，不能因为请求成功返回就认定任务完成。

## 4. 压缩与恢复

裁剪或压缩上下文可以减少后续请求的输入，但不会清零历史累计消耗；生成摘要本身也会产生用量。要求完整保留信息的任务应明确压缩策略或直接拒绝超限调用。

预算账本应持久保存，暂停、恢复和子任务结束后继续累计。接近软预算时预留收尾额度，硬上限后停止新调用并说明未完成事项。

## 5. 如何设置

根据代表性任务的输入输出分布、成功率和超限率设置预算，不将模型窗口直接当作整轮任务额度。不同模型的分词方式不同，Token 也不能固定换算成汉字数。

累计 Token 适合控制用量，但不同计费类别单价不同，仍需单独管理费用。
