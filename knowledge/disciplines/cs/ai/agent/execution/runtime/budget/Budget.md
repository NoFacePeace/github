# Agent 执行预算

执行预算（Budget）是运行时对 Agent 完成一次任务所能消耗的资源设置的限制，用于控制成本、执行时间和循环次数。它约束执行过程，也可以作为产品配额的一部分。

## 1. 预算范围

| 范围 | 限制对象 | 主要目的 |
|---|---|---|
| 单次模型调用 | 输入容量、输出长度 | 避免上下文超限，控制单次生成消耗 |
| 一轮用户任务 | 多次调用累计的 Token、费用、步数和时间 | 防止任务持续重试或消耗失控 |
| 会话或账号 | 跨任务累计的费用和资源用量 | 管理整体配额 |

一轮用户任务通常从用户提交要求开始，到 Agent 返回结果、暂停或失败结束，中间可能调用模型和工具多次。具体边界需要由应用定义；任务跨多次运行、恢复或用户确认继续时，应明确预算是否延续。

## 2. 预算类型

| 类型 | 限制内容 | 主要作用 |
|---|---|---|
| [步数预算](Step.md) | 执行循环或模型调用次数 | 限制循环和反复重试 |
| [Token 预算](Token.md) | 上下文容量、单次输出和任务累计 Token | 控制容量与用量 |
| [费用预算](Cost.md) | 模型、工具与外部服务的累计成本 | 控制任务成本 |
| [时间预算](Time.md) | 请求、工具、子任务及整个任务的时长 | 限制等待与持续执行 |

各文档分别说明统计口径、执行方式和超限处理。多种预算可以同时生效，不能通过一种预算直接推断其他资源的消耗。

## 3. 单次调用与任务预算的配合

单次调用需要同时满足模型容量和任务剩余预算。对于输入、推理和输出共享窗口的模型，应为输出预留上下文空间；对于分别计算输入与输出上限的接口，应遵循对应口径。

调用前可以使用 Tokenizer 或估算方法预测输入用量，并通过模型接口设置输出上限。调用后使用实际用量校正账本。达到输出上限通常表现为截断，应检查结束原因，避免将不完整的 JSON、代码或工具参数当作完整结果。

```text
检查任务剩余预算
    ↓
估算输入并预留输出、费用和并发额度
    ↓
设置本次调用限制并执行
    ↓
读取实际用量，结算并释放未使用的预留额度
    ↓
继续执行 / 进入收尾 / 停止
```

只在调用结束后检查预算，可能在最后一次调用中超出上限。输入估算误差、远程取消延迟和计费延迟也会影响硬上限的精度，需要预留余量并明确保证范围。

## 4. 软预算与硬上限

| 机制 | 到达后的行为 |
|---|---|
| 软预算 | 进入收尾阶段，停止扩展任务，保存进度并整理已有结果 |
| 硬上限 | 停止发起受限调用，保存状态并说明停止原因 |

收尾本身可能需要调用模型，因此应提前保留收尾额度，或在没有额度时使用已有状态生成确定性的进度说明。

停止时应区分“任务完成”和“预算耗尽”，记录已完成工作、未完成事项、产物及可恢复位置。用户选择继续后，应明确追加多少预算或是否新建预算周期，避免恢复过程隐式绕过限制。

## 5. 并发与子 Agent

- 根任务统一管理总预算，各子 Agent 可以具有独立子预算，但消耗仍计入根任务。
- 并发调用前原子预留额度，避免多个执行者同时使用同一份剩余预算。
- 调用完成后按实际用量结算；失败、超时或取消的请求也可能产生费用，不能一律记为零。
- 子 Agent 的步数、并发数和时间限制可以独立设置，不能直接当作根任务的总消耗限制。
- 预算状态应持久化，恢复后继续结算，避免重启导致累计用量丢失。

## 6. 如何设置预算

没有适用于所有 Agent 的统一 Token、步数或费用标准。可以按以下流程确定：

1. 明确任务类型、成功条件和可接受成本。
2. 使用代表性任务测量成功率、调用次数、输入输出用量、费用和执行时间。
3. 按任务类型设置软预算与硬上限，观察用量分位数和超限率。
4. 根据成功率、成本及等待体验调整，并为长任务提供保存进度和继续执行的机制。

步数、Token、费用和时间可以同时限制，任一达到相应边界就触发处理策略。经验数字只能作为实验起点，不应直接当作生产环境的通用默认值。
