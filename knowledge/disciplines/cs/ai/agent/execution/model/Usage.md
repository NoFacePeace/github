# 模型用量

Usage 表示单次模型调用实际消耗的 Token，由提供商返回并经过适配器归一化。它用于用量展示、成本估算和任务预算结算，不是调用前设置的生成上限。

## 1. 数据结构

以下为内部接口示例，不是某个提供商的原生字段格式：

```ts
type Usage = {
  inputTokens?: number;
  outputTokens?: number;
  totalTokens?: number;
  cacheReadTokens?: number;
  cacheWriteTokens?: number;
};
```

| 字段 | 含义 |
|---|---|
| `inputTokens` | 本次调用的输入用量，归一化后包含缓存输入 |
| `outputTokens` | 本次调用的输出用量，按接口口径包含计入输出的推理 Token |
| `totalTokens` | 本次调用的输入与输出总量 |
| `cacheReadTokens` | 输入中命中缓存的数量 |
| `cacheWriteTokens` | 输入中按提供商规则写入缓存的数量 |

字段缺失表示用量未知或未提供，不能直接当作零。只有输入和输出用量都已知且统计口径一致时，才可以用两者之和补充缺失的 `totalTokens`。

## 2. 与输出上限的区别

| 概念 | 示例命名 | 含义 |
|---|---|---|
| 模型输出限制 | `modelMaxOutputTokens` | 模型接口最多支持生成多少 Token |
| 用户输出限制 | `outputTokenLimit` | 用户或管理员允许单次生成多少 Token |
| 最终请求上限 | `effectiveMaxOutputTokens` | 综合模型能力、配置及可用预算后，本次请求采用的上限 |
| 实际输出用量 | `usage.outputTokens` | 本次调用实际生成的数量 |

例如，模型支持输出 128,000 Token，用户设置 8,000 Token，并且上下文与任务预算都足够，则最终请求上限为 8,000 Token。模型生成 500 Token 就结束时，实际用量是 500，而不是 8,000。

推理模型的输出统计可能包含不可见的推理内容，因此 `outputTokens` 不一定等于用户可见回答的 Token 数量。

## 3. 统计口径与归一化

- 输入包括系统指令、历史消息、工具定义和工具结果等，不能只统计用户最后一条消息。
- 每次重新发送的历史上下文都计入该次输入；缓存命中也可能产生计量和费用。
- 提供商若将普通输入、缓存读取和缓存写入分别报告，适配器需要按明确口径合并为 `inputTokens`；若原始输入已包含缓存，不得重复相加。
- 缓存字段用于描述输入构成或计费类别，不再加到 `totalTokens` 上；不同缓存类别是否互斥由提供商定义，不能自行假定。
- 推理用量已经包含在输出统计时，不再额外相加。需要展示明细时，可扩展独立字段并注明与输出总量的关系。
- 费用需要结合模型、价格和计费类别计算，不能仅依据 `totalTokens` 使用统一单价。

## 4. 流式与缺失用量

流式用量可能在文本生成结束标记之后的独立片段中到达。适配器应收齐预期结束信息和用量，再交给运行时记录；消费者仍需完整消费事件流，以捕获后续异常。

同一次调用可能同时存在中间统计和最终统计。应明确片段表示增量还是累计值，避免把多个累计值与最终值重复相加。

网络中断、取消或服务端错误可能导致无法获取完整用量。这不等于没有消耗，应记录统计完整性，必要时保留待核对状态。生成被截断时，已发生的消耗仍应计入。

## 5. 任务累计

运行时按调用标识记录用量，再汇总到任务。摘要、内部评审、重试及子 Agent 的调用应按任务归属分别入账；同一条用量记录不能重复结算。

已知用量之和只能表示已确认的消耗。存在缺失记录时，应同时展示统计不完整状态，不能将其当作任务的精确总量。压缩上下文、暂停或恢复执行，都不会清零已经发生的消耗。
