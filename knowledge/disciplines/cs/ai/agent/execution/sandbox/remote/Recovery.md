# 远程沙箱节点故障与恢复

节点故障恢复是执行节点失联、宕机或被回收后，在健康节点上重新提供环境并继续任务的过程。环境可重建、磁盘可恢复和任务可续跑是不同层次的保证。

## 1. 恢复层次

| 能力 | 故障后的行为 | 主要限制 |
|---|---|---|
| 重新调度 | 在健康节点创建新环境，再启动任务 | 原节点的本地文件与内存不会自动恢复 |
| 磁盘恢复 | 新环境挂载原持久卷，或从文件快照恢复 | 进程需要重启；未持久化写入可能丢失 |
| 检查点恢复 | 恢复已保存的应用、进程或 VM 状态 | 可能丢失检查点之后的进度，受运行时与设备兼容性限制 |
| 无损接管 | 尽量保留故障瞬间的执行状态并继续服务 | 需要额外复制与接管机制，不能由普通快照推导得到 |

正常暂停恢复和计划内热迁移都需要源节点参与。它们不自动保证源节点突然断电后的恢复能力；此时只能使用故障前已可靠保存或复制的状态。

## 2. 块存储的作用

接入块存储后能否恢复，取决于数据是否独立于故障节点、卷能否由其他节点接管，以及应用写入是否已经达到所需的持久化边界。节点本地块设备不天然具备跨节点恢复能力。

| 对象 | 接管持久化块存储后的结果 |
|---|---|
| 已按存储持久化语义写入的代码、文件和产物 | 通常可以恢复，仍需校验完整性 |
| 应用缓冲区或未确认持久化的写入 | 可能丢失 |
| 数据库文件 | 需要数据库通过 WAL、事务恢复等机制恢复一致状态 |
| 进程内存与正在运行的命令 | 不会仅因挂载磁盘而恢复，需要重启或检查点 |
| TCP、SSH、WebSocket 连接 | 通常需要重连 |
| Agent 会话与任务进度 | 需要事先保存到该卷或独立持久化服务 |

普通文件写入成功不一定代表已经落到故障后可恢复的介质。应用需根据文件系统、数据库和存储的语义使用适当的刷盘、事务提交或检查点机制；多文件业务一致性也不能只靠文件系统日志保证。

多数单写块存储不能由两个节点同时安全写入。可接管的区域、卷访问模式、解绑挂载耗时及存储自身的可用性，都需要单独验证；同可用区换节点不等于跨可用区容灾。

## 3. 接管流程

```text
检测节点失联，标记当前执行状态未知
  → 确认接管权限，隔离旧节点的存储与业务写入
  → 解绑原卷，在健康节点挂载或恢复快照
  → 检查文件系统与应用数据一致性
  → 启动执行服务，恢复会话与任务检查点
  → 核对未确认完成的操作，重建连接并继续任务
```

节点失联可能只是网络分区，旧进程仍在执行。Fencing 必须实际阻止旧执行者继续写入，例如由存储撤销访问、关闭旧节点，或由目标系统校验单调递增的执行代次。仅在调度数据库标记“已切换”或获得一把过期锁，不足以保证旧进程停止。

Kubernetes 可以由控制器在其他节点重建 Pod，但不会自动搬运原进程内存。使用持久卷还需要存储驱动支持重新挂载；本地卷、卷拓扑约束和旧节点未完成解绑都可能阻止或延迟接管。

## 4. 平台能力边界

以下依据 2026-11-05 核对的公开文档，不代表特定商业合同的 SLA：

| 方案 | 已公开的相关能力 | 不能据此推断的保证 |
|---|---|---|
| E2B | 暂停保存文件系统与内存，之后恢复 | 运行节点突然宕机后的自动无损接管；所查文档未明确承诺 |
| Daytona | 持久化与快照；部分错误可从最后成功备份恢复，另一些需要替换沙箱 | 所有类型、版本都自动跨节点保留故障瞬间状态 |
| Modal Sandboxes | 文件系统及内存快照、持久化卷；退出快照属于 Beta 功能 | 退出快照不保证硬件故障时保住文件系统；官方建议更强持久性需求使用 Volumes |
| gVisor / Kata / Firecracker | 隔离与运行能力，部分组合提供检查点机制 | 不配套调度、存储和恢复控制面就自动完成节点接管 |

Modal Functions 在抢占后按原输入重新执行的机制，与 Sandboxes 的故障接管不同。CPU Sandbox 不被正常抢占，也不表示其宿主机不会发生硬件故障。

## 5. 任务续跑与恢复指标

会话状态与工作文件通常处于不同持久化边界。任务可能已经修改文件或提交远程请求，但还没有保存完成记录。恢复后需要核对实际结果，再决定补记、重试或人工处理；具体见 [Agent 故障恢复](../../recovery/Recovery.md)。

编程 Agent 可将环境定义保存在镜像与模板中，工作文件保存到持久卷，会话、工具调用和进度保存到外部数据库，并为长任务设置检查点。恢复时重新启动服务和未完成步骤，对外部写入使用幂等或去重机制。

| 指标 | 需要明确的问题 |
|---|---|
| RTO：恢复时间目标 | 从故障发生到环境和任务重新可用，最多允许多久 |
| RPO：恢复点目标 | 故障后最多允许丢失多少时间范围内的进度或数据 |
| 自动化范围 | 自动恢复环境，还是连应用重启、状态核对与任务续跑也自动完成 |

RTO 包括故障检测、旧节点隔离、调度、卷接管、启动和应用恢复的耗时。RPO 取决于写入确认、复制与检查点策略，不能只根据“使用持久卷”判断为零。

验证时应覆盖节点强制断电、网络分区、写入过程中故障及接管后旧节点恢复，而不只测试正常停止和重新启动。
