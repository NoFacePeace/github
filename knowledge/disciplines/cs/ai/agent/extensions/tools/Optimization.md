# 工具调用优化

工具调用优化是通过改进工具接口、调用上下文和执行反馈，提高 Agent 选择工具、填写参数、组织调用及完成任务的准确性与可靠性。它既涉及模型的判断能力，也涉及应用提供给模型的工具设计与执行机制。

## 1. 优化目标

| 维度 | 判断标准 | 常见问题 |
|---|---|---|
| 调用必要性 | 需要外部信息或操作时调用，否则不调用 | 遗漏必要查询，或为普通解释反复调用工具 |
| 工具选择 | 选择适合当前任务的工具 | 混淆日志查询与指标查询 |
| 参数正确性 | 参数满足结构约束和业务含义 | 时间单位错误、服务 ID 编造或选错 |
| 调用依赖 | 前置结果可用后再执行依赖调用 | 未取得服务 ID 就查询日志 |
| 结果处理 | 根据实际结果继续执行或结束 | 将空结果当成故障，将超时当成查询成功 |
| 最终效果 | 最终产物或外部状态满足任务目标 | 工具调用成功，但没有解决用户问题 |

## 2. 工具定义与接口设计

### 2.1 明确用途与边界

工具名称与描述应说明做什么、何时使用、前置条件及输出含义；容易混淆的工具需要说明区别。例如，日志查询用于获取事件记录，指标查询用于观察错误率、延迟等时序变化。

接口应围绕清晰的任务设计，避免一个工具承载大量含义不明的操作类型，也避免为完成一个简单操作暴露过多底层步骤。

### 2.2 减少参数歧义

- 写明时间格式、时区、数值单位、取值范围，以及空值的含义。
- 用枚举表示有限选项，用对象结构表达参数关系。
- 已由应用确定的参数由程序注入，减少模型重复生成或抄写。
- 资源 ID 应来自用户输入、已验证的上下文或查询结果；信息不足时先查询或澄清。

例如，`timeout_ms` 比未说明单位的 `timeout` 更明确；服务名称用于搜索，`service_id` 用于精确查询，两者需要区分。

### 2.3 区分结构约束与业务校验

JSON Schema 和严格模式可以约束参数结构。以 OpenAI Function Calling 为例，`strict: true` 用于确保参数符合受支持的 Schema 约束。

结构合法不代表业务正确：一个字符串类型的服务 ID 可能不存在，也可能属于其他服务。执行端仍需验证资源、参数间关系和权限等业务条件，并在执行操作前拒绝无效请求。

## 3. 工具调用策略

工具调用策略（Tool Calling Policy）规定是否调用、何时调用以及何时停止调用；工具选择决定调用哪个工具，参数构造决定传入什么信息，执行控制负责校验、执行和重试。

### 3.1 调用与停止条件

| 情况 | 应有行为 |
|---|---|
| 普通知识解释，现有信息足够 | 直接回答，无需调用工具 |
| 需要实时信息、私有数据或实际操作 | 调用对应工具获取证据或执行操作 |
| 缺少必要参数 | 先通过查询获取或向用户澄清，避免编造 |
| 已有结果满足任务需求 | 停止调用并输出结论 |
| 工具调用失败 | 根据错误类型恢复；达到重试上限或无法恢复时，说明限制 |

是否调用还取决于已有证据是否适用于当前问题。例如，已有结果覆盖相同资源和时间范围，且满足时效要求时，可以复用；用户询问当前状态而旧结果已经过时时，应重新查询。

### 3.2 策略落实方式

- **工具描述与 Skill**：说明触发条件、前置条件和停止条件，并针对容易混淆的情况提供正反例。
- **Workflow 与程序约束**：对已经确定的必要步骤直接执行，或按当前流程状态控制可调用工具集合。
- **执行与交付检查**：执行前检查参数和前置条件；交付前检查必要证据是否取得，避免把未验证的推测表述为查询结论。

以 OpenAI Function Calling 为例，可以通过以下配置控制调用行为：

| 配置 | 作用 |
|---|---|
| `tool_choice: "none"` | 禁止当前轮调用工具 |
| `tool_choice: "auto"` | 允许模型选择直接回答或调用工具 |
| `tool_choice: "required"` | 要求模型调用至少一个工具 |
| 指定函数 | 要求模型调用指定函数 |
| `allowed_tools` | 将可调用工具限制在指定集合内 |

`required` 只要求模型发起调用，不保证工具选择正确、执行成功或任务完成。约束应随阶段调整，例如查询完成并满足证据要求后，生成结论时无需继续强制调用。

提示词和 Skill 可以提高判断准确率，但不能单独提供绝对保证。明确的规则由程序执行和检查；开放场景中的调用必要性仍需模型判断，并通过评测持续改进。

### 3.3 示例

用户问“什么是服务错误率”时，可以直接解释；问“这个服务现在是否异常”时，需要相关实时数据。若查询失败，应说明未能确认当前状态；若现有结果已经足够，应停止重复查询。

## 4. 工具发现与选择

每个阶段优先提供与当前任务相关的工具。工具规模较大时，可以按领域分组、通过工具搜索按需加载，或根据当前流程阶段缩小可调用范围。

减少工具数量的目标是降低歧义，同时保证任务所需能力可被发现。应通过实际案例检查是否遗漏必要工具，而不是追求固定的工具数量。

## 5. 调用上下文与指引

调用时保留用户目标、已确认的资源、前置调用结果和当前约束，避免模型因缺少信息重复查询或猜测参数。

Skill 可以封装可复用的操作方法，例如如何定位服务、如何选择日志时间范围，以及如何根据错误类型继续排查。Workflow 可以约束稳定的步骤依赖和分支；需要现场判断的步骤再交给 Agent。

对于反复出现的错误，可加入少量针对性示例，并通过评测确认效果；示例过多或指令冲突也可能降低表现。

例如，查询某服务的错误日志时：

```text
用户目标：查询某服务最近的错误日志
    ↓
search_services(name)
    ↓
确定唯一服务；存在多个候选时继续消除歧义
    ↓
query_logs(service_id, start_time, end_time, level)
    ↓
读取结果，根据需要继续排查或输出结论
```

前一次调用的结果决定后一次调用的参数时，应等待结果后再调用；只有相互独立的查询才适合并行。

## 6. 结果反馈与错误恢复

工具返回应便于 Agent 区分成功、空结果、部分结果和执行失败。结果较多时提供分页或筛选方式，并明确是否截断，避免模型把部分数据当成完整证据。

错误信息应说明失败原因和可恢复条件，例如参数无效、资源不存在、权限不足或临时超时。根据错误类型处理：修正参数、重新定位资源、报告权限限制，或对临时错误进行有限重试。

查询通常可以重试；有副作用的操作需要确认执行状态，并结合幂等机制避免重复执行。请求超时并不能证明操作未发生，不应直接重复提交。

## 7. 评测与迭代

从真实任务和失败记录中整理评测案例，覆盖正常调用、无需调用、参数缺失、相似工具、多步依赖及工具失败等情况。

分别衡量工具选择正确率、参数业务正确率、依赖关系遵守情况、最终任务成功率，以及耗时和成本。调用策略还应分别检查“应该调用却未调用”和“无需调用却调用”，并观察满足需求后仍继续调用的情况。不要仅凭参数 JSON 合法或接口返回成功判断任务完成。

建议按以下顺序迭代：

1. 建立基线并定位主要失败类型。
2. 改进工具接口、描述和参数约束。
3. 补充必要上下文、Skill 指引和 Workflow 控制。
4. 在同一评测集上比较模型及其配置。
5. 当错误模式稳定、数据充足且所用模型支持时，再考虑微调。

工具接口、Skill 和 Workflow 主要改善系统整体表现；模型选择或训练可以改善模型自身的调用能力。每次调整后都应检查目标指标和已有能力是否退步。
