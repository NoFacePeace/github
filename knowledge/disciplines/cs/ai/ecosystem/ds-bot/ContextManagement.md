# DS Bot 上下文管理

DS Bot 在应用层管理长期聊天的上下文：根据占用和任务状态，选择在当前 Session 中压缩历史，或者创建新 Session 并交接工作。界面可以把多个底层 Session 显示成同一条连续聊天。

本文依据 2026-11-06 核对的项目 `main` 分支源码整理，主要涉及 `steward.js`、`parts.js` 与 `chat-index.js`。阈值与函数名属于该次核对的实现，不是固定协议。

## 1. 聊天、Session 与分段

| 对象 | 含义 |
|---|---|
| 长期聊天 | 用户在界面中持续看到的对话 |
| 当前 Session | 本次执行使用的底层会话，保存消息与运行事件 |
| Part | 长期聊天中的一个分段，对应一个底层 Session |
| Checkpoint | 当前 Session 内生成的压缩检查点，不会因此更换 Session ID |
| Handoff | 切到新 Session 时传递的交接内容 |

Bot 的私聊、它在不同群中的成员会话分别维护上下文。群本身用于转发与展示的记录会话，不按成员模型的上下文占用执行同一套阈值判断。

原地压缩与切换交接都可能生成摘要，但修改的对象不同：前者调整当前 Session 的有效上下文，后者建立新 Session，再将其设为当前分段。

## 2. 占用计量与触发

### 2.1 Token 计量

`tokensOf()` 优先使用 DSH 的 `tokenMeter.measure(session)` 获取上下文占用。计量失败时，回退到对 `session.deriveMessages()` 的文本估算。

模型窗口读取实际模型路由的 `contextWindow`；回复预留量优先取请求的 `maxTokens`，否则使用模型的默认回复上限。模型窗口配置不准确会影响触发时机。

### 2.2 检查线与硬线

`steward.js` 的 `linesFor()` 计算可用空间与两条阈值。以下为计算关系，省略参数合法性处理：

```text
W = 模型声明的上下文窗口
R = 回复预留 Token
U = max(W - R, floor(W / 2))

hard  = floor(U × 0.95)
check = min(floor(U × checkRatio), hard)
```

`checkRatio` 默认是 `0.8`。例如，窗口为 128,000、回复预留为 16,000 时：

- 可用空间为 112,000 Token。
- 默认检查线为 89,600 Token。
- 硬线为 106,400 Token。

### 2.3 检查时机

- **一轮结束后**：监听 `agent/status` 进入 `idle`，由 `checkContext()` 检查是否达到检查线。
- **每一步执行前**：监听 `agent/pre-step`，达到硬线时，在继续下一步前尝试腾出空间。
- **请求溢出时**：遇到 `CONTEXT_WINDOW_EXCEEDED`，进入新分段的恢复路径。

达到阈值不是唯一条件。代码还检查是否正在切换、是否只读、前一轮是否出错，并设置增长门槛和失败冷却。`grown()` 要求相对分段或检查点基线继续增长一定量，避免大系统提示或失败切换导致每轮重复处理。

正常情况下可以在两轮之间交接，但没有“每两轮交接一次”的固定计数规则。执行中触及硬线，也可能中途暂停并交接后续工作。

## 3. 上下文管家决策

### 3.1 请求组织

`askSteward()` 发起独立的模型请求，使用当前 Bot 的模型路由与专用系统提示词。这里的“管家”是专用判断调用，不是另外训练的模型，也不是一个长期运行的团队 Bot。

它读取近期聊天，携带以下背景：

- 当前是私聊还是群内会话。
- 是否正处于一轮执行中。
- 当前分段已经生成过多少次检查点。
- 最近用户、其他 Bot 与自身的消息。

源码最多先收集 40 条近期聊天条目，再按约 6,000 个估算 Token 的正文预算组织请求；过长单条消息保留头尾。这个预算不等于包含系统提示与输出在内的总调用量。模型支持关闭思考时，该请求使用 `off`。

### 3.2 动作选择

| 动作 | 判断方向 | 后续处理 |
|---|---|---|
| `compact` | 工作还在进行、等待结果或存在未完成要求 | 在当前 Session 中生成检查点 |
| `switch` | 当前工作已经到达可交接的停顿点 | 写交接笔记并创建新 Session |

管家输出包含 `action` 与简短原因的 JSON，由 `parseDecision()` 解析。提示词要求核对用户要求是否实际完成，并考虑尚未回答的问题，不能仅凭助手声称“完成”就判断可以切换。

如果缺少可用的压缩后端，或管家请求失败、结果无法解析，`decide()` 回退选择 `switch`。选择切换仍须经过后续可行性检查与交接处理，并不保证立刻换到新 Session。

## 4. 原地压缩

### 4.1 接入 DSH 压缩后端

`adoptEngine()` 包装 DSH 压缩服务，对 Bot Session 抑制底层自主压缩入口，由 DS Bot 决定时机。真正压缩时，`condense()` 使用 DSH 后端执行，同时通过 `writeCheckpoint()` 提供 DS Bot 的摘要内容。其他非 Bot 会话仍保留原来的压缩行为。

### 4.2 生成检查点

`writeCheckpoint()` 使用当前模型，对待压缩内容生成结构化摘要，保留：

- 已完成的结果和当前进度。
- 决策、原因及已经否决的方案。
- 用户约束、偏好与更正。
- 未完成要求和接下来的动作。
- 后续需要的精确数字、路径、标识符及错误信息。

它还会让摘要请求看到压缩区域之后仍会保留的消息，避免把已经回答的新要求误判为待办。先前检查点会合并进新摘要，新消息更正旧消息时，以新内容为准。

`keptMessages()` 从已保存记录中读取用户与其他 Bot 的输入，优先保留较新的内容，附在检查点之后；自身较早的回复主要由摘要承载。保留预算默认不超过 16,384 个估算 Token，并受检查线四分之一的限制；单条内容也有长度限制。

因此，“带上原文”只适用于预算内保留的部分，不能理解为所有历史消息都无限原样注入。

```text
压缩前：系统提示 + 早期消息与工具记录 + 近期消息
压缩后：系统提示 + 检查点摘要与保留输入 + 未被压缩的近期消息
```

### 4.3 压缩后复查

完成后重新计量占用、刷新记忆快照并记录新的增长基线。若仍未降到检查线以下，且能够通过换分段缩小请求，则尝试切换 Session。

## 5. 切换 Session 与交接

### 5.1 交接笔记

正常切换由 `writeNote()` 生成交接笔记，按目标、约束、进展、决策、关键事实、未结事项、下一步和历史查找线索组织。代码检查内容是否为空、是否被输出上限截断，以及必要章节是否存在。

新分段由 `handoffPackage()` 组装开场内容：交接笔记、预算内的近期消息、适用的较早输入摘录，以及历史查找方式。这个开场包作为历史参考，不应被当成新的用户指令。

### 5.2 状态迁移

`runSwitch()` 与 `moveOn()` 的主要流程为：

1. 保存切换状态，在维护流程中等待旧 Agent 空闲。
2. 生成交接笔记并选择携带内容。
3. 创建新 Session，设置模型、工作目录与执行权限。
4. 将旧 Session 登记为已结束分段，并更新 Bot 或群成员的当前 Session 指针。
5. 向新 Session 交付开场包，以及切换期间排队的输入。
6. 迁移相关定时任务，归档旧 Session；若旧执行尚未完成，则安排恢复。

界面通过分段记录连续展示聊天，所以用户看到的 Bot 和聊天可以不变，后台 Session ID 已经改变。

### 5.3 失败与溢出恢复

普通检查线触发的切换，如果写不出合格笔记，可以暂时保留原分段并冷却重试。达到硬线或已溢出时，代码可使用旧笔记和可携带消息回退交接；已溢出的上下文不会强求再调用模型生成新笔记。

创建新 Session 不是无损复制旧上下文。交接内容受预算和模型摘要质量限制，无法携带的细节需要从历史重新查询。

## 6. 原始记录与历史检索

原始记录保存在 DSH Session 日志中；压缩或归档不等于删除日志。`chat-index.js` 在 Bot 数据目录维护可重建的 `chat-index.sqlite`，供 `read_own_chat` 查询。

| 实现 | 用途 |
|---|---|
| SQLite FTS5 | 建立可展示聊天文本的全文索引 |
| trigram tokenizer | 支持连续三个或更多字符的子串匹配，适用于中文检索 |
| `LIKE` 回退 | 处理不足三个字符的短查询词 |
| BM25 排序 | 对全文匹配结果进行相关性排序 |
| 分段号与事件序号 | 提供定位历史消息和读取周边内容的锚点 |

索引来自日志中的聊天条目，不应等同于所有原始工具输出的完整索引。索引损坏可重建，SQLite 不可用时回退扫描日志。群内交接还会提示使用 `read_group_chat` 查询群记录，需要区分私聊历史与群记录的读取范围。

保存与索引只提供取回能力；Agent 必须实际调用读取工具，相关内容才会再次进入后续模型上下文。

## 7. 与长期记忆的区别

[上下文管理](../../agent/knowledge/context/management/Management.md)关注当前模型请求需要哪些信息。DS Bot 的三类数据不能互相等同：

| 数据 | 作用 |
|---|---|
| 检查点或交接笔记 | 让当前工作在较小上下文中延续 |
| 长期记忆 | 跨会话保留偏好、事实与决策，按 Bot、群和团队划分范围 |
| 原始聊天记录 | 保存详细历史，提供搜索与核实依据 |

摘要可能遗漏信息，连续摘要也可能累积误差。关键限制需要明确写入交接；精确代码、日志与结果，在影响判断时仍应重新读取和验证。
