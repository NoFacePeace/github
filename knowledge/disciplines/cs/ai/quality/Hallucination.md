# AI 幻觉

AI 幻觉（AI Hallucination）通常指生成式 AI 输出不真实、错误或缺乏依据的内容，并以看似确定的方式呈现。本文主要讨论大语言模型及其应用中的幻觉。

## 1. 定义与表现

常见表现包括：

- 编造不存在的论文、人物、事件、链接、函数或配置项。
- 给出错误的数字、日期、版本行为或事实关系。
- 总结资料时，加入原文未支持的观点或遗漏关键限定条件。
- 在资料不足时，用貌似合理的细节补全答案。

幻觉可以涉及事实准确性，也可以涉及依据一致性。例如，关于某产品的一句话可能符合现实，但若不在所给资料中，就不能声称该资料证明了它。

表达流畅、细节丰富或语气自信，都不能证明内容真实。用户要求的虚构创作本身不属于事实性幻觉；需要区分创作内容与事实陈述。

## 2. 产生原因

- 生成机制：语言模型依据训练中学到的规律和当前上下文生成内容，生成合理的文本不等同于核实事实。
- 知识不足或过期：训练数据、当前资料可能未覆盖问题，或不再适用于当前时间和版本。
- 输入不完整：问题含糊、存在错误前提，或缺少地区、版本、时间等必要条件。
- 资料处理错误：检索遗漏、上下文裁剪、误读原文或混合不同来源，可能导致错误结论。
- 缺少核验与退出机制：系统直接交付答案，没有检查证据，也没有在依据不足时停止。

幻觉通常不意味着模型有意撒谎。模型也不总能准确判断自己是否知道，因此不能仅依赖它自报的置信度。

## 3. 减少幻觉的方法

以下五类方法可以组合使用。前四类直接约束或检查每次回答，第五类用于衡量和持续改进整套系统。

### 3.1 提示词约束

明确任务范围、资料边界和未知信息的处理方式，要求区分事实与推测，减少无依据的补全。

```text
请仅依据下面的资料回答问题。

要求：
1. 资料不足时说明缺少什么，不要自行补全事实。
2. 每条关键事实结论标注资料编号，并保留原文的适用条件。
3. 区分资料明确说明的内容和推测；推测需说明依据。
4. 资料冲突时说明冲突，不要擅自选定结论。
5. 不要编造链接、引用、数字或 API。

资料：
[1] ……
[2] ……

问题：……
```

提示词只能引导行为，不能保证模型遵循要求或正确理解资料。模型自行生成的解释也不能作为独立证据。

### 3.2 证据支撑

在生成前提供可信且适用的资料，让关键结论能够追溯到具体证据。[检索增强生成](../rag/RAG.md) 是常见实现方式，也可以直接提供原始文档或业务查询结果。

- 保留来源标识、原文、版本、更新时间和必要的适用条件。
- 检查检索结果是否足以回答问题，而不只是主题相关。
- 为关键结论引用具体段落，检查来源是否真的支持该结论。
- 资料缺失、过期或互相冲突时，补充检索、追问或说明无法确定。

附上引用不等于证据充分。引用真实但不支持结论，或来源本身错误，同样会导致不可靠的回答。

### 3.3 工具验证

把可计算、可查询或可执行验证的内容交给相应工具，以外部结果支撑回答。

| 内容 | 验证方式 |
| --- | --- |
| 数学计算 | 调用计算器或执行计算代码 |
| 订单、库存、价格 | 查询适用的业务 API 或数据库 |
| 函数与配置项 | 检查对应版本的文档、编译或运行结果 |
| 代码行为 | 执行相关测试，检查实际产物和状态 |

工具验证还需要检查参数、查询对象、时间范围和结果解释是否正确。例如，查错订单或使用过期价格，即使调用成功也无法支持答案。工具失败时，应说明无法核实，不能补造结果。

### 3.4 程序校验

在输入、工具调用和输出环节设置确定性规则，拦截违反约束的内容。

- 结构校验：检查必填字段、类型、枚举值和 JSON Schema。
- 引用校验：检查来源编号存在，引用原文确实出现在对应资料中。
- 业务校验：检查金额范围、日期顺序、单位和跨字段关系。
- 交付控制：校验失败时，补充信息、有限次重试、拒答或转人工。

工具验证侧重获取外部结果，程序校验侧重按照明确规则判断结果是否合格，两者可以重叠，例如由程序自动执行测试并检查结果。

格式正确不代表事实正确，引用原文存在也不代表它支持结论。语义支持关系可结合规则、模型复核和人工抽查判断；另一个模型复核仍可能出错。

### 3.5 评估与改进

准备可重复运行的测试集，覆盖正常问题、资料缺失、错误前提、版本差异和资料冲突。明确每个案例的参考证据，以及应该回答、追问还是拒答。

可关注以下指标，并明确统计单位与分母：

- 事实正确率：被检查的事实性结论中，正确结论所占的比例。
- 引用支持率：被检查的带引用结论中，引用确实支持结论的比例。
- 无依据断言率：需要证据的结论中，缺少充分支持的比例。
- 回答与拒答表现：分别统计可回答问题被错误拒答，以及不可回答问题被强行回答的情况。
- 任务质量与成本：同时观察任务完成情况、延迟和调用成本。

使用可核验的参考答案、程序检查和人工评审；模型评分可以辅助，但不能独自作为真实性标准。将实际失败案例加入测试集，在修改提示词、资料、检索、模型或验证规则后进行回归评估。

## 4. 实现流程

```text
用户问题 → 检查必要条件 → 检索资料或查询工具 → 判断证据是否充分
                                                  ├─ 不足或冲突：补充信息、追问或拒答
                                                  └─ 充分：生成带依据的答案
                                                            ↓
                                                   程序校验与必要复核
                                                            ↓
                                                   通过后交付，否则纠正或停止
```

生成结果可以包含回答、逐条结论、来源编号、引用原文和缺失信息，便于程序校验。校验对象应包含实际答案及其关键事实，不能只检查模型自报的“已验证”状态。

最小实现可以采用“可信资料检索 + 带引用回答 + 引用存在性检查 + 依据不足时拒答”，再按任务加入业务工具和语义复核。检索与重试需要设置次数、时间和成本上限，避免反复调用却无法补足证据。

评估位于持续改进流程中：记录失败案例，判断问题出在资料、检索、生成还是验证环节，再修改对应组件并检查效果。

## 5. 能力边界

- 目前可以大幅减少幻觉，但无法保证任意问题的回答都绝对真实。
- 降低 temperature 可以减少采样随机性，不能保证事实正确；temperature 为零也可能稳定地产生错误答案。
- RAG、工具调用和模型复核都可能失败，需要分别检查来源、执行结果和解释过程。
- 在缺少必要证据时，合理拒答、追问或转人工是可靠系统的一部分。
- 验证强度应结合错误后果与任务要求确定；高风险结论需要适当的专业复核。
