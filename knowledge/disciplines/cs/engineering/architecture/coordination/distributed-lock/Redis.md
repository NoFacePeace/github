# Redis

Redis 可以用带 TTL 的 String key 表示一把锁：key 标识受保护资源，value 保存本次获取尝试的唯一随机 token。获取、续约和释放都围绕这个 token 校验身份。

## 1. 获取锁

```redis
SET lock:task:123 unique-token NX PX 30000
```

| 参数或选项 | 含义 |
| --- | --- |
| `lock:task:123` | 竞争同一任务的实例使用同一个 key。 |
| `unique-token` | 每次新的获取尝试使用不同的随机 token。 |
| `NX` | 仅在 key 不存在时写入。 |
| `PX 30000` | 设置 30000 毫秒有效期。 |

返回 `OK` 表示获取成功，空响应表示 key 已存在、未获取到锁。获取失败可以直接返回，也可以在截止时间内退避重试。

锁值与 TTL 必须一起设置，不能先 `SETNX` 再单独设置过期时间，否则中途崩溃可能留下不自动过期的锁。

如果请求超时，命令可能已经执行，结果属于不确定状态。可以用相同 token 查询当前归属并确认剩余有效期；不能仅凭“可能获取成功”进入临界区，也不能认为超时自动撤销了锁。

## 2. 安全释放

不能直接 `DEL`，应将身份比较和删除放在一段 Lua 中：

```lua
if redis.call('GET', KEYS[1]) ~= ARGV[1] then
    return 0
end
return redis.call('DEL', KEYS[1])
```

`KEYS[1]` 是锁 key，`ARGV[1]` 是本次持锁 token。返回 `1` 表示删除成功，`0` 表示已过期或不属于自己。

否则可能出现：A 的锁过期，B 已获取新锁，A 在收尾时直接删除 B 的锁。Lua 防止比较和删除之间插入其他客户端的命令。

## 3. 校验续约

工作时间超过初始租期时，可以在到期前定期续约：

```lua
local ttlMs = tonumber(ARGV[2])
if not ttlMs or ttlMs <= 0 or ttlMs ~= math.floor(ttlMs) then
    return redis.error_reply('invalid lock ttl')
end
if redis.call('GET', KEYS[1]) ~= ARGV[1] then
    return 0
end
return redis.call('PEXPIRE', KEYS[1], ARGV[2])
```

调用方应限制 TTL 范围并传入规范整数字符串。返回 `1` 表示续约成功，`0` 表示不能继续以这份锁执行。

例如租期 30 秒，每 10 秒续约一次。网络错误时只能在已确认的期限内重试，不能自行延长期限；本地截止时间应保守计算，并考虑请求耗时和时钟误差。

任务完成时停止续约并尝试校验释放。独立续约线程仍可能在业务卡死时维持锁，因此还需要任务超时或最大持有期限等业务约束。

## 4. 过期不等于进程停止

锁到期后其他实例可以获取，但旧实例可能仍在运行，或有请求已发送到外部系统。

随机 token 保护的是锁自身的释放和续约，不能阻止旧实例写数据库、文件或外部服务。需要严格保护时，应在资源端检查执行代次或 fencing token，或通过条件写入等机制拒绝失效操作。

## 5. 复制与故障切换

Redis 主从通常异步复制。A 获取锁的写入若尚未复制，主节点就故障，晋升的副本可能没有该锁，导致 B 再次成功获取，而 A 仍在执行。

Lua 与 `SET NX PX` 保证当前节点上的操作原子性，不保证故障切换后不会丢失已确认的锁写入。

可以在获取成功后，通过同一连接执行 `WAIT` 等待副本确认此前写入：

```redis
WAIT 1 1000
```

返回值是实际确认的副本数。未达到目标不会回滚锁，等待耗时也会消耗租期。副本确认不等于落盘，也不保证切换时一定选择包含该写入的副本，因而不能把 `WAIT` 视为强一致互斥保证。

## 6. 使用边界

- 锁 key 应避免因内存淘汰提前消失，并为协调数据规划容量和淘汰策略。
- TTL 是整个 key 的期限，GET 不会自动续约。
- 该基础方案不默认支持公平排队、可重入或多资源死锁检测。
- 防止重复计算和严格保护业务正确性的要求不同，应按后果选择协调机制及资源端保护。
- 与数据库事务和外部 API 之间没有自动的原子提交，仍需考虑幂等、条件更新与结果不确定时的恢复。
