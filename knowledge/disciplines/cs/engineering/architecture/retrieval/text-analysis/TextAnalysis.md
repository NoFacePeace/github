# 文本分析

文本分析（Text Analysis）将原始文本转换为用于建立索引或匹配查询的词项，通常包含字符预处理、分词和词元处理。分析器（Analyzer）是组织并执行这些步骤的组件，具体规则由语言、字段用途和检索需求决定。

## 1. 基本流程

```text
原始文本 → 字符预处理 → 分词 → 词元处理 → 索引或查询词项
```

- [字符预处理](CharacterPreprocessing.md)：在分词前清理、替换或规范化字符，输出仍然是文本。
- [分词](tokenization/Tokenization.md)：确定词元边界，输出词元及其位置、字符偏移等信息。
- [词元处理](TokenProcessing.md)：对已有词元进行转小写、词干提取、停用词过滤或同义词处理等操作。

例如，配置 HTML 清理、英文单词切分、转小写、停用词过滤和词干提取后：

```text
原始文本：<b>The cats</b> are running.
字符预处理：The cats are running.
分词：The / cats / are / running
词元处理：cat / run
```

此例只展示一种分析配置，不代表所有分析器的默认输出。各步骤按需要启用，执行顺序也会影响结果。

## 2. 分析器与组成组件

以 Lucene、Elasticsearch 等系统中的常见分析链为例：

| 组件 | 操作对象 | 职责 |
| --- | --- | --- |
| 字符过滤器（Char Filter） | 分词前的文本 | 字符替换、HTML 清理等 |
| 分词器（Tokenizer） | 预处理后的文本 | 确定词元边界并产生词元流 |
| 词元过滤器（Token Filter） | 已产生的词元流 | 过滤、改写或扩展词元 |

这类分析器通常包含零个或多个字符过滤器、一个分词器，以及零个或多个词元过滤器。其他系统可能使用不同的组件名称或实现方式。

“分词”是文本分析中的一个步骤。工程交流中有时会用“分词”泛指整个分析流程，阅读工具配置时应区分分析器与单独的分词器。

## 3. 按语言组织分析方案

- [中文](Chinese.md)：重点关注词边界歧义、未登录词、领域词典与切分粒度，并结合需要配置字符和词元处理。
- [英文](English.md)：通常先按单词边界切分，再按需进行大小写归一化、词形处理和停用词过滤。

多语言混合字段需要同时覆盖各语言和业务标识符。可以选择适合混合文本的分析器，也可以使用多个字段分别建立索引，再组合查询结果。

## 4. 索引与查询的配合

索引构建与查询都会使用文本分析：

```text
索引阶段：文档 → 文本分析 → 词项及位置等信息 → 倒排索引
查询阶段：查询 → 文本分析 → 查询词项 → 查找倒排表并匹配
```

例如，文档 `Redis caches data` 被分析为 redis、caches、data，索引中就会为这些词项建立到文档的映射。查询 `Redis` 若也被归一化为 redis，即可查到对应候选。

索引与查询的分析规则需要相互兼容，但不要求完全相同。例如，同义词可以只在查询阶段展开。若词边界或归一化规则不兼容，可能导致漏召回或误匹配；修改索引阶段的规则后，通常需要重建受影响的索引才能应用到已有文档。

验证时应同时检查词元文本、位置和原文偏移，并结合真实查询评估普通词项匹配、短语匹配、高亮、召回、误匹配、索引大小和延迟。
