# 状态机

## 1. 定义

状态机（State Machine）通过状态、事件和转换规则描述对象的行为。状态记录对象当前所处的阶段，事件触发变化，转换规则规定变化是否允许，也可以包含前置条件和伴随动作。

状态机不依赖分布式场景。单机程序中的连接管理、界面交互和任务调度同样可以使用。它也不等同于面向对象设计中的 State 模式，后者是一种组织不同状态行为的代码方式。

## 2. 任务示例

| 当前状态 | 事件 | 下一状态 |
| --- | --- | --- |
| CREATED | 确认入队 | QUEUED |
| QUEUED | 执行器领取成功 | RUNNING |
| CREATED / QUEUED | 请求取消 | CANCELLED |
| RUNNING | 请求取消 | CANCEL_REQUESTED |
| CANCEL_REQUESTED | 执行器确认停止 | CANCELLED |
| RUNNING | 执行成功 | SUCCEEDED |
| RUNNING | 确认执行失败 | FAILED |

此示例将 SUCCEEDED、FAILED、CANCELLED 视为终态，终态不再转换。请求超时仅代表结果不确定，不能直接当作任务执行失败。

若完成与取消同时发生，需要明确裁决规则。例如此表采用先成功写入状态的转换生效；取消先写入后，执行器仍需检查实际业务效果，不能把已发生的副作用当作已撤销。

## 3. 原子地执行转换

迟到的入队回调只能推进仍处于 CREATED 的任务：

```sql
UPDATE task
SET status = 'QUEUED'
WHERE id = :task_id AND status = 'CREATED';
```

执行器通过条件更新取得执行资格：

```sql
UPDATE task
SET status = 'RUNNING'
WHERE id = :task_id AND status = 'QUEUED';
```

只有更新成功才能执行。取消接口同样通过条件更新，把 CREATED 或 QUEUED 改为 CANCELLED。取消与领取竞争同一条记录，取消先成功时，执行器无法领取；领取先成功时，取消方需要重新判断并请求正在运行的任务停止。

不能先查询状态，再无条件修改，否则两步之间的并发变化可能被覆盖。条件更新影响零行时，应按业务需要重新读取，区分记录不存在、已经结束或已被其他执行器领取等情况。

## 4. 状态与投递顺序

上例要求执行器领取前，QUEUED 已经持久化。如果消息可能先于入队回调到达，执行器读到 CREATED 时应延迟重试，或重新设计协议，让投递前的持久化状态表示可领取。另一种方案是明确允许 CREATED 直接进入 RUNNING，但应同步修改转换规则。

状态机本身不会撤回消息或终止线程。所有回调、执行器、恢复逻辑和取消接口都必须遵守相同的转换规则；业务写入还需要匹配的事务与权限校验，不能仅凭状态字段保证正确。
