# 事务发件箱

## 1. 解决的问题

事务发件箱（Transactional Outbox）解决本地业务数据提交与消息发送之间的双写问题。

先创建任务再发送消息，进程可能在数据库提交后崩溃，导致任务存在却没有消息。先发送消息再创建任务，则可能出现消费者收到消息时，任务尚未创建或创建失败。

## 2. 同一事务记录发送意图

在业务数据库中增加 outbox 表，在同一个本地事务中写入业务记录和待发送事件：

```sql
BEGIN;

INSERT INTO task (id, status)
VALUES ('task-1', 'CREATED');

INSERT INTO outbox (id, task_id, event_type, status)
VALUES ('event-1', 'task-1', 'TASK_CREATED', 'PENDING');

COMMIT;
```

事务成功，两条记录同时存在；事务失败，两条记录都不提交。这保证的是业务记录与事件记录的一致性，不是数据库与消息队列同时提交。

## 3. 后台投递

```text
读取待发送事件
    ↓
发送到消息队列
    ↓
收到队列确认
    ↓
将事件标记为 SENT
```

投递失败或结果不确定时保留记录并重试；进程恢复后继续处理未确认的事件。也可以通过数据库变更捕获驱动投递，而不是扫描表。

实现时需要处理投递器并发领取、领取者崩溃后的恢复、失败退避、积压监控和历史记录清理。若同一业务对象的事件有顺序要求，还需单独设计分区键、序号或消费端版本校验，Outbox 本身不自动保证全局顺序。

## 4. 重复投递与保证边界

队列已经接收消息，但投递器在标记 SENT 前崩溃，恢复后会重复发送。因此 Outbox 通常提供至少一次投递，需要消费者通过稳定事件 ID 和业务操作标识实现[幂等性](../reliability/Idempotency.md)。

至少一次投递依赖事件持久保存、持续重试及数据库和队列最终可用等前提。标记 SENT 表示完成了约定的队列投递确认，不代表下游业务已经执行成功，也不会把消费者的业务写入纳入原来的本地事务。

## 5. 与任务取消的关系

Outbox 不负责取消任务。任务取消后，投递器可以跳过尚未发送且允许跳过的任务触发事件，但消息可能已在发送途中或已经被消费。

执行端仍需通过权威任务状态和原子领取规则决定是否执行。正在运行的任务需要响应取消信号，并处理已发生的业务效果。队列中的旧消息即使无法物理删除，也可以在消费时被判定为无效。
