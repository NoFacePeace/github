# 事务管理

事务管理关注如何在应用中定义事务边界，协调模块执行，并在成功、失败或结果不确定时完成提交与恢复。它既涉及数据库访问，也涉及业务用例和模块接口的组织。

## 1. 职责划分

| 层次 | 职责 |
| --- | --- |
| 业务用例层（Application Service） | 定义一个完整业务动作，决定哪些操作必须一起成功，协调事务的开始、提交和回滚。 |
| 模块业务接口 | 提供创建订单、扣减库存等业务能力，维护模块内部规则，失败时向调用方返回错误。 |
| store | 封装数据库访问，使用指定的事务或数据库连接执行操作。 |
| 事务管理组件（Unit of Work） | 封装事务生命周期，将同一个事务提供给参与操作，并统一处理提交和回滚。 |

模块可以保持 store 私有。调用方通过业务接口协调操作，不需要直接访问各模块的数据表或 store。

## 2. 事务边界

事务边界由业务不变量决定，而不是由模块或函数数量决定。例如创建订单和扣减库存必须同时生效，就应在支持的范围内放进同一个事务。

参与同一事务的模块不能各自提交。模块内部事务即使单独执行成功，也无法保证多个模块整体成功；把多个调用写在一个函数里或并发执行，同样不会自动产生原子性。

事务应覆盖必要的读取、校验和修改，同时避免不必要的耗时操作。对竞争资源的检查还需要合适的隔离级别、锁、条件更新或约束，共享事务本身不能消除所有并发问题。

## 3. 跨模块协调方式

- [共享本地事务](SharedLocalTransaction.md)：多个模块的内部 store 使用同一个本地事务，通过显式参数、调用上下文或事务范围实例传递事务依赖。

如果操作跨越独立服务或无法参加同一本地事务的资源，需要单独设计跨资源协调。Saga 通过已提交步骤的补偿恢复业务结果；TCC 通过预留、确认和取消协调资源。它们与本地事务统一提交的保证不同。

仅仅由用例层依次调用多个模块，不代表使用了 Saga；接口名为预占或冻结，也不代表实现了完整的 TCC。

## 4. 外部副作用与恢复

数据库回滚通常无法撤销 HTTP 调用、邮件发送等外部副作用。需要可靠发布事件时，可以在本地事务中同时保存业务数据和 Outbox 事件，再异步投递并由消费者幂等处理。

提交时连接中断可能导致结果不确定，不能直接推断数据库已经回滚。应结合稳定业务标识、结果查询和幂等重试恢复，避免重复创建、扣款等操作。
