# 心跳

心跳（Heartbeat）是一种周期性发送存活信号的故障检测机制。被检测对象定期上报或续约，观察者在超过期限仍未收到有效信号时，将其判定为疑似离线或不可用。

## 1. 基本角色

| 角色 | 职责 |
| --- | --- |
| 上报者 | 周期性发送身份、状态及可选的资源信息。 |
| 状态存储或接收端 | 记录最近心跳或有效期限，也可以直接运行在观察者内部。 |
| 观察者 | 检查有效期限，更新可用名单或触发后续处理。 |

```text
节点或进程 → 定期心跳 → 最近存活状态
                              ↓
                         观察者检查
                         ├─ 有效 → 保持在线
                         └─ 超时 → 疑似离线
```

## 2. 上报与续约

例如，每 10 秒发送一次心跳，每次将有效期延长到接收后的 30 秒：

```text
00 秒收到心跳 → 有效至 30 秒
10 秒收到心跳 → 有效至 40 秒
20 秒收到心跳 → 有效至 50 秒
之后未收到心跳 → 到期后可判定为疑似离线
```

这就是续约：每次收到有效上报，都延长存活状态的有效期。心跳状态的续约不等同于任务执行权的续约，后者需要单独定义授权和失效规则。

## 3. 身份与上报内容

常见字段包括：

| 字段 | 用途 |
| --- | --- |
| 节点或服务 ID | 稳定标识被检测对象。 |
| 实例 ID | 标识本次进程启动，重启后变化。 |
| 在线、维护或未就绪状态 | 区分能否接收新工作。 |
| 最近接收时间或过期时间 | 判断心跳是否仍有效。 |
| 能力与资源信息 | 辅助选择执行节点，不能代替原子的容量预留。 |

实例 ID 可用于防止旧进程注销新进程的状态；系统还需要对冲突上报和身份替换制定校验规则，不能只增加一个字段就认为已经隔离旧实例。

## 4. 主动退出与异常失联

- **正常退出**：可先标记维护或 draining，停止接新任务，再注销心跳；异常退出仍需有超时兜底。
- **异常失联**：观察者根据超时判定不可用，从可调度名单移除。
- **恢复上线**：接收到新的有效心跳，并确认就绪后，按恢复策略重新加入可用名单。

移出在线名单只改变调度或发现结果，不会自动杀死原进程，也不必然释放已有任务绑定、删除工作区或迁移正在运行的任务。

## 5. 超时设计

上报间隔应明显短于有效期，允许短暂延迟和少量丢失。10 秒上报、30 秒过期只是示例，不是所有系统的固定最佳值。

心跳发送者与观察者可能时钟不同。单进程计算间隔宜使用单调时钟；跨节点存储过期时间时，应统一时间依据，例如由接收端或共享存储确定期限，避免任意依赖发送端墙上时钟。

超时检测可能由轮询、定时器或存储过期机制触发，发现离线的时间还受检查周期影响。不能将有效期直接当作整个系统严格的故障发现时延。

## 6. 能力边界

心跳主要证明“最近能发送信号”。业务线程卡死、依赖故障或资源耗尽时，独立心跳线程仍可能正常上报，需要结合就绪探测和工作进展判断。

网络分区时，节点可能仍在工作却无法上报。若要在其他节点重试或接管任务，需要确保旧执行权失效，并对结果提交进行租约或 fencing 校验。心跳本身不能保证任务只执行一次。

## 7. 实现选择

常见实现包括 Redis TTL 与在线索引、注册中心租约、HTTP 健康探测中的周期性确认，以及本机 IPC 或共享状态。选型取决于是否需要枚举在线节点、故障检测速度、节点规模及协调存储的可用性。

如果将心跳详情和在线名单分别存储，需要考虑二者的一致更新、过期清理，以及读到过期状态时的再次校验。

- [Redis](Redis.md)：使用 String TTL 保存详情、ZSet 维护在线索引，通过 Lua 原子上报并按期限清理。
