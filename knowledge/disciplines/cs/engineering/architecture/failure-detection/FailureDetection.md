# 故障检测

故障检测（Failure Detection）通过心跳、健康探测、请求结果等信号，判断进程、节点或服务是否可能异常，为调度、告警和故障恢复提供依据。它属于系统可靠性设计中的通用机制，可用于单机进程，也可用于分布式节点。

## 1. 检测目标

| 目标 | 关注的问题 |
| --- | --- |
| 存活性 | 进程或节点最近是否仍在响应。 |
| 就绪性 | 是否初始化完成、依赖可用，能够接收新请求。 |
| 工作进展 | 任务是否持续推进，是否可能卡死。 |

这些目标不能相互替代。进程能发送心跳，不代表业务线程正常工作；节点存活，也不代表资源充足或可以接收新任务。

## 2. 检测方式

| 方式 | 工作原理 | 局限 |
| --- | --- | --- |
| [心跳](heartbeat/Heartbeat.md) | 被检测对象周期性上报或续约，观察者判断是否超时。 | 暂停和网络延迟可能导致误判。 |
| 主动健康探测 | 观察者定期请求 HTTP、TCP 或进程接口。 | 需要设计能反映目标能力的探测内容。 |
| 请求结果与进展检测 | 观察错误率、请求超时、任务进度或处理延迟。 | 没有业务流量时，可能缺少检测信号。 |

实际系统可以组合多种信号。例如，心跳用于判断节点是否在线，健康探测用于判断依赖是否可用，进度检测用于发现任务停滞。

## 3. 超时与误判

没有在期限内收到信号，可能是进程退出，也可能是网络分区、长时间 GC、CPU 调度延迟或观察者自身异常。

因此，超时通常表示“怀疑不可用”，不能证明目标进程已经停止。阈值越短，发现异常越快，但误判概率可能更高；阈值越长，检测更宽容，但恢复更慢。

## 4. 检测与恢复的边界

故障检测提供状态判断，后续如何处理由业务决定，例如停止分配新任务、告警、重试或切换节点。

不能仅因旧节点心跳过期，就假定它已停止访问资源。需要独占执行权的系统，还应使用租约、执行代次或 fencing token，并在写入或提交结果时校验，拒绝失效执行者继续操作。

## 5. 设计要点

- 明确检测对象与能力，区分进程存活、业务就绪和任务进展。
- 结合网络延迟、进程暂停和恢复目标，选择探测间隔及超时阈值。
- 区分节点身份与本次进程实例，避免重启前后的报告相互覆盖。
- 同时考虑离线判定、恢复上线和计划内维护的状态变化。
- 将状态判断与恢复策略分开，避免一次误判直接触发不可逆操作。
