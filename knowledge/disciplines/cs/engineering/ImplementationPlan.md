# 实现计划

实现计划将项目目标拆解为有依赖顺序、可以执行和验证的任务，适用于新项目、功能开发和开源项目精简版（mini）的实现。

基本结构：目标与范围 → 核心流程 → 模块划分 → 实现阶段 → 具体事项 → 阶段验收，另列待确认问题。

## 1. 目标与范围

先明确最终要获得什么成果，以及本次实现的边界：

- 实现目标：项目解决什么问题，最终通过什么示例展示成果。
- 学习目标：如果是 mini 项目，重点理解哪些算法、机制或设计。
- 本次实现：必须支持的操作、行为和运行环境。
- 暂不实现：本轮不涉及的能力，避免范围不断扩大。
- 技术约束：技术栈、兼容要求和必要的资源限制。

实现 mini 时，先运行官方示例，阅读 README 和公开接口，确定行为约定及精简范围；实现中再围绕具体问题阅读源码，比较设计取舍。

## 2. 核心流程

描述一次真实输入到输出的完整路径，说明各环节的输入、输出和关键异常，为模块划分及阶段拆解提供依据。例如 mini Redis：

```text
客户端请求 → 协议解析 → 命令分发 → 存储操作 → 响应编码 → 返回结果
```

## 3. 模块划分

根据核心流程识别必要模块，明确各模块的职责边界、交互方式和依赖关系。例如 mini Redis：

| 模块 | 职责 | 主要交互 |
| --- | --- | --- |
| 网络模块 | 管理连接和数据收发 | 调用协议模块解析请求，将命令交给执行入口并发送响应 |
| 协议模块 | 解析请求与编码响应 | 在协议数据与命令参数、执行结果之间转换 |
| 命令模块 | 检查参数并分发操作 | 调用存储模块，返回执行结果 |
| 存储模块 | 维护键值数据 | 提供命令执行所需的数据操作 |

先明确职责和必要的交互约定，具体结构、字段和接口随阶段补充；模块边界也可随实现调整。

## 4. 阶段与具体事项

### 4.1 按可验证的能力划分阶段

按依赖顺序划分阶段，每个阶段都产出可运行、可验证的成果，并明确涉及哪些模块、各自实现到什么程度。例如，先通过命令与存储模块实现本地读写，再接入网络与协议模块支持客户端访问。

一个阶段可以涉及多个模块，同一模块也可跨阶段完善。每阶段只实现必要部分并复用已有能力；未来才需要的模块先记录职责，到对应阶段再实现。

### 4.2 沿流程拆分和执行具体事项

阶段内可按模块或流程步骤组织事项，勾选放在具体事项上。任务少时可直接列事项，过大时继续拆分。

执行时沿一条最小流程跨模块推进，按需实现并接通调用。例如先打通 SET 的参数检查、存储写入和结果返回，验证后再增加 GET、DEL，无须先完成某个模块的全部功能。

事项描述应具体，例如“GET 在键不存在时返回空结果”，避免“理解核心逻辑”“完善系统”等难以判断完成的表述。

### 4.3 按需补充结构、字段和接口

根据当前步骤的行为和约束补充结构、字段和接口。例如，写入时定义键值存储，增加过期能力时再补充过期时间及其语义。

定义结构和字段可以作为事项，应写清用途及含义、单位、默认值等必要约定。影响多个环节的关键约定提前明确，其他细节按需补充，变更时同步更新代码和计划。

### 4.4 事项完成条件与阶段验收

- 事项层面：每项都有明确的完成条件。简单事项直接写在描述中，复杂或容易歧义的事项补充验证操作和预期结果。
- 阶段层面：单列可复现的操作及预期结果，验证多个模块接通后的完整能力，覆盖必要的边界和异常情况。

定义类事项通过检查是否满足当前流程及约定来确认完成，功能类事项通过运行示例或适当的测试验证。结构定义完成不代表功能完成，各事项完成后仍需通过阶段验收。

## 5. 待确认问题与进度维护

单独记录技术疑问、解决方式和预期产出，优先解决影响当前实现的问题。例如：“阅读 RESP 文档并通过实验确认消息边界，整理解析规则和请求样例”。

进度使用 Markdown 任务清单维护：

- `- [ ]`：待完成，或实现后尚未验证。
- `- [x]`：已满足完成条件，并通过相应检查或验证。

近期任务写细，后续阶段保留轮廓。随实现更新任务、依赖和范围；变更使已完成事项不再成立时，重新打开该事项。任务和阶段验收均完成后，该阶段才算完成。

## 6. 可复用模板

以下以 mini Redis 为例，阶段内按流程组织事项，按项目需要调整。

```markdown
# Mini Redis 实现计划

## 1. 目标与范围
- 实现目标：支持通过 redis-cli 操作的单机内存数据库。
- 学习目标：理解命令执行、协议解析和网络请求处理。
- 本次实现：单连接，支持 SET、GET、DEL 的基本形式。
- 暂不实现：持久化、复制、集群，以及命令的可选扩展参数。
- 技术栈与运行方式：实施前填写。

## 2. 核心流程
客户端请求 → 协议解析 → 命令分发 → 存储操作 → 响应编码 → 返回结果。

## 3. 模块划分

- 网络模块：管理连接，读取请求数据并发送响应。
- 协议模块：解析请求，编码响应。
- 命令模块：检查名称和参数，分发存储操作。
- 存储模块：维护内存键值数据。

主要交互：网络模块调用协议模块解析请求，将命令交给命令模块；命令模块调用存储模块；执行结果经协议模块编码后由网络模块发送。

## 4. 阶段一：本地命令可执行

本阶段模块范围：实现命令模块的基本检查与分发，以及存储模块的内存读写删除。网络和协议模块在下一阶段接入。

本阶段流程：本地传入命令和参数 → 参数检查 → 存储操作 → 返回执行结果。

### 4.1 打通 SET 写入（命令、存储模块）
- [ ] 明确 SET 的参数与成功结果，实现参数数量检查
- [ ] 定义写入所需的键值存储，同名键再次写入时覆盖原值
- [ ] 接通 SET 分发、存储写入和结果返回，验证写入行为

### 4.2 增加 GET、DEL（命令、存储模块）
- [ ] 确定读取结果的表示方式，区分键不存在与空值
- [ ] 接通 GET 参数检查、存储读取和结果返回，键不存在时返回约定的空结果，值为空时仍视为键存在
- [ ] 接通 DEL 参数检查、存储删除和结果返回，结果为实际删除的键数量
- [ ] 统一处理未知命令和参数数量错误

### 4.3 阶段验收
- [ ] 本地调用完成写入、读取、覆盖和删除，结果符合预期
- [ ] 验证键不存在、未知命令和参数错误时的行为

## 5. 阶段二：客户端可访问

本阶段模块范围：实现网络模块的单连接收发和协议模块的必要 RESP 支持，复用阶段一的命令执行与存储能力。

本阶段流程：接收请求 → 解析命令 → 调用已有执行入口 → 编码并发送响应。

### 5.1 接收请求（网络模块）
- [ ] 启动 TCP 服务并接收连接，读取请求数据

### 5.2 解析、执行并响应（协议、命令、网络模块）
- [ ] 明确解析器如何返回命令参数，以及区分请求完整、不完整和非法的情况
- [ ] 实现 SET 所需的 RESP 解析，接入已有命令执行入口
- [ ] 编码并发送 SET 响应，验证一次完整的客户端写入
- [ ] 补齐 GET、DEL 所需的解析与响应，接通客户端读写删除流程

### 5.3 处理通信边界（协议、网络模块）
- [ ] 按需补充接收缓冲与已消费字节数的记录，处理不完整请求和连续多条请求

  该事项验收：将一条请求拆成两段发送，第一段不执行命令，补齐后执行一次；一次发送两条完整请求，按顺序执行并分别返回响应。

- [ ] 客户端断开时结束该连接的处理，并释放对应的连接资源

### 5.4 阶段验收
- [ ] 使用 redis-cli 完成 SET、GET、DEL 操作
- [ ] 拆分或合并发送请求，确认解析与执行结果正确

## 6. 待确认问题
- [ ] 确认 redis-cli 在目标版本下建立连接时使用的命令，确定必要的支持范围

## 7. 交付验收
- [ ] 补充启动方式、使用示例和已知限制
- [ ] 记录模块职责及关键设计取舍
- [ ] 按 README 从零启动并完成演示
```

## 7. 保存位置

知识库保存制定实现计划的通用方法与模板。具体项目的执行计划保存在其代码仓库根目录的 `PLAN.md` 中，随代码实现持续更新。
