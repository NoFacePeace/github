# 发布与迁移

发布与迁移关注如何将新实现交付到运行环境，并逐步将流量或数据迁移过去，包括验证、灰度、切换和回退。

## 1. 与兼容性的关系

[兼容性](Compatibility.md)关注新实现是否仍满足旧有约定；发布与迁移关注如何验证新实现，并控制切换过程中的影响范围。兼容性验证通过，并不意味着新实现没有缺陷或性能问题，仍需分阶段验证实际运行效果。

## 2. 保留 API 入口，切换内部实现

如果新实现兼容现有 API，可以保持对外入口不变，在内部通过开关选择新旧实现，通常不必额外提供一个对外的新 API。

```text
现有 API 入口
      ↓
    路由开关
   ↙       ↘
旧实现     新实现
```

开关可以按测试账号、租户或流量比例分流。需要保持业务流程一致时，应按稳定的业务标识分流，避免同一账号或同一业务流程的请求在新旧实现之间反复切换。

## 3. 分阶段验证与切换

### 3.1 测试环境验证

直接测试新实现的正常流程、边界和异常情况，再通过现有 API 验证完整调用链。除返回值外，还需验证错误码、数据库写入、消息发送等业务效果，以及必要的并发和性能场景。

### 3.2 生产环境定向验证

先让指定测试账号或内部用户通过现有入口访问新实现，其他请求继续使用旧实现。生产验证可能产生真实数据和外部副作用，应明确验证范围及数据处理方式。

### 3.3 小流量灰度

让少量真实流量进入新实现，比较新旧实现的业务结果、错误率、延迟和资源消耗。发布前明确扩大流量、暂停和回退的条件，并按业务流量周期和关键场景设置观察窗口。

指标稳定且关键场景得到覆盖后，再逐步扩大比例。灰度初期未发现问题，只能说明当前样本中未发现问题，不能保证所有场景都正确。

### 3.4 全量切换与清理

全量切换后继续观察，并保留一段时间的回退能力。确认运行稳定、旧实现不再被依赖后，再删除旧代码和临时开关，并更新相关文档。

## 4. 流量复制与结果对比

对于适合复制的只读请求，可以将同一请求额外发送给新实现，对外仍返回旧实现的结果，在后台比较两者输出。这种方式也称为影子流量验证。

对比时应处理时间戳、随机值、数据更新时机等可能造成的合理差异，并限制复制流量，避免额外负载影响服务。名义上的只读请求也可能写缓存、更新计数或调用外部服务，需要先检查副作用。

涉及写入时，不应直接让新旧实现同时执行，以免重复扣款、创建订单或发送消息。可以在隔离环境中回放请求，或比较不产生副作用的计算结果。

## 5. 回退与数据处理

流量切回旧实现，不会自动撤销新实现已经写入的数据或触发的外部操作。切换前应确认：

1. 开关能否及时生效，以及生效范围是否符合预期。
2. 旧实现能否读取和处理新实现产生的数据与配置。
3. 已开始执行的请求、后台任务和消息如何处理。
4. 失败重试或切换是否可能造成重复操作，必要的幂等机制是否有效。
5. 已发生的错误写入是否需要数据修复或业务补偿。

如果旧实现无法处理新数据，应先设计兼容的数据迁移方案；仅保留旧代码不足以保证能够回退。
