# 分页

Google API 的分页规则由 AIP-158 定义，常用于 List 等返回集合的操作。调用方通过 `page_size` 指定每页最多返回多少条，通过 `page_token` 继续读取后续结果。

本文用“必须”“应”“可以”分别对应规范中的 MUST、SHOULD、MAY，区分强制要求、推荐做法和可选能力。

## 1. 请求与响应

### 1.1 请求字段

| 字段 | 类型 | 含义与规则 |
| --- | --- | --- |
| `page_size` | `int32` | 应提供，且必须为可选字段，表示本页返回条数的上限。 |
| `page_token` | `string` | 应提供，且必须为可选字段；传入上一次响应中的 `next_page_token`，第一页不传。 |

`page_size` 的处理规则：

- 不传或传 `0`：服务端选择默认值，不得因此报错；应在 API 文档中说明默认值。
- 传负数：必须返回 `INVALID_ARGUMENT`。
- 超过服务端允许的最大值：应收缩到最大值。
- 实际返回条数可以少于该值，甚至为零，即使集合尚未遍历结束。

默认值和最大值由具体 API 定义。AIP 示例中的默认 `50`、最大 `1000` 只是示例，不是所有 API 的统一限制。

翻页时，调用方可以修改 `page_size`，服务端必须按新的大小处理；其他参数，例如父资源、筛选条件和排序，应与生成 token 的请求保持一致，否则 API 应返回 `INVALID_ARGUMENT`。

### 1.2 响应字段

| 字段 | 类型 | 含义与规则 |
| --- | --- | --- |
| 资源列表，例如 `books` | `repeated Book` | 应为响应消息的第一个字段，字段编号为 `1`，包含本页资源。 |
| `next_page_token` | `string` | 应提供，用作下一次请求的 `page_token`。 |
| `total_size` | `int32` | 可选，表示列表总条数；可以是估算值，但应明确说明。 |

分页响应必须是非流式响应。

是否结束，只能通过 `next_page_token` 判断：

- 已到集合末尾：`next_page_token` 必须为空。
- 尚未到末尾，或服务端无法及时确定是否到末尾：必须提供 `next_page_token`。

因此，不能用“本页不足 `page_size` 条”或“本页没有数据”判断遍历结束，也不应依赖 `total_size` 判断。

## 2. 调用流程

以下用 JSON 表示请求和响应，保留 proto 字段名以突出分页语义；具体 REST JSON 映射通常使用 `pageSize`、`pageToken`、`nextPageToken` 等名称。

首次请求不带 token：

```json
{
  "parent": "publishers/example",
  "page_size": 20
}
```

服务端返回当前页及后续 token。这里省略了部分资源，示例 token 仅作占位：

```json
{
  "books": [{ "name": "publishers/example/books/book-1" }],
  "next_page_token": "opaque-token-a"
}
```

下一次请求原样回传 token，并保持查询参数一致：

```json
{
  "parent": "publishers/example",
  "page_size": 20,
  "page_token": "opaque-token-a"
}
```

重复此过程，直到 `next_page_token` 为空或未返回。客户端不解析或自行构造 token。

## 3. 为什么使用 token

### 3.1 隐藏实现细节

token 表达“从哪里继续”，具体状态由服务端解释。服务端可以用它承载游标位置、查询状态或快照标识，也可以让它引用服务端保存的状态。

AIP-158 要求 token 必须是不透明、URL 安全的字符串，不能让调用方解析其内部结构。否则调用方可能依赖这些细节，使分页实现成为对外契约的一部分，之后难以修改。

单纯把一个明文页码或 offset 做 Base64 编码，并不足以满足不透明性的要求。规范允许的一种做法是：对于无需存入数据库且不含敏感数据的状态，使用内部 protobuf 消息序列化后再进行 Base64 编码；该内部结构不作为公开契约。

### 3.2 支持游标查询

以下是使用 token 支持游标分页的实现思路，不是 AIP 对底层数据库算法的强制要求。

假设按创建时间和唯一 ID 排序，第一页读取 20 条：

- 使用 offset 时，下一页跳过前 20 条；如果此前的数据被插入或删除，结果位置可能移动，导致重复或漏读。
- 使用游标时，可以在 token 中记录上一页最后一条的创建时间和 ID，下一页从该位置之后继续查询，减少位置移动的影响。

在索引合适时，游标查询也可以避免大 offset 带来的大量扫描和跳过操作。

token 只是接口形式，不保证底层使用游标，也不自动保证不重不漏。实际结果还取决于排序是否稳定、排序字段是否变化、数据是否新增或删除，以及是否使用一致性快照。

### 3.3 鉴权与有效期

token 必须只表示分页续读位置，不能赋予资源访问权限。即使请求携带有效 token，服务端也必须正常执行鉴权。

对于在数据库中保存的 token，服务端可以在合理时间后使其过期，以回收状态；AIP 给出的经验参考是三天，并非强制期限，也不要求必须在文档中说明过期行为。

## 4. 跳过结果

API 可以提供 `int32 skip` 字段，表示跳过的资源条数，必须按条数解释，不能按页数解释。

- 不传 token，`skip=30`：从第 31 条开始返回一页。
- token 指向第 51 条，再传 `skip=30`：从第 81 条开始返回一页。

如果服务端因大数据量等原因无法及时完成跳过操作，必须返回 `200 OK` 和空结果集；在尚未确认到达末尾时，仍需提供 `next_page_token`，以便继续处理。若已确认跳过位置超出集合总量，则必须不提供 `next_page_token`。

## 5. 兼容性要求

返回集合的 RPC 必须从一开始就提供分页，并实际采用有限的默认页大小，不能只预留分页字段而始终返回全部数据。对于初期较小的集合，可以先在内存中完成分页。

事后给原本返回全部数据的接口增加分页，属于不兼容变更。例如，原调用方一次能获取全部 75 条数据，增加默认每页 50 条后，旧代码只会拿到前 50 条，并不知道需要继续翻页。

此外，客户端库通常会为分页接口提供自动遍历能力，方法签名可能与非分页接口不同，后加分页也可能破坏客户端库兼容性。
