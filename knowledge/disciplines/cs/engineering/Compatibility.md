# 兼容性

兼容性（Compatibility）指软件在接口、数据格式、版本或运行环境发生变化时，仍能按照约定协同工作或正确运行的能力。

## 1. 兼容方向

- **向后兼容（Backward Compatibility）**：新版本仍能支持旧版本的使用方式。例如，新服务仍能处理旧客户端的请求，新程序仍能读取旧格式的数据。
- **向前兼容（Forward Compatibility）**：旧版本能够处理新版本产生的输入，通常依赖预先设计的扩展机制。例如，旧客户端能够忽略新响应中不认识的可选字段，并继续正确处理已知字段。

判断兼容性时，应明确谁升级、谁保持旧版本，以及需要保留哪些行为。忽略未知字段只能提供有限的兼容能力，不能保证旧程序理解新功能。

## 2. 常见场景

### 2.1 接口兼容

修改 API 时，需要考虑已有调用方是否仍能正常使用。删除字段、增加必填参数、改变字段类型或业务含义，都可能破坏兼容性。

新增可选字段通常更容易保持兼容，但仍需确认调用方是否允许未知字段，以及序列化和校验规则是否支持这种变化。

### 2.2 数据兼容

修改数据库结构、消息格式或文件格式时，需要确认已有数据能否继续读取，以及新数据是否仍能被需要保留的旧程序处理。

例如，字段重命名可以分阶段完成：先增加新字段并保留旧字段，迁移读写逻辑和历史数据，待旧版本退出后再删除旧字段。迁移期间还需明确新旧字段的同步和冲突处理规则。

### 2.3 版本兼容

滚动发布期间，新旧服务实例、客户端和消息消费者可能同时存在，需要验证实际会出现的版本组合。

不仅要验证升级过程，还要考虑回退：如果新版本已写入旧版本无法读取的数据，仅回退程序可能无法恢复服务。

### 2.4 环境兼容

软件可能依赖特定的操作系统、浏览器、CPU 架构、语言运行时或依赖库版本。应明确支持范围，并验证关键环境中的行为。

## 3. 开发与发布检查

1. 明确需要支持的调用方、数据格式、版本组合和运行环境。
2. 检查接口、数据结构、默认值、错误码和业务语义是否发生变化。
3. 对必要的兼容场景进行验证，包括旧请求、历史数据和新旧版本共存。
4. 对破坏性变更采用分阶段迁移，并明确迁移完成和旧能力下线的条件。
5. 发布前检查回退后的程序能否处理已经产生的新数据和配置。
