# 倒排索引

倒排索引（Inverted Index），简称倒排，是组织“词项 → 包含该词项的文档列表”映射的数据结构，常用于全文检索。它使系统能够从查询词项直接定位候选文档，避免每次查询都逐篇扫描正文。

## 1. 正向与倒排

正向关系从文档出发，记录文档包含哪些词项；倒排关系从词项出发，记录哪些文档包含该词项。“倒排”描述的是映射方向的转换，不是把文字顺序反过来。

假设文本分析后得到以下词项：

| 文档 | 词项 |
| --- | --- |
| A | Redis、内存、管理 |
| B | MySQL、内存、优化 |
| C | Redis、缓存 |

对应的倒排索引为：

| 词项 | 文档列表 |
| --- | --- |
| Redis | A、C |
| 内存 | A、B |
| 管理 | A |
| MySQL | B |
| 优化 | B |
| 缓存 | C |

## 2. 基本组成

### 2.1 词项字典

词项字典记录可检索的词项，以及对应倒排列表的位置和相关统计信息。字典可以使用哈希表、树或有限状态转换器等结构实现，具体选择取决于精确查找、前缀枚举和存储空间等需求。

### 2.2 倒排列表

倒排列表（Posting List）由多个倒排记录（Posting）组成，每条记录对应一个包含该词项的文档，常见信息包括：

- 文档标识：用于定位文档，通常按标识排序，便于合并列表。
- 词频：该词项在文档中出现的次数，可以支持相关性评分。
- 词项位置：词项在文档中的位置，可以支持短语匹配和邻近查询。
- 字符偏移：词项对应的原文起止位置，可用于高亮等功能。

以上信息按需求保存，并非所有倒排索引都包含位置或偏移。标题、正文等字段也可以分别建立词项与文档之间的映射。

## 3. 查询操作

### 3.1 单词与布尔查询

单词查询先查词项字典，再读取对应倒排列表。多词查询可以按查询语义对列表进行集合运算：

- AND：取交集，要求文档包含全部指定词项。
- OR：取并集，要求文档至少包含一个指定词项。
- 排除：从当前候选集合中移除包含指定词项的文档。

例如，要求同时包含“Redis”和“内存”时：

```text
Redis → {A, C}
内存  → {A, B}
交集  → {A}
```

排序后的倒排列表可以通过多指针推进求交集或并集。高频词的列表可能很长，实际实现还会使用跳跃信息等方式减少扫描。

### 3.2 短语查询

文档包含所有查询词项，并不意味着这些词项连续出现。短语查询通常先确定共同文档，再检查各词项的位置关系；仅保存文档标识的倒排索引无法独立完成这类位置判断。

具体匹配语义取决于文本分析方式，例如停用词处理、位置间隔和同义词展开都可能影响短语匹配。

## 4. 构建与维护

1. 分配文档标识，并对需要索引的字段进行文本分析。
2. 收集每个词项在文档中的词频和位置等信息。
3. 按词项聚合记录，形成通常按文档标识排序的倒排列表。
4. 保存词项字典、倒排列表及所需统计信息。

大型系统常将索引分成多个段，在新数据写入后生成新段，并通过后台合并整理数据。删除可以先记录删除标记，后续合并时再清理；更新也可以通过删除旧记录并添加新记录实现，具体机制取决于实现。

有序文档标识可以采用差值编码等压缩方式，降低存储与读取成本，但压缩和解码也会引入计算开销。

## 5. 与相关性评分的关系

倒排索引负责组织词项与文档之间的匹配信息，评分算法利用词频、文档频率及文档长度等数据计算相关性。文档长度等统计数据可以由索引系统单独保存，并不一定放在每条倒排记录中。

倒排列表的顺序通常是文档标识顺序，不是相关性排名。实际查询可以交错执行候选匹配与评分，结合上界估计等优化，减少不必要的计算。

## 6. 局限

- 匹配依赖文本分析后的词项；分词或规范化不合适会导致漏召回或误匹配。
- 词项匹配本身不理解语义，同义表达需要查询扩展或其他检索方式补充。
- 全词匹配不等同于任意子串匹配；子串查询可能需要 n-gram 等额外索引策略。
- 高频词、位置记录和频繁更新可能增加存储、查询及维护成本。
