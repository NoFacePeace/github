# Cgroup

cgroup（Control Groups，控制组）是 Linux 内核用于管理一组进程资源的机制，可以对 CPU、内存、磁盘 I/O 等资源进行限制、分配和统计。Docker、Kubernetes 和 systemd 都会使用它管理资源。

## 1. 资源管理

cgroup 的资源控制功能由不同的控制器（controller）提供。

| 资源 | 管理能力 | 示例 |
| --- | --- | --- |
| CPU | 限制计算时间、设置竞争时的相对权重。 | 一组进程最多使用相当于 2 个 CPU 核的计算时间。 |
| 内存 | 统计内存用量，设置回收阈值和硬限制。 | 一组进程的内存硬限制为 4 GiB。 |
| 磁盘 I/O | 按块设备限制读写带宽、IOPS 等。 | 限制某个服务的磁盘读写速率。 |
| 任务数量 | 限制任务数量，Linux 中包含进程和线程。 | 防止服务无限创建进程或线程。 |

限制通常针对组内进程的合计用量，而不是给每个进程分别分配同样的额度。具体能力和行为取决于内核版本、启用的控制器及配置。

## 2. 层级结构

cgroup 支持父子层级，可以先限制一组服务的总资源，再为其中的服务细分额度。

```text
服务组：内存上限 8 GiB
├─ 服务 A：内存上限 6 GiB
└─ 服务 B：内存上限 6 GiB
```

服务 A 和 B 的实际合计用量仍受父级 8 GiB 上限约束，子组设置更大的额度不能绕过祖先的限制。

进程创建子进程时，子进程通常继承父进程所属的 cgroup；管理程序也可以通过相应接口迁移进程。

## 3. CPU 与内存限制

### 3.1 CPU 配额

CPU 配额限制的是一段时间内可以消耗的 CPU 时间，不表示独占或固定绑定某几个 CPU 核。

例如，cgroup v2 的 `cpu.max` 设置为 `200000 100000`，表示每个 100000 微秒周期最多消耗 200000 微秒的 CPU 时间，相当于 2 个 CPU 核的计算时间。多线程可以在多个核上并行运行，但耗尽周期配额后通常会被限流，等待后续周期。

CPU 权重表示资源竞争时的相对份额，不等于固定的 CPU 使用上限，也不保证持续获得某个核数。

### 3.2 内存限制与 OOM

内存统计不仅涉及应用堆内存，还可能包含页缓存和部分内核内存。达到硬限制时，内核会尝试回收内存；如果无法满足分配，可能触发该 cgroup 范围内的 OOM，杀死进程。

因此，设置 4 GiB 内存限制不表示应用可以把全部 4 GiB 都用于堆内存。交换空间也有相应的独立控制项，需要结合配置理解。

## 4. 与 namespace、容器的关系

| 机制 | 主要作用 |
| --- | --- |
| namespace | 隔离进程看到的系统环境，例如进程列表、网络和挂载点。 |
| cgroup | 管理进程使用的资源额度、权重与统计。 |
| 容器 | 结合 namespace、cgroup、文件系统和运行时等构建运行环境。 |

Docker 的 CPU、内存限制，以及 Kubernetes 的容器资源限制，最终通常通过 cgroup 等内核机制执行。Kubernetes 的资源请求还用于调度，并可影响运行时的资源配置，不能简单等同于硬限制。

## 5. cgroup v1 与 v2

| 版本 | 主要特点 |
| --- | --- |
| v1 | 不同控制器可以使用不同层级，管理接口较分散。 |
| v2 | 使用统一层级，控制器之间的组织规则和资源管理语义更加一致。 |

cgroup 通常通过挂载在 `/sys/fs/cgroup` 的虚拟文件系统暴露管理接口。v2 中常见文件包括：

| 文件 | 作用 |
| --- | --- |
| `cgroup.procs` | 查看组内进程 ID，或写入进程 ID 将其迁入该组。 |
| `cpu.max` | 设置 CPU 时间配额及周期。 |
| `memory.current` | 查看当前内存用量。 |
| `memory.max` | 设置内存硬限制。 |
| `memory.events` | 查看达到阈值、触发 OOM 等事件计数。 |
| `pids.max` | 设置任务数量上限。 |

这些文件是否出现取决于控制器是否可用、是否启用等条件。实际系统中通常通过 systemd、容器运行时或编排平台配置资源，由它们维护对应的 cgroup。
