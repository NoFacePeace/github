# Page Cache

Page Cache（页缓存）是操作系统在内存中维护的文件内容缓存，用于减少重复存储读取，并合并或延后部分写入。以下主要描述 Linux 普通文件的缓冲 I/O，其他平台和文件系统的细节可能不同。

## 1. 缓冲读取

程序通过普通文件读取接口访问数据时，内核通常先检查页缓存：

```text
程序读取文件
      ↓
检查 Page Cache
      ├─ 命中：从缓存取得数据
      └─ 未命中：从存储读取，填充缓存后返回
```

内核还可能预读后续内容，改善顺序读取。缓存命中通常减少存储 I/O，但仍有系统调用、数据复制等开销。

## 2. 缓冲写入与脏页

普通缓冲写入通常先更新页缓存，将尚未同步到后端存储的页标记为脏页。内核后续回写这些页，也可以按应用的同步要求提前处理。

```text
应用缓冲区
      ↓ write 等写入接口
Page Cache 中的脏页
      ↓ 回写与必要的存储同步
持久化存储
```

write 成功通常表示返回长度对应的数据已被内核接受，不代表已经持久化；调用还可能部分写入、报错，或因资源压力而阻塞。

## 3. 回写触发

| 场景 | 主要行为 |
| --- | --- |
| 后台回写 | 内核根据脏页年龄、阈值等策略安排写出。 |
| 脏页积累或内存压力 | 推动脏页回写，并可能限制产生脏页的进程速度；干净缓存则可以直接回收。 |
| 应用显式同步 | fsync、fdatasync 等请求同步指定范围的文件数据及所需元数据。 |
| 同步 I/O 选项 | O_SYNC、O_DSYNC 等改变写入完成所需满足的同步条件。 |

后台周期不是严格的持久化时间承诺。普通 close 也不能代替明确的持久化操作；需要掉电恢复保障时，应按文件系统与接口语义设计同步流程。

## 4. write、fsync 与掉电保障

| 接口或状态 | 含义 |
| --- | --- |
| write 返回成功 | 缓冲 I/O 下，通常已接受数据到内核缓存，但未必落盘。 |
| fsync 成功完成 | 请求文件数据及相关元数据达到接口定义的持久化要求。 |
| fdatasync 成功完成 | 同步数据及正确读取该数据所必需的元数据，不要求同步所有非必要元数据。 |

持久化仍依赖文件系统、存储栈和设备正确兑现请求，不能仅用“到达磁盘控制器”判断掉电安全。新建或重命名文件时，文件内容同步还不一定保证目录项持久化，可能需要同步相应目录。

仅应用进程崩溃时，内核页缓存通常仍在；操作系统崩溃或掉电则可能丢失尚未持久化的修改。因此“进程重启后数据还在”不能证明已满足掉电持久性。

## 5. 与应用缓存的区别

| 缓存 | 所属层次 | 作用 |
| --- | --- | --- |
| 应用缓冲区 | 用户态进程。 | 暂存应用准备读写或处理的数据。 |
| Page Cache | 操作系统。 | 缓存文件内容，协调缓冲 I/O 与回写。 |
| 数据库 Buffer Pool | 数据库引擎。 | 管理数据库页及其状态，并配合引擎并发控制与恢复机制。 |

例如 InnoDB Buffer Pool 的脏页与操作系统脏页不是同一个概念。数据库将页交给文件系统后，在缓冲 I/O 路径下还可能进入 Page Cache；使用直接 I/O 时，路径又有所不同。

## 6. 直接 I/O 与内存观察

直接 I/O 通常用于绕过文件数据的页缓存，减少部分双重缓存，但有对齐和文件系统支持等限制。O_DIRECT 本身不等于 O_SYNC，也不能单凭绕过 Page Cache 就认定数据已经持久化。

页缓存会使用空闲内存，并可在需要时回收，其中脏页通常要先处理回写。因此系统显示较少 free 内存不一定表示内存不足，还应结合 available、回收压力、换页、脏页和 I/O 延迟判断。
