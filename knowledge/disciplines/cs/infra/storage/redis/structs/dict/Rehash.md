# Rehash

Redis 字典的 rehash 是重新分配桶数组、将条目迁移到新表的过程，常用于扩容或缩容。以下以 Redis 7.2 为例。

## 1. 为什么需要迁移

桶数量改变后，同一个键的哈希值可能对应不同的桶下标。因此不能只扩大或缩小原数组而保持条目位置不变，需要重新确定条目的桶位置。

```text
旧表：8 个桶，hash & 7
新表：16 个桶，hash & 15
```

这里重新安排的是条目的位置，并非修改键或值，也不是 AOF 日志重写。

## 2. 触发与容量

字典插入时会检查是否需要分配初始表或扩容；删除后的某些上层路径也会检查是否需要缩容。触发行为取决于负载、字典使用场景以及当前的扩缩容控制状态，不能简单认为每次删除都会缩容。

普通自动扩容在允许调整容量时，通常于条目数量达到桶数量后考虑扩容。后台持久化等场景会调整 resize 策略，减少迁移和写时复制开销；更高负载下也可能允许扩容，因此不能把常见负载阈值当成所有状态下的固定规则。

新桶数量按二的幂选择，并由 `ht_size_exp` 记录对应指数。初始分配也会建立桶数组，但因为没有旧条目，不需要执行实际的迁移工作。

## 3. 迁移过程

1. 为第 `1` 张表分配新桶数组，保留第 `0` 张旧表，并将 `rehashidx` 设为迁移起点。
2. 从旧表当前位置扫描，跳过空桶，将选中桶内的条目重新挂到新表对应的桶中。
3. 旧表的条目计数减少，新表的条目计数增加，并推进 `rehashidx`。
4. 旧表条目全部迁移完毕后，释放旧桶数组，让新表接替旧表，重置备用表状态及 `rehashidx`。

条目通常通过调整链接迁移，不需要把每个键值对象的内容重新复制一份。分配新桶数组及修改内存页仍有资源开销。

## 4. 渐进式执行

Redis 不要求一次搬完全部条目，而是将迁移工作分摊到多次操作中：

- 常规字典访问路径会尝试推进少量 rehash 工作。
- Redis 的周期性维护也会在符合条件时，对部分字典推进有时间预算的迁移，并非所有字典都有独立的后台任务。
- 存在[暂停计数](struct/pauserehash.md)时，遵守该状态的推进路径会暂时跳过迁移。

迁移通常以桶为推进单位，一个桶可能包含多个冲突条目。分批执行降低了集中搬运的成本，但不保证每一步严格只处理一个条目，也不保证每次操作耗时完全相同。

这里的渐进式迁移通常由 Redis 主线程在操作和维护过程中执行，不等于另起一个子进程负责迁移。

## 5. 迁移期间的读写

| 操作 | 行为 |
| --- | --- |
| 查找 | 根据迁移状态查询旧表和新表，避免遗漏尚未迁移或已经迁移的条目。 |
| 插入新键 | rehash 期间通常插入新表，避免继续增加旧表的迁移负担。 |
| 更新已有键 | 找到条目后更新值，不因迁移而创建重复键。 |
| 删除 | 在可能包含目标键的表中查找并删除，更新对应计数。 |

纯迁移不会改变字典的总条目数；期间业务插入或删除则会改变总数。

## 6. 相关字段

| 字段 | 作用 |
| --- | --- |
| [ht_table](struct/ht_table.md) | 保存新旧两套桶数组的入口。 |
| [ht_used](struct/ht_used.md) | 分别记录新旧表的条目数量。 |
| `ht_size_exp` | 记录两张表各自的桶数量指数。 |
| `rehashidx` | 记录旧表扫描迁移位置，`-1` 表示没有进行 rehash。 |
| [pauserehash](struct/pauserehash.md) | 控制常规迁移推进是否暂停。 |
