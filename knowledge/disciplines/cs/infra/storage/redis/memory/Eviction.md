# Eviction

内存淘汰是 Redis 在受控内存用量超过配置上限时，根据策略删除键、释放空间的机制。是否淘汰以及选择哪些键，由内存上限和淘汰策略共同决定。

## 1. 配置与默认行为

- [maxmemory](../config/maxmemory.md)：内存上限，常见 64 位 Redis 默认值为 `0`，表示不设置此上限。
- [maxmemory-policy](../config/maxmemory-policy.md)：淘汰策略，默认值为 `noeviction`，不主动淘汰键。

因此默认配置通常不会因为达到某个 Redis 内存阈值而自动删键，但仍受机器或容器限制，可能因系统内存不足而被终止。

例如缓存实例可以按容量规划设置：

```conf
maxmemory 1gb
maxmemory-policy allkeys-lru
```

该示例并非适用于所有业务的推荐值；应根据工作集、访问模式和可接受的数据丢失范围选择。

## 2. 淘汰策略

| 策略 | 候选范围 | 行为 |
| --- | --- | --- |
| `noeviction` | 不淘汰 | 内存不足时拒绝受内存限制的写入，读取和删除等操作通常仍可执行。 |
| `allkeys-lru` | 所有键 | 优先淘汰较久未访问的键。 |
| `allkeys-lfu` | 所有键 | 优先淘汰使用频率较低的键。 |
| `allkeys-random` | 所有键 | 随机淘汰。 |
| `volatile-lru` | 设置了过期时间的键 | 按 LRU 淘汰。 |
| `volatile-lfu` | 设置了过期时间的键 | 按 LFU 淘汰。 |
| `volatile-random` | 设置了过期时间的键 | 随机淘汰。 |
| `volatile-ttl` | 设置了过期时间的键 | 优先淘汰剩余 TTL 较短的键。 |

LRU 关注最近访问时间，LFU 关注访问频率并考虑衰减。Redis 使用采样等近似机制，不会对所有键持续进行精确排序。

`volatile-*` 的候选键只是设置了过期时间，不要求已经过期。找不到候选键或无法释放足够内存时，也可能拒绝写入。

## 3. 淘汰与过期

| 机制 | 触发原因 | 对尚未过期键的影响 |
| --- | --- | --- |
| 过期 | TTL 到期，由惰性检查和主动清理等机制处理。 | 不会仅因内存紧张而提前过期。 |
| 淘汰 | 内存压力达到策略触发条件。 | 可能提前删除键，`allkeys-*` 还可删除没有 TTL 的键。 |

选择 `noeviction` 不会关闭正常过期清理。TTL 到期也不意味着所有键都在同一时刻立即完成物理删除。

## 4. 内存上限的边界

`maxmemory` 不是进程驻留内存的严格上限，部分复制或 AOF 缓冲开销不计入淘汰判断，内存碎片和后台持久化的写时复制也会增加实际占用。大型命令还可能使内存暂时超过阈值。

应为这些开销留出余量，并监控淘汰速率、命中率和数据库回源压力，避免淘汰导致缓存抖动。

## 5. 场景选择

可重建的缓存通常能够接受淘汰；锁提前被删除可能允许其他客户端重复获取，消息流被淘汰则会丢失整个键及其消息状态。

应按数据用途选择策略，必要时将缓存与锁、消息等数据分开部署。`noeviction` 可以避免按策略淘汰，但内存不足时仍会导致写入失败，不代替容量规划和故障处理。
