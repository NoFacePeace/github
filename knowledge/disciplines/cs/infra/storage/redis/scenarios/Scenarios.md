# Scenarios

Redis 适合需要低延迟访问、原子数据操作和临时状态管理的场景，选型时需要结合内存容量、持久性和故障后的正确性要求。

## 1. 常见场景

| 场景 | 常用类型或机制 | 示例 |
| --- | --- | --- |
| 缓存 | String、Hash、TTL | 缓存商品信息，减少数据库查询。 |
| 会话与临时凭证 | String、Hash、TTL | 登录会话、验证码和短期令牌。 |
| 计数器 | String、`INCR` | 浏览量、点赞数和调用次数。 |
| 限流 | 计数器、ZSet、Lua | 限制用户在时间窗口内的请求次数。 |
| 排行榜 | ZSet | 积分榜、热度榜和游戏排名。 |
| 集合关系 | Set | 标签、共同关注和去重。 |
| 消息流 | Stream、消费者组 | 异步任务和事件处理。 |
| [分布式锁](DistributedLock.md) | `SET NX PX`、Lua | 协调多个实例对共享资源的访问。 |
| 库存与配额 | 整数操作、Lua | 检查并扣减可用数量。 |
| 实时通知 | Pub/Sub | 向当前在线订阅者广播消息。 |
| 活跃状态统计 | Bitmap | 签到记录和每日活跃状态。 |
| 近似去重计数 | HyperLogLog | 估算独立访客数量。 |
| 地理位置查询 | Geo | 查找附近门店或司机。 |

## 2. 选型边界

- Pub/Sub 不保存消息，订阅者离线会错过消息；需要保留消息和消费确认时可以考虑 Stream，并设计重试与幂等处理。
- HyperLogLog 提供近似计数，不能用于列出具体成员。
- 锁、库存和配额需要结合过期、故障切换和数据丢失分析正确性，不能仅凭单条命令原子执行就认为业务流程始终安全。
- 数据主要驻留内存，应评估容量、过期与淘汰策略，以及恢复和备份需求。
