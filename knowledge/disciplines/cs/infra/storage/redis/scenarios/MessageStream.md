# Message Stream

Redis 的 [Stream](../types/Stream.md) 类型按消息 ID 保存追加式记录，配合消费者组可以作为消息队列使用，适合异步任务和事件处理。

## 1. 消息流与消息队列

消息流和消息队列不是互斥分类。Stream 强调按顺序保存消息记录；消费者组提供分工消费、确认和待处理消息管理。

Kafka、RocketMQ 等消息系统也支持多个消费组，不能用是否支持多个消费组区分消息流和消息队列。选型应比较具体的消息保留、失败重试、顺序保证、持久性和吞吐量要求。

## 2. 写入与消费

以下命令演示创建消费者组、写入消息、读取并确认：

```redis
XGROUP CREATE orders inventory 0 MKSTREAM
XADD orders * order_id 123 action created
XREADGROUP GROUP inventory worker-1 COUNT 10 STREAMS orders >
```

`orders` 是消息流，`inventory` 是消费者组，`worker-1` 是组内消费者。`>` 表示读取尚未投递给该组消费者的新消息。

业务处理成功后，使用返回的真实消息 ID 确认，例如：

```redis
XACK orders inventory 1720000000000-0
```

组创建时的 `0` 表示从现有消息开始消费；如果使用 `$`，则只消费创建该组之后的新消息。上述创建命令用于首次初始化，重复创建同名组会报错。

## 3. 消费者组

- 同一个组内，新的消息通常分配给其中一个消费者处理，实现任务分工；失败认领等情况可能使同一消息被再次处理。
- 不同组拥有独立的消费进度和待处理记录，可以分别消费同一批消息。例如库存组扣减库存，通知组发送通知。
- `XACK` 只清除指定组中该消息的待确认状态，不会自动删除流中的消息，也不代表其他组已经处理完成。

不使用消费者组时，也可以通过 `XREAD` 读取消息，但应用需要自行维护读取位置，不会自动获得组内分工和待确认记录。

## 4. 失败与重试

默认情况下，`XREADGROUP` 投递的消息会进入该组的待处理条目列表（PEL），直到被确认。消费者崩溃后，消息不会仅因超时就自动重新投递，需要应用或框架处理：

| 命令 | 用途 |
| --- | --- |
| `XPENDING` | 检查待确认消息及相关消费者、空闲时间和投递次数。 |
| `XCLAIM` | 将符合条件的待处理消息转交给另一个消费者。 |
| `XAUTOCLAIM` | 扫描并认领空闲时间达到阈值的消息，Redis 6.2 起支持。 |

业务处理成功但尚未 `XACK` 时发生故障，会导致消息可能再次被处理。消费者应使用业务唯一键、去重记录或幂等更新，不能假设恰好执行一次。

还应设置重试次数与失败消息处置策略，避免一条持续失败的消息反复占用处理资源。

## 5. 保留与顺序

消息由 `XTRIM`、`XDEL` 或写入时的裁剪选项等机制控制保留，确认与保留是不同的概念。裁剪策略应结合所有消费者组的进度设计，避免清理仍待消费或处理的消息内容。

单个流的记录按 ID 排序，但多个消费者并行处理时，业务完成顺序不一定与消息顺序相同。需要严格顺序时，应设计分区、消费者并发和重试策略。

## 6. 持久性与容量

Stream 保存在 Redis 数据集中，故障后的消息保留取决于持久化和复制配置。异步复制下，主节点已确认的消息仍可能在故障切换后丢失。

消息不会因消费确认自动移除，需要评估内存容量、积压监控、保留时间和淘汰策略。Pub/Sub 则不保留消息，也不提供 Stream 消费者组的确认与待处理机制。
