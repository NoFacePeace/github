# Distributed Lock

分布式锁用于协调多个进程或服务实例对同一资源的访问。Redis 常用带过期时间的 [String](../types/String.md) 类型键表示锁，值为本次持有者的唯一随机 token。持有者在有效期内执行任务，完成后验证身份并释放。

## 1. 获取锁

```redis
SET lock:order:123 unique-token NX PX 30000
```

| 参数 | 作用 |
| --- | --- |
| `lock:order:123` | 对应受保护资源的锁键，竞争同一资源的客户端使用同一个键。 |
| `unique-token` | 每次获取尝试生成的唯一随机标识，用于验证持有者身份。 |
| `NX` | 仅在键不存在时设置。 |
| `PX 30000` | 设置 30000 毫秒的有效期，避免持有者崩溃后锁一直不释放。 |

返回 `OK` 表示成功，空结果表示未获取锁。设置锁值和过期时间应在同一条命令中完成，避免分开执行 `SETNX` 与 `EXPIRE` 时中途失败。

请求超时不等于获取失败，命令可能已在服务端执行；客户端需要处理结果不确定的情况，不能在未确认持有有效锁时直接进入临界区。

## 2. 释放锁

不能直接执行 `DEL`：自己的锁可能已过期并被另一客户端重新获取。可以通过 [Lua](../lua/Lua.md) 脚本先比较 token，再原子删除：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

`KEYS[1]` 传入锁键，`ARGV[1]` 传入本次获取锁使用的 token。比较与删除必须放在同一个脚本中，避免两步之间锁状态变化。

## 3. 过期与续期

任务应在锁有效期内完成。需要续期时，也应在脚本中先确认 token 仍匹配，再执行 `PEXPIRE`，防止延长其他客户端的锁。

进程暂停、网络延迟或续期失败都可能使锁先于任务结束而过期。锁过期不会停止旧持有者的代码，旧持有者恢复后仍可能继续访问资源，与新持有者并发执行。

## 4. 故障切换的边界

Redis 主从通常采用异步复制，副本可能落后于主节点。单实例上的原子获取不能保证故障切换后仍保持互斥，例如：

1. 客户端 A 在主节点成功获取锁，并开始执行任务。
2. 锁的写入尚未复制到副本，主节点就发生故障。
3. 副本晋升为新主节点，但没有这把锁，客户端 B 因而也能成功获取锁。
4. 客户端 A 可能仍在执行任务，导致 A 和 B 同时访问受保护的资源。

Lua 只保证当前节点上的检查与修改连续执行，不能保证写入已复制到副本，也不能避免故障切换造成的锁丢失。普通业务数据也存在类似问题：从副本读取可能得到旧值，已确认的主节点写入也可能在故障切换后丢失。

### 4.1 WAIT 的作用与限制

获取锁成功后，可以在同一个连接上执行 `WAIT`，等待副本确认该连接此前的写入。例如：

```redis
WAIT 1 1000
```

表示最多等待 1000 毫秒，目标是至少一个副本确认复制。返回值是实际确认的副本数量，超时返回不代表目标已达成，也不会撤销此前的锁写入。

`WAIT` 可以降低未复制就发生故障导致锁丢失的风险，但副本确认复制不等于已经持久化到磁盘，也不保证故障切换一定选择包含该写入的副本。因此，它不能将 Redis 变为具有强一致性保证的锁服务。

持久化与复制可以改善恢复能力，但不能自动消除所有锁丢失和重复持有风险。需要严格互斥的业务，应根据一致性要求选择锁服务，并在资源端提供额外保护。

## 5. 业务侧保护

- 使用幂等键、唯一约束或条件更新，限制重复执行造成的影响。
- 需要防止过期持有者继续写入时，可以使用单调递增的 fencing token，由受保护的资源端检查并拒绝旧 token 的请求。
- 随机的锁 token 用于验证锁身份，不具备 fencing token 的顺序语义；fencing token 的生成机制也需要满足故障场景下的单调性要求。
- 释放与续期只能操作自己持有的锁，获取失败时采用有界重试和退避，避免无限等待与集中竞争。
