# Pub/Sub

Redis 内置发布/订阅（Pub/Sub）机制：发布者向频道发送消息，Redis 将消息推送给当前订阅该频道的客户端。它适合允许消息丢失的实时通知，不提供持久化消息队列的消费确认和补读能力。

## 1. 发布与订阅

客户端 A 订阅频道：

```redis
SUBSCRIBE order-events
```

客户端 B 发布消息：

```redis
PUBLISH order-events "order 123 created"
```

当前在线并已完成订阅的客户端会收到消息。订阅者之后才连接或订阅时，不能读取此前的消息。

| 命令 | 作用 |
| --- | --- |
| `SUBSCRIBE channel` | 订阅频道。 |
| `UNSUBSCRIBE channel` | 取消频道订阅。 |
| `PUBLISH channel message` | 向频道发布消息。 |
| `PSUBSCRIBE pattern` | 按模式订阅，例如 `order:*`。 |
| `PUNSUBSCRIBE pattern` | 取消模式订阅。 |

应用通常使用专用订阅连接和客户端库的消息回调。`PUBLISH` 的返回值不是业务处理成功的确认，发布者不能据此判断订阅者是否完成处理。

## 2. 频道与数据类型

Pub/Sub 是通信机制，不是 String、List 或 Stream 等键的数据类型。使用前不需要创建数据键，也不需要事先创建频道。

频道名与键名彼此独立：一个叫 `news` 的 String 键，可以与 `news` 频道同时存在，互不影响。发布消息不会修改同名键，删除同名键也不会取消频道订阅。

普通 Pub/Sub 频道不按 Redis 数据库编号隔离，不同数据库中的客户端可以通过同名频道通信。需要业务隔离时，应设计频道命名空间。

## 3. 内存与消息存储

Redis 在内存中维护频道、订阅者及连接之间的关系。发布时，将消息交给匹配的订阅连接，通过连接输出缓冲区和网络发送。

输出缓冲区只临时保存待发送的数据，不是可查询、可回放的消息存储。Pub/Sub 消息不会作为持久化记录保存到 RDB 或 AOF，也没有供消费者恢复进度的历史日志。

没有订阅者时，消息不会被保留。订阅连接断开后也不能补读断线期间的消息；慢消费者还可能因输出缓冲区超过限制而被断开。

## 4. 与 Stream 的区别

| 能力 | Pub/Sub | Stream |
| --- | --- | --- |
| 保存消息供后续读取 | 不支持。 | 支持，受保留策略限制。 |
| 离线补消费 | 不支持。 | 消息仍保留时可以。 |
| 消费确认与待处理管理 | 不支持。 | 消费者组支持。 |
| 消费者分工 | 向匹配订阅者广播，没有消费者组分工机制。 | 同组分工、不同组独立消费。 |

需要消费确认、失败重试或历史回放时，可以考虑[消息流](MessageStream.md)。Stream 的持久性仍取决于 Redis 的持久化与复制配置。

## 5. 使用边界

Pub/Sub 可用于在线事件提示、界面刷新信号等场景。接收通知后重新查询事实来源，通常比把通知本身作为唯一业务依据更稳妥；丢失通知时还需要定期刷新或重新同步等补救方式。

不能仅凭 Pub/Sub 保证订单处理、支付或库存扣减等任务可靠执行。它提供至多一次的投递语义，没有消费确认与自动重试机制。
