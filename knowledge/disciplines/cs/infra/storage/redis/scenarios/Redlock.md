# Redlock

Redlock 是一种基于多个独立 Redis 节点的分布式锁算法，通过在多数节点上获取锁，降低对单个节点的依赖。它的正确性依赖锁有效期、时钟和故障模型等假设，不能仅凭多数节点获取成功就认为任意故障下都能保持互斥。

## 1. 节点部署

典型部署使用 5 个独立 Redis 节点，每个节点独立保存锁状态，彼此不通过主从复制同步这把锁。应尽量避免节点共享同一个故障来源。

多数节点数量为 `floor(N / 2) + 1`；5 个节点时需要至少 3 个。单个 Redis 主节点及其副本不能直接作为多个独立节点计数。

## 2. 获取流程

1. 为本次获取尝试生成唯一随机 token，并记录开始时间。
2. 使用同一锁键、token 和有效期，向各节点尝试执行 `SET key token NX PX ttl`。单节点请求超时应显著小于锁有效期，避免长期等待不可达节点。
3. 统计成功节点数和本次获取的总耗时。
4. 只有成功节点达到多数，且扣除获取耗时和时钟漂移余量后仍有有效时间，才认为获取成功。
5. 如果获取失败，向所有节点尝试释放本次 token 对应的锁，包括请求超时、结果不确定的节点；需要重试时加入随机退避。

可以向多个节点并发发送请求，以减少获取耗时，但仍必须检查整个获取过程的时间和结果。

## 3. 剩余有效期

```text
剩余有效期 = 设置的锁有效期 - 获取总耗时 - 时钟漂移余量
```

例如有效期为 10000 毫秒，获取耗时 200 毫秒，预留漂移余量 100 毫秒，则剩余有效期最多按 9700 毫秒计算。

客户端必须在剩余有效期内完成受保护操作，不能从收到最后一个成功响应时重新计算完整有效期。客户端应使用适合测量持续时间的单调时钟，但这不能消除服务端过期计时异常带来的风险。

## 4. 释放与续期

释放时向所有节点发送操作，在各节点原子比较 token 并删除，避免删除其他客户端后来获取的锁。释放不需要等到本地计算的有效期耗尽。

需要续期时，在各节点原子验证 token 并延长有效期，还必须在当前有效期内获得多数成功确认，并重新计算可用时间。只延长一个节点不能视为整把 Redlock 锁续期成功。

## 5. 故障与正确性限制

| 情况 | 风险或影响 |
| --- | --- |
| 进程长时间暂停 | 锁可能已过期，旧持有者恢复后仍继续执行，与新持有者并发访问资源。 |
| 网络延迟或分区 | 获取可能失败或结果不确定，等待锁过期也可能降低可用性；延迟到达的资源写入仍需防护。 |
| 时钟漂移或服务端时钟跳变 | 可能破坏对锁有效期的判断，影响互斥假设。 |
| 节点丢失锁状态后立即重启 | 可能重新授予尚未实际失效的锁；需结合持久化或延迟重新加入等策略分析安全性。 |
| 多个节点同时故障 | 多数节点不可达时无法正常获取锁，共享故障来源还可能导致多个节点同时丢失状态。 |

Redlock 的安全性存在公开讨论，不能把多数节点获取锁等同于基于共识协议的强一致性协调。部署和客户端实现必须明确其时间与故障假设。

## 6. 资源端保护

随机 token 用于验证锁身份，不能判断某次操作是否来自过期的旧持有者。Redlock 本身不提供单调递增的 fencing token。

对不能容忍并发写入的业务，应评估基于共识协议的协调服务，并在资源端结合 fencing token、唯一约束、条件更新或幂等机制限制旧请求和重复操作造成的影响。即使使用协调服务，锁过期后旧持有者继续执行的问题仍需要资源端配合处理。
