# Cache

Redis 缓存将数据库查询结果或计算结果保存在内存中，减少重复查询与计算，降低响应延迟。缓存通常是可以重建的数据副本，数据库等持久存储仍作为事实来源。

## 1. 数据类型

| 类型 | 适合的数据 | 示例 |
| --- | --- | --- |
| [String](../types/string/String.md) | 序列化后的对象、文本或二进制结果。 | 将商品对象序列化为 JSON，整体读取和替换。 |
| [Hash](../types/Hash.md) | 需要按字段读取或修改的对象。 | 商品名称、价格和状态分别存为字段。 |

选择类型时，应结合访问方式、序列化开销和对象大小。缓存键应包含业务命名空间、资源标识及必要的版本或查询条件，避免不同请求错误复用同一份结果。

## 2. 读取与回填

常见的旁路缓存模式（Cache-Aside）由应用负责读取和更新缓存：

1. 查询 Redis，命中则返回结果。
2. 未命中时查询数据库。
3. 将查询结果写入 Redis，并设置过期时间，再返回结果。

例如缓存一个商品对象：

```redis
SET cache:product:123 '{"id":123,"name":"book"}' EX 300
GET cache:product:123
```

`EX 300` 表示 300 秒后过期。String 的值与 TTL 应尽量在同一条命令中设置，避免分开操作时中途失败，留下未过期的键。

## 3. 更新与一致性

常见做法是先更新数据库，成功后删除对应缓存，让后续读取回源并重建。先删除缓存再更新数据库，可能让并发读请求把旧值重新写入缓存。

即使先更新数据库再删除缓存，也不等于强一致：删除可能失败，更新前开始的慢查询也可能在删除后将旧数据回填。TTL 只能限制某次缓存写入后的存活时间，不能单独消除并发竞态。

可结合业务版本校验、可靠的失效事件、失败重试或串行化更新减少旧数据窗口。对不能接受旧数据的读取，应按业务要求直接读取事实来源或采用更严格的一致性方案。

## 4. 过期与容量

- 根据数据更新频率和允许的陈旧时间设置 TTL，过短会增加回源，过长会扩大旧数据窗口。
- 对大量键的 TTL 加入随机偏移，避免集中失效。
- 过期与内存淘汰是不同机制，键也可能因内存压力被提前淘汰，应用必须能够处理未命中。
- 控制大键与缓存总量，监控命中率、回源量、延迟、内存和淘汰次数。

## 5. 常见问题

| 问题 | 表现 | 常见处理 |
| --- | --- | --- |
| 缓存穿透 | 请求不存在的数据，反复回源。 | 校验参数、短 TTL 缓存空结果，或使用布隆过滤器辅助过滤。 |
| 缓存击穿 | 热点键失效时，大量并发请求同时回源。 | 合并同一键的加载请求、互斥重建、提前刷新或按业务允许返回旧值。 |
| 缓存雪崩 | 大量键集中失效或缓存服务故障，回源流量激增。 | 随机 TTL、限流、降级、容量规划与故障演练。 |

缓存空结果时需要区分“不存在”和“查询失败”，并处理数据新建后的失效，避免长期遮蔽新数据。使用互斥重建时，仍需考虑锁过期、等待超时与故障切换。

## 6. 故障处理

缓存不可用时，不能无条件将所有请求转发数据库，应设置超时、回源并发上限和降级策略，避免将缓存故障扩散到事实存储。

如果 Redis 同时保存锁、队列等不可随意丢弃的数据，应分别评估其持久性与淘汰要求，避免直接沿用纯缓存的配置。
