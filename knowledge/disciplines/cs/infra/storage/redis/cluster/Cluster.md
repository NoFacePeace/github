# Cluster

Redis Cluster 将数据分散到多个主节点，并通过副本与自动故障切换提高可用性。它同时涉及容量扩展、请求路由和故障处理。

## 1. 数据分片

Redis Cluster 将键空间划分为 16384 个哈希槽，每个主节点负责其中一部分。一个键映射到一个槽，由负责该槽的主节点处理。

例如三个主节点可以这样分配：

| 主节点 | 负责的槽 | 副本 |
| --- | --- | --- |
| A | `0`～`5460` | A 的副本。 |
| B | `5461`～`10922` | B 的副本。 |
| C | `10923`～`16383` | C 的副本。 |

新增主节点不会自动将所有现有数据均匀分配过去，需要迁移部分槽及其数据。一个键及其值不会因为使用 Cluster 就自动拆分到多个主节点，因此大键和热点键仍可能成为单节点瓶颈。

## 2. 哈希槽与 Hash Tag

通常按以下方式计算键对应的槽：

```text
slot = CRC16(key) mod 16384
```

如果键包含符合规则的非空 `{...}`，只对其中的内容计算哈希，这部分称为 Hash Tag。例如：

```text
order:{123}:info
order:{123}:items
```

两个键都根据 `123` 计算槽，可以放到同一个槽中。Hash Tag 适合需要共同操作的相关键，但大量键使用相同标签可能导致数据和流量集中。

## 3. 客户端路由

客户端通常维护槽到节点的映射，并直接向负责目标槽的节点发送请求。访问错误节点或发生迁移时，可能收到重定向：

| 响应 | 含义 |
| --- | --- |
| `MOVED` | 目标槽由其他节点负责，客户端应刷新或修正路由。 |
| `ASK` | 槽迁移期间的一次临时重定向，客户端向目标节点发送 `ASKING` 后重试该命令，不应据此永久修改整个槽的归属。 |

应用应使用支持 Cluster 的客户端，处理路由更新、重连和重定向。连接任意节点并不意味着该节点会替客户端代理所有跨节点请求。

### 3.1 客户端与节点的职责

普通业务客户端主要查询路由和接收重定向，不参与决定槽归属或故障切换选举。槽分配与迁移由管理操作发起，节点维护并传播归属信息；副本晋升由集群节点协调。

客户端通常先连接配置中的一个可达节点，查询槽与节点的映射，再根据键计算目标槽并直接访问对应节点。拓扑变化后，客户端根据重定向和拓扑查询更新映射。这些流程通常由客户端库完成，业务代码不需要自行实现。

Redis Cluster 没有代理所有请求的全局 leader。各主节点分别负责自己的槽，故障切换时也只是为失效主节点选择副本接管其槽。

### 3.2 节点之间的通信

集群节点通过 Cluster Bus（集群总线）交换成员、槽归属和故障状态，并协调副本选举等操作。节点使用 PING/PONG 和 Gossip 等机制传播状态，不依赖业务客户端转发这些信息。

| 通信通道 | 主要用途 |
| --- | --- |
| 客户端连接数据端口 | 查询拓扑、执行读写、接收 `MOVED` 或 `ASK` 重定向。 |
| 节点之间的 Cluster Bus | 心跳、成员发现、槽信息传播、故障报告与选举协调。 |
| 主从复制连接 | 传输全量数据和后续增量变更，与 Cluster Bus 是不同通道。 |

Cluster Bus 端口默认通常为数据端口加 `10000`，例如数据端口 `6379` 对应总线端口 `16379`；也可以通过 `cluster-port` 单独配置。节点间需要能够访问总线端口以及复制等操作所需的数据端口，总线端口不用于客户端执行普通 Redis 命令。

## 4. 多键操作限制

多键命令、事务和 Lua 脚本通常要求涉及的键位于同一个槽，否则可能收到 `CROSSSLOT` 错误。Hash Tag 可以让相关键落入同一槽。

某些客户端会将部分批量请求拆到多个节点执行，但这不等于跨节点原子操作。Cluster 不提供通用的跨槽事务；槽迁移期间，多键操作还可能因键分布发生变化而暂时失败，需要结合错误类型设计重试。

## 5. 副本与故障切换

每个主节点可以配置副本。主节点故障后，符合条件的副本可以通过选举晋升，并接管原主节点的槽。

自动故障切换需要满足多数主节点可达、候选副本符合条件等要求。常见部署是三个主节点各配置一个副本，并将副本与对应主节点放在不同故障域；这不代表任意多个节点故障都能继续提供服务。

复制通常是异步的，主节点已确认的写入如果尚未复制，就可能在故障切换后丢失。副本读取也可能得到旧数据，Cluster 不因此提供强一致性保证。

## 6. 槽覆盖与可用性

节点失效且没有可接管的副本时，相关槽可能不可用。`cluster-require-full-coverage` 决定缺少槽覆盖时的整体服务行为：

| 值 | 行为 |
| --- | --- |
| `yes` | 默认要求完整槽覆盖；存在未覆盖槽时，集群会拒绝正常的数据操作。 |
| `no` | 缺少部分槽时，可继续处理仍正常覆盖的槽，缺失槽的数据访问仍失败。 |

关闭完整覆盖要求不代表可以忽略多数主节点不可达等其他故障条件，也不能恢复缺失的数据。

## 7. 与 Sentinel 的区别

| 方式 | 主要用途 |
| --- | --- |
| 主从复制配合 Sentinel | 监控、发现主节点并执行故障切换，通常不提供自动数据分片。 |
| Redis Cluster | 将数据分片到多个主节点，并提供副本故障切换和客户端重定向机制。 |

需要突破单个主节点的容量或吞吐限制时，可以评估 Cluster；仅需一组主从的自动切换时，可以评估 Sentinel。最终仍需结合客户端兼容性、多键操作和故障处理成本选择。
