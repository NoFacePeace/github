# Transactions

Redis 事务将一组命令先排队，再按顺序连续执行。执行期间其他客户端的命令不能插入，但 Redis 不提供执行失败后的自动回滚。

## 1. 常用命令

| 命令 | 作用 |
| --- | --- |
| `MULTI` | 开始事务，将后续普通数据操作命令加入队列。 |
| `EXEC` | 检查事务能否执行，并执行已入队的命令，返回各命令的结果。 |
| `DISCARD` | 丢弃尚未执行的事务队列，退出事务并清除 WATCH 状态。 |
| `WATCH` | 在 `MULTI` 之前监视键，供 `EXEC` 检查是否发生修改。 |
| `UNWATCH` | 清除当前连接监视的所有键。 |

事务队列和 WATCH 状态属于当前连接，相关操作必须使用同一个连接。

## 2. 排队与执行

```redis
MULTI
SET count 10
INCR count
EXEC
```

`SET` 和 `INCR` 入队时通常返回 `QUEUED`，并不立即修改数据。`EXEC` 执行这两条命令后，`count` 为 `11`。

从 `MULTI` 到 `EXEC` 之前，其他客户端仍可读写相关键。只有在 `EXEC` 执行事务队列期间，其他客户端的命令才不能插入；不能把它理解为从 `MULTI` 开始就锁住了键。

入队命令无法根据前一条命令的执行结果即时决定后续命令，因为客户端在 `EXEC` 后才拿到这些结果。需要根据读取结果计算新值时，可以使用 WATCH 后先读取，再构建事务。

## 3. WATCH 乐观锁

WATCH 不阻止其他客户端修改键，而是在 `EXEC` 时检查被监视的键是否发生变化。

例如客户端先读取余额，在客户端计算扣款后的值，再提交事务：

```redis
WATCH balance
GET balance
MULTI
SET balance 90
EXEC
```

这里假设 `GET` 返回 `100`，客户端计算扣除 `10` 后得到 `90`。如果从 `WATCH` 到 `EXEC` 之间，被监视的 `balance` 被其他客户端修改，`EXEC` 返回空结果，事务中的 `SET` 根本不会执行。客户端需要重新监视、读取和计算，再尝试提交。

键过期或被内存淘汰也可能使 WATCH 检查失败；从 Redis 6.0.9 起，过期事件会导致事务中止。成功执行 `EXEC`、WATCH 检查导致中止或执行 `DISCARD` 后，监视状态都会被清除。

## 4. 取消与回滚

| 情况 | 行为 |
| --- | --- |
| 执行 `DISCARD` | 丢弃尚未执行的队列，没有事务修改需要撤销。 |
| WATCH 检查失败 | 整批命令不执行，无需回滚。 |
| 入队时报错 | 如命令不存在或参数数量错误，现代 Redis 会标记事务失败，`EXEC` 拒绝执行整个队列。 |
| 执行时报错 | 如对字符串执行列表命令，该命令失败，队列中的其他命令仍会执行，成功的修改不会撤销。 |

例如：

```redis
MULTI
SET value hello
LPUSH value item
SET done yes
EXEC
```

`LPUSH` 因为 `value` 是字符串而返回类型错误，但 `value = hello` 和 `done = yes` 仍然生效。这就是 Redis 事务不支持回滚的含义。

## 5. 持久性边界

事务保证执行期间命令不被其他客户端插入，不代表执行结果一定已经落盘。重启或故障后能否保留数据，仍取决于持久化方式、同步策略及存储状态。
