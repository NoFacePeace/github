# XCLAIM

`XCLAIM` 将消费者组中指定待确认消息的归属转给目标消费者，常用于接管长时间未确认的任务。接管后消息仍处于待确认状态，处理成功后需要执行 `XACK`。

## 1. 基本用法

```redis
XCLAIM orders workers consumer-B 60000 1000-0
```

| 参数 | 含义 |
| --- | --- |
| `orders` | Stream 的 key。 |
| `workers` | 消费者组名称。 |
| `consumer-B` | 接管消息的目标消费者，不存在时会自动创建。 |
| `60000` | 最小空闲时间，单位为毫秒；此处要求消息至少空闲 60 秒。 |
| `1000-0` | 要接管的消息 ID，可以连续指定多个。 |

默认只接管已存在于该组 PEL、满足空闲时间条件且正文仍保留的消息。空闲时间从最近一次投递或接管计算，不代表业务执行耗时。

## 2. 返回结果

默认返回成功接管的消息 ID 和 field-value 内容，形式与 `XRANGE` 返回的消息列表相同。例如：

```text
1) 1) "1000-0"
   2) 1) "order_id"
      2) "1001"
      3) "status"
      4) "created"
```

没有符合条件的消息时返回空列表。一次指定多个 ID 时，只返回成功接管的消息，不为失败项保留空占位。

## 3. 对消费状态的影响

接管成功后，消息归目标消费者负责，并默认重置空闲时间、增加投递次数。消息仍在该组的 PEL 中，Stream 中的正文也仍然保留。

```redis
XACK orders workers 1000-0
```

目标消费者完成业务处理后，通过实际消息 ID 确认。`XCLAIM` 本身不会确认消息，也不会推进组的新消息投递位置。

接管不会停止原消费者的执行。原消费者可能仍在处理同一条消息，因此业务需要保证幂等，空闲阈值也应考虑正常处理耗时。

## 4. 常用选项

| 选项 | 作用 |
| --- | --- |
| `JUSTID` | 只返回成功接管的消息 ID，不返回正文，也不增加投递次数。 |
| `IDLE milliseconds` | 将接管后记录的空闲时间设为指定毫秒数。 |
| `TIME unix-time-milliseconds` | 将记录的最近投递时间设为指定 Unix 毫秒时间。 |
| `RETRYCOUNT count` | 显式设置投递次数。 |
| `FORCE` | 消息正文存在但没有 PEL 记录时，允许创建待确认记录并接管。 |

例如，只获取成功接管的 ID：

```redis
XCLAIM orders workers consumer-B 60000 1000-0 1001-0 JUSTID
```

`FORCE` 不会恢复已删除的消息正文，也不能用来绕过已有待确认记录的最小空闲时间检查。除非需要调整恢复状态，通常使用默认选项即可。

## 5. 与 XAUTOCLAIM 的区别

| 命令 | 选择消息的方式 |
| --- | --- |
| `XCLAIM` | 显式指定要接管的消息 ID，通常先通过 `XPENDING` 查询目标。 |
| `XAUTOCLAIM` | 扫描 PEL，自动查找满足空闲时间条件的消息并接管。 |

`XCLAIM` 从 Redis 5.0 起提供；`XAUTOCLAIM` 从 Redis 6.2 起提供。Redis 7.0 起，`XCLAIM` 处理正文已删除的待确认消息时，会从 PEL 清理相应记录，并且不返回该消息。
