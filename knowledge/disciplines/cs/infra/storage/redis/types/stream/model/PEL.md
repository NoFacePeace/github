# PEL

PEL（Pending Entries List，待确认列表）是 Stream 消费者组维护的状态，记录已投递但尚未确认的消息。

## 1. 归属与内容

每个消费者组有独立的 PEL，组内每个消费者也有自己负责的待确认记录索引。同一条消息可以在一个组中已确认，在另一个组中仍待确认。

待确认记录主要包含：

| 信息 | 含义 |
| --- | --- |
| 消息 ID | 标识待确认的消息。 |
| 所属消费者 | 当前负责处理该消息的消费者。 |
| 最近投递时间 | 用于计算消息的空闲时间。 |
| 投递次数 | 用于追踪重复投递情况。 |

PEL 不重复保存消息正文，正文仍保存在 Stream 的消息记录中。

## 2. 状态变化

默认情况下，`XREADGROUP ... >` 向消费者投递新消息时，会将消息加入该组的 PEL。使用 `NOACK` 选项时不创建待确认记录。

```text
Stream 中保存：A、B、C
        ↓
consumer-A 读取 A、B
        ↓
PEL：A → consumer-A，B → consumer-A
        ↓
处理完 A，执行 XACK
        ↓
PEL：B → consumer-A
Stream 中仍保存：A、B、C
```

组的投递进度和 PEL 是两种不同状态：投递进度决定后续投递哪些新消息，PEL 跟踪已经投递的消息。创建组时通过 `$` 跳过已有消息，不会将这些消息加入 PEL，也不等于对它们执行了确认。

普通读取 `XREAD` 不维护 PEL，也不会改变消费者组的待确认状态。

## 3. 查看与重新读取

```redis
XPENDING orders workers
XPENDING orders workers - + 10
XREADGROUP GROUP workers consumer-A COUNT 10 STREAMS orders 0-0
```

第一条命令查看待确认消息总数、最小和最大 ID 及消费者分布；第二条列出最多 10 条待确认记录，包含所属消费者、空闲毫秒数和投递次数。

`XREADGROUP` 使用 `0-0` 时，读取当前消费者自己名下、ID 大于该位置的待确认消息。它不会读取其他消费者的待确认消息，也不会读取组内尚未投递的新消息。继续分页时传入上次返回的最后一个消息 ID。

## 4. 接管与重试

消费者宕机不会自动移除其待确认记录，也不会自动将消息重新分配给其他消费者。应用需要安排接管和重试。

```redis
XAUTOCLAIM orders workers consumer-B 60000 0-0 COUNT 10
```

该命令从 `0-0` 开始扫描，将空闲至少 60 秒的待确认消息接管给 `consumer-B`，并返回消息内容及后续扫描游标。继续扫描时使用返回的游标；游标为 `0-0` 表示本轮扫描结束。`XAUTOCLAIM` 从 Redis 6.2 起提供，也可以使用 `XCLAIM` 接管指定 ID 的消息。

空闲时间不代表原消费者一定已经停止处理。接管后可能发生重复处理，因此业务需要保证幂等；处理成功后再执行 `XACK`。

## 5. 确认与消息删除

```redis
XACK orders workers 1000-0
```

`XACK` 将指定消息从该组及所属消费者的待确认记录中移除，返回成功移除的记录数。它不删除 Stream 中的消息，也不影响其他组的 PEL。

默认的 `XDEL` 或 `XTRIM` 可以删除尚未确认的消息正文，而留下对应的 PEL 记录。此时，待确认记录存在不代表正文仍可读取。Redis 7.0 起，`XAUTOCLAIM` 扫描到正文已删除的待确认记录时，会清理这些记录并返回其 ID。
