# XPENDING

`XPENDING` 查询 Stream 消费者组的待确认列表（PEL），用于查看哪些消息已投递但尚未确认、由谁负责以及空闲多久。它不返回消息正文，也不确认或接管消息。

## 1. 查询汇总

```redis
XPENDING orders workers
```

返回四项：待确认消息总数、最小消息 ID、最大消息 ID，以及各消费者的待确认数量。例如，redis-cli 中的输出为：

```text
1) (integer) 3
2) "1000-0"
3) "1002-0"
4) 1) 1) "consumer-A"
      2) "2"
   2) 1) "consumer-B"
      2) "1"
```

表示共有 3 条待确认消息，ID 范围为 `1000-0` 至 `1002-0`；其中 `consumer-A` 负责 2 条，`consumer-B` 负责 1 条。

组存在但没有待确认消息时，总数为 `0`，最小 ID、最大 ID 和消费者列表返回空值。Stream 或消费者组不存在时会报错。

## 2. 查询明细

```redis
XPENDING orders workers - + 10
```

`-` 和 `+` 表示整个消息 ID 范围，`10` 表示最多返回 10 条待确认记录。每条记录返回四项：

| 顺序 | 返回内容 | 含义 |
| --- | --- | --- |
| 1 | 消息 ID | 标识待确认的消息。 |
| 2 | 消费者名称 | 当前负责该消息的消费者。 |
| 3 | 空闲毫秒数 | 距离上次投递或接管经过的时间。 |
| 4 | 投递次数 | 该消息的投递计数。 |

例如，返回的一条记录为：

```text
1) 1) "1000-0"
   2) "consumer-A"
   3) (integer) 65000
   4) (integer) 2
```

表示 `1000-0` 归 `consumer-A` 负责，空闲 65 秒，投递计数为 2。空闲时间不等于业务执行时间，也不能证明消费者已经宕机。接管命令可以影响投递计数，因此它也不等于业务处理次数。

没有匹配记录时，明细查询返回空列表。查询本身不会重置消息的空闲时间或增加投递次数。

## 3. 按消费者和空闲时间筛选

```redis
XPENDING orders workers - + 10 consumer-A
XPENDING orders workers IDLE 60000 - + 10
```

第一条只返回 `consumer-A` 的待确认记录；第二条最多返回 10 条空闲至少 60 秒的记录。也可以在第二条命令末尾追加消费者名称，组合筛选。

`IDLE` 筛选从 Redis 6.2 起提供。`COUNT` 对应位置上的数量限制的是返回条数，按空闲时间筛选时，实际扫描的记录可能更多。

## 4. 范围与分页

明细查询默认包含起止 ID。Redis 6.2 起，可以在 ID 前加 `(` 表示排除该边界：

```redis
XPENDING orders workers (1000-0 + 10
```

这会返回 ID 大于 `1000-0` 的待确认记录。分页时，将上页最后一条消息 ID 作为排除式起点，避免重复返回边界记录。

## 5. 后续处理

`XPENDING` 只查看待确认信息。需要重新读取当前消费者自己的待确认消息时，使用 `XREADGROUP` 并传入普通 ID；需要接管其他消费者的消息时，使用 `XCLAIM` 或 `XAUTOCLAIM`；处理成功后使用 `XACK` 确认。

PEL 中存在记录不保证消息正文仍保留：正文可能已被删除或裁剪。
