# Rewrite

AOF 重写根据 Redis 当前的全量数据生成新的基础内容，减少历史写操作积累带来的文件增长。它读取内存中的数据状态，而不是逐条分析旧日志来合并命令。

## 1. 重写的作用

例如对同一个计数器执行一万次递增，旧日志可能保留大量操作；重写只需生成恢复计数器当前值所需的内容。

重写保留当前数据状态，不保留完整操作历史，因此 AOF 不能作为长期历史审计日志。

## 2. 触发条件

| 触发方式 | 条件 |
| --- | --- |
| [自动重写](AutomaticRewrite.md) | AOF 大小同时达到最小阈值和增长比例阈值。 |
| [手动重写](ManualRewrite.md) | 执行 `BGREWRITEAOF` 请求后台重写。 |
| [运行时开启 AOF](EnableAtRuntime.md) | 从关闭切换到开启，生成包含现有数据的基础内容。 |

## 3. 执行过程

以 Redis 7 起的多文件 AOF 为例：

1. 主进程通过 [fork](../../../../../os/process/Fork.md) 创建子进程，子进程根据创建时的数据视图生成新的基础文件。
2. 主进程继续处理请求，将期间的写操作记录到新的增量文件。
3. 基础文件生成成功后，Redis 更新 manifest，使新的基础文件和所需增量文件组成有效的恢复集合，再清理不再需要的旧文件。

基础文件可以采用 AOF 命令格式；开启 `aof-use-rdb-preamble` 时，也可以采用 RDB 格式。Redis 7 之前的单文件 AOF 实现不同。

后台执行仍有资源开销：`fork` 可能短暂阻塞主进程，写时复制可能增加内存占用，生成新文件也需要额外磁盘空间和 I/O。

### 3.1 全量与增量的边界

子进程不需要逐条判断数据是否为新增数据，而是以 `fork` 时刻的数据视图作为全量基础。主进程将这个边界之后的写操作记录到增量日志，包括新增键、修改已有键和删除键。

这依靠操作系统的[写时复制（Copy-on-Write，COW）](../../../../../os/process/CopyOnWrite.md)机制：父子进程最初共享内存页；主进程修改共享页时，操作系统复制相关内存页，使子进程仍能读取修改前的内容。因此，主进程后续的写入不会改变子进程用于生成基础文件的数据视图。

基础文件生成与增量日志写入同时进行，不需要等待基础文件生成完毕才开始记录增量。

### 3.2 计数器示例

假设 `fork` 时 `count = 10`，随后客户端执行 `INCR count`：

| 阶段 | 基础数据或增量操作 |
| --- | --- |
| 子进程生成基础文件 | 保存 `count = 10`。 |
| 主进程处理新请求 | 将 `count` 改为 `11`，并在增量日志中记录相应的递增操作。 |
| 重启恢复 | 先从基础文件加载 `10`，再重放递增操作，得到 `11`。 |

如果期间新增或删除了其他键，也通过增量日志恢复对应变更，而不是要求子进程重新扫描最新数据。

## 4. 查看重写状态

使用以下命令查看持久化状态：

```redis
INFO persistence
```

| 字段 | 含义 |
| --- | --- |
| `aof_rewrite_in_progress` | 是否正在执行 AOF 重写。 |
| `aof_rewrite_scheduled` | 是否已安排稍后执行重写。 |
| `aof_last_bgrewrite_status` | 最近一次后台重写是否成功。 |
| `aof_current_size` | 当前 AOF 大小。 |
| `aof_base_size` | 用于计算自动重写增长比例的基准大小。 |

## 5. 对误删恢复的影响

重写前，如果基础文件和增量日志仍完整保留误删前的数据，可以在文件副本上将日志截断到误删操作之前进行恢复，但会丢失截断点之后的操作，需要准确定位命令边界。

误删后重写生成的基础内容反映删除后的状态，被删内容可能已不在当前有效的 AOF 文件集合中。需要恢复历史数据时，应依靠提前保留的备份。
