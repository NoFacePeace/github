# Sentinel

Sentinel（哨兵）监控 Redis 主从节点，在满足故障判定和选举条件时协调自动切换，并为客户端提供当前主节点的地址。Sentinel 本身不保存业务数据，也不为业务请求代理转发。

## 1. 部署关系

一组主节点与副本通过[主从复制](Replication.md)同步数据，多个 Sentinel 监控这组节点。各副本保存完整数据集，Sentinel 不负责分片。

生产部署通常至少使用三个 Sentinel，并放在不同故障域。一个 Sentinel 可以监控多组主从，每组使用不同的主节点名称。

## 2. 故障判断与切换

1. Sentinel 定期检查主节点、副本和其他 Sentinel 的状态。
2. 单个 Sentinel 在规定时间内无法获得有效响应时，将节点标记为主观下线。
3. 对主节点，达到配置的 quorum 数量的 Sentinel 同意其不可用后，可判定为客观下线。
4. Sentinel 还需要获得多数 Sentinel 的授权，选出本次负责故障切换的 Sentinel。
5. 执行切换的 Sentinel 选择合适副本并将其提升为主节点，再调整其他副本的复制目标；旧主节点恢复并重新纳管后，也会被配置为副本。

选出负责切换的 Sentinel 与选出新的 Redis 主节点是两个步骤。quorum 是故障判定门槛，不等于绕过多数授权；只有少数 Sentinel 可达时，通常不能完成自动切换。

## 3. 配置示例

以下仅展示监控相关配置，实际部署还需要配置网络可达性、认证和文件写权限等：

```conf
sentinel monitor mymaster 10.0.0.10 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1
```

`mymaster` 是这组主从的名称，`2` 是 quorum。Sentinel 会发现副本和其他 Sentinel，并维护拓扑信息；它使用的配置文件需要可写，以保存状态变化。

## 4. 客户端访问

客户端应使用支持 Sentinel 的连接方式，配置多个 Sentinel 地址和主节点名称，而不是永久固定某个 Redis 主节点地址。

可以向 Sentinel 查询当前主节点：

```redis
SENTINEL get-master-addr-by-name mymaster
```

客户端根据返回地址连接 Redis 进行业务读写。故障切换后，需要重新发现并连接新主节点；Sentinel 不会替客户端转发数据请求。连接中断可能使请求结果不确定，业务重试需要考虑幂等性。

## 5. 可用性与一致性边界

Sentinel 提供自动切换，不会将异步复制改为强一致性。晋升的副本可能缺少最近写入，故障切换仍可能丢失已确认数据。

网络分区期间，旧主节点可能继续接受部分客户端的写入；Sentinel 本身不保证立即阻止所有客户端访问旧主节点。需要结合客户端发现、写入限制和业务侧条件更新等机制控制风险。

### 5.1 脑裂的含义

脑裂（Split-Brain）是指系统因网络分区等原因形成多个主节点，并同时接受本应由唯一主节点处理的操作。这里指同一组主从出现新旧两个可写主节点，而不是数据分片后各自负责不同数据的多个主节点。

例如原主节点为 A，副本为 B：

1. A 与多数 Sentinel、B 之间的网络中断，但部分客户端仍能连接 A。
2. 多数 Sentinel 确认 A 不可用，并在满足选举条件后将 B 提升为新主节点。
3. 部分客户端继续写 A，其他客户端通过 Sentinel 发现 B 并写 B，两边数据开始分叉。
4. 网络恢复后，A 被重新配置为 B 的副本，以 B 的数据为准重新同步；A 在隔离期间接受的独有写入可能被丢弃，不会自动合并到 B。

```text
部分客户端 → A（旧主，继续接受写入）
              × 网络分区
其他客户端 → B（晋升后的新主，也接受写入）
```

Sentinel 的多数授权用于协调故障切换，但不能立即关闭或隔离仍在运行的旧主节点，所以选举成功本身不等于已经阻止双主写入。

### 5.2 缓解措施与限制

可以在 Redis 数据节点配置写入限制，例如：

```conf
min-replicas-to-write 1
min-replicas-max-lag 10
```

该示例要求主节点至少有一个复制确认延迟在 10 秒以内的健康副本，否则拒绝写入。复制确认延迟用于判断副本健康，不代表每条写入都已得到副本确认或落盘。

旧主失去健康副本后，可以通过上述限制减少继续接受写入的时间，但仍存在检测窗口；如果旧主所在分区仍有足够的健康副本，也可能继续写入。这些配置不是完整的防脑裂保证。

写入限制也会影响可用性。例如一主一副本部署中，副本晋升后如果没有其他健康副本，新的主节点也会因上述配置拒绝写入，需要结合拓扑与故障容忍目标权衡。

客户端应通过 Sentinel 发现并重连当前主节点，避免固定访问旧主。关键业务还应结合唯一约束、条件更新或资源端验证的 fencing token 等机制，限制旧持有者和重复请求的影响；Sentinel 本身不提供业务所需的 fencing token。

这些措施可以降低风险，但不能将 Sentinel 与异步复制组合变为强一致性系统。

## 6. 与 Redis Cluster 的区别

Sentinel 通常管理不分片的一组主从，重点是监控、自动切换与主节点发现。Redis Cluster 则将数据分片到多个主节点，并自行协调副本切换，通常不再搭配 Sentinel 管理其选主。
