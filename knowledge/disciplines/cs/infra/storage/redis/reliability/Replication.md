# Replication

主从复制让副本跟随主节点的数据变更，为故障恢复提供数据副本，也可以分担读请求。普通的一组主从不进行数据分片，主节点保存完整数据集，各副本保存其副本。

## 1. 节点职责

| 节点 | 主要职责 |
| --- | --- |
| 主节点 | 接收业务写入，将数据变更传播给副本，也可处理读取。 |
| 副本 | 同步主节点的数据，默认只读，可处理允许一定陈旧度的读取。 |

单靠主从复制不会在主节点故障后自动选出新主节点；需要人工切换，或配合 [Sentinel](Sentinel.md) 等机制。

## 2. 配置与状态

副本可以在配置文件中指定上游主节点：

```conf
replicaof 10.0.0.10 6379
```

也可以通过 `REPLICAOF host port` 动态调整复制关系。将已有实例配置为副本可能使其原有数据被上游数据替换，实际操作前应确认数据用途与备份。

使用以下命令检查节点角色、复制连接及偏移量等状态：

```redis
INFO replication
ROLE
```

## 3. 同步方式

### 3.1 全量同步

首次连接或无法补齐缺失变更时，副本需要全量同步。主节点通常生成 RDB 数据并传给副本，副本加载基础数据，再接收生成和传输期间的增量变更。

RDB 数据可以经磁盘文件或无盘复制等路径传输，不一定依赖事先生成的独立 `dump.rdb`。复制所需的 RDB 数据传输与定期 RDB 备份不是同一个用途。

### 3.2 部分同步

短暂断连后，如果复制标识、偏移量和主节点的复制积压缓冲区允许补齐缺失数据，可以通过 `PSYNC` 进行部分同步，避免重新传输完整数据集。

积压缓冲区容量有限，断连时间过长或变更量过大可能导致所需历史数据已被覆盖，只能重新全量同步。

## 4. 一致性与数据丢失

复制通常是异步的。主节点向客户端确认写入时，副本可能尚未收到或应用这次变更，因此：

- 从副本读取可能得到旧值，尤其需要注意写入后立即读副本的场景。
- 主节点故障后，如果晋升的副本缺少最近写入，这些已确认写入仍可能丢失。
- 网络分区期间，客户端可能仍访问旧主节点，其接受的写入在重新加入复制拓扑后可能被覆盖。

`WAIT` 可以等待副本确认当前连接此前的写入，降低复制尚未完成就故障的风险，但不等于副本已落盘，也不提供强一致性保证。`min-replicas-to-write` 和 `min-replicas-max-lag` 可以在副本数量或连接健康不足时限制主节点写入，但不能代替逐次写入的同步提交。

## 5. 与持久化和备份的关系

复制、持久化和备份解决不同问题：复制提供副本，持久化支持重启恢复，备份保留历史数据。

误删除和错误更新也会复制到副本，所以副本不是历史备份。还需要评估主节点丢失数据后自动以空数据重启的风险，避免空数据继续同步到副本。
