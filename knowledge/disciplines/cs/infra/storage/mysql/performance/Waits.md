# MySQL 等待排查

等待慢是数据库访问流程在连接、锁、资源或结果传输等环节暂时无法推进。连接池排队发生在应用端，其他等待可能发生在数据库内部或网络交互中，应先确定耗时位置。

## 1. 常见场景与处理

| 场景 | 典型原因 | 排查与解决方向 |
| --- | --- | --- |
| 连接池等待 | 连接泄漏、长事务、并发突增。 | 检查等待时长、连接持有时间和活跃数；修复泄漏、缩短事务，按数据库承载能力控制并发。 |
| 建立连接慢 | DNS、网络、TLS 或认证耗时。 | 单独记录建连耗时，检查网络路径和认证过程，合理复用连接。 |
| 记录或范围锁等待 | 其他事务持有不兼容的锁，或间隙保护阻塞插入。 | 沿等待关系找到阻塞源，缩短事务，优化定位索引并统一访问顺序。 |
| 元数据锁等待 | DDL 与未结束事务互相阻塞。 | 检查持有者和排队 DDL，处理长事务并调整 DDL 时机。 |
| 表锁、自增锁等待 | 显式表锁或特定自增值分配方式。 | 检查锁模式、语句类型和自增锁配置；依据业务与复制要求调整策略。 |
| 数据 I/O 等待 | 缓存未命中、扫描量大或磁盘繁忙。 | 检查 Buffer Pool、访问数据量和磁盘延迟，先减少无效读取，再评估容量。 |
| 提交等待 | redo、binlog 刷盘慢，或半同步复制等待确认。 | 单独观察 COMMIT，检查日志 I/O 和复制；调整持久性配置前明确其可靠性取舍。 |
| 内部同步等待 | 热点页或内部 mutex、rwlock 竞争。 | 结合 Performance Schema 等待统计定位热点，降低无效并发或分散热点。 |
| CPU 调度等待 | CPU 饱和，线程难以获得运行机会。 | 检查运行队列和主要 CPU 消耗，优化热点 SQL、控制并发或扩容。 |
| 网络、客户端读取等待 | 返回量大、网络慢、应用消费结果慢。 | 减少列和行数，采用有边界的分批或流式读取，检查客户端处理速度。 |

扩大连接池可能把应用排队转移成数据库争用，并非通用解决方法。等待事件的累计时间也可能包含正常空闲等待，需要结合业务延迟、发生频率和阻塞链判断。

## 2. 检查锁等待

MySQL 8.0 可使用以下信息，结果受权限和采集配置影响：

```sql
-- 当前会话。
SHOW FULL PROCESSLIST;

-- InnoDB 数据锁等待关系。
SELECT * FROM performance_schema.data_lock_waits;
SELECT * FROM performance_schema.data_locks;

-- 当前事务；Sleep 会话也可能有未结束事务。
SELECT trx_id, trx_state, trx_started,
       trx_mysql_thread_id, trx_query
FROM information_schema.innodb_trx;

-- 元数据锁；OWNER_THREAD_ID 对应 Performance Schema 线程标识。
SELECT OBJECT_SCHEMA, OBJECT_NAME, LOCK_TYPE,
       LOCK_STATUS, OWNER_THREAD_ID
FROM performance_schema.metadata_locks;
```

沿等待关系找到最上游阻塞者，确认其事务范围和业务用途。终止语句不一定结束整个事务；终止连接会触发事务回滚，回滚也可能耗时，处理前应评估业务影响。

## 3. 区分等待与死锁

等待不一定形成环，也不一定报错。循环等待构成死锁时，默认检测机制会选择一个事务回滚；超过等待时间则可能返回锁等待超时，回滚范围与死锁不同。

具体案例和程序处理见[死锁](../innodb/locks/Deadlock.md)。普通一致性 SELECT 通常不等待已有记录 X 锁，但仍可能等待 MDL、I/O 或其他资源。

## 4. 检查资源等待

将数据库等待事件与同一时段的 CPU、磁盘延迟、队列、内存和网络指标对齐。Performance Schema 的事件采集依赖 instruments、consumers 等配置，统计还可能是累计值，应比较观察窗口内的变化。

如果大量扫描或回表导致 I/O 增加，应继续进行[执行排查](Execution.md)，不能只通过加内存或换磁盘处理。
