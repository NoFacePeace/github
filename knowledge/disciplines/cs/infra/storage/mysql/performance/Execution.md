# MySQL 执行排查

执行慢通常来自处理数据太多、处理次数太多，或单条记录计算成本过高。应根据实际执行统计找到主要工作量，而不是仅凭 SQL 长短或是否使用索引判断。

## 1. 常见场景与处理

| 场景 | 主要成本 | 处理方向 |
| --- | --- | --- |
| 全表或大范围扫描 | 读取、检查大量记录。 | 缩小业务范围，评估定位索引。 |
| 索引定位能力不足 | 找到大量候选记录后继续过滤。 | 优化联合索引与条件写法，检查类型转换。 |
| 大量回表 | 通过二级索引反复访问聚簇索引。 | 先减少候选记录，再评估少量覆盖列。 |
| 大量排序 | 排序输入多，可能伴随落盘。 | 减少输入，评估支持过滤与排序的索引。 |
| 大范围聚合或去重 | COUNT、SUM、GROUP BY、DISTINCT 处理大量数据。 | 提前过滤，评估索引、预聚合、汇总表或缓存。 |
| 关联中间结果膨胀 | 一对多、多对多连接产生大量组合。 | 检查连接条件、连接键索引，必要时先聚合。 |
| 内层重复执行 | 嵌套循环或相关子查询反复访问数据。 | 检查循环次数和每次成本，优化查找或改写 SQL。 |
| 深分页 | 扫描并跳过大量 OFFSET 之前的记录。 | 使用稳定排序键的游标分页。 |
| 复杂表达式计算 | 大量字符串、JSON、正则或函数运算。 | 先过滤，必要时预计算或使用生成列。 |
| 计划不合适 | 行数估计偏差导致高成本访问路径。 | 检查数据分布、统计信息和已有索引，比较实际计划。 |
| 大量写入 | 修改记录、维护索引、约束或触发器。 | 合理分批、缩短事务，评估冗余索引与触发器。 |

一次请求发出大量 SQL 的 N+1 问题，还会叠加网络往返。应同时看单条 SQL 与请求总调用次数，必要时改成批量查询。

## 2. 查看计划与实际工作量

```sql
EXPLAIN
SELECT id, name FROM users WHERE age >= 18;

-- MySQL 8.0.18 起支持；会实际执行查询。
EXPLAIN ANALYZE
SELECT id, name FROM users WHERE age >= 18;
```

示例假设 users 表包含 id、name、age 列。执行前需评估成本，不能把 EXPLAIN ANALYZE 当作只读计划展示工具。

重点比较访问索引、估计与实际行数、过滤位置、循环次数，以及排序和聚合的输入量。多次循环时需结合输出口径理解每次与累计工作量；父子节点耗时存在包含关系，不能简单相加。

## 3. 扫描很多、返回很少

这通常意味着大量记录读取后被过滤或跳过，是检查[索引优化](IndexOptimization.md)的常见起点。但也可能是合理的大范围统计，或无法避免的过滤，不能只看两者比例就决定新增索引。

普通 EXPLAIN 中的 rows 是估计值。COUNT(*) 即使只返回一行，也可能需要处理大量可见记录，这与查询一条业务记录的工作量不同。

## 4. 计划变化与统计信息

相同 SQL 突然变慢时，检查参数、数据倾斜、统计信息和索引变化。统计信息不准确时，可以评估 ANALYZE TABLE；用法与限制见 [ANALYZE](../sql/ANALYZE.md)。

更新统计信息不保证变快，也可能改变其他查询的计划。应记录并比较前后结果，避免把强制某个索引当作长期通用方案。

## 5. 验证边界

优化后既检查代表性慢参数，也检查常见参数，防止只改善一个样例却拖慢其他请求。缓存冷热、并发、返回量和数据规模应具有可比性。

减少扫描往往能同时降低 CPU、I/O 和锁争用，但性能瓶颈也可能转移。若实际工作量不大仍耗时高，应回到[等待排查](Waits.md)。
