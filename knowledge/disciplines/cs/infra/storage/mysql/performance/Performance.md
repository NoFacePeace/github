# MySQL 性能排查与优化

数据库访问慢，可以先按等待与执行两个方向排查：等待是操作暂时无法推进，执行是扫描、关联、排序和计算等工作本身消耗时间。这是排查角度，不是互斥分类；一次查询通常会交替执行和等待。

## 1. 排查入口

| 方向 | 典型问题 | 文档 |
| --- | --- | --- |
| 等待慢 | 等连接、锁、I/O、提交或客户端读取。 | [等待排查](Waits.md) |
| 执行慢 | 扫描过多、大量回表、排序、关联或重复计算。 | [执行排查](Execution.md) |
| 索引优化 | 改善定位、排序与覆盖能力，控制写入维护成本。 | [索引优化](IndexOptimization.md) |

例如扫描过多既增加 CPU 工作，也可能增加数据页读取的 I/O 等待。不能只因为看到 I/O 等待就排除索引和 SQL 问题。

## 2. 收集问题信息

先记录具体 SQL、参数、发生时间、耗时、调用频率和返回量，区分偶发或持续、单条或整体变慢。相同 SQL 的不同参数可能对应完全不同的数据量与计划表现。

同时检查近期发布、数据增长、批处理、DDL、索引及配置变更，并记录数据库版本、表结构和已有索引。

应用端应尽量分别测量连接池排队、建立连接、SQL 执行、结果拉取和程序处理时间。驱动是否缓冲结果会影响这些阶段的测量边界，不能直接把接口总耗时当作数据库执行时间。

## 3. 定位当前与历史慢请求

```sql
SHOW FULL PROCESSLIST;
```

当前会话状态可以提供锁等待、长查询等线索，但只是一个瞬时快照。Sleep 会话也可能存在未结束事务并持锁。

已结束的慢 SQL 应结合慢查询日志、Performance Schema 的语句统计与历史事件排查。相关采集是否开启、历史保留范围和访问权限需要先确认。

## 4. 分析执行计划

使用 EXPLAIN 检查访问索引、估计行数、连接顺序和排序等操作。需要实际行数与循环次数时，可结合版本使用 EXPLAIN ANALYZE，具体用法见 [EXPLAIN](../sql/EXPLAIN.md)。

EXPLAIN ANALYZE 会实际执行目标查询，应先评估其资源成本。估计行数不等于实际扫描量，实际节点耗时也可能包含等待，不能将其全部解释为 CPU 计算时间。

## 5. 验证改动

优化前后应使用有代表性的参数和数据规模，对比延迟、吞吐、实际处理行数、资源消耗及锁等待。还需检查写入和其他查询是否受影响。

优先验证与证据对应的改动，避免同时调整多个不相关因素。不要仅凭使用了索引、消除了某个 Extra 标记或单次缓存命中后的耗时就判断优化成功。
