# MySQL 索引优化

索引优化通过改善定位、排序和覆盖能力减少读取工作，也通过控制索引数量降低写入维护成本。既适用于 SELECT，也影响 UPDATE、DELETE 的定位及锁范围，以及 INSERT 等操作的写入成本。

## 1. 什么时候需要优化

当性能达不到业务要求，且证据表明主要开销与索引访问有关时，再考虑调整索引。常见信号包括扫描量大而返回少、频繁回表、排序大量数据后只取少量、修改操作扫描并锁住大量记录，或索引过多导致写入成本高。

小表全表扫描、需要读取大部分数据或已经足够快的查询，不一定需要增加索引。连接池、网络和与访问路径无关的锁等待，通常需要其他手段处理。

## 2. 常见问题与处理

| 问题 | 优化方向 |
| --- | --- |
| 多个条件过滤，但索引只定位一个宽泛条件 | 评估联合索引，让适合的条件参与索引定位。 |
| 条件精确却扫描大表 | 检查已有索引、最左前缀、表达式和转换，并确认扫描是否确实成本更低。 |
| 大量回表 | 先减少候选记录；必要时增加少量列形成覆盖索引。 |
| 过滤后仍排序大量数据 | 根据等值条件与 ORDER BY 设计索引。 |
| 对列调用函数 | 在语义一致时改写为可定位的范围条件，或评估支持的函数索引、生成列。 |
| 参数、连接列类型或字符集不匹配 | 对齐定义与参数类型，检查执行计划确认转换的影响。 |
| LIKE '%keyword%' | 普通 B+ 树通常难以定位，评估全文索引或其他检索方案及其语义。 |
| 索引过多 | 评估重复、被覆盖或长期低使用的索引，合并或删除冗余项。 |

## 3. 联合索引示例

假设 orders 包含主键 id，以及 user_id、status、created_at、amount 列：

```sql
SELECT id, amount
FROM orders
WHERE user_id = 100 AND status = 1
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

如果只有 user_id 索引，可能先读取该用户的大量订单，再过滤 status 并排序。可评估以下联合索引：

```sql
CREATE INDEX idx_orders_user_status_created_id
ON orders (user_id, status, created_at, id);
```

它有机会先按 user_id、status 定位，再沿索引倒序读取，取得足够结果后停止。仍需结合已有索引、实际计划及数据分布验证，不应直接重复创建。

如果只需回表读取约 20 条记录，通常不必为了完全覆盖再加入 amount。InnoDB 二级索引本身包含主键，是否需要显式声明 id 还应结合索引定义、排序方向及优化器对扩展索引的利用判断。

## 4. 列顺序与取舍

可以从“等值条件 → 范围或排序需求 → 必要覆盖列”开始设计，但这只是起点。范围过滤与排序可能无法同时最佳满足，需要结合选择性、LIMIT 和其他查询的复用需求取舍。

“选择性最高的列必须在第一位”不是通用规则；多个等值列的顺序还会影响前缀复用。范围条件之后的列也并非完全无用，可能用于索引条件下推、覆盖或特定排序，不能笼统说后面的列全部失效。

## 5. 条件改写

假设 created_at 为 DATETIME，查询某个自然日可以由函数过滤改写为半开区间：

```sql
-- 普通 created_at 索引通常难以直接定位这个函数条件。
WHERE DATE(created_at) = '2026-10-16'

-- 可评估的范围写法。
WHERE created_at >= '2026-10-16 00:00:00'
  AND created_at <  '2026-10-17 00:00:00'
```

改写必须保持时区、字段类型和业务日期语义一致。索引是否有收益还取决于范围内的数据占比；读取绝大多数记录时，全表扫描可能更合适。

## 6. 写入成本与验证

新增索引会增加存储、缓存占用和写入维护成本；建索引本身也消耗资源，并可能涉及元数据锁等等待。删除索引前应确认唯一约束、外键和关键查询依赖，观察窗口需覆盖周期性任务。

通过 EXPLAIN 及适用时的 EXPLAIN ANALYZE 比较实际处理行数、排序、回表相关成本与延迟，并评估写入和其他查询的变化。只看到 key 非空，或消除 Using filesort，并不足以证明性能改善。
