# InnoDB 事务

InnoDB 通过撤销日志、重做日志、锁与多版本机制共同提供事务能力。SQL 事务控制由 MySQL Server 接收和协调，具体数据修改、并发控制及引擎恢复由 InnoDB 完成。

## 1. ACID 的实现分工

| 性质 | InnoDB 的主要相关机制 |
| --- | --- |
| 原子性 | undo 与回滚机制撤销事务修改；故障恢复时还需要 redo 和事务状态协作。 |
| 一致性 | 正确的业务逻辑、约束及原子性、隔离性等共同维护规则，不由某一种日志单独保证。 |
| 隔离性 | 锁、MVCC 与隔离级别规则协调可见性及冲突。 |
| 持久性 | redo、预写日志和提交刷盘策略，结合可靠的操作系统与存储设备。 |

## 2. 修改与提交过程

事务修改记录时，InnoDB 按需获取相应锁，保存 undo 信息，并更新 Buffer Pool 中的页；相关数据页与 undo 页的修改产生 redo。

```text
开始事务
    ↓
获取必要的锁、记录撤销信息并修改内存页
    ↓
提交：按配置持久化相关日志并确认事务结果
或回滚：利用 undo 撤销修改
```

这是逻辑流程，不表示实际代码只有一次日志写入或一次加锁。多条语句、索引维护和约束检查会交织执行。

未提交修改也可能存在于数据页中，甚至按预写日志规则刷到磁盘。提交不是第一次修改数据页，而是确认事务结果的边界。

## 3. 回滚与历史版本

[undo log](../logs/UndoLog.md) 保存撤销修改及重建旧版本所需的信息，不是每次保存完整旧行快照。

事务回滚会撤销修改；其他事务的一致性读则可以借助 undo 重建可见旧版本供读取，不会因此把页里的新值改回去。undo 页的修改也受 redo 保护，以便故障后恢复必要的撤销信息。

## 4. 锁与隔离

- [Read View](ReadView.md)：一致性读的视图建立时机、版本可见性与历史版本读取。

InnoDB 默认隔离级别是[可重复读（REPEATABLE READ）](../../../../../runtime/transactions/RepeatableRead.md)，实例或会话配置可以修改该默认行为。

[锁](../locks/Locks.md)负责协调冲突访问，普通一致性读通过 MVCC 选择可见版本。READ COMMITTED 通常按语句建立新的读取视图，REPEATABLE READ 下普通一致性读通常复用事务内首次一致性读建立的视图。

读取视图的建立时机还受语句和选项影响。锁定读、UPDATE、DELETE 等操作不能直接套用普通一致性读的快照规则；写冲突也不能仅靠 MVCC 解决。

锁定范围取决于实际索引访问、条件及隔离级别，不一定等于最终返回的记录集合。长事务可能延长持锁时间或阻碍历史版本清理。

## 5. 持久化与崩溃恢复

[redo log](../logs/RedoLog.md) 按预写日志规则先于相关数据页持久化。事务提交不要求立即写回全部脏页，崩溃后可以重做必要修改，再根据事务状态处理未完成事务。

innodb_flush_log_at_trx_commit 为 1 时，提交要求持久化相关 redo，实际 I/O 可以通过组提交合并。其他取值可能在部分故障场景丢失已提交结果。

启用 binlog 时，Server 与 InnoDB 通过[内部两阶段提交](TwoPhaseCommit.md)协调结果；通常还需结合 sync_binlog 为 1 及可靠存储，保障 binlog 的持久化。恢复时需判定处于准备阶段事务的最终结果，不能将所有崩溃时尚未完成提交流程的事务一律回滚。

## 6. 业务用法与边界

```sql
-- 假设 accounts 使用 InnoDB，相关业务条件已经正确检查。
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

应用必须检查语句结果，并在必要时执行 ROLLBACK。普通语句错误不一定中止整个事务，死锁和锁等待超时的处理也可能不同。

多数 DDL 等语句可能导致隐式提交，非事务表修改及外部副作用不受 InnoDB 回滚统一保护。提交期间连接中断时，客户端还可能不知道最终结果，应通过业务标识、结果查询及幂等机制处理。
