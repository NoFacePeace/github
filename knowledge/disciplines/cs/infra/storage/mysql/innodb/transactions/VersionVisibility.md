# InnoDB 版本可见性

版本可见性判断决定某条记录的某个版本能否被当前一致性读看到。InnoDB 将版本的 DB_TRX_ID 与 Read View 的创建者、事务 ID 边界及活跃事务集合比较，不是简单选择数值最大的事务 ID。

## 1. 字段与版本范围

下文采用 MySQL 5.7、8.0 系列 ReadView 类中常见的字段名称说明概念，不对应某个小版本的逐行源码。具体定义与算法应以目标版本为准，类定义通常位于 storage/innobase/include/read0types.h。

| 字段 | 主要含义 |
| --- | --- |
| [m_creator_trx_id](m_creator_trx_id.md) | 创建视图的事务标识，用于识别自身修改；事务 ID 分配存在实现细节。 |
| [m_ids](m_ids.md) | 创建视图时活跃的其他读写事务 ID 集合。 |
| [m_up_limit_id](m_up_limit_id.md) | 较小的可见性边界，通常是活跃集合中最小 ID；集合为空时使用相应上边界。 |
| [m_low_limit_id](m_low_limit_id.md) | 较大的不可见性边界，代表创建视图时事务 ID 分配的边界。 |

虽然名称包含 up 与 low，数值关系却是 m_up_limit_id 不大于 m_low_limit_id。比前者小的版本可见，大于等于后者的其他事务版本不可见。

较早版本可能采用 read_view_t 及不同成员名称，不能将这些字段名视为所有版本的固定接口。

## 2. 简化判断流程

对于普通持久化记录，可以将版本事务 ID trx_id 的判断简化为：

```text
trx_id 属于当前事务？
  是 → 通常可见
  否 ↓
trx_id < m_up_limit_id？
  是 → 可见
  否 ↓
trx_id >= m_low_limit_id？
  是 → 不可见
  否 ↓
trx_id 在 m_ids 中？
  是 → 不可见：创建视图时仍活跃
  否 → 可见：创建视图时已提交
```

这是普通版本可见性规则的概括，不覆盖所有内部特殊记录和恢复路径。事务自己的修改通常可见，也不表示事务内每条记录都只来自同一个历史时刻。

## 3. 数值示例

假设创建视图时，其他活跃读写事务集合为 `{100, 102}`，m_up_limit_id 为 100，m_low_limit_id 为 105：

| 版本的事务 ID | 是否可见 | 原因 |
| --- | --- | --- |
| 99 | 可见 | 小于较小边界。 |
| 100、102 | 不可见 | 在视图创建时仍活跃。 |
| 101、103、104 | 可见 | 位于边界之间，但不在活跃集合。 |
| 105 及之后 | 不可见 | 达到或超过视图创建时的分配边界。 |

这里排除创建者自身的特殊情况。某个事务若在视图创建时活跃，即使它在查询过程中提交，对原视图而言仍不可见；不能途中更新 m_ids 来改变这次读取的快照。

## 4. 不可见时如何读取

当前版本不可见时，InnoDB 根据 DB_ROLL_PTR 与 undo 信息重建更早版本，再对该版本的事务信息进行判断。

```text
当前版本 → 不可见
    ↓ undo 重建
上一版本 → 不可见
    ↓ undo 重建
更早版本 → 可见，检查记录状态后返回
```

若没有可见版本，该行对本次读取可以视为不存在；若可见版本带有删除标记，也不会作为普通结果行返回。历史重建不会把数据页里的当前值改回去。

## 5. 与读取方式的关系

READ COMMITTED 的普通一致性读通常每次建立新视图，REPEATABLE READ 通常在首次一致性读建立后复用。因此，同一已提交修改对不同视图的可见性可以不同。

FOR UPDATE、FOR SHARE 等锁定读和修改操作采用相应的当前记录访问及锁定规则，不能直接套用上述旧视图读取流程。

二级索引记录不直接保存聚簇记录中的整套事务字段，其可见性处理还可能借助页级信息并访问聚簇索引。不能对所有索引记录都直接假设存在可供比较的 DB_TRX_ID。
