# InnoDB 内部两阶段提交

启用 [binlog](../../logs/Binlog.md) 时，MySQL 通过内部两阶段提交（Two-Phase Commit，2PC）协调 InnoDB 事务与 binlog 的提交结果。它是事务提交过程的一部分，不是事务已经提交成功后再执行的额外流程。

## 1. 作用与参与方

redo 用于 InnoDB 崩溃恢复，binlog 用于复制和基于备份的时间点恢复。两者内容不同，需要协调的是同一事务是否提交，而不是让日志内容完全相同。

如果独立提交，崩溃可能导致 InnoDB 已提交但 binlog 缺少事务，或 binlog 已记录事务而 InnoDB 最终回滚，造成数据与复制、恢复结果不一致。

| 角色 | 职责 |
| --- | --- |
| 客户端 | 显式执行 COMMIT；自动提交时由 Server 发起相应过程。 |
| MySQL Server 事务协调器 | 协调引擎准备、binlog 写入和同步，以及引擎最终提交。 |
| InnoDB | 准备事务，保存可恢复的修改与事务状态，并根据最终决策提交或回滚。 |

这里讨论普通 InnoDB 事务与 binlog 的内部协调，不等同于业务跨多个数据库使用的外部 XA 事务。

## 2. Prepare 准备什么

Prepare 将 InnoDB 事务置于“已准备、尚未最终提交”的中间状态。相关修改及准备状态可以通过日志恢复，事务因而能够在崩溃后继续接受提交或回滚决策。

准备不是首次修改数据。执行 DML 时，InnoDB 已修改 Buffer Pool 中的页、保存 undo，并产生 redo；prepare 进一步记录事务的准备状态，相关锁仍持有，尚未完成最终提交。

## 3. 提交步骤

以下以启用 binlog、innodb_flush_log_at_trx_commit = 1、sync_binlog = 1 为前提，假设底层存储正确兑现同步写入请求：

| 步骤 | 执行方 | 行为 |
| --- | --- | --- |
| 执行 DML | InnoDB 与 Server | InnoDB 修改内存页并产生 undo、redo；Server 收集事务的 binlog 事件。 |
| 发起提交 | 客户端或 Server | 显式 COMMIT 或自动提交触发事务提交。 |
| 第一阶段：Prepare | InnoDB，由 Server 协调 | 进入准备状态；在提交协调中确保恢复所需的 redo 及准备状态持久化。 |
| 持久化提交决策 | Server | 将事务事件及提交标识写入 binlog，并同步刷盘。 |
| 第二阶段：Commit | InnoDB | 根据协调器决定完成引擎提交，处理事务状态并释放相关事务锁。 |
| 返回结果 | Server | 正常流程完成后向客户端返回成功。 |

```text
修改数据，产生 redo，收集 binlog 事件
                   ↓
             发起 COMMIT
                   ↓
       InnoDB prepare，所需 redo 持久化
                   ↓
       完整事务 binlog 写入并持久化
                   ↓
             InnoDB commit
                   ↓
              返回成功
```

这是逻辑依赖关系，不是逐行对应内部函数的固定执行顺序。[组提交](../../server/GroupCommit.md)会批量完成日志写入和同步；不能理解成每个事务在 prepare、commit 时都各做一次独立刷盘。

## 4. 崩溃恢复如何决定

在上述持久性前提下，可以按恢复到的事务状态理解：

| 崩溃恢复时的情况 | 决策 |
| --- | --- |
| InnoDB 尚未准备，也未提交 | 作为未提交事务处理，撤销其修改。 |
| InnoDB 已 prepare，binlog 无对应的完整事务提交记录 | 回滚。 |
| InnoDB 已 prepare，binlog 有对应的完整事务提交记录 | 完成提交，即使崩溃前尚未执行完引擎 commit。 |
| InnoDB 已确定提交 | 按已提交事务恢复。 |

协调器通过事务标识等关联信息匹配准备事务与 binlog 提交记录。不是只要 binlog 文件存在、包含部分行事件，或执行过一次 write，就认定事务已提交。

数据修改仍由 redo、undo 等引擎恢复机制处理；binlog 在这里为处于准备状态的事务提供提交决策依据。不能把恢复理解为直接重放 binlog 来替代 InnoDB 崩溃恢复。

## 5. binlog 持久化是否等于完成

当 InnoDB 已持久准备，且 binlog 中该事务的完整提交记录已持久化，提交决定已经确定。此时即使崩溃，也可以在恢复时完成 InnoDB commit。

但正常执行中，引擎仍需完成提交和释放锁，Server 才返回成功。因此应区分“提交决定已持久化”与“提交收尾及客户端确认已经完成”。

如果崩溃或断连发生在客户端收到成功前，客户端可能无法确认结果，而恢复后的事务实际已经提交。应用应通过业务唯一标识、结果查询及幂等机制处理，不能盲目重试造成重复业务操作。

## 6. 写入与刷盘配置

写入内存日志缓冲区、写到操作系统缓存与持久化到存储设备是不同层次。两阶段提交负责协调，持久性还取决于配置及底层存储。

| 配置 | 值为 1 时的主要保障 |
| --- | --- |
| innodb_flush_log_at_trx_commit | 提交要求相关 redo 写入并持久化，实际同步可以合并。 |
| sync_binlog | 每个 binlog 提交组要求同步 binlog。 |

现代 MySQL 中两者通常默认均为 1，但实例配置可能覆盖默认值，可以查看：

```sql
SELECT @@GLOBAL.innodb_flush_log_at_trx_commit,
       @@GLOBAL.sync_binlog;
```

放宽配置后，不同故障类型下可能丢失已经返回成功的事务，或影响日志间的一致性，不能直接套用强持久性前提下的全部结论。

事务提交不要求同时把全部脏数据页写回数据文件。数据页可后续按预写日志规则刷盘，不能将“数据页尚未落盘”与“事务尚未持久提交”混为一谈。
