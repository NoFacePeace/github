# InnoDB Read View

Read View 是 InnoDB 一致性读使用的版本可见性视图，记录创建时的事务边界及活跃读写事务等信息。它不保存业务行数据，而是帮助判断某个版本能否被当前读取看到。

## 1. 何时建立

| 隔离级别或语句 | 常见行为 |
| --- | --- |
| READ COMMITTED | 每次普通一致性读使用新建立的 Read View。 |
| REPEATABLE READ | 首次普通一致性读时建立，随后在事务内复用。 |
| RR 下 START TRANSACTION WITH CONSISTENT SNAPSHOT | 在开始事务时建立一致性快照，而不是等待首次普通查询。 |

普通 START TRANSACTION 通常不会立即创建 Read View。因此，事务开始后、首次一致性读之前，其他事务提交的修改仍可能对该首次读取可见。

WITH CONSISTENT SNAPSHOT 不会改变隔离级别；其建立一致性快照的效果适用于 REPEATABLE READ，其他级别不能据此获得相同语义。

## 2. 判断版本可见性

- [版本可见性](VersionVisibility.md)：ReadView 字段、事务 ID 边界、活跃集合及 undo 版本查找。

Read View 保存创建者事务标识、创建时活跃的读写事务集合，以及用于快速判断的事务 ID 边界等信息。

对于普通持久化记录，可以将判断简化为：

- 当前事务自己的修改通常可见。
- 创建视图前已提交的修改通常可见。
- 创建视图时仍活跃的其他事务修改不可见。
- 创建视图之后才获得相关新事务 ID 的事务修改不可见。

事务 ID 不等于提交顺序，不能只比较某个事务 ID 大小就完整判断可见性。只读事务的事务 ID 分配也有实现细节，不能把活跃集合简单理解为所有连接或所有事务的列表。

## 3. 查询期间提交的处理

假设初始 age 为 20：

| 顺序 | 事务 A | 事务 B |
| --- | --- | --- |
| 1 | | 修改 age 为 21，尚未提交。 |
| 2 | 开始普通一致性查询，建立视图，其中 B 仍活跃。 | |
| 3 | 查询继续执行。 | 提交。 |
| 4 | 根据原视图判断，B 的新版本仍不可见，读取可见旧版本。 | |

同一次读取不会因为 B 途中提交，就刷新视图并改为返回 B 的版本。READ COMMITTED 下，A 下一次普通查询使用新视图，才可能看到 21；REPEATABLE READ 下通常继续复用原视图。

上述比较假设 A 未自行修改相关记录；自身修改的可见性需要按读己之写等规则处理。

## 4. 与 undo 的协作

数据页中的当前记录可以包含未提交修改。InnoDB 检查其事务信息，若当前版本不可见，就通过回滚指针与 [undo](../logs/UndoLog.md) 信息重建更早版本，并继续判断。

```text
当前记录：age=22，版本不可见
        ↓ undo 重建
历史版本：age=21，版本不可见
        ↓ undo 重建
历史版本：age=20，版本可见 → 返回
```

重建旧版本供读取不会把页中的当前值改回去。如果记录是在视图之后才插入，且没有可见的旧版本，查询可以将其视为不存在。

## 5. 不适用同一规则的读取

FOR UPDATE、FOR SHARE 等锁定读以及 UPDATE、DELETE 等操作，不按普通一致性读的 Read View 规则简单读取旧快照，而是结合当前记录和锁协调执行。

没有普通 Read View 不等于没有并发控制。锁定读遇到冲突的未提交修改通常需要等待；READ UNCOMMITTED 的普通读取则可能看到未提交版本。

## 6. 生命周期与历史清理

READ COMMITTED 下视图通常按一致性读取的生命周期使用；REPEATABLE READ 下复用的事务视图通常在事务结束时释放。

仍然活跃的旧视图可能需要较早的历史版本，使 purge 无法清理相关 undo。长事务或长时间一致性读取因此可能增加历史保留及版本遍历的成本。
