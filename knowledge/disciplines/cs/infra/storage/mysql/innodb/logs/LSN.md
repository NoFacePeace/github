# LSN

LSN（Log Sequence Number，日志序列号）是 InnoDB 标识 redo 日志流位置的单调递增编号，用于比较日志生成、写出、持久化和检查点等进度。它不是事务 ID，也不是每提交一个事务就增加 1 的计数器。

## 1. 日志位置与物理文件

LSN 随 redo 日志流向前推进，体现日志位置而非事务数量。一个事务可以产生多段 redo，不同事务的日志也可以交错出现。

redo 文件空间可以循环复用，但逻辑 LSN 不会因为切换文件或复用旧空间而回到原来的值。LSN 不是某个固定文件内部的简单偏移量。

## 2. 常见进度

| 进度 | 含义 |
| --- | --- |
| 当前日志 LSN | redo 日志流已经生成到的位置。 |
| 已写出 LSN | redo 已经写入日志文件的进度，不必然表示已完成持久化。 |
| 已刷盘 LSN | redo 已经完成同步持久化的进度。 |
| 检查点 LSN | 崩溃恢复的起始边界；此前不再需要的日志空间可按规则复用。 |

通常可以按“检查点 ≤ 已刷盘 ≤ 已写出 ≤ 当前日志”的关系理解。具体内部进度还包括日志预留、缓冲区完成等状态；并发采样的字段不一定构成完全同时刻的快照。

## 3. 提交与批量刷盘

假设三个事务需要持久化的目标 LSN 分别为 100、120、150。如果一次刷盘将进度推进到 150，就覆盖三个事务各自的 redo 持久化要求。

```text
事务 A 需要：100
事务 B 需要：120
事务 C 需要：150
       ↓
已刷盘 LSN 推进到 150
       ↓
三者所需 redo 都已持久化
```

这里的数字只是示意。一个事务发现已刷盘进度覆盖自己的目标后，无须重复刷同一段日志，这是合并刷盘需求的基础。

满足 redo 持久化要求不等于整个事务已经完成提交。开启 binlog 时，还需完成对应提交协调；刷盘也可能覆盖未提交事务的 redo。

## 4. 数据页 LSN 与 WAL

数据页会记录与其修改相关的 LSN。脏页写回数据文件前，InnoDB 必须先确保恢复该页修改所需的 redo 已持久化，满足预写日志规则。

崩溃恢复时，可以结合页上的 LSN 判断某些 redo 是否已经反映在该页中，避免重复应用已完成的修改。具体恢复还需遵循日志记录和页恢复规则，不能仅按一个大小比较概括所有处理。

## 5. 检查点与日志空间压力

检查点推进依赖必要的数据页修改已持久化。当前日志 LSN 与检查点 LSN 的差距常用于观察检查点年龄，反映尚不能复用的日志区间规模。

该差值不是未提交事务数量，也不等于所有未刷盘 redo 的大小。如果日志产生速度长期超过数据页写回与检查点推进速度，会增加 redo 空间压力，进而影响写入吞吐和延迟。

## 6. 查看进度

```sql
SHOW ENGINE INNODB STATUS;
```

输出的 LOG 部分通常可见 Log sequence number、Log written up to、Log flushed up to、Last checkpoint at 等字段，具体字段随版本变化，访问也受权限影响。

排查时应比较观察窗口内的进度变化，并结合磁盘延迟、脏页和写入量分析。LSN 持续增长本身是正常现象，不能仅凭数值大就判断数据库异常。
