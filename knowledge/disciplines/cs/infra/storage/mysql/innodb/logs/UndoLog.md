# InnoDB undo log

## 1. 定义与格式

undo log 是 InnoDB 的撤销日志，保存回滚修改及重建旧版本所需的信息。它采用专门的日志记录格式，不使用 DYNAMIC、COMPACT 等表的行格式，也不是每次保存一份完整旧行快照。

现代 MySQL 通常通过独立 undo 表空间管理持久化 undo；具体组织与表空间配置随版本变化。

## 2. 不同操作保存什么

| 操作 | 主要需要支持的恢复行为 |
| --- | --- |
| INSERT | 回滚时删除新插入的记录。 |
| UPDATE | 利用被修改列的旧值和相关内部信息恢复修改前状态。 |
| DELETE | 普通删除先设置删除标记，undo 支持撤销相应修改及版本信息变化。 |

具体 undo 记录还可能包含索引维护和清理需要的信息，不能仅将其理解为一个“旧值字典”。

## 3. 当前记录与历史版本

聚簇索引叶子记录通常保存当前版本，可能包含未提交的修改。DB_ROLL_PTR 用于定位相关 undo，DB_TRX_ID 等信息用于版本可见性判断。

```text
当前记录：age = 22
        ↓ 回滚指针
undo：恢复到 age = 21 所需的信息
        ↓ 历史版本的相关信息
undo：恢复到 age = 20 所需的信息
```

一致性读结合当前记录和 undo 重建历史版本，再根据 Read View 等规则判断可见性。Read View 本身不保存业务行快照。

## 4. 回滚与一致性读的区别

- [原子性](../../../../../runtime/transactions/Atomicity.md)：事务修改整体生效或撤销的保证，undo 是 InnoDB 实现该保证的重要机制。

- **事务回滚**：使用 undo 撤销修改，恢复记录状态。
- **一致性读**：重建可见的旧版本供当前读取使用，不会因此将数据页中的新值改回去。

事务只是尚未提交，不会自动撤销。其他事务能否看到新版本取决于隔离级别及具体读取方式，不能一律认为所有读取都会去找旧版本。

## 5. 生命周期与 purge

插入 undo 通常在事务提交后即可释放或复用。更新类 undo 在事务提交后仍可能被一致性读需要，不能立即全部清理。

当没有相关读取需要这些历史版本时，purge 可以清理相应历史信息，并在安全时移除删除标记记录等。长时间持有 Read View 的事务可能拖延历史清理，增加 undo 和历史链压力。

undo 不是永久审计日志，也不提供任意历史时间点查询的通用接口。故障恢复时，undo 还需与 [redo](RedoLog.md) 和事务恢复机制协作。

对于普通持久化表，写入或修改 undo 页本身也会产生相应 redo。如果 undo 页尚未写盘就发生崩溃，InnoDB 可以通过 redo 恢复必要的 undo 信息，再处理未完成事务的回滚。这不是将整个 undo 文件复制到 redo，而是记录相关页修改；临时表等场景有不同规则。
