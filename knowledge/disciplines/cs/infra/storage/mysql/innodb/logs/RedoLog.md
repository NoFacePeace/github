# InnoDB redo log

## 1. 定义

redo log 是 InnoDB 的重做日志，记录页修改相关信息，用于崩溃后恢复尚未完整写入数据文件的修改。它不是 SQL 文本日志，也不是长期历史归档。

redo 与页修改紧密相关，但记录内容采用专门的恢复格式，不应简单理解为每次保存整个数据页副本。

## 2. 预写日志

InnoDB 修改 Buffer Pool 中的页时产生相关 redo。将脏页写回数据文件前，必须确保恢复这些修改所需的 redo 已按规则持久化，这就是[预写日志（WAL）](../../../../../architecture/storage/WAL.md)的核心要求。

事务提交不要求立即写回所有修改过的数据页。通过先持久化日志，再逐步写回数据页，可以减少数据文件的随机写入压力。

## 3. 提交与刷盘配置

- [持久性](../../../../../runtime/transactions/Durability.md)：成功提交的结果在约定故障模型下保留，redo 是 InnoDB 实现该保证的重要机制。

innodb_flush_log_at_trx_commit 控制提交时 redo 的写入和刷盘行为：

| 值 | 主要行为 |
| --- | --- |
| 1 | 每次事务提交时要求写入并刷盘相关 redo；组提交等机制可能合并实际 I/O。 |
| 2 | 提交时写入操作系统缓存，刷盘通常由周期性机制完成。 |
| 0 | 提交时不要求立即写出 redo，写入和刷盘通常由周期性机制完成。 |

周期性处理不是严格的实时承诺，间隔还受配置、调度等影响。模式 0、2 可能在故障时丢失已提交事务，保障也取决于操作系统和设备是否正确执行持久化请求。

```sql
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
```

## 4. 检查点与空间复用

redo 使用日志序列号 LSN 标识日志位置和修改进度。随着相关脏页持久化，检查点可以推进，不再需要用于恢复的旧日志空间可以复用。

如果脏页刷出速度跟不上日志产生速度，日志空间压力可能促使更积极的刷页并影响写入性能。redo 容量与文件组织随版本变化，不能将某个版本的固定文件名当作通用规则。

## 5. 崩溃恢复与边界

崩溃后，InnoDB 根据检查点和可用 redo 恢复必要的页修改，并结合 undo 和事务状态处理未完成事务。

redo 可以包含尚未提交事务产生的修改，因此“日志中存在修改”不等于“对应事务已经提交”。redo 也不能替代备份与 binlog 完成任意时间点恢复。
