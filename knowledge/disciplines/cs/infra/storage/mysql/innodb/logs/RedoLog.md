# InnoDB redo log

## 1. 定义

redo log 是 InnoDB 的重做日志，记录页修改相关信息，用于崩溃后恢复尚未完整写入数据文件的修改。它不是 SQL 文本日志，也不是长期历史归档。

redo 与页修改紧密相关，但记录内容采用专门的恢复格式，不应简单理解为每次保存整个数据页副本。

## 2. 预写日志

InnoDB 修改 Buffer Pool 中的页时产生相关 redo。将脏页写回数据文件前，必须确保恢复这些修改所需的 redo 已按规则持久化，这就是[预写日志（WAL）](../../../../../architecture/storage/WAL.md)的核心要求。

事务提交不要求立即写回所有修改过的数据页。通过先持久化日志，再逐步写回数据页，可以减少数据文件的随机写入压力。

## 3. 提交与刷盘配置

- [持久性](../../../../../runtime/transactions/Durability.md)：成功提交的结果在约定故障模型下保留，redo 是 InnoDB 实现该保证的重要机制。

innodb_flush_log_at_trx_commit 控制提交时 redo 的写入和刷盘行为：

| 值 | 主要行为 |
| --- | --- |
| 1 | 每次事务提交时要求写入并刷盘相关 redo；组提交等机制可能合并实际 I/O。 |
| 2 | 提交时写入操作系统缓存，刷盘通常由周期性机制完成。 |
| 0 | 提交时不要求立即写出 redo，写入和刷盘通常由周期性机制完成。 |

周期性处理不是严格的实时承诺，间隔还受配置、调度等影响。模式 0、2 可能在故障时丢失已提交事务，保障也取决于操作系统和设备是否正确执行持久化请求。

```sql
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
```

## 4. 刷盘触发场景

redo 刷盘不只由客户端执行 COMMIT 触发。这里的刷盘指请求将相关日志持久化到存储设备，不是仅写入操作系统 Page Cache；保障仍依赖操作系统与设备正确兑现同步请求。

| 触发场景 | 说明 |
| --- | --- |
| 事务提交 | innodb_flush_log_at_trx_commit = 1 时，提交过程要求所需 redo 已持久化；显式 COMMIT 和自动提交都会触发相应流程。 |
| 后台周期刷新 | 后台按配置周期写出和刷新日志，实际时机受线程调度等影响，不是严格的实时定时承诺。 |
| 数据页刷盘前的 WAL 要求 | 脏页写回数据文件前，必须先持久化恢复该页修改所需的 redo；相关日志已持久化时无需重复同步。 |
| 显式日志刷新、正常关闭等操作 | 相关操作按其语义和关闭模式刷新日志，不同操作的范围与行为不能混为一谈。 |

日志缓冲区空间不足也会推动 redo 写出，但写出不一定等于完成同步刷盘。常见的缓冲 I/O 路径可以简化为：

```text
InnoDB Log Buffer
        ↓ 写出
操作系统 Page Cache
        ↓ 同步刷盘（fsync 等）
持久化存储
```

实际路径受平台和配置影响，可能绕过 Page Cache。应始终区分内存缓冲、文件写出与持久化完成，而不是将任意 write 都视作掉电后可恢复。

多个事务可以共享一次 redo 刷盘。若已刷盘 LSN 覆盖某事务的目标位置，它的 redo 持久化要求已经满足，不需要为该事务重复刷同一段日志。

刷盘也可能包含未提交事务的 redo，所以“redo 已刷盘”不等于“事务已提交”。事务提交还需完成相应的提交协调和引擎状态处理。

## 5. 检查点与空间复用

redo 使用[日志序列号 LSN](LSN.md) 标识日志位置和修改进度。随着相关脏页持久化，检查点可以推进，不再需要用于恢复的旧日志空间可以复用。

如果脏页刷出速度跟不上日志产生速度，日志空间压力可能促使更积极的刷页并影响写入性能。redo 容量与文件组织随版本变化，不能将某个版本的固定文件名当作通用规则。

## 6. 事务回滚与 redo

事务回滚通过 undo 撤销数据修改，不会删除已经写入的 redo，也不会把 redo 的写入位置倒退到事务开始前。

```sql
-- 假设 users 使用 InnoDB，id = 1 的记录存在。
START TRANSACTION;
UPDATE users SET age = 20 WHERE id = 1;
ROLLBACK;
```

此过程可以简化为：

```text
UPDATE 保存 undo，修改数据页并产生 redo
                    ↓
ROLLBACK 利用 undo 撤销数据修改
                    ↓
撤销过程中对持久化页的修改继续产生新的 redo
```

回滚本身也需要崩溃恢复保护。如果回滚途中发生崩溃，InnoDB 可以通过 redo 恢复已完成的相关页修改，再结合 undo 和事务状态继续处理尚未完成的回滚。

因此，redo 不仅包含最终提交事务的修改，也可能包含未提交事务的修改以及撤销修改时产生的页变化。redo 已刷盘不表示事务已提交；未提交事务的 redo 也可能提前持久化。

旧 redo 是否可以复用，由检查点及恢复需求决定，不是在执行 ROLLBACK 时立即清除。回滚完成后，数据修改被撤销，但不能据此认为原始日志已经消失。

## 7. 崩溃恢复与边界

崩溃后，InnoDB 根据检查点和可用 redo 恢复必要的页修改，并结合 undo 和事务状态处理未完成事务。

redo 可以包含尚未提交事务产生的修改，因此“日志中存在修改”不等于“对应事务已经提交”。redo 也不能替代备份与 binlog 完成任意时间点恢复。
