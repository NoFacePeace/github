# 非唯一索引等值查询加锁

在 InnoDB 的 REPEATABLE READ 下，锁定读取通过非唯一索引等值查询时，需要扫描全部匹配项，并保护可能插入相同键值的位置。通常涉及临键锁和边界间隙锁。

## 1. 示例与前提

假设 users 使用 InnoDB，id 是主键，age 上有普通二级索引，且执行计划使用该索引。索引项按 (age, id) 排列如下：

```text
(10, 1) → (20, 2) → (20, 3) → (30, 4) → (40, 5)
```

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;

SELECT * FROM users WHERE age = 20 FOR UPDATE;

-- 后续业务操作。
COMMIT;
```

事务先获取或沿用表级 IX。下面描述典型升序扫描时的加锁结果，实际应结合版本和执行计划验证。

## 2. 二级索引上的锁

| 位置 | 典型保护 |
| --- | --- |
| 第一条匹配项 (20, 2) | X 临键锁，覆盖 ((10, 1), (20, 2)]。 |
| 第二条匹配项 (20, 3) | X 临键锁，覆盖 ((20, 2), (20, 3)]。 |
| 最后一条匹配项到后继项之间 | 间隙锁，覆盖 ((20, 3), (30, 4))，通常不锁 (30, 4) 记录本身。 |

括号中的端点是完整索引项，比较顺序同时考虑 age 和主键 id，不能只按 age 数值理解边界。

上述范围保护可以阻止其他事务插入新的 age = 20 记录，但也可能阻塞 age = 15 或 25 等位于相关间隙中的插入。锁范围可能大于 WHERE 条件对应的逻辑集合。

## 3. 聚簇索引上的锁

通过二级索引取得 id = 2、3 后，FOR UPDATE 还会对对应的聚簇索引记录获取 X 记录锁，通常不额外保护这些主键前方的间隙。

这是按找到的主键逐条定位并加锁，不是遍历全表的所有 id。即使另一个事务直接通过主键更新 id = 2，也会与该聚簇索引记录锁冲突。

## 4. 未命中与隔离级别

如果查询值不存在，例如查询 age = 25，通常没有匹配记录可锁，但在 RR 下仍可能锁住目标值所在的二级索引间隙，阻止插入。

READ COMMITTED 下，普通搜索通常不加间隙锁，主要保护相应记录；重复键检查和外键检查等除外。普通一致性 SELECT 不采用这里的锁定读取规则。

## 5. 与范围查询的区别

等值查询的停止条件是已经越过全部相同键值；范围查询则根据上下界及其是否包含端点决定扫描边界。两者可能使用相同类型的锁，也可能在特定数据下得到相近范围，但不能认为它们始终具有相同的锁边界。

UPDATE、DELETE 通过非唯一索引搜索时遵循相近规则，修改索引项及约束检查还可能增加锁。
