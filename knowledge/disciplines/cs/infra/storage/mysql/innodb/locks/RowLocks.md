# InnoDB 行锁

InnoDB 的行级锁体系以索引记录及相关间隙为基础，不是简单地锁住一行在数据文件中的物理地址。通常将记录锁、间隙锁、临键锁和插入意向锁放在这一体系下讨论。

## 1. 常见类型

| 类型 | 范围与作用 |
| --- | --- |
| [记录锁](RecordLock.md) | 锁定索引记录，协调对同一记录的冲突访问。 |
| [间隙锁](GapLock.md) | 保护索引记录之间及首尾间隙，阻止相关位置的插入。 |
| [临键锁](NextKeyLock.md) | 记录锁与其前方间隙锁的组合，同时保护记录和插入范围。 |
| [插入意向锁](InsertIntentionLock.md) | 特殊间隙锁，表达在某个位置插入的意图，协调插入冲突。 |

表级 IS／IX 意向锁和 AUTO-INC 自增锁不属于行级锁，但一次数据操作可以同时涉及这些不同层次的机制。

## 2. 锁类型与模式

锁类型描述保护范围或用途，S／X 描述模式，两者不能机械地组合成统一的兼容规则。

| 类型 | 模式与兼容性 |
| --- | --- |
| 记录锁 | 可以是 S 或 X；不同事务的 S 兼容，X 与同一记录上的 S、X 冲突。 |
| 临键锁 | 可以是 S 或 X，区别主要体现在记录部分；间隙部分阻止插入。 |
| 纯间隙锁 | 可以带 S／X 标记，但间隙保护效果相同，纯间隙锁之间可以共存。 |
| 插入意向锁 | 通常表现为带 INSERT_INTENTION 标记的 X 间隙锁，不是业务可选的两种普通 S／X 模式。 |

插入意向锁可能等待阻止目标位置插入的间隙锁，因此“间隙锁可以共存”不能直接推广到所有插入相关冲突。

## 3. 加锁范围如何确定

实际锁定范围受 SQL 类型、隔离级别、索引、执行计划和记录是否存在等因素影响，不仅取决于 WHERE 最终匹配多少行。

- 完整唯一键等值访问且记录存在时，通常可以只锁定匹配记录。
- REPEATABLE READ 下的非唯一索引和范围锁定访问通常涉及临键锁及间隙锁。
- READ COMMITTED 下，普通搜索通常不使用间隙锁，但外键和重复键检查等有例外。
- 使用二级索引进行排他锁定访问时，还可能锁定对应的聚簇索引记录。

普通一致性 SELECT 在常见 READ COMMITTED、REPEATABLE READ 下通常通过 MVCC 读取，不获取这些记录与范围锁；锁定读和数据修改则按相应规则加锁。

## 4. 与表级锁的协作

获取记录 S 锁前，需要表上的 IS 或满足要求的更强模式；获取记录 X 锁前，需要 IX。意向锁帮助表级访问判断冲突，具体记录上的锁继续处理记录冲突。

同一事务可以在表上持有一个适当的意向模式，并锁定多条记录。InnoDB 不会仅因为记录锁数量很多，就自动升级为整表 X 锁。

## 5. 生命周期与诊断

事务记录锁通常保留到提交或回滚，部分不匹配记录锁等可以根据隔离级别和执行过程提前释放。锁冲突可能造成等待和死锁，应结合事务范围和访问顺序分析。

MySQL 8.0 可通过 performance_schema.data_locks 和 data_lock_waits 观察锁与等待关系。底层 RECORD 类型还可能包含间隙保护，需要结合 LOCK_MODE 判断，不能把所有 RECORD 对象都视为纯记录锁。
