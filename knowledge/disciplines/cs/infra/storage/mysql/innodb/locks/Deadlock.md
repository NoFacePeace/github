# InnoDB 死锁

死锁（Deadlock）是多个事务互相持有其他事务需要的锁，形成循环等待，导致相关事务无法继续推进。单纯存在锁等待不等于死锁，关键在于等待关系是否形成环。

## 1. 循环等待示例

假设 users 使用 InnoDB，id 是主键，且 id = 1、2 的记录都存在。两个会话分别开启事务，并按下列顺序执行：

| 步骤 | 事务 A | 事务 B |
| --- | --- | --- |
| 1 | START TRANSACTION; | START TRANSACTION; |
| 2 | SELECT * FROM users WHERE id = 1 FOR UPDATE; | |
| 3 | | SELECT * FROM users WHERE id = 2 FOR UPDATE; |
| 4 | SELECT * FROM users WHERE id = 2 FOR UPDATE;，等待 B。 | |
| 5 | | SELECT * FROM users WHERE id = 1 FOR UPDATE;，形成循环等待。 |

```text
A 持有 id=1 的 X 记录锁，等待 B 释放 id=2
                     ↓
B 持有 id=2 的 X 记录锁，等待 A 释放 id=1
                     ↓
                 形成等待环
```

两个事务的表级 IX 意向锁互相兼容，此例的冲突发生在记录锁层面。死锁也可能涉及范围锁、插入意向等待或锁模式升级，不限于两条记录或两个事务。

## 2. 并发 REPLACE 案例

### 2.1 表结构与冲突来源

此例来自《数据库内核月报》2015 年 3 月的[并发 Replace into 导致的死锁分析](http://mysql.taobao.org/monthly/2015/03/01/)，原文测试版本为 MySQL 5.6.23。

```sql
CREATE TABLE t1 (
    a INT AUTO_INCREMENT PRIMARY KEY,
    b INT,
    c INT,
    UNIQUE KEY (b)
) ENGINE = InnoDB;

-- 多个会话并发执行。
REPLACE INTO t1 (b, c) VALUES (2, 3);
```

虽然主键 a 使用自增值，但 b 还有唯一索引。所有会话都尝试写入 b = 2，因此会在该唯一索引上发生冲突，而不是因为分配到了重复的自增主键。

REPLACE 的语义是在唯一键冲突时替换已有记录。即使内部选择 UPDATE 路径优化执行，新旧主键不同仍可能导致聚簇索引和二级索引项的删除、插入。

唯一二级索引项包含主键，按 (b, a) 排序。因此 b 始终为 2，主键 a 变化时，索引项的位置仍可能变化。自增值按分配顺序产生，不保证并发会话按相同顺序执行替换。

### 2.2 等待环如何形成

为便于说明，将原文主键值缩写为 619、614 等。假设已有唯一索引项为 (2, 619)，事务 A 已分配自增值 614，但较晚才执行到替换阶段。原文还通过 purge 清理历史删除项，构造了下列插入位置和锁排队关系：

| 步骤 | 事务 A | 事务 B |
| --- | --- | --- |
| 1 | 检查到 b = 2 冲突，持有旧索引项 (2, 619) 的 X 锁及对应聚簇索引记录的锁。 | |
| 2 | | 同样检查到冲突，请求旧索引项上的 X 锁，排队等待 A。 |
| 3 | 标记删除旧索引项，准备插入新项 (2, 614)。 | 仍在等待旧索引项上的锁。 |
| 4 | 新项排在 (2, 619) 前方，申请目标间隙的插入意向锁；按该案例的排队规则，该请求受到 B 已排队的相关锁请求阻塞。 | 仍需 A 释放锁。 |

```text
B 的 X 锁请求 → 等待 A 释放旧索引项的锁
A 的插入意向请求 → 等待 B 已排队的相关锁请求
                         ↓
                        死锁
```

关键是等待中的锁请求也参与了插入协调：不是 A 与自己持有的 X 锁冲突，也不是两个插入意向锁互相冲突。此处涉及插入意向请求不能越过相关等待锁的规则，不能简化成任意纯记录锁都会阻止在记录前方插入。

### 2.3 自增、purge 与版本边界

自增在这里影响新二级索引项的位置，不是说 AUTO-INC 锁直接导致了此次死锁。原文中的并发分配与执行顺序，使较小的新主键需要插到较大的旧主键前面。

purge 是否已物理清理被标记删除的历史索引项，会改变索引页中的插入位置，以及哪个后继索引项上存在等待请求。原文对比了停止 purge 的情况，说明该等待环依赖具体的物理记录与执行时序，不是每次并发 REPLACE 都必然发生。

此例用于解释 MySQL 5.6.23 的具体路径，不能据此认定所有新版本都原样复现。新版本仍可能出现 REPLACE 并发死锁；是否属于同一路径，应结合具体版本和死锁报告确认。

### 2.4 程序处理

默认开启死锁检测时，InnoDB 会选择一个事务整体回滚，向对应会话返回 1213 错误，SQLSTATE 为 40001。牺牲者不固定是 A 或 B，程序应捕获异常，并在适当情况下重试整个事务。

## 3. 检测与回滚

InnoDB 默认开启 innodb_deadlock_detect。检测到引擎能够识别的死锁后，会选择一个事务作为牺牲者，将整个事务回滚并释放相关锁，让其他事务有机会继续。

被回滚的不一定是最后发起锁请求的事务，也不应假设固定回滚某一方。InnoDB 通常倾向于选择回滚成本较小的事务，具体选择由内部规则决定。

关闭死锁检测后，InnoDB 数据锁的循环等待通常需要依靠锁等待超时等机制打破。涉及其他锁层次时，检测能力和处理机制可能不同。

## 4. 程序收到的错误

被选中回滚的事务，其正在执行的 SQL 通常返回以下错误：

```text
错误码：1213
SQLSTATE：40001
Deadlock found when trying to get lock; try restarting transaction
```

数据库驱动通常将该错误转为程序异常。未捕获时，异常可能向上抛出，导致本次业务调用失败；配置了适当重试的框架可能在内部处理它。

另一个事务可以继续，但仍可能因其他竞争或错误失败，不能据此保证其最终一定提交成功。

## 5. 事务重试

死锁牺牲者的整个事务已经回滚，因此需要从新的事务开始，重新执行读取、判断和修改，而不是只重试最后报错的一条 SQL。

```text
开启事务
    ↓
读取并执行业务修改
    ↓
成功 → 提交
死锁 → 清理当前事务状态 → 有限次数退避 → 开启新事务重试
```

重试应有次数上限，并可加入随机退避以减少再次碰撞。每次重试都应重新读取数据和判断业务条件，避免沿用上一次事务中的过期结果。

事务回滚不会自动撤销已经发送的消息、外部接口调用等副作用。带有这些操作的业务需要结合幂等性、事务消息或其他协调机制设计重试。

## 6. 与锁等待超时的区别

| 对比项 | 死锁 | 锁等待超时 |
| --- | --- | --- |
| 原因 | 锁等待关系形成循环。 | 等待超过允许时间，不一定存在等待环。 |
| 常见错误码 | 1213。 | 1205。 |
| InnoDB 典型回滚范围 | 整个牺牲者事务。 | 默认通常只回滚超时的语句；innodb_rollback_on_timeout 等设置会影响范围。 |

不能把两种错误当作相同的事务状态。对超时错误，应根据配置与业务语义明确处理事务，避免在不确定的状态下继续提交。

## 7. 减少死锁

- 多个事务尽量按相同顺序访问表和记录，例如按主键升序逐条锁定。
- 缩短事务，避免持锁期间等待用户输入、远程接口或其他耗时操作。
- 使用合适索引减少扫描与锁定范围，并检查实际执行计划。
- 已知要修改记录时，可考虑直接使用 FOR UPDATE，减少先持有 S 再竞争升级 X 的场景。
- 对死锁实施有限次数的整个事务重试。

这些措施可以降低概率，但不能保证并发系统完全不出现死锁。唯一键检查、多个索引维护及范围保护等也可能形成复杂的锁依赖。

## 8. 排查方法

```sql
-- 查看最近一次记录的 InnoDB 死锁信息。
SHOW ENGINE INNODB STATUS;

-- MySQL 8.0：查看当前数据锁和等待关系。
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;
```

死锁通常很快被解除，因此当前等待视图不一定保留已发生死锁的完整现场。应结合死锁报告中的事务、SQL、索引、已持有锁和正在等待的锁重建等待环。

需要持续记录时，可以根据排查需要启用 innodb_print_all_deadlocks，将 InnoDB 死锁信息写入错误日志；需考虑权限、日志量和 SQL 中业务数据的可见范围。
