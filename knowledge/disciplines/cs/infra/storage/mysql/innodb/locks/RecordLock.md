# InnoDB 记录锁

## 1. 定义

记录锁（Record Lock）锁定一条索引记录，协调事务对同一记录的并发访问。即使表没有显式索引，InnoDB 也会使用内部聚簇索引实施记录锁。

记录锁本身不保护记录之间的间隙。临键锁则同时保护记录及其前方间隙，不能将所有涉及记录的锁都理解为纯记录锁。

## 2. 共享与排他模式

| 模式 | 用途 | 与其他事务的 S 记录锁 | 与其他事务的 X 记录锁 |
| --- | --- | --- | --- |
| S（共享） | 保护记录不被修改，允许其他事务共享锁定读取。 | 兼容 | 冲突 |
| X（排他） | 用于修改记录或提前排斥其他锁定访问。 | 冲突 | 冲突 |

兼容性针对同一索引记录、不同事务之间的锁判断。普通 MVCC 一致性读不申请 S 记录锁，通常不因已有 X 记录锁而等待。

## 3. 业务主动获取 S 锁

假设 users 是 InnoDB 表，id 是主键，且 id 为 10 的记录存在：

```sql
START TRANSACTION;

SELECT * FROM users WHERE id = 10 FOR SHARE;

-- 完成需要保护该记录的业务操作。
COMMIT;
```

MySQL 8.0 的 FOR SHARE 用于显式共享锁定读，旧写法为 LOCK IN SHARE MODE。其他事务仍可对同一记录获取 S 锁，但修改、删除或 FOR UPDATE 需要等待冲突锁释放。

锁定读应在显式事务中使用，以便在后续操作期间保留锁。事务结束通常释放相关记录锁。

## 4. 业务主动获取 X 锁

```sql
START TRANSACTION;

SELECT * FROM users WHERE id = 10 FOR UPDATE;
UPDATE users SET age = age + 1 WHERE id = 10;

COMMIT;
```

FOR UPDATE 获取相应的排他锁；UPDATE、DELETE 等修改操作本身也会获取相应锁，不要求业务必须先执行锁定读。

如果需要先读取、计算再修改，提前使用 FOR UPDATE 可以避免两个事务先持有 S 锁再同时升级 X 锁的典型死锁情形，但不能消除所有死锁。能够用一条原子 UPDATE 表达的业务，也不必为了加锁额外执行 SELECT。

## 5. 自动获取 S 锁的场景

业务显式共享锁定读主要使用 FOR SHARE，但其他机制也可能获取 S 锁：

- **外键检查**：检查引用关系时，可能对相应父表记录获取共享记录锁。
- **部分重复键检查**：普通 INSERT 遇到重复键时，可能对重复索引记录申请共享锁；不同写入语句的处理并不完全相同。
- **SERIALIZABLE**：关闭自动提交时，普通 SELECT 会隐式转为共享锁定读，锁定范围仍取决于实际访问路径。

在常见的 READ COMMITTED、REPEATABLE READ 下，普通 SELECT 通常使用 MVCC，不会自动获取 S 记录锁，但仍会涉及 Server 层元数据锁。

## 6. 什么情况下不只锁一条记录

### 6.1 记录锁不只用于等值查询

范围查询、非等值条件以及 UPDATE、DELETE 等操作也会锁定访问到的相应索引记录。需要区分“锁定记录”和“只加记录锁、不锁间隙”：临键锁同时包含记录锁与前方间隙锁的作用。

以下讨论锁定读或修改操作，不适用于通常使用 MVCC 的普通一致性 SELECT。

| 场景 | 典型锁定情况 |
| --- | --- |
| 完整唯一键等值访问，记录存在 | 通常可以只锁匹配记录，不锁前方间隙。 |
| REPEATABLE READ 下的非唯一索引等值访问 | 通常涉及临键锁、间隙锁，既保护匹配记录，也限制相关间隙中的插入。 |
| REPEATABLE READ 下的范围访问 | 通常涉及临键锁；具体边界处可能使用纯记录锁或间隙锁。 |
| READ COMMITTED 下的范围访问 | 普通搜索通常不使用间隙锁，主要锁定相应索引记录；外键和重复键检查等仍有例外。 |

例如以下查询不是等值查询，但仍会锁定相应记录：

```sql
-- 假设 users 使用 InnoDB，age 上有普通索引。
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT * FROM users WHERE age > 20 FOR UPDATE;
COMMIT;
```

“完整唯一键等值且记录存在”是常见的只锁记录的条件，不是获取记录锁的唯一条件。

### 6.2 实际锁定范围

完整唯一键等值访问且记录存在时，通常可以只锁定匹配记录，不锁前方间隙。以下情况不能直接套用该结论：

- 条件只使用联合唯一索引的一部分。
- 使用非唯一索引或范围查询。
- 查询目标记录不存在。
- 实际执行计划扫描了比结果集更大的范围。

这些场景可能涉及间隙锁或临键锁，行为受隔离级别、索引和语句类型影响。使用二级索引进行排他锁定访问时，还可能锁定对应的聚簇索引记录。

因此，WHERE 看起来只匹配一行，并不保证实际只获取一把记录锁。

## 7. 等待与诊断

事务 A 对 id 为 10 的记录持有 X 锁时，事务 B 对该记录申请 S 或 X 锁通常需要等待；B 在常见隔离级别下执行普通一致性 SELECT，则可以读取符合其可见性规则的版本。

MySQL 8.0 可通过以下信息观察锁及等待关系，具体可见性受权限影响：

```sql
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;
SHOW ENGINE INNODB STATUS;
```

data_locks 中的 RECORD 表示索引记录层面的锁对象，还需要结合 LOCK_MODE 判断是否包含间隙部分，不能仅凭 RECORD 就认定是纯记录锁。例如，REC_NOT_GAP 标记表示不包含间隙。

遇到死锁或锁等待超时，应依据错误类型和事务状态处理回滚与重试，而不是直接忽略错误继续业务流程。
