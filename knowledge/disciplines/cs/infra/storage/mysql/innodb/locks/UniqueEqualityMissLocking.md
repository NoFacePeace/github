# 唯一索引等值查询加锁（未命中）

在 InnoDB 的 REPEATABLE READ 下，锁定读取通过完整唯一键查找一条不存在的记录时，通常保护目标值所在的索引间隙。没有返回记录，不代表没有加锁。

## 1. 主键查询示例

假设 users 使用 InnoDB，id 是主键，相邻键为 10 和 20，id = 15 不存在：

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;

SELECT * FROM users WHERE id = 15 FOR UPDATE;

-- 后续业务操作。
COMMIT;
```

事务获取或沿用表级 IX，并通常锁住主键索引间隙 (10, 20)。这不是对不存在的 id = 15 加记录锁，也不是只保护数字 15 这个点。

| 其他事务的操作 | 典型结果 |
| --- | --- |
| 插入 id = 15 | 插入意向请求受到间隙保护阻塞，需要等待。 |
| 插入 id = 12 或 18 | 同样位于受保护间隙，可能等待。 |
| 仅锁定已有 id = 20 的记录 | 不会仅因该纯间隙锁而冲突。 |
| 对同一间隙申请普通间隙锁 | 间隙锁之间可以共存。 |

## 2. 边界与唯一二级索引

目标值小于最小索引键或大于最大索引键时，可能保护最前方或最后方的间隙。实际边界由索引中的现有键决定。

若使用唯一二级索引查找不存在的值，间隙保护发生在该二级索引上。没有匹配行时，也就没有对应的匹配主键记录需要锁定；其他检查或访问路径仍可能涉及额外锁。

## 3. 不存在检查与并发插入

两个事务可以同时锁住相同间隙，并都查到目标不存在。随后都尝试插入时，可能互相等待并形成死锁。

因此，“先查询不存在，再插入”不能替代唯一约束。应通过主键或唯一索引保证唯一性，并处理重复键错误、死锁和必要的事务重试。

## 4. 隔离级别与事务边界

READ COMMITTED 下，普通搜索通常不使用上述间隙保护；重复键、外键检查等仍有例外。普通一致性 SELECT 则按 MVCC 读取，不因查不到记录就自动加这种间隙锁。

RR 下的相关事务锁通常随提交或回滚释放。若需保护后续操作，应使用明确的事务边界。
