# 索引范围查询加锁

在 InnoDB 的 REPEATABLE READ 下，锁定读取按索引范围扫描时，通常通过记录锁、间隙锁和临键锁保护访问到的记录及相关插入位置。实际边界受索引、比较条件、扫描方向和版本优化影响。

## 1. 主键范围示例

假设 users 使用 InnoDB，id 是主键，现有键为 10、20、30、40，且执行计划使用主键范围扫描：

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;

SELECT * FROM users WHERE id >= 20 AND id < 30 FOR UPDATE;

-- 后续业务操作。
COMMIT;
```

事务获取或沿用表级 IX。支持相应边界优化的典型加锁结果是：

| 位置 | 保护方式 |
| --- | --- |
| id = 20 | X 记录锁；下界命中主键且包含该点时，无需保护其前方间隙。 |
| 间隙 (20, 30) | 间隙锁，阻止插入 id = 25 等范围内记录。 |
| id = 30 | 在可排除上界记录的执行路径中，不必锁定该记录本身。 |

不能将此边界结果机械套用于所有版本、扫描方式或二级索引范围。部分执行路径可能锁住扫描到的上界记录及其前方间隙。

## 2. 临键锁如何覆盖范围

如果将条件改为以下范围：

```sql
SELECT * FROM users WHERE id > 10 AND id <= 30 FOR UPDATE;
```

对 id = 20、30 的典型 X 临键锁分别覆盖 (10, 20] 和 (20, 30]，既保护已有记录，也阻止向这两个间隙插入新记录。是否额外访问并锁住后继边界，需要结合实际扫描判断。

范围端点是否命中现有记录，以及使用 >、>=、<、<=，都会影响哪些记录与间隙需要保护。主键或唯一索引参与范围查询时，也不能套用唯一键完整等值查询只锁一条记录的规则。

## 3. 二级索引范围

假设 age 上有普通二级索引，查询如下：

```sql
SELECT * FROM users WHERE age >= 20 AND age < 40 FOR UPDATE;
```

使用 age 索引时，通常对扫描涉及的二级索引记录和间隙加锁，并对匹配行对应的聚簇索引记录加 X 记录锁。

二级索引的实际顺序包含主键。同一 age 可以对应多个主键，因此端点处理比单列主键范围更复杂；边界处不满足最终条件的索引项也可能被扫描或锁定。

## 4. 实际锁范围与结果集

索引间隙是按相邻现有索引项划分的，不会按 WHERE 中的任意数值切成精确区间。因此即使只查询某个小范围，也可能阻塞范围外但处于同一索引间隙中的插入。

如果还有无法直接用于索引定位的过滤条件，扫描范围也可能大于最终返回集合。没有合适索引时，可能转为大范围扫描并锁住大量记录和间隙。

## 5. 隔离级别与验证

READ COMMITTED 下，普通搜索通常不使用间隙锁，并允许提前释放部分不匹配记录的锁；重复键和外键检查等有例外。普通一致性 SELECT 不按上述规则获取记录与范围锁。

分析实际行为时，应结合 EXPLAIN 确认访问索引，并在事务保持打开时检查 performance_schema.data_locks 和 data_lock_waits。仅凭 SQL 文本或返回行数，无法完整确定所有锁边界。
