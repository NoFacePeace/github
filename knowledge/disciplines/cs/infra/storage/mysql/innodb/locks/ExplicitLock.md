# InnoDB 显式锁

## 1. 定义

显式锁是由 InnoDB 在内存锁管理结构中登记的锁，包括已授予的锁及等待中的请求。这里的“显式”描述内部表示方式，不是说业务必须显式执行某条加锁 SQL。

UPDATE 等自动加锁操作同样可以产生显式锁；Server 的 LOCK TABLES 显式表锁则是另一语境，不能直接等同。

## 2. 为什么需要显式表示

- **共享持有者**：多个事务可以同时持有同一记录的 S 锁，需要登记持有关系。
- **锁定但不修改**：FOR UPDATE 可以保护记录而不修改数据，不能靠改写记录的事务 ID 表示锁的归属。
- **间隙保护**：间隙没有业务行，无法只靠行上的事务信息表达保护范围。
- **等待管理**：冲突时需要登记请求及阻塞关系，以便唤醒等待者和检测死锁。

## 3. 常见场景

记录 S 锁、显式记录 X 锁、纯间隙锁、临键锁和表级意向锁等，都需要相应的显式管理。插入意向锁在需要等待时也会登记请求，无冲突插入路径未必保留独立的显式对象。

底层记录锁对象可以通过页及位图等方式关联多条索引记录，并非每条记录永远对应一个完全独立的内存对象。

## 4. 与隐式锁的协作

新插入等场景的记录 X 保护可以先采用隐式方式，减少无冲突时的登记成本。其他事务请求不兼容访问时，InnoDB 可以按需为原事务创建显式记录锁，再安排等待请求。

转换不是提高锁的保护强度，而是将已有保护转为便于统一管理冲突的形式。原事务的保护不会因为尚未登记显式对象就失效。

## 5. 观察与边界

MySQL 8.0 的 performance_schema.data_locks 和 data_lock_waits 可用于观察引擎暴露的锁及等待，具体可见性受权限和实现影响。

锁未出现在某次查询结果中，不足以证明记录没有受到保护；还应考虑隐式锁、采集时机及相关事务状态。
