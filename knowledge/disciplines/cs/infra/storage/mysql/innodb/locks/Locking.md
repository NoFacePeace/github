# InnoDB Locking

Locking（加锁）描述 InnoDB 在执行具体操作时，如何选择锁模式与范围、判断冲突、等待以及释放锁。分析加锁行为需要结合 SQL、索引、事务隔离级别和执行计划。

## 1. 加锁流程

- [插入加锁流程](InsertLocking.md)：INSERT 涉及的表级 IX、插入意向、新记录排他保护，以及约束检查和锁等待。

## 2. 索引访问加锁场景

以下文档以 REPEATABLE READ 下的 SELECT ... FOR UPDATE 为主要示例，区分查询条件与实际索引访问路径：

| 场景 | 主要内容 |
| --- | --- |
| [唯一索引等值查询（命中）](UniqueEqualityHitLocking.md) | 完整唯一键定位已有记录，通常直接获取记录锁。 |
| [唯一索引等值查询（未命中）](UniqueEqualityMissLocking.md) | 目标记录不存在时，保护其所在的插入间隙。 |
| [非唯一索引等值查询](NonUniqueEqualityLocking.md) | 扫描全部相同键值，保护匹配记录及相关间隙。 |
| [索引范围查询](RangeLocking.md) | 按范围扫描索引，结合端点条件判断记录和间隙保护。 |

上述场景不适用于普通一致性 SELECT。UPDATE、DELETE 的搜索阶段遵循相近规则，但修改索引项、约束检查等可能引入额外锁。

## 3. 分析方法

分析一条语句的加锁行为时，可以依次检查：

1. 操作类型：一致性读、锁定读取，还是插入、更新、删除。
2. 访问路径：使用哪个索引，是唯一键等值查找、非唯一键查找还是范围扫描。
3. 隔离级别：是否需要间隙保护，是否允许提前释放部分不匹配记录的锁。
4. 约束检查：是否涉及唯一键、外键或自增值分配。
5. 事务边界：相关锁按语句结束还是事务结束释放。

这些因素共同决定实际加锁结果，不能只根据 SQL 返回了几行推断锁住了哪些记录或范围。

## 4. 逻辑流程与实际实现

文档中的加锁步骤用于解释各类锁的职责，不代表每次操作都会按固定顺序创建相同的显式锁对象。已有锁可以沿用，新记录可能先受到隐式保护，等待后也可能重新检查条件。

判断实际持锁和等待情况时，应结合 Performance Schema 中的数据锁、等待关系及当前事务状态。
