# InnoDB 隐式锁

## 1. 定义

隐式锁是 InnoDB 利用记录的事务信息等判断保护归属的机制，常用于新插入记录等场景的排他保护，无需立即为每条记录登记显式 X [记录锁](RecordLock.md)对象。

“隐式”不代表没有锁或保护较弱，也不代表由普通 MVCC 读取替代了写入冲突控制。

## 2. 如何判断归属

对于聚簇索引记录，可以结合 DB_TRX_ID 和事务是否仍活跃等信息判断其是否受到某事务的隐式 X 保护。

二级索引记录不直接保存聚簇记录中的整套事务隐藏字段，其隐式保护判断更复杂，需要结合页级事务信息，必要时查询聚簇记录及相关版本信息。

并非记录上出现一个事务 ID 就表示锁仍有效，必须结合事务状态和具体访问路径判断。

## 3. 冲突时的转换

```text
A 插入记录，事务尚未结束
        ↓
记录先受到隐式 X 保护
        ↓
B 请求同一记录上的不兼容锁
        ↓
InnoDB 确认 A 的保护，必要时转换为显式记录锁
        ↓
登记 B 的等待，随后按锁管理规则处理
```

冲突检查通常由另一事务的访问请求触发，不是后台持续扫描所有记录寻找访问者。原持有事务结束后，等待者还需要重新按相关规则判断操作是否可以继续。

## 4. 不同访问的处理

| 其他事务的操作 | 典型处理 |
| --- | --- |
| 普通一致性 SELECT | 按 MVCC 选择可见版本，通常不等待相应记录 X 锁；未提交的新插入行通常不可见。 |
| FOR SHARE、FOR UPDATE 或修改同一记录 | 需要检查 S／X 兼容性，可能等待。 |
| 插入相同唯一键 | 进行重复键检查，并按语句及事务状态处理等待或冲突。 |

## 5. 为什么不能替代所有显式锁

隐式保护主要表达记录与未结束修改事务之间的关系，无法独自表示多个共享持有者、没有修改的锁定读、索引间隙保护，以及完整的等待队列。

它优化无冲突路径的内存和管理成本，显式锁则提供更完整的模式、范围和等待关系。事务结束后的历史事务信息还可能用于 MVCC，但不能因此认定隐式 X 保护仍然持续。
