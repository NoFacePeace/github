# InnoDB 存储格式

InnoDB 采用按行组织、按页管理和读写的存储方式。存储格式需要区分两个层面：表空间内部如何管理页和索引，以及一条记录内部如何编码字段。

## 1. 空间组织

```text
表空间（Tablespace）
  └─ 段（Segment）
      └─ 区（Extent）与单独分配的页
          └─ 页（Page）
              └─ 记录（Record，以索引页为例）
```

这是逻辑管理关系，不是文件系统目录结构。表空间还包含空间管理页等内容，并非所有页都保存业务记录。

| 层次 | 作用 |
| --- | --- |
| 表空间 | 管理数据与索引的存储空间，可以对应一个或多个文件。 |
| 段 | 管理分配给它的区及单独分配的碎片页，例如分别管理索引的叶子页和非叶子页。 |
| 区 | 由连续页组成，便于批量分配空间；默认 16 KiB 页大小下，一个区包含 64 页，即 1 MiB。 |
| 页 | 数据管理与读写的基本单位，默认大小为 16 KiB。 |
| 记录 | 索引页中的数据条目，其内容取决于索引类型和行格式。 |

段较小时可以使用单独分配的碎片页，增长后再按区分配，并非从第一条记录开始就独占完整的区。

### 1.1 为什么需要区

区是批量分配和管理页的单位。索引增长时，按区为段分配一批页，可以减少反复寻找、分配单个空闲页的管理开销，并便于跟踪区的空闲和使用状态。

区内的页在表空间页号上连续，有助于改善访问局部性，为范围扫描和预读提供更好的条件。但索引分裂等操作会影响页的布局，不能保证逻辑相邻的索引页都位于连续存储位置，也不能保证底层设备的物理连续性。

默认 16 KiB 页大小下，一个区为 1 MiB。小段先使用共享碎片区中的单个页，可以避免一开始就独占完整区造成的空间浪费。

**页是数据管理、缓存和读写的基本单位，区主要用于空间分配与管理。** 分配一个区，不代表每次读写都要处理整个区。

### 1.2 叶子页与非叶子页的段

一棵常规 InnoDB B+ 树索引使用两个段，分别管理叶子页与非叶子页，使两类页可以独立分配空间。每个段可以拥有自己的区及单独分配的碎片页。

根页归非叶子节点段管理。树很小时，根页本身也可以是叶子页，此时它虽保存叶子记录，仍属于非叶子节点段。

## 2. 表空间与文件

常见的表空间包括系统表空间、独立表空间、通用表空间、undo 表空间和临时表空间，各自承担不同用途。

启用 innodb_file_per_table 时，新建的普通非分区 InnoDB 表通常使用独立表空间，以 `.ibd` 文件保存该表的数据和索引。通用表空间可以保存多张表，分区表的独立表空间通常按分区组织。

因此，不能把所有 InnoDB 表都理解为必然对应一个独立文件，也不能认为 `.ibd` 只保存行数据而不保存索引。redo log 则使用独立日志文件，不属于表的 `.ibd` 数据文件。

## 3. 页与索引记录

常规索引使用 B+ 树组织，节点通常对应索引页。索引页包含页头、记录、页目录及其他管理信息，不是把字段字节简单连续拼接。

- **聚簇索引叶子页**：保存行记录，包含用户列及必要的内部信息。
- **二级索引叶子页**：保存索引列和聚簇索引键。
- **非叶子索引页**：保存用于导航的键和子页引用。

InnoDB 还有 undo 页、页外数据页等其他页类型。默认页大小为 16 KiB，可以在初始化实例时配置其他受支持的大小，不能当作普通会话参数随时修改。

索引的逻辑顺序不要求页在磁盘上物理连续。一个行记录也不一定把全部字段字节放在同一个页内，长字段可能使用页外存储。

## 4. 行格式

- [行格式](RowFormat.md)：记录内部结构、各格式差异、页外存储以及查看与指定方式。

行格式决定字段、NULL 标记、变长字段长度和页外引用等信息的组织方式。

| 格式 | 主要特点 |
| --- | --- |
| DYNAMIC | 现代 MySQL 的默认行格式；需要页外存储时，长变长字段可以整体移到页外，行内保留 20 字节引用。 |
| COMPACT | 较早的常用格式；适用的长字段移到页外时，通常保留前 768 字节及 20 字节引用。 |
| REDUNDANT | 旧行格式，主要用于兼容，元数据编码方式与现代格式不同。 |
| COMPRESSED | 支持压缩页，页外存储方式与 DYNAMIC 类似；有页大小、表空间及版本等使用限制。 |

字段是否移到页外由字段类型、长度和行能否放入页等因素决定。不能把“使用 DYNAMIC”理解为所有 VARCHAR、TEXT 或 BLOB 都自动放到页外。

COMPRESSED 行格式与透明页压缩是不同机制，不能混为一谈。

## 5. 行记录内部信息

以 COMPACT、DYNAMIC 等格式的聚簇索引叶子记录为例，除用户列外，还包含记录头、适用的 NULL 位图和变长字段长度信息，以及事务相关的隐藏列。

| 内部列 | 主要作用 |
| --- | --- |
| DB_TRX_ID | 记录最近插入或更新该行的事务 ID，大小为 6 字节。 |
| DB_ROLL_PTR | 指向相关 undo 记录的回滚指针，大小为 7 字节。 |
| DB_ROW_ID | 未定义合适的主键或唯一非空索引时，用于内部聚簇索引的隐藏行 ID，大小为 6 字节。 |

DB_ROW_ID 并非每张表都需要。普通二级索引记录也不直接保存聚簇索引行中的整套事务隐藏列。

## 6. 查看与指定格式

以下示例假设 users 表已经存在：

```sql
SHOW TABLE STATUS LIKE 'users';
SHOW CREATE TABLE users;

SHOW VARIABLES LIKE 'innodb_page_size';
SHOW VARIABLES LIKE 'innodb_default_row_format';
SHOW VARIABLES LIKE 'innodb_file_per_table';
```

SHOW TABLE STATUS 的 Row_format 可以用于查看实际行格式，SHOW CREATE TABLE 则用于查看建表定义及显式选项。

创建表时可以显式指定行格式：

```sql
CREATE TABLE storage_example (
    id BIGINT PRIMARY KEY,
    content TEXT
) ENGINE = InnoDB ROW_FORMAT = DYNAMIC;
```

修改默认行格式配置不会自动重写所有已有表。调整已有表的行格式通常涉及表重建，应结合数据量和在线 DDL 支持情况评估。
