# InnoDB 索引

索引通过维护有序的数据结构，减少查询需要扫描的数据。本文介绍 InnoDB 常见的 B+ 树索引；全文索引和空间索引使用不同的结构，不在本文范围内。

## 1. B+ 树结构

InnoDB 以页为单位组织索引。B+ 树的非叶子节点存储用于导航的键和子页引用，叶子节点存储记录；同一层的索引页通过链接连接，便于顺序访问。

查询先从根节点向下定位叶子页，再查找记录。范围查询可以在定位起点后沿叶子页扫描，而不必为每条记录重新从根节点查找。

## 2. 聚簇索引

- [聚簇索引](ClusteredIndex.md)：叶子记录、键的选择规则、主键查询与设计影响。

聚簇索引的叶子节点存储完整行数据，一张 InnoDB 表只有一个聚簇索引。其键按以下规则选择：

1. 有显式主键时，使用主键。
2. 没有主键时，使用第一个所有列都为 NOT NULL 的唯一索引。
3. 没有合适的唯一索引时，使用 InnoDB 生成的隐藏行 ID。

通常应显式定义短小、稳定的主键。主键越大，二级索引中保存它所需的空间通常也越大。

## 3. 二级索引与回表

- [二级索引](SecondaryIndex.md)：叶子记录、唯一性、回表、覆盖查询与维护成本。

二级索引的叶子记录包含索引列和聚簇索引键。当查询需要二级索引中未包含的列时，通常先从二级索引取得聚簇索引键，再访问聚簇索引获取完整记录，这个过程称为回表。

以下表使用 `id` 作为主键，并在 `name` 上建立二级索引：

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    age INT NOT NULL,
    INDEX idx_name (name)
) ENGINE = InnoDB;
```

执行以下查询时，如果优化器选择 `idx_name`，通常需要回表读取 `age`：

```sql
SELECT age FROM users WHERE name = 'Alice';
```

索引的存在不保证查询一定使用它，优化器会根据统计信息和成本选择执行计划。

## 4. 覆盖索引

当查询所需的列都包含在某个索引中时，该索引对这条查询构成覆盖索引。覆盖索引是索引与查询之间的关系，不是一种独立的索引结构。

例如，`idx_name` 包含 `name` 和主键 `id`，可以覆盖以下查询：

```sql
SELECT id, name FROM users WHERE name = 'Alice';
```

覆盖索引通常可以减少回表，但一致性读在需要判断记录可见性等情况下，仍可能访问聚簇索引。

## 5. 联合索引与最左前缀

联合索引按多个列的组合顺序排序。例如 `(name, age)` 先按 `name` 排序，再在相同 `name` 下按 `age` 排序。

```sql
CREATE INDEX idx_name_age ON users (name, age);
```

该索引通常适用于按 `name` 查找，或同时按 `name` 和 `age` 查找。SQL 中条件书写的先后顺序不决定索引列的顺序。

仅按 `age` 查询时，通常无法直接使用这个索引做普通的最左前缀定位；特定版本和查询条件下，优化器可能选择跳跃扫描或全索引扫描。

范围条件通常限制后续索引列继续缩小扫描区间的能力，但后续列仍可能用于索引条件下推、过滤或覆盖查询，应结合执行计划判断。

## 6. 索引成本与验证

索引占用磁盘和缓存空间，插入、删除及相关列更新时也需要维护索引，可能引起页分裂等额外开销。应围绕常用查询的过滤、连接与排序需求设计索引，并评估重复索引的维护成本。

```sql
-- 查看表的索引。
SHOW INDEX FROM users;

-- 查看优化器选择的执行计划。
EXPLAIN SELECT age FROM users WHERE name = 'Alice';
```

检查执行计划时，可以关注所选索引、估计扫描行数及额外操作。估计值不等于实际执行耗时；MySQL 8.0.18 起提供的 `EXPLAIN ANALYZE` 可以显示实际执行信息，但会执行查询，使用时需要考虑查询成本。
