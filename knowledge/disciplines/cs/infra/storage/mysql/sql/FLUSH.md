# FLUSH

FLUSH 是 MySQL 的一组管理语句，根据选项刷新日志、表缓存、权限缓存或部分状态信息。它不是统一的“把所有内存数据写入磁盘”命令。

## 1. 常用选项

| 语句 | 主要用途 |
| --- | --- |
| FLUSH LOGS | 刷新相关日志，各类日志的具体处理方式不同。 |
| FLUSH BINARY LOGS | 轮换二进制日志，关闭当前文件并打开新文件。 |
| FLUSH TABLES | 关闭适用的已打开表并清理相关表缓存，可能等待正在使用表的操作。 |
| FLUSH TABLES WITH READ LOCK | 刷新表并获取全局读锁，限制写入，用于备份等协调。 |
| FLUSH PRIVILEGES | 重新加载授权表，使直接修改授权表等场景下的变更生效。 |
| FLUSH STATUS | 重置或汇总部分状态计数器，具体范围取决于版本和变量。 |

可用选项、所需权限和行为随版本变化，通常需要 RELOAD 或相应的细分管理权限，不能将不同选项视为相同操作。

## 2. 日志刷新

```sql
FLUSH LOGS;
FLUSH BINARY LOGS;
```

对 binlog，刷新通常包含日志轮换；对错误日志、通用查询日志和慢查询日志等，可能是关闭并重新打开文件；对引擎日志则有相应的刷新处理。

因此，“刷新日志”不等于对每一种日志都创建同样的新文件，也不表示清空或删除所有历史日志。清理 binlog 应使用相应的日志清理机制，并考虑复制和恢复需求。

## 3. 表刷新与全局读锁

```sql
FLUSH TABLES;
```

刷新表可能等待正在使用表的操作，并影响后续重新打开表的开销。对于 InnoDB，不能把它当作强制刷出 Buffer Pool 全部脏页的接口。

```sql
FLUSH TABLES WITH READ LOCK;

-- 完成需要全局读锁保护的操作后释放。
UNLOCK TABLES;
```

全局读锁通常阻止普通持久化表的数据修改、相关 DDL 及事务提交等操作，普通读取仍可进行；临时表等存在例外。锁由当前会话持有，连接断开也会释放。

获取过程可能等待正在执行的操作，持锁期间会影响业务写入。它本身不会完成备份文件复制，也不能单独保证整个备份流程正确。

## 4. 权限与状态刷新

```sql
FLUSH PRIVILEGES;
FLUSH STATUS;
```

正常使用 CREATE USER、ALTER USER、GRANT、REVOKE 等账户管理语句后，权限变更会按相应规则生效，通常不需要额外执行 FLUSH PRIVILEGES。直接修改授权表不是日常账户管理的推荐方式。

FLUSH STATUS 不会重启实例，也不会把所有监控指标统一清零。其会话与全局计数处理规则及权限要求应结合版本理解，执行前需考虑对监控基线的影响。

## 5. 与脏页刷盘的区别

InnoDB 更新通常先修改 Buffer Pool 页，形成脏页，再由后台刷页机制按检查点推进、脏页比例及可用空间等因素写回数据文件。

FLUSH TABLES 不是这个过程的统一手动开关，FLUSH LOGS 也不等于将所有数据页刷盘。日志持久化和数据页写回是不同过程，遵循相应的预写日志及恢复规则。

## 6. 与事务提交的关系

FLUSH 不应作为 COMMIT 的替代写法。很多 FLUSH 语句会在执行前导致当前会话事务隐式提交，但存在例外，例如 FLUSH TABLES WITH READ LOCK 和 FLUSH TABLES ... FOR EXPORT。

因此，既不能说“所有 FLUSH 都提交事务”，也不能说“FLUSH 完全不影响事务”。执行管理语句前应明确事务边界，避免把未完成的业务事务意外提交。
