# MySQL 备份

备份保存数据库在某个可恢复状态下的数据、结构及必要元信息，用于应对误删、损坏和故障。在线备份需要建立一致的数据状态，不能将复制文件期间不同时间的数据任意拼接。

## 1. 备份分类

| 维度 | 类型 | 含义 |
| --- | --- | --- |
| 表示方式 | 逻辑备份 | 导出对象定义和数据，例如 mysqldump；恢复通常需要重新执行建表与写入。 |
| 表示方式 | 物理备份 | 复制数据文件及恢复所需日志，例如适配版本的 XtraBackup；依赖文件格式和工具兼容性。 |
| 数据范围 | 全量备份 | 保存所选备份范围内的完整数据基线。 |
| 数据范围 | 增量备份 | 保存相对指定基线的变化，恢复时依赖基线和所需增量链。 |

这些维度可以组合。全量也不必然表示整个实例，可能只覆盖选定数据库或表；恢复前需明确账户、权限、存储过程、事件等对象是否包含在内。

## 2. InnoDB 一致性逻辑备份

InnoDB 可以利用一致性快照导出事务可见的数据。备份事务通过 Read View 判断版本可见性，必要时借助 undo 读取旧版本，即使导出期间其他事务继续提交，也可以保持同一快照。

这不代表备份记录了导出结束时的最新状态。长时间快照还可能阻碍旧版本清理，增加 undo 历史保留和存储压力。

并发 DDL、非事务表和工具选项可能破坏预期的一致性保障。不能只开启一个快照选项，就假设所有数据库对象都获得同样保护。

## 3. 数据基线与 binlog 位点

为了接续时间点恢复，备份工具还需使数据状态与 binlog 文件位置或 GTID 集合建立一致对应关系。

逻辑备份的典型协调方式可以简化为：

1. 建立短暂的受保护窗口，阻止相关提交推进。
2. 在该窗口内建立一致性快照，并记录对应日志坐标。
3. 解除保护，让业务继续写入。
4. 持续读取已建立的快照，完成导出。

具体加锁及取位点顺序由工具和版本决定；上面描述的是需要保证的关系，不是所有工具通用的命令步骤。

```text
快照已包含的事务 A、B │ 后续事务 C、D
                     ↑
              备份对应的日志坐标
```

快照数据包含 A、B，即使导出期间 C、D 已提交，导出仍读取原快照。恢复后从对应坐标重放 C、D，避免重复或遗漏。

Read View 本身不包含 binlog 位点，对应关系由备份工具协调建立。不能在导出完成后随意查询当前位点作为恢复起点。

## 4. 物理热备份与 prepare

物理热备份期间复制的数据页可能来自不同时间，工具还需收集相关 redo，并在恢复准备阶段进行日志应用等处理，将备份整理为可恢复状态。

备份工具的 prepare 不等同于事务两阶段提交的 prepare。物理备份的锁定、日志坐标和增量合并流程需要遵循具体工具要求，不能照搬逻辑快照流程。

## 5. 时间点恢复

```text
恢复可用的全量备份
        ↓
按工具要求准备或合并所需增量
        ↓
从备份对应坐标重放后续 binlog
        ↓
在目标事务边界停止并验证数据
```

日志用途、位点与保留策略见 [binlog](../../logs/Binlog.md)。binlog 启用后持续记录变更，不是全量备份之后才开始记录；恢复使用的是与该备份衔接的日志部分。

必须保留从备份到恢复目标的完整所需日志链。GTID 能标识事务，但不能补回丢失的日志。目标时间可以帮助定位，最终仍需确认事务边界，避免应用误操作事务。

## 6. 查看位置与备份元信息

```sql
-- MySQL 8.4：查看当前 binlog 状态。
SHOW BINARY LOG STATUS;

-- MySQL 8.0 中对应的命令。
SHOW MASTER STATUS;
```

以上为不同版本的命令示例，不是要求在同一实例依次执行。在并发写入时，单独查询当前位置不能保证其与另一份备份一致；恢复应使用工具生成并验证的备份元信息。

## 7. 保留与恢复验证

备份与日志应结合 RPO、RTO 制定保留和归档策略，避免与源库处于同一故障域。还需确保加密密钥、权限、配置和工具版本在恢复环境可用。

定期在独立环境恢复备份并接续日志，校验关键业务数据，记录恢复耗时。只有备份任务成功或文件存在，不能证明备份链可以恢复。
