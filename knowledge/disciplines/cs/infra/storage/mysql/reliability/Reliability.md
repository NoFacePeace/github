# MySQL 可靠性

MySQL 可靠性关注故障下的数据安全、服务连续性和恢复能力，需要结合事务持久性、冗余复制、备份及容灾设计。单一机制无法覆盖进程崩溃、节点故障、误操作和地域故障等所有情况。

## 1. 知识入口

- [备份](backup/Backup.md)：逻辑与物理备份、一致性快照、binlog 位点衔接及恢复验证。

## 2. 高可用、备份与容灾

| 方向 | 主要目标 | 典型手段与边界 |
| --- | --- | --- |
| 事务持久性 | 提交的数据在约定故障范围内可恢复。 | redo、提交协调和刷盘策略，需要可靠存储配合。 |
| 高可用 | 节点故障后尽量保持服务可用。 | 冗余副本、故障检测、流量切换与防止双写。 |
| 备份恢复 | 找回可用的数据状态。 | 独立备份、日志归档、时间点恢复和恢复演练。 |
| 容灾 | 在机房、地域故障等情况下恢复服务与数据。 | 跨故障域部署、备份与切换预案，覆盖数据库和应用依赖。 |

复制可能同步误删或错误修改，不能替代独立备份。备份也不直接提供故障时的自动接管能力，恢复可能需要较长时间。

## 3. 恢复目标

| 指标 | 含义 | 影响因素 |
| --- | --- | --- |
| RPO（恢复点目标） | 可容忍的数据丢失时间窗口。 | 复制方式、备份与日志归档频率，以及故障时可访问的数据。 |
| RTO（恢复时间目标） | 可容忍的服务恢复时长目标。 | 故障检测、数据恢复、日志重放、校验和应用切换耗时。 |

应先按业务定义目标，再选择方案。不能仅凭“有副本”或“每天有备份”断言达到零丢失或快速恢复。

## 4. 验证与运维

持续检查备份成功率、日志链完整性、复制延迟和存储容量，并通过演练测量实际恢复时间及数据缺口。

恢复预案还需涵盖访问权限、密钥、配置、网络和应用切换。备份文件存在不等于一定可恢复，验证应包含完整还原、必要的日志重放及业务校验。
