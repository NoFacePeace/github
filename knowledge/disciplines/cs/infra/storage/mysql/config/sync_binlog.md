# sync_binlog

sync_binlog 控制 MySQL 对 [binlog](../logs/Binlog.md) 执行同步刷盘的频率。将事件写到文件的操作系统缓存，不等于已持久化到存储设备。

## 1. 作用域与默认值

| 属性 | MySQL 8.0 / 8.4 |
| --- | --- |
| 默认值 | 1。 |
| 作用域 | GLOBAL。 |
| 动态修改 | 支持，需相应管理权限。 |
| 取值 | 0 或正整数。 |

MySQL 从 5.7.7 起默认值为 1；更老版本的默认值不能直接套用。

## 2. 不同取值

| 值 | 行为 | 影响 |
| --- | --- | --- |
| 0 | 不由该策略主动同步 binlog，依赖操作系统等刷新机制。 | 系统崩溃或掉电时可能丢失尚未持久化的日志。 |
| 1 | 每个 binlog 提交组同步一次，再继续相应引擎提交。 | 常用的强持久性设置，可由组提交分摊同步开销。 |
| N，大于 1 | 按 N 个 binlog 提交组的间隔执行同步。 | 降低同步频率，但可能丢失上次同步之后的已提交日志。 |

一个提交组可以包含多个事务，因此值为 N 不等于严格每 N 个事务同步，也不能按 N 精确推断最多丢失多少事务。还需考虑其他刷新和故障条件。

## 3. 查看与修改

```sql
SELECT @@GLOBAL.sync_binlog;

-- 修改运行值。
SET GLOBAL sync_binlog = 1;

-- MySQL 8.0：修改运行值并持久化。
SET PERSIST sync_binlog = 1;
```

两种设置方式按需求选择。修改前应记录原值，并评估提交延迟、存储同步能力和可靠性目标。

## 4. 与 redo 及恢复的关系

sync_binlog 不负责 redo log 的持久化。通常与 innodb_flush_log_at_trx_commit = 1 配合，保障提交协调所需的两种日志。

如果 binlog 在故障后缺失，即使部分引擎修改仍可恢复，复制和时间点恢复也可能缺少相应事务。不能仅因为正常运行时收到提交成功，就认定放宽同步后的日志链在掉电后仍完整。
