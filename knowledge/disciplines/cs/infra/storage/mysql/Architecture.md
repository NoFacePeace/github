# MySQL 架构

MySQL 的整体架构主要分为 Server 层和存储引擎层。客户端发送 SQL，Server 层负责解析、优化和执行，存储引擎负责具体的数据读写。

## 1. 整体分层

```text
客户端（应用、命令行）
        │ SQL
        ▼
Server 层
  连接管理 → SQL 解析 → 查询优化 → 执行器
        │ 调用存储引擎接口
        ▼
存储引擎层（通常是 InnoDB）
  索引、数据读写、事务、锁、崩溃恢复
        │
        ▼
磁盘文件（数据、索引、日志）
```

Server 层提供各存储引擎共用的能力，存储引擎层决定数据如何组织、访问与持久化。以下以常用的 InnoDB 为例介绍存储引擎层。

- [MySQL 存储引擎](StorageEngines.md)：常见引擎的差异，以及通用机制与 InnoDB 实现的关系。

## 2. Server 层

| 组件 | 主要职责 |
| --- | --- |
| 连接与权限管理 | 建立连接、验证身份，并在执行过程中检查操作权限。 |
| 解析器 | 检查 SQL 语法并生成语法结构，供后续语义解析与优化使用。 |
| 优化器 | 选择执行计划，例如使用哪个索引、按什么顺序连接表。 |
| 执行器 | 按执行计划调用存储引擎接口，处理并返回结果。 |
| binlog | 记录数据变更，主要用于复制和按时间点恢复。 |

binlog 属于 Server 层，与 InnoDB 的 redo log 分工不同：binlog 服务于复制和恢复，redo log 服务于存储引擎的崩溃恢复。

## 3. InnoDB 存储引擎层

### 3.1 Buffer Pool

Buffer Pool 在内存中缓存数据页和索引页。读取时优先访问缓存，未命中时从磁盘加载；修改产生的脏页由后台机制刷回磁盘，以减少直接磁盘访问。

### 3.2 数据与索引

InnoDB 使用 B+ 树组织常见索引：

- **聚簇索引**：通常以主键组织，叶子节点存储完整行数据。
- **二级索引**：叶子节点存储索引列和主键值；查询需要其他列时，通常还要通过主键访问聚簇索引，这个过程称为回表。

数据和索引以页为单位管理，并持久化到表空间文件中。

### 3.3 事务、锁与 MVCC

- **事务**：将多个操作组织为一个逻辑单元，支持提交和回滚。
- **锁**：协调并发读写，例如通过记录锁、间隙锁和临键锁控制冲突。
- **MVCC**：结合历史版本与 Read View，在适用的隔离级别下实现一致性读，减少读写之间的阻塞。

### 3.4 redo log 与 undo log

| 日志 | 主要作用 |
| --- | --- |
| redo log | 记录页修改相关信息，通过预写日志机制支持崩溃恢复；持久性保障取决于日志刷盘配置等条件。 |
| undo log | 保存撤销修改所需的信息，用于事务回滚，并为 MVCC 提供历史版本。 |

启用 binlog 时，MySQL 通过内部两阶段提交协调 InnoDB 与 binlog，避免崩溃恢复后两者的事务提交状态不一致。

## 4. 查询执行流程

以以下 SQL 为例，假设 `id` 是主键：

```sql
SELECT * FROM users WHERE id = 10;
```

1. 客户端建立连接并通过身份验证后，发送 SQL。
2. Server 层解析 SQL，解析表和列，并完成相关权限检查。
3. 优化器选择使用主键索引的执行计划。
4. 执行器调用 InnoDB，按主键查找记录。
5. InnoDB 通过 B+ 树定位数据页，优先从 Buffer Pool 读取；缓存未命中时从磁盘加载，并按事务可见性规则返回记录。
6. 执行器将查询结果返回客户端。

## 5. 版本说明

旧架构图中的 Query Cache（查询缓存）已在 MySQL 8.0 中移除。Query Cache 缓存的是查询结果，InnoDB Buffer Pool 缓存的是数据页和索引页，两者是不同的机制。
