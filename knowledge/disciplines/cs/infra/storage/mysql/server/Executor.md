# MySQL 执行器

## 1. 职责与位置

执行器位于 Server 层，按照优化器生成的[执行计划](ExecutionPlan.md)组织实际执行。它调用存储引擎接口访问记录，并完成计划中的过滤、连接、聚合、排序和结果输出等操作。

优化器决定采用什么方案，执行器落实这个方案；执行器不会简单地在读取每行时重新选择一个索引。

## 2. 与存储引擎的分工

| 层次 | 主要职责 |
| --- | --- |
| 执行器 | 驱动扫描、组合各执行操作、计算表达式、处理结果并返回客户端。 |
| 存储引擎 | 根据接口请求定位和访问记录，实现具体的数据组织、并发控制及持久化。 |

例如使用 InnoDB 时，B+ 树查找、Buffer Pool 页读取、MVCC 可见性判断和行锁等由存储引擎实现。执行器不直接按文件偏移读取表数据。

过滤并不都发生在执行器：适用条件可以通过索引条件下推等机制交给存储引擎提前判断，减少读取或传递的记录。

## 3. 查询执行示例

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    age INT NOT NULL,
    INDEX idx_age (age)
) ENGINE = InnoDB;

SELECT name FROM users WHERE age = 20 LIMIT 10;
```

假设计划选择 idx_age，执行过程可以简化为：

1. 初始化相关执行节点和存储引擎访问状态。
2. 请求 InnoDB 定位 age 为 20 的索引记录，并读取查询需要的行数据。
3. 按计划计算表达式、检查仍需处理的条件，并生成输出行。
4. 继续请求后续匹配记录，直到产生 10 行或数据耗尽。
5. 结束访问并释放语句执行过程中持有的相关资源；事务锁等资源仍按事务规则管理。

idx_age 不包含 name，InnoDB 通常需要回表读取该列。这个例子没有 ORDER BY，因此不保证返回哪 10 条匹配记录。

## 4. 迭代执行模型

MySQL 8.0 的现代查询执行框架大量采用迭代器模型。可以将一个计划理解为多个执行节点组成的树：上层节点向下层请求下一条记录，下层完成相应工作后返回记录、结束或错误。

```text
Limit：最多返回 10 行
          ↓ 请求记录
索引访问：通过 idx_age 读取匹配行
          ↓
InnoDB
```

实际节点和接口随版本及语句类型不同，不是所有 SQL 都能用这一简图完整表示。

## 5. 流式处理与阻塞操作

过滤等操作通常可以逐行处理，多表连接按照所选算法驱动输入。排序、某些聚合以及需要物化的中间结果，则可能先收集数据再向上输出。

因此，存在 LIMIT 不代表一定只读取相同数量的记录：过滤可能丢弃候选行，排序也可能需要先读取大量输入。是否能提前结束取决于执行计划。

结果可以逐步发送给客户端，不必总是等所有结果生成后一次性返回；需要排序等处理时，首行返回时间可能较长。

## 6. 数据修改语句

对于 UPDATE、DELETE 等语句，Server 层按计划定位目标记录、处理表达式和相关检查，并通过存储引擎接口请求修改。INSERT 则根据输入构造记录并请求写入。

InnoDB 在此过程中处理相关锁、undo 和 redo 等机制；Server 层参与 binlog 记录与事务协调。修改不是执行器直接改写数据文件。

## 7. 观察实际执行

EXPLAIN 展示计划和估计值；MySQL 8.0.18 起，EXPLAIN ANALYZE 可以实际执行查询，显示执行节点的行数、循环次数与耗时。

```sql
EXPLAIN ANALYZE
SELECT name FROM users WHERE age = 20 LIMIT 10;
```

分析时应结合节点层次和 loops 判断工作量，不能简单相加节点耗时。EXPLAIN ANALYZE 会执行查询，需要考虑查询本身的资源开销。
