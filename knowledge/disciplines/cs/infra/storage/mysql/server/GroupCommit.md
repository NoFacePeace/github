# MySQL 组提交

组提交（Group Commit）将多个事务的部分提交工作批量处理，尤其让它们共用日志写入与同步操作，以减少每个事务单独刷盘的开销。各事务仍保持独立的事务边界，不会合并成一个业务事务。

## 1. 与两阶段提交的关系

[两阶段提交](../innodb/transactions/TwoPhaseCommit.md)协调 InnoDB 与 binlog 的提交结果；组提交则优化这些工作如何批量完成。开启 binlog 时，Server 层协调组提交，InnoDB 配合完成 redo 持久化与引擎提交。

事务仍需依次满足准备、持久化提交决策、引擎提交等依赖关系，不能为了批量处理而跳过一致性保障。放宽刷盘配置时，故障下的持久性保障也随之改变。

## 2. 提交阶段

以启用 binlog、innodb_flush_log_at_trx_commit = 1、sync_binlog = 1 的常见场景理解，事务进入 InnoDB prepare 后，Server 的有序提交流程通常分为以下阶段：

| 阶段 | 主要工作 |
| --- | --- |
| Flush | 收集事务，批量将各事务的 binlog 缓存写入 binlog 文件，并协调满足所需 redo 的持久化要求。 |
| Sync | 根据 sync_binlog 策略同步 binlog；值为 1 时，每个提交组要求完成同步。 |
| Commit | 完成相应事务的存储引擎提交，随后按流程返回结果。 |

这里 Flush 是阶段名称，不意味着每次文件写入都已经持久化。关键顺序是：在 binlog 提交决策按强持久性要求完成同步前，所需 redo 和准备状态已具备恢复保障；随后完成引擎提交。

不同版本的阶段划分、线程协作和内部调用可能调整，这个表不等于固定的源码调用顺序。各阶段可以流水处理不同批次，批量大小也不是固定值。

## 3. redo 与 binlog 分别刷盘

组提交流程会同时协调两种日志，但它们是不同的日志文件与持久化操作。一次 redo 同步不能替代 binlog 同步，反之亦然。

redo 按 LSN（日志序列号）向前推进。例如三个事务需要的持久化位置分别为 100、120、150，一次将 redo 持久化到 150，就覆盖了它们各自的 redo 要求，不需要为每个事务重复同步同一日志前缀。

这只说明 redo 持久化条件已满足，不代表三个事务已经完成全部提交步骤。它们还需满足各自的 binlog 与引擎提交要求。

一次 redo 刷盘可能覆盖更多事务产生的日志，包括尚未提交的日志，因此 redo 的覆盖范围不必与某个 binlog 提交组一一对应。即使关闭 binlog，InnoDB 仍可合并多个事务的 redo 刷盘需求。

## 4. 是否会主动等待

多个事务在并发到达、排队和日志 I/O 期间，可以自然形成批次，并不要求每次固定等待一段时间。

| 配置 | 作用 |
| --- | --- |
| binlog_group_commit_sync_delay | 在同步阶段引入收集更多事务的延迟，单位微秒，MySQL 8.0 / 8.4 默认 0。 |
| binlog_group_commit_sync_no_delay_count | 达到设定事务数时，可以提前结束上述延迟；默认 0 表示不使用该数量阈值。 |

主动延迟可能增加批量和吞吐，也会增加提交延迟；实际效果还取决于并发量、同步策略和存储性能。默认延迟为 0 也不代表提交没有排队或 I/O 等待。

## 5. 持久性与性能

innodb_flush_log_at_trx_commit = 1 表示每个事务提交都要满足相关 redo 已持久化的要求，不表示每个事务必须单独执行一次 fsync。

sync_binlog = 1 表示每个 binlog 提交组要求同步，而非每个事务独占一次同步。组提交因此可以在保持相应持久性要求的同时分摊 I/O 开销，前提仍是操作系统和存储正确兑现持久化请求。

评估效果时，应同时观察提交延迟、吞吐、并发量和日志同步耗时。扩大批次可能改善吞吐但增加尾延迟，不能只比较每秒事务数。
