# MySQL 存储引擎

存储引擎负责 MySQL 表的数据组织、索引访问和读写操作。不同引擎在事务、锁、缓存和恢复机制上的支持不同；现代 MySQL 的业务系统通常使用默认存储引擎 InnoDB。

## 1. 与 Server 层的分工

Server 层负责连接管理、SQL 解析、查询优化、执行调度和 binlog。执行器通过存储引擎接口访问表，由引擎完成具体的数据操作。

存储引擎以表为单位选择，同一个数据库可以包含使用不同引擎的表。事务能否回滚取决于参与操作的表所使用的引擎，不能因为 MySQL 支持事务，就认为所有表都支持事务。

## 2. 常见存储引擎

| 引擎 | 事务 | 并发控制 | 数据存储与主要用途 |
| --- | --- | --- | --- |
| [InnoDB](innodb/InnoDB.md) | 支持 | 支持行级锁和 MVCC，也使用表级锁等机制 | 持久化存储，适用于常见业务数据和事务处理。 |
| MyISAM | 不支持 | 主要使用表级锁，不支持 MVCC | 持久化存储，常见于历史系统，现代业务通常优先选择 InnoDB。 |
| MEMORY | 不支持 | 表级锁，不支持 MVCC | 行数据保存在内存中，重启后丢失；适用于可重建的临时数据，支持 HASH 和 BTREE 索引。 |

MEMORY 表与 MySQL 执行查询时自动创建的内部临时表不是同一个概念；内部临时表使用的引擎取决于版本和配置。

## 3. 为什么主流资料通常讲 InnoDB

InnoDB 从 MySQL 5.5 起成为默认存储引擎，支持事务、崩溃恢复和高并发访问，是现代业务系统最常用的选择。因此，资料中讨论以下机制时，通常默认采用 InnoDB：

- Buffer Pool 的页缓存与脏页刷盘。
- 主键聚簇索引、二级索引和回表。
- 行锁、间隙锁、临键锁和 MVCC。
- redo log、undo log 和事务恢复。

SQL 解析、优化器、执行器和 binlog 则属于 Server 层，不能归为 InnoDB 内部组件。

## 4. 通用机制与 InnoDB 实现

这些技术并非由 InnoDB 独占，需要区分通用概念和具体实现。

| 机制 | 通用概念 | InnoDB 的具体实现 |
| --- | --- | --- |
| 内存页缓存 | 缓存数据与索引，减少磁盘访问。 | 使用 Buffer Pool 缓存数据页和索引页。 |
| B+ 树索引 | 使用树形结构组织索引，加速查找。 | 聚簇索引叶子节点存储完整行，二级索引叶子节点包含主键值。 |
| 事务与锁 | 保证操作的事务语义，协调并发冲突。 | 支持事务和多种锁，具体加锁行为受语句、索引及隔离级别等因素影响。 |
| MVCC | 通过多个版本实现并发访问和一致性读取。 | 结合 undo log 中的历史版本与 Read View 判断记录可见性。 |
| 重做日志 | 在故障后重做修改，支持恢复。 | 使用 redo log 配合预写日志机制进行崩溃恢复。 |
| 撤销日志 | 保存撤销修改所需的信息。 | 使用 undo log 支持事务回滚和 MVCC 历史版本读取。 |

其他引擎可能采用类似机制，也可能使用不同实现。例如，MyISAM 具有树形索引，但不支持事务和 MVCC，也没有 InnoDB 的 redo/undo 日志机制。支持 MVCC 的数据库也不一定使用 undo log 保存历史版本。

## 5. 查看与指定存储引擎

```sql
-- 查看当前实例支持的引擎及默认引擎。
SHOW ENGINES;

-- 查看默认存储引擎配置。
SHOW VARIABLES LIKE 'default_storage_engine';

-- 查看已有表的定义，其中包含 ENGINE 信息。
SHOW CREATE TABLE users;

-- 创建表时显式指定引擎。
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100) NOT NULL
) ENGINE = InnoDB;
```
