# binlog

binlog（Binary Log，二进制日志）是 MySQL Server 层以事件形式记录数据变更等信息的日志。它主要用于复制和结合备份进行时间点恢复，不属于 InnoDB 专有日志。

## 1. 记录内容与格式

binlog 通常记录 INSERT、UPDATE、DELETE 和 DDL 等变更，不记录普通 SELECT。日志过滤、会话设置、存储引擎和语句类型会影响具体记录行为，不能将它当作完整的访问审计日志。

| 格式 | 内容 |
| --- | --- |
| STATEMENT | 以语句事件记录变更。 |
| ROW | 以行事件记录数据变化，包含哪些字段受 binlog_row_image 等配置影响。 |
| MIXED | 根据语句特征选择语句或行格式。 |

可用格式、默认值及弃用情况随版本变化。ROW 不是数据页的物理副本，binlog 也不是可直接按文本执行的 SQL 文件；查看事件通常使用 mysqlbinlog 等工具。

## 2. 没有副本时的用途

没有副本，binlog 仍可用于时间点恢复。例如凌晨有一份全量备份，下午误删数据，可以先恢复备份，再重放后续日志至误删事务之前。

CDC、数据同步等系统也可以消费 binlog。是否保留日志，应同时考虑复制、变更订阅和恢复需求，不能只根据当前是否配置副本决定。

## 3. 全量备份与数据基线

binlog 启用后持续记录，不是做完全量备份才开始记录。恢复时使用的是与该备份相衔接的那部分日志：

```text
一致的全量备份
      +
从备份对应坐标开始的后续 binlog
      ↓
恢复到目标事务边界
```

全量备份提供数据基线，后续 binlog 补齐变更。单独的 binlog 通常不能替代完整备份，单独的旧备份也不能提供备份之后的修改。

## 4. 基线如何对齐

备份工具需要让备份数据与日志坐标建立一致关系，不能只按备份时间估算恢复起点。

| 坐标方式 | 含义 |
| --- | --- |
| binlog 文件名与 position | 标记备份状态对应的日志位置，恢复后从匹配位置继续应用变更。 |
| GTID 集合 | 标识备份状态已经执行的事务，配合恢复工具选择和跳过相应事务。 |

例如备份记录 mysql-bin.000123 的位置 456789，恢复流程就应使用这份备份对应的坐标，避免重复或遗漏事务。GTID 不保存事务数据，也不能补齐已经丢失的日志。

工具通过一致性快照、锁定或备份协调等机制建立对应关系。物理热备份还可能需要先执行 prepare，利用备份中的 redo 整理数据页。不能在备份结束后随意查询当前位点，充当该备份的恢复起点。

恢复必须保留完整日志链，并确认目标事务边界；时间戳可以帮助定位，但不能替代事务和位点检查。

## 5. 与 redo 的协调

redo 主要用于 InnoDB 崩溃恢复，binlog 主要用于复制和时间点恢复。两者通过内部两阶段提交协调同一事务的提交结果，不要求日志内容相同。

在相关 redo 与准备状态已持久化、binlog 也具有完整持久提交记录的前提下，即使崩溃时 InnoDB 尚未完成 commit，恢复时也可完成提交。数据修改仍由引擎恢复机制处理，不是通过 binlog 替代 redo 恢复数据页。

sync_binlog = 1 时，每个 binlog 提交组要求同步刷盘；通常配合 innodb_flush_log_at_trx_commit = 1 及可靠存储保障持久性。放宽配置后，不能仅凭正常运行时返回提交成功就推断掉电后的所有日志都完整保留。

## 6. 轮换、过期与清理

binlog 会轮换为多个文件，不是始终写入一个无限增长的文件。若没有有效清理策略，总占用仍会持续增长；轮换本身不会删除历史文件。

MySQL 8.0、8.4 中，binlog_expire_logs_seconds 默认通常为 2592000 秒，即 30 天；实例配置及自动清理开关可能改变实际行为。MySQL 5.7 的 expire_logs_days 默认值为 0，表示不按天自动过期。

过期清理通常在启动、日志轮换等时机触发，不保证到期立即删除，也不是磁盘容量上限。单个文件大小受 max_binlog_size 等影响，但事务通常不拆分到多个文件，因此大事务可能使文件超过该值。

```sql
-- 查看当前保留策略；变量支持范围取决于版本。
SHOW GLOBAL VARIABLES LIKE 'binlog_expire_logs_seconds';
SHOW GLOBAL VARIABLES LIKE 'binlog_expire_logs_auto_purge';

-- 手动清理示例：删除指定文件之前的日志，保留该文件及其后文件。
PURGE BINARY LOGS TO 'mysql-bin.000123';
```

清理前应确认副本、CDC 和备份恢复都不再依赖这些文件。即使没有副本，也要保留从可用备份到目标恢复点的完整链，或确认已有可读取的完整日志归档。不要直接从文件系统删除 binlog 文件。

## 7. 查看配置与日志

```sql
SHOW GLOBAL VARIABLES LIKE 'log_bin';
SHOW GLOBAL VARIABLES LIKE 'binlog_format';
SHOW GLOBAL VARIABLES LIKE 'sync_binlog';
SHOW GLOBAL VARIABLES LIKE 'max_binlog_size';
SHOW BINARY LOGS;
```

这些命令用于确认启用状态、记录格式、持久化策略和文件列表，执行结果受版本与权限影响。保留时间、写入量及归档速度需要结合磁盘监控评估，并通过恢复演练验证备份与日志链可用。
