# Lag

Lag（消费积压）衡量消费进度距离分区末尾有多远。消费组和消费者客户端分别用已提交进度和当前读取进度计算 lag。

## 1. 消费组的 lag

```text
Lag = 日志末尾 offset − 消费组已提交 offset
```

消费组的 lag 按 `group.id + Topic + 分区` 计算。分区末尾位置见 [Offset](Offset.md)。更换负责分区的消费者时，只要末尾位置和已提交位置都没变，消费组的 lag 就保持不变。

如果消费组的 lag 持续上升，说明分区末尾比已提交位置前进得更快。

## 2. 消费者的读取 lag

Java 消费者客户端的分区指标 `records-lag` 以实例的当前读取位置（position）为基准。它衡量该实例的下一次读取位置距离客户端可读取的分区末尾还有多远。分区末尾保持不变时，`poll()` 推进 position 会降低读取 lag，提交更靠后的 offset 会降低消费组的 lag。

## 3. 对比示例

假设 `orders-0` 在 CLI 和客户端看到的分区末尾都是 `50`。`group-a` 的已提交 offset 是 `43`，消费者 A 已经通过 `poll()` 拿到了 `43` 到 `49` 的记录，position 已推进到 `50`。

| 指标 | 计算 |
| --- | --- |
| 消费组的 `LAG` | `50 - 43 = 7` |
| 消费者 A 的 `records-lag` | `50 - 50 = 0` |

如果消费者 B 此时接管分区，会从 `43` 恢复读取。提交 `50` 后，在分区末尾仍为 `50` 的情况下，消费组的 lag 就会降到 `0`。
