# Seatbelt

Seatbelt 是 macOS 的沙箱机制，可以对进程访问文件、网络及其他系统能力施加限制。程序仍在本机运行，不要求创建容器或独立虚拟机。

## 1. 工作原理

宿主根据所需权限准备沙箱策略，在启动程序时应用。程序访问受控资源时，由系统按策略允许或拒绝，而不是依赖程序自觉遵守。

沙箱限制通常会随进程创建传递给子进程。它不自动约束无关进程或远程服务，因此需要确认实际执行操作的进程是否处于限制之内。

## 2. sandbox-exec

`sandbox-exec` 是使用策略启动命令的入口之一：

```sh
sandbox-exec -f profile.sb /path/to/program argument
```

| 参数 | 含义 |
| --- | --- |
| `-f profile-file` | 从文件读取策略 |
| `-p profile-string` | 直接传入策略文本 |
| `-D key=value` | 设置策略参数 |

当前 macOS 手册已将 `sandbox-exec` 标记为弃用，并建议应用开发者采用 App Sandbox。命令弃用不等于系统沙箱能力已被移除；命令可用性与策略兼容性需要按系统版本确认。

## 3. 策略示例

策略通常采用类似 Scheme 的表达式。下面仅用于展示禁止网络的写法：

```scheme
(version 1)
(allow default)
(deny network*)
```

这里默认允许其他操作，不构成完整的最小权限策略，也没有限制文件写入。生产用途需要按程序依赖和资源范围设计并验证策略。

文件策略可围绕具体路径及读写操作配置。允许写入的路径仍是真实文件系统中的路径；策略不会自动创建工作目录副本。

## 4. 限制边界

- Seatbelt 的访问限制不等于容器的独立文件系统或虚拟机隔离。
- 文件访问限制不等于 CPU、内存和执行时长配额，其他资源控制需要另行配置。
- 域名允许列表不能仅靠命令名称判断，可能需要受控代理等网络机制配合。
- 系统已有权限仍然适用，沙箱中的允许规则不能直接授予运行账号原本没有的权限。

## 5. 与审批的关系

Seatbelt 负责执行资源限制，本身不负责展示用户审批界面。访问被拒绝后，宿主可以报告失败，或发起权限申请，再按获批范围选择执行方式。

批准不会自动修改已经运行进程的沙箱策略。具体系统是否重启命令、重新启动执行环境或使用其他授权路径，需要查看宿主实现。
