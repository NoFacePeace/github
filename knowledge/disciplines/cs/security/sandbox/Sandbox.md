# 沙箱

沙箱（Sandbox）是对程序执行施加隔离与访问限制的机制，用于约束程序能够影响的资源。它是通用系统安全技术，可用于浏览器、应用、代码执行平台和 Agent，不要求使用容器或独立虚拟机。

## 1. 基本原理

宿主在程序执行前配置资源边界，再由操作系统、隔离环境或受控服务检查实际访问。程序尝试读写文件、连接网络或使用系统能力时，超出边界的操作会被拒绝。

不必先理解程序的全部代码，才能限制其影响范围。执行前分析可以识别预计行为，执行时的强制限制则约束未被提前识别的行为。

典型过程为：

```text
确定资源边界
  ↓
以受限权限启动程序
  ↓
程序请求访问资源
  ├─ 符合策略 → 允许访问
  └─ 超出边界 → 拒绝访问
```

只要求程序遵守提示词或自行检查，不构成独立的强制隔离。限制还应覆盖子进程及其他可能的访问路径，具体保证取决于实现。

## 2. 限制对象

| 对象 | 常见限制 |
| --- | --- |
| 文件系统 | 可见路径、只读或可写目录、挂载和临时空间 |
| 网络 | 是否允许连接、目标地址、端口、协议和受控代理 |
| 进程与系统能力 | 进程可见性、系统调用、提权和设备访问 |
| 计算资源 | CPU、内存、磁盘、进程数量和执行时间 |
| 凭据 | 只提供必要的环境变量、令牌或权限受限账号 |

这些能力不一定由同一个组件提供。沙箱、资源配额、凭据管理和服务端权限可以共同构成执行边界。

## 3. 实现方式

### 3.1 操作系统级限制

进程可以直接在本机运行，由系统限制其资源访问。例如 macOS [Seatbelt](Seatbelt.md) 可限制文件和网络操作，Linux 可使用 [Bubblewrap](Bubblewrap.md) 构造隔离环境，并结合 seccomp 等机制。

不同机制能力不同：文件访问限制、系统调用过滤和资源视图隔离不能互相等同。

### 3.2 容器

容器通过文件系统挂载、namespace、运行账号、能力限制和 cgroup 等机制组织受限环境。进程、文件、网络隔离与资源配额需要分别配置。

容器通常与宿主共享内核，并非天然具有虚拟机相同的隔离边界。

### 3.3 虚拟机与 microVM

虚拟机通过虚拟化运行独立操作系统，将程序与宿主内核分开。microVM 以精简设备和运行环境降低开销，适合需要快速创建的隔离执行场景。

共享目录、网络、设备和凭据仍需要配置，使用虚拟机不代表自动消除所有外部影响。

## 4. 工作目录与真实文件

沙箱不一定复制工作目录。它可以允许进程直接修改宿主的指定目录；容器也可以通过可写挂载访问真实文件。

因此，沙箱内的修改可能立即反映到真实仓库。是否影响宿主文件，取决于路径映射、读写权限及是否使用副本，而不是环境是否称为沙箱。

## 5. 网络与外部服务

整体禁止联网可以通过系统网络限制实现；按域名控制通常需要代理或其他网络策略，并确保不存在未受控的直连路径。仅设置 `HTTP_PROXY` 等环境变量，不能保证程序无法绕过代理。

本地沙箱只能约束其覆盖的执行路径。远程工具通过 API 修改数据库、发送邮件等操作，需要服务端账号权限和业务控制；本地文件限制不能直接约束远程服务内部行为。

本地工具服务若是另行启动的进程，也不应默认认为会继承调用方的沙箱。需要确认其启动方式、运行账号和隔离配置。

## 6. 与权限和审批的关系

权限策略规定允许访问的资源，沙箱负责强制落实适用的执行限制。审批处理是否授予某次操作所需权限，是宿主系统的流程。

沙箱拒绝访问后，不一定能够暂停请求并原地继续。某些系统先让操作失败，再申请权限并重试；另一些通过受控代理支持等待审批后继续。

批准操作不代表任意扩大执行权限。宿主应按批准范围落实权限，并保留其他适用限制。
