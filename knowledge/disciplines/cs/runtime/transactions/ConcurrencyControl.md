# 并发控制

事务并发控制（Concurrency Control）协调多个事务的读写，使可见性、冲突处理和提交结果满足系统承诺的隔离保证。

## 1. 需要控制什么

并发事务可能访问相同记录，也可能通过不同记录形成关联依赖。并发控制需要管理读取版本、冲突写入、约束检查与提交验证，避免不允许的执行结果。

仅仅保证单次写入不可分割，不足以保证多步事务正确；仅检测同一行写冲突，也不一定能防止跨记录的写偏斜。

## 2. 常见策略与机制

| 策略或机制 | 核心思路 |
| --- | --- |
| [悲观并发控制](PessimisticConcurrencyControl.md) | 在访问过程中先获取适当的锁或预留资源，阻止冲突操作直接并行进行。 |
| [乐观并发控制（OCC）](OptimisticConcurrencyControl.md) | 先读取并计算，在验证或提交阶段检查冲突，不满足条件则中止或重试。 |
| [多版本并发控制（MVCC）](MVCC.md) | 保存或重建多个版本，为读取选择符合可见性规则的版本，减少读写阻塞。 |

这些并非完全互斥的方案。MVCC 可以与锁或乐观验证配合，具体系统也可能对不同操作采用不同策略。

## 3. 乐观并发控制与乐观锁

“乐观锁”常指版本号条件更新等做法，更准确的上位名称是乐观并发控制。核心是验证读取依据是否仍然有效，而不是获取一把名为“乐观”的锁。

例如，应用读取对象的版本为 3，提交时仅在版本仍为 3 的条件下更新，并将版本改为 4。条件不满足时，需要重新读取和判断，而不是直接覆盖。

这种做法不保证底层完全不加锁，也不自动实现整个事务的可串行化。单行版本检查只保护其明确验证的范围。

## 4. 与隔离性的关系

隔离性描述系统承诺什么，并发控制描述如何协调执行以实现这些承诺。同一种机制可以提供不同程度的隔离，同一级别也可以采用不同机制实现。

MVCC 不自动等于可串行化，使用锁也不等于所有事务必须物理串行执行。需要结合读取、写入和验证规则判断。

## 5. 冲突与重试

悲观策略可能产生等待和死锁，乐观策略可能在验证时失败并重试。高竞争下，重复读取与计算的成本可能较高；低竞争下，乐观策略可能减少长时间持锁。

重试必须重新检查状态，并处理幂等性与外部副作用。不能无条件重复发送消息或支付请求，也不能简单重放基于过期读取计算出的绝对值。

## 6. 选择依据

应根据业务不变量、冲突概率、事务长度、热点分布和实现提供的保证选择策略。简单计数或扣减可以评估原子条件更新，复杂的读后修改则需要明确保护和验证边界。

通用策略与具体产品行为应区分：数据库的锁范围、快照建立时机和错误处理仍需按产品版本确认。
