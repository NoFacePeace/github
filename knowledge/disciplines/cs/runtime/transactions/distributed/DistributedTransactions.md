# 分布式事务

分布式事务（Distributed Transaction）涉及多个参与资源之间的提交与恢复协调。业务中也常用这个名称统称跨服务一致性方案，但不同方案提供的保证并不相同：原子提交、业务补偿和资源预留不能等同看待。

## 1. 为什么本地事务不够

创建订单可能同时需要创建订单记录、扣减库存和扣款。若这些修改使用同一个数据库事务，可以在任意一步失败时统一回滚。

若订单、库存、账户分别由独立服务管理，各自提交本地事务，就可能出现订单已创建、库存已扣减，但扣款失败的情况。调用方的 `try/catch` 只能处理异常，不能撤销其他服务已经提交的修改；请求超时也不代表对方没有执行成功。

判断依据是操作能否参加同一个事务，而不是模块数量。模块不公开内部 store，并不妨碍它通过业务接口接收事务上下文，或使用事务范围内注入的依赖。只要共享同一个本地事务，就不必引入跨服务协调。

## 2. 常见方案

| 方案 | 核心机制 | 保证与成本 |
| --- | --- | --- |
| 两阶段提交（2PC） | 参与者先准备，再根据协调者的决定提交或中止。 | 在资源和协议支持下提供原子提交；故障时可能阻塞并占用资源，隔离性还依赖具体实现。 |
| Saga | 每一步先提交本地事务，失败后执行补偿。 | 通常实现业务上的最终一致；已提交的中间结果可能可见，补偿不等于数据库回滚。 |
| TCC | 先预留资源，再确认或取消。 | 通过业务接口控制资源使用；需要实现预留、确认、取消及故障恢复，不自动获得全局 ACID 保证。 |

- [Saga](Saga.md)：通过本地事务和补偿动作协调长业务流程。
- [TCC](TCC.md)：通过 Try、Confirm、Cancel 协调资源预留和最终处理。

如果需求只是数据库更新后可靠地产生消息，可以考虑 Transactional Outbox：在同一个本地事务中写入业务数据和待发送事件，再由后台投递。它解决本地数据与事件记录的一致性，不会把下游消费者的执行纳入同一个原子事务。

## 3. 共同的故障处理要求

- **持久化流程状态**：记录业务标识、步骤结果和最终决定，进程重启后仍能继续恢复。
- **幂等处理**：同一步骤被重复调用时，不能重复扣款、释放或补偿。
- **处理不确定结果**：请求超时后通过结果查询或幂等重试确认状态，不能直接假定失败。
- **重试与对账**：处理暂时不可用，并为长期无法恢复的流程提供告警和人工处理入口。

仅在内存中依次调用几个接口，或在异常处理里调用一次补偿接口，都不足以构成可靠的协调机制。

## 4. 选择依据

优先明确业务不变量、可接受的中间状态、资源是否支持预留，以及失败后能否补偿。

能够共享本地事务时，通常先使用本地事务。跨服务且允许中间状态、存在明确补偿动作时，可以考虑 Saga；必须先保证库存或余额可用，并且各服务可以实现资源预留时，可以考虑 TCC。需要跨资源原子提交时，应确认资源是否支持相应协议，并评估阻塞、性能和可用性成本。
