# TCC

TCC 是 Try、Confirm、Cancel 的缩写，通过业务层的资源预留与最终处理协调多个服务。每个参与者需要提供相应业务接口，而不是只提供一次直接修改数据的接口。

## 1. 三个阶段的职责

| 操作 | 职责 | 库存示例 | 账户示例 |
| --- | --- | --- | --- |
| Try | 检查业务条件并预留资源。 | 减少可用库存，增加预留库存。 | 减少可用余额，增加冻结金额。 |
| Confirm | 将已预留资源正式用于本次业务。 | 将预留库存转为已售。 | 将冻结金额正式扣除。 |
| Cancel | 释放本次业务预留的资源。 | 释放预留库存，恢复可用库存。 | 解除冻结，恢复可用余额。 |

Try 需要真正预留资源，仅检查“库存足够”或“余额足够”无法防止资源随后被其他请求占用。预留和预留记录的写入应由参与者的本地事务保护。

## 2. 协调流程

1. 协调者为本次业务生成全局事务标识，并调用各参与者的 Try。
2. 所有 Try 成功后，持久化提交决定，继续调用各参与者的 Confirm。
3. 任一 Try 失败且尚未决定提交时，持久化取消决定，并对可能发生预留的参与者执行 Cancel。
4. Confirm 或 Cancel 暂时失败时，按已记录的决定重试，直到完成或进入人工处理流程。

一旦决定提交，某个 Confirm 超时不应让协调者随意改为取消；此时应查询状态或继续完成确认。参与者的 Confirm 应尽量只处理已经预留的资源，避免重新进行可能因资源不足而失败的竞争性分配。

## 3. 必须处理的边界

### 3.1 幂等

网络重试可能导致 Confirm 或 Cancel 被多次调用。参与者应使用事务标识和分支标识记录状态，确保不会重复扣减或重复释放资源。

### 3.2 空回滚

Cancel 可能在 Try 尚未执行时到达，例如 Try 请求发生延迟。参与者需要记录取消状态，即使当前没有资源可释放，也应让后续请求能够识别该分支已经取消。

### 3.3 悬挂

如果 Cancel 已经完成，延迟到达的 Try 不能再次预留资源，否则资源可能长期无法释放。Try 必须检查分支状态，拒绝已经取消的分支重新执行。状态检查、资源修改和状态更新应通过本地事务等机制保证并发安全。

## 4. 保证边界与成本

TCC 可以通过冻结和预留保护业务资源，但它不是一个天然具有全局 ACID 性质的数据库事务。各服务的确认可能在不同时间完成，查询接口仍需定义如何展示处理中状态。

长期未决事务会占用库存、余额等资源。超时释放必须与协调者的决定及恢复机制配合，不能让参与者在已经决定提交后自行释放资源。

## 5. 适用场景

适合资源能够明确预留、业务需要先确认资源可用再正式执行，并且能够承担接口改造与恢复机制成本的场景，例如库存预占、额度冻结。若操作无法预留，或不可逆外部动作无法纳入阶段设计，则不能仅靠套用三个接口获得一致性保证。
