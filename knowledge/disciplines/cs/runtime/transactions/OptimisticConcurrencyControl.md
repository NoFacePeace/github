# 乐观并发控制

## 1. 定义

乐观并发控制（Optimistic Concurrency Control，OCC）允许先读取并计算，再在验证或提交时检查冲突。验证失败则拒绝更新、中止事务或重新尝试。

业务中常称为“乐观锁”，但它不是一种锁对象，也不保证底层完全不使用锁。

## 2. 典型流程

```text
读取数据及其版本
      ↓
计算拟提交的修改
      ↓
原子地验证条件并更新，或执行事务级提交验证
      ↓
成功提交，或因冲突中止并重新判断
```

验证与发布修改必须通过正确协议协调，不能先单独检查版本，再无条件写入，否则检查与写入之间仍有竞争窗口。

## 3. 版本号更新示例

以下示例假设应用读取到对象版本为 3，并据此计算出新库存：

```sql
UPDATE products
SET stock = 9, version = version + 1
WHERE id = 1 AND version = 3;
```

需要检查影响行数。更新成功表示条件在更新时成立；影响 0 行可能表示版本已变化或记录不存在，需要重新读取并判断。

这是单行比较更新的常见用法，不等同于完整事务级 OCC。数据库执行该语句时，仍可能获取记录锁。

## 4. 验证范围

完整的事务级乐观控制可能跟踪读集、写集及相关依赖，在提交阶段验证。具体规则决定提供什么隔离保证。

只验证一个对象的版本，不能自动保护所有关联记录、范围条件或跨对象不变量。多个事务修改不同记录时，仍可能发生写偏斜。

## 5. 成本与重试

低冲突场景下，乐观策略可能减少长时间持锁；高竞争或事务较长时，反复计算、中止和重试可能代价较高。

重试应重新读取、验证业务条件并计算，而不是反复提交旧结果。可能重试的操作还需处理幂等性，避免重复执行不可撤销的外部副作用。

[CAS](../atomics/CAS.md) 可以作为实现乐观更新的原子原语，但 CAS 本身不等于完整的事务并发控制协议。
