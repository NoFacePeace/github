# GC

GC（Garbage Collection，垃圾回收）是一种自动内存管理机制，用于识别不再需要的对象并回收其占用的空间。本文介绍语言运行时中的通用原理，具体实现取决于运行时和收集器。

## 1. 为什么需要 GC

程序在执行过程中不断创建对象。对象不再需要时，其内存应当能够被后续分配复用，否则内存占用会持续增加。

手动内存管理要求程序显式释放内存；自动内存管理由运行时承担回收工作，减少忘记释放、重复释放以及释放后继续访问等错误。

GC 通常无法判断业务上是否还需要一个对象。如果缓存一直持有已经无用的对象，GC 仍可能保留它。文件和网络连接等资源也应按照其生命周期显式关闭，不能依赖 GC 及时释放。

## 2. 如何判断对象可以回收

### 2.1 引用计数

引用计数记录对象被引用的次数，在计数降为零时回收对象。它可以较及时地释放对象，但维护计数有开销；单纯引用计数无法处理不可达的引用环，需要额外机制。

### 2.2 可达性分析

追踪式 GC 从根引用（GC Roots）出发，沿对象之间的指针查找可达对象。根通常包括全局变量中的引用、执行栈上的活跃引用以及运行时需要扫描的引用位置。

```text
根 → A → B     A、B 可达，需要保留
     C ↔ D     若不存在从根到达它们的路径，C、D 可以回收
```

只要对象能从根到达，就需要保留；没有从根到达的路径，即使对象相互引用，也可以回收。

## 3. 常见回收算法

| 算法 | 基本过程 | 主要特点 |
| --- | --- | --- |
| 标记清扫 | 标记可达对象，回收未标记对象 | 通常不移动存活对象，可能产生碎片 |
| 复制 | 将存活对象复制到另一片空间，回收原空间 | 便于连续分配，需要预留复制空间并更新引用 |
| 标记整理 | 标记存活对象，再移动对象以整理空间 | 减少碎片，但移动对象及更新引用有额外成本 |

这些是基本策略，实际收集器可以组合使用。三色标记描述的是标记过程，不是与上述算法并列的完整回收策略；详细过程参见 [三色标记](tri-color-marking.md)。

## 4. 如何组织回收工作

### 4.1 暂停、并行与并发

- **暂停（STW，Stop the World）**：暂时停止业务线程执行，便于扫描或更新对象引用。
- **并行 GC**：多个 GC 工作线程同时执行回收任务，业务线程可能仍处于暂停状态。
- **并发 GC**：GC 工作与业务代码执行交错进行，部分阶段仍可能需要暂停。

并行关注 GC 工作线程之间的执行关系，并发关注 GC 与业务代码之间的执行关系，两者可以同时存在。

### 4.2 分代回收

分代收集器根据对象年龄划分区域，例如年轻代和老年代。其依据是许多程序中大量对象生命周期较短，可以更频繁地回收年轻对象。

为了避免每次年轻代回收都扫描整个老年代，收集器通常通过写屏障、记忆集等机制记录跨代引用。并非所有 GC 都采用分代策略。

### 4.3 写屏障

业务代码修改指针时，写屏障执行必要的额外操作，例如记录跨代引用或保护并发标记中的可达对象。不同收集器的写屏障规则不同，不能将某一种实现当作所有 GC 的通用规则。

## 5. 性能与内存观察

GC 通常需要在以下指标之间权衡：

- **吞吐量**：业务执行与 GC 分别消耗多少 CPU 时间。
- **延迟**：暂停及业务线程参与回收工作对响应时间的影响。
- **内存占用**：存活对象、待回收对象及收集器元数据占用的空间。

对象被回收意味着其空间可以被复用，不代表运行时立即将对应物理内存归还操作系统。因此，存活对象大小、运行时管理的内存和进程 RSS 不能直接等同。

排查时应结合分配速率、存活对象规模、GC 频率和暂停时间，区分频繁分配与对象长期被引用这两类问题。
