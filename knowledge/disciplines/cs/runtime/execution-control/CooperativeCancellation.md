# 协作式取消

## 1. 定义

协作式取消（Cooperative Cancellation）由外部发出取消信号，执行中的代码主动检查信号，并在合适的位置停止、清理和退出。请求方负责表达意图，执行方负责响应；写入取消标记本身不会强行终止工作。

同一进程中可以使用取消令牌、事件或可取消上下文。跨进程任务通常需要持久化取消意图，并通过通知或轮询传递信号，避免只依赖可能丢失的通知。

## 2. 请求与确认

尚未执行的任务可以在原子地阻止领取后直接标记为 CANCELLED。已经运行的任务通常先进入 CANCEL_REQUESTED，执行器确认停止后再进入 CANCELLED。

取消接口返回“请求已接受”不等于执行已经停止。执行器失联或进程崩溃时，可能需要恢复程序确认执行归属和业务结果，不能仅凭超时宣称取消完成。

## 3. 检查点与清理

```python
def execute(token):
    try:
        for item in items:
            token.raise_if_cancelled()
            process(item)
    finally:
        release_resources()
```

此伪代码假设取消异常会向上传播，由外层根据实际结果记录终态；正常返回时也应释放资源。清理本身需要有界，某些场景下应使用独立的清理超时，避免已经取消的上下文使清理立即失败。

取消响应速度取决于检查点之间的最长执行时间。长计算需要适当拆分；网络请求、数据库查询或外部进程应结合对应 API 的取消与超时能力。取消本地等待不一定会停止远端操作。

## 4. 副作用与竞态

检查取消之后，取消请求仍可能立即到达。因此“执行前检查一次”不能保证取消请求之后绝对不再产生副作用。

同一数据库内的状态检查与业务写入，可以通过事务、条件更新和必要的并发控制协调。跨系统调用则需要结合对方的幂等、取消协议或结果查询能力，已发生的动作可能需要补偿。

取消不等于回滚：已发送的邮件通常无法收回，已经提交的扣款不会因线程退出自动撤销。只有确认任务停止并按业务约定处理结果后，才能报告相应终态。
