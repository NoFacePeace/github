# 推送聊天回复

聊天适配器将适用的执行输出解析为文本增量、工具调用或完成等聊天协议消息，再交给已登记的 SSE 写入函数。

## 1. 响应写入

```text
执行回调
  → 转换为聊天协议消息
  → 写入 data: <JSON> 和空行
  → 前端读取并更新界面
```

使用的是原来的 HTTP 响应，不需要每段内容重新建立连接；也不是前端直接读取 Redis。

## 2. 事件转换与过滤

事件进入回放记录，不等于一定显示成回复正文。聊天适配器按事件来源和引擎协议解析、过滤并转换：

| 来源 | 聊天侧处理 |
| --- | --- |
| `stdout` 中解析出的 Agent 文本 | 转为流式文本回复。 |
| `stdout` 中的工具调用与结果 | 按前端工具或后端工具展示逻辑处理，不直接将所有工具输出作为回答正文。 |
| 引擎协议中解析出的错误 | 转为适用的错误提示。 |
| 执行完成回调 | 处理剩余输出并结束本轮回复。 |
| 特定模型警告 | 可转为提示文字，普通进度事件不会全部显示。 |

`accepted`、`started` 等生命周期事件和 `executor_ready` 等控制事件，不直接作为回答正文。普通 `stderr` 主要用于诊断，不直接作为正常回复。

## 3. 示例

用户请求“读取 README，总结项目用途”，执行过程可简化为：

| 执行事件 | 页面表现 |
| --- | --- |
| `accepted`：Runner 接受任务 | 不作为回复正文。 |
| `stdout`：引擎输出“我先查看 README” | 解析后显示为文字。 |
| `stdout`：引擎发起读文件工具调用 | 按工具展示逻辑呈现。 |
| `stdout`：工具返回文件内容 | 用于工具结果处理，不直接整段作为最终回答。 |
| `stdout`：引擎输出“这个项目用于……” | 解析后显示为回答。 |
| `completed`：执行结束 | 触发完成处理，结束本轮回复。 |

外层执行事件与内层引擎消息是两个层次。以下为简化示意，具体内层格式随引擎及其协议变化：

```json
{
  "type": "stdout",
  "payload": {
    "data": "{\"type\":\"text\",\"content\":\"这个项目用于处理任务。\"}\n"
  }
}
```

Server 通过输出回调取得 `data`，逐行解析其中的引擎消息，转换为文本增量，再写入 SSE。页面显示的是“这个项目用于处理任务。”，不是外层 `stdout` 标识或整段原始 JSON。

文本与工具结果可能有多种协议路径，具体是否展示还取决于解析器与适配器；不能将示例视为所有事件的统一原样转发规则。

## 4. 断开处理

连接关闭或异常时清理相应聊天登记，按当前实现释放适用的聊天对象。不能无条件清理后来建立的新连接，也不能把连接关闭直接等同于远端执行已停止。

重新连接时需要重建聊天状态与适用历史，不应认为 Redis 回放记录是完整、永久、可广播给任意连接的历史。
