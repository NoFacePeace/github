# Seccomp 执行策略

## 1. 策略定位

Linux 沙箱可以在启动目标程序前加载 seccomp 过滤器，减少任务能够访问的内核接口。下面给出一份包含 14 个受限系统调用的精简策略示例。

示例采用拒绝列表：拒绝指定的 14 个系统调用，其余默认允许，另有架构和 ABI 检查。这是可供分析的自定义策略，不是 Linux 或 bwrap 的标准默认规则，也不等同于 Docker/Moby、containerd、Podman 的完整默认策略。

## 2. 14 个受限系统调用

| 系统调用 | 用途 | 过滤结果 |
| --- | --- | --- |
| `kexec_load` | 加载供切换启动的新内核。 | `EPERM` |
| `kexec_file_load` | 通过文件描述符加载新内核。 | `EPERM` |
| `init_module` | 从内存加载内核模块。 | `EPERM` |
| `finit_module` | 从文件描述符加载内核模块。 | `EPERM` |
| `delete_module` | 卸载内核模块。 | `EPERM` |
| `swapon` | 启用交换空间。 | `EPERM` |
| `swapoff` | 关闭交换空间。 | `EPERM` |
| `bpf` | 加载、管理 BPF 程序和映射等。 | `EPERM` |
| `perf_event_open` | 创建性能监控事件。 | `EPERM` |
| `userfaultfd` | 创建供用户态处理缺页的接口。 | `EPERM` |
| `open_by_handle_at` | 根据文件句柄打开文件。 | `EPERM` |
| `io_uring_setup` | 创建 io_uring 实例。 | `ENOSYS` |
| `io_uring_enter` | 提交或等待 io_uring 操作。 | `ENOSYS` |
| `io_uring_register` | 注册 io_uring 使用的资源。 | `ENOSYS` |

`EPERM` 表示操作不允许；`ENOSYS` 表示系统调用不可用，使具备替代实现的应用有机会回退到其他 IO 路径。命中上述规则时拒绝该次调用，不直接终止进程；应用是否退出取决于自身错误处理。

## 3. 选择依据与保留能力

设计这类精简策略时，可以按任务需求作以下取舍：

- 内核切换、模块加载及卸载、swap 管理属于任务不需要的宿主维护能力，作为核心禁止项。
- BPF、性能观测、用户态缺页处理和文件句柄访问参考社区默认限制；特殊性能分析任务需另行评估。
- io_uring 参考社区默认限制及内核安全风险保留禁止，真实任务需验证回退能力。
- keyring 和挂载接口在不同社区产品中存在差异，本示例不增加限制，实际使用时需另行评估。
- `ptrace`、`process_vm_readv`、`process_vm_writev` 保留，用于任务内调试。
- `clone`、`clone3`、`unshare`、`setns` 不作为统一禁止项，考虑浏览器与嵌套沙箱需求。

清空 capabilities 后，模块加载等操作通常已被内核权限检查拒绝；seccomp 再显式禁止，形成额外保护。保留调用不代表操作必然成功，仍受 namespace、capabilities、文件权限和外层策略约束。

此策略缩小共享内核攻击面，不能代替独立内核隔离。新增系统调用默认放行，需要持续审查；也不能认为它与完整容器默认策略具有相同覆盖范围。

## 4. 架构与 ABI 检查

本示例按原生 Linux x64 和 arm64 设计；规则生成器应拒绝未支持的架构，不能直接套用其他架构的系统调用编号。

过滤器运行时先检查系统调用架构；遇到不匹配的 ABI，执行 `KILL_PROCESS`。x64 额外拒绝带 `__X32_SYSCALL_BIT` 的调用，以及编号 512～547 的旧 x32 专用范围，动作同样为终止调用进程。

这些检查用于防止通过兼容 ABI 的不同系统调用编号绕过规则。32 位兼容 ABI 和 x32 程序不属于本策略支持的任务范围。

## 5. 生成与加载顺序

以下以 RootlessKit 提供网络、bwrap 建立沙箱的组合为例；这是集成示例，不是这些工具固定要求的启动流程。

```text
启动管理程序
  ├─ 在内存中生成经典 BPF 字节码
  ├─ 将字节码保存为私有文件，例如权限 0600
  ├─ 准备 bwrap 参数：--info-fd 3 --cap-drop ALL --seccomp 4
  └─ 启动执行链
       └─ RootlessKit
            └─ 网络脚本设置规则，打开 FD 3
                 └─ seccomp 包装脚本打开 FD 4
                      └─ exec bwrap
                           ├─ 读取并安装过滤器
                           └─ 启动目标程序及其子进程
```

示例约定 FD 3 用于 bwrap 输出子进程信息，FD 4 用于读取过滤器；这两个编号可按实际启动逻辑调整。网络包装与系统调用过滤是独立层，不使用 RootlessKit 时也可以加载 seccomp。

包装脚本的核心操作为：

```sh
exec 4<"$seccomp_file"
exec bwrap ... --seccomp 4 ...
```

这是说明参数传递的片段，实际使用时需补全挂载选项和目标命令。将 FD 4 的打开操作放在 RootlessKit 启动后，可以避免依赖外层启动工具保留任意父进程描述符。

规则文件应保存在任务无法访问的私有管理目录。bwrap 消费并关闭 FD 4；过滤器安装后由内核执行，目标程序后续创建的子进程及 exec 替换后的程序继承限制，不需要反复读取规则文件。

## 6. 验证与验收边界

验证应覆盖三个层面：

1. 规则逻辑：检查支持的架构、ABI、14 个拒绝项及普通允许调用是否得到预期动作。
2. Linux 内核集成：通过真实 bwrap 启动路径，检查过滤器加载、错误返回和 fork/exec 继承；加载失败时停止启动目标程序。
3. 业务兼容性：运行代表性的 CLI、依赖安装、构建、浏览器和调试任务，确认所需能力仍可使用。

查看目标进程及其 exec 子进程的 `/proc/<pid>/status`，可检查 `Seccomp: 2` 和内核支持时提供的 `Seccomp_filters`。还需结合实际策略版本和无副作用探针，确认受限调用返回预期错误。

单次 `EPERM` 可能来自其他权限检查，不能单独证明过滤生效；仅看到 `Seccomp: 2` 也不能证明加载了预期规则。非 Linux 环境的字节码测试不能替代目标 Linux 内核上的验证。
