# 建立执行监控

启动后保存本次执行的 cgroup、manifest、私有文件与网络目录信息，返回输出流、退出等待及失败原因查询等接口。

## 1. 生命周期

使用隔离网络时监控网络辅助进程与执行进程的存活关系。执行主进程退出后，清理 cgroup 内遗留子进程，避免它们继续占用资源或持有输出管道。

执行服务继续消费输出、跟踪超时与停止、按适用条件备份日志，并等待终态结果。

## 2. 本轮日志定时备份

远程沙箱的 Agent 执行分支在 `runtime.start(spec, secrets)` 返回执行句柄后，启动当前 Session 的日志备份定时器。它属于启动后的监控环节，不属于执行环境准备，也不是 Runtime 进程启动后一直运行的全局扫描。

```text
准备执行环境
  → 启动 Executor 并取得执行句柄
  → 开启本轮日志备份定时器
  → 消费输出、监控退出并定时上传日志
  → 收尾时关闭定时器
  → 适用的任务文件备份
```

开启定时器不代表底层 Agent 引擎已就绪；Executor 的配置读取、引擎启动与定时器计时可以并行推进。

### 2.1 上传时机与范围

每 30 秒尝试上传一次，首次尝试在定时器开启约 30 秒后。只上传当前 Session 的 `<sessionUuid>.jsonl`，不扫描整个 session 目录，也不上传 config、memory 或 workspace。

文件不存在或为空时跳过；上次上传尚未结束时不启动重叠上传。单次上传带有 30 秒超时，并受执行租约及备份停止信号约束。上传失败记录警告，执行继续。

### 2.2 覆盖方式

Runtime 读取当前本地日志文件，上传到同一个对象 key：

```text
tasks/<taskUuid>/session/<sessionUuid>.jsonl
```

每次上传当前文件内容，覆盖此前上传的对象，不是追加对象内容，也不是每 30 秒创建一个新对象。上传期间本地日志可能继续增长，因此一次备份不代表实时同步全部最新输出。文件职责见[对象存储 session](../../../../storage/object-storage/Session.md)。

### 2.3 停止与其他备份

执行进入收尾时清除定时器、中止适用的进行中上传，并等待上传处理结束。后续任务备份是独立流程，会备份 config 和 session 目录，不能把它理解为定时器再运行一次。

Memory 有独立的变更监听、上传与同步流程；当前代码未实现 workspace 整体备份。30 秒定时器仅负责本轮日志文件。

## 3. 异常清理

启动失败时清理适用的 cgroup、网络目录、manifest 和私有辅助文件；若发现资源限制导致的失败，返回相应原因。

## 4. 与引擎启动的边界

拿到 Runtime 进程句柄不代表 Agent 已经就绪。Executor 还要读取输入、生成引擎配置并启动引擎，后续需依据执行事件判断实际进度。

后续进入 [Executor 流程](../../executor/Executor.md)，从读取执行输入开始。
