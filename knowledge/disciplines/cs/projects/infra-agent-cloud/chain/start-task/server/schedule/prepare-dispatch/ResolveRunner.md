# 选择 Runner 与预留容量

根据 Task、Session、执行引擎及运行方式，确定目标 Runner 与执行租约。协调状态通过共享存储管理，以处理多个 Server 的并发争用。

预留通过 Redis 的[执行租约](../../../../../storage/redis/ExecutionLease.md)和 [Runner 容量集合](../../../../../storage/redis/RunnerCapacity.md)共同记录：前者关联本轮执行与节点，后者统计节点已占用的名额。

## 1. 已有执行归属

若 Task 已有有效的 Runner 归属，检查该节点的资源池、心跳与能力是否匹配，并尝试在该节点预留本轮执行容量。不会仅因当前节点不可用就随意切换任务归属。

## 2. 新建执行归属

没有有效归属时，获取在线且能力匹配的候选节点，再逐个尝试预留执行租约。先预留成功，再声明 Task 的 Runner 归属，避免过期心跳将任务绑定到不可用节点。

若声明时发现其他流程已经取得归属，释放本次预留，并重新按已确定的归属处理。

## 3. 结果与后续步骤

成功后将目标 Runner ID、租约 ID 和租约截止时间写入待派发 Job，并按节点能力调整兼容字段。调度 claim 保护准备过程，执行租约约束 Runner 执行归属，两者分别管理。
