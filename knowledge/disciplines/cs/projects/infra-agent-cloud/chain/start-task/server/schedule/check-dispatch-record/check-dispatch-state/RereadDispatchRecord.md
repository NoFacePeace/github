# 再次读取调度记录

业务状态同步返回后，调度器根据 Session UUID 再次通过 Redis `GET` 读取[调度记录](../../../../../../storage/redis/dispatch-record/DispatchRecord.md)。

## 1. 再次确认

- 记录仍存在且 `state = queued`：继续检查排队超时，未超时才尝试分配 Runner。
- 记录不存在或状态已改变：结束当前处理，不按原来的排队状态继续派发。

## 2. 作用

第一次查询与业务同步之间，用户可能停止任务；业务同步本身也可能触发取消。再次读取可以发现这段时间内的状态变化。

本步骤只读 Redis，不更新调度记录。后续超时、准备派发、派发成功等阶段才按各自条件更新调度状态。

## 3. 并发边界

再次读取不能完全消除后续竞态。用户仍可能在确认后发起停止，需要后续取消、派发校验和停止指令共同处理。调度 claim 只协调调度处理权，不阻止用户停止任务。
