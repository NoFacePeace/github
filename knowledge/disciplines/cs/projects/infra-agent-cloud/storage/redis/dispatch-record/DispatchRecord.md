# 调度记录

保存单轮执行的待调度状态及加密输入。

## 1. Key 与类型

以下使用通用命名空间：

```text
<namespace>:<scope>:runner:{<runnerScope>}:dispatch:session:<sessionUuid>
```

类型为 String，值为序列化 JSON。`scope` 表示提交方运行范围，`runnerScope` 表示 Runner 资源池范围。

## 2. 入队字段

| 字段 | 含义 |
| --- | --- |
| taskUuid | 任务标识。 |
| sessionUuid | 本轮执行标识。 |
| jobId | 调度作业标识。 |
| state | 入队时为 `queued`。 |
| [queuedAt](QueuedAt.md) | 排队时间，毫秒时间戳。 |
| [deadline](Deadline.md) | 排队超时截止时间。 |
| encryptedInput | 加密后的完整提交输入。 |

后续调度阶段可以更新状态并补充派发信息。排队超时截止时间属于业务字段，不能等同于 Redis key 的 TTL。

## 3. 写入

通过 Lua 脚本执行存在性检查与 `SET`，并同步添加待调度集合成员。已有记录不会因重复提交被直接覆盖。

## 4. 排队超时

`deadline` 由排队时间加排队时限得到。排队时限默认 10 分钟，可通过运行配置调整。

调度器根据该字段判断请求是否排队超时。它是业务截止时间，不是 Redis TTL，到达该时间不会由 Redis 自动删除记录。

## 5. 过期与清理

- 排队（`queued`）和派发中（`dispatching`）阶段，不设置 TTL。
- 已派发（`dispatched`）、失败（`failed`）或取消（`cancelled`）后，需先成功同步对应业务状态，再确认调度结果。
- 确认时，从待调度集合移除该 Session，并将调度记录 key 的 TTL 设置为 24 小时。

24 小时从设置 TTL 时开始计算，不从最初排队时计算。仅改变状态、尚未完成结果确认时，不应认为记录已经具有该 TTL；它也不需要等待 Agent 执行完成才进入这一步。

## 6. 记录用途

调度记录保存本轮执行的输入和调度进度，供调度器后续分配 Runner：

- 提供执行输入：等待集合只保存 Session UUID，调度器根据它查找记录，取得加密的执行输入。
- 跟踪调度状态：记录排队时间、超时截止时间及排队、派发中、已派发等状态。
- 避免重复提交：同一 Session 已有记录时校验并复用，避免重复入队。

```text
等待集合：哪些 Session 等待调度
调度记录：每个 Session 的执行输入和调度状态
```

Task、Session 表保存业务任务和执行记录；本记录描述调度过程，不能代替两张业务表。

## 7. 调度示例

假设用户提交“分析服务延迟升高的原因”，创建了 `task-001` 和首轮执行 `session-001`。以下标识、时间和密文均为示例。

等待集合中加入：

```text
成员：session-001
分数：1800000000000（排队时间，毫秒）
```

对应调度记录保存为：

```json
{
  "taskUuid": "task-001",
  "sessionUuid": "session-001",
  "jobId": "job-001",
  "state": "queued",
  "queuedAt": 1800000000000,
  "deadline": 1800000600000,
  "encryptedInput": "<加密后的完整执行输入>"
}
```

示例中的截止时间比排队时间晚 10 分钟。记录入队时没有设置 TTL，不会在该截止时间由 Redis 自动删除。

调度器后续的处理可概括为：

```text
从等待集合取得 session-001
  → 查询对应调度记录
  → 检查排队是否超时
  → 获取执行输入并选择合适的 Runner
  → 下发任务并更新调度状态
  → 业务状态同步成功后确认调度结果
  → 移除等待成员，为调度记录设置 24 小时 TTL
```

等待集合提供待处理标识，调度记录提供执行内容与状态；两者共同支持调度，入队成功本身不代表 Agent 已启动。
