# 检索评测

检索评测使用固定问题和相关内容标注，检查检索服务能否在指定范围内返回正确证据，以及证据排名是否合理。它聚焦召回结果，不要求 Agent 完成多轮调查或生成最终回答。

## 1. 输入与输出

- 输入：查询问题、固定仓库与版本、文档语料、相关内容标识、Top K 和检索配置。
- 输出：有序检索结果、命中情况、各项指标、请求耗时与失败状态。

参考答案可以辅助理解问题，但检索指标通常需要明确的相关文档、章节或 Chunk 标注，不能只凭答案文本判断召回是否正确。

## 2. 执行流程

```text
固定查询集、语料版本和相关性标注
  → 按配置提交检索请求
  → 保存实际范围与有序结果
  → 将返回项映射到统一评测单位并去重
  → 计算不同 Top K 的命中与排名指标
  → 记录失败或不可计算原因
  → 汇总并比较配置，复查漏召回与误召回
  → 保存报告，上传评测平台展示逐题结果
```

查询服务可能返回章节及多个命中块，评测时需明确如何映射到标注单位。不能将章节数量直接当作命中 Chunk 数，也不能用重复结果抬高得分。

## 3. 常用指标

| 指标 | 关注问题 |
| --- | --- |
| Precision@K | 前 K 项中相关内容的比例 |
| Recall@K | 全部标注相关内容中，前 K 项找回多少 |
| F1@K | 综合精确率与召回率 |
| AP@K 与 MAP@K | 是否把相关项排在前面，以及查询集上的平均表现 |

计算前需固定分母、去重和不足 K 项等约定。单个查询计算 AP，查询集平均为 MAP；不同实现的指标命名与归一化方式应记录清楚。

## 4. 对照条件

可以比较全文、向量、融合排序及不同候选数量、切块策略或模型配置。每次比较应记录索引版本、实际发布批次、过滤条件与模型身份，避免将语料变化误判为排序改进。

多变量同时变化时，结果只能说明组合效果，不能直接归因于某一个参数。

## 5. 结果解释

有效查询但没有命中、请求失败、标注缺失和结果无法映射属于不同状态，应分别统计。汇总分数时明确哪些查询进入分母，避免只统计成功请求而掩盖不可用性。

相关性标注可能不完整，漏标会影响精确率解释。检索命中证明证据可被找到，不证明 Agent 能正确使用证据，也不等同于最终回答质量。

## 6. 数据集来源与固定

数据集可以从固定版本已发布的文档导出真实 Chunk，再围绕这些内容编写问题、参考答案并标注证据块。运行评测时读取固定数据，不临时生成新问题。

建议分别保存语料与问题：

| 文件 | 内容 |
| --- | --- |
| `chunk.json` | 文档与 Chunk 标识、正文、来源路径、版本及索引指纹 |
| `query.json` | 问题、参考答案、相关 Chunk 标识、原文引用及语料摘要 |

校验问题引用的 Chunk 存在、原文引用确实出现在对应正文中，并核对语料摘要，防止更换切块或文档后仍使用旧标注。

记录出题方式、生成时间、人工或模型参与情况、审核方法，以及是否利用检索排名调整过题目。若未记录作者或模型，不能仅凭问题措辞推断其来源。

根据文档编写的问题不等于经过独立源码审计的事实标注；引用子串校验也只证明文字对应，不能证明参考答案完全正确。只标出支持答案的正向证据时，应明确它不是穷尽的相关内容集合。

## 7. 结果对齐与命中判断

先确认参考标注与被测索引对应，再对齐检索结果：

```text
固定参考语料及被测版本
  → 将参考证据唯一映射到被测语料的 Chunk
  → 按章节返回顺序展开 matchedChunks
  → 按 Chunk 标识去重，保留第一次出现的排名
  → 校验返回块的仓库、版本、文档、正文与索引身份
  → 比较标注 Chunk 集合与返回有序列表
```

同版本远程标注可以要求 Chunk 标识、文档标识、正文和索引指纹一致。需要跨语料映射时，应明确规则，例如要求完整相对来源路径及正文精确且唯一匹配，不仅比较文件名或使用语义相似度猜测。

对齐示例：

```text
标注相关块：A、B
返回排名：  A、C、B
命中结果：  是、否、是

Precision@3 = 2/3
Recall@3 = 2/2 = 1
```

如果参考没有唯一映射，或返回内容与固定索引不一致，标记为不可计算并记录原因，不将其简单视为未命中。数据中未标注的 C 在此计算中不计命中，但仅有正向标注时不能据此证明 C 实际不相关。

## 8. 实验汇总与展示

先逐题计算，再对每项有效指标取算术平均，并记录有效样本数。这样每道有效问题对宏平均贡献相同，不是先把所有问题的命中数相加再统一计算。

| 汇总项 | 口径 |
| --- | --- |
| 指标平均值 | 对该指标有效的有限数值取平均，记录样本数 |
| 请求成功率 | 非请求失败数除以全部问题数 |
| 可评分率 | 有效评分问题数除以全部问题数 |
| 完全未命中数 | 有效查询中未命中任何标注证据的问题数 |
| 请求失败与不可计算数 | 分别计数，不混入正常零命中 |
| 平均耗时与 P95 | 按明确的成功请求集合统计，记录单位与口径 |

正常执行但未命中的问题以零分参与对应指标平均。请求失败或无法对齐的样本不伪装成正常检索零分，应同时展示失败比例，避免只看有效样本平均值而高估系统效果。

可以另设可用性加权汇总值，例如 `平均 Recall@5 × 可评分率`，但必须说明含义，不能替代各项原始指标。

保存逐题排名、命中、错误和汇总到 JSON 与 HTML 报告，并可上传 [Arize Phoenix](https://github.com/Arize-ai/phoenix) 展示。不同配置、评分版本和独立运行分别保留实验身份，不将重复运行无标记地混成同一次实验。

## 9. 判别模型与标注评分的区别

以上流程按预先标注的 Chunk 身份计算指标，不需要模型 Judge 或相关性判别模型逐条打分。

```text
标注评分：返回块 → 与固定标注比对 → 计算指标

模型判别：问题 + 返回内容 → 模型判断相关性 → 按判定计算或辅助分析
```

Embedding 模型负责把问题与内容转换为向量，不负责决定评测分数。相关性判别模型评价问题与候选内容的关联；回答 Judge 则评价最终答案，两者的评分对象不同。模型重排序也属于检索算法的一部分，不能自动当作独立正确性标注。

固定标注便于重复比较，但可能漏标。判别模型可以辅助审核未标注候选、扩充标注，或形成明确标记的另一套评价；它会引入误判、模型偏差与重复评分波动，不能静默覆盖原始标注。

引入模型判别时，需要固定模型、提示词、判定规则和阈值，保存判定理由与人工复核记录。更换判别条件后统一重评待比较结果，并区分人工标注指标与模型判别指标。
