# 部署版本跟踪

部署版本跟踪关注目标环境实际运行的代码版本，使文档可以对应部署中的系统。本文为 Infra 知识库的设计规划，不限定具体部署平台。

## 1. 跟踪配置

| 配置 | 含义 | 示例 |
| --- | --- | --- |
| 仓库与部署映射 | 确定部署对象属于哪个源码项目 | 服务与仓库的关联 |
| 目标环境 | 选择观察的环境 | 测试或生产环境 |
| 观察范围 | 明确检查哪些部署对象与实例 | 指定服务的目标实例集合 |
| 收敛条件 | 确定何时认为版本已稳定 | 观察范围内版本一致且信息齐备 |
| 版本映射方式 | 将运行制品关联到源码提交 | 镜像 digest 对应的构建元数据 |

这些规则用于选择运行版本，不用于证明系统健康。

## 2. 输入与输出

- 输入：仓库与部署映射、环境、观察范围及收敛规则。
- 处理：读取运行版本，检查收敛，再映射到源码提交。
- 输出：仓库身份、完整 Commit SHA、环境及运行版本来源。

```text
部署跟踪配置
  → 查询运行版本
  → 检查范围完整性与版本收敛
  → 映射源码 Commit
  → 校验并登记版本
```

制品地址或版本号只有在存在可靠映射时才能确定 SHA，不根据名称猜测源码版本。

## 3. 示例

目标环境中三个实例起初都运行版本 A。滚动发布时出现 A、B 混合，系统暂缓确认新版本；待观察范围内实例都满足约定条件并运行 B，再将 B 映射到完整 SHA 并登记。

若 B 已有版本记录，可以复用。是否将其设为默认文档版本，需要独立的产物选择策略。

## 4. 边界与待定策略

- 查询结果缺少预期实例时不能直接判断版本一致，应先处理信息不完整的问题。
- 制品与提交无法唯一映射时，不登记为已确认版本。
- 回滚可能重新出现历史 SHA，应保留版本历史，不将回滚误当作提交身份变化。
- 多仓库共同构建一个制品时，需明确每个源码版本的关联方式，不能只保存一个未经验证的 SHA。
- 金丝雀、多版本长期共存等场景需要专门定义选择规则，不能沿用“全部实例同一版本”的假设。
