# 分支跟踪

分支跟踪持续关注指定 Git 分支的 HEAD，适合让文档跟随开发中的代码更新。本文为 Infra 知识库的设计规划。

## 1. 跟踪配置

| 配置 | 含义 | 示例 |
| --- | --- | --- |
| 仓库 | 被跟踪的代码项目 | `order-service` |
| 分支选择策略 | 精确指定分支或跟随默认分支 | 指定分支 |
| 分支名 | 精确指定时使用的引用 | `main` |

跟随默认分支时，每次发现版本应查询当前默认分支；精确指定 `main` 时，仓库修改默认分支不会改变跟踪目标。

## 2. 输入与输出

- 输入：仓库配置与分支选择规则。
- 处理：确定目标分支，查询 HEAD 并解析为完整 Commit SHA。
- 输出：仓库身份、完整 SHA、实际分支名及观察信息，交由版本登记环节处理。

```text
仓库 + 分支选择规则
  → 确定分支
  → 查询 HEAD
  → 解析完整 SHA
  → 登记版本
```

## 3. 示例

第一次观察到 `main → Commit A`，系统登记 A。下一次观察到 `main → Commit B`，系统判断 B 是否已登记，再决定是否请求构建。

已经开始处理 A 的任务仍使用 A，不因分支更新而切换到 B。

## 4. 边界与待定策略

- 周期检查只观察当时的 HEAD，可能遗漏两次检查之间的中间提交；是否逐提交补齐应另外设计。
- 分支删除、读取失败和权限不足应区分记录，不把旧 SHA 当作新的观察结果。
- 强制推送和回退不保证提交按时间或祖先关系单向前进，版本身份仍以仓库与 SHA 判断。
- 同一 SHA 被再次观察到时复用版本记录；是否重新生成由独立构建策略决定。
- 检查周期和事件通知属于触发机制，不属于分支选择规则。
