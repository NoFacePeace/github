# 跟踪方式

跟踪方式决定系统从哪里发现仓库版本，跟踪规则决定具体关注哪些引用或运行版本。两者作为仓库登记配置保存。本文为 Infra 知识库的设计规划。

## 1. 方式与规则

| 跟踪方式 | 版本来源 | 跟踪规则示例 |
| --- | --- | --- |
| [分支跟踪](Branch.md) | Git 分支 HEAD | 指定 `main`，或明确选择跟随仓库默认分支 |
| [Tag 跟踪](Tag.md) | Git Tag | 用正则 `^v\d+\.\d+\.\d+$` 匹配发布标签 |
| [部署版本跟踪](Deployment.md) | 目标环境的运行版本 | 指定环境、部署对象范围及版本收敛条件 |

例如，“方式为分支、规则为 main”表示持续观察 `main` 指向哪个提交。“方式为 Tag、规则为发布标签正则”表示只关注匹配的标签。

## 2. 分支跟踪

分支跟踪适合持续更新的开发文档。发现分支 HEAD 指向新提交时，将其解析为完整 SHA，再交给版本登记和构建流程。

需要区分精确指定分支与跟随默认分支；仓库修改默认分支时，两者行为不同。周期检查 HEAD 也不保证覆盖检查间隔内出现过的每个提交。

## 3. Tag 跟踪

Tag 跟踪适合按发布版本生成文档。匹配规则用于筛选标签，例如 `v1.2.3` 匹配上述正则，`test-build` 不匹配。

正则只能判断名称是否匹配，不能确定版本先后。历史标签处理范围、版本排序和预发布标签是否纳入，需要另外定义。

## 4. 部署版本跟踪

部署版本跟踪适合使文档对应目标环境运行的版本。系统根据部署信息或制品元数据，映射到仓库的精确提交。

需明确环境和观察范围。版本未收敛、信息不完整或无法唯一映射到 Commit 时，暂不触发该版本的构建。

## 5. 与触发的区别

跟踪方式与规则描述“关注什么”，触发机制描述“何时检查或通知”。同一种跟踪方式可以采用定时检查，也可以接收事件通知；具体方案需独立设计。

```text
仓库跟踪配置
  → 定时检查或接收事件
  → 按规则筛选版本
  → 解析完整 Commit SHA
  → 登记版本并请求构建
```

手动触发由使用者选择已登记版本，不是一种自动跟踪方式。无论入口如何，构建过程都使用确定的 SHA，不在执行时重新追随变化中的引用。
