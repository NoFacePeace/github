# Tag 跟踪

Tag 跟踪关注符合规则的 Git 标签，适合按发布版本组织文档。本文为 Infra 知识库的设计规划。

## 1. 跟踪配置

| 配置 | 含义 | 示例 |
| --- | --- | --- |
| 仓库 | 被跟踪的代码项目 | `order-service` |
| 标签匹配规则 | 筛选哪些 Tag | `^v\d+\.\d+\.\d+$` |
| 历史处理范围 | 首次接入处理哪些已有标签 | 全部匹配项或选定起始版本 |
| 版本选择策略 | 怎样排序及处理预发布版本 | 按约定的语义化版本规则 |

正则只判断名称是否匹配，不提供版本排序能力。正则方言、排序方式和首次接入策略应明确约定。

## 2. 输入与输出

- 输入：仓库配置、标签匹配与版本选择规则。
- 处理：获取标签，筛选候选并解析到实际提交。
- 输出：仓库身份、完整 Commit SHA、来源标签及提交信息。

```text
仓库 + 标签规则
  → 查询 Tag
  → 匹配与选择
  → 解析完整 SHA
  → 登记版本
```

附注 Tag 应解引用到实际 Commit；不能直接将标签对象 ID 当作提交 SHA。

## 3. 示例

使用规则 `^v\d+\.\d+\.\d+$`：

| 标签 | 是否匹配 |
| --- | --- |
| `v1.2.3` | 是 |
| `v2.0.0` | 是 |
| `v2.0.0-rc.1` | 否 |
| `test-build` | 否 |

如需预发布标签，应调整匹配和版本选择规则。

## 4. 边界与待定策略

- 多个 Tag 指向同一 SHA 时复用版本身份，保留各自来源。
- 标签可被移动或删除，需要记录变化；已生成产物仍关联原 SHA。
- 无法解析到提交、提交不可获取或查询失败时，不将候选当作已确认版本。
- 是否要求发布流水线成功属于附加准入策略，应显式配置。
- 排序不能直接依赖字符串大小，例如 `v1.10.0` 与 `v1.9.0` 应按约定版本规则比较。
