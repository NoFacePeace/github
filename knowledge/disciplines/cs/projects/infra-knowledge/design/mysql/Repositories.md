# 仓库存储

仓库存储负责持久化已登记代码项目的身份、接入信息和配置，供查询、版本发现与构建流程使用。本文为 Infra 知识库的 MySQL 设计规划，具体表名、字段类型及 SQL 尚待确定。

## 1. 存储范围

| 信息 | 用途 |
| --- | --- |
| 稳定仓库身份 | 供版本、任务和产物关联，避免用可变名称作为唯一关联依据 |
| 仓库名称与 Git 地址 | 展示项目、定位源码来源 |
| 来源平台及项目身份 | 区分不同平台或实例中的项目 |
| 归属、负责人和简介 | 支持管理与检索 |
| 跟踪配置 | 保存版本来源及选择规则 |
| 生成配置 | 保存仓库默认的文档生成选项 |
| 创建与更新时间 | 追踪记录生命周期 |

具体字段是否必填、配置是否拆表及是否保存变更历史，应在详细表结构中明确。真实凭据不作为普通仓库字段明文保存。

## 2. 唯一性与关联

内部主键用于稳定关联，远端项目身份用于识别来源。若使用平台项目 ID，应连同平台实例或命名空间判断唯一性，不能假设跨平台 ID 全局唯一。

仓库名称和地址可能发生变化，是否唯一及如何规范化需要明确规则。一个仓库可关联多个版本，但提交 SHA、构建状态和日志分别由对应记录管理。

## 3. 登记与更新流程

```text
经过应用层校验的登记信息
  → 按身份查询已有记录
  → 创建或更新仓库
  → 依靠数据库约束处理并发冲突
  → 提交事务并返回稳定身份
```

先查询再插入不能单独保证并发去重。唯一索引、事务和冲突返回语义应配合设计，不能因名称碰撞覆盖其他项目。

## 4. 更新语义

- 区分未传字段、显式空值和清空操作，避免局部更新误删配置。
- 修改地址前确认是否仍为同一项目，不能静默替换仓库身份。
- 跟踪与生成配置变化影响后续处理，不改写历史版本和构建记录。
- 并发修改可采用版本号或其他冲突检测方式，具体策略待确定。

## 5. 查询与索引

查询可包括按稳定身份读取、按名称搜索，以及筛选某种跟踪方式的仓库。索引设计应依据最终查询条件、排序和分页方式确定。

配置保存完成不代表远端访问成功，也不代表已登记版本或构建完成。存储层返回持久化结果，由上层决定后续动作。
