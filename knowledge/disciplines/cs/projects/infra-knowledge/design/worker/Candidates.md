# 候选构建

候选构建是 Worker 本轮准备尝试领取的构建集合。查询只筛选可能执行的对象，不授予执行权。本文为 Infra 知识库的设计规划，具体查询接口与 SQL 尚待确定。

## 1. 输入与输出

| 项目 | 内容 |
| --- | --- |
| 输入 | 本地可用槽位数、支持的构建类型及筛选策略 |
| 查询来源 | 构建记录及其关联的源码版本 |
| 输出 | 有界的候选标识集合及领取所需信息 |

构建状态与记录关系见 [Build 存储](../mysql/Build.md)。候选按单个构建尝试还是按版本归组返回，需要与领取粒度统一设计。

## 2. 筛选条件

候选通常需要满足以下条件：

- 处于待执行状态，或符合明确的失效恢复规则。
- 构建目标与配置能够由当前 Worker 执行。
- 没有被取消、替代或禁止继续执行。
- 满足前置依赖与工作区并发约束。

是否只允许最新尝试参与执行、失败任务是否自动重试，以及失效任务的判断条件，应在任务状态设计中明确，不能仅靠一次状态查询推断。

## 3. 数量与顺序

查询数量应有上限，并参考本地可用槽位，避免无界读取或在进程内囤积大量候选。

排序可以考虑等待时间、优先级及恢复需求，但需要稳定的次级排序，并评估是否导致低优先级任务长期得不到执行。具体策略尚待确定。

## 4. 查询与领取的区别

```text
查询候选 A
  → 申请执行额度
  → 尝试领取 A
      ├── 成功：启动执行
      └── 失败：释放已申请额度，不执行 A
```

查询结束后，任务可能已被其他 Worker 领取或被用户取消。领取时必须再次校验当前状态，并原子确认执行归属；不能直接使用候选快照启动构建。

尝试领取前的共享额度协调见 [GlobalSlots](GlobalSlots.md)。

## 5. 异常处理

没有候选属于正常结果，本轮可以结束。存储查询失败应返回错误并记录诊断，不能当成队列为空。

候选之间发生竞争不代表任务执行失败。是否继续尝试其他候选、何时结束本轮，应结合剩余容量和取消状态判断。
