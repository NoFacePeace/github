# Worker

Worker 负责领取待执行构建，调用对应构建组件，并记录执行结果。本文为 Infra 知识库的设计规划，具体接口、并发额度和部署方式尚待确定。

## 1. 职责

- 检查当前可用执行容量。
- 查询并领取本实例能够执行的构建。
- 准备执行上下文，调用文档或图谱等构建组件。
- 跟踪进度，保存成功、失败或取消结果。
- 管理执行归属、资源释放及退出恢复。

源码分析、模型调用和图谱生成由相应构建组件实现，Worker 组织这些能力的执行。

## 2. 创建与调用

一种可选实现是在服务启动时创建 Worker，由调度器周期调用其领取方法：

```text
服务启动
  → 创建 Worker
  → 注册构建领取定时任务
  → 调度器周期调用领取方法
  → Worker 启动领取到的构建
```

Worker 对象持续存在，定时调用不重复创建对象。周期执行的是领取检查，每次构建则是有明确终态的一次性任务。

## 3. 单轮领取

单轮入口规划为 [ScanPending](ScanPending.md)，负责检查待执行构建并启动可领取的任务。

```text
检查空闲容量
  → 查询候选任务
  → 竞争执行归属
  → 确认领取成功
  → 启动构建执行
```

没有任务或容量已满时，不启动新构建。查询候选不代表已经领取；并发 Worker 之间需要通过明确的原子领取机制协调。

## 4. 并发与实例

一个 Worker 可以管理多个并发执行，不等于只能同时构建一个任务。每实例额度与全局额度应分别设计，避免扩容后突破下游资源容量。

不同服务实例可以拥有各自的 Worker。是否拆分查询与构建角色、同仓库任务是否允许并行，需要结合源码工作区和构建组件约束确定。

## 5. 退出与恢复

停止时先暂停领取，再按约定等待或取消正在执行的任务。执行超时、进程异常和失效接管需有可追踪的状态及归属检查。

失败后的新尝试应保留历史记录。模型调用、制品写入和发布等副作用需要分别处理重试，不能只靠领取去重保证全过程恰好执行一次。
