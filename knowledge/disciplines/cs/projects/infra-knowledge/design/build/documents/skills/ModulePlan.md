# 模块规划 Skill

模块规划阶段调查源码的职责边界，形成供后续模块文档执行的任务计划。它属于可选模块文档能力。

## 1. 输入

当前安全源码、任务说明，以及适用的已有模块计划与增量资料。

## 2. 处理职责

- 根据源码职责划分模块，避免只按目录机械切分。
- 为每个模块确定稳定标识、主题范围和相关源码。
- 明确模块页面任务，使后续执行有可检查的边界。

## 3. 输出与后续执行

输出结构化模块计划，例如 `modules/plan.json`。计划通过校验后，再按任务执行模块设计阶段。

模块规划与模块设计可以复用同一 Skill 的不同阶段指令；计划本身不等于模块文档已经生成。

## 4. 具体规划步骤

1. 从生产代码装配、入口注册、后台任务、生命周期与状态归属建立职责图。
2. 按职责及故障边界选择模块；不要求每个目录、类或函数都有页面，小仓库可以只有一个模块。
3. 为模块指定稳定标识、入口、依赖、关键问题、源码证据与未解决事项。
4. 增量时对每个旧模块明确选择创建、更新、复用或删除，持续职责保留稳定标识。
5. 拆分或合并时记录旧标识关系，检查活动模块、依赖引用和证据完整性。

## 5. 计划内容示例

```json
{
  "modules": [{
    "id": "task-execution",
    "title": "Task Execution",
    "responsibility": "Claim and execute queued tasks",
    "action": "create",
    "reason": "Separate execution and failure boundary",
    "entryPoints": ["Worker.Run"],
    "dependencies": [],
    "questions": ["When is a task considered complete?"],
    "evidence": ["internal/worker.go"],
    "priorIds": [],
    "unresolved": []
  }],
  "gaps": []
}
```

以上仅为通用结构示例，实际标识、字段校验与数量上限由计划契约规定。

## 6. 决策与完成条件

复用必须证明相关证据、引用和保证仍有效；影响不确定时选择更新，不用复用掩盖未完成调查。退役模块明确删除，依赖只引用活动模块且不引用自身。

计划是结构化产物，不在这一阶段编写全部模块页面。对照发现的装配与职责检查一次后，将计划交给校验及后续页面执行。
