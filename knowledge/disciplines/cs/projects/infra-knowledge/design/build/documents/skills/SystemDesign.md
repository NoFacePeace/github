# 系统设计 Skill

系统设计 Skill 从安全源码中梳理系统用途、架构组成、关键组件及主要执行链路，生成系统设计文档。

## 1. 调查重点

- 程序入口、启动过程和依赖装配。
- 核心组件的职责、边界及调用关系。
- 关键业务链路、状态变化与数据流。
- 外部依赖、持久化、后台任务及失败处理。

## 2. 输入与输出

输入为当前安全源码、任务说明及清单；增量时补充旧文档与基线差异。输出为完整系统设计页面，例如 `design/system-design.md`。

## 3. 证据要求

通过入口与调用链确认实际行为，区分源码事实、推断和未确认内容。引用文件与行号，不将目录名直接等同于运行架构。

## 4. 具体调查步骤

1. 从启动装配、已注册入口、后台任务和状态存储建立初始组件与流程图。
2. 每次沿一条完整链路调查触发条件、参与组件、状态变化和真正的完成条件。
3. 继续追踪超时、取消、重试、部分失败及恢复路径，说明副作用和并发边界。
4. 将资源竞争、配置生效与观测信号放回相关机制，解释相似症状可能对应哪些原因，以及如何区分。
5. 对照已发现的入口和组件检查一次覆盖范围，记录缺失证据，完成文档。

## 5. 输出格式与内容

系统设计 Skill 内置 Markdown 模板，明确规定输出标题、二级章节及其顺序。固定的是文档骨架和分析要求；具体流程、三级标题及解释内容由 Agent 根据实际源码确定。

### 5.1 文件与标题

一次系统设计任务生成一份文档，写入执行环境的 `output/design/system-design.md`，文档产物路径为 `design/system-design.md`。文档以 `# System Design: <repository>` 开头，在正文各节之前标明仓库身份和完整 Commit SHA。

生成产物的标题、正文及解释性表格内容使用英文，保留源码中的准确标识符和字面值。模板中的写作指令应替换为实际分析结果，不把模板标题、写作约定或示例占位内容复制进产物。

### 5.2 固定章节

正文按下表顺序使用 10 个英文二级标题。中文说明用于解释各节职责，不作为生成产物的标题。

| 顺序 | 二级标题 | 内容要求 |
| --- | --- | --- |
| 1 | `Repository Summary` | 一个纯英文段落，概括实际能力、使用者和职责；在分析完成后撰写，放在正文最前面。 |
| 2 | `Reading Guide` | 用简短表格将重要问题或症状映射到实际章节，并说明 API、指标和配置参考文档的用途。 |
| 3 | `Scope and System Boundaries` | 说明解决的问题、职责边界、拥有的对象、外部责任、分析版本和排除范围。 |
| 4 | `Architecture and Runtime Topology` | 说明组件、入口、职责、状态归属、依赖及逻辑组件与进程或节点的映射。 |
| 5 | `Core Flows and Mechanisms` | 按核心能力或完整执行链路组织三级标题，解释触发、步骤、分支、完成条件、失败及恢复。 |
| 6 | `State and Correctness` | 说明重要状态、状态转换、正确性约束及适用的一致性和并发保证。 |
| 7 | `Resources and Capacity` | 沿工作负载、执行过程、资源消耗、瓶颈和容量边界分析，区分配置值、推断值和实际观测。 |
| 8 | `Cross-cutting Runtime Controls` | 说明实质共享的可靠性、配置与生命周期、部署变更、安全与隔离机制。 |
| 9 | `Observability and Evidence Navigation` | 将重要机制映射到日志、指标、追踪或状态入口，解释信号含义及其无法证明的内容。 |
| 10 | `Coverage and Knowledge Gaps` | 记录已覆盖组件和流程、实质排除范围、证据冲突、缺失依赖及需要运行环境确认的事项。 |

仓库摘要最多 200 个 `cl100k_base` tokens，建议 100–150；不使用列表、链接、行内 Markdown、源码引用或版本变更内容。

### 5.3 章节组织与证据

每条核心流程或实质共享机制使用描述性的三级标题，不按源码目录、类或函数逐个生成章节。条件、行为、失败和证据放在同一机制中，使章节被单独检索时仍可理解；不按任意 token 数切断因果链。

核心流程要同时说明正常行为、分支、失败传播、恢复条件和证据。例如任务服务应解释“提交成功”“领取成功”“执行结束”“结果可见”是否属于不同阶段。

重要结论附近附仓库相对路径与符号，适用时加行号，例如 `internal/worker.go:Run`。这些定位信息对应文档标明的仓库和版本，不包含临时执行目录或宿主机绝对路径。

接口、指标与配置仅保留解释机制必需的内容；完整目录由对应主题负责。源码事实、设计陈述、测试代码、运行观测和推断应明确区分，不能把静态分析写成已经完成运行验证。

小仓库保持章节简洁，将不适用的内容及原因集中说明在覆盖范围与知识缺口中；缺失证据标为未知，不把未知当作不适用，不保留空表、示例行或占位文字。

## 6. 保存与完成条件

尽早保存骨架，按完整流程或共用机制分批保存；恢复执行时读取已有输出，继续尚未完成的部分。覆盖关键入口、执行链路及实质知识缺口后结束，文档长度不是质量目标。
