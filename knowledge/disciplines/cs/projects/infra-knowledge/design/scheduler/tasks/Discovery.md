# 版本发现任务

版本发现任务周期检查仓库关注的版本来源，将确认的提交交给版本登记与构建请求流程。本文为 Infra 知识库的设计规划，按统一职责组织说明；不同来源是否共用执行循环与周期，需在实现时确定。

## 1. 输入与输出

- 输入：已登记仓库、[跟踪方式](../../../features/documents/repositories/tracking/Tracking.md)、选择规则及来源访问配置。
- 输出：仓库身份、完整 Commit SHA、来源信息，以及按策略登记的构建请求。

读取的仓库信息与跟踪配置，其持久化设计见 [MySQL 仓库存储](../../mysql/Repositories.md)。

## 2. 共同流程

```text
读取仓库与跟踪配置
  → 查询对应版本来源
  → 按规则筛选候选
  → 解析并校验完整 Commit SHA
  → 调用版本登记能力
  → 按策略请求构建
```

发现版本、登记版本与创建构建是不同步骤。多个引用指向同一 SHA 时复用版本身份，是否构建需另外判断。

- [Commit 存储](../../mysql/Commit.md)：登记完整 SHA 对应的源码版本，并处理重复发现。
- [Build 存储](../../mysql/Build.md)：关联已登记版本，保存构建请求对应的执行尝试与状态。

## 3. 版本来源

### 3.1 Tag

查询标签，按匹配与版本选择规则筛选，再解析到实际提交。附注 Tag 需要解引用，不能将标签对象 ID 当作 Commit SHA。

需要明确分页、排序、首次扫描范围及标签移动的处理方式。查询失败不能视为所有标签被删除。

### 3.2 分支

确定指定或默认分支，查询 HEAD 并解析完整 SHA。构建使用本次确定的 SHA，不在执行时重新追随最新 HEAD。

周期检查可能遗漏两轮之间的中间提交；需要逐提交处理时，应补充事件接入或历史补扫。分支删除、强制推送和默认分支变化需分别处理。

### 3.3 部署版本

查询目标环境及观察范围内的运行版本，检查信息完整性和收敛条件，再通过可靠的制品元数据映射到源码提交。

滚动发布、信息缺失或映射不唯一时暂缓确认。回滚可以复用历史版本身份；多版本共存需要明确选择规则，不能猜测源码 SHA。

## 4. 执行边界

- 每轮可以处理多个仓库，不必为每个仓库创建独立定时循环。
- 仓库跟踪配置中途变化时，应避免过期观察结果覆盖新的选择。
- 单个来源失败、权限不足、提交不可获取等情况需记录诊断，是否继续其他仓库应明确约定。
- 任务负责发现与请求，不在扫描循环中同步完成文档或图谱生成。
- 确认部署版本来源不代表证明系统运行健康。
