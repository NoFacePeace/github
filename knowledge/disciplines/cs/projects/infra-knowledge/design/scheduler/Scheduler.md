# 调度器

调度器负责按照约定周期调用后台处理函数，是文档、图谱及其他后台功能可以共用的基础能力。本文为 Infra 知识库的设计规划，不限定具体实现或部署方式。

## 1. 职责

- 注册定时任务及其执行函数。
- 根据周期与启动策略决定调用时机。
- 管理循环启动、取消和退出。
- 记录每轮执行结果，按约定处理错误与重复执行。

具体处理函数负责查询版本、领取构建或刷新数据，调度器不承担这些业务逻辑。

各类周期处理见 [定时任务](tasks/Tasks.md)。

## 2. 定时任务与构建任务

| 类型 | 含义 | 生命周期 |
| --- | --- | --- |
| 定时任务 | 按周期调用一个处理函数 | 持续运行，直到停止或取消 |
| 构建任务 | 对指定仓库版本执行一次构建 | 等待、执行，最终成功或失败 |

例如：

```text
定时调用 Worker 的领取函数
  → 查询待执行构建
  → 领取某个仓库版本的任务
  → 启动一次构建
  → 构建结束
```

反复执行的是领取检查，不是同一个版本的构建。两类任务应分别建模，避免混用执行周期与构建状态。

## 3. 定时任务配置

| 信息 | 用途 |
| --- | --- |
| 名称 | 标识任务类型 |
| 执行函数 | 定义每轮调用的处理逻辑 |
| 周期 | 决定调用频率 |
| 启动策略 | 立即执行或等待首个周期 |
| 启用状态 | 控制是否启动该任务 |

超时、失败后等待时间、同类任务是否允许重叠等行为，需要明确约定，不能仅由周期推断。

## 4. 运行过程

```text
加载配置
  → 注册启用的定时任务
  → 启动各任务循环
  → 等待调用时机
  → 执行处理函数并记录结果
  → 等待下一轮
```

停止时通知处理函数取消，并按约定等待退出。单轮执行失败是否继续循环、如何重试，应由明确策略决定。

## 5. 并发与部署边界

新增仓库通常增加扫描函数处理的数据，不需要为每个仓库单独注册定时循环。

单进程内避免同类任务重叠，不代表多实例之间已经协调。多实例部署需另行选择执行归属、重复处理防护及失效恢复机制。

调度器可以内嵌于服务，也可以由独立进程或外部调度设施承载；具体方案随执行成本与部署需求确定。
