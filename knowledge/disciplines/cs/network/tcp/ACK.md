# ACK 标志

ACK（Acknowledgment，确认）是 TCP 首部中的一个控制标志，表示确认号字段有效。ACK 置为 `1` 时，确认号表示发送该报文的一方下一步期望收到的序列号。

## 1. 标志与确认号的区别

ACK 标志只有一个位，取值为 `0` 或 `1`；确认号是一个 32 位数值，标识确认到的位置。

```text
ACK 标志 = 1     → 确认号字段有效
确认号   = 1101  → 下一步期望收到序列号 1101
```

抓包或时序图中的 `ACK=1101` 通常是在描述确认号，而不是说 ACK 标志的值为 `1101`。ACK 标志没有置位时，不应把确认号字段当作有效的确认信息。

## 2. 累计确认

TCP 使用累计确认。若接收方连续收到序列号 `1001`～`1100` 的数据字节，就可以发送设置 ACK 标志、确认号为 `1101` 的报文段。

```text
发送方                               接收方
  | ---- Seq=1001, Len=100 ---------> |
  | <--- ACK 标志=1, Ack=1101 ------- |
```

确认号表示连续数据之后的下一个期望位置，不是最后收到的字节编号。接收方可能延迟确认，或用一个确认覆盖多个报文段，并非每个数据报文段都对应一个独立 ACK。

## 3. 在握手中的作用

常见的三次握手中，客户端首先发送 SYN，服务器发送 `SYN + ACK`，客户端再发送 ACK。

服务器的 ACK 确认客户端的 SYN，客户端最后的 ACK 确认服务器的 SYN。由于 SYN 占用一个序列号，对一个不携带数据的 SYN 的确认号为其初始序列号加 `1`，并按模 `2^32` 运算。

## 4. 纯 ACK 与携带数据的 ACK

纯 ACK 报文段通常没有数据，仅携带确认号、窗口等信息。ACK 也可以与本方向的数据一起发送，这通常称为捎带确认（Piggybacked Acknowledgment）。

```text
纯 ACK：     [ TCP 首部：ACK=1 ][ 无数据 ]
捎带确认：   [ TCP 首部：ACK=1 ][ 本方向的数据 ]
```

ACK 标志本身不占用序列号。不携带数据且没有 SYN、FIN 的纯 ACK 不推进发送序列号；携带数据的报文段则按数据字节数消耗序列空间。

## 5. 重复 ACK 与确认限制

累计确认号不前进的重复 ACK 可以帮助发送方判断前方可能存在缺失数据。经典快速重传算法在收到三个重复 ACK 后触发重传，但重复 ACK 也可能由网络乱序引起，不能单凭它认定数据一定丢失。

TCP 确认表示对端 TCP 已接收数据，不表示对端应用已读取、处理或持久化。业务处理成功仍需要由应用协议确认。
