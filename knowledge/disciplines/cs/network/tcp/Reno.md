# TCP Reno

Reno 是一种经典的 TCP 拥塞控制算法，名称来自早期实现它的 BSD 系统版本。它结合慢启动、拥塞避免、快速重传和快速恢复，根据确认与丢失反馈调整发送量。

## 1. 核心机制

| 机制 | 作用 |
| --- | --- |
| 慢启动 | 从较小拥塞窗口开始，快速探测网络容量 |
| 拥塞避免 | 更谨慎地增加拥塞窗口 |
| 快速重传 | 收到三个重复 ACK 后，重传疑似丢失的数据 |
| 快速恢复 | 调整快速重传后的窗口，维持恢复期间的数据传输 |

发送方维护拥塞窗口 cwnd 和慢启动阈值 ssthresh，同时还需满足接收方通告的接收窗口 rwnd。cwnd 和 ssthresh 都是发送方内部状态，不是 TCP 首部中的字段。

## 2. 窗口增长

慢启动时，在持续有数据可发、每个报文段都分别得到确认等理想条件下，cwnd 大约每个 RTT 翻倍。达到慢启动阈值附近后，通常进入拥塞避免。

拥塞避免时，cwnd 大约每个 RTT 增加 1 MSS。这种加性增长与丢失后的乘性减小共同构成 AIMD（Additive Increase, Multiplicative Decrease）的思路。

```text
示意，单位为 MSS，假设初始窗口为 1、阈值为 8：

cwnd：1 → 2 → 4 → 8 → 9 → 10 → 11 → …
      慢启动阶段       拥塞避免阶段
```

这只是经典模型的示意，不表示实际初始窗口一定为 1 MSS；延迟确认、应用发送量和接收窗口等都会影响增长。

## 3. 三个重复 ACK 后的处理

经典 Reno 收到三个重复 ACK 后，触发快速重传并进入快速恢复：

```text
ssthresh = max(FlightSize / 2, 2 × MSS)
重传缺失数据
cwnd = ssthresh + 3 × MSS
```

FlightSize 表示已发送但尚未被累计确认的数据量，不一定等于 cwnd。恢复期间，每收到一个额外重复 ACK，cwnd 增加 1 MSS；窗口允许时可以继续发送新数据。

收到使累计确认号前进的 ACK 后，经典 Reno 退出快速恢复，将 cwnd 收缩到 ssthresh，继续拥塞避免。这套规则适合解释单处丢失的恢复，但在多处丢失时可能过早退出。

## 4. 重传超时后的处理

RTO 超时意味着缺少及时的确认进展，经典 Reno 采用更保守的策略。首次针对相应丢失数据发生超时时，通常执行：

```text
ssthresh = max(FlightSize / 2, 2 × MSS)
cwnd = 1 × MSS
重传最早尚未确认的数据
RTO 加倍，重新启动定时器
```

随后重新慢启动，接近阈值后转入拥塞避免。对同一批数据连续超时时，不应简单地理解为每次都再次将 ssthresh 减半。

## 5. 与 Tahoe、NewReno 的区别

| 算法 | 主要区别 |
| --- | --- |
| Tahoe | 具有慢启动、拥塞避免和快速重传；快速重传后也将 cwnd 降至 1 MSS，重新慢启动 |
| Reno | 增加快速恢复，三个重复 ACK 后通常不立即退回 1 MSS |
| NewReno | 改进部分确认的处理，使一个窗口内多处丢失时可以继续恢复 |

NewReno 记录恢复边界，在只确认部分恢复数据时继续重传下一处缺失数据，直到恢复前的数据全部得到确认后再退出。支持 SACK 的实现还可以利用更具体的已接收范围改善恢复。

## 6. 现代使用与局限

Reno 仍可用于现代系统，也常作为解释 TCP 拥塞控制的经典模型，但并非所有系统的默认算法。现代 Linux 通常默认使用 CUBIC，并支持选择 Reno；部分部署使用 BBR，具体选择取决于系统和配置。

在高带宽、长 RTT 的路径上，Reno 降低窗口后，以每个 RTT 约增加 1 MSS 的速度恢复可能较慢。CUBIC、BBR 等算法采用不同的增长或建模方式，不能直接套用 Reno 的全部窗口规则。

拥塞控制算法的选择与丢失检测、重传实现也不是完全绑定的。例如，系统可以在保留 Reno 窗口增长逻辑的同时，使用 SACK 等机制改进丢失恢复。
