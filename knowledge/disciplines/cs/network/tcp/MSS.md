# 最大报文段长度

MSS（Maximum Segment Size，最大报文段长度）表示一个 [TCP 报文段](Segment.md)能够承载的最大数据长度，单位为字节，不包含 TCP 首部和 IP 首部。

## 1. 与报文段长度的区别

```text
IP 数据包
├── IP 首部
└── TCP 报文段
    ├── TCP 首部
    └── TCP 数据 ← MSS 限制的是这部分的长度
```

MSS 限制的是 TCP 数据部分，而不是整个 TCP 报文段。实际发送的数据可以小于 MSS，并非每个报文段都必须填满。

## 2. 与 MTU 的关系

MTU 限制一个链路能够承载的 IP 数据包大小，MSS 限制 TCP 报文段的数据长度。在不包含 IP 和 TCP 选项的情况下，常用的计算方式为：

```text
MSS = MTU - IP 固定首部长度 - TCP 固定首部长度

IPv4：1500 - 20 - 20 = 1460 字节
IPv6：1500 - 40 - 20 = 1440 字节
```

这些示例假设 MTU 为 1500 字节。实际发送时，如果存在 TCP 选项、IPv4 选项或 IPv6 扩展首部，发送方还需要为这些额外首部留出空间，减少数据长度，以避免超过路径 MTU。

## 3. 为什么尽量避免 IP 分片

IPv4 可以在允许分片时拆分过大的 IP 数据包，但 TCP 通常会先控制报文段的数据长度，使封装后的 IP 数据包适合路径 MTU，尽量避免依赖 IP 分片。

例如，路径 MTU 为 1500 字节，使用 IPv4 且没有 IP、TCP 选项时：

```text
TCP 数据为 1500 字节：
IP 首部 20 + TCP 首部 20 + TCP 数据 1500 = 1540 字节
超过路径 MTU，需要分片或调整发送大小。

TCP 数据为 1460 字节：
IP 首部 20 + TCP 首部 20 + TCP 数据 1460 = 1500 字节
符合路径 MTU，无需 IP 分片。
```

避免分片主要有以下原因：

- **额外开销**：每个分片都需要 IP 首部，接收方还需缓存分片并重组原始 IP 数据包。
- **丢失代价**：任意一个分片丢失，原始 IP 数据包就无法完整重组，TCP 接收方也无法获得其中的报文段。TCP 需要重传对应的数据，不能只要求重传某一个 IP 分片。
- **分片限制**：IPv4 设置 DF（Don't Fragment，禁止分片）时不允许分片；IPv6 路由器不能分片，只能由源主机执行分片。

TCP 分段与 IP 分片发生在不同层级：TCP 分段产生多个各自带有 TCP 首部的报文段；IP 分片则拆分一个已经封装好的 IP 数据包，并由目的主机在 IP 层重组。

对端通告的 MSS 和路径 MTU 是两个独立限制，通告的 MSS 不保证始终小于路径上每条链路的 MTU。发送方通常通过路径 MTU 发现等机制确定可用大小，并同时满足对端 MSS 与路径 MTU 的限制；实际每段的数据长度可能小于通告的 MSS。

## 4. MSS 选项

TCP 在建立连接时，可以通过 SYN 报文段中的 MSS 选项通告自己能够接收的最大 TCP 数据长度。该选项长 4 字节，其中 MSS 数值字段占 16 位。

双方分别通告 MSS，两个方向的限制可以不同。这并不是双方协商出一个共同值：客户端通告的 MSS 约束服务器发往客户端的数据，服务器通告的 MSS 约束客户端发往服务器的数据。

例如，客户端通告 MSS 为 `1460`，服务器通告 MSS 为 `1440`：

- 客户端向服务器发送时，单个报文段的数据长度不应超过 `1440` 字节。
- 服务器向客户端发送时，单个报文段的数据长度不应超过 `1460` 字节。

发送方还需结合路径 MTU 等条件，实际可发送的数据长度可能更小。

## 5. 与应用消息的关系

MSS 不限制一条应用消息的总长度。较大的应用消息可以由 TCP 分成多个报文段发送，接收方再将数据重组为字节流。

例如，在实际每段最多承载 1460 字节数据的情况下，3000 字节的应用数据可以拆成 `1460 + 1460 + 80` 字节发送；实际分段方式还取决于发送时机、窗口大小等因素。
