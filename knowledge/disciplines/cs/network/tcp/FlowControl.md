# TCP 流量控制

TCP 流量控制（Flow Control）用于避免发送方发送的数据超过接收方的接收能力。接收方通过 TCP 首部的窗口字段通告接收窗口（rwnd，Receive Window），发送方据此限制尚未确认的数据量。

## 1. 为什么需要流量控制

网络传输数据的速度可能超过接收方应用读取数据的速度。TCP 接收方需要把收到的数据暂存在接收缓冲区中；如果发送方持续发送，缓冲区可能被耗尽。

```text
发送方 → 网络 → 接收方 TCP 缓冲区 → 接收方应用
                      ↑                 |
                暂存已收到的数据    读取并释放空间
```

流量控制根据接收方可接收的数据量限制发送，应用读取数据、释放空间后，接收方可以通告更大的窗口。

## 2. 接收窗口

接收方在报文中通过确认号和窗口大小描述可以接收的序列号范围。忽略序列号回绕时，可表示为：

```text
接收范围：[ACK, ACK + rwnd)

ACK  = 1001
rwnd = 3000 字节

允许接收的字节序列号：1001～4000
```

窗口描述的是一个字节范围，不是允许发送的报文段数量。双方分别通告窗口，两个方向的流量控制相互独立。

接收窗口与接收缓冲区可用空间密切相关，但通告值还受到操作系统的缓冲区管理和窗口更新策略影响，不一定等于某一时刻的全部空闲空间。

## 3. 滑动窗口与发送限制

随着接收方连续收到数据、确认号前进，允许发送的序列号范围也向前移动，这称为滑动窗口（Sliding Window）。发送方可以在等待确认的同时发送窗口允许范围内的后续数据，不必每发送一个报文段就等待一次确认。

```text
接收方通告：ACK=1001，rwnd=3000
发送方已发送但未确认：1001～2000，共 1000 字节

仅考虑接收窗口：还能发送 2001～4000，共 2000 字节

接收方随后通告：ACK=2001，rwnd=3000
新的接收范围：2001～5000
```

实际发送量同时受接收窗口和拥塞窗口（cwnd）限制。在常见的简化模型中：

```text
允许在途的数据量 ≈ min(rwnd, cwnd)
可继续发送的新数据量 ≈ max(0, min(rwnd, cwnd) - 已在途数据量)
```

该公式帮助理解两个窗口的共同作用；实际实现还会考虑窗口边界、丢失恢复、发送节奏等因素。

## 4. 零窗口与窗口探测

接收方暂时无法接收更多数据时，可以通告 `rwnd=0`。发送方应暂停普通新数据的发送，但连接并未因此关闭。

应用读取数据并释放空间后，接收方可以发送窗口更新，重新通告非零窗口。如果窗口更新丢失，双方可能陷入一方等待数据、另一方等待窗口恢复的状态。

发送方通过持续定时器（Persist Timer）安排零窗口探测（Zero Window Probe），促使接收方返回当前的确认号和窗口信息，避免因窗口更新丢失而长期停滞。

```text
接收方通告 rwnd=0 → 发送方暂停普通新数据
发送方进行窗口探测 → 接收方回复当前窗口
接收方通告 rwnd>0 → 发送方可在窗口允许范围内继续发送
```

零窗口探测用于检查接收能力是否恢复，与判断数据可能丢失的超时重传作用不同。

## 5. 窗口扩大选项

TCP 首部的窗口字段为 16 位，未使用窗口扩大时，最大通告值为 `65535` 字节。

双方可以在建立连接时通过窗口扩大选项（Window Scale）交换各自的缩放因子，使后续报文能够表示更大的接收窗口：

```text
实际接收窗口 = 窗口字段值 × 2^缩放因子

窗口字段值 = 32768，缩放因子 = 4
实际接收窗口 = 32768 × 16 = 524288 字节
```

缩放因子最大为 `14`，两个方向可以不同。窗口扩大仅在双方均支持并交换该选项时启用；SYN 报文自身的窗口字段不进行缩放。

## 6. 与拥塞控制的区别

| 机制 | 关注对象 | 主要限制 |
| --- | --- | --- |
| 流量控制 | 接收方是否能够接收更多数据 | 接收窗口 rwnd |
| 拥塞控制 | 网络是否能够承受更多在途数据 | 拥塞窗口 cwnd |

即使网络畅通，接收方应用读取过慢也可能使接收窗口变小；即使接收方空间充足，网络拥塞也可能使发送方减少发送量。
