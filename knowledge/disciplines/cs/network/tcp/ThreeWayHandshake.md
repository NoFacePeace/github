# TCP 三次握手

三次握手（Three-Way Handshake，常缩写为 3WHS）是 TCP 常见的连接建立过程。双方通过 [SYN](SYN.md)、SYN + ACK 和 [ACK](ACK.md) 同步[初始序列号](InitialSequenceNumber.md)、确认对方的连接请求，并交换参数和能力信息。

## 1. 握手过程

假设客户端初始序列号为 `1000`，服务器初始序列号为 `5000`，三个报文段都不携带应用数据：

图中的 `Seq` 表示[序列号](SequenceNumber.md)，`Ack` 表示[确认号](AcknowledgmentNumber.md)。

```text
客户端                                      服务器
CLOSED                                      LISTEN
  |                                            |
  | ---- SYN, Seq=1000 -----------------------> |
SYN-SENT                                       |
  |                                          SYN-RECEIVED
  | <--- SYN + ACK, Seq=5000, Ack=1001 --------- |
  |                                            |
ESTABLISHED                                    |
  | ---- ACK, Seq=1001, Ack=5001 --------------> |
  |                                          ESTABLISHED
```

### 1.1 第一次：SYN

客户端主动发起连接，发送 SYN，通告自身的初始序列号，并进入 SYN-SENT 状态。SYN 中还可以携带 MSS、窗口扩大、SACK 许可等选项。

### 1.2 第二次：SYN + ACK

服务器接受请求后，发送 SYN + ACK，确认客户端的 SYN，同时通告自身的初始序列号，进入 SYN-RECEIVED 状态。

SYN 占用一个序列号，因此确认号为 `1001`，表示下一步期望收到客户端序列号为 `1001` 的内容。

### 1.3 第三次：ACK

客户端收到并验证 SYN + ACK 后，确认服务器的 SYN，发送确认号为 `5001` 的 ACK，并进入 ESTABLISHED 状态。服务器收到并验证该 ACK 后，也进入 ESTABLISHED 状态。

双方进入已建立状态的时刻不同，不能把第三次发送 ACK 理解为双方同时完成连接建立。

## 2. 为什么需要三次

TCP 的两个方向有各自独立的序列号空间，双方都需要通告初始序列号，并获得对方的有效确认。

```text
第一次：客户端通告自身初始序列号
第二次：服务器确认客户端，并通告自身初始序列号
第三次：客户端确认服务器
```

第二次报文把“确认客户端”和“通告服务器”合并，因此常见过程是三次，而不是四次。只有前两次时，服务器还没有收到对自己初始序列号的确认。

这一机制也帮助服务器避免仅凭一个延迟到达的旧 SYN 就把连接认定为已建立。不过，三次握手不提供身份认证，也不保证随后网络不会中断。

## 3. 序列号与数据

SYN 各占用一个序列号，不携带数据的纯 ACK 不占用序列号。示例握手完成后，客户端和服务器的第一个数据字节分别从 `1001` 和 `5001` 开始编号。

第三次 ACK 可以同时携带客户端数据。某些机制还允许 SYN 携带数据，例如满足相应条件的 TCP Fast Open；这时需要把数据字节数也计入确认位置，不能直接套用无数据示例。

## 4. 参数与能力交换

握手中的 SYN 报文段可以通告或协商以下信息：

- **MSS**：各自能够接收的最大 TCP 数据长度，两个方向可以不同。
- **窗口扩大**：各自的接收窗口缩放因子，需要双方支持才能启用。
- **SACK 许可**：表明是否支持接收选择性确认信息。
- **时间戳与 ECN 等能力**：按各自规则交换或协商。

这些参数并非都协商成一个双方共用的数值，具体生效条件取决于对应机制。

## 5. 丢失与重传

SYN 或 SYN + ACK 丢失时，发送方可以在超时后重传。第三次纯 ACK 没有独立的重传定时器；如果服务器未收到它而重传 SYN + ACK，客户端通常会再次发送 ACK。

连接尝试长期无法完成时，系统可能向应用报告超时；服务器也可能拒绝请求并返回 RST。因此，发出 SYN 不意味着连接必然成功。
