# TCP 拥塞控制

TCP 拥塞控制（Congestion Control）根据网络状况调整发送量，避免过多数据使网络队列持续积压、时延上升或大量丢包。发送方通过确认、丢失、往返时间和显式拥塞通知等信息判断网络状态，具体使用哪些信号取决于算法。

## 1. 为什么需要拥塞控制

多条连接可能共享同一个瓶颈链路。当总发送速率长期超过链路的转发能力时，网络设备的队列会积压，队列满后可能丢包。持续重传而不减少发送量，还可能进一步加剧拥塞。

```text
连接 A ─┐
连接 B ─┼→ 网络队列 → 瓶颈链路 → 接收方
连接 C ─┘     ↑
         到达速度超过转发速度时，队列积压
```

拥塞控制用于探测网络能够承受的发送量，并在发现拥塞时调整发送行为。

## 2. 拥塞窗口与发送量

拥塞窗口（cwnd，Congestion Window）是发送方维护的内部状态，限制允许在途、尚未确认的数据量，不是 TCP 首部中的窗口字段。

接收窗口（rwnd）反映接收方的接收能力，拥塞窗口反映发送方对网络承载能力的判断。常见的简化模型为：

```text
允许在途的数据量 ≈ min(cwnd, rwnd)
可继续发送的新数据量 ≈ max(0, min(cwnd, rwnd) - 已在途数据量)
```

窗口限制的是数据量，不直接等于发送速率。在窗口受限且持续发送的简化场景中，吞吐量可近似理解为窗口大小除以 RTT；实际速率还受到链路带宽、发送节奏和应用供给等因素限制。

## 3. 慢启动

[慢启动（Slow Start）](SlowStart.md)从较小的初始拥塞窗口开始，通过收到的确认逐步增加窗口，探测可用容量。

在经典模型中，若每个报文段都得到确认且没有其他限制，cwnd 大约每经过一个 RTT 翻倍：

```text
示意，单位为 MSS：
初始窗口 → 1 → 2 → 4 → 8 → …
```

这里的 `1 MSS` 仅用于演示增长过程，不表示所有实现的实际初始窗口都是 1 MSS。延迟确认、接收窗口和应用发送量等也会影响实际增长。

慢启动阈值（ssthresh，Slow Start Threshold）用于区分慢启动与拥塞避免。经典算法通常在 cwnd 小于 ssthresh 时使用慢启动，超过阈值后使用拥塞避免。

## 4. 拥塞避免

[拥塞避免（Congestion Avoidance）](CongestionAvoidance.md)以更谨慎的方式增加窗口，减少持续快速增长造成的拥塞。

在经典 [Reno](Reno.md) 模型中，窗口大约每个 RTT 增加 1 MSS；检测到拥塞时则降低窗口。这体现了加性增大、乘性减小（AIMD，Additive Increase, Multiplicative Decrease）的思路。

```text
窗口逐步增加 → 检测到拥塞 → 降低窗口 → 再逐步增加
```

这些增长规则不是所有 TCP 算法的统一行为。例如，CUBIC 使用基于时间的三次函数调整窗口，BBR 则根据带宽和传播时延估计等建立模型。

## 5. 丢失后的调整

### 5.1 超时

重传超时通常被视为较强的拥塞信号。在经典 Reno 的[超时恢复](TimeoutRecovery.md)流程中，发送方根据在途数据量降低 ssthresh，将 cwnd 降到 1 MSS，然后重新慢启动；重传定时器也采用指数退避。

具体实现和算法的行为可能不同，不能把所有超时后的调整都概括为固定的“窗口减半”。

### 5.2 快速重传与快速恢复

经典快速重传在收到三个重复 ACK 后重传疑似丢失的数据。Reno 配合[快速恢复（Fast Recovery）](FastRecovery.md)，降低慢启动阈值，并利用重复 ACK 所反映的数据离开网络的信息调整窗口，恢复后进入拥塞避免。

快速重传解决的是重新发送可能丢失的数据，快速恢复解决的是恢复期间如何控制发送量。SACK 和其他丢失检测机制可以改善多处丢失时的恢复行为。

丢包也可能由链路错误或其他原因引起，不一定都是拥塞；基于丢失的算法通常仍会把它作为可能的拥塞信号处理。

## 6. 显式拥塞通知

显式拥塞通知（ECN，Explicit Congestion Notification）允许支持它的网络设备通过 IP 层标记反馈拥塞，而不必先丢弃报文。

经典 ECN 中，接收方通过 TCP 的 ECE 标志反馈拥塞，发送方降低发送量后通过 CWR 表示已响应。使用 ECN 需要端系统和路径上的相关设备支持，具体响应方式取决于算法。

## 7. 与流量控制的区别

| 机制 | 关注对象 | 主要依据 |
| --- | --- | --- |
| 流量控制 | 接收方是否有能力接收更多数据 | 接收窗口 rwnd |
| 拥塞控制 | 网络是否能够承受更多在途数据 | 拥塞窗口 cwnd 及其他算法状态 |

接收方缓冲区充足并不代表网络没有拥塞；网络畅通也不代表接收方应用能够及时读取数据。发送方需要同时满足两类限制。
