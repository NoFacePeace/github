# TCP 超时恢复

TCP 超时恢复（Timeout Recovery）指重传定时器到期后，发送方重传尚未确认的数据，并调整拥塞控制状态、重新探测网络容量的过程。它不仅涉及重新发送数据，还涉及拥塞窗口、慢启动阈值和重传定时器的调整。

## 1. 触发条件

发送方仍有未确认的数据，而重传定时器到期时，就进入超时处理。定时器使用重传超时时间（RTO，Retransmission Timeout），其取值根据往返时间及波动估计。

数据丢失、确认丢失或时延显著增加，都可能导致超时。超时并不能证明一定发生了拥塞，但经典 TCP 通常将它作为较强的拥塞信号，采取保守的恢复策略。

## 2. 经典 Reno 的处理

在经典 Reno 模型中，首次针对相应丢失数据发生重传超时时，通常执行：

```text
ssthresh = max(FlightSize / 2, 2 × MSS)
cwnd = 1 × MSS

重传最早尚未确认的数据
RTO 加倍，并重新启动重传定时器
```

FlightSize 表示已发送但尚未被累计确认的数据量，不一定等于 cwnd。对同一批数据连续发生超时时，不应简单地把每次超时都理解为重新将 ssthresh 减半。

降到 `1 MSS` 的是拥塞窗口 cwnd，MSS 本身没有改变。发送方仍需满足接收窗口等限制，窗口恢复也不意味着连接一定能够成功继续传输。

## 3. 恢复过程示例

假设首次超时时在途数据为 `20 MSS`，且接收窗口和应用数据量不构成限制：

```text
超时发生：
  FlightSize = 20 MSS
  ssthresh   = 10 MSS
  cwnd       =  1 MSS

重传得到确认后：
  慢启动：1 → 2 → 4 → 8 → 阈值附近
  随后转入拥塞避免，更谨慎地增加窗口
```

增长序列是理想化示意，实际窗口随 ACK 到达逐步调整，还受延迟确认、恢复中的未确认数据和实现策略等因素影响。

## 4. 指数退避

如果网络持续无法取得进展，重复使用较短的超时会频繁注入重传数据。发送方因此采用指数退避，逐步延长等待时间：

```text
示意：RTO 1 秒 → 2 秒 → 4 秒 → 8 秒 → …
```

该示例不表示所有连接都从 1 秒开始。实际 RTO 有估计值和上下限；连接长期无法恢复时，TCP 可能最终向应用报告超时错误。

## 5. 与其他恢复机制的区别

| 机制 | 作用 |
| --- | --- |
| 超时重传 | RTO 到期后，重新发送尚未确认的数据 |
| 超时恢复 | 包含超时重传，以及窗口调整、定时器退避和后续增长 |
| 快速恢复 | 根据重复 ACK 等丢失反馈，控制快速重传后的发送行为 |

经典快速恢复利用后续数据仍在到达接收方的信息，通常不会立即把 cwnd 降至 `1 MSS`；超时恢复缺少及时的确认进展，因此采用更保守的策略。快速恢复期间若发生 RTO 超时，也会转入超时处理。

## 6. 算法与实现差异

以上窗口调整主要用于解释经典 Reno。不同拥塞控制算法和操作系统实现可能使用不同的状态管理、丢失恢复或虚假超时检测机制，不能把 `cwnd = 1 MSS` 当作所有实现中每次超时后的绝对规则。
