# TCP 确认号

确认号（Acknowledgment Number，常记为 Ack）是 TCP 首部中的 32 位字段，在 ACK 标志置位时有效，表示接收方下一步期望收到的序列号。

## 1. 累计确认

TCP 的确认号用于累计确认，表示在当前连接的序列空间中，此前的数据已连续收到。

```text
收到：Seq=1001，数据长度=100
      字节编号 1001～1100

返回：ACK=1101
含义：已连续收到截至 1100 的数据，下一步期望 1101
```

确认号不是“最后收到的字节编号”，也不是收到的报文段数量。它通常比最后一个连续收到的数据字节的序列号大 `1`，并需考虑 SYN、FIN 和序列号回绕。

## 2. 乱序与重复确认

如果接收方期望 `1001`，却先收到从 `1101` 开始的数据，累计确认号仍为 `1001`，因为前面还存在缺口。

```text
期望收到：1001
收到数据：1101～1200 → ACK=1001
收到数据：1201～1300 → ACK=1001
补齐数据：1001～1100 → ACK=1301
```

这里假设接收方缓存了乱序数据。缺口补齐后，确认号可以直接前进到连续数据末尾之后。多个重复 ACK 可以帮助发送方推断丢失并触发快速重传；重复 ACK 也可能由网络乱序引起。

选择性确认（SACK）可以额外报告已收到的不连续数据范围，但不会改变确认号字段的累计确认含义。

## 3. ACK 标志与确认号的区别

ACK 标志是控制标志中的一个位，表示确认号字段有效；确认号则是一个 32 位数值，表示确认的位置。

```text
ACK 标志 = 1     → 确认号有效
确认号   = 1101  → 下一步期望收到序列号 1101
```

TCP 建立连接后的报文段通常设置 ACK 标志，确认信息可以与本方向的数据一起发送，不一定需要单独发送纯 ACK 报文段。

## 4. SYN、FIN 与确认

SYN 和 FIN 各占用一个序列号，因此不携带数据时也需要确认其后的序列号：

```text
收到 SYN：Seq=1000 → 确认 ACK=1001
收到 FIN：Seq=1301 → 确认 ACK=1302
```

一条连接的两个方向分别维护序列号和确认状态。某一方发出的 Seq 描述本方向发送的数据，Ack 则确认反方向收到的数据，两者不属于同一个字节流。

## 5. 确认的含义与限制

TCP 确认表示数据已被对端 TCP 接收，不代表对端应用已经读取、处理或持久化数据。业务处理是否成功，需要由应用协议另行确认。

确认报文丢失时，发送方可能重传已经到达的数据。接收方会识别重复字节并再次确认，避免向应用重复交付。
