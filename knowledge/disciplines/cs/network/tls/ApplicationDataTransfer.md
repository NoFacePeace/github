# 应用数据传输

这是 TLS 握手后的业务通信阶段，使用应用流量密钥保护 HTTP 请求、响应等内容，不属于握手本身。以下延续基于 TCP 的 TLS 1.3 常规完整握手场景。

## 1. 派生应用密钥

具体派生与使用方式见[应用密钥](ApplicationKeys.md)。

以下为简化的密钥依赖关系：

```text
Handshake Secret → 进一步派生 Master Secret
                              ↓
          结合到服务端 Finished 的握手记录哈希
                              ├─ "c ap traffic" → 客户端应用流量秘密
                              └─ "s ap traffic" → 服务端应用流量秘密
                                                       ↓
                                        各自派生加密密钥 key 和 IV
```

应用密钥与握手密钥使用不同的基础秘密、记录范围和用途标签，实现用途隔离。握手记录参与派生的是消息内容的哈希，不是网络上传输的加密密文。

## 2. 两个方向使用不同密钥

| 方向 | 客户端 | 服务端 |
| --- | --- | --- |
| 客户端 → 服务端 | 用客户端应用密钥加密 | 用客户端应用密钥解密 |
| 服务端 → 客户端 | 用服务端应用密钥解密 | 用服务端应用密钥加密 |

双方各自派生两个方向的密钥，密钥本身无需通过网络传输。方向按发送方命名，服务端接收时使用客户端发送方向的密钥。

## 3. 加密与解密

TLS 将应用字节组织成记录，使用协商的 AES-GCM 或 ChaCha20-Poly1305 等认证加密算法保护：

```text
应用数据 → TLS 记录 → 使用 key、nonce 加密 → 密文与认证标签
                                                 ↓
应用数据 ← 验证成功后解密 ← 接收方验证认证标签 ← 网络传输
```

每条记录的 nonce 由该方向的 IV 与记录序号组合得到。接收方使用对应密钥与 nonce 验证、解密，发现篡改时拒绝接受数据。

## 4. 与 Finished 的边界

客户端可以先发送 Finished，紧接着发送应用数据，两者无需等待新的服务端回复，但属于不同的 TLS 记录：

```text
Finished 记录    → 使用客户端握手流量密钥
应用数据记录    → 使用客户端应用流量密钥
```

它们可能位于同一个 TCP 报文段，也可能分开发送。应用通信期间，可以通过 KeyUpdate 更新应用流量密钥。
