# TLS 握手

TLS 握手用于协商通信参数、认证对端身份并建立保护通信所需的密钥。本文以基于 TCP、使用 ECDHE 密钥交换、仅认证服务器的 TLS 1.3 完整握手为例，不包含会话恢复、0-RTT 和 HelloRetryRequest。

## 1. 握手流程

按学习顺序，从[参数协商与密钥交换](NegotiationAndKeyExchange.md)开始，再进入身份认证与握手确认，最后进入应用数据传输。前两个阶段属于握手，第三个阶段属于握手后的通信；这是便于理解的阶段划分。

TCP 连接建立后，客户端开始 TLS 握手：

```text
客户端                                      服务端
   │                                           │
   │── ClientHello ───────────────────────────→│
   │   支持的版本、密码套件、客户端密钥份额       │
   │                                           │
   │←─ ServerHello ────────────────────────────│
   │   选定的版本、密码套件、服务端密钥份额       │
   │                                           │
   │   双方计算共享秘密，派生握手流量密钥         │
   │                                           │
   │←─ EncryptedExtensions ────────────────────│
   │←─ Certificate ────────────────────────────│
   │←─ CertificateVerify ──────────────────────│
   │←─ Finished ───────────────────────────────│
   │   以上消息使用服务端握手流量密钥加密         │
   │                                           │
   │   客户端验证证书、签名和 Finished           │
   │                                           │
   │── Finished ──────────────────────────────→│
   │   使用客户端握手流量密钥加密               │
   │── HTTP 请求等应用数据 ────────────────────→│
   │   使用客户端应用流量密钥加密               │
```

服务端从 ServerHello 到 Finished 的消息可以连续发送，中间无需等待客户端回复。客户端验证完成后，也可以连续发送自己的 Finished 和应用数据，无需等待服务端再次确认。

### 1.1 Hello 与密钥交换

ClientHello 和 ServerHello 通常是明文，携带协商参数和公开的密钥份额，不携带私钥或共享秘密。

双方各自生成临时私钥和公钥，交换公钥后，结合自己的私钥计算共享秘密：

```text
客户端私钥 + 服务端公钥 → 共享秘密 S
服务端私钥 + 客户端公钥 → 相同的共享秘密 S
```

ECDHE 的数学性质保证双方得到相同结果；旁观者仅凭交换的公钥难以计算该秘密。启用 ECH 时，可以保护包含真实域名等信息的内部 ClientHello，外层 ClientHello 仍然可见。

### 1.2 服务器身份认证

- **EncryptedExtensions**：传递其他协商参数。
- **Certificate**：提供服务器证书；客户端检查信任链、有效期、域名匹配情况等。
- **CertificateVerify**：对握手上下文签名，证明服务端持有证书对应的私钥。
- **Finished**：验证握手记录的完整性，并确认对端掌握对应的密钥材料。

ServerHello 之后的这些握手消息使用握手流量密钥加密。证书主要用于身份认证，HTTP 数据不会直接用证书公钥逐条加密。

### 1.3 Finished 与应用数据

Finished 属于握手消息，内部携带校验值 verify_data，不携带 HTTP 等应用数据。该校验值使用对应方向的 finished_key 对握手记录哈希计算 HMAC 得到；Finished 消息本身再使用对应方向的握手流量密钥加密。

```text
finished_key + 握手记录哈希 → 校验值 → Finished
                                      ↓
                              握手流量密钥加密
```

Finished 与随后发送的 HTTP 数据位于不同的 TLS 记录中，使用不同密钥。它们在 TCP 中可能放入同一个报文段，也可能分开发送。

## 2. 1-RTT 的含义

RTT（Round-Trip Time）表示网络中一次往返所需的时间。常规 TLS 1.3 握手被称为 1-RTT 握手，强调客户端在发送应用数据前，需要等待一次往返：

```text
发 ClientHello → 等服务器整组回复 → 收到并验证
                  约 1 RTT

发 Finished → 紧接着发应用数据，无需再等回复
```

客户端 Finished 仍属于握手；它不需要额外等待一个往返，并不意味着可以省略。服务端收到并验证客户端 Finished 后，服务端一侧的握手才完成。

假设两个方向传播时间相等，忽略处理、排队和消息传输耗时，从发送 ClientHello 起计算：

| 时间点 | 事件 |
| --- | --- |
| 0 | 客户端发送 ClientHello |
| 0.5 RTT | 服务端收到，发送服务器整组握手消息 |
| 1 RTT | 客户端收到并验证，发送 Finished 和应用请求 |
| 1.5 RTT | 服务端收到并验证客户端 Finished，处理请求 |
| 2 RTT | 客户端收到应用响应 |

以上不包含 TCP 建连时间。1-RTT 描述协议引入的往返等待，实际耗时还受网络和处理时间影响；发生 HelloRetryRequest 时会增加往返。

## 3. 密钥派生

### 3.1 HKDF

HKDF 是基于 HMAC 的密钥派生函数，分为提取（Extract）与扩展（Expand）两个步骤，用已有秘密材料生成不同用途、指定长度的秘密或密钥。相同输入和规则产生相同输出，不同用途标签用于隔离不同输出。

TLS 1.3 在 HKDF 基础上定义了带标签和上下文的派生规则。HKDF 本身不加密业务数据，实际加密由 AES-GCM 或 ChaCha20-Poly1305 等算法完成。

### 3.2 握手与应用密钥

下面是简化的依赖关系，不是完整的 TLS 1.3 密钥调度公式：

```text
ECDHE 共享秘密等材料
        ↓
Handshake Secret
        ├─ 结合到 ServerHello 为止的握手记录哈希、方向标签
        │       ↓
        │   握手流量秘密 → 握手加密密钥、IV
        │               → finished_key
        ↓
Master Secret
        └─ 结合到服务端 Finished 为止的握手记录哈希、方向标签
                ↓
            初始应用流量秘密 → 应用加密密钥、IV
```

握手记录参与派生的是消息内容的哈希，不是网络上传输的加密密文。通常握手流量秘密使用的记录范围是 ClientHello 到 ServerHello；发生 HelloRetryRequest 时，记录按协议规定进行特殊处理。

流量秘密是中间材料，再从中分别派生加密算法需要的 key 和 IV。每条记录使用由 IV 和记录序号组合得到的 nonce，配合加密密钥进行认证加密。

握手密钥需要较早生成，以保护证书等后续握手消息；应用密钥则结合更完整的握手记录派生。用途分离也避免同一个密钥同时承担握手保护与业务数据保护。

### 3.3 两个传输方向

同一阶段内，双方使用相同的基础秘密和握手记录，但通过不同的方向标签生成不同流量秘密：

| 用途 | 客户端发送方向标签 | 服务端发送方向标签 |
| --- | --- | --- |
| 握手流量秘密 | `c hs traffic` | `s hs traffic` |
| 初始应用流量秘密 | `c ap traffic` | `s ap traffic` |

因此，初始握手流量与应用流量共有四把主要的记录加密密钥。方向始终按发送方命名，不随观察视角改变：

```text
客户端发送密钥 = 服务端接收密钥
服务端发送密钥 = 客户端接收密钥
```

双方各自派生两个方向的密钥；服务端解密客户端数据时，使用客户端发送方向的密钥，与客户端加密使用的那把相同。密钥本身无需通过网络传输。应用通信期间还可以通过 KeyUpdate 更新应用流量密钥。
