# 参数协商与密钥交换

这是 TLS 1.3 握手的第一阶段，对应 ClientHello 和 ServerHello。以下以基于 TCP、使用 ECDHE 的常规完整握手为例，不包含 HelloRetryRequest、会话恢复和 0-RTT。

## 1. 协商通信参数

1. 客户端发送 **ClientHello**，提供支持的 TLS 版本、密码套件、密钥交换组和客户端密钥份额等信息。
2. 服务端发送 **ServerHello**，返回选定的版本、密码套件和服务端密钥份额等信息。

这两条消息通常明文传输。密钥份额是公开信息，不是私钥或最终加密密钥。启用 ECH 时，可以保护内部 ClientHello 中的敏感信息，外层仍可见。

## 2. 计算共享秘密

概念与用途见[共享密钥与共享秘密](SharedSecret.md)。

双方各自生成临时私钥和公钥，将公钥作为密钥份额交换，私钥保留在本地：

```text
客户端：自己的私钥 + 服务端公钥 → 共享秘密 S
服务端：自己的私钥 + 客户端公钥 → 相同的共享秘密 S
```

ECDHE 的数学性质保证双方计算结果相同。旁观者仅凭交换的公钥难以算出共享秘密，双方也不需要直接传输它。

## 3. 派生握手密钥

具体用途见[握手密钥](HandshakeKeys.md)。

TLS 1.3 使用 HKDF 派生密钥。HKDF 分为提取（Extract）与扩展（Expand），用于将秘密材料转换为不同用途、指定长度的输出。

下面是简化的依赖关系，不是完整密钥调度公式：

```text
共享秘密等材料 → Handshake Secret
                       ↓ 结合到 ServerHello 的握手记录哈希
                       ├─ "c hs traffic" → 客户端握手流量秘密
                       └─ "s hs traffic" → 服务端握手流量秘密
                                                ↓
                                 各自派生加密密钥 key 和 IV
```

同一基础秘密和握手记录，结合不同的方向标签，得到不同方向的流量秘密。流量秘密是中间材料，实际加密使用从中继续派生的 key；IV 用于构造每条记录的 nonce。

双方都能派生两个方向的密钥。同一方向的发送方加密密钥与接收方解密密钥相同，不随观察视角改变。
