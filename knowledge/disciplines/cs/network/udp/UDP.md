# UDP 协议

UDP（User Datagram Protocol，用户数据报协议）是传输层协议，使用端口区分通信端点，在 IP 提供的尽力而为传输基础上发送独立的数据报。

## 1. 传输特点

- **无连接**：发送数据前不需要进行协议握手，也不维护 TCP 式的连接状态。
- **面向数据报**：保留消息边界，每个数据报独立传输，不提供字节流重组服务。
- **尽力而为**：不保证数据到达、按顺序到达或不重复。
- **机制简单**：协议本身不提供确认、重传、流量控制和拥塞控制，所需能力应由上层协议或应用实现。

UDP 无需握手，但这不意味着所有场景下都比 TCP 更快。应用若需要可靠传输、加密或连接管理，仍可能引入额外机制和开销。

## 2. 数据报结构

UDP 首部固定为 8 字节，每个字段为 16 位：

```text
+-------------------------------+-------------------------------+
|          Source Port          |       Destination Port        |
+-------------------------------+-------------------------------+
|             Length            |            Checksum           |
+-------------------------------+-------------------------------+
|                             Data                              |
|                       variable length                         |
+-------------------------------+-------------------------------+
```

| 字段 | 含义 |
| --- | --- |
| 源端口 | 标识发送方端口；未使用时可以为零 |
| 目的端口 | 标识接收方端口 |
| 长度 | UDP 首部与数据的总长度，普通数据报至少为 8 字节 |
| 校验和 | 检测损坏，计算范围包括 IP 伪首部、UDP 首部和数据 |

IPv4 中，校验和字段为零表示未使用 UDP 校验和；IPv6 中通常必须使用，只有特定标准规定的场景例外。校验和不提供加密或身份认证。

## 3. 消息边界与数据大小

UDP 保留数据报边界，不会像 TCP 一样把多条消息合并成供应用读取的字节流。接收接口的缓冲区过小时，数据可能被截断或按接口规则处理，不能假设下次读取可以继续取得同一个数据报的剩余部分。

普通 IPv4 数据报在没有 IP 选项时，UDP 数据最多为 `65507` 字节：

```text
65535（IPv4 总长度上限）- 20（IPv4 首部）- 8（UDP 首部）
= 65507 字节
```

这是协议长度上限，不是推荐的发送大小。实际发送应考虑路径 MTU，尽量避免 IP 分片；任何一个分片丢失，都可能使整个 UDP 数据报无法交付。UDP 没有 TCP 式的 MSS 通告机制。

## 4. 谁控制数据报大小

主要由应用或 UDP 之上的协议控制。应用决定每次交给 UDP 发送的数据长度，UDP 不会像 TCP 一样自动将这些数据分成多个独立的传输层报文。

### 4.1 避免 IP 分片

为了避免超过路径 MTU，单个 UDP 数据报的应用数据长度应满足：

```text
应用数据长度 ≤ 路径 MTU - IP 首部长度 - UDP 首部长度

路径 MTU 为 1500，使用 IPv4 且没有 IP 选项：
1500 - 20 - 8 = 1472 字节

路径 MTU 为 1500，使用 IPv6 且没有扩展首部：
1500 - 40 - 8 = 1452 字节
```

这些是指定条件下的示例，不是所有路径通用的大小。存在额外 IP 首部开销时，需要进一步减少应用数据长度。

操作系统可以通过路径 MTU 发现和“报文过大”等发送错误提供反馈，应用或上层协议需要据此调整大小；不能仅根据本机接口的 MTU 假设整条路径都能承载同样大的数据包。

### 4.2 超过路径 MTU 时的处理

UDP 本身不分片，IP 层是否能够分片取决于协议和配置：

- **IPv4**：允许分片时，源主机或路由器可以分片；设置 DF（禁止分片）时不能分片。
- **IPv6**：路由器不能分片，只能由源主机执行分片。

如果无法分片，可能在本机发送时返回报文过大错误，或由途中路由器丢弃数据包并返回 ICMP 错误；错误反馈也可能丢失或被过滤，应用不能假设每次失败都会收到通知。

```text
一个 UDP 数据报 → IP 分片 → 多个 IP 分片
                                 ↓ 目的主机在 IP 层重组
                         一个完整 UDP 数据报 → 应用
```

IP 分片不改变 UDP 的消息边界。目的主机需要先完成 IP 重组，才能交付完整 UDP 数据报；缺少任何分片都会导致该数据报无法交付，UDP 本身不会重传。

### 4.3 应用自行分块

消息较大时，应用可以将其拆成多个大小适合路径的 UDP 数据报，并定义消息编号、分块编号和总块数等信息，由接收端应用重组。

```text
一条大消息 → 应用分块 → UDP 数据报 A、B、C
                                 ↓ 接收端应用按编号重组
                              一条完整消息
```

这会产生多个独立的 UDP 消息边界，与 IP 分片不同。分块可能丢失、乱序或重复，应用还需根据业务需求处理这些情况，并合理控制发送速率。

## 5. 与 TCP 的区别

| 特性 | UDP | TCP |
| --- | --- | --- |
| 连接建立 | 无需协议握手 | 通常需要三次握手 |
| 数据形式 | 独立数据报，保留消息边界 | 字节流，不保留消息边界 |
| 可靠性 | 协议本身不保证 | 提供可靠、有序的传输 |
| 基础首部长度 | 固定 8 字节 | 20 字节，可通过选项扩展 |
| 流量与拥塞控制 | 协议本身不提供 | 提供 |

UDP Socket 可以调用 `connect` 指定默认对端，但这不会产生 TCP 式的握手，也不会使 UDP 自动获得可靠传输能力。

## 6. 常见用途

UDP 常用于 DNS 查询、实时音视频、游戏状态更新等场景。应用可以根据需求容忍部分丢失，或实现重传、排序和发送速率控制。

QUIC 也基于 UDP，并在上层提供可靠传输、加密和拥塞控制，HTTP/3 使用 QUIC。基于 UDP 的应用仍需合理控制发送速率，避免持续向网络注入过量数据。
