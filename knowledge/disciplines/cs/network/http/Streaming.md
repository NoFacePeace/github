# HTTP 流式传输

HTTP 流式传输指发送方逐步发送报文内容，接收方在完整报文体到齐前读取并处理已到达的数据。它不要求使用某个固定的 Content-Type，也不等于某一种传输编码。

## 1. 流式与内容长度

流式描述数据如何发送和处理，内容长度描述数据总量，两者不冲突。

- 长度已知：例如发送已有文件，可以通过 [Content-Length](headers/ContentLength.md) 声明大小，同时分批读取文件、发送数据，客户端边接收边写入磁盘。
- 长度未知：例如模型生成内容或持续事件推送，通常不声明 Content-Length，通过协议的其他机制标记响应结束。

即使声明了 100 万字节的长度，客户端收到前 1000 字节时也可以读取；长度只说明何时收齐，不要求收齐后才能处理。

## 2. 不同版本的响应结束方式

| 场景 | 如何判断响应体结束 | 能否流式处理 |
|---|---|---|
| HTTP/1.1，长度已知 | 收够 Content-Length 指定的字节数 | 可以 |
| HTTP/1.1，长度未知且采用 chunked | 收到分块编码的结束标记 | 可以 |
| HTTP/1.1，通过连接关闭界定响应 | 连接关闭 | 可以，但无法复用该连接 |
| HTTP/2、HTTP/3 | 各自的流结束机制 | 可以，不使用 chunked |

HTTP/1.1 下，总长度未知且希望保留连接供后续请求使用的流式响应，通常采用 [Transfer-Encoding: chunked](headers/TransferEncoding.md)。HTTP/2、HTTP/3 不需要设置该首部。

使用关闭连接界定响应结束时，客户端难以仅凭连接关闭区分正常完成与意外截断。需要确认业务完整性时，还应设计完成事件等应用层标记。

## 3. 与持久连接的区别

[HTTP Keep-Alive](headers/KeepAlive.md) 允许复用同一连接完成多次请求与响应。流式响应是在一次响应尚未结束时，逐步发送并消费响应体。

连接可以保持打开，但当前响应已经结束；也可以在发送一个流式响应后关闭连接。因此，启用持久连接不等于启用流式推送，单纯不关闭连接也不会自动产生数据。

## 4. 及时交付的条件

- 服务端保持当前响应未结束，有新内容时写入，并根据框架需要刷新输出缓冲区（flush）。
- 反向代理和网关不长期缓存响应，压缩等中间处理也不应导致明显积压。
- 客户端使用流读取接口；调用等待整个响应体完成的方法，仍会表现为最后一次性得到结果。
- 检查空闲超时；在需要时使用应用层心跳，但心跳不能保证绕过所有超时或连接故障。

通常由服务端框架根据 HTTP 版本和响应方式处理报文分帧，无需手动拼接 chunked 编码。flush 也不保证一次写入就对应客户端的一次读取。

## 5. 传输块与消息边界

SSE、NDJSON 是响应体中的应用数据格式；chunked 是 HTTP/1.1 的传输编码；HTTP/2、HTTP/3 使用各自的帧机制。它们解决的问题不同。

一条应用消息可能分散在多个传输块中，一个传输块也可能包含多条消息。客户端应先处理字节流和文本解码，再按应用格式识别事件或记录，不能把一次读取当作一条消息。
