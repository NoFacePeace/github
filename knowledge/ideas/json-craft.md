# JsonCraft

## 1. 产品构想

一个通过自然语言动态修改 JSON 数据及结构的 Agent。用户描述修改意图，Agent 读取当前文档，生成 JSON Patch，由工具执行字段和数组的增删改，并提供差异查看、变更历史与回滚能力。

项目名称暂定为 **JsonCraft**，表示塑造 JSON 结构；代码中的 Agent 可命名为 `JsonPatchAgent`。

## 2. 核心能力

- 字段操作：新增、修改、删除字段，包括嵌套对象中的字段。
- 数组操作：修改、插入、追加、删除元素，以及调整顺序。
- 结构调整：新增嵌套对象、移动字段、替换子树。
- 变更查看：展示修改前后的字段值和结构差异。
- 历史管理：记录每次修改，支持比较版本和恢复历史内容。
- Tag 与行为：给集合、对象或字段添加 tag，支持按 tag 查找目标、按路径查询 tag，并通过处理器实现提醒等能力。

## 3. 统一更新工具

使用 JSON Patch（RFC 6902）表达修改，通过一个工具统一执行：

```text
update_json(document_id, expected_version, operations)
```

示例：修改标题、修改数组元素、插入元素并删除元素。

```json
{
  "document_id": "demo",
  "expected_version": 3,
  "operations": [
    {"op": "replace", "path": "/title", "value": "新标题"},
    {"op": "replace", "path": "/members/1/role", "value": "admin"},
    {"op": "add", "path": "/members/1", "value": {"id": "u3", "role": "viewer"}},
    {"op": "remove", "path": "/members/0"}
  ]
}
```

- 支持 `add`、`replace`、`remove`、`move`、`copy`、`test`。
- 路径使用 JSON Pointer（RFC 6901），例如 `/members/1/role`；字段名中的 `~` 和 `/` 分别转义为 `~0` 和 `~1`。
- 数组下标从 `0` 开始；`add` 在指定下标前插入，路径以 `/-` 结尾表示追加。
- 操作按顺序执行，后续下标基于前面操作完成后的数组。
- `replace`、`remove` 的目标必须存在；`add` 的父路径必须存在。
- 任意操作失败，整批修改不保存。

## 4. 执行与校验

```text
用户描述修改意图
    ↓
Agent 读取当前 JSON 和版本
    ↓
Agent 调用 update_json，提交 JSON Patch
    ↓
工具检查参数、权限和预期版本
    ↓
在副本上应用 Patch，校验最终数据
    ↓
事务内按预期版本更新文档，并保存变更记录
    ↓
返回新版本和实际差异
```

JSON 和 JSON Patch 本身不要求业务 Schema。工具参数 Schema 描述操作格式；最终数据则可以通过 JSON Schema，或结构体的严格反序列化与业务规则校验。

如果结构允许自由扩展，可以只校验基础约束；如果必须符合已有结构体，则需约束字段类型、必填字段和未知字段。修改文档结构与修改约束它的 Schema 应明确区分。

版本检查必须包含最终保存时的条件更新，避免读取后发生的并发修改被覆盖。版本冲突时，Agent 重新读取数据并重新生成操作。

## 5. 存储与历史

可以使用 MySQL，无需因为存储 JSON 而专门更换数据库。JSON Patch 的应用在程序中完成，MySQL 负责 JSON 存储和事务。

| 表 | 主要内容 |
|---|---|
| `documents` | 文档 ID、当前 JSON、版本号、更新时间 |
| `document_changes` | 文档 ID、变更前后版本、JSON Patch、历史快照、修改人、修改时间 |

文档更新和历史记录在同一个事务内提交。初期可以保存每次修改前后的完整 JSON，方便查看差异和恢复；数据规模增大后，再考虑定期快照加 Patch 重放。

正向 Patch 不一定包含被删除或覆盖的旧值，不能直接作为回滚依据。回滚时读取目标历史内容，并以一次新的、有版本检查的更新保存，保留回滚操作本身的历史。

ZK 更适合少量协调数据和配置，不提供按版本查询历史 JSON 的接口，因此不作为这个方案的默认文档存储。

## 6. 差异展示

根据修改前后的实际 JSON 生成 diff，展示新增、删除和修改的字段，以及旧值和新值。Agent 提交的 Patch 作为操作记录保留，实际数据 diff 用于展示最终变化。

前端可以使用 `jsondiffpatch` 等库展示嵌套对象和数组差异。对象数组尽量使用稳定 ID 匹配元素，减少插入和排序产生的无关差异；执行标准 JSON Patch 时仍使用路径下标，并通过版本检查保证基准一致。

## 7. Tag 与稳定标识

### 7.1 身份、名称和路径

集合、对象或字段都可以关联 tag。为需要长期关联的目标分配稳定 ID，名称用于展示，路径表示它在当前 JSON 中的位置。

| 信息 | 用途 | 变化规则 |
|---|---|---|
| `target_id` | 标识集合、对象或字段 | 创建时生成，改名、移动时不变 |
| `name` | 展示名称 | 可以修改 |
| `path` | 当前 JSON Pointer 路径 | 移动或字段改名时更新 |
| `tags` | 分类和声明能力 | 可添加、移除，一个目标可以有多个 tag |

稳定 ID 由工具生成和维护。复制目标时分配新 ID，移动时保留 ID；同一路径删除后重新创建的目标默认使用新 ID，避免继承旧提醒。

对象和集合可以使用 ID 作为 JSON key；固定字段仍使用 `title`、`due_at` 等名称。需要支持字段任意改名且保留关联时，也为字段分配 ID，由元数据记录其当前路径。业务数据无需全部包装为 `value` 对象。

稳定 ID 不代表层级路径永远不变：对象移入其他集合后，完整路径仍然会变化。因此长期关联使用 ID，路径作为可更新的位置索引。

### 7.2 数据与元数据

元数据与业务数据分开存放。以下示例中，所有路径相对于 `data`：

```json
{
  "data": {
    "collections": {
      "col_001": {
        "name": "工作事项",
        "items": {
          "task_001": {
            "title": "提交报告",
            "due_at": "2026-10-23T18:00:00+08:00",
            "status": "pending"
          }
        },
        "item_order": ["task_001"]
      }
    }
  },
  "metadata": {
    "col_001": {
      "kind": "collection",
      "path": "/collections/col_001",
      "tags": ["task_collection"]
    },
    "task_001": {
      "kind": "object",
      "path": "/collections/col_001/items/task_001",
      "tags": ["task"]
    },
    "field_001": {
      "kind": "field",
      "path": "/collections/col_001/items/task_001/due_at",
      "tags": ["datetime", "remindable"]
    }
  }
}
```

`metadata` 的 key 是稳定 ID，形成“ID → 当前路径和 tag”的映射。额外建立“路径 → ID”索引后，就能按路径定位元数据，无需每次递归查找业务数据。

有序集合可以使用“ID → 对象”的映射保存内容，再用 `item_order` 数组维护顺序；保存时校验顺序 ID 存在、无重复且覆盖应展示的对象。简单列表仍可使用数组。

如果保留对象数组，标准 JSON Pointer 仍使用下标，不能把 ID 直接写在数组下标的位置。数组插入、删除、移动后，工具必须同步更新受影响的路径索引。

### 7.3 双向查询

支持两种查询：按 tag 返回关联目标及当前路径；按路径返回目标的全部 tag。

MySQL 可以使用以下表结构组织元数据和关联关系：

| 表 | 主要内容与索引 |
|---|---|
| `field_metadata` | `document_id`、`target_id`、`kind`、`path`、配置；唯一键为文档和目标 ID，另对文档和路径建立唯一索引 |
| `field_tags` | `document_id`、`target_id`、`tag`；主键为文档、目标 ID 和 tag，另建文档、tag 和目标 ID 的索引 |

这里 `field_metadata` 统一包含集合、对象和字段的元数据，以 `kind` 区分目标类型。

```text
按 tag 查询：document_id + tag → target_id → 当前路径和数据
按路径查询：document_id + path → target_id → tags
```

路径和 tag 使用区分大小写的比较规则。JSON 文档、元数据、tag 关联及历史在同一事务内维护；对外展示的元数据和数据库索引来自同一份逻辑数据，不分别独立编辑。

### 7.4 更新与行为处理

Tag 本身只是声明，实际行为由注册的处理器执行，例如 `remindable` 对应提醒处理器。行为配置需要有明确的 Schema，不能仅根据任意字段名猜测行为。

继续通过统一更新工具修改数据与元数据，工具依据修改前后的最终状态同步索引和行为。即使 Agent 整体替换集合或子树，也要识别目标和 tag 的实际变化。

- 新增目标：分配 ID，建立路径和 tag 索引。
- 改名或移动：保留 ID，更新目标及其后代的路径。
- 删除目标：移除其元数据和 tag 关联，并取消关联任务。
- 添加、移除 tag 或修改配置：通知对应处理器重新计算行为。
- 整体替换：通过受管理的 ID 判断保留、新增和删除；身份无法确定时，不自动继承旧关联。

首次导入任意 JSON 时可以递归扫描建立索引，后续根据受影响子树增量维护；无法可靠确定影响范围时，重建索引。所有索引都必须与最终文档状态一致。

## 8. 子项提醒规则

### 8.1 集合配置与触发范围

支持在集合上配置一份规则，让子项分别触发提醒，集合本身不提醒，也不需要把规则复制到每个子项。

```json
{
  "id": "rule_001",
  "target_id": "col_001",
  "scope": "children",
  "match_tags": ["task"],
  "trigger": {
    "field": "/due_at",
    "offset_seconds": -3600,
    "timezone": "Asia/Shanghai"
  },
  "channel": "push",
  "enabled": true
}
```

这里 `children` 表示集合的业务子项，即示例中的 `items` 成员，不是任意 JSON 直接子字段。集合类型明确规定如何枚举子项；`field` 是相对于每个子项的 JSON Pointer。`match_tags` 要求子项包含指定的全部 tag。

规则表示：为工作事项集合中带 `task` tag、状态未完成且具有有效 `due_at` 的子项，在截止前一小时生成提醒。缺少时间的子项不生成任务，无效时间返回配置或数据错误；状态字段及完成条件由事项类型约定。

如需单独提醒某个对象，可以使用 `scope: "self"`；如需递归作用于后代，可以显式扩展 `descendants` 范围。集合规则默认不隐式传播到所有后代。

### 8.2 调度与生命周期

```text
统一工具保存 JSON、规则和变更事件
    ↓
后台处理器按规则枚举符合条件的子项
    ↓
计算各子项的触发时间，同步调度任务
    ↓
到期前再次检查规则、子项状态和任务版本
    ↓
发送通知并记录结果
```

JSON 保存和调度变更事件写入同一 MySQL 事务，通过 outbox 机制可靠驱动后台同步。初版使用 `reminder_jobs` 表和后台轮询领取到期任务，精度取决于轮询间隔。

| 变化 | 调度动作 |
|---|---|
| 新增或移入符合条件的子项 | 创建提醒 |
| 修改截止时间 | 重新安排提醒 |
| 完成、删除、移出子项或移除匹配 tag | 取消待发送提醒 |
| 修改规则 | 重新计算受影响的任务 |
| 禁用、删除规则或删除集合 | 取消该规则的待发送任务 |

任务以“文档 ID + 规则 ID + 子项 ID + 触发批次”建立唯一约束，重复处理事件不会创建重复任务。改期时使旧任务失效，执行时再次校验；通知渠道支持时传递幂等键，降低重试造成重复提醒的风险。

## 9. 待探索问题

- 面向任意 JSON，还是限定某类业务文档和 Schema？
- 哪些变更直接执行，哪些需要先展示 diff 再由用户确认？
- JSON 较大时，如何只向 Agent 提供相关子树及其路径？
- 是否需要给对象数组提供按稳定 ID 定位的辅助能力？
- 结构变化后，如何处理已有消费者、业务约束和数据迁移？
- 子项同时命中集合规则和独立提醒时，如何合并或保留两条提醒？
- 触发时间已过去时，选择跳过、补发还是由用户指定？
